### lscpu 里的三个数

Tutorial 1 的第一题让学生在 lab cluster 的一个 node（`soctf-pdc-001`）上跑 `lscpu`。和这一站有关的几行是：

| 字段 | 值 |
|---|---|
| Model name | Intel Xeon Silver 4114 @ 2.20GHz |
| CPU(s) | 20 |
| Socket(s) | 1 |
| Core(s) per socket | 10 |
| Thread(s) per core | 2 |
| L1d / L2 / L3 | 320 KiB / 10 MiB / 13.8 MiB |
| NUMA node(s) | 1 |

Socket 是主板上插一块 processor package 的位置；一块 package 里有 10 个 core，每个 core 有自己的 execution unit；每个 core 又能同时挂 2 个 hardware thread。OS 看到、能 schedule thread 上去的单位是 hardware thread，`lscpu` 把它叫做 CPU，所以

$$\text{CPU(s)}=\text{sockets}\times\text{cores per socket}\times\text{threads per core}=1\times10\times2=20$$

Cache 的大小是整块 chip 加起来的：L1d 的 320 KiB 是 10 个 core 各 32 KiB，L2 的 10 MiB 是每个 core 各 1 MiB，L3 的 13.8 MiB 是 10 个 core 共用的一块。这就是 cheatsheet 里说的 hierarchical design：每个 core 私有 L1、L2，往上共享 L3，再往上共享 memory。

20 个 CPU 里只有 10 套 execution unit。这件事要先弄清楚每个 core 里 thread 是怎样共享 hardware 的。

### 四层 parallelism

一个 processor 同时做几件事，可以发生在四个层次上。

**Bit-level。** 一条 instruction 处理多少个 bit。在 32-bit 的 machine 上把两个 128-bit 的 integer 相加，要 4 次 32-bit 的 add，后三次还要带上前一次的 carry；在 64-bit 的 machine 上是 2 次。Word 的宽度从 4 bit 一路加到 64 bit，之后再加宽就没有多少程序用得上了。

**Instruction-level（ILP）。** 一个 instruction stream 里互不依赖的 instruction 同时执行。Pipelining 让不同 instruction 同时处在不同的 stage（[CS2100 第 7 站](../courses/CS2100.html#pipe)），是时间上的 parallelism；superscalar 让好几条 instruction 在同一个 cycle 进入同一个 stage，是空间上的 parallelism。两者都受同一个限制：instruction 之间有 dependency，一个 stream 里同时 ready 的 instruction 不多，[CS149 第 1 站](../courses/STANFORD-CS149.html#core)给了 4-issue 之后收益很小的例子。

**Thread-level（TLP）。** 一个 core 上挂好几个 thread 的 context（PC、register），在它们之间切换或同时取 instruction，用别的 thread 填上一个 thread 等 memory 时留下的空。下一节专门讲。

**Processor-level。** 多放几个 core，每个 core 是一个独立的 logical processor，有自己的 functional unit 和 pipeline。前三层都在榨一个 core，这一层直接复制 core。

### 同一个 core 上的几个 thread

设一个 core 每个 cycle 最多 issue 4 条 instruction（4 个 issue slot）。两个 thread A、B 的 instruction stream 写成一串 group：数字是这一组里互不依赖、可以同一个 cycle 发出的 instruction 数，“停 $k$”是一次 cache miss，要等 $k$ 个 cycle：

- A：3，1，停 3，2，4，1，停 2，3
- B：2，2，1，停 3，3，1，2，2

在 8 个 cycle 里一共有 $8\times4=32$ 个 slot。下面四种 hardware 各填满了多少：

- **只有 A（superscalar，无 multithreading）。** 第 0、1 个 cycle 发出 3 条、1 条，接着停 3 个 cycle，之后 2、4、1 条。用掉 $3+1+2+4+1=11$ 个 slot。
- **Fine-grained multithreading。** 每个 cycle 换一个 thread，正在等 miss 的 thread 跳过。每个 cycle 只从一个 thread 取 instruction，所以同一个 cycle 里 A 的空位不能给 B 用。用掉 15 个。
- **Coarse-grained multithreading。** 一直跑 A，A 遇到 miss 才换到 B（switch-on-event），B 遇到 miss 再换回去。用掉 16 个。
- **Simultaneous multithreading（SMT）。** 每个 cycle 先放 A 的 instruction，剩下的 slot 给 B。用掉 19 个。

::fig[cs3210-slots] 横向是 4 个 issue slot，纵向是 8 个 cycle，深色是 A 的 instruction，浅色是 B 的。前三种每个 cycle 只来自一个 thread；SMT 一行里可以两种颜色都有。

前两种 multithreading 只填竖着的空（整个 cycle 都空着的那几行），SMT 连横着的空（一行里没用完的 slot）也填。代价是 SMT 要能在同一个 cycle 里从两个 context 取 instruction、分别 rename register；Intel 叫它 hyper-threading，`Thread(s) per core: 2` 就是它。

SMT 复制的是 context：PC、register、几张记录 instruction 属于谁的表。ALU、load/store unit、L1、L2 都没有复制，两个 thread 分着用。所以一个 thread 自己就能把 slot 填满时，第二个 thread 几乎没有好处。

:::wrong lscpu 显示 20 个 CPU，所以开 20 个 thread 就能快 20 倍

| 8 | 1.451 | 7.8 | $2.88\times10^{10}$ | 2.21 | $4.38\times10^{10}$ |
| 16 | 1.340 | 13.3 | $4.35\times10^{10}$ | 1.46 | $4.75\times10^{10}$ |

### Flynn's taxonomy：一条 instruction 管几份 data

拿一个 loop 来看 hardware 的分类：`for (i = 0; i < n; i++) c[i] = a[i] + b[i];`。

- **SISD**（single instruction stream, single data stream）：一个 core、不用 vector instruction，每条 add 加一对数，$n$ 次 add。
- **SIMD**（single instruction, multiple data）：一条 instruction 同时作用在一排 data 上。上面 `lscpu` 的 flags 里有 `avx512f`，一条 512-bit 的 `vaddps` 一次加 16 个 float，$n$ 个数只要 $n/16$ 条。分支要靠 mask，两边都走（[CS149 第 1 站](../courses/STANFORD-CS149.html#core)）。
- **MIMD**（multiple instruction, multiple data）：10 个 core 各有自己的 PC，各自跑一段 loop，可以在不同的地方 branch。今天的 multicore、cluster 都是 MIMD，而且每个 core 内部还有 SIMD。
- **MISD**：多个 instruction stream 作用在同一份 data 上，没有真正通用的实现；cheatsheet 和 LLNL 的 tutorial 都只举出 systolic array 或“同一个 signal 过几个不同的 filter”这类说法。

GPU 的 SIMT 介于 SIMD 和 MIMD 之间：程序按一个个 scalar thread 写，hardware 把 32 个 thread 捆成一个 warp 用 SIMD 的方式执行（第 6 站）。

Flynn 只回答 instruction 和 data 的关系，不回答一个 core 怎样拿到另一个 core 算出来的数。这要看 memory 怎样组织。

### Memory 的组织：distributed、UMA、NUMA

**Distributed memory。** 每个 node 有自己的 processor 和 memory，node 之间只有 network。一个 node 不能用 load instruction 读另一个 node 的 memory，只能请对方把 data 用 message 发过来。Lab 用的 Slurm cluster 就是这样：`soctf-pdc-005` 到 `024` 是一台台独立的机器（Tutorial 1 的 `sinfo`）。好处是 memory 和 processor 一起扩展、每个 node 访问本地 memory 很快；代价是 data 放在哪、什么时候发，全部由程序员决定（第 8 站）。

**Shared memory。** 所有 processor 看到同一个 address space，任何一个 processor 都能 load 任何一个 address。按访问 memory 的时间是否一样，再分两种：

- **UMA**（uniform memory access）：所有 processor 经过同一条 bus 或同一个 crossbar 访问 memory，latency 一样。Processor 一多，大家抢同一条路，所以只适合少数几个 processor。上面那台单 socket 的 Xeon（`NUMA node(s): 1`）对它的 10 个 core 来说就是 UMA。
- **NUMA**（non-uniform memory access）：每个 socket 有自己挂着的 memory，访问别的 socket 的 memory 要经过 socket 之间的 interconnect，更慢。[CS149 第 6 站](../courses/STANFORD-CS149.html#coherence)的 Xeon 5500 数字：本地 DRAM 约 30 ns，另一个 socket 的 DRAM 约 100 ns。一个 thread 的 DRAM access 如果一半落在对面 socket，平均是 $0.5\times30+0.5\times100=65$ ns，比全部本地慢 $65/30=2.2$ 倍。

每个 processor 有 cache、hardware 负责让各 cache 一致的 NUMA 叫 ccNUMA，这是今天多 socket server 的标准做法，一致性怎样维护是第 5 站。COMA（cache-only memory access）把每个 node 的 memory 本身当成 cache，data 按访问需要在 node 之间迁移，没有固定的“家”。

::fig[cs3210-memorg] 左：distributed memory，node 之间只有 network。中：UMA，所有 processor 经过同一条 bus 到同一块 memory。右：NUMA，每个 socket 有本地 memory，虚线箭头是一次经过 socket 之间连线的 remote access，更慢。

真实的 cluster 是两者的组合（hybrid）：node 内部是 shared memory，node 之间是 distributed memory。所以同一门课里既有 OpenMP 又有 MPI：node 内部用 thread 共享 data，node 之间用 message。

:::edge Data 第一次被谁碰，就住在谁那里
在 Linux 上，一个 page 第一次被写时才真正分配 physical memory，而且分在执行这次写的 thread 所在的 NUMA node（first-touch policy）。如果一个 array 由 main thread 用一个 serial loop 初始化，再交给 16 个 thread 去算，所有 page 都在 main thread 那个 socket 上，另一个 socket 的 8 个 thread 每次 miss 都是 remote access。常见的修法是用和计算时相同的 parallel loop 去初始化。这一条是凭我自己的知识写的，cheatsheet 和读过的材料里没有。
:::

## [shm] Shared-memory programming：Pthreads 与 OpenMP

:::skip

### Process 还是 thread

Lab 1 的第一部分把同一件事分别用 process 和 thread 做一遍。Process 之间默认什么都不共享：`fork` 出来的 child 有一份自己的 address space，要交换 data 只能另开 shared memory segment 或者通过 OS 发 message（IPC）。Thread 属于同一个 process，共享 code、global variable 和 heap，只各自有 stack 和 register。创建 thread 不复制 address space，所以比创建 process 便宜得多，交换 data 也只是读写同一个 address。

代价是 thread 之间的每一次共享都可能是 race。Lab 1 Exercise 2 让很多 thread 对同一个 `counter` 做 `counter++`，每次跑出来的最终值都不一样，原因是一行 `counter++` 在 machine 上是 load、add、store 三步，两个 thread 的三步交错时一次加法会丢失（[CS2106 第 3 站](../courses/CS2106.html#race)逐条 instruction 走过这件事）。User-level thread 与 kernel thread、many-to-one 和 one-to-one 的 mapping 也在那一站。

### Pthreads：fork-join 写出来

Pthreads 的程序就是 fork-join：main thread 用 `pthread_create` 创建几个 child，各自执行一个 function，main thread 用 `pthread_join` 等它们结束。Lab 1 的 Exercise 3 到 5 一步步修一个 counter：

```c
#include <pthread.h>
#include <stdio.h>
#define NUM_THREADS 8
long counter = 0;
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

void *work(void *arg) {
    for (int i = 0; i < 100000; i++) {
        pthread_mutex_lock(&lock);      // Exercise 5：critical section 只有这一行
        counter++;
        pthread_mutex_unlock(&lock);
    }
    return NULL;
}

int main(void) {
    pthread_t t[NUM_THREADS];
    for (int i = 0; i < NUM_THREADS; i++) pthread_create(&t[i], NULL, work, NULL);
    for (int i = 0; i < NUM_THREADS; i++) pthread_join(t[i], NULL);   // Exercise 4
    printf("%ld\n", counter);           // 一定是 800000
}
```

两个修正对应两个不同的错误。没有 `pthread_join` 时（Exercise 3），main thread 打印的时候 child 可能还没跑完，打出来的数偏小，这和 race 无关，是 main thread 没等。加了 join 但没有 mutex 时（Exercise 4），打印时 child 都结束了，结果仍然不对，这才是 race。Mutex 和 semaphore、condition variable 的用法见 [CS2106 第 4 站](../courses/CS2106.html#sema)。

### OpenMP：让 compiler 写 fork-join

Pthreads 每次都要手写“把 $n$ 个 iteration 切成几段、每段交给谁、最后 join”。OpenMP 用一行 compiler directive 代替这些：

```c
#pragma omp parallel for shared(a, b, result) private(i, j, k)
for (i = 0; i < size; i++)
    for (j = 0; j < size; j++)
        for (k = 0; k < size; k++)
            result.element[i][j] += a.element[i][k] * b.element[k][j];
```

这是 Lab 2 的 `mm-omp.c`。`#pragma omp parallel` 在这里 fork 出一组 thread（team），`for` 把外层 $i$ 的 iteration 分给它们，loop 结束处有一个隐含的 barrier，所有 thread 到齐之后 team 结束，只剩 main thread 往下走。Thread 数由 `omp_set_num_threads` 或 environment variable `OMP_NUM_THREADS` 决定。

每个 variable 要么所有 thread 共用一份（shared），要么每个 thread 一份（private）。规则是：Parallel region 之前声明的 variable 默认 shared，region 里面声明的是 private，被 `omp for` 切分的那个 loop index 自动 private。所以这段 code 里如果漏写 `private(j, k)`，$j$、$k$ 在 function 开头声明，默认 shared，8 个 thread 共用同一个 $j$ 和 $k$ 做内层 loop，结果全乱。在 parallel region 里面声明（`for (int j = 0; ...)`）就不会有这个问题。

### schedule：iteration 怎样分给 thread

`parallel for` 默认（对多数 implementation 而言）把 iteration 平均切成连续的几块。每个 iteration 的 cost 一样时这最好：零运行时 overhead，每个 thread 访问连续的 data。Cost 不一样时就不行了。看一个上三角的 loop：

```c
#pragma omp parallel for schedule(...)
for (int i = 0; i < 16; i++)
    for (int j = i; j < 16; j++)
        work(i, j);            // 第 i 个 iteration 做 16 - i 次 work
```

16 个 iteration 的 cost 是 16、15、……、1，总共 $\sum_{i=0}^{15}(16-i)=136$ 份。4 个 thread 时理想的完成时间是 $136/4=34$。四种 schedule：

- `schedule(static)`：切成 4 块连续的，thread 0 拿 0 到 3，cost $16+15+14+13=58$；thread 3 拿 12 到 15，cost $4+3+2+1=10$。完成时间是最慢的那个，58。
- `schedule(static, 1)`：chunk 大小 1，轮流发：thread $t$ 拿 $t,\,t+4,\,t+8,\,t+12$。Thread 0 是 $16+12+8+4=40$，thread 3 是 $13+9+5+1=28$，完成时间 40。
- `schedule(dynamic, 1)`：运行时每个 thread 做完一个 chunk 就去领下一个。前 4 个 iteration 同时开始，thread 3 拿到的 iteration 3 最便宜（13），最先做完，去领 iteration 4；如此下去，四个 thread 都在 34 结束，正好是理想值。
- `schedule(guided)`：也是动态领，但 chunk 一开始大、越来越小，每次领 $\lceil\text{剩余}/\text{thread 数}\rceil$ 个：4、3、3、2、1、1、1、1。偏偏第一块的 4 个 iteration 是最贵的，thread 0 一领就是 58，完成时间 58。

::fig[cs3210-sched] 同一个上三角 loop 在 4 个 thread 上的四种 schedule。每个色块是一个 chunk，宽度是它的 cost，竖线是理想的 34。

Dynamic 的代价是每领一次 chunk 都要和其他 thread synchronize 一次（一个 shared 的 counter），chunk 越小次数越多；guided 用逐渐变小的 chunk 减少领取次数，它默认的假设是 iteration 的 cost 差不多，这个例子正好违反了它。`schedule(runtime)` 把选择推迟到运行时，从 `OMP_SCHEDULE` 读；`schedule(auto)` 让 runtime 自己决定。[CS149 第 3 站](../courses/STANFORD-CS149.html#work)从 Mandelbrot 的角度讲了同一个取舍和 work stealing。

### 对同一个 sum 的四种写法

Mattson 的 OpenMP tutorial 用 $\int_0^1\frac{4}{1+x^2}\,dx=\pi$ 做例子：把 $[0,1]$ 切成 `num_steps` 个小矩形，每个矩形的高取中点的函数值。

```c
static long num_steps = 100000000;
double step = 1.0 / (double) num_steps, sum = 0.0;
for (int i = 0; i < num_steps; i++) {
    double x = (i + 0.5) * step;
    sum = sum + 4.0 / (1.0 + x * x);
}
double pi = step * sum;
```

所有 iteration 都在加同一个 `sum`，直接加 `parallel for` 就是 Lab 1 的 race。Tutorial 依次给了四种写法：

1. **SPMD，`sum[id]`**：每个 thread 用 `omp_get_thread_num()` 得到自己的 `id`，只加 `sum[id]`，最后由一个 thread 把 `sum[0..n-1]` 加起来。
2. **SPMD，padding**：同上，但把 `sum` 声明成 `double sum[NUM_THREADS][8]`，每个 thread 只用 `sum[id][0]`。
3. **SPMD，critical**：每个 thread 加一个 private 的局部 `sum`，最后用 `#pragma omp critical` 保护 `pi += sum * step` 这一行。
4. **`parallel for reduction(+:sum)`**：每个 thread 自动得到一个初值为 0 的 private `sum`，loop 结束时 OpenMP 把它们加到外面的 `sum` 上。

Tutorial 的实测（dual-core Core i5，4 个 hardware thread，Intel compiler，不开 optimization）：

| thread 数 | sum[id] | padding | critical | reduction |
|---|---|---|---|---|
| 1 | 1.86 | 1.86 | 1.87 | 1.91 |
| 2 | 1.03 | 1.01 | 1.00 | 1.02 |
| 3 | 1.08 | 0.69 | 0.68 | 0.80 |
| 4 | 0.97 | 0.53 | 0.53 | 0.68 |

第一种从 2 个 thread 到 4 个几乎没有变快：$1.86/0.97=1.9$ 倍，第二种是 $1.86/0.53=3.5$ 倍。两者做的计算一模一样，差别只是 `sum[0]` 到 `sum[3]` 挤在一条 64-byte 的 cache line 里，每个 thread 每加一次都要把这条 line 从别的 core 抢过来。这叫 false sharing，第 5 站和 [CS149 第 6 站](../courses/STANFORD-CS149.html#coherence)讲它在 coherence protocol 里是怎样发生的。padding 的 `[8]` 是 $8\times8=64$ byte，让每个 thread 的 sum 独占一条 line。Critical 版本同样快，因为每个 thread 只进 critical section 一次；如果把 `critical` 放在 loop 里面，每次加法都要排队，就比 serial 还慢。

`#pragma omp atomic` 是 critical 的特例：它只保护一条简单的 update（`x += expr` 一类），可以直接编成一条 atomic instruction，比通用的 critical section 便宜。

:::wrong 写了 private(tmp)，parallel region 里的 tmp 就从外面的值开始，结束后再写回去
Tutorial 里的例子：

```c
int tmp = 0;
#pragma omp parallel for private(tmp)
for (int j = 0; j < 1000; ++j)
    tmp += j;
printf("%d\n", tmp);
```

看起来是在算 $0+1+\cdots+999=499500$。实际上 `private` 给每个 thread 一个新的、没有初始化的 `tmp`，region 里每个 thread 从一个不确定的值开始加；region 结束后这些副本全部丢弃，外面那个 `tmp` 从头到尾没被碰过，打印出来是 0。想让副本从外面的值开始要写 `firstprivate(tmp)`；想要把各线程的结果合起来，要的其实是 `reduction(+:tmp)`。
:::

### Loop-carried dependence

`parallel for` 要求 iteration 之间没有依赖。Tutorial 的例子：

```c
int j = 5;
for (int i = 0; i < MAX; i++) {
    j += 2;
    A[i] = big(j);
}
```

第 $i$ 个 iteration 用的 $j$ 是第 $i-1$ 个 iteration 留下的，这叫 loop-carried dependence。直接 parallelize，不同 thread 读写同一个 $j$，顺序全乱。修法是把 $j$ 直接写成 $i$ 的 function：第 $i$ 个 iteration 之前 $j$ 已经被加了 $i+1$ 次 2，所以

```c
#pragma omp parallel for
for (int i = 0; i < MAX; i++) {
    int j = 5 + 2 * (i + 1);
    A[i] = big(j);
}
```

验算：$i=0$ 时原 loop 里 $j=5+2=7$，新写法 $5+2\times1=7$；$i=2$ 时原 loop 里 $j=5+2+2+2=11$，新写法 $5+2\times3=11$。这样每个 iteration 只读自己的 $i$，可以任意顺序执行。

:::back
`counter++` 为什么会丢、mutex 和 semaphore 怎样实现，依赖 [CS2106 第 3、4 站](../courses/CS2106.html#race)。False sharing 的机制在第 5 站。
:::

## [design] Parallel algorithm design：task graph、PCAM、data distribution 与 pattern

### Task dependence graph：最长的那条链

写 parallel program 之前先要知道问题本身允许多少 parallelism。把计算拆成 task，task 之间“必须先做完 A 才能开始 B”画成一条有向边，得到一个 directed acyclic graph，叫 task dependence graph。每个 node 标上它的执行时间。

::fig[cs3210-dag] 8 个 task，数字是执行时间。粗线是 critical path：T3 → T5 → T7 → T8。

Critical path 是从任一起点到任一终点、时间加起来最长的那条路。这张图里几条路是：

- T1 → T4 → T6 → T8：$4+2+3+1=10$
- T1 → T4 → T7 → T8：$4+2+2+1=9$
- T2 → T5 → T7 → T8：$2+5+2+1=10$
- T3 → T5 → T7 → T8：$3+5+2+1=11$

最长的是 11。不管有多少个 processor，T3、T5、T7、T8 只能一个接一个做，所以 $T_p\ge11$。另一个下限来自总工作量：所有 task 加起来 $W=4+2+3+2+5+3+2+1=22$，$p$ 个 processor 每个单位时间最多做 $p$ 份，$T_p\ge W/p$。合起来

$$T_p\ \ge\ \max\Big(\frac Wp,\ \text{critical path}\Big)$$

$W$ 除以 critical path 叫 average degree of concurrency，这里是 $22/11=2$：平均来说同时只有 2 个 task 能做，speedup 最多是 $W/\text{critical path}=2$。Maximum degree of concurrency 是某一时刻同时能做的 task 最多有几个，这里一开始 T1、T2、T3 都没有前驱，是 3。

$p=2$ 时下限是 $\max(11,11)=11$，但实际做不到 11。要在 11 结束，critical path 上的四个 task 必须一刻不停，占满一个 processor 的 0 到 11；剩下的 T1、T2、T4、T6 只能放在另一个 processor 上，它们一共 $4+2+2+3=11$，而 T8 在 10 就要开始，T6 必须在 10 之前做完，11 份工作塞不进 10 个单位的时间。最好的 schedule 是 12（例如一个 processor 做 T2、T1、T4、T6、T8，另一个做 T3、T5、T7）。下限只是下限，不同 task 的大小凑不整齐时达不到。

### Foster 的四步：partitioning、communication、agglomeration、mapping

Foster 的书给了一套设计顺序，简称 PCAM。前两步只管找出 parallelism，不考虑有几个 processor；后两步才回到具体的机器。用一个 2D stencil 走一遍，Foster 的 Jacobi 例子是每个 time step 把每个点更新成

$$X^{(t+1)}_{i,j}=\frac{4X^{(t)}_{i,j}+X^{(t)}_{i-1,j}+X^{(t)}_{i+1,j}+X^{(t)}_{i,j-1}+X^{(t)}_{i,j+1}}{8}$$

**Partitioning。** 把计算和 data 切成尽可能小的 task。先切 data、再把计算跟着 data 走，叫 domain decomposition；先切计算、再看每段计算要哪些 data，叫 functional decomposition（例如一个 signal 依次经过四个 filter，每个 filter 是一个 task）。Stencil 用 domain decomposition：一个点一个 task，$N\times N$ 个。Foster 的 checklist 问五件事：task 数是否至少比 processor 多一个数量级，有没有重复的计算和存储，task 的大小是否相近，task 数是否随问题变大而增长，有没有考虑过别的切法。

**Communication。** 每个 task 每一步要读上下左右四个邻居的旧值，所以要和 4 个 task 交换 data。这是 local（只和少数几个 task）、structured（规则的 grid）、static（伙伴固定）、synchronous（每一步双方都参与）的 communication。

Global communication 的例子是求和：$N$ 个 task 各有一个数，要得到总和。让一个 manager 逐个接收再加，要 $N-1$ 步，而且 manager 是 bottleneck；排成一条链逐个往下传，同样 $N-1$ 步。按 binary tree 两两相加，每一层的加法同时做，$N=8$ 时 $\log_28=3$ 步。Foster 对这一步的要求是：每个 task 的 communication 量差不多、每个 task 只和少数几个 task 通信、communication 之间能同时进行、计算之间能同时进行。

**Agglomeration。** 一个点一个 task 太细：每个 task 每一步只算一个点，却要发 4 个 message。把相邻的点合成一个大 task：

::fig[cs3210-agglom] 左：$8\times8$ 个 task，每个 task 每一步向 4 个邻居各发 1 个值。右：合成 $2\times2$ 个 task，每个 $4\times4$，只有边上的点需要发出去，每条边打包成一个 message。

设 grid 在四周是 wrap around 的，每个点都有 4 个邻居。左边每一步 $64\times4=256$ 个 message，共 256 个值；右边 4 个 task 各发 4 个 message，每个 message 装一条边的 4 个值，共 $4\times4=16$ 个 message、$16\times4=64$ 个值。值少了 4 倍，message 数少了 16 倍。Message 数更重要，因为每个 message 都有一个固定的 startup cost（第 8 站的 $\alpha$）。按 CS267 给的 GigE 上 MPI 的 $\alpha=5.854\ \mu$s、$\beta=0.00872\ \mu$s/byte，一个 processor 负责 $4\times4$ 的点时，每一步要送出去的：

- 不合并：边上 16 个值各一个 8-byte 的 message，$16\times(5.854+8\times0.00872)=94.8\ \mu$s；
- 合并：4 个 32-byte 的 message，$4\times(5.854+32\times0.00872)=24.5\ \mu$s。

送的 byte 一样多，时间差了将近 4 倍，全部来自 startup cost。

这背后是 surface-to-volume：一个 task 的计算量正比于它那块 subdomain 的“体积”（点数），communication 正比于它的“表面”（边上的点数）。$N\times N$ 的 grid 分给 $P$ 个 task，每个 task 的计算都是 $N^2/P$ 个点；communication 取决于怎样切：

- 1D：切成 $P$ 条，每条 $N\times N/P$，上下两条边各 $N$ 个值，每步 $2N$ 个；
- 2D：切成 $\sqrt P\times\sqrt P$ 块，每块 $(N/\sqrt P)^2$，四条边各 $N/\sqrt P$ 个值，每步 $4N/\sqrt P$ 个。

$N=1024$、$P=64$ 时，两种切法每个 task 都算 $1024^2/64=16384$ 个点；1D 每步发 2048 个值，2D 发 $4\times1024/8=512$ 个。所以 Foster 的结论是 higher-dimensional 的 decomposition 通常更好。

Agglomeration 有时故意重复计算来省 communication。求和之后每个 task 都要知道总和：先 tree 求和再 tree broadcast，$N=8$ 要 $3+3=6$ 步；改成 butterfly，第 $k$ 步每个 task 和编号只差第 $k$ 个 bit 的 task 交换并相加各自手上的部分和，3 步后每个 task 都有总和。每个 task 都做了加法，加法的总次数从 7 次变成 $8\times3=24$ 次，换来步数减半。这个 pattern 就是第 8 站的 hypercube all-reduce。

**Mapping。** 把 task 放到 processor 上，两个目标互相冲突：能同时做的 task 放在不同 processor 上以增加 parallelism，经常通信的 task 放在同一个 processor 上以增加 locality。一般情况下求最优 mapping 是 NP-complete。规则的问题直接按 domain 切（stencil 就是把每个 $4\times4$ 的 task 放在一个 processor 上）；每个 task 的工作量不均匀时，用 recursive bisection 把 domain 反复切成两个 cost 相等的半边，或者用 cyclic mapping 让每个 processor 拿到每隔 $P$ 个的 task（第 2 站的上三角 loop：Block 是 58，cyclic 是 40）；task 是运行中动态产生的，用 manager/worker 或每个 processor 一个 task pool。

### Data distribution

Data-parallel 的问题里，mapping 往往就是决定 array 的每个 element 归谁。1D array 的三种基本做法，以 16 个 element、4 个 process 为例：

- **Blockwise**：process $q$ 拿连续的一段，第 $4q$ 到 $4q+3$ 个。
- **Cyclic**：element $i$ 归 process $i\bmod4$。
- **Block-cyclic**：先切成大小为 $b$ 的 block，再把 block 轮流发；$b=2$ 时 process 0 拿 0、1、8、9。

二维的 $n\times n$ matrix 可以对 row 用上面任何一种（每个 process 拿若干整行），也可以两个方向都切：把 process 排成 $2\times2$ 的 grid，matrix 切成 $2\times2$ 块，叫 checkerboard（blockwise）；两个方向都 block-cyclic，叫 2D block-cyclic。

::fig[cs3210-dist] 颜色表示 element 归哪个 process。上面一行是 16 个 element 的三种1D 分法，下面是 $8\times8$ matrix 的 row blockwise、checkerboard 和 $2\times2$ block 的 2D block-cyclic。

选哪一种取决于两件事。一是 load balance：工作量随位置变化时（上三角 loop、LU factorization 里越来越小的 active submatrix），blockwise 会让一些 process 早早没事做，cyclic 让每个 process 都均匀地拿到轻的和重的部分。二是 locality：stencil 要读邻居，blockwise 和 checkerboard 让邻居大多在同一个 process 里；cyclic 恰好让每个点的左右邻居都在别的 process，每一个点都要通信。Block-cyclic 在两者之间折中，block 越大越接近 blockwise。

### Parallel programming pattern

几种程序结构在这门课的 lab 里反复出现，区别在于谁创建 parallel 的工作、synchronization 落在哪里。

- **Fork-join**：一个 thread 用 fork 创建几个 child，自己也可以参与，最后用 join 等它们全部结束。第 2 站的 Pthreads 和 OpenMP 的 parallel region 都是。Synchronization 在 join。
- **Parbegin-parend**：写出一组语句，执行到这个结构时每条语句交给一个 thread，全部完成后才执行后面的语句。OpenMP 的 `sections` 就是它。它是 fork-join 的一种结构化写法，synchronization 在 parend。
- **SPMD**：所有 thread 或 process 跑同一个程序，靠自己的 rank 或 id 决定处理哪一部分 data，彼此 asynchronously 执行，需要时用显式的 synchronization（barrier、message）。第 2 站 pi 程序的 SPMD 版本、第 8 站所有的 MPI 程序都是。
- **Master-worker**：一个 master 负责分配工作、收集结果，worker 只算。开头第四次实验那个 rank 0 逐个发 data 的 broadcast 就是 master 在发；master 本身容易成为 bottleneck。
- **Client-server**：一个 server 同时响应多个 client 的请求，各方跑不同的程序（MPMD），常见于 cloud 和 heterogeneous system。
- **Task pool**：固定数量的 thread 从一个共享的 pool 里取 task，执行时可以产生新 task 放回 pool。对 pool 的访问要 synchronize。程序结束的条件有两个：pool 空了，而且每个 thread 都做完了手上的最后一个 task；只看前一个不够，因为正在执行的 task 可能还会往 pool 里放新 task。适合工作量不规则、运行时才产生的问题；task 太小时取放 task 的 overhead 占主导。[CS149 第 3 站](../courses/STANFORD-CS149.html#work)讲了把一个 pool 换成每个 thread 一个 deque 的 work stealing。
- **Producer-consumer**：producer 产生 data 放进 buffer，consumer 取出来用，buffer 满了 producer 等、空了 consumer 等。Lab 1 的 `prod-con-threads.c` 和 `prod-con-processes.c` 分别用 thread 和 process 写它，三个 semaphore 的写法见 [CS2106 第 4 站](../courses/CS2106.html#sema)。
- **Pipelining**：data 是一串 element，依次流过几个 stage，每个 stage 由一个 thread 负责一个处理步骤，不同 element 同时处在不同的 stage。这是 functional decomposition 的一种，也叫 stream parallelism。

Pipeline 的时间要数一下。$k$ 个 stage、每个 stage 用时 $t$，处理 $n$ 个 element：第一个 element 走完全程用 $kt$，之后每隔 $t$ 出来一个，共

$$T=(k+n-1)\,t$$

$k=3$、$n=4$ 时是 $6t$，不用 pipeline 是 $3\times4\,t=12t$。Stage 用时不一样时，每隔“最慢的 stage 的时间”才能出来一个，throughput 由最慢的 stage 决定。

::fig[cs3210-pipe] 3 个 stage、4 个 element。每一列是一个时间单位，第 3 个时间单位起三个 stage 同时在忙。

:::wrong Task 切得越细，parallelism 越多，程序就越快
上面 stencil 的例子：一个点一个 task 时 task 有 64 个，parallelism 是最多的，但每一步要发 256 个 message；合成 4 个 task 之后每个 processor 每步的通信从 94.8 μs 降到 24.5 μs，而计算量一点没变。Foster 的 checklist 正是要求 agglomeration 之后 task 数仍然比 processor 多、仍然随问题变大，但不必更多。Granularity 的选择是在“够多的 task 以便 load balance”和“够少的 message 以便省 startup cost”之间折中，LLNL 的 tutorial 把 computation 和 communication 的比值叫 granularity，比值高（coarse-grain）通常更有利。
:::

### 一个 sequential program 的时间从哪里来

先看一个 processor。程序的 response time（wall-clock time）由三部分组成：user CPU time（CPU 执行程序本身）、system CPU time（CPU 执行 OS 的 routine，例如 system call）、waiting time（等 I/O，或者 time sharing 时轮到别的程序）。后两项取决于 OS 和机器的 load，一个程序能控制的是 user CPU time：

$$T_\text{user}=N_\text{cycle}\times T_\text{cycle},\qquad N_\text{cycle}=\sum_i n_i\,\text{CPI}_i$$

$n_i$ 是第 $i$ 类 instruction 执行的次数，$\text{CPI}_i$ 是这一类平均要几个 cycle。用整个程序的平均 CPI 写成

$$T_\text{user}=N_\text{instr}\times\text{CPI}\times T_\text{cycle}$$

拿开头第二次实验检验。两个版本 instruction 数都是 $6.35\times10^{10}$，`perf` 报告的 cycle 数和 clock frequency：

| 版本 | cycle | frequency | cycle ÷ frequency | 实测 | CPI | L1d miss |
|---|---|---|---|---|---|---|
| inner loop 沿 column（ijk） | $2.649\times10^{10}$ | 4.170 GHz | 6.35 s | 6.34 s | 0.417 | $1.270\times10^9$ |
| inner loop 沿 row（ikj） | $1.998\times10^{10}$ | 4.161 GHz | 4.80 s | 4.78 s | 0.315 | $6.84\times10^7$ |

$N_\text{instr}$ 和 $T_\text{cycle}$ 都一样，差别全在 CPI。CPI 是平均值，它把等 memory 的 cycle 也算了进去；把这部分单独写出来是

$$T_\text{user}=(N_\text{cycle}+N_\text{mm\_cycle})\times T_\text{cycle},\qquad N_\text{mm\_cycle}=N_\text{read op}\times R_\text{read miss}\times N_\text{miss cycles}+(\text{write 同理})$$

两个版本多出来的 cycle 是 $2.649\times10^{10}-1.998\times10^{10}=6.51\times10^9$，多出来的 L1 miss 是 $1.270\times10^9-6.84\times10^7=1.20\times10^9$ 次，平均每次多出的 miss 花 $6.51/1.20=5.4$ 个 cycle。这比一次 L2 hit 的 latency（[CS149 第 6 站](../courses/STANFORD-CS149.html#coherence)的表里约 10 个 cycle）还短，因为 out-of-order 的 core 在等一个 miss 的时候还在执行后面不依赖它的 instruction，hardware prefetcher 也会提前把顺序访问的 line 取进来，一部分 miss 的时间被藏起来了。

Miss 为什么多了 18.6 倍：row-major 的 matrix 里 `b[k][j]` 和 `b[k+1][j]` 隔了一整行，1024 个 float 即 4 KB，每次访问都落在一条新的 64-byte cache line 上；沿 row 走时一条 line 里的 16 个 float 全部用上，大约每 16 次访问才 miss 一次。如果 column 版本的每次访问都 miss，比值应该接近 16，实测 18.6，同一个量级。Average memory access time 的公式和 block size 的分析见 [CS2100 第 8 站](../courses/CS2100.html#cache)，loop order 在更多版本之间的对比见 [CS249R 第 3 站](../courses/HARVARD-CS249R.html#kernel)。

**MIPS 与 MFLOPS。** 常见的两个 throughput 指标是

$$\text{MIPS}=\frac{N_\text{instr}}{T_\text{user}\times10^6},\qquad \text{MFLOPS}=\frac{N_\text{flop}}{T_\text{user}\times10^6}$$

上面两个版本：MIPS 是 $6.35\times10^{10}/(4.78\times10^6)=13285$ 和 $6.35\times10^{10}/(6.34\times10^6)=10016$；矩阵乘法做 $2n^3=2\times1024^3=2.15\times10^9$ 次 floating-point operation，MFLOPS 是 449 和 339。注意 $6.35\times10^{10}$ 条 instruction 只做了 $2.15\times10^9$ 次 flop，平均约 30 条 instruction 一次 flop，这是没有 optimization 的编译结果（`b[k][j]` 每次都要先读 row pointer 再算 address）。开了 optimization、用上 SIMD 之后，instruction 数会少很多，时间缩短，MIPS 反而可能下降。所以 MIPS 只能比较同一个 binary，不能比较不同的程序或 compiler；MFLOPS 稍好一些，但它把一次 add 和一次 division 算成一样的。

### Parallel 的时间与 cost

一个 parallel program 的执行时间 $T_p(n)$（$n$ 是问题规模，$p$ 是 processor 数）由四部分组成：local computation、processor 之间交换 data、synchronization，以及 waiting（load 不均时先做完的等后做完的、等一个被别人占着的 shared data structure）。

Cheatsheet 开头的例子：要算 $n=24$ 个值再加起来，$p=8$ 个 core 各算 3 个、各求一个 partial sum，结果是

| core | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| my_sum | 8 | 19 | 7 | 15 | 7 | 13 | 12 | 14 |

然后 master core 0 逐个接收另外 7 个 partial sum 加到自己的上：7 次接收、7 次加法，得 $8+19+7+15+7+13+12+14=95$。更好的做法是两两相加：第一轮 core 0 加 core 1 的、core 2 加 core 3 的……得 27、22、20、26；第二轮得 49、46；第三轮得 95。$\log_28=3$ 轮。

::fig[cs3210-sumtree] Cheatsheet 里那 8 个 partial sum。左：master 逐个接收，7 轮；右：tree，每一轮的加法同时进行，3 轮。

衡量一个 parallel program 用了多少资源，用 cost：

$$C_p(n)=p\times T_p(n)$$

它是 processor 和时间的乘积，等于所有 processor 一共花掉的时间（包括闲着的时间）。如果 $C_p(n)$ 和最快的 sequential program 的时间是同一个量级，就叫 cost-optimal：Parallel 版本没有比 sequential 版本多做多少工作。

用求和来看。设一次加法和一轮 communication 都算 1 个单位，$n$ 个数、$p$ 个 processor：每个 processor 先把自己的 $n/p$ 个数加起来，要 $n/p-1$ 次加法，再按 tree 合并 $\log_2p$ 轮：

$$T_p(n)=\frac np-1+\log_2p,\qquad C_p(n)=n-p+p\log_2p$$

Sequential 要 $n-1$ 次加法。

| $n$ | $p$ | $T_p$ | $C_p$ | sequential | efficiency |
|---|---|---|---|---|---|
| 16 | 16 | 4 | 64 | 15 | 0.23 |
| 16 | 4 | 5 | 20 | 15 | 0.75 |
| 1024 | 16 | 67 | 1072 | 1023 | 0.95 |
| 1024 | 1024 | 10 | 10240 | 1023 | 0.10 |

$p=n$ 时最快，但 cost 是 $n\log_2n$，比 sequential 的 $n$ 多一个 $\log n$ 的 factor，不是 cost-optimal：大部分 processor 在第一轮之后就闲着了。$p$ 远小于 $n$ 时，$C_p=n-p+p\log_2p$ 里主导的是 $n$，只要 $p\log_2p$ 不超过 $n$ 的量级，cost 就和 $n$ 同阶，是 cost-optimal 的。

### Speedup 与 efficiency

$$S_p(n)=\frac{T_\text{best seq}(n)}{T_p(n)},\qquad E_p(n)=\frac{S_p(n)}{p}=\frac{T_\text{best seq}(n)}{C_p(n)}$$

分母 $T_p$ 是 parallel 版本的时间，分子是最快的 sequential program 的时间，不是 parallel 程序在一个 processor 上跑的时间。用后者得到的叫 relative speedup，Foster 的例子说明它会误导：algorithm A 在 1 个 processor 上 10000 s、1000 个 processor 上 20 s；algorithm B 在 1 个 processor 上 1000 s、1000 个 processor 上 5 s。Relative speedup 是 A 的 $10000/20=500$ 对 B 的 $1000/5=200$，A 看起来好得多；可是 B 在每一个 processor 数下都比 A 快。用最快的 sequential 时间 1000 s 做分子（absolute speedup），A 是 $1000/20=50$，B 是 200。A 的 relative speedup 高，只是因为它在一个 processor 上本来就慢。

上表的最后一列就是 $E_p$。理想情况 $S_p=p$、$E_p=1$。

:::edge Speedup 超过 p
理论上 $S_p\le p$：$p$ 个 processor 一起做的工作，一个 processor 轮流做也做得完。实测中偶尔会 $S_p>p$（superlinear speedup），常见原因是 cache：把一个 4 MiB 的 working set 分给 8 个 core，每个 core 只有 0.5 MiB，放得进上面那台 Xeon 每个 core 1 MiB 的 L2；一个 core 独自做时 4 MiB 放不进 L2，大量 access 落到 L3 和 DRAM。Parallel 版本每次 access 都更便宜，于是比 $p$ 倍还快。另一种是 search：Parallel 的搜索可能碰巧早早在某个分支找到答案，比 sequential 少搜了很多。前者是 hardware 资源也跟着放大了 $p$ 倍，后者是做的工作变少了，都不违反上面的论证。
:::

### Amdahl's law：固定问题，加 processor

设 sequential 时间里比例 $f$ 的部分只能 serial 执行，其余可以完美地分给 $p$ 个 processor：

$$S_p(n)=\frac{T_\text{seq}}{f\,T_\text{seq}+\frac{1-f}{p}T_\text{seq}}=\frac{1}{f+\frac{1-f}{p}}\ \le\ \frac1f$$

推导和 CS149 的图像例子见 [CS149 第 3 站](../courses/STANFORD-CS149.html#work)。这里只看它的数字有多严厉：$p=1024$ 时，$f=1\%$ 给出 $1/(0.01+0.99/1024)=91.2$，$f=4\%$ 给出 24.4。

Cheatsheet 给的反驳是：$f$ 常常不是常数，它依赖问题规模，$f=f(n)$。上面的求和就是这样：serial 的部分是 $\log_2p$ 轮合并，parallel 的部分是 $n/p-1$ 次加法，$n$ 越大 serial 部分占的比例越小。如果 $\lim_{n\to\infty}f(n)=0$，那么 $\lim_{n\to\infty}S_p(n)=p$：对足够大的问题，Amdahl 的上限不起作用。

### Gustafson's law：固定时间，放大问题

Gustafson 1988 年的文章从一组实测出发。Sandia 在一台 1024 个 processor 的 hypercube 上跑了三个应用（beam stress analysis、baffled surface wave、unstable fluid flow），speedup 分别是 1021、1020、1016，而它们的 serial fraction 是 0.4% 到 0.8%。按 Amdahl，$f=0.4\%$ 的上限是 $1/(0.004+0.996/1024)=201$，$f=0.8\%$ 是 111，实测是它的五到九倍。

矛盾出在 Amdahl 的一个隐含假设：问题规模固定，换了更多 processor 去做同一个问题。用户实际上不这样用大机器，他们按机器的大小放大问题（更细的 grid、更多的 time step），让程序在差不多的时间里跑完。放大的是 parallel 的部分；serial 的部分（读入程序、I/O、一些初始化）基本不随问题变大。

于是换一个固定的量。在 parallel 机器上量时间，把它归一化成 1：serial 部分 $s'$，parallel 部分 $p'$，$s'+p'=1$。同样的问题交给一个 processor，serial 部分还是 $s'$，parallel 部分要一个 processor 做 $N$ 份，是 $p'N$。所以

$$S=\frac{s'+p'N}{s'+p'}=s'+p'N=N+(1-N)\,s'$$

这是一条 slope 为 $1-N$ 的直线。$N=1024$、$s'=0.4\%$ 时 $1024-1023\times0.004=1019.9$；$s'=0.8\%$ 时 1015.8，和实测的 1016 到 1021 对得上。

::fig[cs3210-gustafson] 左：两种定律固定的东西不同。Amdahl 固定问题（上），serial 时间是 1；Gustafson 固定 parallel 机器上的时间（下），换成一个 processor 时 parallel 部分要放大 $N$ 倍。右：$N=1024$ 时 speedup 随 serial fraction 的变化，Amdahl 的曲线很快掉下去，Gustafson 是一条缓缓下降的直线。

这两种实验在实践中有名字：问题规模固定、增加 processor，量的是 strong scaling；每个 processor 的问题规模固定、问题总量随 processor 一起增加，量的是 weak scaling。Amdahl 描述 strong scaling 的上限，Gustafson 描述 weak scaling。

:::wrong 1% 的 code 是 serial 的，所以 1024 个 processor 最多快 100 倍，买再多也没用
这句话只在“问题固定不变”时成立。Sandia 的三个应用 serial fraction 是 0.4% 到 0.8%，按这个说法最多 111 到 201 倍，实测是 1016 到 1021 倍，因为他们让问题随 processor 一起变大，serial 的那 1% 并没有跟着变大。要回答“多买 processor 有没有用”，先要问用它来做什么：同一个问题算得更快（strong scaling，Amdahl 说了算），还是同样的时间算更大的问题（weak scaling，Gustafson 说了算）。
:::

### Scalability：问题要长多快才能保住 efficiency

把第 3 站的 stencil 放进一个具体的 model。$N\times N$ 的 grid，每个点每步计算 $t_c$，一个 $m$ 个值的 message 用时 $t_s+m\,t_w$。Sequential 每步 $T_1=t_cN^2$。

- 1D：每个 task 算 $N^2/P$ 个点，和上下两个邻居各交换 $N$ 个值：$T_P=t_c\dfrac{N^2}{P}+2(t_s+Nt_w)$。
- 2D：每个 task 算同样多，和四个邻居各交换 $N/\sqrt P$ 个值：$T_P=t_c\dfrac{N^2}{P}+4\Big(t_s+\dfrac{N}{\sqrt P}t_w\Big)$。

Efficiency $E=T_1/(PT_P)$：

$$E_\text{1D}=\frac{t_cN^2}{t_cN^2+2Pt_s+2PNt_w},\qquad E_\text{2D}=\frac{t_cN^2}{t_cN^2+4Pt_s+4\sqrt P\,Nt_w}$$

$P$ 增大时 efficiency 下降，问题是问题规模要以多快的速度增长才能把它保持住。分母里和 $t_cN^2$ 比较的主要是含 $t_w$ 的那一项。1D 要 $N^2$ 和 $PN$ 同阶，即 $N\propto P$，工作量 $N^2\propto P^2$；2D 要 $N^2$ 和 $\sqrt PN$ 同阶，即 $N\propto\sqrt P$，工作量 $N^2\propto P$（含 $t_s$ 的那项同样只要求 $N^2\propto P$）。这个“工作量必须随 $P$ 怎样增长”的 function 叫 isoefficiency function：1D 是 $P^2$，2D 是 $P$，增长越慢越 scalable。

代入数字：$t_c=10$ ns，$t_s=5.854\ \mu$s，每个值 8 byte、$t_w=8\times0.00872=0.0698\ \mu$s，$N=1024$：

| $P$ | 每步计算 | 1D 通信 | 2D 通信 | $E_\text{1D}$ | $E_\text{2D}$ |
|---|---|---|---|---|---|
| 16 | 655 μs | 155 μs | 95 μs | 0.81 | 0.87 |
| 64 | 164 μs | 155 μs | 59 μs | 0.51 | 0.73 |
| 256 | 41 μs | 155 μs | 41 μs | 0.21 | 0.50 |

1D 的通信量不随 $P$ 减少，计算却按 $1/P$ 减少，efficiency 掉得很快；2D 的通信量按 $1/\sqrt P$ 减少，掉得慢一些。

### Energy：同样的工作，花多少焦耳

CMOS 电路的 dynamic power 大约是

$$P_\text{dyn}=a\,C\,V^2f$$

$a$ 是每个 cycle 翻转的比例，$C$ 是 capacitance，$V$ 是 supply voltage，$f$ 是 clock frequency。Frequency 降低时 voltage 可以跟着降（dynamic voltage and frequency scaling，DVFS），而 power 对 $V$ 是平方。除此之外还有和 frequency 无关的 static（leakage）power。Energy 是 power 乘时间，一个固定的工作在 frequency $f$ 下要 $1/f$ 的时间。

一个归一化的例子（数字是为这一页构造的）：Frequency 1、voltage 1 时 $P_\text{dyn}=1$，static power 恒为 0.3，工作在 frequency 1 下要 1 个单位时间。Voltage 最低只能降到 0.7。

| frequency | voltage | $P_\text{dyn}=V^2f$ | 时间 | dynamic energy | static energy | 总 energy |
|---|---|---|---|---|---|---|
| 1.0 | 1.0 | 1.000 | 1.00 | 1.000 | 0.300 | 1.300 |
| 0.8 | 0.8 | 0.512 | 1.25 | 0.640 | 0.375 | 1.015 |
| 0.7 | 0.7 | 0.343 | 1.43 | 0.490 | 0.429 | 0.919 |
| 0.5 | 0.7 | 0.245 | 2.00 | 0.490 | 0.600 | 1.090 |

从 1.0 降到 0.7，dynamic energy $V^2f\times(1/f)=V^2$ 随 voltage 平方下降，总 energy 变少。Voltage 到了下限之后再降 frequency，dynamic energy 停在 $0.7^2=0.49$ 不动，static energy 却随时间增长，总 energy 反而上升。所以“越慢越省电”只在 voltage 还能跟着降时成立；voltage 降不下去时，尽快做完然后进入low-power state（race-to-idle）更省。

::fig[cs3210-energy] 上表的 model 画成曲线：横轴是 frequency，纵轴是完成同一个工作的 energy。Voltage 降到 0.7 之前曲线下降，之后上升。

这也是 multicore 的理由。把一个 core 换成两个 frequency 减半、voltage 降到 0.6 的 core，若工作能完美地分成两半，完成时间不变，dynamic power 是 $2\times0.6^2\times0.5=0.36$，只有原来的 36%。[CS149 第 1 站](../courses/STANFORD-CS149.html#core)讲了 power wall 怎样让 single-thread performance 停止增长，[第 8 站](../courses/STANFORD-CS149.html#special)讲搬 data 比计算费 energy 多少倍。

:::back
求和的 tree 是[第 3 站](#design)的 divide-and-conquer summation；stencil 的 1D 与 2D 是第 3 站 surface-to-volume 的定量版本；$t_s$、$t_w$ 的来历在[第 8 站](#mpi)。

### Coherence 要保证的三件事

第 1 站的 ccNUMA 里每个 core 有自己的 cache，同一个 address 可以同时有好几份 copy。[CS149 第 6 站](../courses/STANFORD-CS149.html#coherence)开头的例子说明了问题：write-back cache 里 P1 写 `x = 1`，新值只在 P1 的 cache 里，P2 从 memory 读到的还是 0。Cheatsheet 把“coherent”拆成三条 property，每一条排除一种错误：

1. **Program order。** P 写 X，之后（中间没有别人写 X）P 读 X，读到的是自己写的值。这在一个 processor 上本来就成立，列出来是为了完整。
2. **Write propagation。** P1 写 X，过了足够长的时间、中间没有别的写，P2 读 X 一定读到 P1 写的值。上面的 `x = 1` 违反的就是这一条：新值永远困在 P1 的 cache 里。
3. **Write serialization。** 对同一个 address 的所有写，不论来自哪个 processor，所有 processor 看到的先后顺序一样。

第 3 条最容易被忽略。Adve 和 Gharachorloo 的例子：P1 写 `A = 1`，P2 写 `A = 2`，P3 和 P4 各读两次 A。如果 update 在 network 里走的路径长短不同，P3 可能先看到 1 后看到 2，P4 先看到 2 后看到 1，两个 processor 对“A 最后是几”意见不一。每一个 write 都传到了（第 2 条成立），但顺序不一致。

Snooping protocol 靠 bus 实现第 3 条：所有 cache 都在同一条 bus 上，谁先拿到 bus，谁的写就排在前面，所有 cache 按 bus 上的顺序看到它们。Directory protocol 靠每条 line 的 home node：对这条 line 的请求都要经过它，它处理的顺序就是这条 line 上所有写的顺序。CS149 那一站 MSI 的六步 trace 里，第 3 步 P3 的 BusRdX 让 P1 的 copy 变 I，保证 P1 之后不会再读到旧值（write propagation）；第 4 步 P1 再读，从 P3 的 cache 拿到新值。

### Write-invalidate 还是 write-update

一个 processor 写一个别人也有 copy 的 line 时，有两种办法让别人的 copy 不过期。Grama 的例子：P0 和 P1 都已经读过 `x = 1`，现在 P1 写 `x = 3`。

- **Invalidate**：P1 通知其他 cache 作废自己的 copy，P0 的 copy 变成 invalid，下次 P0 读 x 是一次 miss，再去拿新值 3。MSI、MESI 都是这一类。
- **Update**：P1 把新值 3 broadcast 出去，P0 的 copy 直接改成 3，下次读是 hit。

哪个好取决于 access pattern。数两种 pattern 的 bus transaction（P0、P1 一开始都有 x 的 shared copy）：

**Pattern 1：P1 连写 10 次，P0 最后读一次。** Invalidate：P1 第一次写发一次 invalidation，copy 变成独占，后面 9 次写都是 hit；P0 读时 miss 一次，从 P1 拿 data。共 2 次。Update：10 次写各 broadcast 一次，P0 读是 hit。共 10 次。

**Pattern 2：P1 写、P0 读，交替 10 轮。** Invalidate：每一轮 P1 写都要作废 P0 的 copy（1 次），P0 读都 miss（1 次），共 20 次。Update：每一轮 P1 的写 broadcast 一次，P0 读 hit，共 10 次。

::fig[cs3210-invupd] 两种 pattern 下的 bus transaction。每个小方块是一次 bus transaction，深色是 invalidation 或 update，浅色是 miss 之后取 data。

Grama 的总结是：一个 processor 只读一次的 data，update 是浪费（pattern 1）；两个 processor 交替读写同一个 variable 时，update 更好（pattern 2）。一般程序里前一种更常见，加上 update 每次都要把整个新值送出去，所以今天的 processor 几乎都用 invalidate。两种都受 false sharing 之害。

### Snooping 与 directory

Snooping 把每一个 coherence 请求 broadcast 给所有 cache，每个 cache 都要查自己有没有这条 line。8 个 core 时还行，core 一多，bus 的 bandwidth 和每个 cache 查 tag 的次数先撑不住。Directory 为每条 line 记一个 presence vector（哪些 cache 有它）和一个 state，请求只发给真正有 copy 的 cache。

::fig[cs3210-dir] 8 个 cache，line 只在 C2、C5 里有 copy，C0 要写它。左：snooping，一次 broadcast，其余 7 个 cache 都要查。右：directory，C0 问 home，home 只给 C2、C5 发 invalidation，收到两个 ack 后回复 C0。

右边一共 6 个点对点的 message（请求、两个 invalidation、两个 ack、回复），比一次 broadcast 多，但只打扰了真正有 copy 的两个 cache，而且不需要一条所有人共用的 bus，所以 directory 适合 NUMA 和更大的系统。代价是 latency 多了一跳（先到 home），以及存储：每条 line 用一个 $p$ bit 的 vector 记录 $p$ 个 cache 有没有它。Line 是 64 byte，即 512 bit：

| $p$ | presence vector | 占 line 大小的比例 |
|---|---|---|
| 16 | 16 bit | 3.1% |
| 64 | 64 bit | 12.5% |
| 256 | 256 bit | 50% |
| 1024 | 1024 bit | 200% |

1024 个 processor 时，记录“谁有这条 line”比 line 本身大一倍。所以大系统不给每条 line 存完整的 bit vector，而改用只记几个 sharer 编号之类的压缩格式（这一点凭我自己的知识）。

### Coherence 的代价

Coherence 让程序正确，也让它变慢。Cache 的 hit rate 下降：一条 line 被别人作废之后再读就是一次 miss，这叫 coherence miss。两个 processor 反复读改同一个 address，line 在两个 cache 之间来回搬，叫 cache ping-pong。两个 processor 写的是同一条 line 上不同的 address，line 照样来回搬，叫 false sharing，第 2 站 Mattson 的 `sum[id]` 版本从 2 个 thread 到 4 个几乎没有变快就是它（CS149 那一站的实测是 14.2 s 对 4.7 s）。

### Memory consistency：四个 model 差在哪

Coherence 只管同一个 address。一个 processor 对两个不同 address 的操作，别的 processor 看到的先后，由 memory consistency model 规定。一个 processor 的 program order 里有四种先后：W→R、R→R、R→W、W→W（前一个操作的 address 和后一个不同）。Cheatsheet 列的四个 model：

| | SC | TSO | PC | PSO |
|---|---|---|---|---|
| 保留 R→R、R→W | 是 | 是 | 是 | 是 |
| 保留 W→R | 是 | 否 | 否 | 否 |
| 保留 W→W | 是 | 是 | 是 | 否 |
| 一个 write 同时对所有其他 processor 可见 | 是 | 是 | 否 | 是 |

前三行讲一个 processor 自己的操作能不能被重排。放松 W→R 的原因是 write buffer：processor 把 write 放进 buffer 就去执行后面的 read。[CS149 第 6 站](../courses/STANFORD-CS149.html#coherence)用两个 processor 各写一个、读另一个的 litmus test 说明 TSO 允许 $(0,0)$ 而 SC 不允许，用 `A = 1; flag = 1;` 的例子说明 PSO 放松 W→W 会让另一个 thread 看到 flag 却看不到 A。

最后一行是 TSO 和 PC 唯一的区别。它管一个 write 是否“一下子”对所有人生效（write atomicity），和一个 processor 自己的操作顺序无关。TSO 下，一个 write 一旦被除写者以外的任何一个 processor 读到，就已经对所有 processor 可见；PC 允许它先被一部分 processor 看到。看一个需要三个 processor 的例子（Adve 和 Gharachorloo 的 Figure 4(b)），一开始 A = B = 0：

```
P1:  A = 1;
P2:  if (A == 1) B = 1;
P3:  if (B == 1) r = A;
```

问：P3 能不能读到 B = 1 却得到 r = 0？

- **SC**：P3 读到 B = 1，说明 P2 的 `B = 1` 已经执行，于是 P2 之前读到了 A = 1，P1 的 `A = 1` 早于这一切；所有操作排成一列，P3 的读 A 排在 `A = 1` 之后，r = 1。
- **TSO**：这里没有一个 W→R 的先后被用到：P2 是先读 A 后写 B（R→W，保留），P3 是先读 B 后读 A（R→R，保留）。P2 读到了 A = 1，按 TSO 的 write atomicity，这时 `A = 1` 已经对所有人可见，P3 也只能读到 1。r = 1。
- **PC**：`A = 1` 可以先到达 P2、还没到达 P3。P2 读到 1，写 B = 1，这个 write 先到了 P3；P3 读到 B = 1，再从自己的 cache 读 A，`A = 1` 还在路上，r = 0。

::fig[cs3210-pc] 三个 processor 和两个 write 的传播。动起来时看 `A = 1` 的两条箭头：到 P2 的那条很快，到 P3 的那条很慢；P2 的 `B = 1` 抢先到了 P3。第一帧是 PC 允许的那个结局。

Adve 和 Gharachorloo 比较 IBM 370、TSO、PC 三个都只放松 W→R 的 model，只有 PC 允许这个结果。PSO 在 write atomicity 上和 TSO 一样，这个例子同样不允许。要在 PC 的机器上禁止它，需要让 P2 在读到 A 之后、写 B 之前等 `A = 1` 传到所有人，即一个 fence。

:::wrong 机器是 coherent 的，所以一个 write 对所有 processor 同时可见
上面 PC 的结局里 coherence 一条都没有违反：对 A 来说，每个 processor 看到的是同一个顺序（先 0 后 1），只是 P3 看到 1 的时间晚；对 B 也一样。Coherence 的 write propagation 只说“最终会看到”，write serialization 只说“顺序一致”，都不说“同时”。P3 的矛盾只在把 A 和 B 放在一起看时出现，那是 consistency model 管的事；“一个 write 同时对所有人可见”正是上表最后一行，TSO 承诺了，PC 没有。
:::

### Lab 3 的几个现象

Lab 3 Exercise 2 把 `hello.cu` 改成 $2\times2\times2$ 的 grid、每个 block $2\times4$ 个 thread。一共 $8$ 个 block、每个 block 8 个 thread、64 个 thread。要给每个 thread 一个全局唯一的编号，把 3D 的 grid 和 2D 的 block 摊平：

$$\begin{aligned}\text{blockId}&=\texttt{blockIdx.x}+\texttt{blockIdx.y}\cdot\texttt{gridDim.x}+\texttt{blockIdx.z}\cdot\texttt{gridDim.x}\cdot\texttt{gridDim.y}\\\text{idx}&=\text{blockId}\cdot(\texttt{blockDim.x}\cdot\texttt{blockDim.y})+\texttt{threadIdx.x}+\texttt{threadIdx.y}\cdot\texttt{blockDim.x}\end{aligned}$$

Block 0 是 0 到 7，block 7 是 $7\times8=56$ 到 63。

Exercise 4 打印每个 thread 的编号，输出总是 32 个一组。这正是 warp：一个 SM 以 32 个连续编号的 thread 为单位创建、schedule、执行，block 0 的第一个 warp 是 thread 0 到 31。

:::wrong 1024 个 block 各放 1 个 thread，和 1 个 block 放 1024 个 thread 是一样的
Exercise 3 的 `slow.cu` 就是这样写的，跑得极慢。Block 不会被拼成 warp：一个 block 内部按 32 个一组切，不满 32 的最后一组也是一个完整的 warp。1024 个单 thread 的 block 产生 1024 个 warp，每个 warp 32 条 lane 里只有 1 条在工作，SIMD 的 utilization 是 $1/32$；1 个 1024 thread 的 block 是 $1024/32=32$ 个满的 warp。同样 1024 份工作，前者让 hardware schedule 32 倍的 warp。Block 大小应该取 32 的倍数。
:::

Exercise 10 的 `synchronise.cu` 说明两件事。`__syncthreads()` 只让同一个 block 里的 thread 互相等，不同 block 之间没有任何 barrier，所以 launch 多个 block 时 counter 的值每次不一样（block 之间为什么不能互相等，见 [CS149 第 5 站](../courses/STANFORD-CS149.html#gpu)的 :::wrong）。kernel 里 spin 等一个 flag 的 `while (!is_done)` 要把 `is_done` 声明成 `volatile`：否则 compiler 看到 loop 里没有写它，就只读一次放进 register，之后永远读 register，别的 thread 改了 memory 也看不到，loop 永不结束。

### 几种 memory

| memory | 在哪 | 谁能访问 | 活多久 | Lab 3 的例子 |
|---|---|---|---|---|
| register | SM 上 | 一个 thread | thread | kernel 里的局部 variable |
| local | device DRAM（经 cache） | 一个 thread | thread | register 放不下的局部 array |
| shared | SM 上 | 一个 block 的所有 thread | block | `__shared__`，`shared_mem.cu` |
| global | device DRAM | 所有 thread，host 通过 `cudaMemcpy` | 整个程序 | `cudaMalloc`、`__device__` variable，`global_comm.cu` |
| constant | device DRAM，有专门的 cache | 所有 thread 只读，host 写 | 整个程序 | `__constant__` |

Host（CPU）和 device（GPU）的 memory 是两个 address space。`global_comm.cu` 里 host 不能直接读一个 `__device__` variable，只能用 `cudaMemcpyFromSymbol` 一类的调用把它拷回来；改成 unified memory（`cudaMallocManaged` 或 `__managed__`）之后，同一个 pointer 在 host 和 device 上都能用，data 由 driver 按需搬（Exercise 7）。

`shared_mem.cu` 让同一个 block 的 thread 先写 shared memory 再读：同一个 block 里的 thread 看到一致的结果；不同 block 各有自己的一份 shared memory，结果不同。`atomic.cu` 让很多 thread 对同一个 global variable 加，用普通的 `+=` 结果每次不一样，换成 `atomicAdd` 才一致。

速度上差得很远：register 和 shared memory 在 SM 上，global memory 在 DRAM，一次 access 几百个 cycle（[CS149 第 1 站](../courses/STANFORD-CS149.html#core)讲了 GPU 怎样靠大量 warp 掩盖这个 latency）。Global memory 的 bandwidth 是有限的，于是关键就是每次去 DRAM 拿回来的 byte 有多少真的被用上。

### Coalescing：一个 warp 的 load 要几个 sector

一个 warp 的 32 个 thread 同时执行一条 load，hardware 把它们要的 address 合起来，按 32-byte 对齐的 segment（sector）去 DRAM 取：涉及几个 sector，就要几次 32-byte 的 transaction。每个 thread 读一个 4-byte 的 float：

- **连续且对齐**：thread $k$ 读第 $k$ 个 float，起点 32-byte 对齐。Cheatsheet 的例子是 address 96 到 223，正好 128 byte，96 是 32 的倍数，落在 96、128、160、192 开头的 4 个 sector 里。取 128 byte、用 128 byte，efficiency 100%。
- **连续但错位**：起点挪到 112，访问 112 到 239。112 不是 32 的倍数，跨过了 96、128、160、192、224 开头的 5 个 sector，取 160 byte、用 128 byte，efficiency $128/160=80\%$。
- **Stride 2**：thread $k$ 读第 $2k$ 个 float，32 个 float 散布在 256 byte 里，要 8 个 sector，取 256 byte 只用一半，50%。Stride 越大越糟，stride 8 起每个 thread 落在一个单独的 sector 里，32 个 sector、$128/1024=12.5\%$。

::fig[cs3210-coalesce] 一行格子是 global memory，每 32 byte 一个 sector（粗线分开）。深色是 warp 要的 byte，浅底是被取回来的 sector。三行依次是对齐、错位、stride 2。

Best Practices Guide 在 V100 上测了这两种情况。`offsetCopy`（每个 thread 拷 `idata[xid]`，`xid` 加一个 offset）不错位时约 790 GB/s；错位时按 sector 数应该掉到 $4/5$，实测只掉到约 $9/10$，因为相邻的 warp 会用到同一个 sector，第二次在 cache 里命中。`strideCopy` 在 stride 2 时每个 warp 要 8 个 L2 sector，load/store efficiency 50%，stride 越大越接近每个 warp 32 个 sector。

### 一个 thread 负责一个 row

Tutorial 3 的 matrix-vector multiply $c=Ab$，$N=16384$，$A$ 按 row-major 存，每个 thread 算一个 $c_i$（仓库里的版本有 index 写错的地方，这里写成正确的形式）：

```c
__global__ void matvec(float *c, const float *a, const float *b) {
    int i = threadIdx.x + blockIdx.x * blockDim.x;
    float sum = 0;
    for (int j = 0; j < N; ++j)
        sum += a[i * N + j] * b[j];
    c[i] = sum;
}
```

对一个 thread 来说它沿着自己的 row 连续地读，看起来很好。可是 coalescing 看的是同一时刻一个 warp 的 32 个 thread：在第 $j$ 次 iteration，thread $i$ 读 `a[i*N+j]`，相邻两个 thread 的 address 差一整个 row，$16384\times4=65536$ byte。32 个 float 落在 32 个不同的 sector，一次 load 取回 $32\times32=1024$ byte 只用 128 byte，efficiency 12.5%。每个 sector 里另外 7 个 float 是这个 thread 之后 7 次 iteration 要的，如果那时它还在 L1 或 L2 里，浪费能收回一部分；能不能留住取决于同时在跑的 warp 有多少、cache 有多大。

把 $A$ 换成 column-major（或者事先转置，存 $A^\top$），thread $i$ 在第 $j$ 次 iteration 读 `at[j*N+i]`，相邻 thread 的 address 相邻，32 个 float 正好 128 byte、4 个 sector，100%。另一种改法是让一个 warp 合作算一个 row：32 个 thread 各读 row 里相邻的元素、各自累加，最后在 warp 内求和，[CS336 第 5 站](../courses/STANFORD-CS336.html#gpu)比较了这两种分工。

这份 tutorial code 还有一个和 memory 无关的问题：`<<<N/512, 512>>>` 只有 $16384/512=32$ 个 block，一个 block 只能在一个 SM 上跑，而 CS149 那一站的 V100 有 80 个 SM，一半以上的 SM 没事做。`multirow` 版本每个 block 32 个 thread、每个 thread 算 32 行，只有 $16384/32/32=16$ 个 block、512 个 thread，更少。

### AoS 与 SoA

Cheatsheet 的例子：

```c
struct Train { size_t id; size_t location; };
// kernel 里每个 thread i：trains[i].location += 1;
```

一个 `Train` 是 16 byte，`location` 在每个 struct 的第 8 到 15 byte。一个 warp 的 32 个 thread 读 32 个 `location`，address 是 $16i+8$，散布在 $32\times16=512$ byte 里，要 16 个 sector，只用了 $32\times8=256$ byte，50%。这种一个 array 装着很多 struct 的写法叫 array of structures（AoS）。

改成 structure of arrays（SoA）：

```c
struct Trains { size_t *id; size_t *location; };
// kernel 里：trains.location[i] += 1;
```

32 个 `location` 连续存放，256 byte、8 个 sector，100%。CPU 上同样的变换能让 SIMD load 变成连续的。

### Shared memory 的 bank

Shared memory 分成 32 个 bank，每个 bank 每个 cycle 能提供一个 4-byte 的 word；连续的 4-byte word 依次落在 bank 0、1、……、31、0、1、……。一个 warp 的 32 个 thread 同时访问 shared memory 时：

1. 访问不同 bank 的不同 address：一个 cycle 完成，没有 conflict；
2. 访问同一个 bank 的不同 address：bank conflict，这几次访问要排队，$k$ 个 thread 撞在同一个 bank 就要 $k$ 次；
3. 访问同一个 address：Broadcast，没有 conflict。

一个 $32\times32$ 的 float tile `tile[32][32]`，`tile[r][c]` 是第 $32r+c$ 个 word，在 bank $(32r+c)\bmod32=c$。所以同一个 column 的 32 个元素全在同一个 bank：

- 一个 warp 读一个 row，`tile[k][tx]`（thread `tx` 读第 `tx` 列）：bank 是 $tx$，32 个 thread 32 个 bank，没有 conflict。
- 一个 warp 读一个 column，`tile[tx][k]`：bank 都是 $k$，32 路 conflict，要 32 次。

Transpose 一类的操作必须按 column 访问其中一边。修法是多声明一列：`tile[32][33]`。现在 `tile[r][c]` 是第 $33r+c$ 个 word，bank $(33r+c)\bmod32=(r+c)\bmod32$，读 column $k$ 时 thread $tx$ 落在 bank $(tx+k)\bmod32$，32 个 thread 各不相同。一般地，32 个 thread 以 $s$ 个 word 为 stride 访问时，用到的 bank 数是 $32/\gcd(s,32)$，conflict 的路数是 $\gcd(s,32)$；$s=32$ 时是 32 路，$s=33$ 时 $\gcd=1$，没有 conflict。

::fig[cs3210-bank] 为了看得清楚缩小成 8 个 bank、$8\times8$ 的 tile，格子里的数字是 bank 编号。左：按 column 读的 8 个元素全在 bank 0。右：多加一列 padding 之后，同一 column 的 8 个元素落在 8 个不同的 bank。

Best Practices Guide 在 V100 上的两组实测：

| kernel | $C=AB$ | $C=AA^\top$ |
|---|---|---|
| 直接从 global memory 读 | 119.9 GB/s | 12.8 GB/s |
| 用 shared memory 的 tile | 144.4 GB/s（只放 $A$ 的 tile） | 140.2 GB/s（未 padding） |
| 进一步优化 | 195.5 GB/s（$A$、$B$ 的 tile 都放） | 199.4 GB/s（`[TILE_DIM][TILE_DIM+1]`） |

$C=AA^\top$ 的直接版本要按 column 读 $A$（即 $A^\top$ 的 row），跨 row 的读不 coalesced，只有 12.8 GB/s。先按 row 把 tile coalesced 地读进 shared memory、再在 shared memory 里转置，到 140.2 GB/s；可是写进 tile 时每个 warp 按 column 写，guide 的说法是“warp 的每个 thread 都打到同一个 bank”。加一列 padding 消掉 conflict，到 199.4 GB/s，和 $C=AB$ 最好的版本相当。

Cheatsheet 列的优化清单，到这里大部分都有了着落：减少 host 与 device 之间的传输、让 global memory 的 access coalesced（本节）、用 shared memory 减少 global access 并避免 bank conflict（本节）、减少 divergent warp（[CS149 第 5 站](../courses/STANFORD-CS149.html#gpu)）、在每个 thread 的工作量和 occupancy 之间取舍（register、shared memory 怎样限制一个 SM 上同时驻留的 warp 数，见 CS149 第 5 站和 [CS336 第 5 站](../courses/STANFORD-CS336.html#gpu)）。

### Topology 的几个指标

第 1 站的 distributed memory 里，node 之间靠 network 交换 message。一个 message 走几跳、多少个 message 能同时走，取决于 node 怎样连。把 node 看成 graph 的 vertex、link 看成 edge（direct network，又叫 static 或 point-to-point network），衡量它有这几个量：

- **Diameter**：任意两个 node 之间最短路径的最大值。小，message 最多走的跳数就少。
- **Degree**：一个 node 直接连着几个邻居。小，每个 node 的 hardware（端口、线）就便宜。
- **Bisection width**：把 network 切成 node 数相等的两半，至少要剪断几条 link。乘上每条 link 的 bandwidth 是 bisection bandwidth，它衡量“一半的 node 同时给另一半发 message”时 network 的容量，all-to-all 一类的 communication 受它限制。
- **Connectivity**：至少坏掉几个 node（node connectivity）或几条 link（edge connectivity），network 才会断开。它衡量 robustness，edge connectivity 也等于任意两个 node 之间互不共用 link 的路径条数的最小值。

$p=16$ 时各种 topology 的值（tree 用 15 个 node 的 complete binary tree）：

| topology | diameter | degree | bisection width | edge connectivity | link 数 |
|---|---|---|---|---|---|
| linear array | $p-1=15$ | 2 | 1 | 1 | 15 |
| ring | $\lfloor p/2\rfloor=8$ | 2 | 2 | 2 | 16 |
| 2D mesh $4\times4$ | $2(\sqrt p-1)=6$ | 4 | $\sqrt p=4$ | 2 | $2(p-\sqrt p)=24$ |
| 2D torus $4\times4$ | $2\lfloor\sqrt p/2\rfloor=4$ | 4 | $2\sqrt p=8$ | 4 | $2p=32$ |
| hypercube $d=4$ | $\log_2p=4$ | $\log_2p=4$ | $p/2=8$ | 4 | $\tfrac{p\log_2p}{2}=32$ |
| complete binary tree | $2\log_2\tfrac{p+1}{2}=6$ | 3 | 1 | 1 | 14 |
| completely connected | 1 | $p-1=15$ | $p^2/4=64$ | 15 | $\tfrac{p(p-1)}2=120$ |

::fig[cs3210-topo] 六种 topology，每张图里的虚线是一种最好的 bisection，旁边是被剪断的 link 数。Hypercube 画成两个 3-cube，它们之间对应的 node 相连。

逐个看这些数是怎么来的。Mesh 的 diameter 是对角两个 corner 之间的距离，横走 3 步、竖走 3 步，$2(\sqrt p-1)=6$；从中间竖着切一刀剪断每一行中间的那条 link，共 $\sqrt p=4$ 条。Torus 在每一行、每一列首尾再连一条 link，每一行变成一个 4 个 node 的 ring，ring 上最远是 2 步，所以 diameter 是 $2+2=4$；同样一刀现在要多剪每一行的 wrap-around link，bisection width 翻倍到 8。Hypercube 的 $p=2^d$ 个 node 用 $d$ bit 编号，两个 node 相连当且仅当编号只差一个 bit；从 0000 到 1111 要把 4 个 bit 都改一遍，diameter 是 $d=4$；按最高 bit 切成两半，每个 node 正好有一条 link 跨过去，bisection width 是 $p/2=8$。Tree 的 diameter 是两片 leaf 经过 root 的距离，而且从 root 往下剪一刀就断了，bisection width 只有 1，root 附近的 link 是 bottleneck；fat tree 让越靠近 root 的 link 越粗来补这一点。表里所有的值我都用程序在这几个 graph 上直接算过（bisection 是枚举所有 12870 种对半分法）。

表里 $4\times4$ torus 和 4-dimensional hypercube 的每一个数都一样，这不是巧合，它们是同一个 graph。一个 4 个 node 的 ring 按 Gray code 编号 00、01、11、10，相邻的编号只差一个 bit，首尾 10 和 00 也只差一个 bit。Torus 的 node $(r,c)$ 编成 $G(r)$ 和 $G(c)$ 拼起来的 4 bit 数：同一行相邻只改后两位中的一位，同一列相邻只改前两位中的一位，正好是 hypercube 的 edge。Grama 用同样的 Gray code 把 $2^r\times2^s$ 的 wraparound mesh 嵌进 hypercube。$k>4$ 时 $k$ 个 node 的 ring 不再是 hypercube 的一部分，两者就不同了。

:::wrong Hypercube 的 diameter 最小、bisection 最大，所以永远是最好的 topology
它的代价在 degree 和 link 数上：degree 是 $\log_2p$，$p=1024$ 时每个 node 要 10 个 port，再加 node 就得改每个 node 的 hardware；2D torus 的 degree 永远是 4。Link 数 $\tfrac{p\log_2p}{2}$ 也随 $p$ 超线性增长，而且 hypercube 很难在 2D 或 3D 的机房里布线。CS267 列的真实机器里，Blue Gene/L 和 Cray XT 用 3D torus，SGI Altix 用 fat tree，hypercube 主要出现在早期（Intel iPSC、nCUBE）。另外 CS267 指出，现代 network 用 wormhole routing 之后，一个 message 走几跳对 latency 的影响已经很小（下面的 cut-through 公式），diameter 不再是最重要的指标。
:::

### Indirect network：bus、crossbar 与 multistage

另一类 network 里 node 不直接相连，而是接在 switch 上，由 switch 动态地接通 input 和 output（indirect 或 dynamic network）。

**Bus**：所有 node 共用一组线，同一时刻只有一对 node 能通信。便宜，天然支持 broadcast（第 5 站的 snooping），但 bandwidth 被所有 node 分，只能挂几十个 node。

**Crossbar**：$p$ 个 input、$m$ 个 output，每个交叉点一个 switch，共 $p\times m$ 个。任何一组 input 到不同 output 的连接都能同时建立（non-blocking），但 $16\times16$ 就要 256 个 switch，代价按 $p^2$ 增长。

**Omega network**：用 $2\times2$ 的小 switch 分几级拼出 $p\times p$ 的连接。$p=8$ 时 $\log_28=3$ 级，每级 $p/2=4$ 个 switch，共 12 个，而 crossbar 要 64 个。相邻两级之间按 perfect shuffle 连线：位置 $i$ 连到把 $i$ 的 3 个 bit 循环左移一位得到的位置（$010\to100$，$110\to101$）。每个 switch 有两种状态：straight（上进上出、下进下出）和 cross（交叉）。

Route 用 XOR-tag：令 $T=\text{source}\oplus\text{destination}$，从最高 bit 开始，第 $k$ 级看 $T$ 的第 $k$ 个 bit，0 走 straight，1 走 cross。为什么对：每经过一次 shuffle，当前位置的最高 bit 被转到最低 bit，switch 决定这个最低 bit 最后是什么；第 $k$ 级 switch 处理的正是 source 的第 $k$ 个 bit，如果它和 destination 的第 $k$ 个 bit 不同就要 cross 把它翻过来。3 级之后每个 bit 都被换成了 destination 的 bit，又转回原来的位置。

Grama 的例子：从 010 到 111，$T=101$，三级依次 cross、straight、cross。逐级写出位置：$010\xrightarrow{\text{shuffle}}100\xrightarrow{\text{cross}}101\xrightarrow{\text{shuffle}}011\xrightarrow{\text{straight}}011\xrightarrow{\text{shuffle}}110\xrightarrow{\text{cross}}111$。同时从 110 到 100：$T=010$，straight、cross、straight：$110\to101\to101\to011\to010\to100\to100$。两条 route 在第一级都要从同一个 switch（处理位置 100 和 101 的那个）的 101 号 output 出去，只能走一个，另一个要等。

::fig[cs3210-omega] $8\times8$ omega network。两条 route 010 → 111 和 110 → 100 在第一级的同一个 switch 里要同一个 output（圆圈处），另一条必须等。

所以 omega network 是 blocking 的：每对 input 和 output 之间只有唯一一条路径，两条路径共用一段 link 就冲突。**Butterfly network** 的规则不同，结论一样：第 $i$ 级的 node $(\alpha,i)$ 连到下一级的 $(\alpha,i+1)$（straight）和 $(\alpha',i+1)$（cross），$\alpha'$ 和 $\alpha$ 只在从左数第 $i+1$ 个 bit 上不同；route 时逐个 bit 比较 source 和 destination，不同就走 cross。CS267 的例子从 101 到 110：第 1 个 bit 相同走 straight，第 2、3 个 bit 不同都走 cross。Cheatsheet 还列了 baseline network，连线规则是把 $\alpha$ 的低几位循环右移，同样是 $\log_2p$ 级、每级 $p/2$ 个 switch、每对 input 和 output 唯一的路径，这里不展开。

### Routing：选哪条路，以及为什么不会卡死

Routing algorithm 决定 message 从 source 到 destination 走哪条路。按路径长短分 minimal（总走最短路）和 non-minimal；按是否看 network 的状态分 deterministic（同一对 source 和 destination 总走同一条路）和 adaptive（避开 congestion 或坏掉的 link）。CMU 18-344 还提到一种中间的 oblivious routing：Valiant 的 algorithm 先发到一个随机的中间 node 再转到 destination，把 load 分散开，代价是多走路，只在 load 很高时用。

**XY routing（2D mesh）**：先沿 X 方向走到 destination 的那一列，再沿 Y 方向走到那一行。从 $(0,0)$ 到 $(3,2)$：X 方向 3 步，Y 方向 2 步，共 5 步，等于两点间的 Manhattan distance，所以是 minimal 的。

::fig[cs3210-xy] 动起来时看 packet 从 $(0,0)$ 先向右走 3 步到第 3 列，再向上走 2 步到 $(3,2)$。

**E-cube routing（hypercube）**：source 和 destination 的编号有几个 bit 不同就要走几步（Hamming distance）。按固定的顺序（例如从最高 bit 到最低 bit）找到下一个不同的 bit，走到把这个 bit 改正的邻居。Grama 的例子从 010 到 111：两个编号的最高 bit 和最低 bit 不同，先改最高 bit 到 110，再改最低 bit 到 111，两步。

两者都是 dimension-order routing：先把一个 dimension 走完，再走下一个。它们的好处是不会 deadlock。在 mesh 上，一个 packet 占着一条 link 等下一条 link 空出来；如果四个 packet 绕着一个方格，每个都占着自己脚下的 link、等着前面那个 packet 占着的 link，就形成 circular wait，谁也走不动。

::fig[cs3210-turns] 左：四个 packet 各占一条 link、各等下一条，四个等待围成一圈。右：XY routing 只允许从 X 方向转到 Y 方向，不允许从 Y 转回 X，这四个转弯里有两个被禁止，圈合不上。

这个圈里每个 packet 都要转一个弯，四个弯里一定有从 Y 方向转到 X 方向的（向上走之后向左，向下走之后向右）。XY routing 下 packet 一旦开始沿 Y 走就不再转回 X，这样的弯不存在，等待关系不能绕成一圈，[CS2106 第 4 站](../courses/CS2106.html#sema)的 circular wait 条件不成立。Torus 多了 wrap-around 的 link，每个 dimension 本身是一个 ring，只靠 dimension order 不够，还需要额外的 virtual channel 来打破 ring 上的圈（这一点凭我自己的知识）。

### Switching：一个 message 怎样过一个 switch

Grama 用三个参数描述一个 message 的时间：$t_s$ 是 startup time（两端准备 message、建立 route 的 overhead），$t_h$ 是 per-hop time（经过一个 switch 的 delay），$t_w$ 是 per-word transfer time（link bandwidth 的倒数）。$m$ 个 word 的 message 走 $l$ 跳：

- **Store-and-forward**：每个中间 node 收完整个 message 才往下一跳转发，每一跳都要 $mt_w+t_h$：

$$t_\text{comm}=t_s+(mt_w+t_h)\,l$$

- **Cut-through**：message 切成很小的 flit，第一个 flit 带着 header 一路开路，后面的 flit 紧跟着，像 pipeline 一样各段 link 同时在传：

$$t_\text{comm}=t_s+l\,t_h+m\,t_w$$

算一个：$t_s=1\ \mu$s，$t_h=50$ ns，link 1 GB/s 即 $t_w=1$ ns/byte，$m=4096$ byte，走 $4\times4$ mesh 的 diameter $l=6$ 跳。Store-and-forward 是 $1+6\times(4.096+0.05)=25.9\ \mu$s；cut-through 是 $1+6\times0.05+4.096=5.40\ \mu$s。差别在于 $mt_w$ 这一大项，store-and-forward 每跳付一次，cut-through 只付一次。

::fig[cs3210-switching] 上面这个例子画出来：4096 byte 走 6 跳。上：store-and-forward，每段 link 等前一段传完才开始，25.9 μs。下：cut-through，6 段 link 几乎同时在传，5.40 μs，只比一跳多几个 $t_h$。

Cut-through 下 $l\,t_h$ 通常远小于 $mt_w$，于是常用的近似就是 $t_\text{comm}=t_s+mt_w$，与走几跳无关，这就是第 8 站 $\alpha+m\beta$ 的来历（$\alpha=t_s$，$\beta=t_w$）。这个近似只在 network 没有 congestion时成立；几个 message 共用一条 link 时，$t_w$ 要乘上共用的个数。CMU 18-344 区分了几种做法：circuit switching 事先预留整条路径；virtual cut-through 在 header 被挡住时把整个 packet 存在当前 switch 里；wormhole 只存几个 flit，header 被挡住时整串 flit 停在沿途的几个 switch 里，占着这些 link（head-of-line blocking），buffer 很省，latency 对大 message 几乎与距离无关。

### Topology 决定 algorithm：mesh 上的 sorting

最快的 sequential sorting 是 $O(n\log n)$。把 $n$ 个数放在 $n$ 个 PE 排成的 linear array 上，每个 PE 只能和左右邻居比较交换，用 odd-even transposition sort：奇数步让每一对 $(1,2),(3,4),\ldots$ 比较，小的留左边；偶数步对 $(2,3),(4,5),\ldots$ 做同样的事。$n$ 步之后排好，时间 $O(n)$。

证明 $n$ 步就够用的是 0-1 sorting lemma：一个只由 compare-exchange 组成、比较哪两个位置不依赖 data 的 algorithm（oblivious），如果能排好所有只含 0 和 1 的 input，就能排好任意 input。于是只要看 0 和 1：最右边的那个 1 最晚从第 2 步起每一步右移一格，第 $k$ 个 1 最晚在第 $k$ 步之后开始一路右移，$n$ 步之内所有 1 都到了右端。

在 $\sqrt n\times\sqrt n$ 的 mesh 上可以更快。目标是 snake order：第 0 行从左到右递增，第 1 行从右到左递增，以此类推。Shear sort 交替做两种 phase：

1. Row phase：偶数行（0、2、……）从小到大排，奇数行从大到小排；
2. Column phase：每一列从上到下从小到大排。

每个 phase 里每一行（或列）就是一个长 $\sqrt n$ 的 linear array，用 odd-even transposition sort，$\sqrt n$ 步。

::fig[cs3210-shear] 16 个数在 $4\times4$ mesh 上的 shear sort。左边的大格子动起来依次是开始、第 1 个 row phase、column phase、第 2 个 row phase、column phase、第 3 个 row phase，最后按 snake order 读出 1 到 16；右边六个小格子是每一步的结果，框出的是当前这一步。

图里这组数正好要用满 $\log_216+1=5$ 个 phase。为什么 $\log n+1$ 个 phase 就够，仍然看 0 和 1。全是 0 或全是 1 的 row 叫 clean，两种都有的叫 dirty。全 0 的 clean row 会停在上面、全 1 的停在下面，以后的 phase 不再动它们，只需要看中间的 dirty row。一个 row phase 之后，相邻的两个 dirty row 一个是 $0\cdots01\cdots1$、一个是 $1\cdots10\cdots0$（方向相反）；接着的 column phase 在这两行之间，每一列要么把一个 1 放到下面、0 放到上面，要么两个一样不动，结果这两行里至少有一行变成 clean。所以每一对 row phase 加 column phase，dirty row 至少减半。开始最多 $\sqrt n$ 个 dirty row，$2\log_2\sqrt n=\log_2n$ 个 phase 之后只剩 1 个，最后一个 row phase 把它排好，共 $\log_2n+1$ 个 phase，时间

$$\sqrt n\,(\log_2n+1)$$

和 linear array 的 $n$ 步比：$n=16$ 时是 $4\times5=20$ 步，反而比 16 步多；$n=1024$ 时 $32\times11=352$ 对 1024；$n=2^{20}$ 时 $1024\times21=21504$ 对 1048576。Topology 多出来的 link，在 $n$ 够大时才变成速度。

### SPMD 与六个 function

一个 MPI 程序启动时同一个 executable 在 $p$ 个 process 上各跑一份（SPMD）。Lab 里用 Slurm 启动，例如 `srun --ntasks=4 --nodes=2 ./bcast`：4 个 process 分在 2 个 node 上。Process 之间没有 shared variable，所有交换都通过 function call。CS267 说只用六个 function 就能写很多程序：

```c
#include <mpi.h>
#include <stdio.h>
int main(int argc, char **argv) {
    int rank, size, value;
    MPI_Init(&argc, &argv);
    MPI_Comm_rank(MPI_COMM_WORLD, &rank);   // 我是第几个：0 .. size-1
    MPI_Comm_size(MPI_COMM_WORLD, &size);   // 一共几个
    if (rank == 0) {
        value = 123456;
        MPI_Send(&value, 1, MPI_INT, 1, 0, MPI_COMM_WORLD);
    } else if (rank == 1) {
        MPI_Status status;
        MPI_Recv(&value, 1, MPI_INT, 0, 0, MPI_COMM_WORLD, &status);
        printf("rank 1 received %d\n", value);
    }
    MPI_Finalize();
}
```

`MPI_Send(buf, count, datatype, dest, tag, comm)`：data 用（起始 address、个数、datatype）描述，不用 byte 数，这样不同机器之间可以转换格式。`tag` 是程序员定的整数，接收方用它区分不同用途的 message，可以用 `MPI_ANY_TAG` 接收任意 tag，用 `MPI_ANY_SOURCE` 接收任意来源；实际的来源和 tag 从 `status` 里读。`comm` 是 communicator：一组 process 加上一个 context，message 只在同一个 communicator 里匹配。`MPI_COMM_WORLD` 包含所有 process。Library 内部用自己的 communicator，就不会误收用户程序的 message，这是 context 比 tag 强的地方：tag 可以被 wildcard 匹配，context 不能。

顺序上 MPI 只保证一件事：同一对 sender 和 receiver 之间、在同一个 communicator 上，先发的先匹配（non-overtaking）。三个以上 process 时，rank 1 和 rank 2 各发给 rank 0 一个 message，哪个先到没有保证。

### Send 什么时候返回

`MPI_Recv` 在 data 完全收到 buffer 里之后返回。`MPI_Send` 是 blocking 的，意思是它返回时 send buffer 可以被改写了，但 message 不一定已经被接收。要做到这一点有两种 implementation：

- **Synchronous**：send 等到对方开始接收、data 送过去才返回，不需要额外的 buffer；
- **Buffered（asynchronous）**：send 把 data 拷进一个 system buffer 就返回，之后由 MPI 在后台送出。

标准的 `MPI_Send` 两种都可以，由 implementation 按 message 大小选：小 message 拷进 buffer 立即返回（eager），大 message 等对方开始接收（rendezvous）。程序员可以指定：`MPI_Ssend` 一定 synchronous；`MPI_Bsend` 用程序员自己提供的 buffer；`MPI_Rsend` 要求对方已经开始接收，否则行为未定义。

Non-blocking 的 `MPI_Isend`、`MPI_Irecv` 只是“开始”一次 communication，立即返回一个 request，程序可以先去做别的计算，之后用 `MPI_Wait`（或 `MPI_Waitall`）等它完成，或者用 `MPI_Test` 查一下。在完成之前不能碰这个 buffer：send 的 buffer 可能还没送走，recv 的 buffer 可能还没写完。

::fig[cs3210-sendmodes] Sender 和 receiver 的时间线。Synchronous send 要等 receiver 调用 `MPI_Recv`；buffered send 拷进 buffer 就返回；non-blocking send 立即返回，计算和传输重叠，`MPI_Wait` 处才确认完成。

### 一个 ring 为什么会卡住

回到开头第三次实验，Tutorial 4 的 `q1a.c`：

```c
left  = (rank - 1 + p) % p;
right = (rank + 1) % p;
MPI_Send(send_buffer1, size, MPI_CHAR, left,  TAG_LEFT, MPI_COMM_WORLD);
MPI_Recv(recv_buffer1, size, MPI_CHAR, right, TAG_LEFT, MPI_COMM_WORLD, &status);
// 接着向右发、从左收，结构相同
```

如果 `MPI_Send` 是 synchronous 的，rank $r$ 的 send 要等 rank $r-1$ 调用 `MPI_Recv`；而 rank $r-1$ 自己正卡在它的 `MPI_Send` 上，要等 rank $r-2$；一路下去绕回 rank $r$。每个 process 都在等左边的 process，左边的又在等它的左边，[CS2106 第 4 站](../courses/CS2106.html#sema)的四个条件全部满足，最关键的是 circular wait。Tutorial 给了三种修法：

**1. 奇偶交错（`q1c.c`）。** Even rank 先 send 再 recv，odd rank 先 recv 再 send。$p=4$ 时第一轮 rank 0 发给 3、rank 2 发给 1（3 和 1 正在 recv），第二轮 rank 1 发给 0、rank 3 发给 2，两轮完成。$p$ 是奇数时 rank 0 和 rank $p-1$ 都是 even、又是邻居，多一轮：$p=3$ 时依次是 2 → 1、0 → 2、1 → 0，三轮。

**2. 最后一个 rank 反过来（`q1c_rh.c`）。** 只有 rank $p-1$ 先 recv 后 send，其余照旧。不会 deadlock，但变成了一条链：第一轮只有 rank 0 发给 rank $p-1$ 能完成；rank 0 发完才开始 recv，于是第二轮 rank 1 发给 rank 0；然后 rank 2 发给 rank 1……一共 $p$ 轮，每一轮只有一个 message 在传。$p=4$ 时 4 轮，奇偶交错只要 2 轮。

**3. Non-blocking（`q1d.c`）。** 四个操作都换成 `MPI_Isend`、`MPI_Irecv`，最后 `MPI_Waitall(4, reqs, stats)`。开始 communication 不会 block，所有 process 都能把 recv 摆出来，所有 message 一轮就能同时完成。

::fig[cs3210-ringfix] 4 个 rank 的两种修法，每一轮完成的 message 用实线箭头。动起来时左边（奇偶交错）两轮完成，右边（最后一个 rank 反过来）一轮只完成一个，要 4 轮。

CS267 还给了第四种：`MPI_Sendrecv` 把一次 send 和一次 recv 交给 MPI 一起做，由 MPI 安排它们不互相 block，ring 上的 shift 正是它的用途。

:::wrong 这个 ring 程序在 lab 机器上跑完了、没有卡住，所以它没有 deadlock
`q1a.c` 里每个 message 只有 20 个 char。这么小的 message，`MPI_Send` 按 eager 方式拷进 system buffer 就返回，每个 process 都能走到 `MPI_Recv`，程序正常结束。把 `MPI_Send` 换成 `MPI_Ssend`，或者把 `SIZE` 加大到超过 implementation 的 eager limit，同一个程序就会卡住。CS267 把这种“能不能结束取决于 system buffer 够不够”的程序叫 unsafe。正确性不能依赖 buffer 的大小，要用上面三种写法之一。
:::

### Communication 的代价：$\alpha+m\beta$

第 7 站推出，network 没有 congestion、用 cut-through 时，一个 $m$ byte 的 message 用时约为 $t_s+mt_w$。CS267 把它写成

$$T(m)=\alpha+m\beta$$

$\alpha$ 是 latency（含两端 software 的 overhead），$\beta$ 是每个 byte 的时间（bandwidth 的倒数），并假设 topology 无关。CS267 列的实测里，Gigabit Ethernet 上的 MPI 是 $\alpha=5.854\ \mu$s、$\beta=0.00872\ \mu$s/byte（约 115 MB/s）。代进去：

- 8 byte：$5.854+8\times0.00872=5.92\ \mu$s，几乎全是 $\alpha$；
- 1 MB（$10^6$ byte）：$5.854+8720=8726\ \mu$s，几乎全是 $m\beta$；
- 两项相等的 message 大小是 $\alpha/\beta=671$ byte。

所以 1000 个 8-byte 的 message 要 $1000\times5.92=5924\ \mu$s，合成一个 8000-byte 的 message 只要 $5.854+8000\times0.00872=75.6\ \mu$s。一般 $\alpha\gg\beta\gg$ 一次 flop 的时间，这就是第 3 站 agglomeration 要合并 message 的定量理由。

CS267 还讲了另外两种 computation model。PRAM 假设每次 memory access 都是一个 cycle、没有 memory hierarchy，只适合用来检查一个 algorithm 有没有足够的 parallelism。LogP 把 $\alpha$ 拆开：发送方的 overhead $o_\text{send}$、network 的 latency $L$、接收方的 overhead $o_\text{recv}$，一个 message 的 end-to-end latency 是 $o_\text{send}+L+o_\text{recv}$；再加上 gap $g$，即连续两次发送之间的最小间隔，连发 $n$ 个 message 要 $(o_\text{send}+L+o_\text{recv}-g)+ng$，对应 $\alpha+n\beta$ 的形式。

### Collective operation

一个 communicator 里所有 process 都要调用同一个 collective function，没有 tag。按用途分三类：synchronization（`MPI_Barrier`）、data movement、computation。

::fig[cs3210-coll] 4 个 rank，每一行是一个 rank 的 buffer。左边是调用前，右边是调用后；A、B、C、D 是各 rank 原来的 data，$\Sigma$ 是按 reduction 的 operator 合起来的结果。

- `MPI_Bcast`：root 的一份 data 复制给所有 rank。
- `MPI_Scatter`：root 的 data 切成 $p$ 段，第 $i$ 段给 rank $i$。`MPI_Gather` 反过来，把各 rank 的一段收集到 root。`MPI_Allgather`：收集之后每个 rank 都有全部。
- `MPI_Alltoall`：每个 rank 给每个其他 rank 各一段不同的 data（total exchange），例如一个 rank 一行的 matrix 做 transpose。
- `MPI_Reduce`：把各 rank 的 data 用一个 associative 的 operator（`MPI_SUM`、`MPI_MAX`、`MPI_MAXLOC`……）合起来放在 root。`MPI_Allreduce`：结果给所有 rank。`MPI_Scan`：rank $k$ 得到 rank 0 到 $k$ 的合并结果（prefix）。

CS267 的例子是用中点法算 $\int_0^1\frac{4}{1+x^2}dx$，和第 2 站 OpenMP 的 pi 程序一样，只是 data 在不同的 process 里：

```c
MPI_Bcast(&n, 1, MPI_INT, 0, MPI_COMM_WORLD);         // rank 0 读入 n，发给所有人
double h = 1.0 / n, sum = 0.0;
for (int i = myid + 1; i <= n; i += numprocs) {        // cyclic 地分 interval
    double x = h * ((double)i - 0.5);
    sum += 4.0 / (1.0 + x * x);
}
double mypi = h * sum, pi;
MPI_Reduce(&mypi, &pi, 1, MPI_DOUBLE, MPI_SUM, 0, MPI_COMM_WORLD);   // 只有 rank 0 得到 pi
```

`MPI_Bcast` 由所有 rank 调用，不是 root 的“群发”：root 参数告诉每个 rank 谁是发送方。

### Broadcast 怎样实现，以及开头第四次实验

Lab 5 的 `my_bad_bcast` 让 rank 0 用一个 loop 依次 `MPI_Send` 给每个 rank。Root 的 link一次只能送一份，$p$ 个 rank 时用时

$$T_\text{naive}=(p-1)(\alpha+m\beta)$$

Recursive doubling 的做法：第一轮 root 发给一个 rank，现在两个 rank 有 data；第二轮这两个各发给一个还没有的，四个有；每一轮有 data 的 rank 数翻倍，$\log_2p$ 轮：

$$T_\text{tree}=\log_2p\,(\alpha+m\beta)$$

::fig[cs3210-btree] 8 个 rank 的 recursive doubling broadcast。动起来依次是第 1、2、3 轮，每一轮有 data 的 rank 数翻倍。

Message 很大时还可以更好：先把 data 切成 $p$ 段 scatter 出去，每个 rank 拿 $m/p$，再做一次 all-gather 让每个 rank 拼出全部。Grama 给出这样做的时间：

$$T_\text{scatter+allgather}=2\Big(\alpha\log_2p+\beta\,m\,\frac{p-1}{p}\Big)$$

和 tree 比，$\beta$ 那一项从 $m\log_2p$ 降到约 $2m$，与 $p$ 几乎无关。

把开头第四次实验代进去：$m=2\times10^7$ byte，$p=4$，4 个 rank 在 4 个 node 上，用 CS267 的 GigE 参数。这样用是有根据的：从 naive 版本的实测反推，每个 byte 花 $0.515/(3\times2\times10^7)=8.58$ ns，约 117 MB/s，正是 Gigabit Ethernet 的量级，和 CS267 的 8.72 ns/byte 几乎一样（lab cluster 的 network 规格我没有查到）：

| 做法 | model | 预测 | 实测（`--nodes=4`） |
|---|---|---|---|
| `my_bad_bcast` | $3(\alpha+m\beta)$ | 0.523 s | 0.515 s |
| recursive doubling | $2(\alpha+m\beta)$ | 0.349 s | |
| scatter + allgather | $2(2\alpha+\tfrac34m\beta)$ | 0.262 s | `MPI_Bcast` 0.248 s |

$\alpha$ 在这里可以忽略，三种做法的比是 $3:2:1.5$。实测的 `MPI_Bcast` 快了 2.08 倍，和 scatter + allgather 预测的 2 倍吻合，比 recursive doubling 的 1.5 倍好。这次 Open MPI 实际选了哪个 algorithm，仓库里没有记录，我也没有查到；上面只说明实测和这个 model 吻合。同一个 lab 在 `--nodes=2`、`--nodes=3` 下测到的倍数是 1.70 和 1.57，那时有几个 rank 在同一个 node 上，它们之间的 message 不走 network，model 不再适用。

### 其他 collective 的 cost

Grama 在 ring 和 hypercube 上推了每一种 collective 的时间（single-port、双向 link、没有 congestion）。以 hypercube 为主：

| 操作 | hypercube 上的时间 | 做法 |
|---|---|---|
| one-to-all broadcast、all-to-one reduction | $(t_s+t_wm)\log p$ | recursive doubling；reduction 是倒过来 |
| all-to-all broadcast（all-gather） | $t_s\log p+t_wm(p-1)$ | 每轮和一个 dimension 上的邻居交换，message 每轮翻倍 |
| scatter、gather | $t_s\log p+t_wm(p-1)$ | 每轮把手上的 data 分一半给邻居 |
| all-reduce | $(t_s+t_wm)\log p$ | 和 all-to-all broadcast 一样的 pattern，但 message 不变长 |
| all-to-all personalized | $(t_s+t_wm)(p-1)$ | 第 $j$ 轮 node $i$ 和 node $i\oplus j$ 交换 |

All-to-all broadcast 的时间要加一下：第 $i$ 轮每个 node 已经攒了 $2^{i-1}$ 份 data，整包发给第 $i$ 维上的邻居，

$$\sum_{i=1}^{\log p}\big(t_s+2^{i-1}t_wm\big)=t_s\log p+t_wm\,(1+2+\cdots+2^{\log p-1})=t_s\log p+t_wm(p-1)$$

Ring 上的 all-to-all broadcast 是每个 node 把收到的东西转给下一个，$p-1$ 轮，$(t_s+t_wm)(p-1)$。Ring 上 bandwidth 最优的 all-reduce（reduce-scatter 接 all-gather）和它在 GPU 训练里的用法见 [CS336 第 6 站](../courses/STANFORD-CS336.html#parallel)。

**Prefix sum。** Tutorial 4 的 `q2.c` 让 200 个 rank 各拿一个数（rank $k$ 拿 $k$），用一条链算 prefix sum：rank $k$ 从 rank $k-1$ 收一个 200 个 int 的 array，加上自己的数，再整个 array 发给 rank $k+1$。链上的 199 个 message 一个接一个，每个 800 byte，按上面的 GigE 参数是 $199\times(5.854+800\times0.00872)=2553\ \mu$s；只发需要的那一个 int 也要 $199\times5.89=1172\ \mu$s，因为 bottleneck 是链本身。Hypercube 上的 prefix sum 借用 all-to-all broadcast 的 pattern：每个 node 维护 result（自己的 prefix）和 msg（自己所在子立方体的总和），第 $i$ 轮和第 $i$ 个 dimension 上的伙伴交换 msg，msg 加上对方的，result 只在对方编号更小时才加。8 个 node、node $k$ 拿 $k$：

| | node 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| 开始 result | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
| 第 1 轮后 result | 0 | 1 | 2 | 5 | 4 | 9 | 6 | 13 |
| 第 1 轮后 msg | 1 | 1 | 5 | 5 | 9 | 9 | 13 | 13 |
| 第 2 轮后 result | 0 | 1 | 3 | 6 | 4 | 9 | 15 | 22 |
| 第 2 轮后 msg | 6 | 6 | 6 | 6 | 22 | 22 | 22 | 22 |
| 第 3 轮后 result | 0 | 1 | 3 | 6 | 10 | 15 | 21 | 28 |

第 1 轮 node 3 和 node 2 交换，2 比 3 小，node 3 的 result 加上 2 变成 5；node 2 收到 3，但 3 比 2 大，result 不变，msg 变成 5。3 轮之后每个 node 的 result 都是 $0+1+\cdots+k$。$\log_2p$ 轮，每轮一个 int 的 message；200 个 rank 时 $\lceil\log_2200\rceil=8$ 轮，约 $8\times5.89=47\ \mu$s。`MPI_Scan` 就是这个操作。

### Communicator 与 Cartesian topology

Collective 作用在一个 communicator 的全部 process 上。只想在一部分 process 之间做，就造一个新的 communicator。Lab 5 的 `new_comm.c`：8 个 process，从 `MPI_COMM_WORLD` 取出 group，rank 0 到 3 组成一个新 group、4 到 7 组成另一个（`MPI_Group_incl`），各自建一个 communicator（`MPI_Comm_create`），再在新 communicator 上 `MPI_Allreduce` 求每个 process 原 rank 的和。实测输出：

```
rank= 0 newrank= 0 recvbuf= 6
rank= 3 newrank= 3 recvbuf= 6
rank= 4 newrank= 0 recvbuf= 22
rank= 7 newrank= 3 recvbuf= 22
```

$0+1+2+3=6$，$4+5+6+7=22$。原来的 rank 4 在新的 communicator 里是 rank 0：一个 process 可以同时属于几个 group，在每个 group 里有不同的 rank。

很多程序的 process 天然排成 grid（第 3 站的 checkerboard）。`MPI_Cart_create` 把 communicator 里的 process 排成一个指定 dimension 数的 grid，之后可以按 coordinate 找邻居。Lab 5 的 `cart.c`：16 个 process 排成 $4\times4$，`periods = {0, 0}` 表示两个 dimension 都不 wrap around，`reorder = 0` 表示不重新编号。Rank $r$ 的 coordinate 是 $(\lfloor r/4\rfloor,\ r\bmod4)$；`MPI_Cart_shift(cartcomm, 0, 1, &up, &down)` 给出第 0 个 dimension 上前后的邻居，`MPI_Cart_shift(cartcomm, 1, 1, &left, &right)` 给出第 1 个 dimension 的。实测输出里 rank 5（coordinate (1, 1)）的邻居是 up 1、down 9、left 4、right 6；rank 0（coordinate (0, 0)）是 up −2、down 4、left −2、right 1。

::fig[cs3210-cart] `cart.c` 的 $4\times4$ grid，每格是 rank 和 coordinate。Rank 5 的四个邻居用浅色标出；rank 0 往上、往左没有邻居，得到 `MPI_PROC_NULL`（这里是 −2）。

−2 是这个 Open MPI 里 `MPI_PROC_NULL` 的值。对 `MPI_PROC_NULL` 的 send 和 recv 什么都不做、立即返回，所以程序里四个方向的 `MPI_Isend`、`MPI_Irecv` 可以不加判断地对所有 rank 一视同仁，边界上的 process 自动少收发几个 message，`inbuf` 里对应的位置保留初值 `MPI_PROC_NULL`。如果把 `periods` 设成 `{1, 1}`，grid 变成 torus，rank 0 的 up 就是 rank 12。
