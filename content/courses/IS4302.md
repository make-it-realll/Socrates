先看三件事。

**第一件。** 一张电子照片可以复制一百份，每份都和原件一模一样。如果“一个 coin”只是一个文件，持有人把它发给 Bob 之后，手里还留着一份，可以再发给 Carol。数字世界里复制几乎不要成本，所以任何数字形式的 money 首先要回答：怎样阻止同一个 coin 被花两次。这叫 double spending problem。

**第二件。** Bank 早就解决了这个问题：balance 不在你手里，在 bank 的 ledger 上，转账就是 bank 在 ledger 上一边减、一边加。代价是所有人都要相信这个 ledger 的维护者：它不乱记、不冻结、不拒绝服务、不在倒闭时把账本一起带走。

**第三件。** 2023 年 3 月 10 日晚，issue USDC 的 Circle 宣布有 33 亿 USD 的 reserve 困在刚倒闭的 Silicon Valley Bank，约占它 reserve 的 8%。按 reserve 算，每个 USDC 最坏也值 0.92 USD 左右，但第二天它在市场上跌到了 0.86。

这门课要回答的问题由这三件事串起来：在没有一个大家都信任的维护者时，怎样让很多互不信任的人维护同一个 ledger（第 1 到 4 站）；ledger 上除了记账还能跑什么 program，这些 program 能做什么、不能做什么（第 5、6 站）；用这些技术造出来的“money”在经济上靠什么维持价值，又在哪里失效，和 central bank 发的 money 有什么不同（第 7、8 站）。NUS 的课程描述把这条线概括为：先弄清 blockchain 在技术上怎样工作，再评估一个 blockchain application 的 business、economic 和 financial performance 与它的技术设计之间的关系。前半学期在 Ethereum 上做一个 application，后半学期分析已有的 application。

## [hash] Double spending、signature 与 hash pointer

:::skip
能说清 digital signature 为什么挡不住 double spending、hash pointer 为什么能让篡改历史被发现，并能手算一个 Merkle proof，就可以去第 2 站。
:::

### 先造一个最简单的 coin，看它在哪里坏掉

Princeton 的书从一个故意做得很简陋的 coin 开始，叫 GoofyCoin。规则只有两条：

1. Goofy 可以随时造新 coin：签一条“CreateCoin [一个新的 ID]”。
2. 谁持有一个 coin，谁就能把它转给别人：签一条“把这个 coin 付给 public key X”，其中“这个 coin”用一个指向上一条记录的 pointer 表示。

验证一个 coin 是否有效，就顺着 pointer 一路往回查，每一步的 signature 都对得上，最后到达 Goofy 的 CreateCoin。

这里用到的 digital signature 是三个 algorithm：$\mathrm{Gen}()$ 生成一对 key $(sk,pk)$；$\mathrm{Sign}(sk,m)$ 对 message $m$ 生成 signature $\sigma$；$\mathrm{Verify}(pk,m,\sigma)$ 输出 accept 或 reject。它的安全性是：只看到 $pk$ 和一些别的 message 的 signature，造不出一条新 message 的 signature。和手写签名的关键区别在于，$\sigma$ 依赖于 $m$，把一份文件上的 signature 剪下来贴到另一份上，Verify 会 reject。

现在 Alice 持有一个 GoofyCoin。她签一条“把它付给 Bob”，又签一条“把它付给 Chuck”。两条都是她亲手签的，都能通过 Verify。Bob 和 Chuck 各自顺着 pointer 往回查，都觉得这个 coin 是自己的。

::fig[is4302-goofy] Alice 对同一个 coin 签了两条转账。每一条单独检查都有效。

:::wrong Digital signature 能防止 double spending
Signature 证明的是“这个 coin 的主人同意了这笔转账”，它回答 authorization 的问题。Double spending 是另一个问题：主人同意了两次，而两次互相矛盾。要发现矛盾，必须知道**所有**已经发生的转账。Nakamoto 论文第 2 节说的就是这一点：确认一笔 transaction 没有发生过的唯一办法，是知道所有 transaction。Signature 是局部的，double spending 是全局的。
:::

### 加一个记账人：ScroogeCoin

既然要知道所有转账，就让一个人把它们全记下来。ScroogeCoin 里，Scrooge 维护一个只能往后追加的 ledger，签上 signature 后公开。一笔 PayCoins transaction 只有出现在这个 ledger 上才算数，而 Scrooge 只接受满足三条的 transaction：被消费的 coin 有效且**尚未花掉**；消费掉的总值等于新造出的总值；被消费的每个 coin 的主人都签了名。

第一条就是 double spending 的解法：Alice 的第二笔转账会被 Scrooge 拒绝。

代价也清楚：Scrooge 可以拒绝替某人记账（censorship），可以收任意的 fee，可以给自己造 coin，可以哪天不干了。这正是开头第二件事里 bank 的位置。整个 Bitcoin 的设计可以看成一个问题：把 Scrooge 换成一群互不信任、随时可以加入和离开的人，还能不能得到同一个 ledger？

在换掉 Scrooge 之前，先解决一个更小的问题：即使 Scrooge 诚实，他公开的 ledger 怎样防止事后被人改动？

### Hash function

Hash function $H$ 把任意长的 input 映射成固定长度的 output。SHA-256 的 output 是 256 bit，也就是 32 byte、64 个 hex 位。用 `python3` 实算：

| input | SHA-256 |
|---|---|
| `hello` | `2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824` |
| `hellp` | `fdd7585e08c4e2afd71dcabdb4636c89d557a3f42db9e2040c8bbd1708aa4ce7` |

Input 只改了最后一个字母，256 个 output bit 里有 131 个变了，差不多是一半，看不出任何关系。

Blockchain 需要的性质是 **collision resistance**：找不到两个不同的 input $x\ne x'$ 使 $H(x)=H(x')$。Collision 一定存在，因为 input 无穷多而 output 只有 $2^{256}$ 种；要求的是“找不到”。

256 bit 为什么够？试 $n$ 个不同的 input，一共有 $\binom n2\approx n^2/2$ 对。如果 output 像随机的，每一对相等的 probability 是 $2^{-256}$，所以 collision 的期望个数约为

$$\frac{n^2}{2}\cdot2^{-256}=\frac{n^2}{2^{257}}$$

要让它到 1，$n$ 得到 $2^{128.5}$ 左右。这叫 birthday bound：256 bit 的 hash 只有 128 bit 的 collision 安全性，但 $2^{128}$ 次 hash 仍然远超全世界的 computing power。

用一次：Alice 把一份很长的文件 $f$ 的 hash $h=H(f)$ 公开，32 byte。以后她拿出一份 $f'$，任何人算一下 $H(f')$ 是否等于 $h$。如果相等而 $f'\ne f$，Alice 就找到了一个 collision。所以 $h$ 把 Alice **绑定**在 $f$ 上，这叫 commitment。

:::wrong 改动一点 input，hash 也只变一点，所以相近的数据有相近的 hash
上面的表就是反例：`hello` 和 `hellp` 的 hash 第一个 hex 位就不同，131 个 bit 不同。`Alice pays Bob 5` 和 `Alice pays Bob 6` 的 SHA-256 也恰好有 131 个 bit 不同。一个 cryptographic hash 如果让相近的 input 有相近的 output，就可以通过不断微调 input、看 output 往哪边靠来逼近目标，collision resistance 和下一站的 proof of work 都会失效。
:::

### Hash pointer：把 commitment 串起来

普通 pointer 记的是“数据在哪”。**Hash pointer** 再加一项：数据的 hash。顺着它取到数据时，可以重算 hash 检查数据有没有被改过。

把 ledger 按 block 分组，每个 block 里放一个指向前一个 block 的 hash pointer，就得到一条 block chain。

::fig[is4302-chain] 上面一行是原来的三个 block，下面一行把 block 2 里的 5 改成了 6。图里的 hash 是对 `prev=…;data=…` 这样的字符串实际算出的 SHA-256 前 8 位。

Block 2 的内容一改，它的 hash 就从 `e0011e51` 变成 `391fb577`，而 block 3 里存的还是 `e0011e51`，对不上。要掩盖，就得把 block 3 的 prev 也改掉，于是 block 3 的 hash 变了，block 4 又对不上……一直要改到最新的 block。所以只要把**最新一个 block 的 hash**（叫 head）存在一个改不了的地方，整条历史中任何一处改动都会被发现。

这把“保护整个 ledger”化简成了“大家对一个 32 byte 的 head 达成一致”。下一站讨论的 consensus，本质上就是在争这个 head。

### Merkle tree：一个 block 里有几千笔 transaction

一个 block 里有很多 transaction。CS251 举的 Bitcoin block 916096 里有 4,811 笔。如果 block 的 hash 直接对全部 transaction 算，要证明“某一笔在这个 block 里”，就得把 4,811 笔全拿出来。

Merkle tree 把它们两两 hash，再把结果两两 hash，一直到只剩一个 root。

::fig[is4302-merkle] 四笔 transaction 的 Merkle tree，所有 hash 都是实算的。要证明 tx3 在里面，只需要给出深色的两个 hash。

用 `tx1` 到 `tx4` 四个字符串实算（拼接的是 32 byte 的原始 digest，表里只写前 8 个 hex 位）：

$$L_i=H(\texttt{tx}i),\qquad h_{12}=H(L_1\,\|\,L_2),\qquad h_{34}=H(L_3\,\|\,L_4),\qquad \text{root}=H(h_{12}\,\|\,h_{34})$$

| node | 值 |
|---|---|
| $L_3=H(\texttt{tx3})$ | `1f3cb18e…` |
| $L_4$ | `41b637cf…` |
| $h_{12}$ | `bbea820f…` |
| $h_{34}$ | `5709445d…` |
| root | `ea59a369…` |

Verifier 手里只有 root `ea59a369…`。Prover 声称 tx3 在里面，给出 proof $(L_4,\ h_{12})$。Verifier 自己算三次 hash：

1. $H(\texttt{tx3})=$ `1f3cb18e…`
2. $H(\texttt{1f3cb18e…}\,\|\,\texttt{41b637cf…})=$ `5709445d…`
3. $H(\texttt{bbea820f…}\,\|\,\texttt{5709445d…})=$ `ea59a369…`，等于 root，接受。

如果有人把 tx3 换成 `tx3*`，第 1 步得到 `6d767aea…`，一路算上去 root 变成 `b15806ee…`，不等于 `ea59a369…`，拒绝。要让假的 tx3 通过，必须在某一层找到 collision。

Proof 的长度是 tree 的高度。$n$ 个 leaf 需要 $\lceil\log_2n\rceil$ 个 hash。Block 916096 的 4,811 笔：$2^{12}=4096<4811\le8192=2^{13}$，所以 proof 是 13 个 hash，$13\times32=416$ byte，而不是几 MB 的整个 block。

Bitcoin 的 block header 只有 80 byte：version（4）、prev（32）、Merkle root（32）、time（4）、bits（4）、nonce（4）。Prev 是 hash pointer，Merkle root 是对 block 内全部 transaction 的 commitment，bits 和 nonce 属于下一站。

:::edge Merkle proof 能证明“在”，不能证明“不在”
上面的 proof 证明 tx3 在 block 里。要证明某笔 transaction **不在**，普通的 Merkle tree 做不到，除非 leaf 按某种顺序排好，再给出夹住它的两个相邻 leaf 的 proof。这也是为什么第 4 站里检查“这个 output 有没有被花掉”要靠每个 node 自己维护的 UTXO set，而不是一个 proof。
:::

### 换掉 Scrooge 难在哪里

想让一群 node 轮流当 Scrooge：每轮选一个 node 提议下一个 block，其他 node 检查后接在后面。要回答两个问题。

**选谁？** 如果按“一个 node 一票”，attacker 可以凭空造出一百万个 node，这叫 Sybil attack。在一个任何人都能加入、没有身份登记的 network 里，node 的数目不能当作权重。CS251 的说法是：必须把权重绑在一种造不出来、很稀缺的资源上。Proof of work 用的是 hash power，proof of stake 用的是锁定的 coin（第 3 站）。

**选出的 node 作恶怎么办？** 它偷不了别人的 coin，因为偷要伪造 signature。它可以不收录某人的 transaction，但下一轮换了 honest 的 node，那笔 transaction 还是会进来。它真正能做的坏事是 double spending，后面细算。

### Mining 是一种抽签

Proof of work 的题目是：找一个 nonce，使

$$H(\text{header 的其余字段}\ \|\ \text{nonce})<T$$

$T$ 叫 target。Hash 的 output 像均匀随机的 256 bit 数，所以每试一次成功的 probability 是 $T/2^{256}$。CS251 把 difficulty 定义为 $D=2^{256}/T$，于是期望要试 $D$ 次。

缩小规模实算一次。要求 SHA-256 的 hex 表示以 4 个 0 开头，相当于 $T=2^{256}/16^4$，每次成功的 probability 是 $1/65536$。对字符串 `prev=ea59a369;root=ea59a369;nonce=N` 从 $N=0$ 往上试：

| 要求开头几个 0 | 期望尝试次数 | 实际找到的 nonce | 那个 hash 的开头 |
|---|---|---|---|
| 2 | 256 | 27 | `009d7ab1…` |
| 3 | 4,096 | 771 | `000af151…` |
| 4 | 65,536 | 34,407 | `0000167d…` |
| 5 | 1,048,576 | 3,066,429 | `00000360…` |

实际次数围绕期望值上下浮动，有时快有时慢，没有任何捷径，只能一个个试。这张表说明了 proof of work 的三个性质：

- **难算**：要求多一个 0，工作量乘 16。
- **难度可调**：Bitcoin 每 2016 个 block（约两周）调一次 $D$，新的 $D$ 等于旧的 $D$ 乘以“预期用时 ÷ 实际用时”，一次最多变 4 倍。比如上一轮只用了 12 天，$D$ 就乘 $14/12\approx1.17$。目标是平均 10 分钟出一个 block。
- **易验**：别人只要算一次 hash，看结果是不是小于 $T$。

谁先找到，谁就当这一轮的 Scrooge。一个 miner 占全网 hash power 的比例是 $\beta$，它赢下一轮的 probability 就是 $\beta$。按 hash power 抽签，造多少个假 node 都没用。

赢的人得到 block reward，写在 block 的第一笔 transaction（coinbase）里，这是新 BTC 唯一的来源，另外还收这个 block 里所有 transaction 的 fee。Reward 起初是 50 BTC，每 210,000 个 block（约四年）减半，现在是 3.125 BTC。Total supply 是

$$50\times210000\times\left(1+\tfrac12+\tfrac14+\cdots\right)=10{,}500{,}000\times2=21{,}000{,}000$$

### Longest chain rule 与 double spend

两个 miner 几乎同时找到 block 时，chain 会 fork。规则是：honest 的 node 永远接在**累计工作量最大**的那条 chain 后面（通常说成 longest chain）。较短那条上的 block 被丢弃。

现在看 double spend。Alice 向 merchant 买车，付款 tx1 进了一个 block。Merchant 等了几个 block 后发车。与此同时 Alice（或她雇的 miner）从 tx1 之前的那个 block 分出一条 branch，在里面放一笔冲突的 tx2，把同一个 coin 付回自己，私下去 mine。

::fig[is4302-fork] 公开的 chain 已经在 tx1 之后长了 6 个 block，attacker 私下这条还差 2 个。

如果私下这条最终比公开那条更长，Alice 把它公布，全网按 longest chain rule 切换过去，tx1 从历史里消失，merchant 的车已经发出去了。

这里看到 proof of work 让“重写历史”变贵的真正原因：要替换掉 $z$ 个 block，attacker 必须自己重新做这 $z$ 个 block 的 proof of work，而且在做的同时，honest 的 node 还在不停往公开那条上加 block。问题变成一场赛跑。

### Attacker 追上的 probability

设 honest node 合起来找到下一个 block 的 probability 是 $p$，attacker 是 $q=1-p$。把“attacker 落后几个 block”记为 deficit。每出一个新 block，deficit 以 probability $q$ 减 1，以 probability $p$ 加 1。

**第一步：从落后 $z$ 个开始，最终追平的 probability $a_z$。** 看下一个 block 是谁 mine 到的：

$$a_z=q\,a_{z-1}+p\,a_{z+1},\qquad a_0=1$$

试 $a_z=r^z$，代入后除以 $r^{z-1}$：

$$r=q+p\,r^2\quad\Longleftrightarrow\quad p\,r^2-r+q=0\quad\Longrightarrow\quad r=\frac{1\pm\sqrt{1-4pq}}{2p}$$

因为 $p+q=1$，$1-4pq=(p+q)^2-4pq=(p-q)^2$，所以两个 root 是

$$r=\frac{1+(p-q)}{2p}=\frac{2p}{2p}=1,\qquad r=\frac{1-(p-q)}{2p}=\frac{2q}{2p}=\frac qp$$

General solution 是 $a_z=A+B\,(q/p)^z$。当 $p>q$ 时，deficit 平均每个 block 增长 $p-q>0$，落后得越多越不可能追上，$z\to\infty$ 时 $a_z\to0$，所以 $A=0$；再由 $a_0=1$ 得 $B=1$：

$$a_z=\begin{cases}1,&p\le q\\[2pt](q/p)^z,&p>q\end{cases}$$

$p\le q$ 时 attacker 必然追上，这就是“51% attack”。$p>q$ 时追上的 probability 随 $z$ **指数**下降。

::fig[is4302-ruin] Deficit 是一条 random walk，0 是终点。$q=0.3$ 时从 $z$ 出发追平的 probability 每多落后一个 block 就乘 $3/7$。

**第二步：merchant 等 $z$ 个 block 时，attacker 已经私下 mine 了多少。** Merchant 看不到私下那条 chain。Honest 一方 mine 出 $z$ 个 block 的这段时间里，attacker 平均 mine 出 $z\cdot q/p$ 个（每个 honest block 期间 attacker 平均 mine $q/p$ 个）。Nakamoto 把 attacker 实际 mine 出的个数 $k$ 当作 mean 为 $\lambda=zq/p$ 的 Poisson random variable。已经 mine 了 $k$ 个，还差 $z-k$ 个；$k>z$ 时已经领先。所以

$$P=\sum_{k=0}^{z}\frac{\lambda^ke^{-\lambda}}{k!}\left(\frac qp\right)^{z-k}+\Pr[k>z]$$

**用一次：$q=0.1$，$z=1$。** $q/p=1/9$，$\lambda=1/9=0.1111$。

- $k=0$：probability $e^{-0.1111}=0.8948$，还差 1 个，追上的 probability $1/9$，乘积 $0.0994$。
- $k\ge1$：probability $1-0.8948=0.1052$，已经追平或领先，算作成功。

$P=0.0994+0.1052=0.2046$。Nakamoto 论文的表里 $z=1$ 一行正是 0.2045873。

**$q=0.3$，$z=6$。** $\lambda=6\times0.3/0.7=2.571$。逐项算：

| $k$ | Poisson probability | $(3/7)^{6-k}$ | 乘积 |
|---|---|---|---|
| 0 | 0.0764 | 0.0062 | 0.0005 |
| 1 | 0.1965 | 0.0145 | 0.0028 |
| 2 | 0.2527 | 0.0337 | 0.0085 |
| 3 | 0.2166 | 0.0787 | 0.0171 |
| 4 | 0.1392 | 0.1837 | 0.0256 |
| 5 | 0.0716 | 0.4286 | 0.0307 |
| 6 | 0.0307 | 1 | 0.0307 |

乘积之和是 0.1158，再加上 $\Pr[k>6]=0.0163$，$P=0.1321$。

::fig[is4302-race] 三种 $q$ 下 $P$ 随 $z$ 的变化，按上面的 formula 实算。纵轴是 log scale，所以指数下降画出来接近直线。

:::wrong 只要 attacker 的 hash power 不到 50%，double spend 就不可能
50% 是“必然成功”的门槛，不是“可能成功”的门槛。上面算过：$q=0.3$ 时 merchant 等 6 个 confirmation，attacker 仍有 13.2% 的机会；要压到 0.1% 以下得等 24 个，也就是 4 个小时。另外 CS251 lecture 5 指出，network 延迟会让 honest miner 同时 mine 出互相竞争的 block，浪费一部分 honest hash power，attacker 实际需要的比例比这个模型更低。2014 年 Ghash.IO 一个 mining pool 曾超过全网 50% 的 hash power，后来自愿让出了一部分。
:::

:::edge Confirmation 数应该随金额变
Attacker 的 payoff 是被 double spend 的金额，成本是 mine 私下那条 chain 的电费加上失败时放弃的 block reward。买一杯咖啡 0 个 confirmation 也许就够，卖一辆车要多等。6 不是一个推出来的常数，是一个经验上的折中，Princeton 的书也这样说。
:::

### Nakamoto consensus 给了什么，没给什么

CS251 把一个 consensus protocol 要求的性质归为两条：**safety**（任意两个 client 看到的 confirmed ledger，一个是另一个的 prefix）和 **liveness**（交给 honest node 的 transaction 在有限时间内进入所有人的 ledger，不能被永久 censor）。

Bitcoin 的结果是：在 network 延迟有已知上界、attacker hash power 比例 $\beta<1/2$、出块足够慢的条件下，safety 和 liveness 成立，失败的 probability 随 $k$ 指数下降。出块慢（10 分钟）正是为了让 network 延迟相对于出块间隔可以忽略。

它没有给的是 **finality**：一个 block 无论多深，被推翻的 probability 都不是 0，只是很小。另外，安全依赖于“大多数 hash power 是 honest 的”，而 proof of work 本身没有办法事后 punish 作恶的 miner，最多让他白花电费。这两点和巨大的能耗，是下一站 proof of stake 出现的理由。

:::back
Head 只要大家一致，历史就不能改，这是[第 1 站](#hash)的结论；这一站解决的是“大家怎样对 head 达成一致”。
:::

## [pos] Proof of stake 与 finality

:::skip
能用 quorum intersection 证明“2/3 的 signature 才 finalize”为什么 safe、作恶者为什么一定能被抓出来，并能说清 quorum 定高了会牺牲什么，就可以去第 4 站。
:::

### 换一种稀缺资源

Proof of work 的问题上一站已经列出：没有 finality，事后无法 punish，耗电。Proof of stake 把稀缺资源从 hash power 换成 coin：想参与 consensus，先把 coin 锁进一个 contract（stake）。被选为 leader 的 probability 和投票的权重都按 stake 算，当 leader 拿 reward，相当于 stake 的 interest。

关键的新东西是 punishment。Validator 的每一票都是一个 digital signature，签在“某个 epoch 的某个 block”上。如果一个 validator 给同一个 epoch 里两个冲突的 block 都签了名，这两个 signature 本身就是证据，任何人都可以提交，protocol 把他锁定的 stake 烧掉。这叫 **slashing**。Proof of work 里作恶的 miner 只是白花电费，proof of stake 里作恶的 validator 会被点名并没收 stake。

### 2/3 quorum 为什么 safe

CS251 用一个最简单的 protocol 说明：$n$ 个 validator，一个 block 得到至少 $2n/3$ 个 validator 的 signature 就 finalize。

假设出了事故：两个冲突的 block X、Y 都 finalize 了。设 X 的 signature 集合是 $A$，Y 的是 $B$，$|A|\ge2n/3$，$|B|\ge2n/3$。两个集合都在 $n$ 个 validator 里，所以

$$|A\cap B|\ \ge\ |A|+|B|-n\ \ge\ \frac{2n}3+\frac{2n}3-n=\frac n3$$

重叠的这些 validator 每人都签了两个冲突的 block，违反了规则。所以：只要作恶的 validator 少于 $n/3$，safety 就不会被破坏；一旦被破坏，至少能点名 $n/3$ 个作恶者，而且不会冤枉 honest 的 validator，因为 honest 的人不会签两次。CS251 把这个性质叫 **accountable safety**。

::fig[is4302-quorum] $n=9$，quorum 是 6。两个 quorum 至少重叠 $6+6-9=3$ 个 validator。

这个论证没有用到“消息多久送达”。所以即使 network 任意延迟（asynchrony），已经 finalize 的 block 也不会被推翻，这就是 finality。对比上一站：Bitcoin 的 safety 依赖于 network 延迟有上界。

### 为什么偏偏是 1/3

设最多有 $f$ 个 validator 作恶，quorum 大小为 $Q$。两个要求：

- **Liveness**：作恶的 $f$ 个可以拒绝投票，剩下的必须仍然凑得够 quorum，所以 $Q\le n-f$。
- **Safety**：任意两个 quorum 的重叠里至少要有一个 honest 的 validator（他不会签两次），所以重叠至少 $f+1$：$2Q-n\ge f+1$。

把第一条代入第二条：$2(n-f)-n\ge f+1$，即

$$n\ \ge\ 3f+1$$

作恶者必须少于三分之一。Nakamoto consensus 能容忍接近一半，代价是只在 network 同步时才 safe；BFT 式的 protocol 在任何 network 条件下都 safe，代价是门槛降到三分之一。

:::wrong Quorum 定得越高越安全，干脆要求所有人都签
Safety 确实随 quorum 提高：9 个里要 7 个，两个 quorum 至少重叠 $7+7-9=5$，作恶者要超过 $5/9$ 才能破坏 safety。但它最多只能容忍 $9-7=2$ 个 validator 掉线，第 3 个掉线就凑不齐 7 票，什么都 finalize 不了，chain 停住。要求全部 9 人都签，则任何一个人掉线都会让 chain 停住。Quorum 是 safety 和 liveness 之间的取舍，不是越高越好。
:::

### Ethereum 怎样把两种性质拼在一起

CS251 指出还有一个更根本的冲突。Bitcoin 有 **dynamic availability**：参与的 node 来来去去，只要还有 honest 的 miner 在线，chain 就继续长。Finality 要求 quorum，在线的人少于 2/3 时就停。可以证明：一个 protocol 不可能在 network 可能分区的条件下同时做到两者。CS251 称之为 blockchain 的 CAP theorem。

Ethereum 的办法是两层 ledger：底下一条 available chain 一直往前长（fork choice 用 LMD GHOST），上面每隔一段由 validator 投票做 checkpoint，得到 2/3 票的 checkpoint 就 finalize（Casper FFG）。Finalized chain 永远是 available chain 的 prefix。用户自己选信哪一条：小额收款看 available chain，不必等；大额收款等 finalize。

::fig[is4302-ffg] 两层 ledger：底下的 available chain 一直长，上面得到 2/3 票的 checkpoint 把它之前的部分 finalize。

几个数字（CS251 lecture 7，2025 年 10 月）：一个 slot 12 秒，一个 epoch 是 32 个 slot（6.4 分钟）；成为 validator 要 stake 32 ETH；当时全网 stake 了 3,570 万 ETH，约占 supply 的 29.4%。2022 年从 proof of work 切换到 proof of stake 时，Ethereum Foundation 预计能耗下降约 99.95%。

:::wrong Proof of stake 让有钱人越来越有钱：stake 多的拿的 reward 也多
拿得多是按比例的。设所有 coin 都参与 stake，年 yield 都是 3%。Alice 持有 10%，一年后她的 coin 和 total supply 都乘 1.03，她仍然持有 10%。比例变化只发生在两种人之间：参与 stake 的人和不参与的人。不参与的人数量不变而 total supply 在增加，他们的比例被稀释。真正受到讨论的集中问题是另一件事：大量 stake 通过少数几家 staking 服务（CS251 举了 Lido）委托出去，这些服务控制的投票权占比很高。这一点上支持者和批评者的看法不同：支持者认为 slashing 和可以随时换服务商约束了它们，批评者认为这重新造出了几个 Scrooge。
:::

:::note CS251 和 NUS 的深度差别
CS251 在 proof of stake 之前专门用了一讲讲 classical consensus（Byzantine broadcast、Dolev–Strong、state machine replication），这一站只取了它推出 1/3 门槛和 accountable safety 的那条线。NUS 的课程描述没有提到 BFT 理论，按它的重心，能讲清 slashing、finality 和“为什么是 2/3”大概就够了。
:::

:::back
“没有 finality、无法 punish”是[第 2 站](#pow)最后指出的两个缺口。
:::

## [utxo] UTXO model 与 account model

:::skip
能读懂一笔 Bitcoin transaction、逐步执行 P2PKH script，能说清 account model 用 nonce 防什么、UTXO model 为什么写不出“每天限额”这类规则，就可以去第 5 站。
:::

### Ledger 记什么：每一笔还是每个人

MIT 15.S12 的 Gensler 把 ledger 分成两种：**transaction ledger** 记一笔笔资金的移动，**balance ledger** 记每个 account 现在有多少。他用 Bitcoin 举前者的例子，用 Ethereum 举后者。两种都能防 double spending，但“检查一笔钱有没有被花过”的办法不同，由此带来一串不同的性质。

### UTXO：只记还没被花掉的 output

Bitcoin 里没有“Alice 的 balance”这个数。每笔 transaction 有若干 input 和若干 output。Output 写着金额和一段锁定 script（谁能花它）；input 指向以前某笔 transaction 的某个 output，并提供解锁所需的证据（通常是 signature）。还没被任何 input 指过的 output，叫 **UTXO**（unspent transaction output）。全网 node 都在内存里维护当前所有 UTXO 的集合，CS251 说 2026 年 9 月大约有 1.66 亿个。

::fig[is4302-utxo] Alice 有一个 7 BTC 的 UTXO，要付 Bob 5 BTC。

一个 output 只能整个花掉。Alice 要付 5 BTC，只能把整个 7 BTC 的 output 当 input，再造两个 output：5 BTC 给 Bob，1.9998 BTC 找零给自己。Input 总额减 output 总额就是 fee，$7-6.9998=0.0002$ BTC，归 miner。Fee 不写在任何地方，是差额。

Miner 对每个 input 检查三件事：

1. 它指向的那个 output 在当前 UTXO set 里，也就是还没被花掉。
2. 解锁 script 接上锁定 script 运行后返回 true。
3. Input 总额 $\ge$ output 总额。

第一条就是 ScroogeCoin 里的“尚未花掉”。Double spend 就是两笔 transaction 指向同一个 output；先被打包进 block 的那笔把它从 UTXO set 里删掉，后一笔检查第一条时失败。

### 锁和钥匙：执行一段 P2PKH script

最常见的锁定方式叫 P2PKH（pay to public key hash）。Bob 生成 key pair，把 public key 的 hash 当作 address 给 Alice。Alice 的 output 上的锁定 script 是

```
OP_DUP OP_HASH160 <pkhashBob> OP_EQUALVERIFY OP_CHECKSIG
```

Bob 要花它时，在 input 里提供解锁 script `<sig> <pkBob>`。Script 是一个 stack machine，把两段接起来从左到右执行（stack 写成左边是底、右边是 top）：

| 步骤 | 执行 | 执行后的 stack |
|---|---|---|
| 1 | push `<sig>` | sig |
| 2 | push `<pkBob>` | sig, pk |
| 3 | `OP_DUP`：复制 top | sig, pk, pk |
| 4 | `OP_HASH160`：把 top 换成它的 hash | sig, pk, H(pk) |
| 5 | push `<pkhashBob>` | sig, pk, H(pk), pkhashBob |
| 6 | `OP_EQUALVERIFY`：弹出两个，不相等就失败 | sig, pk |
| 7 | `OP_CHECKSIG`：弹出 pk 和 sig，验证 sig 是 pk 对这笔 transaction 的 signature | 1 |

第 6 步检查 Bob 给的 public key 确实是 address 对应的那个；第 7 步检查 signature。最后 stack 上是 1，解锁成功。Signature 覆盖了这笔 transaction 的 output，所以 miner 不能偷偷把 output 改成付给自己。

Bitcoin Script 没有 loop，每段 script 的执行步数不超过它的长度，一定会停。这一点在下一站很重要。

### Account model：记每个人的状态

Ethereum 的 world state 是一张表：20 byte 的 address 对应一个 account。每个 account 有 balance（单位 Wei，$1\text{ Wei}=10^{-18}$ ETH）和 nonce；contract account 另外还有 code 和 storage。

一笔 transaction 直接说“从 Alice 转 5 ETH 给 Bob”。设 Alice 的 balance 是 7、nonce 是 4，transaction 里写着 nonce 4。执行后 Alice 的 balance 变成 $2$ 减 fee，nonce 变成 5，Bob 加 5。

Nonce 防的是 **replay**。Account model 里没有“这个 output 已经花掉”的记录，一笔签好的 transaction 被人原样再广播一次，如果没有 nonce，它会再转 5 ETH。有了 nonce，第二次广播时 Alice 的 nonce 已经是 5，transaction 里的 4 对不上，被拒绝。UTXO model 不需要 nonce，因为重放的 transaction 指向的 output 已经不在 UTXO set 里了。

### 两种 model 的取舍

CS251 用一个例子说明 UTXO model 的局限：一个 wallet 想规定“每天最多转出 2 BTC”。这个 wallet 的钱分散在 100 个 UTXO 上，每个 UTXO 的锁定 script 只能规定**花它自己**的条件，看不到今天别的 UTXO 已经花了多少。“今天已经转出多少”是一个跨越所有 UTXO 的状态，UTXO model 里没有地方放它。Account model 里，contract 的 storage 里存一个“今天已转出”的数，每次转账检查并更新它就行。

| | UTXO model（Bitcoin） | Account model（Ethereum） |
|---|---|---|
| 检查 double spending | output 在不在 UTXO set 里 | balance 够不够，nonce 对不对 |
| 防 replay | 天然：output 只能花一次 | 靠 nonce |
| 跨 transaction 的状态 | 没有地方放 | contract storage |
| 并行验证 | 不碰同一个 output 的 transaction 互不影响 | 碰同一个 account 的必须按顺序执行 |
| Privacy | 每次找零可以换新 address | 一个 account 用到底，历史全连在一起 |

:::wrong 每个 Bitcoin address 里存着一个 balance
Ledger 里只有 UTXO。Wallet 软件显示的“balance”，是它把自己能解锁的所有 UTXO 的金额加起来算出的。上图里 Alice 付完款后的“balance 1.9998 BTC”是一个新的 UTXO，可以锁在一个全新的 address 上。把 UTXO model 当成 account model 来想，会看不懂为什么一笔转账有两个 output、fee 为什么不出现在 transaction 里。
:::

:::back
UTXO set 是[第 1 站](#hash) ScroogeCoin 里“尚未花掉”那条规则的实现；transaction 用 Merkle root 放进 block header。
:::

## [evm] Smart contract、EVM 与 gas

:::skip
能写出一个 deposit、withdraw 都正确的 contract 并说出 EVM 执行它时发生了什么，能按 EIP-1559 算一笔 fee，能解释 gas 和 oracle problem 各自是被什么逼出来的，就可以去第 6 站。
:::

### 一笔 transaction 跑一整个 program

上一站的结论是：要表达跨 transaction 的规则，ledger 里得有状态，还得有能读写这些状态的 code。Ethereum 让一个 account 可以带 code，叫 **contract**。一笔发给 contract 的 transaction 会触发它的 code，code 可以读写这个 contract 自己的 storage、转出 ETH、调用别的 contract。每个 validator 都执行同一段 code，得到同一个新的 world state。

Code 用 Solidity 写，编译成 EVM bytecode。EVM 和 Bitcoin Script 一样是 stack machine，但多了 `JUMP`，可以写 loop。

### 一个最小的 contract

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract Bank {
    mapping(address => uint256) public balances;

    function deposit() external payable {
        balances[msg.sender] += msg.value;
    }

    function withdraw(uint256 amount) external {
        require(balances[msg.sender] >= amount, "insufficient balance");
        balances[msg.sender] -= amount;                     // effect
        (bool ok, ) = msg.sender.call{value: amount}("");    // interaction
        require(ok, "transfer failed");
    }
}
```

逐行看 EVM 做了什么。

**谁在调用、带了多少钱。** `msg.sender` 是直接调用这个 contract 的 address，`msg.value` 是这次调用附带的 Wei。只有标了 `payable` 的 function 能收 ETH，往 `withdraw` 里附带 ETH 会被拒绝。

**怎样找到要执行的 function。** Transaction 的 data 字段开头 4 个 byte 叫 function selector，是 function signature 的 Keccak-256 hash 的前 4 byte。实算：`withdraw(uint256)` 的 selector 是 `0x2e1a7d4d`，`deposit()` 是 `0xd0e30db0`。调用 `withdraw(1 ether)` 的 data 就是 `2e1a7d4d` 后面跟着把 $10^{18}$ 编码成的 32 byte。编译器生成的 bytecode 开头是一段分派 code，拿这 4 byte 和每个 function 的 selector 比较，跳到对应的位置。

**`balances` 存在哪。** 每个 contract 有自己的 storage，是 $2^{256}$ 个 32 byte 的格子，初值全为 0。`balances` 是第 0 个 state variable，`balances[a]` 存在第 $\text{keccak256}(a\text{ 补成 32 byte}\ \|\ 0\text{ 补成 32 byte})$ 号格子里。读写分别是 `SLOAD`、`SSTORE`。Storage 是公开的，任何人都能读任何 contract 的任何格子，所以 contract 里不能存密码之类的秘密，标成 `private` 只是不让别的 contract 通过 code 读取，挡不住人直接读 storage。

**`require` 失败时。** 执行 `REVERT`，这笔 transaction 对 state 的所有改动撤销，到这一步为止消耗的 gas 照付。

**Overflow。** Solidity 0.8 起编译器自动检查加减法的 overflow，`balances[msg.sender] -= amount` 如果会变成负数，直接 revert。上面那行 `require` 是为了给出可读的错误信息。

### 为什么要 gas

有了 loop，就有了一个 Bitcoin Script 没有的问题：有人提交一个永不结束的 program，每个 validator 都得执行它，全网卡死。能不能先检查一个 program 会不会停？不能，这是 halting problem，没有 algorithm 能对所有 program 判定。

Ethereum 的办法是不判定，而是收费：每条 instruction 有一个 price，单位叫 gas。发 transaction 时写一个 gasLimit，执行过程中 gas 用完就强行停止，所有改动撤销，但已经用掉的 gas 不退。这样一个死循环最多烧掉发送者自己预付的 gas。每个 block 也有 gas 上限（CS251 记录的是 4,500 万），所以一个 block 的执行时间有上界。

Price 按 instruction 消耗的资源定。最贵的是永久 storage，因为每个 node 要永远存着它。CS251 列出的几个数：

| 操作 | gas |
|---|---|
| 一笔普通的 ETH 转账（固定的基础成本） | 21,000 |
| `SSTORE`：把一个格子从 0 写成非 0 | 20,000 |
| `SSTORE`：把非 0 改成另一个非 0 | 5,000 |
| `SSTORE`：把非 0 改回 0 | 退还 15,000 |
| `MLOAD`、`MSTORE`（只在本次执行中存在的 memory） | 3 |

把格子清零给退款，是在鼓励大家缩小全网必须保存的 state。

### 一笔 fee 怎样算：EIP-1559

2021 年 8 月起，每个 block 有一个 baseFee，是这个 block 里 gas 单价的下限。Transaction 写两个数：maxFee（每单位 gas 最多愿付多少）和 maxPriorityFee（愿意给 proposer 的小费上限）。实际单价是

$$\text{gasPrice}=\min(\text{maxFee},\ \text{baseFee}+\text{maxPriorityFee})$$

付出去的钱分两块：$\text{gasUsed}\times\text{baseFee}$ 被 burn 掉，$\text{gasUsed}\times(\text{gasPrice}-\text{baseFee})$ 给 proposer。

例子：baseFee 20 gwei（$1\text{ gwei}=10^9$ Wei），maxFee 30 gwei，maxPriorityFee 2 gwei，gasLimit 30,000，实际是一笔普通转账，用了 21,000。

1. $\text{gasPrice}=\min(30,\ 20+2)=22$ gwei。
2. 先从 Alice 的 balance 扣 $30000\times22=660{,}000$ gwei。
3. 执行完剩下 $9{,}000$ gas，退回 $9000\times22=198{,}000$ gwei。
4. 实付 $660000-198000=462{,}000$ gwei，即 0.000462 ETH。其中 burn $21000\times20=420{,}000$ gwei，给 proposer $21000\times2=42{,}000$ gwei，两者相加正好 462,000。

::fig[is4302-fee] 上面四步的钱怎么分：预扣的 660,000 gwei 里，198,000 退回，其余按 baseFee 和小费分成 burn 与给 proposer 的两块。

BaseFee 本身随拥堵调整。目标是每个 block 用 2,250 万 gas（上限的一半）。用满 4,500 万，下一个 block 的 baseFee 涨 12.5%，从 20 到 22.5 gwei；用了 3,000 万，超出目标 $7.5/22.5=1/3$，涨 $12.5\%\times\tfrac13\approx4.17\%$，到 20.83 gwei；完全空的 block 降 12.5%。

为什么要 burn 而不是给 proposer？CS251 的解释：如果 baseFee 归 proposer，proposer 可以在链下给用户回扣，自己往 block 里塞假 transaction 推高 baseFee。Burn 掉之后这么做无利可图。

:::edge gasLimit 写大一点会不会多付钱
不会，没用完的按上面第 3 步退回，gasLimit 只是上限。写小了才有风险：一个本来需要 80,000 gas 的 contract 调用，gasLimit 只给 50,000，执行到一半 gas 耗尽，state 全部撤销，而 50,000 gas 的费用全额照付。
:::

### 先改账再转钱：reentrancy

上面 contract 里 `withdraw` 先改账、后转钱，顺序是刻意安排的。CS251 的反例是一个先转钱、后改账的版本，一次取出全部 balance：

```solidity
function withdrawAll() external {
    uint256 amount = balances[msg.sender];
    require(amount > 0);
    (bool ok, ) = msg.sender.call{value: amount}("");   // 先转钱
    require(ok);
    balances[msg.sender] = 0;                           // 后改账
}
```

:::wrong 先转账后改 balance 也没关系，反正都在同一个 transaction 里，最后结果一样
`msg.sender` 可以是一个 contract。给 contract 转 ETH 时，EVM 会执行对方的 `receive()` function，而这段 code 是 attacker 写的。他可以在 `receive()` 里**再次调用** `withdrawAll`。这时外层那次还没执行到最后一行，`balances` 还是原来的数，读出来的 `amount` 还是 75，于是又转一次钱，又触发 `receive()`……

设 Bank 里原有别人的 300 Wei，attacker 存入 75 Wei，共 375。每一层取 75：第 1 层后剩 300，第 2 层后 225，第 3 层后 150，第 4 层后 75，第 5 层后 0。Attacker 的 `receive()` 先检查 Bank 还有没有 75，没有了就不再调用，于是各层依次返回，每一层都执行一次 `balances[msg.sender] = 0`，都不出错。Attacker 存了 75，取走 375。

如果最后一行写成 `balances[msg.sender] -= amount`，在 Solidity 0.8 下，最里层把 balance 减到 0 之后，外面一层再减 75 就 underflow，整笔 transaction revert，攻击碰巧失败。但这是 overflow 检查顺带挡住的，换一种记账写法就不成立，不能当作防御。
:::

::fig[is4302-reent] 每一层都在把 balance 改掉之前重新进入。

治法是一条写 contract 的纪律，叫 checks-effects-interactions：先检查条件，再改自己的 state，最后才和外部 contract 交互。第一个版本正是这样排的：第二次进入时 balance 已经减掉，`require` 失败。另一个办法是加一个锁，function 执行期间不允许再次进入。2016 年 The DAO 被盗走大量 ETH 用的就是 reentrancy，事后 Ethereum 社区用 hard fork 把这些 ETH 转回，不同意的人留在旧 chain 上，成了 Ethereum Classic。

### Smart contract 不能做什么

**不能主动做事。** Contract 只在被 transaction（或被别的 contract）调用时执行。“每月 1 号自动付款”得有人每月 1 号发一笔 transaction 去触发它。

**不能读 off-chain 的数据。** 每个 validator 都要重新执行同一段 code，并且必须得到完全相同的结果，否则大家对新 state 达不成一致。如果 code 里能发一个 HTTP 请求查 ETH 的 price，不同 validator 在不同时刻查，得到不同的数，consensus 就破了。所以 EVM 的执行必须是 deterministic 的，只能读 on-chain 已有的东西。

Off-chain 的数据要由某人写一笔 transaction 送上 chain，这个角色叫 **oracle**。问题随之而来：contract 本来不需要信任任何人，现在它的正确性取决于 oracle 送来的数据对不对。这叫 **oracle problem**。缓和的办法是让多个独立的 oracle 各报一个数、取 median，并对偏离的报价施加 penalty；但它们终究是 off-chain 的人。Blockchain 能保证的是“on-chain 的记录没有被改过”，不能保证“on-chain 的记录和现实相符”。

**不能藏秘密，也不能产生真正的随机数。** Storage 和 transaction 都是公开的。`block.timestamp` 之类的值由 proposer 填写，可以在一定范围内操纵，拿它当随机数，proposer 就能影响结果。

**部署之后不能改。** Code 写进链里就固定了，有 bug 也改不了。实际中常用的办法是在前面放一个 proxy contract 转发调用，需要升级时改 proxy 指向的 address，但这等于又引入了一个能改规则的人。

## [defi] DeFi：lending 与 AMM

:::skip
能算一次 constant product swap 的 output 和 slippage、说清 arbitrage 怎样把 pool 的 price 拉回市场价、推出 impermanent loss，并能算一个 lending position 的 health，就可以去第 7 站。
:::

### 没有 credit score 的借贷

Bank 放贷靠两样东西：知道 borrower 是谁，default 了能追讨。Blockchain 上的 address 是一串 hash，这两样都没有。所以 DeFi 的 lending protocol（Aave、Compound）只做一种 loan：**over-collateralized**，collateral 的价值高于 loan。

CS251 用 Aave 的参数说明。每种 collateral 有两个比例：LTV（最多能借 collateral 价值的多少）和 liquidation threshold。ETH 是 80.5% 和 83%。定义

$$\text{health}=\frac{\sum_i\text{value}(\text{collateral}_i)\times\text{threshold}_i}{\text{value}(\text{debt})}$$

Health 跌破 1 就可以被 liquidate。

例子：Bob 存入 2 ETH，当时 ETH 是 3000 USDC，collateral 值 6000。最多能借 $6000\times80.5\%=4830$ USDC，他借了 4000。

$$\text{health}=\frac{6000\times0.83}{4000}=1.245$$

ETH price 跌到 $P$ 时，health 是 $\dfrac{2P\times0.83}{4000}$，令它等于 1，得 liquidation price

$$P=\frac{4000}{2\times0.83}=2409.64$$

Price 跌破 2409.64，任何人都可以调用 liquidate：替 Bob 还掉一部分 USDC debt，按 discount 拿走等值的 ETH collateral，discount 就是对 Bob 的 penalty和给 liquidator 的报酬。没有人要去催收，规则写在 contract 里，谁都可以执行。

::fig[is4302-health] Bob 的 health 是 ETH price 的 linear function，在 2409.64 处穿过 1。

这种 loan 有什么用？Borrower 通常手里有 ETH、不想卖掉，又需要 USDC，或者想加 leverage。它不能替代需要 credit 的 loan。

唯一不要 collateral 的是 **flash loan**：borrow 和 repay 在同一个 transaction 里。如果 transaction 结束时钱没有还回去，整笔 transaction revert，等于从没借过，lender 没有任何风险。CS251 的例子：从 Aave 借 100 万 USDC，在 Uniswap 按 1 USDC = 1.002 DAI 换成 100.2 万 DAI，在 Curve 按 1 USDC = 1.001 DAI 换回约 100.1 万 USDC，还掉 100 万，留下约 1,000 USDC。这件事只有在 transaction 具有 atomicity 的系统里才可能，传统金融里没有对应物。

::fig[is4302-flash] Flash loan 的四步都在同一笔 transaction 里。

### 没有 counterparty 的 exchange

Exchange 传统的做法是 order book：buyer 报 bid、seller 报 ask，两边 match 上就成交。放到 Ethereum 上，每一次 place order、cancel order 都是一笔要付 gas 的 transaction，太贵。**AMM**（automated market maker）换了一种做法：一些人（liquidity provider，LP）把两种 token 存进一个 pool，trader 直接和 pool 换，price 由一个 formula 决定。

Uniswap v2 的 formula 是 **constant product**：pool 里有 $x$ 个 ETH 和 $y$ 个 USDC，trade 必须保持

$$x\cdot y=k$$

（加上 fee 之后是 $k$ 不能减少。）

设 pool 里有 100 ETH 和 300,000 USDC，$k=3\times10^7$。Pool 现在的 price 是多少？把 $y=k/x$ 对 $x$ 求 derivative：

$$\frac{dy}{dx}=-\frac{k}{x^2}=-\frac yx=-\frac{300000}{100}=-3000$$

多放进去极少量 ETH，换出的 USDC 是它的 3000 倍。这个 $y/x$ 叫 marginal price。

现在 Alice 卖 10 ETH（先不算 fee）。Pool 的 ETH 变成 110，USDC 必须变成

$$\frac{3\times10^7}{110}=272{,}727.27$$

Alice 拿到 $300000-272727.27=27{,}272.73$ USDC，平均每个 ETH 2727.27，比 marginal price 3000 低 9.09%。

::fig[is4302-amm] Trade 让 pool 的状态沿着 curve 移动：卖 10 ETH 从 A 到 B，卖 50 ETH 从 A 到 C。A 点的 tangent slope 是 marginal price，chord 的 slope 是实际成交的 average price，trade 越大，chord 越平。

### Slippage 有多大

一般地，卖入 $\Delta x$，拿到

$$\Delta y=y-\frac{xy}{x+\Delta x}=\frac{y\,\Delta x}{x+\Delta x}$$

Average price 是

$$\frac{\Delta y}{\Delta x}=\frac{y}{x+\Delta x}=\frac yx\cdot\frac{x}{x+\Delta x}$$

比 marginal price $y/x$ 低了 $\dfrac{\Delta x}{x+\Delta x}$ 这个比例。它只取决于 trade size 和 pool 大小的比：

| 卖入 ETH | 占 pool 的比例 | 拿到 USDC | average price | 比 3000 低 |
|---|---|---|---|---|
| 1 | 1% | 2,970.30 | 2970.30 | 0.99% |
| 10 | 10% | 27,272.73 | 2727.27 | 9.09% |
| 50 | 50% | 100,000.00 | 2000.00 | 33.3% |

这就是 slippage，也叫 price impact。Pool 越深，同样的 trade slippage 越小。另外，$\Delta y$ 永远小于 $y$：无论卖入多少 ETH，都不可能把 pool 的 USDC 换空，所以 pool 永远有 price。

**加上 fee。** Uniswap v2 收 0.3%，归 LP。实现是：卖入的 $\Delta x$ 只有 $0.997\Delta x$ 参与 formula，剩下的 0.3% 留在 pool 里。Alice 卖 10 ETH 实际拿到

$$\frac{300000\times9.97}{100+9.97}=27{,}198.33$$

成交后 pool 是 110 ETH 和 $300000-27198.33=272{,}801.67$ USDC，乘积 $3.0008\times10^7$，比原来的 $k$ 大，多出来的就是 fee 留给 LP 的部分。

### AMM 的 price 从哪里来

Pool 自己不知道外面的 ETH 卖多少钱。Alice 卖完后，pool 的 marginal price 是 $272801.67/110=2480.02$，而外面的 exchange 还是 3000。

于是有人来做 arbitrage：从 pool 买 ETH，拿到外面按 3000 卖，直到 pool 的 price 也到 3000。目标状态满足 $x'y'=k$ 且 $y'/x'=3000$，所以 $x'=\sqrt{k/3000}$。用成交后的 $k=30{,}008{,}184$：

$$x'=\sqrt{30008184/3000}=100.014,\qquad y'=3000\,x'=300{,}040.92$$

Arbitrageur 从 pool 买走 $110-100.014=9.986$ ETH，付 $300040.92-272801.67=27{,}239.24$ USDC（为简单起见这一步不计 fee），在外面卖得 $9.986\times3000=29{,}959.08$，赚 2,719.84。

把账对一下。Alice 的 10 ETH 按外面的 price 值 30,000，她只拿到 27,198.33，少了 2,801.67。这笔钱去了两个地方：arbitrageur 赚 2,719.84；pool 的价值按 3000 算从 600,000 变成 $100.014\times3000+300040.92=600{,}081.84$，LP 多了 81.84（fee）。$2719.84+81.84=2801.68$，和 Alice 的损失相等（差 0.01 是四舍五入）。

AMM 不需要任何 oracle 告诉它 price，arbitrageur 为了赚钱会把它拉到和外面一致。代价是：每次外面 price 变动，都有人从 pool 里把差价拿走，这个人是 arbitrageur，付钱的是 LP。

### LP 为什么会亏：impermanent loss

LP 存入 100 ETH 和 300,000 USDC。之后外面的 ETH price 从 3000 涨到 6000，arbitrage 把 pool 的 price 拉到 6000。Pool 现在是什么样？

由 $xy=k$ 和 $y/x=P$ 解出：

$$x=\sqrt{k/P},\qquad y=\sqrt{kP},\qquad\text{pool 的价值}=xP+y=2\sqrt{kP}$$

代入 $k=3\times10^7$、$P=6000$：$x=70.71$ ETH，$y=424{,}264$ USDC，价值 $848{,}528$。如果 LP 当初什么都不做，拿着 100 ETH 和 300,000 USDC，现在值 $100\times6000+300000=900{,}000$。存进 pool 反而少了 5.72%。

一般地，设 price 变成原来的 $r$ 倍。Pool 的价值和 $\sqrt P$ 成正比，变成原来的 $\sqrt r$ 倍：$2\sqrt{kP_0}\cdot\sqrt r$。拿着不动的价值是 $x_0rP_0+y_0$，而一开始 $x_0P_0=y_0=\sqrt{kP_0}$，所以它是 $\sqrt{kP_0}\,(1+r)$。两者之比是

$$\frac{\text{pool}}{\text{hold}}=\frac{2\sqrt r}{1+r}$$

$r=2$ 时是 $2\sqrt2/3=0.9428$，少 5.72%，和上面一致。由 AM–GM，$1+r\ge2\sqrt r$，等号只在 $r=1$ 成立：只要 price 变了，LP 就比拿着不动差。

::fig[is4302-il] 横轴是 price 变成原来的几倍。涨一倍和跌一半损失相同，都是 5.72%；变成 4 倍损失 20%。

叫 impermanent 是因为 price 回到原来的水平时损失消失。但如果 LP 在 price 变动后取出，损失就实现了。LP 赚的是 fee，亏的是这个，提供 liquidity 是否划算取决于两者谁大。CS251 进一步指出，volatility 高的时期 fee 通常补不回来，LP 会在那时撤出。

:::wrong AMM pool 给出的 price 就是这个 token 的市场 price
Pool 的 price 只是 pool 里两种 token 数量之比。它跟得上市场，完全是因为 arbitrageur 在不停地纠正它；arbitrage 的成本（gas、fee）越高、pool 越浅，偏离就越大、持续越久。直接拿某个 pool 的瞬时 price 当作 lending protocol 的 oracle 是危险的：用 flash loan 借一大笔钱砸进一个浅 pool，可以在同一个 transaction 里把 price 推到任意位置，CS251 把这列为 flash loan 的一种攻击用途。Uniswap v2 的 whitepaper 因此提供的是 time-weighted average price，要操纵它就得维持被扭曲的 price 很多个 block。
:::

:::edge Sandwich：mempool 是公开的
Alice 的 swap 在进 block 之前躺在公开的 mempool 里。有人看到后，抢在她前面买入同一个方向（把 price 推高），让 Alice 在更差的 price 成交，再紧跟在她后面卖出。按上面的 slippage formula，Alice 那笔 trade 越大，这样做的利润越大。Trader 能做的是在 transaction 里写一个能接受的最少 output，低于它就 revert。
:::

:::back
Flash loan 能成立，是因为[第 5 站](#evm)说的 revert：transaction 中途失败，所有改动撤销。
:::

## [stable] Stablecoin：peg 怎样维持、怎样断

:::skip
能用 arbitrage 解释 custodial stablecoin 的 peg、说清 2023 年 USDC 断在哪一环，能说出 UST 的 peg 依赖什么条件以及它为什么会自我加速地崩溃，就可以去第 8 站。
:::

### 为什么需要 stablecoin

Gensler 在 15.S12 里的出发点是：BTC 和 ETH 的 price volatility 太大，当 store of value 和 unit of account 都不合格，在 crypto 之间来回 trade 时需要一个“停车的地方”；而把钱换回 bank account 要经过 exchange 和 KYC。如果 on-chain 有一个始终值 1 USD 的 token，就能 on-chain 用 USD 计价，第 6 站的 lending 和 AMM 也大多以它计价。CS251 举的另一个用途是 cross-border payment：international wire transfer 约 44 USD，在 Base 这条 chain 上转 USDC 不到 0.01 USD。

难点在于“始终值 1 USD”。Contract 能保证的只有 on-chain 的规则；1 USD 在 off-chain，怎样让 on-chain 的 token 和它挂钩？按回答方式，CS251 把 stablecoin 分成几类，这一站看三种，每种都有一次有记录的失败。

### Custodial：off-chain 存 1 USD，on-chain mint 一个

USDC、USDT 是这一类。CS251 的例子：

1. Bob 把 100 USD 汇给 custodian，custodian 调用 ERC-20 contract 的 `mint(Bob, 100)`。Alice 汇 35，`mint(Alice, 35)`。Total supply 135。
2. Bob 转 15 给 Carol：`transfer(Bob → Carol, 15)`，这一步 on-chain 完成，不需要 custodian。
3. Bob redeem 60 USD：custodian 把钱汇给他并调用 `burn(Bob, 60)`。Supply 变成 75：Alice 35、Bob 25、Carol 15。

Off-chain 的 bank 里的 reserve 始终等于 on-chain 的 supply。

::fig[is4302-mint] 三步之后各方的 balance 和 bank 里的 reserve。

**Peg 怎样维持。** 大部分持有者不直接和 custodian 打交道，而是在 exchange（secondary market）买卖。能直接 mint 和 redeem 的（primary market）是少数机构。

::fig[is4302-peg] 两个市场之间的 arbitrage 把 price 钉在 1 附近。

如果 exchange 里 1 USDC 只卖 0.98，有资格 redeem 的人就买入，拿去 custodian 换 1 USD，每个赚 0.02，买入推高 price。卖 1.02 时就反过来：给 custodian 1 USD mint 一个，拿去卖。只要 redemption 随时可用、大家相信 reserve 足额，price 偏离 1 就有人赚钱，把它推回去。

所以 peg 依赖两个条件：reserve 真的在，并且 redemption 通道开着。

### USDC，2023 年 3 月

下面的时间和数字都来自美联储 2025 年 12 月的一篇 FEDS Note。

- **3 月 10 日（周五）上午**，Silicon Valley Bank 在单日被提走超过 400 亿 USD 之后被接管。
- **当晚 10 点（美东）**，Circle 宣布有 33 亿 USD 的 USDC reserve 在 SVB 里取不出来，约占它当时 400 多亿 reserve 的 8%。
- **周末**，bank 不营业，Circle 的 mint 和 redeem 都停了。Secondary market 的成交量暴增，3 月 11 日每小时近 20 亿 USD，而且主要在 DEX 上。USDC 最低跌到 0.86。
- **3 月 12 日（周日）下午 6:15**，美国财政部、美联储和 FDIC 联合宣布 SVB 的所有 depositor 都会得到全额保护。USDC 随即大幅反弹。
- **3 月 13 日（周一）**，Circle 恢复处理 redemption，USDC 回到 1。到 3 月 15 日，它在这几天里 redeem 了 38 亿、mint 了 8 亿。

用上面的两个条件来读。**Reserve 的损失有多大？** 按 reserve 等于 supply、reserve 约 400 亿来估，即使 SVB 里的 33 亿一分都拿不回，每个 USDC 也还有 $(40-3.3)/40=0.9175$ USD 的 reserve。最低价 0.86 比这个最坏情形还低。**Redemption 通道** 在周末是关的。FEDS Note 的观察是：USDC 直到 primary market 关闭后才跌到最低，直到 redemption 恢复后才回到 peg。通道一关，arbitrage 就没有了，price 只剩 secondary market 的恐慌和 supply and demand。

:::wrong 有 1:1 reserve 的 stablecoin 不会 depeg
USDC 的 reserve 是 cash 和短期 Treasury bill 一类的 asset，92% 没有受任何影响，它仍然跌到了 0.86。Reserve 足额只保证“最终能拿回多少”，peg 每时每刻成立靠的是 redemption 随时可用，而 redemption 又依赖 banking system 的营业时间和 bank 本身的安全。Gensler 在 2018 年就指出 fiat-backed token 最大的风险在于和 commercial bank 的关系（他的例子是 Tether 因为 anti-money laundering 方面的顾虑失去了一些 bank account），2023 年的事故是这一点的一次具体实现。
:::

**传染。** DAI 不是 custodial 的，但它有一个 Peg Stability Module，允许 USDC 和 DAI 按 1:1 互换，每日上限 9.5 亿。USDC 出事后，大家把 USDC 换成 DAI 出逃，3 月 10 日和 11 日各换进约 10 亿，两天都打满上限。结果 DAI 的 backing 里塞满了 USDC，DAI 跟着 USDC 一起跌。MakerDAO 的紧急提案在两小时内通过，但有 48 小时的生效延迟，等它在 3 月 13 日生效时，风波已经过去。

### Crypto-collateralized：用 volatile 的东西支撑稳定的东西

DAI 的本来设计不靠 bank：用户把 ETH 锁进 contract 作 collateral，mint 出 DAI，按 Richmond Fed 的文章，collateral ratio 是 150%。这和第 6 站的 lending 是同一个机制，只不过借出来的是新 mint 的 DAI。ETH 跌，就像 Bob 的 health 跌破 1 一样被 liquidate。

它的代价是 capital efficiency 低：锁价值 150 USD 的 ETH 才能得到 100 个 DAI。它的风险是 collateral 在极短时间内暴跌、liquidation 来不及。2023 年它被 USDC 拖下水，是因为为了维持 peg 又引入了 USDC 这种 custodial 的 collateral。

### Algorithmic：UST 与 LUNA

TerraUSD（UST）没有 off-chain 的 reserve。它的机制是一个 contract，允许任何时候用 1 个 UST 换价值 1 USD 的 LUNA（Terra 自己的 token），反之亦然。Richmond Fed 的文章这样解释 peg：

- UST 跌到 0.98：买入 UST，burn 掉换成价值 1 USD 的 LUNA，卖掉 LUNA，赚 0.02。UST 被买入、被销毁，price 回升。
- UST 涨到 1.03：花 1 USD 买 LUNA，burn 掉 mint 1 个 UST，卖出赚 0.03。

看起来和 custodial 一样是 arbitrage。区别在于 redeem 换到的东西：custodial 换到 bank 里的 USD，UST 换到的是新 mint 的 LUNA，而 LUNA 的价值本身依赖于大家对 UST 的信心。

Redeem 1 亿 UST 需要 mint 多少 LUNA？$10^8/P_{\text{LUNA}}$ 个。

| LUNA price（USD） | redeem 1 亿 UST 要 mint 的 LUNA |
|---|---|
| 20 | 500 万 |
| 2 | 5,000 万 |
| 0.2 | 5 亿 |

LUNA price 每跌到十分之一，同样的 redemption 就要多 mint 十倍的 LUNA；新 mint 的 LUNA 被卖出，price 进一步下跌。Richmond Fed 的文章把条件说得很直接：只有 LUNA 的 total market cap 大于流通中的 UST，全部 UST 才可能按 1 USD redeem；一旦 LUNA market cap 跌破 UST 的规模，UST 就不再是 stablecoin。

**2022 年 5 月发生的事**（数字来自 Richmond Fed 和 Liu、Makarov、Schoar 的研究）：

- 高峰时流通约 180 亿 UST，其中约 160 亿存在 Anchor 这个 protocol 里，享受 19.5% 的 deposit rate。Liu 等人指出这个 interest rate 是靠 subsidy 维持的，到 2022 年 4 月每天 subsidy 600 万 USD。
- 5 月 7 日，两个大 address 从 Anchor 撤出 3.75 亿 UST。5 月 7 至 8 日，Curve 上的 liquidity 被抽走，UST 跌到 0.985。
- 管理 Terra reserve 的 LFG 拿出 15 亿 USD 护盘，相对于 180 亿的 UST 很小。
- 5 月 9 日，LUNA 一天跌 48%，UST 在 Binance 一度跌到 0.60。
- 此后 UST 跌到 0.22。LUNA 的 supply 从 5 月 10 日的 4 亿增加到 5 月 12 日的 320 亿，price 从 31 USD 跌到 0.01。

Liu 等人的研究还发现，规模大、更有经验的持有者撤得早、损失小，小额持有者撤得晚、损失大，有些人还在下跌中买入。On-chain 数据人人可见，但看得懂它的能力并不平均。

:::edge Algorithmic stablecoin 是不是注定失败
这是一个有争议的问题。Richmond Fed 的文章认为 UST 的 backing 是循环的（LUNA 的价值依赖于 UST），一旦信心动摇必然自我加速，稳定的 stablecoin 需要传统形式的 backing，而后者 capital efficiency 低。另一些设计者认为问题出在 UST 的具体参数（靠 subsidy 维持、没有上限的 deposit rate、过小的 reserve），可以用 partial collateral、动态的 redemption 限额等办法改进。两方都同意的是：没有外部 backing 时，peg 最终取决于市场是否相信它。
:::

## [cbdc] CBDC、cryptocurrency 与评估一个 blockchain 应用

:::skip
能说出 cash、bank deposit、stablecoin、CBDC、BTC 各是谁的 liability、记在谁的 ledger 上，能把 retail CBDC 的争议两边讲清，并能对一个应用回答“为什么不用 database”，这门课就读完了。
:::

### Money 是哪一本 ledger 上的记录

Gensler 在 15.S12 第二讲给 money 列了三个 function：medium of exchange、unit of account、store of value。然后他把现代的 money 描述成一个 ledger 的层级：central bank 的 ledger 在最上面，记着各家 commercial bank 的 reserve；每家 commercial bank 的 ledger 记着客户的 deposit。Alice 和 Bob 在同一家 bank，转账只改这家 bank 的 ledger；在不同 bank，两家 bank 的差额在 central bank 的 ledger 上结算。

::fig[is4302-tiers] 每一种 money 都是某个机构的 liability。

把这一页出现过的几种“money”放进这个框架：

| | 是谁的 liability | 记在谁的 ledger | 价值稳定吗 |
|---|---|---|---|
| Cash | central bank | 实物，不记账 | 以本国 currency 计，是 |
| Bank deposit | commercial bank | commercial bank | 是，有 deposit insurance 兜底一部分 |
| Custodial stablecoin | issuer | public chain（由 validator 维护） | 依赖 reserve 和 redemption（第 7 站） |
| Retail CBDC | central bank | central bank 或其指定的系统 | 是 |
| BTC | 不是任何人的 liability | public chain | 否 |

BTC 是表里唯一不是任何人 liability 的东西：没有人承诺把它换成别的什么。这正是它不需要信任某个 issuer 的原因，也是它的 price 完全由 supply and demand 决定的原因。

### CBDC 是什么，不是什么

CBDC（central bank digital currency）是 central bank 直接 issue 的数字形式的 money。Central bank 本来就有数字的 money：commercial bank 在 central bank 的 reserve 就是。所以问题其实是：要不要把 central bank 的 ledger 开放给更多人。只开放给金融机构，叫 wholesale CBDC；开放给公众，叫 retail CBDC。设计上还有一个维度：account-based（像 bank account，按身份记）还是 token-based（像 cash，按持有记）。

:::wrong CBDC 就是 central bank 发的 cryptocurrency，必然要用 blockchain
Gensler 在 session 16 明确说 CBDC 不需要 blockchain，最多是受它启发。Central bank 本身就是大家信任的 ledger 维护者，第 1 站里 ScroogeCoin 的那个“问题”在这里不是问题。他举的 Senegal 和 Philippines 的试点，据他所知都没有用 blockchain。CBDC 和 cryptocurrency 的共同点只是“数字的”；在“谁的 liability”“谁维护 ledger”这两个根本问题上，它们恰好相反。
:::

### Retail CBDC 的争论

这是一个仍在争论的问题，各国 central bank 的做法也不同。下面把两边的主要论证各自写清楚。

**支持的一方。**

- 现金在消失。Gensler 举的 Sweden：cash 占 GDP 的比例从约 4% 降到 2% 以下，而美国和欧洲接近 10%。如果公众手里只剩 commercial bank 的 deposit，就再也没有一种无风险的、由公共部门提供的支付手段。Sweden 的 e-krona 研究就是从这里出发的。
- 防止支付被私人的 money 主导。ECB 2023 年的金融稳定报告专栏认为，digital euro 可以作为 big tech 支付服务和 stablecoin 之外的选择，让 public money 继续当整个 monetary system 的锚。

**担忧的一方。**

- **Disintermediation 与 bank run。** Gensler 课上提到 central banker 最担心的是 bank run。如果每个人都能在 central bank 开一个无风险的 account，危机时 deposit 会一键从 commercial bank 搬过去，速度比 2023 年 SVB 那天的 400 亿还快。平时，deposit 流走会让 bank 失去便宜而稳定的资金来源，影响放贷。
- **Credit allocation。** Central bank 接收了大量 deposit 之后，这些钱借给谁？如果由 central bank 决定，它就从管理 money 变成了分配 credit。课上有学生认为可以用 interest rate policy 处理，Gensler 则指出 Fed 的 balance sheet 里已经有大量 mortgage。
- **Privacy。** Account-based 的 retail CBDC 意味着 central bank 能看到每一笔支付。Gensler 提到 Sweden 表示不会提供完全匿名的 e-money。

**一个折中：holding limit。** ECB 的专栏讨论了每人最多持有 3,000 euro 的 digital euro 的方案。它的模拟假设 household 的 overnight deposit 有 5% 到 30% 转成 digital euro；在 3,000 euro 的上限下，即使在“所有人同时采用并立刻存满”这种极不可能的条件下，流出也最多约 15%，而它估计大型 bank 要到约 20% 的 overnight deposit 流出才会面临实质的 liquidity risk。批评者会说，有上限的 CBDC 也就失去了它作为“无风险 store of value”的大部分意义；支持者会说，它本来就只想做支付手段。

BIS 和七家 central bank 2020 年的联合报告没有主张发或不发，只提出前提：issue CBDC 不能损害 monetary stability 和 financial stability，要和现有的 money 共存。

:::edge BTC 能不能当 money
同样是争议问题。按三个 function 检查，批评者指出：price volatility 大，商家几乎不用 BTC 标价，所以它不是 unit of account；同一个理由也让它当 store of value 的可靠性存疑（这和 Gensler 对 crypto 的描述一致）。支持者认为它的 supply cap（第 2 站算出的 2,100 万）和不依赖任何 issuer，使它更像 gold 一类的 store of value，而 store of value 本来就不要求短期 price 稳定。本页不对这个问题下结论，也不构成任何 investment advice。
:::

### 什么时候需要 blockchain

NUS 课程描述的后半部分是评估 blockchain application 的 business 和 economic performance 与它的技术设计之间的关系。CS251 第一讲的答案最直接：blockchain 提供的是**在没有一个可信第三方时的协调**；如果有一个大家都信任的第三方，就不需要 blockchain。

15.S12 讲 use case 的那一讲把 benefit 归为两种成本的降低：

- **Verification cost**：确认一笔记录真实、未被篡改、已经结算所需要的成本，包括信任中介的成本、中介收的租金、被 censor 的风险。
- **Networking cost**：让一个 network 从无到有建起来并维持运转的成本，token 的作用是 incentivize 早期参与者。

同一讲把 blockchain 和传统 database 对比：database 由一个受信任的一方托管，可以增删改查；blockchain 是只能追加、带时间戳、公开可验证的 log，没有中央中介。它还要求设计者回答三个问题：为什么用 blockchain 而不是 database；为什么用 public chain 而不是 permissioned chain；如果是 permissionless 的，为什么需要一个 token。

**用一次：一家公司的请假审批系统，做成 Ethereum 上的 contract。**

1. 谁需要写入？员工提交申请，雇主审批。只有这两方。
2. 有没有一个大家都信任的第三方？雇主本身就维护着 HR 系统，员工的工资、合同都记在那里；员工已经在信任它。
3. 降低了哪种 verification cost？雇主篡改请假记录的风险确实存在，但员工对工资记录承担着同样的风险，单独把请假放上 chain 没有改变信任结构。
4. 降低了哪种 networking cost？没有需要从零建立的 network。
5. 成本：每次申请和审批都是一笔付 gas 的 transaction；员工需要 wallet；记录永久公开，涉及 privacy。

按这个框架，一个 database 更合适。如果问题变成“多家互不隶属的雇主共享一份工作经历记录，没有谁愿意让对手托管”，第 2 条的答案就变了，blockchain 才开始有理由。

**再用一次：用 USDC 做 cross-border payment。**

1. 有没有可信第三方？传统 wire transfer 有，代价是 CS251 记录的约 44 USD fee 和几天时间。
2. 降低了哪种 verification cost？On-chain 转账几分钟内确认，不经过代理行，CS251 记录的成本不到 0.01 USD。
3. 没有消失的成本：两端都要把法币换进换出（on-ramp 和 off-ramp），要过 KYC；USDC 的 issuer 是一个能冻结 account 的 Scrooge；peg 本身有风险（第 7 站）。

评估结果取决于两端换汇的成本和对 issuer 的信任，而不只是 on-chain 那一步。这正是课程描述说的“经济表现与技术设计的关系”：on-chain 那一步便宜，是 public chain 的设计带来的；整个链条是否便宜，取决于 chain 和现实世界的接口。
