先看三次通信。每一次，每一条 link 都完好无损，结果都慢得离谱或者错得离谱。

**第一次。** 一个网页有 1 个 HTML 和 10 张图片，client 和 server 之间的 RTT 是 20 ms。浏览器每取一个 object 就新开一条 TCP connection，取完关掉，整个页面要 440 ms。同样的 server、同样的网络，换一种用 connection 的方式，60 ms。

**第二次。** 两台机器之间是一条 1 Gbps 的 link，RTT 30 ms。用最直接的办法传文件：发一个 1000 byte 的 packet，等对方说收到了再发下一个。实际 throughput 是 267 kbps，不到 link 容量的三千分之一。

**第三次。** 三个 router x、y、z 互相连着。x 和 y 之间那条 link 的 cost 从 4 涨到 60。之后 y 和 z 互相把发往 x 的 packet 推给对方，两个 router 交换了 47 次更新才停下来。

网络里的每个零件都只做一件有限的事：link 只负责把 bit 送到另一头，router 只负责按表把 packet 往下一站推，而且随时可能因为 buffer 满了把它丢掉。这门课研究的是怎样在这些零件上一层一层搭出“可靠、够快、找得到路、不被偷看”的通信。上面三次事故分别在第 2、3、6 站得到解释。

课程的顺序是从上往下：先弄清一个 packet 在路上花的时间和它身上那几层 header（第 1 站），然后是用户直接碰到的 HTTP 和 DNS（第 2 站），再往下是让通信可靠的 transport layer（第 3、4 站），找路的 network layer（第 5、6 站），一条 link 上怎样发（第 7 站），最后是怎样不被偷看和篡改（第 8 站）。

每一层只用下面一层提供的 service，并补上它缺的那一样东西：

| Layer | 下面一层给了什么 | 这一层补上什么 |
|---|---|---|
| application（HTTP、DNS） | 一条 process 到 process 的通道 | 具体的应用：取网页、查名字 |
| transport（UDP、TCP） | 尽力把 datagram 送到某台 host，可能丢、乱序 | 送到哪个 process；可靠、按顺序；不压垮网络 |
| network（IP、OSPF、RIP） | 一条 link 上的两个 node 能互发 frame | 跨很多条 link 找到目的 host |
| link（Ethernet、ARP） | 一根线上能传 bit | 同一条 link 上多个 node 怎样轮流发、发错了能发现 |

## [net] Packet switching、delay 与 encapsulation

:::skip
能算出 3 个 packet 经过一个 router 的 end-to-end delay，说出 traffic intensity 大于 1 时 queue 怎样增长，并能画出一个 frame 经过 router 时哪个 header 被换掉，就可以去第 2 站。
:::

### 一个 packet 在一条 link 上花多少时间

Source 要把一个 $L=8000$ bit 的 packet 发到 2000 km 外的 router，link 的 rate 是 $R=1$ Mbps。时间分两段，彼此无关。

第一段，把 8000 个 bit 一个一个推上线。推一个 bit 要 $1/R$，推完全部要

$$d_\text{trans}=\frac{L}{R}=\frac{8000}{10^6}\text{ s}=8\text{ ms}$$

这叫 transmission delay，只和 packet 大小、link rate 有关。

第二段，每个 bit 推上线以后还要在线上走到对面。信号在线里的速度大约是 $2\times10^8$ m/s，走 2000 km 要

$$d_\text{prop}=\frac{2\times10^6\text{ m}}{2\times10^8\text{ m/s}}=10\text{ ms}$$

这叫 propagation delay，只和距离有关，和 packet 多大、link rate 多高都无关。

Router 收到一个 packet 要先收完整个 packet、检查过、查好表，才开始往下一条 link 发，这叫 store-and-forward。所以经过两条同样的 link，一个 packet 的 end-to-end delay 是 $2\times(8+10)=36$ ms。

### 为什么要把 message 拆成 packet

现在要送的是 24000 bit。整个作为一个 message 发，每条 link 的 transmission delay 是 24 ms，两条 link 共 $2\times24+2\times10=68$ ms。

拆成 3 个 8000 bit 的 packet 再发，结果是 52 ms。

::fig[cs2105-delay] Source 一个接一个地发 3 个 packet，router 每收完一个就转发一个。深色是最后一个 packet。看 router 那条竖线：packet 2 还在 link 1 上的时候，packet 1 已经在 link 2 上了。

快的原因在图里：拆开以后两条 link 同时在忙。把这个数一般化。第一个 packet 和单独发一样，经过 $N$ 条 link 要 $N(L/R+d_\text{prop})$。之后每条 link 都是一个接一个地发，后面的 packet 一个比一个晚 $L/R$ 到达，最后一个比第一个晚 $(P-1)L/R$：

$$d_\text{end-to-end}=N\,\frac{L}{R}+N\,d_\text{prop}+(P-1)\,\frac{L}{R}=(N+P-1)\frac{L}{R}+N\,d_\text{prop}$$

代入 $N=2$、$P=3$、$L/R=8$ ms、$d_\text{prop}=10$ ms：$(2+3-1)\times8+2\times10=52$ ms，和图里一致。

照这个 formula，packet 拆得越小越快。拦住这件事的是每个 packet 身上的 header，下面第 4 小节算这笔账。

:::wrong Link 的 bandwidth 越高，一个 packet 到得越快
Bandwidth 只缩短 $d_\text{trans}$，管不到 $d_\text{prop}$。上面那条 2000 km 的 link 从 1 Mbps 升到 1 Gbps，一个 8000 bit 的 packet 的 delay 从 $8+10=18$ ms 变成 $0.008+10=10.008$ ms，快了不到一倍，而 rate 涨了一千倍。剩下的 10 ms 是信号走 2000 km 的时间，任何 link 都省不掉。对小 packet、长距离来说，限制速度的是距离。
:::

### Queue 什么时候会无限增长

上面假设 router 收到 packet 时下一条 link 正空闲。实际上很多 input 的 packet 挤向同一条 output link，来不及发的在 buffer 里排队，等的时间叫 queueing delay。

设 packet 平均每秒到达 $a$ 个，每个 $L$ bit，output link 的 rate 是 $R$。每秒涌进来 $La$ bit，最多送走 $R$ bit。比值 $La/R$ 叫 traffic intensity。

**$La/R>1$。** 例如每秒到达 1.2 Mbit，link 只有 1 Mbps。每秒净增 0.2 Mbit，10 秒后积压 2 Mbit，也就是 250 个 8000 bit 的 packet。Buffer 是有限的，满了以后新来的 packet 只能被丢掉。这就是 packet loss 的主要来源：不是线坏了，是 router 的 buffer 满了。

**$La/R<1$ 也会排队。** 每 100 ms 到达 10 个 packet，$La/R=10\times8000\times10/10^6=0.8$。如果它们均匀地每 10 ms 来一个，每个到达时前一个早已发完（只要 8 ms），谁都不用等。如果 10 个同时到，第 $n$ 个要等前面 $n-1$ 个发完，等 $(n-1)\times8$ ms，平均

$$\frac{(0+1+\cdots+9)\times8}{10}=\frac{45\times8}{10}=36\text{ ms}$$

同样的 traffic intensity，queueing delay 从 0 变成 36 ms，差别全在到达是否扎堆。所以 queueing delay 是四种 delay 里唯一不固定的一种，$La/R$ 越接近 1，越容易排长队。第 4 站的 congestion control 就是为了让 sender 自己发现这件事并减速。

还剩一种是 processing delay：router 检查 header、查表的时间，通常是 microsecond 量级，题目里一般忽略。

### 一层套一层：encapsulation

第一个表里每一层要补的东西，都要靠在 packet 上写字来实现：transport 要写明送给哪个 process（port），network 要写明送给哪台 host（IP 地址），link 要写明这一跳送给线上的哪个 node（MAC 地址）。每一层把上面交下来的东西整个当作 payload，在前面加上自己的 header，交给下一层。这叫 encapsulation。

::fig[cs2105-encap] 一个 message 从 host A 到 host B。每一层的方框里是这一层看到的东西；动起来时可以看到它往下走一层就多一个 header，到了 switch 只拆到 link 层，到了 router 拆到 network 层，换一个新的 link header 再发。

不同的设备拆到不同的层，这决定了它们各自能做什么：switch 只看 MAC 地址，所以只能在一个 LAN 里转发（第 7 站）；router 看 IP 地址，所以能跨网络找路（第 5、6 站）；只有两端的 host 才拆到 transport 和 application，中间的设备不碰 TCP 的内容。

现在算 header 的账。TCP header 和 IP header 各 20 byte，Ethernet 在前面加 14 byte header、后面加 4 byte CRC。一个装满的 Ethernet frame 带 1460 byte 的 application data，frame 一共 $1460+20+20+18=1518$ byte，efficiency 是 $1460/1518=96.2\%$。如果只发一个 byte（比如远程登录时按一个键），IP datagram 是 $1+40=41$ byte，而 Ethernet 规定 payload 至少 46 byte（第 7 站推它的来历），frame 被补到 64 byte，efficiency 只有 $1/64=1.6\%$。Packet 拆得太小，bandwidth 就都花在 header 上了。

:::from
Delay 的四种分类和 $(N+P-1)L/R$ 的数法是 Kurose & Ross 第 1 章的标准讲法，这一章的 slides 没有读到，是凭自己的知识写的；数值例子和扎堆到达的 queue 例子是为这一页算的。Header 的字节数取 TCP、IP 不带 option 时的 20 byte；Ethernet 的 46 到 1500 byte payload、4 byte CRC 来自 [CS144 Lecture 10](https://www.scs.stanford.edu/08sp-cs144/notes/l10.pdf) 的 frame 格式。
:::

## [app] HTTP 与 DNS

:::skip

### Process 怎样找到另一个 process

一台 host 上同时跑着浏览器、聊天软件、后台更新程序。IP 地址只能把 packet 送到这台 host，再往里送给哪个 process，要靠 16 bit 的 port number。Server 守在一个大家事先约定的 port 上（HTTP 是 80，HTTPS 是 443，DNS 是 53），client 由 operating system 随手分配一个临时的 port。一个通信端点就是一对（IP 地址，port），application 通过 socket 往里写、从里读。

下面是一个最小的 HTTP client，用 Python 的 socket。它说明 HTTP 不过是在一条 TCP connection 上来回传的几行文字：

```python
from socket import socket, AF_INET, SOCK_STREAM

s = socket(AF_INET, SOCK_STREAM)          # SOCK_STREAM = TCP
s.connect(("example.com", 80))            # 这一步完成 TCP handshake
s.sendall(b"GET /index.html HTTP/1.1\r\n"
          b"Host: example.com\r\n"
          b"Connection: close\r\n"
          b"\r\n")                        # 空行表示 header 结束
reply = b""
while chunk := s.recv(4096):              # server 关掉 connection 时 recv 返回空
    reply += chunk
print(reply.split(b"\r\n")[0])            # 例如 b'HTTP/1.1 200 OK'
```

### HTTP 的 message 长什么样

Request 第一行是 request line：method、路径、版本。下面每行一个 header，`名字: 值`，最后一个空行。Response 第一行是 status line：版本、status code、一句说明，然后是 header、空行、body。

```
GET /index.html HTTP/1.1          HTTP/1.1 200 OK
Host: example.com                 Date: Sat, 16 Mar 2024 18:33:08 GMT
User-Agent: robjs                 Content-Type: text/html
                                  Content-Length: 1256

                                  <!doctype html> ...
```

常用的 method 是 GET（取东西，body 通常为空）、POST（交东西，比如表单，内容在 body 里）、HEAD（只要 header 不要 body）。Status code 按第一位分类：

| Code | 意思 | 例子 |
|---|---|---|
| 2xx | 成功 | 200 OK |
| 3xx | 去别处取 | 301 Moved Permanently（新地址在 `Location` header 里）、304 Not Modified |
| 4xx | client 的错 | 400 Bad Request、403 Forbidden、404 Not Found |
| 5xx | server 的错 | 500 Internal Server Error、503 Service Unavailable |

### 取一个页面要几个 RTT

回到开头的第一次事故。HTTP 跑在 TCP 上，TCP 在传数据之前要先 handshake：client 发 SYN，server 回 SYNACK，这用掉 1 个 RTT；client 随后把第三个 handshake 消息和 GET 一起发出，server 回 response，又是 1 个 RTT。所以新开一条 connection 取一个 object，至少 2 个 RTT（这里忽略 transmission time）。

::fig[cs2105-http] 一个 base HTML 加两张图片。Non-persistent 的每个 object 都要重新 handshake；persistent 只 handshake 一次；pipelining 不等上一个 response 回来就把两张图的 request 一起发出。

**Non-persistent HTTP**：每个 object 一条新 connection，用完就关。1 个 HTML 加 10 张图，一个接一个地取，$11\times2=22$ 个 RTT，$22\times20=440$ ms。浏览器可以同时开多条 connection：先用 2 个 RTT 取到 HTML（不读到 HTML 不知道要哪些图），再同时开 10 条 connection 取图，又是 2 个 RTT，共 4 个 RTT，80 ms。代价是 server 要同时维护很多条 connection。

**Persistent HTTP**：取完不关，后面的 request 沿用同一条 connection。不 pipelining 时，handshake 1 个 RTT，之后每个 object 1 个 RTT，$1+11=12$ 个 RTT，240 ms。

**Persistent + pipelining**：client 读到 HTML 以后，不等第一张图回来就把 10 个 request 连着发出，server 依次回答，10 张图只占 1 个 RTT。$1+1+1=3$ 个 RTT，60 ms。这就是开头说的“换一种用 connection 的方式”。

### HTTP 记不住你，cookie 替它记

HTTP server 不保存任何关于 client 的状态，每个 request 单独处理，这叫 stateless。好处是 server 崩溃重启后不需要恢复什么。坏处是购物车、登录状态没地方放。

Cookie 的办法是让 client 替 server 带着一个号码：

1. 第一次访问时，server 在自己的 database 里开一条记录，在 response 里加 `Set-Cookie: id=1678`。
2. 浏览器把 `id=1678` 存下来，以后每次访问这个网站，request 里都带 `Cookie: id=1678`。
3. Server 用 1678 去 database 里查出“这是谁、购物车里有什么”。

状态仍然只在 server 的 database 里，HTTP 本身照旧 stateless，每个 request 带的只是一把钥匙。

### 不重复传没变过的东西：conditional GET

浏览器的 cache 里已经有一张 100 KB 的图，但不知道 server 上的是否更新过。重新取一遍，在 1 Mbps 的 link 上要 $100\times8/1000=0.8$ s。HTTP 的办法是问一句“如果改过才给我”：

```
GET /logo.png HTTP/1.1
Host: example.com
If-Modified-Since: Wed, 9 Sep 2026 09:23:24 GMT
```

没改过，server 回 `HTTP/1.1 304 Not Modified`，没有 body，只花一个 RTT 和几百 byte；改过，就照常回 200 和新内容。网络里的 proxy cache 用的也是这一招。

### DNS：名字怎样变成 IP 地址

IP packet 里写的是 32 bit 的地址，人记的是 `eecs.berkeley.edu`。最直接的设计是一台 server 存下全世界所有名字。它要回答全世界的查询，一坏全网失灵，离大多数用户都很远，而且每个新名字都要去它那里登记。

DNS 把名字空间切成一棵树，每一级只管自己下面那一级：

- **Root server** 只知道每个 top-level domain（`.com`、`.edu`、`.sg`……）由谁负责。Root 的地址一共 13 个，每个背后有很多台物理机器。
- **TLD server**（例如 `.edu` 的）只知道 `berkeley.edu`、`mit.edu` 这样的 domain 由谁负责。
- **Authoritative server**（例如 `berkeley.edu` 的）存着这个 domain 里的真正答案。

每台 host 还配有一个 local DNS server（recursive resolver，通常是 ISP 或学校的），host 只问它，由它去这棵树上逐级问。

::fig[cs2105-dns] 查 `eecs.berkeley.edu`，图里的地址来自 CS168 textbook 用 `dig +norecurse` 实际走的一遍。Root 和 TLD 都不知道答案，只告诉 local DNS 下一个该问谁。

逐条看这 8 条消息：

1. Host 问 local DNS：`eecs.berkeley.edu` 的 IP 地址是什么？
2. Local DNS 问 root。
3. Root 回答：我不知道，`.edu` 归 `a.edu-servers.net` 管，它的地址是 192.5.6.30。
4. Local DNS 问 192.5.6.30。
5. `.edu` 回答：`berkeley.edu` 归 `adns1.berkeley.edu` 管，地址 128.32.136.3。
6. Local DNS 问 128.32.136.3。
7. 它回答：`eecs.berkeley.edu` 的地址是 23.185.0.1，这条答案可以 cache 86400 秒。
8. Local DNS 把答案交给 host。

第 2 到 7 条里，每个 server 都只回答一步，由 local DNS 自己去问下一个，这叫 iterative query。第 1、8 条是 recursive query：host 要的是最终答案。如果 root 也替 local DNS 去问 TLD、TLD 再替它去问 authoritative，就是全程 recursive。

答案以 resource record 的形式存放，每条是（name，value，type，TTL）：

| Type | name | value |
|---|---|---|
| A | hostname | IPv4 地址 |
| NS | domain | 负责它的 name server 的 hostname |
| CNAME | 别名 | 真正的 hostname |
| MX | domain | 收邮件的 server 的 hostname |

例如上面第 7 条回答是（`eecs.berkeley.edu`，23.185.0.1，A，86400），第 5 条回答里有（`berkeley.edu`，`adns1.berkeley.edu`，NS）。

第 5 条回答里，`.edu` 除了给 NS record（“问 `adns1.berkeley.edu`”），还顺带给了那台 server 的 A record（128.32.136.3）。否则 local DNS 为了问 `berkeley.edu` 里的一台机器，得先查出 `adns1.berkeley.edu` 的地址，而这个名字本身又在 `berkeley.edu` 里，绕成一个圈。

**Caching。** 每条答案都带 TTL，在 TTL 之内 local DNS 直接用 cache。CS168 的例子里 `.edu` 的 NS record 的 TTL 是 172800 秒（48 小时）。几分钟后有人查 `www.berkeley.edu`，local DNS 的 cache 里已有 `berkeley.edu` 的 NS record 和地址，直接去问 128.32.136.3，消息只剩 1、6、7、8 四条，root 和 `.edu` 都不用问。绝大多数查询就这样被 cache 挡在 root 和 TLD 之外。

**为什么用 UDP。** DNS 查询和回答都很短，一个 packet 装得下。用 TCP 要先 handshake，多一个 RTT，server 还要为每个 client 保留 connection 的状态。用 UDP 的 port 53，一问一答一个 RTT；丢了就由 client timeout 重问，消息里有一个 16 bit 的 ID 用来把回答和问题对上。

:::wrong Recursive query 比 iterative query 少发消息
数一下就知道不是。全程 recursive 时：host → local（1）→ root（2）→ TLD（3）→ authoritative（4），答案沿原路回来（5、6、7、8），也是 8 条。消息数一样，差别在于谁干活：recursive 要 root 替你去问 TLD，root 就得为每个请求记住“我还欠谁一个答案”，全世界的查询都压在 13 个 root 地址上，它扛不住。所以实际系统里，host 对 local DNS 用 recursive，local DNS 对 root、TLD 用 iterative。
:::

HTTP 的 message 格式、status code 分类、`User-Agent: robjs` 的例子和 Date 那一行来自 [CS168 textbook 的 HTTP 一节](https://textbook.cs168.io/applications/http.html)；那一节没有讲 RTT 的数法、cookie 和 conditional GET，这三部分是按 Kurose & Ross 第 2 章的标准讲法凭自己的知识写的（这一章的 slides 没有读），10 张图的数字是为这一页算的。DNS 的逐级查询、全部地址和 TTL、13 个 root 地址、16 bit ID 和用 UDP 的理由来自 [CS168 textbook 的 DNS 一节](https://textbook.cs168.io/applications/dns.html)；那一节没有用 “iterative” 和 “glue” 这两个词，iterative 与 recursive 的消息对比是自己数的，record types 的表对照的是 CS168 那一节的列表。

## [rdt] UDP 与 reliable data transfer

:::skip
能算 UDP checksum；能说出 stop-and-wait 里 checksum、ACK、sequence number、timer 各防哪一种出错；能在 timeline 上走 Go-Back-N 和 Selective Repeat；能推出 SR 的 window 上限，就可以去第 4 站。
:::

### UDP 给了什么

IP 只负责把 datagram 尽力送到对方 host，可能丢、可能乱序、可能有 bit 出错。UDP 在它上面只加了两样东西：port（送给哪个 process）和 checksum（发现 bit 出错）。Header 一共 8 byte：source port、destination port、length、checksum，各 16 bit。

Checksum 的算法：把要保护的内容切成 16 bit 的 word，全部加起来，最高位进出来的 1 加回到最低位（wraparound），最后把结果按位取反。Kurose & Ross 的例子是三个 word：

$$\begin{array}{r}0110011001100000\\+\ 0101010101010101\\\hline1011101110110101\end{array}\qquad\begin{array}{r}1011101110110101\\+\ 1000111100001100\\\hline1\,0100101011000001\end{array}$$

第二次加法进出一位，把它加回最低位：$0100101011000001+1=0100101011000010$。按位取反得到 checksum $1011010100111101$。

Receiver 把收到的三个 word 和 checksum 全部加起来（同样 wraparound）。Sum 加上它的反码，每一位都是 1，所以没出错时结果是 $1111111111111111$；有任何一位是 0，就知道出了错，把它扔掉。

:::edge Checksum 漏掉的错
第一个 word 的最低位从 0 变成 1，第二个 word 的最低位从 1 变成 0。前者让 sum 加 1，后者让 sum 减 1，总和不变，checksum 照样通过。同一列上一增一减的两个错它都看不出来。Link layer 用更强的 CRC（第 7 站），UDP 的 checksum 只是最后一道粗筛。
:::

UDP 不 retransmit、不排序、不控制速度。DNS 用它，是因为一问一答、丢了重问即可；视频通话用它，是因为迟到的画面已经没用，retransmit 反而添乱。要可靠，就得自己在 UDP 或 IP 之上搭，这就是下面几节和 TCP 做的事。

### 从一个 packet 开始，一次补一个漏洞

先只考虑发一个 packet，看它可能怎样出事，每出一种事就补一个机制。这个顺序来自 Kurose & Ross 的 rdt 1.0 到 3.0。

**Bit 出错。** 加 checksum，receiver 发现错了就回 NAK，对了回 ACK；sender 收到 NAK 就 retransmit。

**ACK 本身出错。** Sender 收到一个坏掉的回复，不知道对方说的是 ACK 还是 NAK。只能 retransmit，但如果对方其实已经收好了，receiver 就会把同一个 packet 收两次，而它分不出这是 retransmit 的还是新的。补救是给 packet 编号。只发一个、等一个的时候，相邻两个 packet 只需要区分开，编号用 0 和 1 轮流就够了。Receiver 收到和上一个同号的 packet，就知道是 retransmit，丢掉但再回一次 ACK。

**不要 NAK。** 有了编号，receiver 可以只回 ACK，并在 ACK 里写明它收到的是几号。Sender 期待 ACK1 却收到 ACK0，意思就是“1 号没收好”，作用和 NAK 一样。TCP 就只有 ACK。

**Packet 或 ACK 丢失。** 前面的机制都假设回复总会来。丢了，sender 会永远等下去。补救是计时：发出后启动 timer，到时没收到 ACK 就 retransmit。Timer 设得太短，ACK 只是来晚了，sender 就 retransmit 了一个对方已有的 packet。这不要紧，编号已经能让 receiver 认出重复，ACK 再晚也只是多一个可以忽略的重复 ACK。

到这里得到的 protocol 叫 stop-and-wait（rdt3.0）：发一个，等它的 ACK，到了再发下一个，timeout 就 retransmit。它在任何“出错、丢失、延迟”下都是对的。

### Stop-and-wait 正确，但太慢

开头第二次事故就是它。Link 1 Gbps，RTT 30 ms，packet 8000 bit。

::fig[cs2105-stopwait] 左边一次只发一个，右边连发三个再等。图里把 transmission time 放大了很多倍，否则它细得看不见。

Sender 从开始发到能发下一个，要经过 $L/R+\text{RTT}$；其中真正在往线上推 bit 的只有 $L/R$。Sender 忙着的时间所占的比例叫 utilization：

$$U_\text{sender}=\frac{L/R}{\text{RTT}+L/R}=\frac{0.008}{30+0.008}=0.00027$$

每 30.008 ms 送出 8000 bit，throughput 是 $8000/0.030008=267$ kbps。Protocol 本身把一条 1 Gbps 的 link 限成了 267 kbps。

办法是不等：一次发出多个 packet，ACK 回来之前继续发。连发 3 个，同样的一个周期里推了 $3L/R$，$U=0.00080$，正好 3 倍。要把 link 填满，一个周期里要能发 $(\text{RTT}+L/R)/(L/R)=30.008/0.008=3751$ 个 packet。这叫 pipelining。

Pipelining 带来两个新问题：编号不能只有 0 和 1；丢了一个之后，后面那些已经发出的怎么办。下面两种做法对第二个问题的回答不同。

### Go-Back-N

**Sender。** 允许最多 $N$ 个已发出、未 ACK 的 packet。最老的未 ACK 的 packet 的编号叫 base，可用的编号是 base 到 base $+N-1$，这一段叫 window。只有一个 timer，计的是最老的那个未 ACK 的 packet。

**Receiver。** 只接收编号恰好是下一个该收的（expectedseqnum）packet，交给上层，回 ACK。收到别的编号，一律丢掉，再回一次“我按顺序收到的最后一个”的 ACK。

**ACK 是 cumulative 的。** ACK $n$ 的意思是“$n$ 和它之前的全收到了”。Sender 收到 ACK $n$，就把 base 挪到 $n+1$。

**Timeout。** Retransmit base 起的全部已发出的 packet，这就是名字里的 “go back N”。

::fig[cs2105-gbn] Window $N=4$，单程 3 个时间单位，每个时间单位最多发一个 packet，timeout 8 个时间单位，pkt2 第一次发送时丢了。上方两条格子是 sender 和 receiver 各自的状态；最左边的小字是 sender 每收到一个 ACK 或 timeout 时做了什么。

跟着图走一遍：

- $t=0$ 到 3：window 是 0 到 3，sender 连发 pkt0 到 pkt3。pkt2 丢了。
- $t=3$：pkt0 到达，receiver 交付并回 ack0。$t=4$：pkt1 到达，回 ack1。
- $t=6$：pkt3 到达。Receiver 等的是 2，于是丢掉 pkt3，再发一次 ack1。同一时刻 ack0 回到 sender，base 挪到 1，window 变成 1 到 4，发 pkt4。
- $t=7$：ack1 到达，base 挪到 2，发 pkt5。Window 2 到 5 已满，sender 停下来等。
- $t=9$、10：pkt4、pkt5 到达，都被丢掉，各回一个重复的 ack1。
- $t=10$：pkt2 是在 $t=2$ 发的，timer 到期。Sender retransmit 2、3、4、5。
- 之后四个 retransmit 的 packet 依次到达并交付，ack2 到 ack5 在 $t=16$ 到 19 回来。

6 个 packet 一共发了 10 次。pkt3、4、5 其实早就安全到达过，只因为排在丢失的 pkt2 后面就被扔掉，又 retransmit 了一遍。

### Selective Repeat

GBN 的浪费在 receiver：它不肯留乱序到达的 packet。Selective Repeat 改的就是这一点。

**Receiver。** 有一个 $N$ 格的 window。落进 window 的 packet 都收下放进 buffer，并单独回一个 ACK，写的就是它自己的编号。等到 window 最左边那格到了，连同后面已经到齐的一起交付，window 往右挪。

**Sender。** 每个 packet 有自己的 timer，谁 timeout 只 retransmit 谁。收到 ACK 就把那一格标记为已 ACK；只有最左边那格被 ACK 了，window 才往右挪，一直挪到第一个未 ACK 的格子。

::fig[cs2105-sr] 和上一张图完全相同的设定。看 receiver 的格子：pkt3、4、5 到达时先变成浅色存进 buffer；看 sender 的格子：ack3、4、5 回来时那几格已经变深，但 window 的框卡在 2 不动。

- $t=6$、9、10：pkt3、4、5 先后到达，存进 buffer，分别回 ack3、ack4、ack5。
- $t=9$、12、13：ack3、4、5 回到 sender，三格被标记，base 仍是 2。
- $t=10$：pkt2 的 timer 到期，只 retransmit pkt2。
- $t=13$：pkt2 到达，receiver 一次交付 2、3、4、5，回 ack2。
- $t=16$：ack2 回到 sender，base 一口气从 2 挪到 6。

6 个 packet 一共发了 7 次，最后一个 ACK 在 $t=16$ 到达，GBN 是 $t=19$。代价是 receiver 要有 buffer，sender 要为每个 packet 维护一个 timer。

:::wrong 一个 ACK 丢了，对应的 packet 就要 retransmit
在 GBN 里，ACK 是 cumulative 的。假设上面的场景里 pkt2 没丢，但 ack0 在路上丢了。Sender 接着收到 ack1，意思是“0 和 1 都收到了”，base 直接挪到 2，pkt0 不需要 retransmit，丢掉的 ack0 没有造成任何后果。只有在 ack0 之后的 ACK 都没在 timeout 之前回来时，才会 retransmit。SR 的 ACK 是逐个的，ack0 丢了确实会让 pkt0 timeout 后 retransmit，所以 SR 的 receiver 对已经交付过的编号也要再回 ACK。
:::

### Sequence number 要有多少个

Header 里的编号只有 $k$ bit，编号从 0 到 $2^k-1$ 循环使用。$k$ 能小到多少？

::fig[cs2105-srdilemma] 只有 0 到 3 四个编号，SR 的 window 取 3。两种情况下 receiver 都在收完 0、1、2 之后把 window 挪到 {3, 0, 1}，然后收到一个编号为 0 的 packet。

在 (a) 里，三个 ACK 都到了，sender 往后发了 pkt3 和下一轮的 pkt0，这是新数据。在 (b) 里，三个 ACK 全丢了，sender timeout 后 retransmit 的是旧的 pkt0。Receiver 看不见 ACK 是否丢了，它收到的东西两种情况下一模一样，在 (b) 里就把旧数据当作新数据交了上去。

一般地推一遍。Receiver 刚收完一整个 window，编号 base 到 base $+N-1$，它的 window 挪到 base $+N$ 到 base $+2N-1$。这时 sender 可能处在两种极端：ACK 全到了，它在发 base $+N$ 起的新 packet；ACK 全丢了，它在 retransmit base 起的旧 packet。要让 receiver 分得清，这两段共 $2N$ 个编号在模 $2^k$ 之后不能有重合：

$$2N\le2^k,\qquad N\le2^{k-1}$$

图里 $2^k=4$、$N=3$，$2N=6>4$，旧的 0 和新的 0 撞上了。$N=2$ 就不会：receiver 收完 0、1 后 window 是 {2, 3}，retransmit 的旧 pkt0 不在其中，会被认出来。

GBN 的 receiver 只接收一个编号，window 相当于 1，同样的推理给出 $N+1\le2^k$，也就是 $N\le2^k-1$。

:::from
Rdt 的递进顺序、1 Gbps / 15 ms / 8000 bit 的 utilization 例子、连发 3 个是 3 倍、GBN 和 SR 的 sender 与 receiver 规则、pkt2 丢失的场景和 SR 用 0 到 3 编号、window 3 的困境，来自 [Kurose & Ross 第 7 版 Chapter 3 的 slides](https://cis.temple.edu/~tug29203/23fall-3329/lectures/ch3b.pdf)；那份 slides 只把困境作为问题提出，没有给出 $N\le2^{k-1}$，这个推导是自己写的。Checksum 的三个 word 是 Kurose & Ross 书里的例子，结果是为这一页重新算的。Duplicate 从哪里来（ACK 丢失、timer 太早）的说法对照过 [MIT 6.02 第 19 章](https://www.ocw.mit.edu/courses/6-02-introduction-to-eecs-ii-digital-communication-systems-fall-2012/2d3a62fd8f18f6bf69c70bc73f7d6ca9_MIT6_02F12_chap19.pdf)，它的 sliding window 实际上就是 SR。两张动图里的 timeline（单程 3、timeout 8、每单位发一个）是为这一页设定并用代码模拟的；Kurose 的原图里 GBN 的 timer 在 base 前进时会重新计时，这里让它计的是最老的未 ACK packet 的发送时刻，这样两张图的 timeout 时刻相同，差别只来自 retransmit 策略。
:::

## [tcp] TCP：reliable transfer、flow control 与 congestion control

:::skip
能按 byte 编号写出 Seq 和 ACK，能套 RTT estimation 的 formula，能逐个 RTT 写出 Reno 的 cwnd，并说清 flow control 和 congestion control 分别防谁被淹没，就可以去第 5 站。
:::

### Seq 和 ACK 数的是 byte

TCP 给 application 的是一条不分段的 byte stream，所以它的编号数的是 byte，不是 segment。一个 segment 的 Seq 是它所装的第一个 byte 的编号；ACK 写的是“我下一个想要的 byte 的编号”，也就是“这之前的全收到了”，和 GBN 一样是 cumulative 的。

例子：一个 500000 byte 的文件，每个 segment 最多装 MSS（maximum segment size）= 1000 byte，共 500 个 segment。第一个的 Seq 是 0（实际从一个随机的初始编号开始，见下一节，这里取 0 方便看），第二个是 1000，第三个是 2000。Receiver 收好前两个，回 ACK = 2000。

和 GBN 不同的是，TCP 的 receiver 会把乱序到达的 segment 留在 buffer 里（标准没有规定，但实际都这样做），而 sender timeout 只 retransmit 最老的那一个未 ACK 的 segment。所以 TCP 是 GBN 和 SR 的混合：ACK 像 GBN，retransmit 像 SR。

### 建立 connection：three-way handshake

两边在传数据之前要商定各自的初始 sequence number（ISN），并确认对方在线：

1. Client 发 SYN，Seq = $x$（随机选的 client ISN）。
2. Server 回 SYNACK，Seq = $y$（server 的 ISN），ACK = $x+1$。
3. Client 回 ACK = $y+1$，这个 segment 可以已经带着数据。

为什么不两次就够，为什么 ISN 要随机，都是同一个原因：网络里可能还飘着这对 port 上一个旧 connection 的 segment。如果只有两步，一个迟到的旧 SYN 到达 server，server 回个 SYNACK 就认定 connection 已建立，为一个早就不存在的 client 保留状态。有第三步，server 要等 client 对“$y+1$”的确认，旧 client 不会回这个，server 就知道这是旧的。ISN 随机，则旧 connection 遗留的 segment 的编号几乎不可能恰好落在新 connection 的 window 里。关闭时两边各发一个 FIN、各被 ACK 一次。

### Timeout 设多长

Timeout 比 RTT 短，会 retransmit 对方已经收到的 segment；比 RTT 长太多，丢了要等很久才 retransmit。RTT 又随 queue 的长短不断变化。TCP 对每个 ACK 测一个 SampleRTT，然后做 exponentially weighted moving average：

$$\text{EstimatedRTT}\leftarrow(1-\alpha)\,\text{EstimatedRTT}+\alpha\cdot\text{SampleRTT},\qquad\alpha=0.125$$

再估计 RTT 的波动有多大：

$$\text{DevRTT}\leftarrow(1-\beta)\,\text{DevRTT}+\beta\,\lvert\text{SampleRTT}-\text{EstimatedRTT}\rvert,\qquad\beta=0.25$$

$$\text{TimeoutInterval}=\text{EstimatedRTT}+4\,\text{DevRTT}$$

加 4 倍的 DevRTT，是为了让“RTT 只是偶然变长”极少被误判成 packet loss。

例子：开始时 EstimatedRTT = 100 ms，DevRTT = 10 ms，先后测到 106、120、140、90 ms。每一步先用旧的 EstimatedRTT 更新 DevRTT，再更新 EstimatedRTT：

| SampleRTT | DevRTT | EstimatedRTT | TimeoutInterval |
|---|---|---|---|
| 106 | $0.75\times10+0.25\times6=9.00$ | $0.875\times100+0.125\times106=100.75$ | 136.75 |
| 120 | $0.75\times9+0.25\times19.25=11.56$ | 103.16 | 149.41 |
| 140 | $0.75\times11.56+0.25\times36.84=17.88$ | 107.76 | 179.29 |
| 90 | $0.75\times17.88+0.25\times17.76=17.85$ | 105.54 | 176.95 |

一个 140 ms 的 sample 只把 EstimatedRTT 拉高了 4.6 ms，却让 timeout 涨了近 30 ms：波动变大时，timeout 留出的余量自动变大。

两个细节。Retransmit 过的 segment 不拿来测 RTT，因为回来的 ACK 分不清是对第一次还是第二次发送的回答。真的 timeout 后，下一次的 timeout 加倍，因为连续 timeout 多半意味着网络正在 congestion，越催越糟。

### 不等 timeout：fast retransmit

Timeout 通常远大于 RTT。等它到期才 retransmit，pipe 里就空转了很久。Cumulative ACK 其实早就透露了消息。

::fig[cs2105-fastrtx] 每个 segment 100 byte，Seq = 1100 那个丢了。后面三个 segment 到达时，receiver 能回的都只是“我还在等 1100”。

Receiver 每收到一个乱序的 segment，都立刻再发一次 ACK = 1100。Sender 收到同一个 ACK 的三个重复（加上第一个共四个），就推断 1100 丢了，不等 timeout 立即 retransmit。retransmit 的 1100 到达后，receiver 的 buffer 里 1200 到 1499 早已就位，于是直接回 ACK = 1500。

为什么要等 3 个重复而不是 1 个：packet 可能只是被乱序了，晚到一点。一个重复 ACK 常常只是乱序，连续三个才大概率是丢了。

### Flow control：别把 receiver 的 buffer 灌满

Receiver 收下的数据放在一块大小为 RcvBuffer 的 buffer 里，等 application 来读。Application 读得慢，sender 发得快，buffer 就会溢出。Receiver 在每个 segment 的 header 里写上自己还剩多少空间：

$$\text{rwnd}=\text{RcvBuffer}-(\text{LastByteRcvd}-\text{LastByteRead})$$

Sender 保证在路上的数据不超过它：

$$\text{LastByteSent}-\text{LastByteAcked}\le\text{rwnd}$$

例子：RcvBuffer = 65536 byte，receiver 已经收到第 50000 byte，application 读到第 30000 byte，buffer 里积着 20000 byte 没读，rwnd = 65536 − 20000 = 45536。Sender 在路上未 ACK 的数据最多 45536 byte。

Rwnd 降到 0 时，sender 停发。但如果之后 receiver 没有数据要发给 sender，就永远没有 segment 把“空出来了”带回去，双方僵住。所以 rwnd = 0 时 sender 仍定期发一个只带 1 byte 的 segment 去探，好让 receiver 在回答里报出新的 rwnd。

### Congestion control：别把网络灌满

Flow control 只保护 receiver。第 1 站说过，router 的 buffer 满了就丢 packet；丢了 sender 就 retransmit，网络里的负载反而更重。CS144 的讲义记下了 Internet 从 1986 年起多次 congestion collapse，1988 年 TCP Tahoe 才加入现在的这套机制。

Sender 没有人告诉它网络有多忙，只能从自己观察到的现象推断：ACK 按时回来，说明还能多发；packet loss（三个 duplicate ACK 或 timeout）说明某处的 queue 满了。它维护一个 congestion window cwnd，要求

$$\text{LastByteSent}-\text{LastByteAcked}\le\min(\text{cwnd},\ \text{rwnd})$$

一个 RTT 里最多送出一个 window，所以 sending rate 大约是 $\text{cwnd}/\text{RTT}$。调 cwnd 就是调速度。规则如下，以 MSS 为单位：

- **Slow start。** cwnd 从 1 开始，每收到一个新的 ACK 加 1。一个 RTT 里送出 cwnd 个 segment、回来 cwnd 个 ACK，cwnd 就翻倍：1、2、4、8……
- **到 ssthresh 以后改为 congestion avoidance。** 每个 ACK 加 $1/\text{cwnd}$，一个 RTT 回来 cwnd 个 ACK，合起来加 1。这是 additive increase。
- **三个 duplicate ACK。** 后面的 segment 还在到达，网络只是轻度 congestion。Ssthresh = cwnd / 2。Reno 把 cwnd 也减到 ssthresh（在 fast recovery 期间先是 ssthresh + 3，新的 ACK 一到就回到 ssthresh），继续 additive increase；Tahoe 直接把 cwnd 降到 1，重新 slow start。这是 multiplicative decrease。
- **Timeout。** 连 duplicate ACK 都没有，说明 congestion 严重。两种版本都是 ssthresh = cwnd / 2，cwnd = 1，重新 slow start。

::fig[cs2105-cwnd] 一个 TCP Reno connection 的前 20 个 RTT，每一列是这一轮送出的 segment，一格一个；深色那一格所在的轮次检测到了 packet loss。动起来时上方逐轮写出 cwnd、ssthresh 和这一轮的规则。

按图逐轮读：

- 第 1 到 5 轮，ssthresh = 16，slow start：1、2、4、8、16。
- Cwnd 到了 16，改为每轮加 1：17、18、19、20。
- 第 9 轮（cwnd = 20）收到三个 duplicate ACK：ssthresh = 20 / 2 = 10，Reno 的 cwnd = 10。若是 Tahoe，第 10 轮的 cwnd 会是 1，然后 1、2、4、8、10、11……
- 第 10 到 14 轮：10、11、12、13、14。
- 第 14 轮 timeout：ssthresh = 14 / 2 = 7，cwnd = 1。
- 第 15 到 18 轮 slow start：1、2、4，下一轮本该是 8，但到 7 就该停止翻倍，所以是 7。之后每轮加 1：8、9。

:::wrong 叫 slow start，所以这一段增长得慢
它是整个过程里增长最快的一段。上面的例子里 cwnd 从 1 到 16 只用了 4 个 RTT，而从 16 到 20 用了 4 个 RTT 只加了 4。“slow” 是和更早的 TCP 比：那时 connection 一建立就直接发出一整个 receiver window，瞬间灌满 router 的 queue。Slow start 从 1 开始、靠 ACK 的节奏放大，可是放大是 exponential 的。

### AIMD 为什么会公平

两个 flow 共用一条 bottleneck link。为了算起来简单，把它们的 rate 直接用 cwnd 的单位表示，capacity 是 16：两者之和超过 16 就都 packet loss。flow 1 从 2 开始，flow 2 从 10 开始，每轮各加 1，packet loss 时各自减半：

| 时刻 | flow 1 | flow 2 | 差 |
|---|---|---|---|
| 开始 | 2 | 10 | 8 |
| 加到 5 和 13，和为 18，packet loss 后减半 | 2.5 | 6.5 | 4 |
| 加到 5.5 和 9.5，和为 15；再加一轮为 17，packet loss 后减半 | 3.25 | 5.25 | 2 |
| 下一次 packet loss 后 | 3.625 | 4.625 | 1 |
| 再下一次 | 3.8125 | 4.3125 | 0.5 |

两个 flow 同时加 1，差不变；同时减半，差也减半。每丢一次包，差距缩小一半，两者走向平分 capacity。换成 additive decrease（packet loss 时各减同样的量），差永远是 8，不公平一直保持。换成 multiplicative increase（每轮各乘同样的倍数），比值永远是 5，同样不会改善。只有“加的时候一样多、减的时候按比例”这种组合，才会一步步把差距抹平。

最后，AIMD 的 cwnd 在 $W/2$ 和 $W$ 之间锯齿形来回（$W$ 是 packet loss 时的 window），平均是 $\tfrac34W$。例如 packet loss 时 $W=20$ 个 1460 byte 的 segment、RTT 100 ms，峰值 rate 是 $20\times1460\times8/0.1=2.336$ Mbps，平均约 $0.75\times2.336=1.752$ Mbps。

:::back
Cumulative ACK、window、timeout retransmit 都是[第 3 站](#rdt)的机制；congestion 从哪来，是[第 1 站](#net)的 traffic intensity。
:::

:::from

## [ip] IP：addressing、forwarding、DHCP 与 NAT

### IP 地址和 subnet

IP 地址是 32 bit，写成四个 0 到 255 的十进制数，例如 223.1.1.1。地址属于一个 interface，不属于一台机器：router 有几个 interface 就有几个地址。

不经过 router 就能互相送达的那些 interface 组成一个 subnet，它们的地址前面若干位相同。CIDR 的写法 a.b.c.d/$x$ 说的是：前 $x$ 位是 subnet 的部分，剩下 $32-x$ 位用来区分 subnet 里的 interface。223.1.1.0/24 的前 24 位固定，最后 8 位从 0 到 255；全 0 表示 subnet 本身，全 1 是 broadcast 地址，能分给 interface 的是 $2^8-2=254$ 个。

判断一个地址在不在某个 subnet 里，就是把它和 subnet mask（前 $x$ 位为 1、其余为 0）按位 AND，看结果是否等于 subnet 的地址。/24 的 mask 是 255.255.255.0。192.0.2.1 AND 255.255.255.0 = 192.0.2.0，在 192.0.2.0/24 里；203.0.113.5 AND 255.255.255.0 = 203.0.113.0，不在。第 7 站的 ARP 一开头就要做这个判断。

### Forwarding：longest prefix match

Router 收到一个 datagram，要根据 destination 地址决定从哪个 interface 送出去。Internet 上的地址有几十亿个，每个一条是不可能的。Forwarding table 里每一行是一个 prefix，代表一整段地址。

问题是，几段 prefix 可以互相包含。一家 ISP 拿到了 200.23.16.0/20，又把其中一段 200.23.24.0/24 经由另一条路送到它的一个客户。看下面这张表：

| Prefix | 区间 | Interface |
|---|---|---|
| 200.23.16.0/21 | 200.23.16.0 到 200.23.23.255 | 0 |
| 200.23.24.0/24 | 200.23.24.0 到 200.23.24.255 | 1 |
| 200.23.24.0/21 | 200.23.24.0 到 200.23.31.255 | 2 |
| 其他 | | 3 |

::fig[cs2105-lpm] 把三条 prefix 画成地址区间（横轴只画了第三个 byte）。/24 那一段整个落在第二个 /21 里面。

规则是：在所有 match 的 prefix 中，取最长的那一条。逐个查：

- 200.23.22.161：第三个 byte 22 = 00010110，前 21 位是 11001000 00010111 00010，和第一行一致，只有它 match，走 interface 0。
- 200.23.24.170：第三个 byte 24 = 00011000。前 21 位 11001000 00010111 00011 和第三行一致；前 24 位 11001000 00010111 00011000 和第二行一致。两行都 match，第二行更长，走 interface 1。
- 200.23.30.5：第三个 byte 30 = 00011110，前 24 位不是 00011000，只有第三行 match，走 interface 2。
- 200.23.40.1：都不 match，走 default 的 interface 3。

这样，ISP 对外只需要宣告一条 200.23.16.0/20，别人表里也只要一行，这叫 route aggregation；被单独转走的那一小段只需要在知道这件事的 router 上多写一行更长的 prefix。

:::wrong 从上往下找到第一条 match 的规则就行
那么结果会依赖表的顺序。把上面的表按 interface 编号排，200.23.24.170 先 match 到第三行，被送到 interface 2，那一小段客户的流量就全送错了地方。Longest prefix match 和行的顺序无关：更具体的规则总是优先。
:::

### Host 怎样拿到地址：DHCP

一台笔记本连上 UTown 的 Wi-Fi，它需要四样东西：自己的 IP 地址、subnet mask、default gateway（第一跳 router 的地址）、DNS server 的地址。问题在于它还没有 IP 地址，也不知道 DHCP server 在哪，没法正常地发 IP packet 去问。

DHCP 的四条消息都在 UDP 上，靠 broadcast 绕过这个困难：

1. **Discover**：client 用 source 0.0.0.0、destination 255.255.255.255 broadcast，“有没有 DHCP server？”
2. **Offer**：server 回一个可用的地址和租期。
3. **Request**：client broadcast“我要这个地址”。仍然用 broadcast，是因为可能有几个 server 都 offer 了，这样其他 server 也知道自己的 offer 没被选中。
4. **ACK**：server 确认，同时给出 mask、gateway、DNS server。

地址是租的，到期前要续租，所以离开的机器的地址会被收回再分配。

### NAT：一个地址，一整个家

家里的 router 从 ISP 只拿到一个公网地址 138.76.29.7，家里的设备用 10.0.0.0/24 这样的私有地址。私有地址在 Internet 上不被 route，所以出门的 datagram 必须改写。

NAT router 维护一张 translation table。10.0.0.1 的浏览器从 port 3345 访问 128.119.40.186 的 80：

1. Datagram 到达 NAT router，source 是 10.0.0.1:3345。
2. Router 选一个没用过的 port 5001，把 source 改成 138.76.29.7:5001，在表里记一行：138.76.29.7:5001 ↔ 10.0.0.1:3345。
3. Server 的回复发往 138.76.29.7:5001。
4. Router 查表，把 destination 改回 10.0.0.1:3345，送进家里。

Port 是 16 bit，一个公网地址最多同时撑起约 65536 条这样的 connection。代价是外面的人不能主动连进来：一个发往 138.76.29.7 的新 connection，表里没有对应的行，router 不知道该给家里哪台机器。

### Datagram 里还写了什么：TTL 和 fragmentation

IP header 里有 TTL，每经过一个 router 减 1，减到 0 就丢掉，并向 source 回一个 ICMP “time exceeded” 消息。这防止 routing 出错时 datagram 在 loop 里永远转下去（第 6 站就有这样的 loop）。Traceroute 利用了它：依次发 TTL = 1、2、3……的 packet，第 $n$ 个 router 把 TTL 减到 0 并回 ICMP，于是 source 一跳一跳地知道路上的每一个 router。

不同的 link 能装的最大 frame 不同，叫 MTU。一个 4000 byte 的 datagram（20 byte header + 3980 byte data）要过 MTU 为 1500 byte 的 link，必须切成 fragment，到目的 host 再拼起来。每个 fragment 自带 20 byte header，最多装 1480 byte data：

| Fragment | 总长 | Data | Offset（8 byte 为单位） | More-fragments flag |
|---|---|---|---|---|
| 1 | 1500 | 1480 | 0 | 1 |
| 2 | 1500 | 1480 | 1480 / 8 = 185 | 1 |
| 3 | 1040 | 3980 − 2960 = 1020 | 2960 / 8 = 370 | 0 |

Offset 以 8 byte 为单位，所以除了最后一个，每个 fragment 的 data 长度都必须是 8 的倍数，1480 恰好是。三个 fragment 的 identification 字段相同，receiver 靠它和 offset 拼回原样；任何一个丢了，整个 datagram 作废。

:::from
Subnet mask 的 AND 判断和 192.0.2.0/24 的例子来自 [CS168 textbook 的 ARP 一节](https://textbook.cs168.io/end-to-end/arp.html)。Longest prefix match 的表、ISP 的 /20 和 route aggregation、DHCP 的四条消息、NAT 的地址和 port、4000 byte 的 fragmentation 例子，都是 Kurose & Ross 第 4 章的例子，那一章的 slides 没有读到，凭记忆重写，表里的区间、binary 和 offset 是用代码重新算过的。TTL 与 traceroute 的讲法凭自己的知识写。

## [route] Routing：link state 与 distance vector

:::skip

### Forwarding table 从哪来

上一站的 forwarding table 是现成的。Routing 要回答它怎么来：把 router 看作 vertex，link 看作带 cost 的 edge，每个 router 要知道到每个 destination 的 least-cost path 的第一跳。这正是 single-source shortest path，算法在 [CS2040 第 8 站](CS2040.html#sssp)已经讲过（Dijkstra 和 Bellman–Ford 的正确性证明都在那里）。网络里的新问题是：没有一台机器掌握整张图，每个 router 只认识自己的邻居，link 的 cost 还会变。两种做法对此的回答不同。

### Link state：先让每个 router 都拿到整张图

第一步，每个 router 向邻居发 hello，得知自己和谁相连、cost 是多少，然后把这些信息（link-state advertisement）flood 给全网：发给所有邻居，邻居再转给它们的所有邻居。

Flooding 必须去重。三个 router 连成三角形，R1 发出一条消息，R2、R3 各转给对方和 R1，R1 又收到两份并各自转发……CS168 textbook 数过，到第 5 步 R1 已经要发 6 份，份数按 exponential 增长，而真正的消息只有一条。办法是给每条 advertisement 一个编号，router 第一次见到某条消息时转发并记下，以后再见到同一条就不转发。

第二步，每个 router 在自己手里的整张图上，以自己为 source 跑 Dijkstra。

::fig[cs2105-dijkstra] Kurose & Ross 的 6 点图，从 u 出发。每个点旁边写的是当前的 D 和 predecessor；深色的点已经确定。

逐步走（初始 $D(v)=2$、$D(w)=5$、$D(x)=1$，$y$、$z$ 为 $\infty$）：

1. 未确定的点里 $D$ 最小的是 $x$（1）。经过 $x$ 更新邻居：$w$：$\min(5,\,1+3)=4$，改由 $x$ 来；$y$：$1+1=2$，由 $x$ 来；$v$：$\min(2,\,1+2)=2$，不变。
2. $v$ 和 $y$ 都是 2，任取一个，这里按课本取 $y$。$w$：$\min(4,\,2+1)=3$，改由 $y$ 来；$z$：$2+2=4$，由 $y$ 来。
3. 取 $v$（2）。$w$：$\min(3,\,2+3)=3$，不变。
4. 取 $w$（3）。$z$：$\min(4,\,3+5)=4$，不变。
5. 取 $z$（4），结束。

Forwarding table 只要第一跳：沿 predecessor 往回走到 u 的邻居。$z$ 的 predecessor 是 $y$，$y$ 的是 $x$，$x$ 的是 u，所以去 $z$ 的第一跳是 $x$。同理 $v\to v$，$w\to x$，$x\to x$，$y\to x$。

### Link state 的前提：大家看到的是同一张图

每个 router 只决定把 packet 交给下一跳，管不了下一跳怎么处理。如果两个 router 手里的图不一样，就可能 R3 认为去 A 要经过 R2，R2 认为要经过 R3，packet 在两者之间来回，直到 TTL 耗尽。所以 link state 要求所有 router 的图一致、都取 least-cost path、cost 为正、tie 的取法也一致。Link 状态刚变化时，消息还没 flood 到每个角落，这几条会暂时被破坏，短暂的 loop 就出现在这段时间里。

### Distance vector：只和邻居交换估计

Distance vector 不收集整张图。Router $x$ 只保存自己到每个 destination 的估计 $D_x(y)$，定期或者在估计变化时把整张向量告诉邻居，然后按 Bellman–Ford equation 更新：

$$D_x(y)=\min_{v\in\text{neighbors}(x)}\{\,c(x,v)+D_v(y)\,\}$$

意思是：经过邻居 $v$ 去 $y$ 的代价，是到 $v$ 的 link cost 加上 $v$ 自己报的距离，取最小的那个邻居作为 next hop。每个 router 都只做这一件事，没有人统一指挥，各自在收到消息时算，最终会收敛到真正的 least cost。这就是 distributed、asynchronous 的 Bellman–Ford。

例子（Kurose & Ross）：三个 router，$c(x,y)=4$，$c(y,z)=1$，$c(x,z)=50$。收敛后 $D_y(x)=4$（直连），$D_z(x)=\min(50,\,1+4)=5$，经过 $y$。

**好消息传得快。** $c(x,y)$ 从 4 降到 1。$y$ 发现后算 $D_y(x)=\min(1,\,1+5)=1$，告诉 $z$；$z$ 算 $D_z(x)=\min(50,\,1+1)=2$，告诉 $y$；$y$ 算 $\min(1,\,1+2)=1$，不变，停止。两次更新就收敛了。

### 坏消息传得慢：count-to-infinity

开头第三次事故：$c(x,y)$ 从 4 涨到 60。

$y$ 算 $D_y(x)=\min(60+0,\ 1+D_z(x))=\min(60,\,1+5)=6$。它用的 $D_z(x)=5$ 是 $z$ 之前报的，而这个 5 恰恰是“经过 $y$ 走 4”得来的，$y$ 不知道。于是 $y$ 改为经过 $z$ 去 $x$。$z$ 收到 6，算 $\min(50,\,1+6)=7$；$y$ 收到 7，算 8……

::fig[cs2105-dv] 左边是三个 router，右边是两个估计随更新次数的变化。动起来时左边的数字和右边的点同步。两条线每次各涨 2，一直涨到 $D_z(x)$ 碰到直连的 50。

每一轮两者各涨 2。直到 $y$ 报出 50，$z$ 算 $\min(50,\,1+50)=50$，改走直连；$y$ 再算 $\min(60,\,1+50)=51$，经过 $z$，收敛。一共 47 次更新。这段时间里，$y$ 把去 $x$ 的 packet 交给 $z$，$z$ 交回给 $y$，全是 loop。Link cost 若是变成 $\infty$（link 断了），这个过程永远不会停。

**Poisoned reverse。** 问题出在 $z$ 把一条经过 $y$ 的路报回给了 $y$。规则：如果 $z$ 去 $x$ 的 next hop 是 $y$，它就对 $y$ 谎称 $D_z(x)=\infty$。重走一遍：$c(x,y)$ 变成 60 时，$y$ 手里的 $D_z(x)=\infty$，算出 $\min(60,\,1+\infty)=60$，直连；告诉 $z$，$z$ 算 $\min(50,\,1+60)=50$，改走直连，并且现在不再经过 $y$，就把真实的 50 报给 $y$；$y$ 算 $\min(60,\,1+50)=51$，改经过 $z$。三次更新收敛。

:::wrong Poisoned reverse 解决了 count-to-infinity
它只挡住两个 router 之间的 loop。CS168 textbook 的例子：R1、R2、R3 两两相连，A 只挂在 R3 上，R1 和 R2 都经过 R3 去 A。R3–A 断了，R3 向 R1、R2 宣告 $\infty$。R2 收下了；但 R1 的 $\infty$ 还没到，R1 照旧对 R2 宣告“我经过 R3 去 A，cost 2”（R1 的 next hop 是 R3，不是 R2，所以 poisoned reverse 不要求它对 R2 撒谎）。R2 于是改为经过 R1，cost 3，再告诉 R3（R2 的 next hop 现在是 R1，同样不必对 R3 撒谎）；R3 改为经过 R2，cost 4，告诉 R1；R1 变成 5……三个 router 组成的 loop 照样一圈一圈地数上去。RIP 的做法是承认治不了，把 16 定义为 $\infty$：cost 数到 16 就当作不可达，loop 最多转十几圈就停下。代价是 RIP 只能用在直径不超过 15 跳的网络里。
:::

### 发现 bit 出错：parity 与 CRC

**Parity。** 在 $d$ 个 bit 后面加 1 个 bit，使 1 的总数为偶数。一位出错，1 的个数变奇数，被发现；两位同时出错，个数仍是偶数，发现不了。把 bit 排成矩阵，每行每列各加一个 parity（two-dimensional parity），一位出错时出错的那一行和那一列都不对，交点就是出错的位置，可以直接改正。

**CRC。** 把 bit 串看成 coefficient 只有 0 和 1 的 polynomial，加法是 XOR（没有进位）。双方事先约定一个 $r+1$ bit 的 generator $G$。Sender 在 data $D$ 后面附上 $r$ bit 的 $R$，使 $D\cdot2^r\oplus R$ 能被 $G$ 整除；receiver 用收到的整串除以 $G$，remainder 不是 0 就是出错了。

$R$ 就是 $D\cdot2^r$ 除以 $G$ 的 remainder。例子：$D=101110$，$G=1001$，$r=3$。在 $D$ 后面补 3 个 0 得 101110000，做不带借位的长除法：每一步找到当前最高的那个 1，从它开始的 4 位和 $G$ 做 XOR，其余位不动。

| 步骤 | 当前的串 | 最高的 1 起的 4 位 | XOR 1001 | 之后的串 |
|---|---|---|---|---|
| 1 | `101110000` | 第 1–4 位 `1011` | `0010` | `001010000` |
| 2 | `001010000` | 第 3–6 位 `1010` | `0011` | `000011000` |
| 3 | `000011000` | 第 5–8 位 `1100` | `0101` | `000001010` |
| 4 | `000001010` | 第 6–9 位 `1010` | `0011` | `000000011` |

剩下的串前 6 位全是 0，除不下去了，最后 3 位就是 remainder。

Remainder $R=011$，发出去的是 101110011。验算：101110011 除以 1001，按同样的步骤，remainder 是 0。

$r$ bit 的 CRC 能发现所有长度不超过 $r$ 的连续出错（burst error）。Ethernet 用 32 bit 的 CRC。

### 一条线，很多人：multiple access

在一根共享的线（或一个无线频道）上，两个 node 同时发，信号叠在一起，谁都收不到，这叫 collision。需要一个规则决定谁发。

固定分配（TDMA：每人一个时隙；FDMA：每人一个频段）没有 collision，但只有一个人有数据时，他也最多只能用 $1/N$ 的容量。Random access 的想法是：想发就发，撞了再说。

**Slotted ALOHA。** 时间切成 slot，一个 slot 发一个 frame。有数据的 node 在每个 slot 以概率 $p$ 发送；撞了就在之后的每个 slot 继续以概率 $p$ 重试。

它的 efficiency 是多少？设 $N$ 个 node 都有数据。一个 slot 成功，当且仅当恰好一个 node 发送：

$$P(\text{成功})=N\,p\,(1-p)^{N-1}$$

对 $p$ 求 derivative 并令它为 0：

$$N(1-p)^{N-1}-N(N-1)\,p\,(1-p)^{N-2}=0\ \Longrightarrow\ (1-p)=(N-1)\,p\ \Longrightarrow\ p^*=\frac1N$$

代回去：

$$P^*=N\cdot\frac1N\left(1-\frac1N\right)^{N-1}=\left(1-\frac1N\right)^{N-1}$$

$N=2$ 时是 0.5，$N=5$ 时 0.41，$N=10$ 时 0.387，$N=100$ 时 0.370。$N\to\infty$ 时 $(1-1/N)^{N-1}\to1/e\approx0.368$。也就是说 node 很多时，最好的情况下也有 63% 的 slot 是空的或撞了的。

不分 slot 的 pure ALOHA 更差：一个 frame 和它之前、之后开始发的 frame 都会撞，危险的时间窗是两个 frame 长，efficiency 最多 $1/(2e)\approx0.18$。

### CSMA/CD：先听再发，边发边听

ALOHA 的浪费在于发之前不看线上有没有人。CSMA（carrier sense multiple access）规定先听：线上有信号就等。仍然会撞，因为信号要走一段时间：B 听的时候，A 刚发出的信号还没传到 B。

CSMA/CD 再加一条：发的同时继续听，一旦发现 collision 立刻停，并发一小段 jam 信号让大家都知道撞了，不把整个 frame 浪费完。

::fig[cs2105-csma] A、B 在线的两端，信号从一端到另一端要 $\tau$。最坏情况：B 在 A 的信号就要到达时开始发，它的信号要再走 $\tau$ 才回到 A。

A 要发现自己的 frame 撞了，必须在 B 的信号回到 A 时还在发。最坏情况下这个时刻接近 $2\tau$。如果 A 在 $2\tau$ 之前就发完了，它会以为发送成功，collision 却实际发生了。所以 frame 的 transmission time 必须至少 $2\tau$：

$$\frac{L_\text{min}}{R}\ge2\tau$$

10 Mbps Ethernet 把这个下限定为 512 bit（64 byte），也就是 51.2 µs。这就是第 1 站那个 1 byte 的 frame 要补到 64 byte 的原因。反过来，给定 64 byte 的下限，rate 越高，$2\tau$ 越短，线就只能越短：CS144 的讲义给出 10 Mbps 时最大直径 2800 m，100 Mbps 时只有 205 m。

撞了以后等多久再试？等固定时间，两个 node 会再次同时重试。Binary exponential backoff：第 $m$ 次 collision 之后，从 $\{0,1,\dots,2^m-1\}$ 里随机取 $K$（$m$ 最多算到 10），等 $K\times512$ 个 bit time 再试。第 1 次撞后 $K\in\{0,1\}$，两个 node 有一半的机会错开；第 3 次撞后 $K\in\{0,\dots,7\}$，在 10 Mbps 上最多等 $7\times51.2=358.4$ µs。撞得越多，说明抢的人越多，随机的范围就自动放大。

### Ethernet、MAC 地址与 switch

Ethernet frame 的格式：8 byte preamble（用来同步时钟），6 byte destination MAC、6 byte source MAC，2 byte type（payload 是 IPv4 还是别的），46 到 1500 byte 的 payload，4 byte CRC。

MAC 地址 48 bit，写成 `f8:ff:c2:2b:36:16` 的样子，出厂时写在 NIC 里，全球唯一，但不按地理位置分配，所以不能像 IP prefix 那样合并。`ff:ff:ff:ff:ff:ff` 是 broadcast 地址，线上所有 NIC 都收。

现代的 Ethernet 用 switch 把 host 连成星形，每个 host 到 switch 是一条独占的、两个方向各自一根线的 link，collision 基本不再发生，CSMA/CD 也就很少用得上。Switch 怎样知道某个 MAC 在哪个 port？它不需要配置，自己学：

1. 每收到一个 frame，把（source MAC，进来的 port，时间）记进 switch table。
2. 查 destination MAC：表里有，就只从那个 port 发出；表里没有，就从除进来的 port 以外的所有 port 发出（flood）。
3. 表项过一段时间不更新就删掉，因为机器可能换了位置。

例如 A 第一次发给 B，switch 还不认识 B，flood 给所有人，同时记住 A 在 port 1；B 回复时，switch 记住 B 在 port 4，并且已经知道 A 在 port 1，只往 port 1 发。

### ARP：知道 IP 地址，要问 MAC 地址

Host 要发一个 IP datagram，交给 link layer 时必须写上这一跳的 destination MAC。它只知道 IP 地址。

第一步是第 5 站的判断：把 destination IP 和自己的 subnet mask 做 AND。

- **在同一个 subnet 里**：要的是对方本人的 MAC。
- **不在**：datagram 要先交给 default gateway（第一跳 router），要的是 router 那个 interface 的 MAC。

第二步，查 ARP table（IP → MAC 的 cache，每项有过期时间）；没有，就发 ARP request。Request 用 broadcast（destination MAC = `ff:ff:ff:ff:ff:ff`）发出，因为不知道对方的 MAC 正是要问的事；它写明“谁有 192.0.2.1？请告诉 f8:ff:c2:2b:36:16”。只有 IP 是 192.0.2.1 的那台回答，回答用 unicast 直接发给提问者，因为提问者的 MAC 已经写在 request 里了。两边都把结果存进 ARP table。

跨 subnet 的完整过程：host A（111.111.111.111）发给另一个 subnet 里的 host B（222.222.222.222），中间是 router R。

1. A 判断 B 不在自己的 subnet，用 ARP 问到 R 在 A 这一侧的 interface 的 MAC。
2. A 发出的 frame：source MAC = A，destination MAC = R 的左侧 interface；里面的 datagram：source IP = A，destination IP = B。
3. R 拆开 frame，查 forwarding table 得知 B 在右侧 interface 所连的 subnet 里，用 ARP 问到 B 的 MAC。
4. R 发出新的 frame：source MAC = R 的右侧 interface，destination MAC = B；里面的 datagram 原封不动（只有 TTL 减了 1，checksum 随之更新）。

这就是第 1 站动图里 router 换掉的那个 link header。

:::wrong 跨 subnet 发 packet 时，frame 的 destination MAC 写对方 host 的 MAC
A 和 B 不在同一个 subnet，A 发出的 frame 根本到不了 B 所在的线上，中间隔着 router。即使 A 知道 B 的 MAC，把它写进 frame，A 这一侧线上没有人认这个地址，router 的 NIC 也会因为不是发给自己的而丢掉它。IP 地址写的是终点，从头到尾不变；MAC 地址写的是这一跳，每过一个 router 换一次。
:::

## [sec] Network security 入门

:::skip
能用小数字走一遍 RSA，能说出 MAC、digital signature、certificate 各自挡住的是哪一种攻击，能按顺序写出 TLS handshake，就读完这门课了。

### 要防的是什么

前面七站假设网络里的每个人都守规矩。现在假设 attacker 控制着路上的某一段：他能读经过的每个 packet，能丢弃、修改、重放它们，也能伪造 packet 冒充别人。CS144 的讲义列了几种现成的做法：ARP spoofing（在 ARP 回答里把自己的 MAC 说成 gateway 的，第 7 站的 ARP 不做任何验证），DNS 回答被伪造（第 2 站的 local DNS 也不验证回答），在开放 Wi-Fi 上架一个假的 DHCP server（第 5 站）把 default gateway 和 DNS server 都指向自己。

要守住的有三样：

- **Confidentiality**：只有对方读得懂。
- **Integrity**：内容没被改过。
- **Authentication**：对方确实是他声称的那个人。

### Symmetric key：快，但钥匙怎么送过去

Alice 和 Bob 共有一把 key $K$，Alice 用 $K$ encrypt，Bob 用同一把 $K$ decrypt。现代的 block cipher（例如 AES）一次 encrypt 128 bit 的一块，速度快到可以跟上线速。

难处在于 $K$ 本身要先安全地到达对方。如果两人从没见过面，第一次通信时只有被监听的网络可用。人多了还有数量问题：100 个人两两之间各用一把，要 $100\times99/2=4950$ 把。

### Public key：用来 encrypt 的 key 可以公开

每个人有一对 key：public key $K^+$ 公开，private key $K^-$ 只有自己知道。用 $K^+$ encrypt 的东西只有 $K^-$ 能解开。任何人都可以用 Bob 公开的 $K_B^+$ 给他发 ciphertext，不需要事先共享秘密。

RSA 是这样构造的，用 Kurose & Ross 的小数字走一遍：

1. 取两个 prime $p=5$、$q=7$，$n=pq=35$，$z=(p-1)(q-1)=24$。
2. 取 $e=5$，它和 24 没有 common factor。
3. 取 $d$ 使 $ed\equiv1\pmod{z}$：$d=29$，因为 $5\times29=145=6\times24+1$。
4. Public key 是 $(n,e)=(35,5)$，private key 是 $(n,d)=(35,29)$。

Encrypt $m=12$：$c=m^e\bmod n=12^5\bmod35=248832\bmod35$。$35\times7109=248815$，余 17，所以 $c=17$。

Decrypt：$c^d\bmod n=17^{29}\bmod35=12$，回到了 $m$。

它成立的原因是 $ed=1+6z$，而 number theory 保证对任何 $m$ 都有 $m^{1+kz}\equiv m\pmod n$。安全性来自：从公开的 $n$ 求 $z$ 需要把 $n$ 分解成 $p\times q$，$n$ 有几百位时没有已知的快速办法。

Public key 的运算比 symmetric 慢得多（CS144 的讲义测得 decrypt 一次要几 ms），不适合 encrypt 大量数据。实际的做法是 hybrid：用 public key encrypt 一把随机生成的 session key 送给对方，之后的数据全用 symmetric key encrypt。

### Integrity：只 encrypt 挡不住篡改

:::wrong encrypt 过的消息，attacker 看不懂，也就改不了
Stream cipher 的 encrypt 是把 plaintext 和一串只有双方知道的 keystream 按位 XOR。Attacker 不需要看懂，只要知道某个位置放的是什么：转账金额的第一个字符是 `1`（0x31），他把 ciphertext 里对应的 byte 和 0x08 做 XOR。Bob decrypt 时那一位的 keystream 被抵消，得到 0x31 ⊕ 0x08 = 0x39，也就是 `9`。100 元变成 900 元，Bob decrypt 顺利，毫无察觉。CS144 的讲义的结论是：只 encrypt、不做 integrity 检查的系统，多半是设计错了。
:::

**Hash** 把任意长的消息压成固定长度的 digest $H(m)$（例如 SHA-256 的 256 bit），要求找不到两个不同的消息有相同的 digest。只附 $H(m)$ 挡不住篡改：attacker 改了 $m$，自己重算一个 $H(m')$ 附上即可。

**MAC（message authentication code）** 让 digest 依赖一个双方共享的秘密 $s$：发送 $(m,\ \text{MAC}(s,m))$。Attacker 没有 $s$，算不出 $m'$ 的正确 MAC。Receiver 用自己的 $s$ 重算一遍对比。（这个 MAC 和第 7 站的 MAC 地址只是缩写相同。）

**Digital signature** 是不需要共享秘密的版本：Bob 用自己的 private key 对 $H(m)$ 做 signature，任何人用 Bob 的 public key 验证。只有持有 $K_B^-$ 的人做得出这个 signature，所以 signature 同时证明了“没被改过”和“是 Bob 发的”，而且 Bob 事后无法否认。

**Replay。** MAC 和 signature 都挡不住原封不动地重放一条旧消息，比如把“转账 100 元”再发一遍。办法是在消息里加入只用一次的东西：sequence number，或者对方临时给出的随机数 nonce。

### Public key 也会被冒名顶替

前面说“用 Bob 公开的 $K_B^+$”。Alice 怎么知道她拿到的真是 Bob 的？

::fig[cs2105-mitm] 上一行：Trudy 在中间把 Bob 的 public key 换成自己的。下一行：Bob 发的是 CA signed certificate，替换就会被发现。

没有任何保护时，Trudy 截下 Bob 发出的 $K_B^+$，换成自己的 $K_T^+$ 交给 Alice。Alice 用 $K_T^+$ encrypt，Trudy 解开、读完，再用 $K_B^+$ encrypt 转给 Bob。两边都以为在和对方直接通信，这叫 man-in-the-middle。encrypt 本身毫无破绽，漏洞在于 Alice 无法确认 key 的主人。

Certificate 的办法是找一个双方都信任的第三方 certificate authority（CA）作证。Bob 事先向 CA 证明自己的身份，CA 对（Bob 的名字，$K_B^+$）做 signature，这一组东西就是 certificate。浏览器出厂时内置了 CA 的 public key。Alice 收到 certificate 后用 CA 的 public key 验证 signature：signature 是对（Bob，$K_B^+$）做的，Trudy 把其中的 key 换成 $K_T^+$，signature 就对不上；她要重新签，就得有 CA 的 private key。

### TLS：把这些零件装在一起

HTTPS 是跑在 TLS 上的 HTTP，port 443。TLS 在 TCP 的 handshake 之后再做一次自己的 handshake：

1. **Hello**：client 发出它支持的 encrypt 方案和一个随机数（nonce）；server 选定方案，也回一个随机数。
2. **Certificate**：server 发来 certificate，client 用内置的 CA public key 验证，得到可信的 server public key。
3. **Shared secret**：client 生成一个随机的 secret，用 server 的 public key encrypt 后发出。只有 server 能解开。
4. **Key derivation**：双方各自用这个 secret 和两个 nonce 算出几把 symmetric key（encrypt 用的、MAC 用的，两个方向各一套）。这些 key 从不在网络上传。
5. **确认**：双方各发一条消息，内容是对此前全部 handshake 消息的 MAC。如果 attacker 在 hello 里篡改过方案列表（例如删掉强的 encrypt 方案，逼双方用弱的），两边算出的 MAC 对不上，handshake 失败。

之后的每条记录都用 symmetric key encrypt 并附 MAC，记录里还带 sequence number 防重放和调换顺序。两个 nonce 保证每次 handshake 得到的 key 都不同：attacker 录下昨天整段通信、今天原样重放，server 这次出的 nonce 不一样，算出的 key 也不一样，重放的记录通不过 MAC。
