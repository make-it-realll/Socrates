先看三次失败。每一次，model 本身都没有错，错在它和身体、时间、旁边的人接不上。

**第一次。** 对 large language model 说“I spilled my drink, can you help?”。SayCan 论文的 Figure 1 里，GPT-3 回答“You could try using a vacuum cleaner”，FLAN 回答“I'm sorry, I didn't mean to spill it”。前一句放在家里是合理的建议，但面前这台 robot 没有 vacuum cleaner 这个 skill；后一句根本没有在帮忙。Language model 知道“该做什么”，不知道“这台 robot 此刻能做什么”。

**第二次。** 一个 vision-language-action model（VLA）控制一台 50 Hz 的 robot arm，每次 inference 要 100 ms，output 一个 action chunk，执行其中 25 步（0.5 s）。这组数接近 π0 的真实设定：50 Hz 的 robot 每执行 25 个 action 重新 inference 一次，π0 论文在 RTX 4090 上量到一次 inference 是 73 ms，model 放在另一台机器上、走网络时是 86 ms。等 chunk 执行完再算下一个，robot 每走 0.5 s 就停 0.1 s；提前开始算、算完立刻换上，新 chunk 可能选了另一种走法，action 在切换处跳一下。

::fig[ee4706-pause] 上一行：每个 chunk 执行完，robot 停 100 ms 等 model。下一行：提前 5 步开始算，robot 不停，但虚线处要把新 chunk 接到旧 chunk 上。

**第三次。** 桌上并排放着两个杯子，robot 要拿右边那个，它走了最短、最顺的直线。旁边的人看着 robot 的手朝两个杯子中间伸过去，直到很晚才看出它要哪个，伸手去拿右边的杯子，两只手撞在一起。

三件事说明 embodied AI 和只处理 token 的 AI 不同的地方。HKU DATA8010 第一讲把它归成三条：基本单位是 sensing 和 acting 交替进行的 closed loop，不是一次 forward pass；它受 physics 的约束，要 real time，错误会弄坏东西；sensor 有 noise，世界只能部分看到，在变，而且里面有独立行动的别的 agent。

## [arch] Cognitive architecture：从 sense-plan-act 到分层

:::skip
能用 $v\,t_{\text{lat}}+v^2/2a$ 算出 stopping distance，能把一个系统拆成 controller、sequencer、deliberator 三层并说出每层的 rate 和接口，能说出 π0.5 的两层分别对应哪一层，就可以去第 2 站。
:::

### 一个 loop 不够快

最直接的 architecture 是 sense-plan-act：读 sensor，建一个 world model，在上面 plan，执行 plan，然后再从头来一遍。三步串在一个 loop 里，loop 转一圈的时间就是 robot 对世界变化的 latency。

问题出在 plan 很慢。设 robot 以 $v=0.5$ m/s 前进，刹车的 deceleration 是 $a=2$ m/s²，一个 person 在前方 0.4 m 处突然出现。从 person 出现到 robot 停下，robot 走过的距离分两段：latency 期间照原速走 $v\,t_{\text{lat}}$，刹车期间走 $v^2/2a$（从 $v^2=2a\,x$ 解出 $x$）：

$$x_{\text{stop}}=v\,t_{\text{lat}}+\frac{v^2}{2a}$$

刹车那一段是 $0.25/4=0.0625$ m，和 architecture 无关。Latency 那一段：

| Loop 转一圈要多久 | Latency 期间走过 | Stopping distance | 0.4 m 外的 person |
|---|---|---|---|
| 1 s（每圈都重新 plan）| 0.5 m | 0.5625 m | 撞上 |
| 0.25 s | 0.125 m | 0.1875 m | 停住 |
| 30 ms（一个只做 obstacle 检测的 loop）| 0.015 m | 0.0775 m | 停住，还剩 0.32 m |

1 s 的那台在 $t=0.4/0.5=0.8$ s 时撞上，那时它还在 latency 里，根本没开始刹车。

::fig[ee4706-react] 同样的速度、同样的 brake，只差 loop 的 latency。看上面那台在开始刹车之前就碰到 person。

所以“想清楚再动”和“立刻反应”不能放在同一个 loop 里。Plan 需要的时间由问题的难度决定，反应需要的时间由 physics 决定，两者差了一到两个 order。

### Subsumption：按 behavior 竖着切

Brooks 1986 年的论文先批评当时通行的分解：把系统横着切成 sensing、mapping、planning、task execution、motor control 几个 functional module，信息沿着这条链往下流。这样切，任何一块改了，要么保持它和邻居的接口不变，要么把改动传给邻居；而且整条链写完之前，robot 什么也做不了。他改成按 task-achieving behavior 竖着切：每一层（论文叫 level of competence）自己就是一条从 sensor 到 actuator 的完整通路，高层包含低层的全部能力。论文列了 0 到 7 共八层，实现的是前三层：

- **Level 0：不碰到东西**，不管东西是静止的还是在动。`sonar` 把一圈 12 个 sonar 的读数变成以 robot 为中心的 obstacle map；`collide` 发现正前方有东西，就向 motor 发 halt；`feelforce` 把每个 obstacle 当作一个 repulsive force 加起来，`runaway` 在合力足够大时让 robot 顺着合力的方向躲开。
- **Level 1：漫无目的地走而不撞东西。** `wander` 大约每 10 s 产生一个随机的 heading，`avoid` 把这个 heading 和 repulsive force 合成一个略微绕开 obstacle 的 heading。
- **Level 2：explore**，朝远处看起来走得到的地方走。`pathplan` 把目标 heading 交给 `avoid`，同时压掉 `wander` 的随机 heading。

层与层之间只有两种接法。**Suppression** 接在一个 module 的 input 上：高层的消息在一段时间里替换掉原来的 input。**Inhibition** 接在 output 上：在一段时间里把这条线上的消息全部丢掉。Level 1 的 `avoid` 就是通过 suppress `runaway` 发给 motor 的 command 来接管的。高层不调用低层，也不改低层内部，所以加上高层之后，调试好的低层照常运行；高层来不及给出结果时，低层仍然给出合理的、只是能力低一些的行为。

::fig[ee4706-subsume] Brooks 1986 年 robot 的前三层。实线是一层自己的通路，圆圈 S 是 suppression：高层的线接进来，就替换掉低层原来送进这个点的消息。看 level 0 在没有上面两层时也是一条完整的、从 sonar 到 motor 的路。

拿上面的表检验：level 0 只做 range 比较和力的叠加，不需要 plan，loop 可以做得很短，所以 0.4 m 外的 person 能被躲开。（Brooks 1986 年的 robot 其实每 1 s 才读一次 sonar，大部分计算在 off-board 的 Lisp machine 上，通过 12 kbit/s 的无线链路传回来，那是当时 hardware 的限制，不是 architecture 的。）它解决了反应的问题。

它的麻烦，Gat 1998 年的综述归成两条。第一，层与层靠 suppress 和 inhibit 对方内部的通路来交互，Hartley 的批评是它 not sufficiently modular：设计高层的人必须知道低层里面怎么接线，两层不能各自独立设计。第二，后来几台很可靠的分层 robot（Tooth、Rocky III）改成让高层只给低层提供 input 或建议，不再压制低层，可靠性上去了，却是 not taskable：换一个任务，就要重写 control program。“把桌上的空罐扔掉，再拿一块 sponge 过来”明天换成“把 cup 放进 sink”，每次都要改 wiring，这对一个按 instruction 工作的 robot 不可接受。

### 三层 architecture

把两边的长处合起来，就是 robot 系统里最常见的三层分法。Gat 记录了 1991 年前后三组人各自独立地走到这里：Connell 的 SSS、Bonasso 等人的 3T、Gat 自己的 ATLANTIS。他认为三层的区分标准是**怎样使用 internal state**：

- **Controller**：一个或多个 feedback loop，把 sensor 和 actuator 紧紧连在一起，执行 primitive behavior，也叫 skill（沿墙走、避障、穿过门）。Gat 的约束是：每次 iteration 的时间和空间有常数上界；尽量不存 internal state（filter 例外），要存也只能是短暂的、过一段时间就失效。避障和 emergency stop 放在这里。
- **Sequencer**：选择 controller 此刻用哪个 skill、给它什么 parameter。只按一串固定的 skill 往下走不可靠，sequencer 要能按当前情况做 conditional 的响应（skill 失败了怎么办、什么时候切换）。它存的是**关于过去的 memory**：做到第几步、刚才哪一步失败了。它不做相对于环境变化速度来说很长的计算，一般不做 search。
- **Deliberator**：做费时的计算，例如 plan、指数级的 search。它存的是**对未来的 prediction**。Deliberator 的一次调用从开始到返回，下面可能已经切换了好几次 behavior。

Deliberator 和 sequencer 有两种接法：deliberator 产生一个 plan，交给 sequencer 当作建议去执行（3T）；或者 sequencer 在需要时向 deliberator 问一个具体的问题（ATLANTIS）。两种可以并存。

Gat 还对 controller 提了一条要求，第 4 站会用到：算法应当 **cognizant failure**。真实 robot 上不可能设计出永远不失败的算法，但可以设计出永远能发现自己失败了的算法，这样 sequencer 和 deliberator 才有机会补救。

::fig[ee4706-layers] 左边是三层 architecture，往下传目标、往上报结果，每层标出它存哪一种 state；右边是 π0.5 的对应。看最底层在两边都是一个与 large model 无关的 fixed-rate controller。

层与层之间传什么，是这种设计里最要紧的选择。Deliberator 交给 sequencer 的可以是一列 skill 的名字（第 4 站的 SayCan 就这么做，robot 一共只有几百个 skill），也可以是一句任意的话。前者每一步都能检查“这个 skill 存在吗”，但表达不了 skill list 之外的事；后者什么都能说，但下层必须真的理解任意一句话。

### 现在的 robot foundation model 怎样分层

π0.5 把上两层合进了同一个 VLA。它把 policy 写成两个 factor 的乘积：

$$\pi(a,\hat\ell\mid o,\ell)=\pi(a\mid o,\hat\ell)\;\pi(\hat\ell\mid o,\ell)$$

$\ell$ 是任务（“put away the dishes”），$o$ 是 observation，$\hat\ell$ 是 model 自己 output 的一句文字 subtask（“pick up the plate”），$a$ 是一个 action chunk。同一个 model 先像 VLM 一样 output 一句话（论文说 high-level 的 inference 频率比 low-level 低，没有给具体数字）；再由一个约 3 亿 parameter、flow matching 的 action expert 读这句话，经过 10 步 denoising output 一个 50 步的 action chunk。Chunk 里是 arm、gripper、torso 的 target pose 和 base 的 velocity（按平台共 18 到 19 个 DoF），以 50 Hz 交给简单的 PD controller 跟踪，论文写明中间没有另外的 trajectory planning，也没有 collision detection。

对照三层：$\pi(\hat\ell\mid o,\ell)$ 是 deliberator 加 sequencer，接口是一句自然语言；$\pi(a\mid o,\hat\ell)$ 是 skill；PD controller 是 controller。它选了“什么都能说”的那种接口，代价是 low-level 要在大量带 subtask 标注的 data 上学会听懂这些话（第 4 站会看到这些 data 从哪来）。

拿第一小节的 stopping distance 再检验一次：一个 chunk 要 100 ms 以上才算得出，emergency stop 不能等它。所以即使上面整个换成了 VLA，最底层仍然需要一个独立的、固定 rate 的 safety loop（velocity 和 force limit、collision check）。π0.5 的论文只说 PD controller 外面没有 collision detection，没有讨论 safety loop；这里的说法是按 Gat 对 controller 的要求推出来的，不是论文的内容。

:::wrong 让 large model 直接 output 每一步的 motor command，architecture 最简单也最通用
看速率。OpenVLA 论文说它在一块 RTX 4090 上约 6 Hz，即每 0.167 s 一个 decision（[RB4301 第 8 站](../courses/RB4301.html#vla)也用了这个数）。按上面的 formula，0.5 m/s 下 stopping distance 是 $0.5\times0.167+0.0625=0.146$ m，是 30 ms reflex loop 的近 2 倍；而且这是 GPU 一切正常的情况，inference 偶尔卡一下，latency 那一项就跟着涨。Model 越大越通用，越慢；“通用”和“反应快”在同一个 loop 里互相拖累，分层就是为了把它们拆开。
:::

:::from
Functional decomposition 的批评、八个 level of competence、level 0 到 2 的 module（sonar、collide、feelforce、runaway、wander、avoid、pathplan）、suppression 接 input 和 inhibition 接 output、低层在高层失效时照常工作、1 s 读一次 sonar 和 off-board 的 Lisp machine 来自 [Brooks 1986](https://apps.dtic.mil/sti/pdfs/ADA160833.pdf)（DTIC 的扫描版，Figure 1 的标签认不出来，按正文第 2.1 节）。Hartley 的 not sufficiently modular、Tooth 与 Rocky III 的 not taskable、1991 年前后的 SSS、3T、ATLANTIS、按 internal state 区分三层、controller 的常数时间与 cognizant failure、sequencer 的 conditional sequencing、deliberator 与 sequencer 的两种接法来自 [Gat 1998](https://u.cs.biu.ac.il/~galk/teach/current/intsys/readings/on-three-layer-arch-tla-1998.pdf)（读了全文）。图里 module 之间的连线按 Brooks 正文的文字描述画，做了简化。π0.5 的 factorization、文字 subtask、high-level 频率较低、约 3 亿 parameter 的 action expert、10 步 denoising、50 步的 chunk、50 Hz 的 target pose 加 PD controller、没有 collision detection 来自 [Black et al. 2025（π0.5）](https://arxiv.org/html/2504.16054v1)（这次读了全文的文字部分，图里的数值读不到）。OpenVLA 的 6 Hz 来自 [OpenVLA 论文](https://arxiv.org/html/2406.09246v3)。三个特征的概括来自 [HKU DATA8010 Lecture 1](https://embodied-ai-hku.github.io/DATA8010/slides/Lecture1.pdf)。Stopping distance 的例子和数表是为这一页算的；safety loop 的说法是我的推论。

## [percep] Multimodal perception：contrastive alignment 与 token

:::skip
能对一个 3×3 的 similarity matrix 算出 CLIP 的 loss，能解释 logit scale 的作用，能说出 image-level embedding 缺了什么、一张 224×224 的 image 变成多少个 patch token，就可以去第 3 站。
:::

### Closed-set 的 detector 找不到“the yellow sponge”

一个在 COCO 上 train 的 object detector，classification head 有 80 个 output，每个对应一个固定的 category。厨房里的 cup、bowl、bottle、sink、microwave 都在其中，“sponge”不在，所以不管 image 里的 sponge 多清楚，它都没有办法说出来。要换成能识别 sponge 的 detector，就要重新标 data、重新 train。

Robot 收到的 instruction 是任意的文字。需要的是一个 image 和 text 能直接比较的空间：image encoder 把 image 变成 vector，text encoder 把任意一句话变成同一个空间里的 vector，两者 cosine similarity 高就说明配得上。这样，“sponge”只是另一句 text，不需要新的 output。

### Contrastive learning：让配对的 image 和 text 靠近

:::back
Contrastive learning 本身（InfoNCE、为什么需要 negative）在 [STANFORD-CS231N 第 7 站](../courses/STANFORD-CS231N.html#ssl)讲得更细，这里只讲 CLIP 和 robot 用得上的部分。
:::

CLIP 从网上收集了 4 亿对 (image, caption)。一个 batch 里有 $N$ 对，image embedding $I_1,\dots,I_N$ 和 text embedding $T_1,\dots,T_N$ 都 normalize 成 unit vector，于是 $N\times N$ 个 cosine similarity $S_{ij}=I_i\cdot T_j$ 里，diagonal 上的 $N$ 个是真的配对，其余 $N^2-N$ 个不是。Training 让 diagonal 变大、其余变小。

具体的 loss：把每一 row 当作一个 $N$ 选 1 的 classification（image $i$ 的正确 caption 是哪个），每一 column 也当作一个（caption $j$ 的正确 image 是哪个），两边各取 cross-entropy 再平均：

$$\mathcal L=\frac12\left[\frac1N\sum_i-\log\frac{e^{sS_{ii}}}{\sum_je^{sS_{ij}}}+\frac1N\sum_j-\log\frac{e^{sS_{jj}}}{\sum_ie^{sS_{ij}}}\right]$$

$s$ 是 logit scale，即 temperature 的倒数。CLIP 把它当作 parameter 来学，初值相当于 temperature 0.07（$s\approx14.3$），并且限制 $s\le100$。

拿一个 3×3 的例子算一遍。

::fig[ee4706-clip] 三张 image、三条 caption 的 cosine similarity。看 diagonal 和同一 row 的其他格只差 0.04 到 0.09，乘上 100 之后，softmax 几乎全落在 diagonal 上。

先用初值 $s=14.3$。第一 row 的 logit 是 $14.3\times(0.31,0.24,0.22)=(4.43,3.43,3.14)$，softmax 是

$$\frac{e^{4.43}}{e^{4.43}+e^{3.43}+e^{3.14}}=0.608$$

所以这一 row 的 loss 是 $-\ln0.608=0.497$。三个 row 分别是 0.497、0.610、0.497，三个 column 分别是 0.423、0.592、0.592，总的 $\mathcal L=\tfrac12(0.535+0.536)=0.536$。

换成 $s=100$，同一 row 的 logit 是 $(31,24,22)$，softmax 是 0.999，loss 降到 0.001；整个 $\mathcal L=0.0058$。Cosine 一个都没变，只是 scale 变了。$s$ 决定了 cosine 上多大的差距算“确定”：$s=100$ 时 0.07 的差距就是 $e^7\approx1100$ 倍的 odds。

为什么用这个 objective，而不是让 model 照着 image 逐字生成 caption？同一张 image 可以有无数种说法，逐字预测要把这些说法的细节都学会。CLIP 论文的对比：逐字预测 caption 的 transformer 学会 ImageNet category 的速度比只预测 bag of words 慢约 3 倍，而把 bag of words 换成 contrastive objective，zero-shot 的 efficiency 又提高约 4 倍。Contrastive 只要求“在这一批里认出谁和谁是一对”，比生成每个字容易得多。

:::edge Negative 只来自同一个 batch
上面的 3×3 里，每张 image 只要从 3 条 caption 里认出对的那条，所以很容易。CLIP 的 batch size 是 32768，每张 image 要从 32768 条里认出一条，相近的 caption（“a white mug”和“a white cup”）更可能同时出现在 batch 里，才逼得 model 分清细节。Batch 小，contrastive learning 学到的区分就粗。
:::

### Zero-shot：classification 变成和一组 text 比

Train 完之后，classification 不需要再 train。把每个 category 写成一句 text，比如“A photo of a {label}.”，送进 text encoder，image 和每句 text 算 cosine，乘 $s$ 做 softmax，就是 classifier。这正是上面每一 row 的计算。

Prompt 的写法有影响：用“A photo of a {label}.”代替单独一个词，ImageNet accuracy 提高 1.3%；把 80 种 prompt 的 text embedding 平均起来再用，又提高约 3.5%。最好的 CLIP 在 ImageNet 上 zero-shot 达到 76.2%，和原版 ResNet-50 持平，而它一张 ImageNet 的 training image 都没看过。

对 robot 来说，这意味着：拿 camera 里的若干个 crop 和“a yellow sponge”比，最高的那个就是要找的东西，category list 可以随 instruction 临时写。

:::wrong Cosine similarity 只有 0.31，说明 image 和 text 不太匹配
CLIPScore 论文的作者报告，他们从没见过 image 和 caption 之间负的 cosine，数值大致落在 0 到 0.4 之间（所以 CLIPScore 把 cosine 乘以 2.5，拉到 [0, 1]）。绝对值本身没有意义，有意义的是同一张 image 对不同 text 的相对大小。上面第一 row 的 0.31 对 0.24，乘上 $s=100$ 后 softmax 是 0.999。反过来，如果拿“0.25 以上才算匹配”这种固定阈值去判断，会同时把第一 row 的 0.24 和第三 row 的 0.23 当成匹配。要判断“是不是”，必须给一组候选（第 3 站的 VLMaps 为此专门加了一个“other”）。
:::

### CLIP 给不了什么：位置、距离、数量

CLIP 论文自己列出的弱点里，对 robot 最要紧的三条是：数不清物体的个数；判断“离最近的车有多远”接近随机猜；fine-grained 的类别（车的型号、花的品种）分不好。原因在结构上：一张 image 只变成一个 vector，“sponge 在左下角、离 gripper 12 cm”这样的信息被压掉了。

Robot 需要知道东西在哪里，所以要保留空间结构的 feature。两种做法：

- **Dense feature。** 给每个 pixel 一个和 text 对齐的 vector（LSeg 就是这样，第 3 站用它建 map），某个 pixel 和“sponge”的 cosine 高，那个位置就是 sponge。
- **Patch token。** Vision Transformer 把 image 切成 patch，每个 patch 一个 token，经一个 linear layer 投影到 language model 的 token 维度，和文字 token 一起处理。PaliGemma（π0 和 π0.5 的 backbone，SigLIP-So400m 的 image encoder 加 Gemma-2B）把 image resize 成 224×224，每张 image 固定变成 256 个 token：14×14 pixel 一个 patch，每边 $224/14=16$ 个，$16\times16=256$。分辨率换成 448 和 896，token 数是 1024 和 4096，按边长的平方涨。

Patch token 是 VLA 的标准做法，它直接决定计算量：π0 的 robot 有 2 到 3 个 camera，三个 camera 就是 $3\times256=768$ 个 image token，加上 instruction 和 proprioception 的 token，每次 inference 都要先把这些全部过一遍 model（第 7 站的 prefill）。Proprioception（joint angle、gripper 开合）是低维、精确的数，π0 用一个 linear projection 把 robot state 投影成和 language token 同一个空间里的一个 token，和 image token 拼在一起。也有 VLA 完全不用它：OpenVLA 只看一张 224×224 的 image，论文把加入 proprioception 和多张 image 列为以后的工作。

:::back
VLA 怎样把这些 token 接到 action 上，见 [RB4301 第 8 站](../courses/RB4301.html#vla)；那里还有一个结论：pretrained 的 vision representation 不一定比从头学的好。
:::

Contrastive objective、32768 的 batch、4 亿对 data、temperature 的初值和上限、3 倍和 4 倍的 efficiency 对比、prompt 的 1.3% 和 3.5%、76.2%，以及 counting、距离、fine-grained 这些 limitation，来自 [Radford et al. 2021（CLIP）](https://ar5iv.labs.arxiv.org/html/2103.00020)（这次读了正文到 Section 6 Limitations 的全部，以及 Section 7 和附录的一部分；Figure 3 的 pseudocode 在图里，没有读到，loss 的写法按正文“symmetric cross entropy”的描述）。COCO 的 80 个 category 对照了 [Ultralytics 的 COCO 文档](https://docs.ultralytics.com/datasets/detect/coco)。Cosine 的范围来自 [Hessel et al. 2021（CLIPScore）](https://arxiv.org/pdf/2104.08718) 的脚注。224 对应 256 个 token、448 和 896 的 token 数、linear projection 来自 [PaliGemma 论文](https://arxiv.org/html/2407.07726v2)；14 pixel 的 patch 边长是从 224 和 256 算出来的，那段原文没有直接写。π0 的 camera 数和 state 的 linear projection 来自 [π0 论文](https://arxiv.org/html/2410.24164v3)，OpenVLA 不用 proprioception 来自 [OpenVLA 论文](https://arxiv.org/html/2406.09246v3)。3×3 的数表和 loss 是为这一页算的。

## [nav] Navigation and mapping：occupancy grid 与 semantic map

:::skip
能从 Bayes rule 推出 log-odds 的 update，能算出 clamping 让 cell 清空快了多少，能说出 VLMaps 的每个 cell 里存了什么、“in between the sofa and the TV”怎样变成一个坐标，就可以去第 4 站。
:::

### Map 要回答两个问题

Robot 要走到某处，map 得先回答“哪里能走”，plan 一条不撞东西的路线；instruction 是“去 sofa 旁边”，map 还得回答“sofa 在哪”。第一个问题要的是 geometry，第二个要的是 semantics。这一站先建 geometry 的 map，再往每个格子里加 semantics。

整站假设 robot 每一刻的 pose 已知（由 localization 或 SLAM 给出）。这是 mapping 的标准分工：pose 已知时 mapping 是一个干净的 estimation 问题。

### Occupancy grid：每个 cell 一个 binary Bayes filter

把地面切成格子（occupancy grid 是 Moravec 和 Elfes 1985 年提出的），每个 cell $m$ 只有两种 state：被占（occupied）或空（free），要 estimate 的是 $p(m\mid z_{1:t})$，$z_{1:t}$ 是到现在为止的所有 measurement。整个 map 的可能 state 多得算不了：一张 100×100 的 binary grid 有 $2^{10000}$ 种。两个假设让问题变得可算：各个 cell 互相独立，整张 map 的 posterior 是各个 cell 的 posterior 的乘积，可以一个一个更新；环境是 static 的，cell 的 state 不随时间变，所以 filter 里没有 predict 这一步，只有 update。

对一个 cell 用 Bayes rule，并用“给定 $m$ 时新的 $z_t$ 和旧的 measurement 独立”：

$$p(m\mid z_{1:t})=\frac{p(z_t\mid m)\,p(m\mid z_{1:t-1})}{p(z_t\mid z_{1:t-1})}$$

对 $\neg m$ 写同样的式子，两式相除，denominator 消掉：

$$\frac{p(m\mid z_{1:t})}{p(\neg m\mid z_{1:t})}=\frac{p(z_t\mid m)}{p(z_t\mid\neg m)}\cdot\frac{p(m\mid z_{1:t-1})}{p(\neg m\mid z_{1:t-1})}$$

$p(z_t\mid m)$ 是 forward sensor model（cell 被占时看到这个 scan 的 probability），很难写。用 Bayes rule 把它翻成 inverse sensor model $p(m\mid z_t)$（看到这个 scan 时 cell 被占的 probability），$p(z_t\mid m)=p(m\mid z_t)\,p(z_t)/p(m)$，对 $\neg m$ 同理，$p(z_t)$ 又消掉：

$$\frac{p(z_t\mid m)}{p(z_t\mid\neg m)}=\frac{p(m\mid z_t)}{p(\neg m\mid z_t)}\cdot\frac{p(\neg m)}{p(m)}$$

三项都是 odds 的形式。取 log，记 $l(p)=\log\frac{p}{1-p}$（log-odds），乘法变成加法：

$$l_t=l_{t-1}+l\big(p(m\mid z_t)\big)-l_0$$

$l_0$ 是 prior $p(m)$ 的 log-odds。每来一个 scan，每个 cell 只做一次加法。Log-odds 的另一个好处是数值上：probability 连乘会贴近 0 或 1、丢失精度，log-odds 是在一条无界的 line 上加减。

Inverse sensor model 取 OctoMap 用的那种：假设 beam 的终点是 obstacle 的表面，从 sensor 到终点之间没有 obstacle。LiDAR beam 打到的那个 cell，$p(m\mid z)=0.7$；beam 穿过、没打到的 cell，$p(m\mid z)=0.4$；beam 终点后面的 cell 看不到，不更新。Prior $p(m)=0.5$，所以 $l_0=0$。0.7 和 0.4 就是 OctoMap 论文给的值（论文写成 log-odds 0.85 和 −0.4），说是对 laser 数据用实验定的。

$$l(0.7)=\ln\frac{0.7}{0.3}=0.847,\qquad l(0.4)=\ln\frac{0.4}{0.6}=-0.405$$

一个 cell 连续 3 次被打到：$l=3\times0.847=2.54$，换回 probability 是 $1/(1+e^{-2.54})=0.927$。

::fig[ee4706-grid] 一条 beam 上的 7 个 cell。看 cell 5：前 10 个 scan 里它被 person 挡住，越来越深；person 走开后，beam 穿过它打到 wall，它要多少个 scan 才变回浅色，上下两行差别很大。

### 环境会变：clamping

Person 在 cell 5 站了 10 个 scan，$l=10\times0.847=8.47$，$p=0.9998$。然后 person 走开，每个 scan 给 cell 5 加 $-0.405$。要回到 $p<0.5$，也就是 $l<0$，需要

$$\left\lceil\frac{8.47}{0.405}\right\rceil=\lceil20.9\rceil=21$$

个 scan。LiDAR 是 10 Hz 的话，这块空地要 2.1 s 才在 map 上重新变成 free，planner 在这段时间里会绕开一个已经不存在的 obstacle。

站得越久，清空得越慢，这正是 static 假设的后果：model 认为 cell 不会变，证据只会越积越多。UW CSE 478 的 slides 用一串 snapshot 展示了同一件事：一个走动的 person 在 map 上留下一道拖影。

实际的系统给 log-odds 设上下限，这叫 clamping（CSE 571 的 slides 把它记在 Yguel 等人 2007 年名下，OctoMap 沿用）：

$$l_t=\max\Big(\min\big(l_{t-1}+l(p(m\mid z_t))-l_0,\ l_{\max}\big),\ l_{\min}\Big)$$

OctoMap 取 $l_{\min}=-2$、$l_{\max}=3.5$，对应 probability 0.12 和 0.97，论文说这是为“大体 static、偶尔有变化”的环境用实验定的。代进上面的例子：前 5 个 hit 之后 $l=5\times0.847=4.24$ 被截成 3.5（$p=0.97$），之后再多的 hit 也不加。清空所需的 scan 数变成 $\lceil3.5/0.405\rceil=\lceil8.6\rceil=9$，0.9 s。OctoMap 论文给 clamping 的理由正是这个：map 的 confidence 有界，改变一个 cell 的 state 所需的 update 次数也就有界，map 能较快地跟上环境的变化。它还有一个好处：到了上下限的 cell 是“stable”的，一片 state 相同的 stable cell 可以在 octree 里合并成一个 node，map 小很多。代价是 static 的 wall 在 map 上最多只有 0.97 的把握，一两个错误的 miss 就能让它往下掉一点；上限取多少，是在“对动态物体反应快”和“对 noise 稳”之间选。

:::wrong 看到的次数越多，map 就越可信，所以 log-odds 应该一直累加
一直累加只在 static 假设成立时对。上面的 person 站了 10 个 scan，unclamped 的 log-odds 记住的是“这里非常确定有东西”，需要 21 个 scan 的反证才推翻，而推翻它的证据早在第 11 个 scan 就开始出现了。Robot 身边最常见的东西（人、门、被搬动的椅子）恰恰是会动的。Clamp 等于承认 model 的假设不完全对，给 belief 留一点随时能改的余地。
:::

:::edge Unknown 和 free 不是一回事
$l=0$ 的 cell 是没看过的，不是空的。Planner 应当把 unknown 当作不能走，至少不能高速穿过。Exploration 也用这个区分：explored 和 unexplored 区域的交界叫 frontier（形式上是“至少有一个 free 邻居的 unknown cell”的集合），robot 走到最近的 frontier 上，就能看到新的区域。这是 Yamauchi 1997 年的 frontier-based exploration。
:::

### Semantic map：每个 cell 存一个 feature vector

Occupancy grid 能回答“哪里能走”，回答不了“sofa 在哪”。上一站的 dense feature 正好补上：VLMaps 用 LSeg 给每一帧 RGB 的每个 pixel 算一个与 CLIP text 对齐的 embedding，再用 depth、camera intrinsics 和 pose 把每个 pixel back-project 成 3D point，投到地面上落进某个 cell。一个 cell 在多帧里会收到很多 point，存它们 embedding 的平均。

查询时，用户给一组 category 的名字，比如论文举的“chair”“sofa”“table”“other”，各自过 CLIP 的 text encoder 得到 embedding（论文用“A photo of …”一类 template 的 ensemble，和第 2 站的 prompt ensembling 是一回事），和每个 cell 的 feature 做 dot product，每个 cell 取 argmax，得到一张 segmentation map。论文的 label list 里总有一个“other”，但没有解释它。它的作用可以从 argmax 推出来：argmax 只在给定的候选里选，如果只问“sofa”，地板上的每个 cell 都会被判成 sofa（这正是第 2 站那个 `:::wrong` 的另一面）。

Instruction 里的空间关系交给一个会写 code 的 LLM。给它几个“注释里是一句话、下面是 robot 的 Python code”的例子，它对新的 instruction 写出调用 navigation primitive 的 code，用 Python 的 `exec` 直接在 robot 上执行。论文的 primitive 有 `move_to(pos)`、`move_to_left(obj)`、`move_in_between(obj_a, obj_b)`、`face(obj)`、`turn(angle)`、`move_forward(dist)`、`move_north(obj)` 等十几个。它们在 VLMap 上找到物体的 mask 和 contour，再加上事先写好的 offset。论文没有给 `move_in_between` 的具体算法，下面用最简单的一种：取两个 mask 的中心，走到连线的 midpoint。

::fig[ee4706-vlmap] 一张 15×10 格的俯视 map，格子按 argmax label 着色。“in between the sofa and the TV”的目标是两个 mask 中心连线的 midpoint，robot 朝它走。

图里一格 0.2 m。Sofa 的 mask 是第 2 到 7 column、第 1 到 2 row，中心在 column 方向 $(2+7)/2+0.5=5$ 格、row 方向 $(1+2)/2+0.5=2$ 格，即 $(1.0,\,0.4)$ m；TV 的中心是 $(2.2,\,1.7)$ m；midpoint 是 $\big(\tfrac{1.0+2.2}{2},\tfrac{0.4+1.7}{2}\big)=(1.6,\,1.05)$ m。

同一张 map 还能给不同的 robot 生成不同的 obstacle map：先用高度在地板和天花板之间的 depth point 建一张基础的 obstacle map，再按 robot 列出“哪些 category 算 obstacle”。论文里 LoCoBot 选的是 wall、chair、table、window、stairs、other；drone 选的是 wall、window、stairs、ceiling lights、cabinet、other，没有 table、chair 和 sofa，可以从上面飞过去。

VLMaps 论文在 Habitat 里的 Matterport3D 场景上测了 91 个 sequence，每个 sequence 有 4 个 subgoal，连续完成 1、2、3、4 个 subgoal 的 success rate 是：

| 方法 | 1 个 | 2 个 | 3 个 | 4 个 |
|---|---|---|---|---|
| LM-Nav | 26% | 4% | 1% | 1% |
| CoW | 42% | 15% | 7% | 3% |
| CLIP Map | 33% | 8% | 2% | 0% |
| VLMaps | 59% | 34% | 22% | 15% |
| Ground-truth map | 91% | 78% | 71% | 67% |

连续 $k$ 个 subgoal 都成功，如果每个独立地以 $p$ 成功，success rate 是 $p^k$。VLMaps 的 $p=0.59$ 给出 $0.348,\,0.205,\,0.121$，实际是 34%、22%、15%，比独立的预测略高，说明失败集中在某些难的场景上；CoW 的 $0.42^k$ 给出 $0.176,\,0.074,\,0.031$，和实际的 15%、7%、3% 很接近。两边都说明一件事：长任务的 success rate 主要由单步的 success rate 决定，单步从 42% 提到 59%，4 步连做就从 3% 变成 15%。最后一行是把 semantic map 换成 ground truth：$0.91^k$ 给出 $0.828,\,0.754,\,0.686$，实际 78%、71%、67%。即使 map 完全正确，4 步连做也只有三分之二，剩下的失败来自 LLM 写的 code 和 navigation 本身。

## [agent] Large-model-based agent：grounding、scoring 与 closed loop

:::skip

### Language model 知道该做什么，不知道此刻能做什么

开头的第一次失败：“I spilled my drink”得到的是 vacuum cleaner 和一句道歉。LLM 读过大量关于“打翻饮料怎么办”的文字，它的知识是对的；缺的是两件事：这台 robot 有哪些 skill，以及在当前这个 state 下哪个 skill 做得成。

SayCan 把这两件事分开问。设 $i$ 是 instruction，$s$ 是当前 state，$\ell_\pi$ 是 skill $\pi$ 的文字描述（“pick up the sponge”）。“执行 $\pi$ 让 instruction 有进展”的 probability 拆成：

$$p(c_i\mid i,s,\ell_\pi)\;\propto\;\underbrace{p(c_\pi\mid s,\ell_\pi)}_{\text{world-grounding}}\;\underbrace{p(\ell_\pi\mid i)}_{\text{task-grounding}}$$

后一个 factor 问 LLM：在这个 instruction 下，下一步是 $\ell_\pi$ 的可能性多大。前一个 factor 问 robot：在 $s$ 下执行 $\pi$ 能成功的 probability，叫 affordance。拆分依据的假设是：skill 成功时，它推进 instruction 的 probability 是 $p(\ell_\pi\mid i)$；skill 失败时，什么也没推进。

### 打分，而不是生成

LLM 有两种用法。一种是让它自由生成下一步，再把生成的文字映射到最接近的 skill（SayCan 的 Generative baseline 用 sentence embedding 找最近的 skill）；另一种是给每个 skill 的描述算 likelihood，即“在 prompt 后面接上这段文字”的 probability。SayCan 用后者：output 一定落在 robot 的 skill 里，而且得到的是一个 distribution，可以和 affordance 相乘。

Prompt 写成对话的样子，例如“How would you bring me a coke can? I would: 1. find a coke can, 2. pick up the coke can, 3. bring it to you, 4. done.”。每选定一步，就把它接到 prompt 后面，再给下一步打分，直到“done”得分最高。

### Affordance 从哪里来

Skill 本身是 image-based 的 behavior cloning policy，用 10 台 robot 在 11 个月里收的 68,000 条 demonstration，加上 12,000 条筛选过的成功 episode 训练。每个 skill 另有一个以 language 为条件的 value function，在 Everyday Robots 的 simulator 里用 MT-Opt（一种 TD learning）train，先用 demonstration 起步，再在 simulation 里在线收 data。Reward 是 sparse 的：episode 以成功结束给 1，否则给 0。这个设定下 value 就是 success probability。一个 episode 的 return $\sum_t\gamma^tr_t$ 只有两种值：成功时是 $\gamma^{T}$（$T$ 是结束的步数），失败时是 0。所以

$$V(s)=\mathbb E\Big[\sum_t\gamma^tr_t\Big]=\mathbb E\big[\gamma^{T}\,\mathbf 1[\text{success}]\big]\approx P(\text{success}\mid s)\quad(\gamma\to1)$$

成功与否由人看 video 判断，三个人里两个说成功才算。这个 value function 本来是 RL 的副产品，在 SayCan 里成了 control 和 scene understanding 之间的接口：它读 image，output 的是“这件事现在做不做得成”。

### 走一遍

::fig[ee4706-saycan] 一步的打分。LLM 最看好“pick up the sponge”，但 robot 还没看到 sponge；乘上 affordance 之后，“find a sponge”胜出。数字是示意。

Robot 站在 table 旁，table 上有打翻的 coke can，sponge 在 counter 上、不在 camera 的视野里。四个候选 skill：

| Skill | LLM score | Affordance | 乘积 |
|---|---|---|---|
| find a sponge | 0.30 | 0.92 | **0.276** |
| pick up the sponge | 0.40 | 0.05 | 0.020 |
| pick up the coke can | 0.20 | 0.85 | 0.170 |
| go to the trash can | 0.10 | 0.95 | 0.095 |

只看 LLM 会选“pick up the sponge”，robot 会对着空气抓；只看 affordance 会选“go to the trash can”，它最容易成功，却和 instruction 关系最小。乘积选出“find a sponge”。

执行之后 state 变了：sponge 在视野里，“pick up the sponge”的 affordance 升到比如 0.88；prompt 后面多了“1. find a sponge”，LLM 给“pick up the sponge”的 score 也升到比如 0.70，乘积 0.616，成为第二步。这样一步一步，得到 SayCan 论文 5.1 节举的那个 plan：find a sponge、pick up the sponge、bring it to you、done。

| 系统 | Plan 正确 | 执行成功 |
|---|---|---|
| PaLM-SayCan，mock kitchen | 84% | 74% |
| PaLM-SayCan，真实 kitchen | 81% | 60% |
| 去掉 affordance（No VF）| 67% | |
| 生成再映射（Generative）| 74% | |

| FLAN，不加 affordance | 38% | |
| 不用 LLM，直接用 language-conditioned BC（BC NL）| | 0% |

:::wrong LLM 选出的 plan 读起来合理，robot 就能完成任务
表里 plan 和执行之间有 10 个百分点的差（84% 对 74%），换到真实 kitchen 差到 21 个（81% 对 60%）。Plan 正确只说明选对了 skill 的顺序，每个 skill 还要在真实的 state 下做成。论文说系统的主要瓶颈在 skill 本身的范围和能力。还有一种失败 plan 看不出来：value function 报了一个高值，执行时 skill 却失败了，论文承认这时系统很难反应过来，因为 SayCan 只在当前这一步通过 value function 接收环境的反馈，选完一步就往下走，不检查结果。
:::

### Closed loop：把执行结果写回去

上面最后一种失败的根源是 open loop：plan 按“每一步都成功”往下排。设每个 skill 一次成功的 probability 是 0.8，各次独立，一个 3 步的 plan 全部成功的 probability 是 $0.8^3=0.512$。

如果每步执行后有一个 success detector 判断成没成，失败就把“failed”写进 prompt，让 LLM 重新打分（多半会再选同一个 skill），每步最多试 3 次，单步失败的 probability 降到 $0.2^3=0.008$，整个 plan 的 success rate 是

$$(1-0.008)^3=0.976$$

这个数有两个假设：detector 从不出错，每次尝试互相独立。

这就是[第 1 站](#arch) Gat 说的 cognizant failure：skill 自己不能保证成功，但只要失败能被发现，上层就能补救。SayCan 论文在 limitation 里也说，skill 失败的问题或许可以靠“prompt language model 做 correction”来解决。

Inner Monologue（Huang et al. 2022）就是这样接回去的。它在 SayCan 的 kitchen 里，每步之后往 prompt 里写几种文字 feedback：success detection（例如“[success: no]”），由一个 fine-tune 过的 CLIP 看执行前后两张 image 和 skill 的文字，output 成功的 probability；passive scene description，列出看得见和被挡住的物体；必要时 LLM 还可以向人提问，人的回答也写进去。实验在 8 个 instruction 上共 120 次 evaluation，一部分加了 adversarial disturbance（在 skill 执行时故意让它失败，往往只要再试一次就好）：

| | SayCan | + success | + object + success |
|---|---|---|---|
| 无 disturbance：manipulation | 50.0% | 62.5% | 75.0% |
| 无 disturbance：mobile manipulation | 50.0% | 50.0% | 75.0% |
| 无 disturbance：drawers | 83.3% | 83.3% | 100.0% |
| 有 disturbance：manipulation | 12.5% | 25.0% | 33.3% |
| 有 disturbance：mobile manipulation | 0.0% | 25.0% | 75.0% |
| 有 disturbance：drawers | 0.0% | 44.4% | 44.4% |
| 总计 | 30.8% | 48.7% | 60.4% |

有 disturbance 时，没有 feedback 的 SayCan 接近 0%，因为它不会重试；加上 success detection，LLM 会重新选同一个 skill 再试一次。数字远没有上面算的 0.976 那么好，原因正是那个算式的两个假设不成立。论文的 limitation 写了 detector 出错的两种后果：false negative（其实成功了却报失败）带来多余的 retry，false positive（其实失败了却报成功）让 LLM 以为 state 已经变了，又回到 open loop 的问题。有时 LLM 还会无视 feedback，提出场景里根本没有的物体。

:::back
“单步成功率连乘”这件事在 [STANFORD-CS224R 第 6 站](../courses/STANFORD-CS224R.html#robot)又出现一次：VLA 停在 80% 左右，要到 99% 每一步得多可靠。
:::

### 从两个 model 到一个：π0.5 的 high-level

SayCan 的 LLM 和 skill 是分开 train 的两个系统，接口是 551 个固定的 skill 描述。[第 1 站](#arch)的 π0.5 换了做法：同一个 VLA 先 output 文字 subtask，再 output action，接口是任意的一句话，没有 skill list。

这样做需要 low-level 真的听得懂各种 subtask，所以 π0.5 的 data 里专门有两类：robot episode 被人分段标上 subtask 和相关物体的 bounding box（high-level 的 training data），以及 post-training 时由人用语言一步步指挥 robot 的 verbal instruction。它的 mobile manipulator data 约 400 小时、来自约 100 个真实的 home，第一阶段的 training example 里 97.6% 来自其他来源（固定的 arm、其他 embodiment、web data）。用 104 个 location 的 data train 的 model，在没见过的 test home 里，和直接在 test home 里收 data train 的 control 表现相近。

论文的 high-level ablation 比较了七种做法：完整的 π0.5；去掉 web data；去掉 verbal instruction；implicit HL（train 时有 subtask data，运行时不先 output subtask）；no HL（train 时也没有 subtask data）；用 zero-shot 的 GPT-4 当 high-level；以及由一个人当 high-level，作为“oracle”。按评分规则得分的结果只画在 Figure 13 里，正文没有给数字，我只读到了作者的结论：完整的 π0.5 最好，甚至比人当 high-level 还好；implicit HL 第二，说明很大一部分好处只来自 train 时有 subtask 的 data；no HL 明显差；verbal instruction 只占 high-level 那部分 mobile manipulation 样本的约 11%，去掉却明显变差；zero-shot GPT-4 最差，作者的解读是 VLM 必须用 robot data 去 adapt。和 SayCan 对照：SayCan 的 LLM 一点 robot data 都没见过，靠 affordance 补上 grounding；π0.5 把 grounding 直接 train 进了 high-level 本身。

:::edge SayCan 难以处理的 instruction
论文列出的 failure：否定（“bring me a snack that isn't an apple”）；指代含糊；长任务里多数失败是 LLM 提前结束（要拿两样东西，拿了一样就输出 done）。前两种是 LLM 的问题，第三种和 open loop 有关：没有人检查“两样都拿到了吗”。
:::

### 为什么要在想象里练

在真实 robot 上，每一条 transition 都花时间、磨损 hardware，还有安全风险（[RB4301 第 1 站](../courses/RB4301.html#mdp)算过一条 transition 有多贵）。如果能从已有的 data 学一个 dynamics model，就可以在 model 里大量 rollout，train policy 时不再碰真实世界。

DreamerV3 是这条路上的代表：同时 train 三个 network，一个 world model 从 replay buffer 里的真实 data 学 dynamics，一个 critic 估计 value，一个 actor 选 action；actor 和 critic 在 world model 想象出来的 trajectory 上 train，每条想象 16 步，与环境交互时直接从 actor sample action，不做 lookahead planning。它用同一套固定的 hyperparameter 跑了 150 多个任务，是第一个在 Minecraft 里不用 human data、也不用 curriculum、从零挖到 diamond 的算法。

:::back
Model-based RL 的另一半（Dyna、short rollout、ensemble）在 [STANFORD-CS224R 第 3 站](../courses/STANFORD-CS224R.html#mbrl)。
:::

[RB4301 第 3 站](../courses/RB4301.html#mpc)讲过 learned model 用来 plan 时会被 planner 利用错误、rollout 的 error 会累积。这一站讲另一半：observation 是 image 时，model 该学在哪个空间里。

### 为什么不直接预测下一张 image

CS285 把从 image 学 model 的困难归成三条：维度高、冗余、partially observable。一张 64×64 的 RGB image 是 $64\times64\times3=12288$ 个数，robot 动一下，其中大部分（背景、桌面）几乎不变；真正决定接下来发生什么的只是少数几个量（物体的位置、速度）。而单独一张 image 连速度都看不出来，state 本来就不在一帧里。

所以 model 在一个低维的 latent state 上做 dynamics：encoder 把 image 压进 latent，dynamics 在 latent 里往前推，reward 从 latent 读出。CS285 比较了 encoder 的几种选法：看整条 sequence 的 smoothing posterior 最准、最复杂，只看当前一帧的 single-step encoder 最简单、最不准。Dreamer 走中间的路：encoder 看当前一帧，再加上一个 recurrent state 记住过去。

### RSSM：一个 deterministic 的 memory，一个 stochastic 的 state

DreamerV3 的 world model 叫 Recurrent State-Space Model（RSSM），state 分成两部分：recurrent state $h_t$ 是 deterministic 的，负责记住历史；representation $z_t$ 是 stochastic 的，负责表达这一刻不确定的部分。

$$\begin{aligned}
\text{sequence model:}&\quad h_t=f_\phi(h_{t-1},z_{t-1},a_{t-1})\\
\text{encoder (posterior):}&\quad z_t\sim q_\phi(z_t\mid h_t,x_t)\\
\text{dynamics predictor (prior):}&\quad \hat z_t\sim p_\phi(\hat z_t\mid h_t)\\
\text{reward / continue / decoder:}&\quad \hat r_t,\ \hat c_t,\ \hat x_t\sim p_\phi(\cdot\mid h_t,z_t)
\end{aligned}$$

关键在于 $z$ 有两条来路。有 image $x_t$ 时，用 encoder 得到 posterior；没有 image 时，只凭 $h_t$ 用 dynamics predictor 猜一个 prior。Train 的时候两条都有；想象的时候只有后一条，因为想象出来的未来没有 image。

::fig[ee4706-rssm] 左半是 world model 的 training：每一步都有真 image，$z$ 来自 encoder。右半是想象：没有 image，$\hat z$ 来自 dynamics predictor，actor 在这些 state 上选 action。

所以 training 必须让 prior 学会预测 posterior，否则想象出来的 state 和真实的 state 不是同一种东西。$z$ 是若干个 categorical distribution 拼成的 vector，sampling 的 gradient 用 straight-through 传回去。

### 两个 KL：谁去迁就谁

让 prior 接近 posterior，最直接是最小化 $\mathrm{KL}[q\,\|\,p]$。DreamerV3 把它拆成两项，各用 stop-gradient（$\mathrm{sg}$）挡住一边：

$$\mathcal L_{\text{dyn}}=\max\big(1,\ \mathrm{KL}[\mathrm{sg}(q_\phi(z_t\mid h_t,x_t))\,\|\,p_\phi(z_t\mid h_t)]\big)$$
$$\mathcal L_{\text{rep}}=\max\big(1,\ \mathrm{KL}[q_\phi(z_t\mid h_t,x_t)\,\|\,\mathrm{sg}(p_\phi(z_t\mid h_t))]\big)$$

$\mathcal L_{\text{dyn}}$ 的 gradient 只进 prior，让 dynamics predictor 去追 encoder；$\mathcal L_{\text{rep}}$ 的 gradient 只进 encoder，让 representation 变得好预测。总 loss 是 $\mathcal L_{\text{pred}}+\mathcal L_{\text{dyn}}+0.1\,\mathcal L_{\text{rep}}$，$\mathcal L_{\text{pred}}$ 是 image、reward、continue flag 的 prediction loss。

为什么要拆开、而且让 encoder 那边 weight 只有 0.1？如果 encoder 也被大力推向 prior，最省事的办法是 encoder 不管 image、output 一个和 prior 一样的东西，KL 变成 0，但 $z$ 里没有任何 image 的信息。论文把这叫作一个 degenerate solution：dynamics 很容易预测，却没有包含足够的 input 信息。让 prior 多迁就 encoder、encoder 少迁就 prior，representation 才保有信息。（[BERKELEY-CS285 第 7 站](../courses/BERKELEY-CS285.html#mbrl)用 deterministic encoder 推过同一种 collapse：encoder 和 dynamics 都 output 0，dynamics loss 就恰好是 0。）

两项外面的 $\max(1,\cdot)$ 叫 free bits：KL 小于 1 nat（约 1.44 bits）时，loss 是常数 1，gradient 为 0。例如某一步 KL 是 0.6 nat，这一步两个 KL 项都不产生 gradient，training 把力气全花在 prediction loss 上；KL 是 2.3 nat 时，gradient 照常。论文的说法是：两项一旦已经压得足够小就不再产生 gradient，learning 的重心回到 prediction loss 上，免得掉进上面那个 degenerate solution；free bits 和小的 $\beta_{\text{rep}}$ 合起来，才让同一套 hyperparameter 能在不同 domain 上不改。Encoder 和 dynamics predictor 的 categorical distribution 还都混进 1% 的 uniform（unimix），probability 不可能变成 0 或 1，KL 保持有限；论文说早期实验里出现过 KL loss 的 spike，unimix 就是为了防它。

### 尺度：symlog、symexp twohot 与 return normalization

固定一套 hyperparameter 跑 150 多个任务，最大的障碍是尺度：有的任务 reward 是 0 或 1，有的一步就是几百；vector observation 里有的维度是零点几，有的是几千。论文先排除了三种常见的办法：大 target 上的 squared loss 会发散；absolute 或 Huber loss 会让 learning 停滞；用 running statistics 去 normalize target，又让 optimization 变成 non-stationary。

**Vector observation：symlog squared loss。** Encoder 的 input 和 decoder 的 target，凡是 vector observation，都先过一个 symlog：

$$\mathrm{symlog}(x)=\mathrm{sign}(x)\ln(|x|+1),\qquad\mathrm{symexp}(x)=\mathrm{sign}(x)\big(e^{|x|}-1\big)$$

Loss 是 $\mathcal L(\theta)=\tfrac12\big(f(x,\theta)-\mathrm{symlog}(y)\big)^2$，用的时候 $\hat y=\mathrm{symexp}(f(x,\theta))$。Symlog 在 0 附近接近 identity（$\mathrm{symlog}(0.1)=0.095$），本来就小的 target 不受影响。设 observation 有两维，target 分别是 1 和 1000，prediction 都从 0 开始。直接用 squared loss，对 prediction 的 gradient 是 $\hat y-y$，分别是 $-1$ 和 $-1000$，差 1000 倍，大的那一维主导一切，learning rate 合适一边就会让另一边发散。经过 symlog，target 是 $\ln2=0.693$ 和 $\ln1001=6.909$，gradient 是 $-0.693$ 和 $-6.909$，只差 10 倍。

**Reward 和 critic：symexp twohot loss。** Reward 和 return 可能是随机的：同一个 state 有时给 0、有时给 10。对随机的 target 做 squared regression，学到的是 mean，而且 gradient 仍然跟着 target 的大小走。所以 reward predictor 和 critic 不做 regression，改成在一组 bin 上做 classification。Bin 的位置是 $B=\mathrm{symexp}([-20,\dots,+20])$，越往外越稀；network output 每个 bin 的 logit，读数是 bin 位置按 softmax probability 的加权平均：

$$\hat y=\mathrm{softmax}(f(x))^\top B$$

Target $y$ 编码成 twohot：只有夹住 $y$ 的两个相邻 bin 非零，两个值加起来是 1，离 $y$ 近的那个按线性比例更大。Loss 是 cross-entropy $-\mathrm{twohot}(y)^\top\log\mathrm{softmax}(f(x))$。

::fig[ee4706-twohot] 两个 target 的 twohot 编码。Bin 的间距在 symlog 的刻度上相等（图里为了好算取 symexp 的整数点；论文的 bin 从 symexp(−20) 排到 symexp(20)，我读到的正文没有写间距），1 和 1000 都只占两个相邻的 bin，weight 都在 0 到 1 之间。

为了好算，取 symexp 的整数点当 bin：$\mathrm{symexp}(6)=402.4$，$\mathrm{symexp}(7)=1095.6$。$y=1000$ 落在两者之间，

$$w_7=\frac{1000-402.4}{1095.6-402.4}=0.862,\qquad w_6=1-0.862=0.138$$

读回来：$0.138\times402.4+0.862\times1095.6=1000$。$y=1$ 落在 $\mathrm{symexp}(0)=0$ 和 $\mathrm{symexp}(1)=1.718$ 之间，$w_1=1/1.718=0.582$，$w_0=0.418$。Cross-entropy 对 logit 的 gradient 是 $\mathrm{softmax}(f)-\mathrm{twohot}(y)$，每一个分量都在 $-1$ 和 1 之间，不管 target 是 1 还是 1000。论文的说法是：loss 只依赖 bin 上的 probability，gradient 的大小和 target 的大小脱钩。

**Actor：return normalization。** Actor 用 REINFORCE 的 gradient，advantage 是 $(R^\lambda_t-v(s_t))/\max(1,S)$，其中 return 用它在 batch 里的分布范围来 normalize（用 percentile 而不用 min 和 max，因为 return 的分布可能 multimodal、有 outlier）：

$$S=\mathrm{EMA}\big(\mathrm{Per}(R,95)-\mathrm{Per}(R,5),\ 0.99\big),\qquad\text{用 }\frac{R}{\max(1,S)}$$

Dense reward 的任务里，若 return 的第 5 到第 95 percentile 是 20 到 820，$S=800$，return 被除以 800，落到 1 的量级。Sparse reward 的任务里，若 return 大多是 0、偶尔是 0.6，$S=0.6$，$\max(1,0.6)=1$，return 不放大。不放大的理由：actor 的 objective 是 normalize 后的 return 加上一个固定 scale $\eta=3\times10^{-4}$ 的 entropy；把 0.6 放大成 1，等于把 sparse reward 里大量的 noise 也放大，压过 entropy，exploration 就停了。论文也比较过用 standard deviation 去 normalize：sparse reward 下 std 接近 0，除下去反而把 noise 放得更大。

论文的 ablation 说这些 robustness technique 都有贡献，最要紧的是 world model 的 KL objective（上一小节的两个 KL 加 free bits），其次是 return normalization，再其次是 reward 和 value 的 symexp twohot。

:::wrong World model 重建出来的 image 很清楚，说明它学好了
Reconstruction loss 是对每个 pixel 平均的。64×64 的 image 里，一个 3×3 pixel 的小球只占 $9/4096=0.22\%$ 的 pixel；model 把背景和 arm 画得很好、把小球画丢了，reconstruction loss 几乎不变。可是对“把球推进洞”这个任务，小球的位置是唯一要紧的东西。判断 world model 有没有用，要看它预测的 reward 和 policy 在真实环境里的表现，而不是 image 好不好看。

这不是说 reconstruction 没用。DreamerV3 的另一个 ablation 把 reward 和 value 传给 representation 的 gradient 停掉、只留 reconstruction 等 unsupervised objective，或者反过来，结论是 Dreamer 主要靠 world model 的 unsupervised objective 学 representation。Reconstruction 是学 representation 的主要信号；错的只是拿“看起来清楚”去当检验。
:::

:::edge 想象只有 16 步
DreamerV3 每条想象的 trajectory 是 $T=16$ 步，discount 是 $\gamma=0.997$。16 步以外的 return 由 critic 的 value 补上，用的是 $\lambda$-return 的递推：

$$R^\lambda_t=r_t+\gamma c_t\big((1-\lambda)v_t+\lambda R^\lambda_{t+1}\big),\qquad R^\lambda_T=v_T$$

$c_t$ 是 continue flag（episode 在这一步结束就是 0）。Critic 不只在想象的 trajectory 上 train，也在 replay buffer 的真实 trajectory 上 train（weight 0.3），并且向自己 parameter 的 EMA 靠拢，作用和 target network 相近。想象得太长，[RB4301 第 3 站](../courses/RB4301.html#mpc)推出的 model error 累积就会让后面的 state 越来越不像真的。

## [hri] Human-robot interaction：legibility 与 shared autonomy

:::skip
能写出 observer 对 goal 的 posterior、在直线 trajectory 上算出一个点的值，能比较两条 trajectory 的 legibility score 并说出 trust region 的作用，能解释 belief 各一半时 shared autonomy 为什么直走，就可以去第 7 站。
:::

### Robot 的 motion 也是给人看的信息

开头第三次失败：两个杯子并排，robot 走直线去拿右边那个，旁边的人很晚才看出它的目标。直线是最省力的，也是人最“预料得到”的，但它在前半程对两个杯子几乎一样近，不传递“要哪个”的信息。

Dragan 等人把这里的两种性质分开：predictability 是“已知 goal 时，motion 符合人的预期”；legibility 是“看到一部分 motion 时，人能多快、多有把握地推出 goal”。两者可以冲突，直线最 predictable，未必最 legible。

### Observer 怎样从 motion 推 goal

假设 observer 认为 robot 是 rational 的：motion 越省 cost，越像是 robot 会做的。用 maximum entropy 的说法，一条 trajectory $\xi$ 被预期的 probability $\propto\exp(-C[\xi])$。看到从起点 $S$ 走到当前点 $Q$ 的一段 $\xi_{S\to Q}$，observer 对 goal $G$ 的 posterior 是

$$P(G\mid\xi_{S\to Q})\;\propto\;\frac{\exp\big(-C[\xi_{S\to Q}]-V_G(Q)\big)}{\exp\big(-V_G(S)\big)}\,P(G)$$

$V_G(q)$ 是从 $q$ 到 $G$ 的最小 cost。分子是“已经走的这段，加上从这里去 $G$ 的最好走法”的总 cost，分母是“从起点直接去 $G$ 的最好走法”。两者的比值衡量：如果目标是 $G$，到目前为止的 motion 浪费了多少。浪费越少，越像是去 $G$ 的。

论文里 $C$ 取 velocity 的平方和。为了能手算，这里把 $C$ 换成 path length 乘一个 rationality coefficient $k=10$ /m，这样 $V_G(q)=k\,|G-q|$。设 $S=(0,0)$，$G_1=(-0.25,1)$，$G_2=(0.25,1)$，单位 m，prior 各一半，robot 真正要去 $G_2$。

沿直线走到四分之一处，$Q=(0.0625,\,0.25)$。已走的长度 $|Q|=0.2577$，两边到 goal 的直线距离：

$$|G_2-Q|=\sqrt{0.1875^2+0.75^2}=0.7731,\qquad|G_1-Q|=\sqrt{0.3125^2+0.75^2}=0.8125$$

起点到两个 goal 都是 $\sqrt{0.25^2+1}=1.0308$。代进去，$G_2$ 的 exponent 是 $-10\,(0.2577+0.7731-1.0308)=0$（直线本来就是去 $G_2$ 的最优走法，没有浪费）；$G_1$ 的是 $-10\,(0.2577+0.8125-1.0308)=-0.394$。所以

$$P(G_2\mid\xi_{S\to Q})=\frac{1}{1+e^{-0.394}}=\frac{1}{1+0.674}=0.597$$

走了四分之一，observer 只有六成把握。

::fig[ee4706-legible] 同一个起点、同样两个杯子。看下面两根条：左边直线走到一半，P(G2) 才 0.75；右边先往右弯，一半时已经 0.93。

把 trajectory 换成一条先往右弯的 quadratic Bézier curve，control point 取 $(0.6,\,0.35)$。它更长（1.17 m 对 1.03 m，多 14%），但从一开始就远离 $G_1$：同样在四分之一的参数处，$P(G_2)=0.798$；一半处 0.927，直线是 0.750。

### Legibility score 与 trust region

要比较整条 trajectory，把 $P(G_R\mid\xi_{S\to\xi(t)})$（$G_R$ 是真正的 goal）对时间加权平均，越早的时刻 weight 越大：

$$\text{Legibility}[\xi]=\frac{\int P\big(G_R\mid\xi_{S\to\xi(t)}\big)\,f(t)\,dt}{\int f(t)\,dt},\qquad f(t)=T-t$$

上面两条按这个公式算，直线是 0.658，弯的是 0.795。

如果直接对这个 score 做 gradient ascent，它会一直往外弯：control point 移到 $(0.8,\,0.35)$，score 升到 0.829。但弯得太厉害，人反而看不懂 robot 在做什么。所以论文把 optimization 限制在一个 trust region 里，要求 $C[\xi]\le\beta$。在 Mechanical Turk 上的实验（有效样本 297 人，七个 $\beta$ 从 0 到 320，看 video 时觉得有把握就按停）里，$\beta\ge20$ 的条件都比 predictable 的 trajectory 显著更 legible，$\beta=40$ 最好。接着的实验只给人看前半段：$\beta=40$ 时人的信心显著高于 $\beta=0$ 和 $\beta=320$；$\beta=320$ 时，人更多地认为 robot“两个都不去”。

:::wrong Robot 走最短、最顺的路线，旁边的人最容易看懂
最短的路线对“已经知道 goal 的人”最好懂（predictable），对“正在猜 goal 的人”不一定。上面的直线走了一半，$P(G_2)$ 只有 0.75，observer 心里还有四分之一的 probability 给了 $G_1$；多走 14% 的路，一半时就到 0.93。反过来也不能弯得越多越好，$\beta=320$ 那一组说明，弯过头的 motion 不再像是去任何一个 goal 的。
:::

### Shared autonomy：robot 反过来推人的 goal

方向倒过来：人用 joystick 遥控 robot arm 去抓一个东西，robot 想帮忙，但不知道人要哪个。Javdani 等人把它写成 POMDP：state 是 robot 的 state 加上未知的 goal $g$，observation 是人的 input，belief $b(g)$ 用和上面同一种 MaxEnt 的 model 从人的 input 更新。只用人的 input 更新 belief，不用 robot 自己的 action，否则 robot 往哪边帮忙，就会越来越相信那边，形成 feedback loop。

POMDP 精确解不了。Hindsight optimization（又叫 QMDP）假设下一步之后 goal 就知道了，于是 belief 下的 action value 是各 goal 的 value 按 belief 加权：

$$Q(b,a)=\sum_g b(g)\,Q_g(x,a)$$

选让它最好的 action（论文实际是沿 $Q$ 的 gradient 走，而不是直接求 argmax）。论文里 robot 的 cost 假设人从下一步起不再给 input、由 robot 把任务做完，再加一项 $(a-D(u))^2$ 惩罚 robot 的 action 偏离人的 command $u$。和它对比的 baseline 是 Dragan 和 Srinivasa 的 predict-then-blend：先预测最可能的 goal，再按 confidence 把人的 command 和“去那个 goal 的 autonomous command”混合。论文 Figure 2 用 $\max_gb(g)-\min_gb(g)$ 当 confidence 来说明这件事（belief 平分时是 0，全在一个 goal 上时是 1）；user study 里实现的 blend 用的是到最近 goal 的距离 $d$：$\text{conf}=\max(0,\,1-d/D)$，$D$ 是一个阈值。

拿上面的两个 goal 做例子，belief 各 0.5，robot 在 $S$，每步走 0.1 m，cost 是剩余距离。

::fig[ee4706-assist] Belief 各一半时的两个候选 action。直走让两边都近了一点，expectation 最小。

直走一步到 $(0,\,0.1)$，到两个 goal 都是 $\sqrt{0.25^2+0.9^2}=0.934$，expectation 0.934。朝 $G_2$ 走一步到 $(0.024,\,0.097)$，到 $G_2$ 是 $1.031-0.1=0.931$，到 $G_1$ 是 0.944，expectation $0.5\times0.944+0.5\times0.931=0.937$。Hindsight optimization 选直走：在不确定时，先做对所有 goal 都有利的事。Predict-then-blend 这时按 Figure 2 的定义，confidence 是 $0.5-0.5=0$；按 user study 里的距离定义，到最近的 goal 还有 1.031 m，只要阈值 $D$ 不超过这个距离，$1-1.031/D\le0$，confidence 也是 0。两种定义下它都完全不帮忙，要等人的 input 把 belief 推偏、或者手已经离某个 goal 很近了，才开始介入。论文在 limitation 里也提到这一点：policy 从起始姿态就开始帮忙，blend 不会，参与者很快就分得出自己在用哪个系统。

论文的 user study：10 个参与者（9 男 1 女，都有 robotics 背景，之前没用过这个系统），用 Razer Hydra 的两个 joystick 遥控一只 robot arm 去抓桌上的三样东西（canteen、block、glass），每人两个系统各做一遍，一半人先用 blend、一半人先用 policy。

| 量 | 结果 |
|---|---|
| 完成时间 | policy 更快，$F(1,9)=12.98$，$p=0.006$ |
| 人给的 control input 总量 | policy 更少，$F(1,9)=7.76$，$p=0.021$ |
| “我想用这个系统”（1–7 分）| blend 4.90（SD 1.58），policy 4.10（SD 1.64），差异不显著 |
| 更喜欢哪个（1 = blend，7 = policy，4 = 中立）| 平均 2.90（SD 1.76），偏向 blend，与中立的差异不显著 |

客观指标 policy 赢，主观偏好反而偏向 blend。参与者觉得 blend 让自己更有控制感，policy 让任务更快完成；一个参与者说 policy 虽然更快，他仍然不喜欢“它好像有自己的想法”的感觉，还有人说要额外去抵消 policy 的动作。作者的解读是 control authority 和 efficiency 之间的 trade-off，也提到有人练得多了偏好会变，并承认 10 个 robotics 背景的人是很小、很偏的样本。

:::back
[STANFORD-CS237B 第 7 站](../courses/STANFORD-CS237B.html#shared)走的是另一条路：goal 的 posterior 从一个 mixture density network 里读出来，assistance 是一个 closed-form 的公式，并且用数字说明了逐步连乘 likelihood 会给出假的确定。

:::edge Robot 不能为了“看清人的意图”而去试探

## [sys] Integrated system design：latency、edge inference 与 real-time chunking

:::skip
能由 bandwidth 和 weight 大小算出 token 速率上限，能算 synchronous 执行时 robot 在动的时间比例，能写出 RTC 的 soft mask 并推出 $d\le H/2$，就可以去第 8 站。
:::

### 一个 decision 的 latency 由什么组成

从 camera 曝光到 action 送进 controller，中间依次是：image 传输与 preprocessing；把所有 image token、文字 token、proprioception token 过一遍 model（prefill）；生成 action（autoregressive decoding 一个个 token，或 flow matching 的若干步 denoising）；如果 model 不在 robot 上，还有 network。

π0 论文在一块 RTX 4090 上、3 个 camera 的设定下把这几段分别量了：image encoder 14 ms，observation 的 forward pass（prefill）32 ms，action expert 的 10 次 forward pass 27 ms，合计 73 ms；model 放在另一台机器上时再加 13 ms 的 network，86 ms。RTC 论文说的“π0 光 KV cache 的 prefill 就要 46 ms”就是前两项之和 $14+32$。RTC 论文还给了 π0.5 加 RTC 在 mobile robot 上的分项：model 96.9 ms、network 21.2 ms、image resize 11.2 ms、其他 9.7 ms，合计 139.0 ms；不移动的 robot 上 network 只有 6.9 ms，合计 108.8 ms。而 50 Hz 的 controller 每 20 ms 就要一个 action。

::fig[ee4706-latency] 三次实测的一次 decision，画在 20 ms 一格的 controller 时间轴上。看每一条都跨过好几格：model 算完之前，controller 已经要了 3 到 6 个 action，右上角的 $d$ 就是这个数。第三条的各段是分项之和，先后顺序是示意。

这几段里，prefill 主要受计算量限制（几百个 token 一起算，GPU 的 matrix multiply 能吃满）；decoding 则受另一个东西限制。

### Decoding 被 memory bandwidth 卡住

Batch size 为 1 时，每生成一个 token，model 的全部 weight 都要从 memory 里读一遍，而每个 weight 只参与一次乘加。读 weight 的时间远多于算的时间，所以 token 速率的上限是

$$\text{tokens/s}\ \le\ \frac{\text{memory bandwidth}}{\text{weight 的 bytes}}$$

一个 7B 的 model（OpenVLA 的大小），每个 7-dim 的 action 要 7 个 token：

| Hardware（bandwidth）| Precision | Weight | Tokens/s 上限 | Action/s 上限 |
|---|---|---|---|---|
| RTX 4090（1008 GB/s）| bf16 | 14 GB | 72 | 10.3 |
| RTX 4090 | int4 | 3.5 GB | 288 | 41 |
| Jetson AGX Orin（204.8 GB/s）| bf16 | 14 GB | 14.6 | 2.1 |
| Jetson AGX Orin | int8 | 7 GB | 29.3 | 4.2 |
| Jetson AGX Orin | int4 | 3.5 GB | 58.5 | 8.4 |

（这里把 7B 粗算成 14 GB；[MIT-6.5940 第 8 站](../courses/MIT-6.5940.html#robot)按 Llama 2 7B 的 13.48 GB 精确算过同一张表，结论一样。）

用实测核对：OpenVLA 论文说 bf16 在 RTX 4090 上约 6 Hz，在 10.3 的上限之内（另外的时间花在 prefill 和 overhead 上）。同一个 model 搬到 robot 身上的 Orin，bf16 连 2 Hz 都到不了。Quantization 把 weight 的 bytes 减半再减半，上限按同样的比例上升，这就是 edge 部署首先考虑 quantization 的原因。

但上限只是上限。OpenVLA 论文在 8 个 BridgeData V2 任务上（每种 80 次 rollout）实测了三种 precision：

| Precision | Success rate | VRAM |
|---|---|---|
| bf16 | 71.3 ± 4.8% | 16.8 GB |
| int8 | 58.1 ± 5.1% | 10.2 GB |
| int4 | 71.9 ± 4.7% | 7.0 GB |

在 A5000 上，int8 只跑到约 1.2 Hz，int4 约 3 Hz。int8 比 bf16 还慢，论文的解释是加进去的 quantization operation 有额外开销；int8 的 success rate 掉下来，论文也归因于速度（离线量 token accuracy，三种 precision 相当）：BridgeData 的 controller 是 5 Hz，action 给得太慢，任务就做坏了。所以 bandwidth 算出来的上限能告诉你“不 quantize 一定不够”，不能告诉你“quantize 之后一定够”，必须实测（怎么做 quantization 而不掉速度和 accuracy，见 [MIT-6.5940 第 4 站](../courses/MIT-6.5940.html#llmq)）。

Flow matching 的 action expert 也要按同样的道理算：约 3 亿 parameter，bf16 是 0.6 GB，10 步 denoising 读 10 遍是 6 GB，在 Orin 上光读 weight 就要 $6/204.8=29$ ms；3B 的 backbone 在 prefill 里至少也要整个读一遍，又是 29 ms。它一次 output 一整个 chunk，不受“每个 action 7 个 token”的限制。

同样拿实测核对，这次结果更难看。在 RTX 4090 上同样的两项下限都是 $6/1008=5.95$ ms，π0 实测的 prefill 是 32 ms，10 次 action forward 是 27 ms，分别是下限的 5.4 倍和 4.5 倍。几百个 token 的 prefill 有真实的计算量；action expert 每一步要对 50 个 action token 和前面几百个 token 做 attention，每次 forward 都有 kernel launch 之类的固定开销。所以“Orin 上每个 chunk 至少要几十 ms”只是一个很松的下限，真实的数要在 Orin 上量。

### Chunk 怎样执行：synchronous 与 naive asynchronous

设 policy 每次 output 一个长 $H$ 的 chunk，只执行前 $s$ 步；controller 周期 $\Delta t$；一次 inference 要 $\delta$，折合 $d=\lfloor\delta/\Delta t\rfloor$ 个 controller step。RTC 论文指出，$\delta\le\Delta t$（在两个 controller step 之间算完）对现在的 VLA 几乎不可能。

**Synchronous**：执行完 $s$ 步再开始算，robot 停 $\delta$。Robot 在动的时间比例是 $s/(s+d)$。取 $\Delta t=20$ ms、$s=25$：$\delta=100$ ms 时 $d=5$，比例 $25/30=83\%$；$\delta=300$ ms 时 $d=15$，比例 $25/40=62.5\%$。这两个 $\delta$ 大致就是 RTC 论文真实实验的两端：π0.5 本身约 76 ms，加上局域网的 10 到 20 ms 约 100 ms；他们再人为注入 +100 ms 和 +200 ms 的 delay，最长的一档约 300 ms。停顿不只是慢：robot 每 0.5 s 停一下，dynamics 和 training data 里的连续动作不一样，state 落到了 training distribution 之外。

**Naive asynchronous**：提前 $d$ 步开始算，算完立刻换上新 chunk，robot 不停。问题在新 chunk 是对一个新 observation 重新 sample 的，它可能选了另一个 mode（旧 chunk 从 obstacle 上方绕，新 chunk 从下方绕），切换那一步 action 跳变，acceleration 很大，同样落到 training distribution 之外。

### Real-time chunking：把切换写成 inpainting

RTC 的出发点是一个事实：inference 进行的这 $d$ 步里，robot 执行的是旧 chunk，这 $d$ 个 action 无论新 chunk 怎么算都已经确定。所以新 chunk 的前 $d$ 个 action 应当等于旧 chunk 的对应部分，后面的部分要和它接得上。这是一个 inpainting 问题：给定 sequence 的一部分，生成其余部分。

对 flow matching 的 policy，这不需要重新 train。在每一步 denoising，先由当前的 noisy chunk $A^\tau$ 和 velocity $v$ 估计最终的 chunk

$$\hat A^1=A^\tau+(1-\tau)\,v(A^\tau,o,\tau)$$

再把 $\hat A^1$ 在指定位置上拉向目标 $Y$（旧 chunk 剩下的 action），把这个拉力通过 vector-Jacobian product 加到 velocity 上：

$$v_{\text{guided}}=v+\min\Big(\beta,\ \frac{1-\tau}{\tau\,r_\tau^2}\Big)\,(Y-\hat A^1)^\top\mathrm{diag}(W)\,\frac{\partial\hat A^1}{\partial A^\tau},\qquad r_\tau^2=\frac{(1-\tau)^2}{\tau^2+(1-\tau)^2}$$

$W$ 是每个位置的 weight（mask）。$\min(\beta,\cdot)$ 把 guidance 的强度截住：control 里 denoising 步数少，不截会不稳定。

$W$ 不取 0/1，而是 soft mask：

$$W_i=\begin{cases}1,& i<d\\[2pt] c_i\,\dfrac{e^{c_i}-1}{e-1},\quad c_i=\dfrac{H-s-i}{H-s-d+1},& d\le i<H-s\\[6pt] 0,& i\ge H-s\end{cases}$$

前 $d$ 个冻结；中间那段旧 chunk 也有预测、但还没确定，guidance 按 exponential 递减；最后 $s$ 个旧 chunk 没有覆盖，完全新生成。取 $H=50$、$s=25$、$d=5$：

| $i$ | 0–4 | 5 | 8 | 12 | 16 | 20 | 24 | 25–49 |
|---|---|---|---|---|---|---|---|---|
| $W_i$ | 1 | 0.882 | 0.587 | 0.309 | 0.133 | 0.037 | 0.001 | 0 |

$i=5$ 那一格：$c_5=(25-5)/21=0.952$，$W_5=0.952\times(e^{0.952}-1)/(e-1)=0.952\times1.591/1.718=0.882$。

::fig[ee4706-rtc] 旧 chunk 执行完 25 步时取新的 observation，5 步后新 chunk 可用。上面：naive async 在可用的那一步直接切换，action 跳到另一个 mode。下面：RTC 的新 chunk 前 5 步和旧 chunk 一致，之后按 soft mask 逐渐交给新的预测。曲线是示意。

只冻结前 $d$ 个（hard mask）也能保证不跳变。论文的 simulation 里 hard mask 整体略差于 soft mask，$d$ 小的时候差得更明显：$d$ 小时冻结区很短，hard mask 几乎只剩“从头生成”，soft mask 还能用上整段重叠里旧 chunk 的信息。附录比较了 mask 怎样衰减，exponential 最好，linear 很接近。

运行时，inference 在后台一直循环，controller 每 $\Delta t$ 取一个 action、交上新的 observation，手里总有 action。$d$ 事先不知道，取最近 $b$ 次 delay 里的最大值，保守地估计；执行的步数取 $s=\max(d,\,s_{\min})$。真实 robot 上论文取 $b=10$、$s_{\min}=25$、$\beta=5$、5 步 denoising（附录的 ablation 说 $\beta$ 超过 5 不再有收益）。

RTC 不是免费的。每一步 denoising 都要对 $\hat A^1$ 求一次 vector-Jacobian product，也就是对 network 做一次 backward。论文在 RTX 4090 上量到，每步 denoising 从 14 ms 变成 35 ms，整个 model 从 76 ms 变成 97 ms。这 21 ms 换来的是不用停。

论文的真实实验用 π0.5、$H=50$、$\Delta t=20$ ms，6 个双臂任务（点蜡烛、插拔 ethernet 线、mobile 铺床、叠衬衫、从篮子里取衣服逐件叠好、mobile 把台面上 4 样东西放进 sink），每个任务每种方法 10 次，共 480 个 episode、约 28 小时。指标是 throughput：完成的任务比例除以 episode 的时长。结果是：

- RTC 在所有 delay 下 throughput 最高，在 +100 ms 和 +200 ms 两档的差异统计显著；注入的 delay 不让 RTC 变差，synchronous 随 delay 线性下降。
- 去掉 synchronous 停下来等的时间、只数 controller 真正在走的 step，RTC 仍然更快完成，所以差别不全来自“不停”。
- 两种 temporal ensembling 在 +100 ms 和 +200 ms 下根本跑不了，robot 振荡得太厉害，触发了保护性的停机。
- 总 delay 超过 300 ms（prediction horizon 的 30%）时，RTC 仍能完成点火柴这种精细动作；Figure 1 的 caption 说同样的动作比 synchronous 快约 20%。

:::wrong 把新旧 chunk 重叠的部分平均一下（temporal ensembling），同样能消掉跳变
平均能让 action 连续，但旧 chunk 从上方绕、新 chunk 从下方绕时，平均出来的是从正中间穿过去，正是 obstacle 所在的地方（[RB4301 第 6 站](../courses/RB4301.html#gen)那个 MSE 撞墙的例子是同一回事）。RTC 的 inpainting 改变的是 sampling 本身：新 chunk 在 denoising 时就被引导到和冻结部分一致的那个 mode 上，得到的是一个完整的、属于某个 mode 的 sample，而不是两个 mode 的平均。实测也是这样：RTC 论文的 simulation 是故意做成 multimodal 的，temporal ensembling 在 $d=0$ 时就表现很差；真实 robot 上它在大 delay 下振荡到触发保护性停机。π0 论文也试过对 chunk 做 ensembling，发现会损害 policy 的表现，最后选择不做平均、open-loop 地执行每个 chunk。
:::

:::edge Delay 最多能有多大
按 soft mask 的写法，新的 observation 在旧 chunk 执行完 $s$ 步时取得；inference 的 $d$ 步里继续执行旧 chunk 的第 $s$ 到 $s+d-1$ 个 action，它们就是新 chunk 冻结的前 $d$ 个，必须在旧 chunk 里，所以 $s+d\le H$。又因为执行的步数取 $s=\max(d,s_{\min})\ge d$，得到 $2d\le H$，即 $d\le H/2$。论文的 simulation（Kinetix 里 12 个动态任务）用 $H=8$，delay 只测到 4，论文说 4 是 $H=8$ 时支持的最大值，原因就在这里。真实实验 $H=50$、$s_{\min}=25$，最长一档 $d\approx16$，在 25 之内。Delay 超过 $H/2$ 时只能加长 chunk，或者把 model 做快。
:::

:::back
在 LeRobot 里真的跑 asynchronous inference（policy server 与 robot client、`refill_seconds`、aligned merge、本地 RTC）见 [HF-LEROBOT 第 6 站](../courses/HF-LEROBOT.html#async)，它从 queue 的角度推出了同一个 $d\le H/2$。Action chunking 本身和它为什么减轻 compounding error 在 [RB4301 第 7 站](../courses/RB4301.html#chunk)；flow matching 的 velocity field 和 sampling 在 [MIT-6.S184](../courses/MIT-6.S184.html)。Latency 怎样进入 stopping distance 见[第 1 站](#arch)；一次对话回合的 latency 怎样一段段相加、streaming 时为什么只剩每段的第一块，见[第 9 站](#speak)。

## [listen] Listen：audio 表示、CTC 与 Whisper

:::skip
能算出一句 1.5 s 的 command 在 Whisper 里是多少个 sample、frame 和 audio token，能对一个 3 个 frame 的小例子算出 CTC 的 $p(\ell\mid x)$ 并说出 best path decoding 为什么会给错答案，能说出 Whisper 的 30 s window、token 格式和 long-form heuristic 对 robot 各意味着什么，就可以去第 9 站。
:::

### Robot 听错了

用户站在 robot 前面 2 m，说了一句 1.5 s 的“Pick up the red cup.”。旁边有 robot 自己的风扇声，房间里有 reverberation。拿 Whisper 做 speech recognition，可能出的错，Whisper 论文在 limitation 里列得很具体：long-form 的 transcription 会卡在一个 repeat loop 里，会漏掉一段 audio 开头或结尾的几个 word，还会 hallucinate，output 一段和 audio 完全无关的 transcript。另一条是 robustness 的数字：它在 LibriSpeech test-clean 上的 word error rate（WER）是 2.7%，在 AMI 会议录音的 single distant microphone（SDM1）条件下是 36.4%。Robot 的 microphone 正是一个离说话人很远的 microphone。

每一种错都和 audio 怎样变成数、model 怎样从这些数里读出文字有关。这一站顺着这条链走：microphone 上的电压，变成 sample，变成 log-mel spectrogram，再由 CTC 或 attention encoder-decoder 变成文字，最后回到多个 microphone 怎样帮忙。

### 一段 audio 是一串 sample

Microphone output 的是连续的电压。每秒取 16000 次值，sampling rate $f_s=16$ kHz，每个值存成 16-bit 的 integer，范围是 $-32768$ 到 $32767$。SLP3 第 15 章说，microphone 录的 speech 一般用 16 kHz，电话只传 4 kHz 以下的 frequency，用 8 kHz。能表示的最高 frequency 是 sampling rate 的一半（Nyquist frequency），16 kHz 对应 8000 Hz，为什么是一半见 [EE2023 第 7 站](../courses/EE2023.html#sampling)。

Whisper 的 `load_audio` 就是这样读的：用 ffmpeg 把任何文件转成 mono、16 kHz、int16，再除以 32768 变成 $[-1,1)$ 之间的 float。所以那句 1.5 s 的 command 是

$$1.5\times16000=24000$$

个数，Whisper 一个 30 s 的 window 是 $30\times16000=480000$ 个数。

直接把 24000 个 sample 交给 model 不好用。单独一个 sample 说明不了任何事；一个 vowel 和另一个 vowel 的区别在于几十 ms 之内哪些 frequency 上有 energy，这要在一小段 sample 上做 Fourier analysis 才看得出来。

### Frame 与 spectrum

把 sequence 切成互相重叠的小段，每段叫一个 frame。SLP3 和 Whisper 用的都是 25 ms 的 window、10 ms 的 hop：

$$0.025\times16000=400\ \text{个 sample 一个 frame},\qquad0.010\times16000=160\ \text{个 sample 往前挪一次}$$

相邻两个 frame 重叠 $400-160=240$ 个 sample。每个 frame 先乘一个 window function，让两端平滑地降到 0，免得 Fourier analysis 把截断处的跳变当成高 frequency。SLP3 写的是 Hamming window：

$$w[n]=0.54-0.46\cos\frac{2\pi n}{L},\qquad 0\le n\le L-1$$

Whisper 的 code 用的是 Hann window（`torch.hann_window(400)`），形状相近。然后做 DFT：

$$X[k]=\sum_{n=0}^{N-1}x[n]\,e^{-j\frac{2\pi}{N}kn}$$

Whisper 取 $N=400$，real signal 的 spectrum 左右对称，只留 $k=0,\dots,200$ 共 201 个 bin。第 $k$ 个 bin 对应 frequency $k\cdot f_s/N=40k$ Hz，从 0 排到 8000 Hz，间隔 40 Hz。每个 bin 取 power $|X[k]|^2$。

数一下 frame 的个数。`torch.stft` 默认在两端补齐，$T$ 个 sample 给出 $1+T/160$ 个 frame，Whisper 再扔掉最后一个：1.5 s 是 $1+24000/160-1=150$ 个 frame，30 s 是 $480000/160=3000$ 个，正是 code 里的 `N_FRAMES = 3000`。

::fig[ee4706-frames] 一段 0.3 s 的合成 audio：前一半是 150 Hz 的 harmonic，在 700、1200、2600 Hz 附近加强（像一个 vowel），后一半是 4 kHz 以上的 noise（像“s”）。25 ms 的 window 每次挪 10 ms，每挪一次，下面的 log-mel spectrogram 多出一列。看 vowel 在低 channel 上是几条横纹，“s”的 energy 全在最上面几十个 channel。

### Mel filterbank 与 log

201 个 bin 还要再压成 80 个 channel。压法照着人耳：人对低 frequency 的差别比对高 frequency 敏感。SLP3 给的 mel scale 是

$$\text{mel}(f)=1127\ln\Big(1+\frac{f}{700}\Big)$$

代几个数：$\text{mel}(500)=607.4$，$\text{mel}(1000)=1000.0$，$\text{mel}(4000)=2146.1$，$\text{mel}(8000)=2840.0$。0 到 500 Hz 在 mel scale 上占 607 个单位，4000 到 8000 Hz 只占 $2840.0-2146.1=694$ 个。在 mel scale 上等间隔地放一排三角形的 filter，每个 filter 把它覆盖的那几个 bin 的 power 加权求和，低 frequency 处 filter 又窄又密，高 frequency 处又宽又稀。

Whisper 实际用的 filterbank 存在仓库的 `mel_filters.npz` 里，是 `librosa.filters.mel(sr=16000, n_fft=400, n_mels=80)` 生成的（librosa 默认的 mel scale 在 1 kHz 以下是 linear 的，以上是 logarithmic 的，和上面的 formula 不完全一样，形状相同）。打开数一下：80 个 filter 里，峰值在 1000 Hz 以下的有 26 个，在 4000 Hz 以上的有 18 个；第 10 个 filter 只在 400 Hz 和 440 Hz 两个 bin 上非零，第 79 个横跨 7440 到 7960 Hz 的 14 个 bin。低端的 filter 间隔大约 37 Hz，比 40 Hz 的 bin 还细，所以有几对相邻的 filter 峰值落在同一个 bin 上（280 Hz、800 Hz 各有两个）：25 ms 的 window 决定了 frequency 分辨率最多是 40 Hz，再细的 filter 也分不出来。

::fig[ee4706-melbank] Whisper 的 80 个 mel filter（从仓库里的 `mel_filters.npz` 读出来画的），横轴是 201 个 bin 的 frequency。看低 frequency 上一个 filter 只盖一两个 bin，8 kHz 附近一个 filter 盖十几个。

最后取 log。Whisper 的三行 code：取 $\log_{10}$（先把小于 $10^{-10}$ 的值抬到 $10^{-10}$）；比整个 window 的最大值低 8 以上的都截到“最大值减 8”，也就是只保留 80 dB 的 dynamic range；再算 $(x+4)/4$，让数值大致落在 $[-1,1]$，论文说 input 被 globally scale 到 $-1$ 和 1 之间、mean 接近 0。

SLP3 给取 log 的三个理由：人对 signal level 的反应本来就是 logarithmic 的；人对大 amplitude 上的小差别不敏感；取 log 之后，嘴和 microphone 的距离变化引起的 power 变化对 feature 的影响小了。最后一条可以算。设 free field 里 power 和距离的平方成反比，用户从 0.5 m 退到 2 m，到达 microphone 的 power 变成 $1/16$。在 linear 的 mel spectrogram 上，这是每个值都乘以 $1/16$；在 log 之后，是每个 channel 都减去 $\log_{10}16=1.204$，再除以 4，变成整体平移 $0.301$。一个乘法因子变成了一个所有 channel 共有的常数，network 很容易学会不理它。

Whisper 的 input 因此是一个 $80\times3000$ 的 matrix。它的第一层是两个 filter width 为 3 的 convolution（GELU activation），第二个 stride 为 2，把 3000 个 frame 变成 1500 个 audio token，每个 token 代表 20 ms，再加上 sinusoidal position embedding，进 Transformer encoder。

### 从 frame 到文字：不知道哪个 frame 对应哪个字母

1.5 s 是 150 个 frame，“pick up the red cup”是 19 个 character。SLP3 第 16 章给的比例：自然对话里一个英文 word 大约 250 ms，即 25 个 frame，平均 5 个字母、1.3 个 BPE token，所以 frame 数是字母数的约 5 倍、BPE token 数的约 19 倍。Training data 只有成对的 (audio, transcript)，没有人标“第 37 到 41 个 frame 是 p”。早期的 HMM-DNN system 为此要有 pronunciation lexicon、phone 级别的 alignment 和一整套迭代的 recipe（CS224S Lecture 10 就是从这里引出 CTC 的）。

两种做法绕过了 alignment：CTC 把所有可能的 alignment 都加起来；attention encoder-decoder 让 decoder 每生成一个 token 时自己去 encoder 的 output 里找该看哪里。

### CTC：对所有 alignment 求和

Graves 等人 2006 年的做法：network 在每个 frame 上 output 一个 softmax，类别是全部 label 再加一个 **blank**（记作 $-$），共 $|L|+1$ 个。$y^t_k$ 是第 $t$ 个 frame 上 output $k$ 的 probability。长度为 $T$ 的一条 path $\pi$（每个 frame 一个 symbol）的 probability 是

$$p(\pi\mid x)=\prod_{t=1}^{T}y^t_{\pi_t}$$

再用一个 many-to-one 的 map $\mathcal B$ 把 path 变成 label sequence：先合并相邻的重复 symbol，再删掉所有 blank。论文的例子是 $\mathcal B(a{-}ab{-})=\mathcal B({-}aa{-}{-}abb)=aab$。Blank 的必要性看 SLP3 的例子：没有 blank 时“dinner”里的 nn 会被合并成“diner”；有了 blank，`d i n - n e r` 折叠后是“dinner”。一个 label sequence $\ell$ 的 probability 是所有折叠成它的 path 之和：

$$p(\ell\mid x)=\sum_{\pi\in\mathcal B^{-1}(\ell)}p(\pi\mid x)$$

Training 最小化 $-\ln p(z\mid x)$，$z$ 是正确的 transcript。不需要知道哪个 frame 是哪个字母，所有 alignment 都算进去了。

拿 CS224S 用的那个最小的例子算一遍：$T=3$，label 只有 H 和 I，target 是“HI”。设 network 的三个 frame 的 output 是

| | H | I | $-$ |
|---|---|---|---|
| $t=1$ | 0.6 | 0.1 | 0.3 |
| $t=2$ | 0.4 | 0.3 | 0.3 |
| $t=3$ | 0.1 | 0.4 | 0.5 |

$3^3=27$ 条 path 里，折叠成“HI”的有 5 条（CS224S 的 slide 列的就是这 5 条）：

| Path | 乘积 |
|---|---|
| H I $-$ | $0.6\times0.3\times0.5=0.090$ |
| H $-$ I | $0.6\times0.3\times0.4=0.072$ |
| $-$ H I | $0.3\times0.4\times0.4=0.048$ |
| H H I | $0.6\times0.4\times0.4=0.096$ |
| H I I | $0.6\times0.3\times0.4=0.072$ |

加起来 $p(\text{HI}\mid x)=0.378$，loss 是 $-\ln0.378=0.973$。

真实的 utterance 不能这样枚举：“pick up the red cup”用 26 个字母、空格和 blank 共 29 个 symbol，150 个 frame 有 $29^{150}\approx10^{219}$ 条 path。Graves 用 dynamic programming。先把 target 改写成 $\ell'$：开头、结尾和每两个 label 之间插一个 blank，长度 $2|\ell|+1$。“HI”变成 $\ell'=(-,\text{H},-,\text{I},-)$，5 个 state。Forward variable $\alpha_t(s)$ 是“前 $t$ 个 frame 的 path 折叠后正好是 $\ell'$ 的前 $s$ 个 state”的 probability 之和。Path 只能从 blank 或第一个 label 开始：

$$\alpha_1(1)=y^1_{-},\qquad\alpha_1(2)=y^1_{\ell_1},\qquad\alpha_1(s)=0\ (s>2)$$

每往后一个 frame，path 可以停在同一个 state（重复或继续 blank），可以走到下一个 state，也可以跳过中间的一个 blank，直接到下一个 label。跳 blank 在两种情况下不允许：当前 state 本身是 blank；当前 label 和两格之前的 label 相同（“nn”中间的 blank 不能跳，否则就合并了）。记 $\bar\alpha_t(s)=\alpha_{t-1}(s)+\alpha_{t-1}(s-1)$：

$$\alpha_t(s)=\begin{cases}\bar\alpha_t(s)\,y^t_{\ell'_s}, & \ell'_s=-\ \text{或}\ \ell'_{s-2}=\ell'_s\\[2pt]\big(\bar\alpha_t(s)+\alpha_{t-1}(s-2)\big)\,y^t_{\ell'_s}, & \text{其他}\end{cases}$$

最后的 path 要停在最后一个 label 或最后一个 blank 上：$p(\ell\mid x)=\alpha_T(|\ell'|)+\alpha_T(|\ell'|-1)$。

代进上面的表。$t=1$：$\alpha_1=(0.3,\,0.6,\,0,\,0,\,0)$。$t=2$ 逐个 state 算：

- $s=1$（$-$）：$0.3\times y^2_-=0.3\times0.3=0.09$
- $s=2$（H）：$(0.6+0.3)\times0.4=0.36$；它前面两格是 state 0，不存在，没有跳的那一项
- $s=3$（$-$）：$(0+0.6)\times0.3=0.18$
- $s=4$（I）：$(0+0+0.6)\times0.3=0.18$，第三项是从 H 跳过 blank
- $s=5$（$-$）：$(0+0)\times0.3=0$

$t=3$ 同理：$\alpha_3=(0.045,\,0.045,\,0.27,\,0.288,\,0.09)$，其中 $\alpha_3(4)=(0.18+0.18+0.36)\times0.4=0.288$，$\alpha_3(5)=(0+0.18)\times0.5=0.09$。所以 $p(\text{HI}\mid x)=0.288+0.09=0.378$，和枚举的结果一样。表的大小是 $T\times(2|\ell|+1)$：“pick up the red cup”是 $150\times39=5850$ 个格子。

::fig[ee4706-ctc] “HI”的 CTC trellis：5 个 state、3 个 frame，格子里是 $\alpha_t(s)$。看每一列只由前一列算出，跳过 blank 的斜线只连到 label。最后一列的两个格子相加就是 0.378。

### Decoding：最好的 path 不一定给出最好的 transcript

Training 之后要 output 一个 transcript。最省事的是 best path decoding：每个 frame 取 probability 最大的 symbol，再折叠。上面的例子里三个 frame 的 argmax 是 H、H、$-$，path 的 probability 是 $0.6\times0.4\times0.5=0.12$，是 27 条里最大的，折叠后是“H”。可是把折叠成“H”的 6 条 path 全加起来，$p(\text{H}\mid x)=0.12+0.09+0.06+0.024+0.012+0.009=0.315$，比 $p(\text{HI}\mid x)=0.378$ 小。最可能的单条 path 和最可能的 label sequence 不是一回事，因为“HI”的 probability 分散在 5 条差不多大的 path 上。Graves 的论文明说 best path 不保证找到最可能的 label，另给了 prefix search decoding；在 TIMIT 上，best path 的 label error rate 是 31.47%，prefix search 是 30.51%。同一张表里，context-dependent HMM 是 35.21%，BLSTM/HMM 是 33.84%：CTC 不需要事先切好的 segmentation，就比这些 system 好。

CTC 有一个硬伤：给定 $x$，每个 frame 的 output 互相 conditionally independent，$p(\pi\mid x)$ 是逐个 frame 乘出来的。所以它学不到“前一个字母是什么，后一个字母多半是什么”，不会隐式地学会 language model。CS224S 的 slide 给了 WSJ 上不带 lexicon 和 language model 的 CTC output：“REHBILITATION”“BETIN EPARTMENTS”。实际 system 在 decoding 时再加一个 language model 的分数（SLP3 的 $\log P_{\text{CTC}}+\lambda_1\log P_{\text{LM}}+\lambda_2L(Y)$）。

它的好处也来自同一个结构：每个 frame 的 output 只依赖 encoder 在这个 frame 的 output，可以从左到右一个 frame 一个 frame 地出字。SLP3 正是因此说 CTC 适合在用户说话的同时识别。能不能真的 streaming，还要看 encoder 看不看未来的 frame；Graves 用的是 bidirectional LSTM，要读完整段才有 output（这一点是我从结构推的）。SLP3 还讲了 RNN-Transducer：在 CTC 的 encoder 上加一个 predictor network，它读已经 output 的非 blank token，于是每一步的 distribution 变成 $p(a_t\mid h_t,y_{<u_t})$，去掉了 conditional independence，又保留了逐个 frame output 的能力。

### Attention encoder-decoder：Whisper

另一条路不要 blank，也不求和。Decoder 是一个以 audio 为条件的 language model：

$$p(y_1,\dots,y_n\mid X)=\prod_{i=1}^{n}p(y_i\mid y_1,\dots,y_{i-1},X)$$

每一层 decoder 有一个 cross-attention，query 来自 decoder，key 和 value 来自 encoder 的 output（Transformer 本身见 [CS4248 第 6 站](../courses/CS4248.html#attn)）。Decoder 每生成一个 token，自己决定看 audio 的哪一段，alignment 由 attention 隐式地学出来。SLP3 的比较：这种 model 一般更准；但 encoder 的 self-attention 看整段 audio，必须等 audio 全部到齐才能开始 decode，不能 streaming。

Whisper 是这种结构，它和之前的 system 的差别主要在 data：从网上收集了 68 万小时带 transcript 的 audio（weak supervision），切成 30 s 的 segment，每段配上落在这 30 s 里的那部分 transcript。没有 speech 的 segment 以较低的比例也放进去，作为 voice activity detection 的 training data。Model 的设定上一小节已经算过：16 kHz、80-channel 的 log-magnitude mel spectrogram、25 ms 的 window、10 ms 的 stride、两层 convolution、sinusoidal position embedding。English-only 的 model 用 GPT-2 的 byte-level BPE（见 [CS4248 第 1 站](../courses/CS4248.html#token)），multilingual 的 model 在同样大小的 vocabulary 上重新 fit。五种大小：

| Model | Layer | Width | Head | Parameter |
|---|---|---|---|---|
| Tiny | 4 | 384 | 6 | 39M |
| Base | 6 | 512 | 8 | 74M |
| Small | 12 | 768 | 12 | 244M |
| Medium | 24 | 1024 | 16 | 769M |
| Large | 32 | 1280 | 20 | 1550M |

仓库的 README 另有一个 809M 的 turbo，说它是 large-v3 的优化版本，在 A100 上的相对速度约是 large 的 8 倍。

**30 s 的 window。** Encoder 只吃 30 s。`pad_or_trim` 把不到 30 s 的 audio 补 0 到 480000 个 sample，超过的截掉。那句 1.5 s 的 command 进 encoder 时是 3000 个 frame、1500 个 audio token，其中只有 $1.5/0.02=75$ 个 token 对应有声音的部分，占 5%，另外 1425 个是补的 0，照样每一层都要算。所以 Whisper 的 encoder 处理一句短 command 的计算量和处理一段 30 s 的话一样；第 9 站算 latency 时会回到这一点。

::fig[ee4706-whisperwin] 一句 1.5 s 的 command 在 Whisper 里的样子。上面：补到 30 s 的 window，3000 个 frame 经 stride 2 的 convolution 变成 1500 个 audio token，有声音的只占最左边的 75 个。下面：decoder 要 output 的 token sequence，前几个 special token 指定任务，timestamp 每 20 ms 一格。

**Token 格式。** 一个 model 同时做 multilingual 的 transcription、翻译成英文、language identification 和 voice activity detection，靠的是让 decoder 先读或先写几个 special token：`<|startoftranscript|>`；一个 language token（共 99 种）；没有 speech 时 output `<|nospeech|>`；`<|transcribe|>` 或 `<|translate|>`；不要 timestamp 时加 `<|notimestamps|>`；否则每段 caption 的前后各有一个 timestamp token，时间相对于这个 30 s 的 segment，quantize 到 20 ms；最后是结束 token（论文叫 `<|endoftranscript|>`，code 里是 `<|endoftext|>`）。前一段的 transcript 可以作为 context 放在最前面（code 里用 `<|startofprev|>` 标出），这部分不算 loss。

上面那句 command，decoder 要 output 的是

```
<|startoftranscript|> <|en|> <|transcribe|> <|0.00|> Pick up the red cup. <|1.50|> <|endoftext|>
```

30 s 以 20 ms 为一格，timestamp token 从 `<|0.00|>` 到 `<|30.00|>` 共 $30/0.02+1=1501$ 个，tokenizer 的 code 里正是 `range(1501)`。`<|nospeech|>` 的 probability 是 decoder 在 `<|startoftranscript|>` 之后那一步读出来的。

**Long-form 的 heuristic。** 超过 30 s 的 audio，Whisper 一次读不了。论文的做法是连续地 transcribe 30 s 的 segment，按 model 预测的 timestamp 决定 window 往前挪多少；一个 window 里的错会传给后面的 window。为了让这件事可靠，论文 4.5 节加了几条规则，仓库 `transcribe.py` 里的默认值和论文一致：

- 用 5 个 beam 的 beam search（beam search 本身见 [CS4248 第 7 站](../courses/CS4248.html#pretrain)），减少 greedy decoding 里更常见的 repetition looping。
- Temperature fallback：先用 temperature 0 decode；如果 output 的平均 log probability 低于 $-1$，或者 gzip compression ratio 高于 2.4，就把 temperature 加 0.2 再来，直到 1.0。
- `<|nospeech|>` 的 probability 单独用不可靠。论文把它和 log probability 合起来用：`<|nospeech|>` 的 probability 高于 0.6，而且平均 log probability 低于 $-1$，才把这段当作没有 speech、跳过。
- Temperature 低于 0.5 时才把前一个 window 的 transcript 当作 prompt。
- 第一个 timestamp token 限制在 0.0 到 1.0 s 之间，因为 model 有时会忽略一段 audio 开头的几个 word。

论文的 ablation 里，只用 greedy decoding 时 long-form 的平均 WER 是 11.0，这些规则全加上是 10.0。

Compression ratio 为什么能抓 repetition loop？`transcribe.py` 里的定义是 text 的 UTF-8 byte 数除以 `zlib.compress` 之后的 byte 数。重复的 text 压得很小。拿“Pick up the red cup and put it on the table.”（44 byte）算：单独一句，压缩后反而更长（有 header 的开销），ratio 是 0.90；一句 163 byte 的正常长句是 1.41；同一句连说 3 遍，134 byte 压成 53 byte，ratio 是 2.53，超过 2.4，触发 fallback。

:::wrong Whisper 在 LibriSpeech test-clean 上 WER 只有 2.7%，放在 robot 上大概也只错 3% 的 word
LibriSpeech 是安静环境里朗读有声书的录音。Whisper 论文 Table 2 拿 wav2vec 2.0 Large 对比：两者在 LibriSpeech test-clean 上都是 2.7，但在其他 speech recognition 数据集上平均是 29.3 对 12.8，Whisper 的 error 平均少 55.2%。同一张表里，AMI SDM1（会议室里的 single distant microphone）上 wav2vec 2.0 是 67.6，Whisper 是 36.4。也就是说，在 clean 的 benchmark 上一样好的两个 model，到了 far-field 的 microphone 上一个错三分之二的 word，一个错三分之一。Robot 离用户一两米、自己还在发出 noise，它的条件比 LibriSpeech 更接近 AMI SDM1。Noise 的实验也说明同一件事：加 white noise 或 pub noise 时，SNR 40 dB 时很多在 LibriSpeech 上 train 的 model 比 zero-shot 的 Whisper 好；pub noise 的 SNR 低于 10 dB 时，它们全都比 Whisper 差。要知道 robot 上的 WER，只能在 robot 上、在它的环境里录一批 audio 测。
:::

:::edge 不同版本的 Whisper，mel channel 数不一样
论文写的是 80 个 channel。SLP3 讲 Whisper 时写的是 128 个，这是 large-v3 的设定；仓库的 `mel_filters.npz` 里同时存了 `mel_80` 和 `mel_128`，`log_mel_spectrogram` 只接受这两种。README 的示例 code 写的是 `n_mels=model.dims.n_mels`，从 model 里读，不要自己写死 80。现在 `load_model("large")` 下载的就是 large-v3 的 weight。
:::

:::edge 没有 speech 的时候
论文自己说 `<|nospeech|>` 的 probability 单独用来判断有没有 speech 不可靠，而 hallucination（output 一段和 audio 无关的 transcript）又是它列出的 failure mode。所以 robot 上一般在前面先放一个专门的 voice activity detector，只把有 speech 的片段交给 Whisper（第 9 站的 silero-vad）。Whisper-Streaming 的论文也测了 VAD 的影响：英语的原声演讲关掉 VAD 质量基本不变，同声传译那种停顿多的 audio，打开 VAD 时 WER 在 0.1 s 的 chunk 下降约 3 个百分点。
:::

### 多个 microphone：把一个方向的声音加强

Whisper 的 noise 实验说，SNR 低于 10 dB 是一道坎。Robot 上提高 SNR 的硬件办法是在头上装几个 microphone。设 4 个 microphone 排成一条线，间距 $d=2$ cm，用户离得足够远，声音到达 array 时可以看成 plane wave，方向和 array 的轴成 $\theta=60^\circ$。相邻两个 microphone 收到同一个 wavefront 的时间差（time difference of arrival）是

$$\tau=\frac{d\cos\theta}{c}=\frac{0.02\times0.5}{343}=29.2\ \mu\text{s}$$

$c=343$ m/s 是空气里的 speed of sound。16 kHz 下一个 sample 是 62.5 μs，所以 $\tau$ 只有 0.47 个 sample；声音沿着轴来（$\theta=0$）时也只有 58.3 μs，0.93 个 sample。

Delay-and-sum beamformer 把每个 microphone 的 signal 按各自的时间差 align 再平均（Aalto 的 speech processing 教材的写法）：

$$\hat x(t)=\frac1K\sum_{k=1}^{K}x_k(t-t_{x_k})$$

目标方向的声音对齐之后同相相加，其他方向的声音错开，部分抵消。时间差不到一个 sample，不能靠挪整数个 sample 来 align；在 frequency domain 里给第 $k$ 个 microphone 的每个 bin 乘一个 phase $e^{j2\pi f t_{x_k}}$ 就能做 fractional delay（这一步是我补的做法）。

能好多少？UiO INF5410 的讲义给出：noise 在各个 sensor 之间 uncorrelated 时，$M$ 个 sensor 的 SNR 是单个的 $M$ 倍，$\text{SNR}=M\sigma_s^2/\sigma_n^2$。4 个 microphone 是 $10\log_{10}4=6.0$ dB。如果单个 microphone 上的 SNR 是 5 dB，align 再平均之后是 11 dB，跨过了 Whisper 论文里那道 10 dB 的坎（这个组合是为这一页设定的）。

这个 6 dB 有前提。它对 microphone 自己的电路 noise 成立，因为每个 microphone 的 noise 各不相关。Robot 自己的风扇和 motor是一个固定方向的声源，它在 4 个 microphone 上是同一个 signal 的不同 delay，delay-and-sum 只能靠方向的差别压它。而方向的分辨能力受 array 的尺寸限制：beam 的宽度大约是 $\lambda/D$，$D=3d=6$ cm。500 Hz 的 wavelength 是 $343/500=68.6$ cm，比 array 大十倍，这个 array 在 500 Hz 上几乎没有方向性；4 kHz 的 wavelength 是 8.6 cm，也只比 $D$ 大一点。另一个约束是 spatial aliasing：间距要满足 $d\le\lambda/2$（Aalto 教材的 code 用这个条件检查）。要对 8 kHz 以下都成立，$\lambda=343/8000=4.29$ cm，$d\le2.14$ cm，所以上面取了 2 cm。

## [speak] Speak 与对话 loop：endpointing、TTS、barge-in 与 latency

### 回答慢：2.6 s 从哪里来

Skantze 和 Irfan 2025 年在 Furhat（一个背投式的拟人 robot head）上做了一个 39 人的实验。Baseline 是最常见的 cascade：Google Speech-to-Text 做 speech recognition，同时负责判断用户说完了没有；判断的依据是一段固定长度的 silence；然后把 transcript 交给 gpt-3.5-turbo；回复交给 ElevenLabs 的 streaming TTS。从录音里量“用户说完”到“robot 开口”的时间，分布的峰值在 2.6 s。论文说这和各段加起来的预期相符：

$$\underbrace{1\ \text{s}}_{\text{silence threshold}}+\underbrace{0.5\ \text{s}}_{\text{LLM}}+\underbrace{1\ \text{s}}_{\text{TTS}}=2.5\ \text{s}$$

人和人说话时，turn 之间的 gap 可以短到 0.2 s；Moshi 论文引用 Stivers 等人 2009 年对 10 种语言的测量，平均是 230 ms。Robot 比人慢了十倍以上，而最大的一段是什么也没做的等待：用户已经说完了，system 还在等 silence 够 1 s。

::fig[ee4706-turn] Furhat baseline 的一次回合，从用户说完的那一刻算起。看三段首尾相接，robot 开口时已经过了 2.5 s；最下面一行是人，0.2 s 后已经在回答。

这一站按这个 loop 的顺序走：怎样知道用户在说话（VAD），怎样知道他说完了（endpointing），怎样一边听一边出字（streaming ASR），回复的第一句要多快（LLM），怎样把文字变回声音（TTS），用户打断 robot 时怎么办（barge-in），最后把各段的 latency 算一遍。

### VAD：这 32 ms 里有没有人在说话

Voice activity detection（VAD）对每一小段 audio 给出“有 speech”的 probability。silero-vad 的 README：16 kHz 下每次读 512 个 sample，即 $512/16000=32$ ms；一个 30 ms 以上的 chunk 在一个 CPU thread 上处理不到 1 ms；JIT model 大约 2 MB；training data 覆盖 6000 多种语言。所以 VAD 本身的计算几乎不占 latency。

把 probability 变成“开始”“结束”两个事件，用的是仓库里 `VADIterator` 的规则，有三个 parameter：`threshold` 默认 0.5，`neg_threshold` 默认 `threshold - 0.15` 即 0.35，`min_silence_duration_ms` 默认 100：

1. 还没在 speech 里时，某个 window 的 probability $\ge0.5$，就报告 speech 开始。
2. 在 speech 里时，probability 掉到 $0.35$ 以下，记下这一刻（`temp_end`），但先不报告结束。
3. 之后只要有一个 window 回到 $\ge0.5$，就把 `temp_end` 清掉，当作没停过。
4. 从 `temp_end` 起累计到 `min_silence` 那么长，才报告结束（结束时间往后补 30 ms 的 `speech_pad`）。

两个 threshold 中间的 0.35 到 0.5 是一段 hysteresis：probability 在这里时什么都不改变。只用一个 0.5 的 threshold 时，一个在 0.5 上下晃的 probability 会让 state 来回翻。

拿一个例子走一遍。用户说“Pick up the……red cup”：0.10 到 1.06 s 是“Pick up the”，中间在 0.46 到 0.62 s 有一个 word 和 word 之间的弱音，probability 掉到 0.42；1.06 到 1.50 s 停下来想了 0.44 s；1.50 到 2.14 s 是“red cup”。每个 32 ms 的 window 的 probability 是设定的示意值，规则按上面的 code 逐个 window 执行：

| 设定 | 报告的事件（检测到的时刻） |
|---|---|
| 0.5 / 0.35，`min_silence` 100 ms | 0.128 s 开始；1.216 s 结束；1.536 s 开始；2.304 s 结束 |
| 0.5 / 0.5（没有 hysteresis），100 ms | 0.128 s 开始；**0.608 s 结束**；0.640 s 开始；1.216 s 结束；…… |
| 0.5 / 0.35，`min_silence` 1000 ms | 0.128 s 开始；3.200 s 结束 |

第一行：0.42 落在两个 threshold 之间，没有影响；1.06 s 以后 probability 掉到 0.06，第一个低于 0.35 的 window 在 1.088 s 结束，`temp_end` 记在这里，再过 4 个 window（128 ms，第一个不小于 100 ms 的 window 整数倍）到 1.216 s 报告结束。第二行把 `neg_threshold` 也设成 0.5，那 5 个 0.42 的 window（160 ms）就够 100 ms 了，“Pick up the”在 0.608 s 被切成两段。第三行把一句话完整地收成一段，代价是用户 2.14 s 说完、system 3.2 s 才知道，晚了 1.06 s。

::fig[ee4706-vad] 同一串 probability，两种 `min_silence`。看 1.06 s 开始的那 0.44 s 停顿：100 ms 的设定在 1.216 s 就宣布说完，robot 会只拿着“Pick up the”去回答；1000 ms 的设定要等到 3.2 s。

### Endpointing：停顿到底是说完了，还是在想

VAD 只回答“有没有声音”。Endpointing 要回答“这个 turn 结束了没有”。SLP3 第 26 章说这件事难，原因有两个：noise，以及人常常在一个 turn 的中间停下来。上面的表正是这个两难：silence threshold 短，就在用户想词时插嘴；长，就每次都白等。Skantze 和 Irfan 的论文说得很直接，靠 silence threshold 的 system 要么 response delay 长，要么经常打断用户，缩短 response time 通常会提高 interruption rate。他们的 baseline 用 1 s，仍有 16.6% 的 system turn 被参与者标成“没让我说完”。

他们的做法是除了 silence，也看内容和 prosody：

- **VAP**（Voice Activity Projection）在约 1000 小时的电话对话上 train，读两个 channel 的 raw waveform（一个是用户，一个是 robot 自己），每秒预测约 10 次：接下来 0 到 600 ms、600 到 2000 ms 里分别是谁在说话。两个预测都偏向 robot（大于 0.5），并且用户最后一次 turn-holding 的信号之后至少过了 0.5 s，才允许 robot 接话。
- **TurnGPT** 是在文字对话上 train 的 GPT-2，读 incremental 的 transcript，打一个“这句话完整了”的分数。分数决定一个备用的 timeout：分数 $\ge0.3$ 时约 0.5 s，0.2 时 1 s，0.1 时 2 s，更低时 3 s。“Pick up the”这种明显没说完的句子分数低，robot 会多等；VAP 错过了 turn 的交接时，timeout 保证 robot 最终会开口。

结果（论文 Table I）：

| | Response time 的 mean | Median | Mode | Interruption rate |
|---|---|---|---|---|
| VAP + TurnGPT | 1.5 s | 1.5 s | 0.6 s | 6.9% |
| Baseline（1 s silence） | 2.2 s | 2.7 s | 2.6 s | 16.6% |

两个指标同时变好，因为判断的依据从“安静了多久”换成了“这句话和这段 prosody 像不像说完了”。39 个参与者里，偏好 baseline 的 9 人，没有偏好的 3 人，其余偏好新 system。

:::wrong 把 silence threshold 调小，robot 就回答得又快又不出错
上面的例子里，`min_silence` 从 1000 ms 调到 100 ms，句末的判定从 3.2 s 提前到 2.304 s，快了将近 0.9 s；同一个设定在 1.216 s 就把“Pick up the”当成了一整句话。用户在句中停 0.44 s 不罕见，threshold 要短于这类停顿才能快，短于它又必然切断这类句子。Silence 只有一个维度，两个要求在这一个维度上互相冲突。Skantze 和 Irfan 的 baseline 用了保守的 1 s，interruption rate 仍是 16.6%；把 interruption 和 delay 一起降下来，靠的是加进 silence 以外的信息。
:::

### Streaming ASR：一边听一边出字

[第 8 站](#listen)说过，Whisper 的 encoder 要看完整个 30 s 的 window。Macháček 等人 2023 年的 Whisper-Streaming 不改 model，改调用方式：

1. 每过 `MinChunkSize` 那么长的新 audio，就把它接到 buffer 后面，把**整个 buffer** 重新交给 Whisper。如果上一次计算比 `MinChunkSize` 还久，算完立刻开始下一次。
2. 每次得到一个新的 transcript。**LocalAgreement-2**：连续两次 output 的最长公共 prefix 算作 confirmed，以后不再改；后面的部分是 unconfirmed，下一次还可能变。
3. 已 confirmed 的最后 200 个 word 作为 prompt 传给下一次调用。Buffer 总是从一句话的开头开始；confirmed 的部分里出现句末标点时，就在那里把 buffer 剪掉；buffer 大约不超过 30 s。

一个设定的例子，用户说“Pick up the red cup and……”，`MinChunkSize` 0.5 s：

| Update | Buffer | Whisper 的 output | 和上一次的公共 prefix（confirmed） |
|---|---|---|---|
| 1 | 0 到 1.0 s | pick up the bread | （第一次，没有） |
| 2 | 0 到 1.5 s | pick up the red cup | pick up the |
| 3 | 0 到 2.0 s | pick up the red cup and | pick up the red cup |

第 1 次的“bread”是听到一半的“red”，第 2 次被改掉，从来没有 confirmed 过。代价是每个 word 至少要出现在两次 output 里，confirmed 总比 audio 晚一个以上的 chunk。

::fig[ee4706-agree] LocalAgreement-2 的三次 update。实心的是 confirmed，空心的是 unconfirmed。看“bread”只出现过一次，没等到第二次就被改了。

论文在 ESIC 的英语演讲上量了 latency：一个 word 被 output 的时刻减去它在 audio 里出现的时刻，每篇文档取平均。Large-v2、faster-whisper、16-bit float、NVIDIA A40：

| `MinChunkSize` | WER（offline 是 7.9） | Latency（含计算） | Latency（假设计算不花时间） |
|---|---|---|---|
| 0.5 s | 8.5 | 3.27 s | 1.02 s |
| 1.0 s | 8.1 | 3.62 s | 1.91 s |
| 2.0 s | 8.0 | 5.45 s | 3.73 s |

最后一列只算“等两次 output 一致”带来的 delay，论文说它大约是 chunk 的两倍。一个粗略的解释（我的）：一个 word 平均在 chunk 的中间说完，要等到这个 chunk 结束才进第一次 output，再等一个 chunk 才被 confirmed，至少是 1.5 个 chunk。中间一列比最后一列多出 1.7 到 2.3 s，来自每次把整个 buffer 重新跑一遍 large-v2 的计算；论文还指出这台机器在共享 cluster 上，同一个设定的 latency 重复 10 次的标准差达 0.36 到 0.81 s。

对 robot 的一句 command，要紧的是用户说完到最终 transcript 的时间。Endpointing 判定说完之后，不会再有新的 audio，最后一次 output 的 unconfirmed 部分可以直接当作最终结果（这一点是我的推论，没有在论文里读到）。这样剩下的只是最后一次计算的时间，而不是 3 s 的平均 latency。CTC 和 RNN-T 那样逐个 frame output 的 model 没有“整段重跑”的开销，这是它们在 streaming 上的结构优势（[第 8 站](#listen)）。

### LLM：回复的第一句要多快

[第 7 站](#sys)的 formula 在这里照样用：batch size 为 1 时，每生成一个 token 都要把 weight 从 memory 读一遍，$\text{tokens/s}\le\text{bandwidth}/\text{weight 的 bytes}$。一个 8B 的 LLM 用 int4 是 4 GB，在 Jetson AGX Orin（204.8 GB/s）上最多 $204.8/4=51.2$ tokens/s，每个 token 至少 19.5 ms。

但 TTS 不需要整段回复。SLP3 给的比例是自然对话里一个 word 约 250 ms、1.3 个 BPE token，说话时每秒只用掉 $1.3/0.25=5.2$ 个 token。51.2 比 5.2 快将近 10 倍，第一句话生成出来以后，LLM 永远跑在 TTS 前面。所以对 latency 有意义的只是第一个短句：8 个 token 至少 $8\times19.5=156$ ms，再加上 prompt 的 prefill（第 7 站算过，实测的 prefill 比这种下限大好几倍）。Skantze 和 Irfan 用 Azure 上的 gpt-3.5-turbo，把这一段记为 0.5 s。

### TTS：先预测 mel spectrogram，再由 vocoder 变成 waveform

Text-to-speech 反过来走第 8 站那条链：从文字得到 log-mel spectrogram，再从 spectrogram 得到 sample。Tacotron 2 把这两步分成两个 network，理由是 mel spectrogram 可以直接由 waveform 算出来，两部分能分开 train；它比 sample 平滑，而且对每个 frame 内部的 phase 不敏感，用 squared error 训练容易得多。它的设定是 50 ms 的 frame、12.5 ms 的 hop、Hann window、80 个 channel 覆盖 125 Hz 到 7.6 kHz，取 log 之前把 magnitude 截在 0.01 以上。和 Whisper 的 25 ms、10 ms、80 channel 是同一种东西。

**Spectrogram prediction network** 是 autoregressive 的：一次预测一个 80 维的 frame，前一个 frame 经过一个 pre-net（两层 256 个 ReLU 单元，论文说这个 bottleneck 对学会 attention 很关键）再进 decoder；location-sensitive attention 把之前各步累积的 attention weight 也当作 input，减少跳字和重复。每一步另有一个 stop token：projection 加 sigmoid，第一次超过 0.5 的那个 frame 就是结尾。

**Vocoder** 把每个 mel frame 变成 sample。Tacotron 2 用 WaveNet，24 kHz 的 output，每个 frame 对应 $24000\times0.0125=300$ 个 sample。WaveNet 有 30 层 dilated convolution，第 $k$ 层的 dilation 是 $2^{k\bmod10}$；它一个 sample 一个 sample 地生成，每秒 audio 要按顺序走 24000 步。Tacotron 2 的 MOS（1 到 5 分的人工评分）是 4.526，录音本身是 4.582；同样的 network 改成预测 linear spectrogram 再用 Griffin-Lim 算法还原 waveform，只有 3.944。

WaveNet 的问题是慢。HiFi-GAN 论文在一块 V100 和一台 2.6 GHz Intel i7 的 MacBook Pro 上（32-bit float、没有优化）量了速度，括号里是相对 real time 的倍数：

| Vocoder | MOS | CPU | GPU | Parameter |
|---|---|---|---|---|
| 录音本身 | 4.45 | | | |
| WaveNet（MoL） | 4.02 | | 0.07 kHz（×0.003） | 24.73M |
| HiFi-GAN V1 | 4.36 | 31.74 kHz（×1.43） | 3701 kHz（×167.86） | 13.92M |
| HiFi-GAN V3 | 4.05 | 296.38 kHz（×13.44） | 26169 kHz（×1186.80） | 1.46M |

“$n$ kHz”是每秒生成 $n\times1000$ 个 sample。WaveNet 在 GPU 上生成 1 s 的 22.05 kHz audio 要 $22.05/0.07=315$ s。HiFi-GAN 快，是因为它不是 autoregressive 的：generator 是全 convolutional 的，用 transposed convolution 把 mel frame 一级一级地 upsample。仓库的 `config_v1.json` 里 hop 是 256 个 sample（22.05 kHz 下 11.6 ms 一个 frame），四级 upsample 的倍数是 8、8、2、2，乘起来 $8\times8\times2\times2=256$，一个 frame 正好变成 256 个 sample，所有 sample 同时算出来。（WaveNet 的 CPU 速度这一格，我读到的表格文字有错位，没有列。）

**Streaming。** Spectrogram 是按 frame 的顺序生成的，vocoder 是 convolution，只看附近的若干 frame，所以不必等整句话的 mel 都出来：每攒够一段就交给 vocoder，算完一段播一段。Chunk 的边界上，convolution 需要相邻 chunk 的几个 frame，实际做法要让 chunk 之间留一点重叠（这一点是我按结构推的，没有读到具体的做法）。

能不能不断，看速度。取一个 chunk 为 20 个 mel frame，即 $20\times256/22050=232.2$ ms 的 audio。HiFi-GAN V1 在那台 CPU 上是 1.43 倍 real time，算一个 chunk 要 $232.2/1.43=162.4$ ms。第一个 chunk 播放的 232 ms 里，第二个 chunk 已经算完了，以后每个 chunk 都在上一个播完之前就绪，声音连续。条件是速度大于 1 倍 real time（real-time factor 小于 1）。反过来，假设一个 vocoder 只有 0.8 倍 real time，一个 chunk 要算 $232.2/0.8=290.2$ ms，比它播放的时间长 58.0 ms，每两个 chunk 之间都会出现 58 ms 的空白，句子被切成一段一段。V3 在 CPU 上算一个 chunk 只要 17.3 ms。

::fig[ee4706-tts] Streaming TTS 的时间线。上面一行是 vocoder 在 CPU 上逐个 chunk 地算（每个 162 ms），下面一行是 loudspeaker 在播（每个 232 ms）。看从第二个 chunk 起，计算总是领先播放，first audio 的 latency 只是第一个 chunk 的那 162 ms（加上生成前 20 个 mel frame 的时间）。

**Codec token。** SLP3 第 17 章讲的是另一种 pipeline：先用一个 neural audio codec 把 waveform 变成离散的 token，再像 language model 一样生成 token。EnCodec 把 24 kHz 的 waveform 压到每秒 75 个 frame（$24000/75=320$ 倍），每个 frame 用 residual vector quantization 变成 8 个 code，每个 codebook 有 1024 个 codeword：每秒 $75\times8=600$ 个 token，$600\times\log_21024=6000$ bit/s。VALL-E 用一个 autoregressive Transformer 生成第一个 codebook 的 code，再用一个 non-autoregressive 的 model 跑 7 次补齐其余 7 个；它在 7000 多个说话人的约 6 万小时英语上 train，给 3 s 的目标说话人录音就能模仿这个人的 voice。对 streaming 来说，autoregressive 那一部分每秒至少要生成 75 个 token，否则跟不上播放。Moshi 的 codec Mimi 把 frame rate 降到 12.5 Hz（一个 frame 80 ms），8 个 codebook、每个 2048 个 codeword：$12.5\times8\times\log_22048=12.5\times8\times11=1100$ bit/s，正是论文写的 1.1 kbps。

### Barge-in：用户打断 robot

Moshi 论文引用的统计：对话里重叠的 speech 占说话时间的 10% 到 20%。人会在对方说到一半时插进来纠正、追问，或者只说一句“yeah”表示在听。Skantze 和 Irfan 说，标准的 Furhat 软件不支持用户打断（barge-in），robot 不听的时候亮一个红色的 LED。

支持 barge-in 有三个具体问题。

**Robot 先听到的是它自己。** Robot 的 loudspeaker 离自己的 microphone 很近。设 loudspeaker 离 microphone 0.1 m，用户离 1.5 m，按 free field 里 sound pressure 和距离成反比，robot 自己的声音在 microphone 上比用户高 $20\log_{10}(1.5/0.1)=23.5$ dB。Robot 一开口，VAD 就会一直报告“有 speech”，分不出用户是不是也在说。Microphone 收到的是 $m(t)=s_{\text{user}}(t)+(h*x_{\text{robot}})(t)+n(t)$：用户的声音、robot 自己播的 $x_{\text{robot}}$ 经过房间的 impulse response $h$、以及 noise。Robot 确切知道 $x_{\text{robot}}$，估计出 $h$ 就能把第二项减掉，这叫 acoustic echo cancellation（这段是我的概括，讲 echo cancellation 的那页材料我没有抓到）。Skantze 和 Irfan 的实验干脆让参与者戴 close-talking 的 headset，论文说是为了不需要 echo cancellation、录音也清楚；同时把 TTS 的 audio 作为第二个 channel 送进 VAP，让 model 知道哪一部分是 robot 自己在说。

**什么时候停。** 他们的 system 在 robot 说话期间，VAP 的两个预测都低于 0.4 时才让出 turn，并且在下一个 word 的边界停下。用户只说了一句“yeah”，预测不会两个都偏向用户，robot 接着说。按 SLP3 一个 word 约 250 ms，robot 从决定停到真的停，还要再说 0 到 250 ms，平均半个 word。

**对话的 history 要改。** Robot 要说的是“I will put the cup in the sink and then wipe the table”，在“sink”之后被打断，后半句从来没有说出口。如果 LLM 的 history 里留着整句，下一轮它会以为用户已经听到了“wipe the table”。论文的做法是丢掉没说出口的部分，history 里只放真正播出来的话。

::fig[ee4706-barge] 上：loudspeaker 离 microphone 0.1 m，用户 1.5 m，robot 自己的声音在 microphone 上高 23.5 dB。下：robot 说到“sink”时用户插话，robot 在下一个 word 边界停下，LLM 的 history 只保留说出口的部分。

### 一次回合的 latency 账

把各段的数字放在一起，都来自上面读到的原文：

| 一段 | 数字 | 来源 |
|---|---|---|
| VAD 一个 window | 32 ms 的 audio，计算不到 1 ms | silero-vad README |
| 等 silence | 1 s（Furhat baseline）；0.5 s（VAP 允许接话的最小 gap） | Skantze 和 Irfan |
| Streaming ASR | 连续演讲上平均 3.27 s（0.5 s chunk，A40，large-v2） | Whisper-Streaming |
| LLM | 0.5 s（Azure 上的 gpt-3.5-turbo）；Orin 上 8B int4 第一句至少 156 ms | Skantze 和 Irfan；第 7 站的 formula |
| TTS | 1 s（ElevenLabs streaming）；HiFi-GAN V1 在 CPU 上一个 232 ms 的 chunk 162 ms | Skantze 和 Irfan；HiFi-GAN |
| 人 | 最短 0.2 s，10 种语言平均 230 ms | Skantze 和 Irfan；Moshi 引 Stivers |

**串行时，每一段的全部时间相加。** 等 silence 结束，ASR 才出最终的 transcript，LLM 写完整段回复，TTS 合成完整段 audio，才开始播：

$$L_{\text{serial}}=T_{\text{end}}+T_{\text{ASR}}+T_{\text{LLM, 全部}}+T_{\text{TTS, 全部}}$$

**Streaming 时，只有每一段的第一块相加。** 每一段一拿到上游的第一块就开始工作，后面的部分在播放的同时生成：

$$L_{\text{stream}}=T_{\text{end}}+T_{\text{ASR, final}}+T_{\text{LLM, 第一句}}+T_{\text{TTS, 第一个 chunk}}$$

成立的条件是每一段的产出速度都不低于下游消耗的速度，否则后面会断。上面已经分别验过：LLM 每秒 51.2 个 token，播放只用 5.2 个；vocoder 是 1.43 倍 real time。

代数字算一个下限：$T_{\text{end}}=0.5$ s，LLM 第一句 0.156 s，vocoder 第一个 chunk 0.162 s，合计 0.818 s，还没有算 ASR 的最后一次计算、LLM 的 prefill 和生成前 20 个 mel frame 的时间。即使每一段都 streaming，串起来仍然是人的 4 倍。

剩下的办法是**在用户说完之前就开始准备**。Skantze 和 Irfan 的 system 在 TurnGPT 的分数超过 0.2，或者距离上一次 incremental ASR 的结果已经 200 ms 时，就用当前的 partial transcript 去请求 LLM 和 TTS。新的 partial transcript 和上次用来准备的那一版 semantic similarity $\ge0.8$ 时，沿用已经准备好的回复；否则取消重来。这样回复常常在 0.5 s 的最小 gap 到来时已经就绪，latency 只剩 $T_{\text{end}}$。Table I 里 response time 的 mode 是 0.6 s，正是这种情况。

Moshi 走得更远：不再有 ASR、LLM、TTS 三个 model，一个 model 直接读用户的 audio token、写自己的 audio token，以 Mimi 的 80 ms 一个 frame 为步长，同时听和说。论文给的 latency 是理论上 160 ms，实际 200 ms，已经在人的 230 ms 之内。

::fig[ee4706-budget] 同一次回合的四种做法，从用户说完的时刻算起。看串行的三段首尾相接；streaming 把每段缩成第一块；提前准备让回复在 0.5 s 的 gap 到来时已经就绪；Moshi 落在人的 0.2 s 附近。
