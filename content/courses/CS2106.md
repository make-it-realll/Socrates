先看三件事。三段 program 本身都没有写错，放到一台同时跑着很多 program 的机器上，结果都不对。

**第一件。** 一个 program 里有一行 `while (1) { }`。如果 OS 的做法是把 CPU 交给 program、等 program 自己交回来，那么这个 program 永远不会交回来。机器上其他所有 program，连同 OS 自己，再也拿不到 CPU，只能重启。

**第二件。** 两个 thread 各把同一个 global variable `counter` 加 10,000,000 次，结果应该是 20,000,000。OSTEP 在一台机器上跑了两次，得到 19,345,221 和 19,221,041，两次还不一样。

::fig[cs2106-race0] 两个 thread 各做一次 `counter = counter + 1`，`counter` 从 50 开始。按图里从上到下的顺序执行，最后是 51，少了一次加法。

**第三件。** 64 KB 的 memory 里空着 16 KB，分成 6 KB、4 KB、6 KB 三块。一个只要 10 KB 的 program 装不进去，因为没有哪一块够 10 KB。

::fig[cs2106-frag] 空着的总量够，但每一块都不够。

三件事是同一个处境：很多 program 共用一个 CPU、一块 memory、一个 disk，每个 program 却都是按“整台机器归我”写的。OS 要做的就是让这个假设成立，并且在 program 确实要共享时让共享不出错。

## [proc] Process、system call 与 context switch

:::skip
能讲清一次 `write()` 从 user mode 进 kernel 再回来经过哪几步、一次 timer interrupt 之后 process A 的 register 分两次存在哪里，能写出 fork 之后 parent 和 child 的输出，并画出五个 state 之间的 transition，就可以去第 2 站。
:::

### Process：一个正在跑的 program

Disk 上的 program 只是一个 file，里面是 instruction 和初始的 data。把它跑起来，就多出了一堆只在运行时才有的东西：一片 memory（code、global data、heap、stack），CPU 里的 register（PC 指向下一条 instruction，SP 指向 stack 顶），以及打开的 file。这些合起来叫一个 process。同一个 program 可以同时跑成好几个 process，各有各的 memory 和 register。

OS 为每个 process 保存一份记录，叫 process control block（PCB）：process ID（PID）、当前 state、不在 CPU 上时那一组 register 的值、memory 的映射信息、打开的 file 列表。Process 不在 CPU 上的时候，它的全部“运行状态”就在 PCB 里。

Unix 里新建 process 只有一个办法：`fork()`。它把调用者完整地复制一份，复制出来的叫 child，原来的叫 parent。

```c
int x = 100;
int main(void) {
    pid_t pid = fork();
    if (pid == 0) {                 /* child */
        x = x + 1;
        printf("child: x = %d\n", x);
        exit(0);
    } else {                        /* parent */
        wait(NULL);
        printf("parent: x = %d, child pid = %d\n", x, pid);
    }
    return 0;
}
```

`fork()` 调用一次、返回两次：parent 和 child 都从 `fork()` 的返回处接着跑，区别只在 return value。Child 拿到 0，parent 拿到 child 的 PID。所以 `if` 的两个 branch 各被一个 process 走了。输出是

```
child: x = 101
parent: x = 100, child pid = 4242
```

（PID 的具体数由 OS 分配，4242 只是举例。）Child 把 `x` 改成了 101，parent 看到的仍然是 100：两个 process 的 `x` 在同一个 address 上，却是两份不同的 memory。`wait(NULL)` 让 parent 停下来等 child 结束，所以 child 的那行一定先打印。

::fig[cs2106-fork] `fork()` 之后有两个 address space，内容一开始完全相同，之后各改各的。两边的 `pid` 是 `fork()` 分别返回的值。

`fork()` 只会复制自己。要跑另一个 program，child 接着调用 `exec()`：把自己的 memory 整个换成另一个 program 的 code 和 data，从那个 program 的开头跑起。`exec()` 成功就不会返回，因为调用它的那段 code 已经不存在了。

为什么不把两件事合成一个“新建一个跑某 program 的 process”？xv6 book 给的理由是 shell 的 I/O redirection。在 shell 里输入 `cat < input.txt`，shell 先 `fork()`，child 在 `exec("cat")` 之前做两件事：`close(0)`，然后 `open("input.txt")`。`open` 总是返回最小的空闲 file descriptor，刚空出来的正是 0，于是 0 号 descriptor（standard input）指向了 `input.txt`。然后 `exec("cat")`，`cat` 照常从 0 号读，读到的就是这个 file。`cat` 自己对 redirection 一无所知，parent shell 的 descriptor 也没有被动过。分成两个 call，中间就留出了一段由 child 自己调整环境的空隙。

### 为什么不能直接调用 OS 的 function

Process 要读 file，最直接的办法是让它自己去操作 disk。可这样一来，file system 里记的 permission 就没有意义了：任何 process 都能绕过检查把整个 disk 读一遍。OS 必须让 process 不能自己做某些事，但能请 OS 代做。

硬件为此提供一个 mode bit。CPU 在 user mode 下跑 process 的 code，此时访问 I/O device、改 page table、关 interrupt 这类 privileged instruction 一执行就触发 exception，交给 OS 处理（通常是杀掉这个 process）。OS 的 code 在 kernel mode 下跑，什么 instruction 都能执行。

Process 请 OS 做事的入口叫 system call。它要同时完成两件事：切到 kernel mode，跳进 OS 的 code。危险在于“跳到哪里”：如果 process 可以指定 kernel 里的任意 address，它就能跳过 permission 检查，直接跳到“检查已通过”之后的那一行。所以跳转目标不由 process 决定。开机时 OS 在 kernel mode 下把一张 trap table 交给硬件，写明“发生 system call 时跳到哪个 handler、发生 timer interrupt 时跳到哪个 handler”。之后 process 执行一条 trap instruction（MIPS 里叫 `syscall`，RISC-V 里叫 `ecall`），硬件就按表跳转。Process 能选的只有 system call 的编号，放在约定的 register 里（MIPS 是 `$v0`，xv6 的 RISC-V 是 `a7`）。

以 `write(1, buf, 3)` 为例，走一遍：

1. Program 调用 C library 里的 `write`，这是一个普通的 function call。
2. Library 把 `write` 的编号放进约定的 register，三个 argument 放进 argument register，然后执行 trap instruction。
3. 硬件把 user 的 PC 等 register 存到这个 process 的 kernel stack 上，切到 kernel mode，跳到 trap table 里登记的 system call handler。
4. Handler 按编号找到 `sys_write`，检查 argument：1 号 descriptor 是否打开、`buf` 到 `buf + 3` 是否都在这个 process 自己的 memory 里。检查通过才去做。
5. 把 return value 放进 return register，执行 return-from-trap：硬件从 kernel stack 恢复 register，切回 user mode，回到第 2 步那条 trap instruction 的下一条。

::fig[cs2106-syscall] 一次 `write()`。虚线以上是 user mode，以下是 kernel mode；穿过虚线的只有两条路：trap 往下，return-from-trap 往上，而往下那条的落点由 trap table 决定。

每个 process 除了 user stack，还有一个只在 kernel mode 下用的 kernel stack（xv6 里是 `p->kstack`）。第 3 步把 register 存在这里而不是 user stack 上，因为 user stack 的 SP 是 process 自己设的，可能指向任何地方。

:::wrong System call 就是一个普通的 function call，只是 function 写在 kernel 里
从 program 的角度看，`write(1, buf, 3)` 长得和 function call 一样，因为 library 把 trap 包在了 function 里面。但 CPU 做的事完全不同：跳转目标由 trap table 而不是 caller 决定；mode 从 user 切到 kernel；register 存到 kernel stack；kernel 要逐个检查 argument。如果它真是普通 call，`buf` 只要指向 kernel 自己的 memory，`write` 就会把 kernel 的 data 写到屏幕上。开销也不在一个量级：普通 function call 是几条 instruction；OSTEP 引用的测量里，1996 年的 Linux 一次 system call 约 4 µs，现在的机器也要零点几 µs，相当于几百到上千个 cycle。
:::

### Timer interrupt：OS 拿回 CPU 的唯一可靠办法

Process 在 CPU 上跑的时候，OS 的 code 没有在跑。OS 想做任何事，前提是 CPU 先回到它手里。如果只靠 process 自己做 system call 或者主动让出（cooperative 的做法），开头那个 `while (1) { }` 就永远不还。

解决办法还是硬件：一个 timer，每隔固定的时间（几 ms 量级，NUS 的讲义叫 timer interrupt interval）发一次 interrupt。Interrupt 和 trap 走同一套机制：硬件保存 register，切到 kernel mode，按 trap table 跳到 timer 的 handler。开机时设置 timer 和登记 handler 都是 privileged 的，process 关不掉它。每次 timer interrupt 之后 OS 都能重新决定让谁跑。分给一个 process 一次连续运行的时间叫 time quantum，它是 timer interrupt interval 的整数倍。

### Context switch：register 分两次存

OS 决定从 process A 换到 process B，就要把 A 的运行状态存起来、把 B 的装回去。OSTEP 第 6 章把一次 timer interrupt 引起的 switch 拆成两次保存：

1. **硬件保存。** Timer interrupt 到来时，硬件把 A 的 user register（PC、SP 等）存到 A 的 kernel stack 上，切到 kernel mode，跳进 timer handler。
2. **OS 保存。** Handler 决定换成 B，调用 `switch()`：把 A 此刻在 kernel 里的 register 存进 A 的 PCB，从 B 的 PCB 里装回 B 的 kernel register，其中包括 SP，于是 stack 换成了 B 的 kernel stack。
3. **回到 B。** 执行 return-from-trap。硬件从当前的 kernel stack（已经是 B 的）恢复 user register，切回 user mode，从 B 上次被打断的地方接着跑。

::fig[cs2106-ctx] 一次 context switch。看 CPU 里那一组 register 的值先被压到 A 的 kernel stack，再连同 kernel 里的状态存进 A 的 PCB；换上 B 的 PCB 之后，return-from-trap 从 B 的 kernel stack 取出 B 当初被打断时的 PC。

第 3 步之所以能“回到 B 上次被打断的地方”，是因为 B 上一次离开 CPU 时，也走过同样的第 1、2 步。

Context switch 的代价有直接和间接两部分。直接的是保存和恢复 register、执行 scheduler 本身，OSTEP 引用的 1996 年测量约 6 µs，现在在 1 µs 以下。间接的是 cache：B 刚上来时，cache 里装的多半是 A 的 data，B 的前一段 access 大多是 miss（cache 的道理见 [CS2100 第 8 站](../courses/CS2100.html#cache)）。第 5 站会看到 TLB 也有同样的问题。

### 五个 state

一个 process 在它的一生里不是一直在 CPU 上。按“能不能马上跑”分成五个 state：

| State | 意思 |
|---|---|
| New | 刚创建，OS 还在为它准备 PCB 和 memory |
| Ready | 什么都不缺，只等 CPU |
| Running | 正在 CPU 上跑 |
| Blocked | 在等某件事（disk 读完、child 结束、key 被按下），给它 CPU 也没用 |
| Terminated | 已经结束，等 OS 回收 |

::fig[cs2106-states] 五个 state 之间的 transition。只有 Running 能主动走向 Blocked 和 Terminated；Blocked 等到事件之后先回 Ready，不能直接回 Running。

用上面的 `fork` 例子检验。Parent 执行 `wait(NULL)` 时 child 还没结束，parent 从 Running 进入 Blocked。Child 被 scheduler 选中，Ready 到 Running，打印，`exit(0)`，进入 Terminated。“child 结束”这个事件让 parent 从 Blocked 回到 Ready，等 scheduler 再选中它才回到 Running，打印第二行。

Ready 和 Running 之间的两条 transition，一条是 scheduler 选中（dispatch），一条是 time quantum 用完被 timer interrupt 换下（preempt）。在 Ready 的一堆 process 里选谁，就是第 2 站的问题。

:::edge Child 先结束、parent 还没 wait：zombie
Child `exit` 之后，它的 memory 可以立刻回收，PCB 却不能，因为 exit status 存在里面，parent 将来 `wait` 时要读。这种只剩 PCB 的 process 叫 zombie。Parent 一直不 `wait`，zombie 就一直占着一个 PCB 和一个 PID。反过来，parent 先结束，child 就成了 orphan，Unix 把它过继给 `init`（PID 1），由 `init` 来 `wait`。
:::

:::from
Restricted operation 与 switching 两个问题的提法、trap table 和“按编号而不是按 address 请求服务”、register 分两次保存的时间线、cooperative 做法里只能重启、system call 和 context switch 的实测数字，来自 [OSTEP 第 6 章](https://pages.cs.wisc.edu/~remzi/OSTEP/cpu-mechanisms.pdf)（全文）。`fork` 返回两次、`exec` 不返回、`cat < input.txt` 的 redirection 为什么需要 fork 与 exec 分开、`ecall` 和 kernel stack，来自 [xv6 book 第 1、2 章](https://pdos.csail.mit.edu/6.S081/2022/xv6/book-riscv-rev3.pdf)。`x = 100` 的 fork 例子是为这一页构造的；五个 state 的划分按 NUS 讲义的通行讲法，zombie 与 orphan 凭自己的知识写，没有对照 NUS 的 slides。

## [sched] CPU scheduling

:::skip
给一组 process 的 arrival time 和 burst time，能画出 FCFS、SJF、SRT、RR 的 Gantt chart 并算出三种时间；能说出 SJF 为什么最优、RR 用什么换来了 response time，以及 MLFQ 每条规则防的是什么，就可以去第 3 站。
:::

### 要优化的是什么

Ready 里有好几个 process，CPU 只有一个，scheduler 要决定先跑谁。先要说清“好”指什么。每个 process 的一次 CPU 使用叫一个 burst。对每个 process 定义三个时间：

$$\text{turnaround time}=\text{completion time}-\text{arrival time}$$

$$\text{waiting time}=\text{turnaround time}-\text{burst time}$$

$$\text{response time}=\text{first run time}-\text{arrival time}$$

Waiting time 是在 Ready 里干等的总时间（这里先不考虑 I/O）。Response time 是从到达到第一次拿到 CPU。没有人在等结果的 batch job 关心 turnaround；有人对着屏幕的 interactive job 关心 response。另外还有系统层面的 throughput（单位时间完成几个 job）和 CPU utilization（CPU 忙的时间占比）。

整站用 Berkeley CS162 的一组 process：四个 process 在 $t=0$ 同时到达，排队顺序是 P1、P2、P3、P4，burst time 分别是 53、8、68、24 ms，都只用 CPU、不做 I/O。

### FCFS：先来先跑

First-Come First-Served（FCFS）按到达顺序，一个跑完再跑下一个，中途不打断（non-preemptive）。

| | P1 | P2 | P3 | P4 |
|---|---|---|---|---|
| 运行区间 | 0–53 | 53–61 | 61–129 | 129–153 |
| completion | 53 | 61 | 129 | 153 |
| waiting = response | 0 | 53 | 61 | 129 |

Average waiting time 是 $(0+53+61+129)/4=243/4=60.75$ ms，average completion time 是 $(53+61+129+153)/4=99$ ms。

P2 只要 8 ms，却等了 53 ms，因为它排在一个长 job 后面。短 job 堵在长 job 后面叫 convoy effect。FCFS 的好处是不会 starvation：排在一个 job 前面的 job 只会越来越少。

### SJF：先跑短的，为什么最优

Shortest Job First（SJF）每次挑 burst 最短的。顺序变成 P2（8）、P4（24）、P1（53）、P3（68）：

| | P2 | P4 | P1 | P3 |
|---|---|---|---|---|
| 运行区间 | 0–8 | 8–32 | 32–85 | 85–153 |
| waiting | 0 | 8 | 32 | 85 |

Average waiting time $(0+8+32+85)/4=125/4=31.25$ ms，average completion time $(8+32+85+153)/4=69.5$ ms，都比 FCFS 少了一半左右。四个 job 都在 $t=0$ 到达时，这已经是所有顺序里最好的，证明如下。

设 job 按某个顺序跑，第 $k$ 个的 burst 是 $b_k$。第 $k$ 个要等前面 $k-1$ 个跑完，waiting time 是 $b_1+b_2+\cdots+b_{k-1}$。把 $n$ 个 job 的 waiting time 加起来，$b_k$ 出现在它后面每个 job 的 waiting time 里，一共 $n-k$ 次：

$$\text{total waiting}=\sum_{k=1}^{n}(n-k)\,b_k$$

$n=4$ 时就是 $3b_1+2b_2+b_3$。排在前面的 burst 系数大。代 FCFS 的顺序：$3\times53+2\times8+68=243$；代 SJF 的顺序：$3\times8+2\times24+53=125$。都和上面的表对上。

假设某个顺序里有相邻的两个 job 满足 $b_k>b_{k+1}$。把它俩对调，只有这两项变了：

$$\big[(n-k)\,b_k+(n-k-1)\,b_{k+1}\big]-\big[(n-k)\,b_{k+1}+(n-k-1)\,b_k\big]=b_k-b_{k+1}>0$$

对调之后 total waiting 严格变小。所以只要还有“前长后短”的相邻对，就还能改进；没有这种对的顺序只有一个，就是从短到长。

SJF 的麻烦是要事先知道 burst time。OS 只能拿过去预测将来，常用 exponential average：

$$\tau_{n+1}=\alpha\,t_n+(1-\alpha)\,\tau_n,\qquad0\le\alpha\le1$$

$t_n$ 是刚刚实际用掉的 burst，$\tau_n$ 是上一次的预测。把 $\tau_n$ 再展开一层、再展开一层：

$$\tau_{n+1}=\alpha\,t_n+\alpha(1-\alpha)\,t_{n-1}+\alpha(1-\alpha)^2\,t_{n-2}+\cdots+(1-\alpha)^{n+1}\tau_0$$

越久以前的 burst，weight 每往前一步乘一次 $1-\alpha$，按 exponential 衰减，这就是名字的来历。取 $\alpha=\tfrac12$，初始预测 $\tau_0=10$，实际 burst 依次是 6、4、6、4、13、13、13：

| $n$ | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| 实际 $t_n$ | 6 | 4 | 6 | 4 | 13 | 13 | 13 | |
| 预测 $\tau_n$ | 10 | 8 | 6 | 6 | 5 | 9 | 11 | 12 |

例如 $\tau_1=\tfrac12\times6+\tfrac12\times10=8$，$\tau_5=\tfrac12\times13+\tfrac12\times5=9$。Burst 从 4 跳到 13 之后，预测要三步才追到 12。

### 有新 job 到达时：SRT

到目前为止所有 job 同时到达。OSTEP 的例子：A 在 $t=0$ 到达，要 100；B 和 C 在 $t=10$ 到达，各要 10。

SJF 是 non-preemptive 的。$t=0$ 时只有 A，A 开始跑，B、C 到了也只能等 A 跑完。Turnaround 是 A：$100-0=100$，B：$110-10=100$，C：$120-10=110$，平均 $310/3\approx103.33$。

Shortest Remaining Time（SRT，OSTEP 叫 STCF）是它的 preemptive 版本：每当有 job 到达，比较新 job 的 burst 和正在跑的 job 的剩余时间，新的更短就抢占。$t=10$ 时 A 还剩 90，B 只要 10，B 抢走 CPU。Turnaround 是 A：$120-0=120$，B：$20-10=10$，C：$30-10=20$，平均 $150/3=50$。

::fig[cs2106-srt] 同一组 job。上面 SJF 让 B、C 在 A 后面等了 90 ms；下面 SRT 在 $t=10$ 打断 A。

### Round robin：用 turnaround 换 response

SJF 和 SRT 的 average turnaround 都好，但一个长 job 一旦排在后面，要等很久才第一次拿到 CPU。对 interactive job，这意味着按下一个键要好几秒才有反应。

Round robin（RR）把 FCFS 改成 preemptive：每个 job 最多连续跑一个 time quantum $q$，用完就排回 ready queue 的队尾，换下一个。回到四个 process 的例子，取 $q=20$ ms。

::fig[cs2106-rr] RR，$q=20$。竖线走过 Gantt chart，下面是这一刻在跑的 process 和 ready queue：用完 quantum 的 process 排到队尾；P2 和 P4 最后一段不到 20 ms，跑完就离开。

从图上读出每个 process 的完成时刻和三种时间：

| | P1 | P2 | P3 | P4 | 平均 |
|---|---|---|---|---|---|
| completion | 125 | 28 | 153 | 112 | 104.5 |
| waiting | 72 | 20 | 85 | 88 | 66.25 |
| response | 0 | 20 | 28 | 48 | 24 |

P1 的 waiting 是两段空档之和：$(68-20)+(112-88)=48+24=72$。P3 是 $28+(88-48)+(125-108)=28+40+17=85$。

三种 scheduling 放在一起：

| | avg waiting | avg completion | avg response |
|---|---|---|---|
| FCFS | 60.75 | 99 | 60.75 |
| SJF | 31.25 | 69.5 | 31.25 |
| RR，$q=20$ | 66.25 | 104.5 | 24 |

RR 的 response 最好，waiting 和 completion 最差。它能保证：$n$ 个 job 同时在 ready queue 里时，任何一个 job 等到下一次拿到 CPU 最多是 $(n-1)\,q$。

$q$ 取多大是另一笔账。每次换 job 要付一次 context switch。OSTEP 的数字：$q=10$ ms、一次 switch 1 ms，CPU 有 $1/(10+1)\approx9.1\%$ 的时间花在 switch 上；$q=100$ ms 时降到 $1/101\approx1\%$。$q$ 太小，时间都耗在 switch 上；$q$ 太大，RR 退化成 FCFS，response 又变差。CS162 给的典型值是 10 到 100 ms。

:::wrong RR 对每个 job 都公平，所以平均下来总不比 FCFS 差
CS162 的例子：10 个 job，每个 100 s，同时到达，$q=1$ s。FCFS 依次在 100、200、…、1000 s 完成，average completion time 是 550 s。RR 每一轮让 10 个 job 各跑 1 s，99 轮之后（990 s）每个都还剩 1 s，于是第 $k$ 个在 $990+k$ s 完成，average 是 $(991+\cdots+1000)/10=995.5$ s，差不多是 FCFS 的两倍，而且最后一个完成的时刻一样是 1000 s。所有 job 一样长时，RR 让每个 job 都拖到最后才结束。它换来的只有 response：average response 从 FCFS 的 450 s 降到 RR 的 4.5 s。
:::

### MLFQ：不知道 burst 也能接近 SRT

SRT 要知道剩余时间，RR 不管长短一律平等。Multi-Level Feedback Queue（MLFQ）想做到：不预先知道 burst，靠观察 job 的行为来区分长短。它有几个 priority 不同的 queue，规则是（NUS 讲义的三条，加上同 priority 的处理）：

1. Priority 高的先跑；priority 相同的之间 RR。
2. 新 job 进入最高 priority。
3. Job 用满了它这一级的 time quantum，priority 降一级。
4. Job 在 quantum 用完之前就主动让出或 blocked，priority 不变。

OSTEP 第 8 章的例子，三级 queue，每级 $q=10$ ms。一个长的 CPU-bound job A 从最高一级进入，每用满一次 quantum 降一级，20 ms 之后就沉到最低一级。$t=100$ 时来了一个要 20 ms 的短 job B，它进入最高一级，比 A 优先，立刻抢到 CPU；跑满 10 ms 降到中间一级，仍然高于 A，再跑 10 ms 就结束。B 的 turnaround 是 20 ms，和 SRT 下一样。一个每次只用 1 ms CPU 就去等 I/O 的 interactive job，永远在 quantum 用完前让出，按第 4 条一直留在最高一级，response 很好。短 job 和 interactive job 浮在上面，长 job 沉到下面，效果接近 SRT。

但这四条有两个漏洞。

**Gaming。** 一个 job 每次跑到 quantum 的 99% 时故意做一次无意义的 I/O，按第 4 条它永远留在最高一级，几乎独占 CPU。OSTEP 的修正是把第 3、4 条合并改写：记录 job 在这一级累计用掉的 CPU 时间，累计满了就降级，不管中间让出过几次。

**Starvation。** 高 priority 的 interactive job 一多，合起来就能占满 CPU，沉到最低一级的长 job 永远轮不到。修正是 priority boost：每隔一段时间 $S$，把所有 job 重新放回最高一级。$S$ 没有理论上的最优值，OSTEP 说它要靠调；Solaris 的默认设置是 60 级 queue，quantum 从最高一级的约 20 ms 到最低一级的几百 ms，大约每秒 boost 一次。

### Lottery scheduling：按比例分

另一种思路是直接规定每个 process 应该得到 CPU 的多少比例。给每个 process 发一些 ticket，每次 scheduling 随机抽一张，抽中谁就跑谁一个 quantum。A 有 75 张、B 有 25 张，每次 A 被抽中的 probability 是 0.75。跑 100 个 quantum，A 得到的个数服从 binomial distribution，expectation 是 $100\times0.75=75$，standard deviation 是 $\sqrt{100\times0.75\times0.25}\approx4.3$，所以 A 大致拿到 71 到 79 个。比例越长期越准。新 process 进来，下一次抽签就有它的份；一个 process 也可以把自己的 ticket 分给它的 child。

### 两个 process 怎样交换 data

第 1 站里 parent 和 child 的 `x` 是两份，各改各的。可很多任务需要合作：shell 把 `ls` 的输出交给 `wc`，web server 的几个 worker 共用一个 cache。Process 之间交换 data（inter-process communication，IPC）有两条路。

**Message passing。** 通过 kernel 转交。Unix 的 pipe 就是这样：`pipe(p)` 得到两个 file descriptor，`p[1]` 写进去的 byte 从 `p[0]` 按顺序读出来，中间的 buffer 在 kernel 里。Shell 执行 `ls | wc` 时先建 pipe 再 `fork` 两次，第一个 child 把 standard output 换成 `p[1]` 后 `exec("ls")`，第二个把 standard input 换成 `p[0]` 后 `exec("wc")`，用的正是第 1 站 `cat < input.txt` 的同一个办法。xv6 book 提醒了一个细节：`wc` 那一边必须 `close` 掉自己手里多余的 `p[1]`，因为 pipe 只有在所有 write end 都关掉之后才会让 reader 读到 end-of-file，`wc` 自己拿着一个 write end，就会永远等下去。

Message passing 不用担心两边同时改同一份 data，因为 data 由 kernel 排好队交过去。代价是每传一次都要两次 system call（一次 `write`、一次 `read`），data 还要先复制进 kernel、再复制出来。

**Shared memory。** 让两个 process 的 page table 把同一块 physical memory 映射进各自的 address space（第 5 站讲 page table）。建好之后读写就是普通的 load 和 store，不经过 kernel，不复制。代价是两边可能同时改同一个地方，这正是这一站的问题。

### Thread：一个 process 里的多个执行流

如果合作的双方本来就是同一个 program 的两部分，用两个 process 再搭 shared memory 就太绕了。Thread 是更直接的做法：一个 process 里跑多个执行流，共享同一个 address space。

| 同一个 process 的 thread 之间 | |
|---|---|
| 共享 | code、global data、heap、打开的 file |
| 各有一份 | register（包括 PC、SP）、stack |

每个 thread 有自己的 PC，所以能各自走到 code 的不同位置；有自己的 stack，所以 local variable 互不干扰。Global variable 和 heap 是共享的。新建一个 thread 不用复制 memory，在多个 core 上几个 thread 可以真正同时跑。

开头第二件事就是两个 thread 共享一个 global 的 `counter`：

```c
static volatile int counter = 0;

void *worker(void *arg) {
    for (int i = 0; i < 10000000; i++)
        counter = counter + 1;
    return NULL;
}
/* main 用 pthread_create 建两个 thread 都跑 worker，再 pthread_join 等它们结束 */
```

OSTEP 跑出 19,345,221 和 19,221,041。

### 一行 C 是三条 instruction

`counter = counter + 1` 在 x86 上编译成三条 instruction（OSTEP 的例子里 `counter` 在 address `0x8049a1c`，code 从 address 100 开始）：

```
100  mov 0x8049a1c, %eax    ; 从 memory 读 counter 到 register eax
105  add $0x1, %eax         ; eax 加 1
108  mov %eax, 0x8049a1c    ; 把 eax 写回 memory
```

Timer interrupt 可以落在任意两条 instruction 之间（第 1 站）。两个 thread 各有自己的一份 `eax`：thread 被换下时 `eax` 存进它的 PCB（对 thread 来说是 thread control block），换回来时恢复。

::fig[cs2106-race] OSTEP 的 interleaving，`counter` 从 50 开始。看 Thread 1 读到 50 之后被 interrupt 打断：它 `eax` 里的 51 在 PCB 里睡着，Thread 2 完整地做完一次加法写回 51；Thread 1 回来把同一个 51 再写一遍。

两次加法，`counter` 只从 50 变到 51。Thread 1 把一个过时的值写了回去，盖掉了 Thread 2 的更新。两千万次加法里有 $2\times10^7-19{,}345{,}221=654{,}779$ 次像这样被盖掉，就得到 19,345,221。

几个名词：

- 结果取决于各 thread 执行的先后时机，叫 race condition。
- 访问共享 data、不能有两个 thread 同时在里面执行的那段 code，叫 critical section。这里就是那三条 instruction。
- 保证同一时刻最多一个 thread 在 critical section 里，叫 mutual exclusion。

一个正确的 critical section 方案要满足三条：

1. **Mutual exclusion。** 最多一个 thread 在里面。
2. **Progress。** 里面没人、又有 thread 想进时，必须有一个能进去；不在 critical section 里的 thread 不能挡住别人。
3. **Bounded waiting。** 一个 thread 提出要进之后，别人插到它前面的次数有上限，它不会被饿死。

### 两个看起来对的办法

**关掉 interrupt。** 进 critical section 前关 interrupt，出来再开。单个 CPU 上，没有 interrupt 就没有 context switch，确实不会被打断。但关 interrupt 是 privileged instruction，让任意 program 执行它，一个 `while (1)` 就能重新独占机器（第 1 站的问题又回来了）；在多个 CPU 上它也没用，别的 CPU 照样在跑另一个 thread。所以它只用在 OS 自己内部很短的地方。

**用一个 flag。**

```c
int flag = 0;
void lock(void)   { while (flag == 1) ; flag = 1; }
void unlock(void) { flag = 0; }
```

:::wrong 用一个 flag variable当 lock 就行：看到 0 就设成 1 进去，别人看到 1 就会等
“看 flag”和“设 flag”是两步，interrupt 可以落在中间。OSTEP 给的 interleaving，flag 从 0 开始：

| 步 | Thread 1 | Thread 2 | flag |
|---|---|---|---|
| 1 | `while (flag == 1)`：读到 0，不等 | | 0 |
| 2 | （interrupt，换到 Thread 2） | | 0 |
| 3 | | `while (flag == 1)`：读到 0，不等 | 0 |
| 4 | | `flag = 1`，进入 critical section | 1 |
| 5 | | （interrupt，换回 Thread 1） | 1 |
| 6 | `flag = 1`，进入 critical section | | 1 |

两个 thread 都在里面了。这个 lock 本身就有 race condition：保护 `counter` 的问题原样转移到了保护 `flag` 上。
:::

### Peterson's algorithm

两个 thread（编号 0 和 1）只用普通的 load 和 store 也能做到 mutual exclusion。要用两样东西：`flag[i]` 表示 thread $i$ 想进去，`turn` 表示两个都想进时让谁。

```c
int flag[2] = {0, 0};
int turn;

void lock(int self) {              /* self 是 0 或 1 */
    int other = 1 - self;
    flag[self] = 1;                /* 我想进 */
    turn = other;                  /* 但先让你 */
    while (flag[other] == 1 && turn == other)
        ;                          /* 你也想进、而且轮到你：等 */
}
void unlock(int self) { flag[self] = 0; }
```

**Mutual exclusion 的证明。** 假设 thread 0 和 thread 1 同时在 critical section 里。两个都执行过 `turn = other`，`turn` 只有一个值，看谁最后写的。不妨设 thread 0 最后写，它写的是 `turn = 1`。此后在两人都离开 critical section 之前，没有人再写 `turn`，所以 thread 0 做 `while` 判断时 `turn == 1`，`turn == other` 成立。Thread 0 要能通过 `while`，就必须读到 `flag[1] == 0`。可是 thread 1 在写 `turn` 之前已经写了 `flag[1] = 1`，那发生在 thread 0 写 `turn` 之前，也就在 thread 0 判断之前；thread 1 进了 critical section 还没出来，`flag[1]` 仍然是 1。Thread 0 读到的只能是 1，过不去，矛盾。设 thread 1 最后写也一样。所以两人不可能同时在里面。

另外两条也满足。Progress：只有一个 thread 想进时，`flag[other] == 0`，它立刻通过。Bounded waiting：thread 1 出来后如果马上又想进，它会重新执行 `turn = 0`，把机会让给正在等的 thread 0，所以 thread 0 最多被插队一次。

把 `counter = counter + 1` 包在 `lock(self)` 和 `unlock(self)` 之间，上面那种重叠就不可能发生，结果是 20,000,000。

Peterson 的局限：只适用于两个 thread；而且 OSTEP 指出，现代 CPU 为了速度会调换 load 和 store 的顺序，上面证明里“先写 `flag` 再写 `turn`”在 hardware 上不一定成立，不加 memory barrier 就会失效。

### Hardware 的帮助：TestAndSet

Flag lock 失败是因为“读旧值”和“写新值”是两步。如果 hardware 保证这两步不可分割（atomic），问题就没了。TestAndSet 就是这样一条 instruction：

```c
/* hardware 一步完成，中间不会被打断，也不会被别的 CPU 插进来 */
int TestAndSet(int *p) { int old = *p; *p = 1; return old; }

void lock(int *L)   { while (TestAndSet(L) == 1) ; }
void unlock(int *L) { *L = 0; }
```

Lock 空着时 `*L == 0`。几个 thread 同时执行 TestAndSet，hardware 让它们一个一个来，只有第一个拿到旧值 0 并把它设成 1，其余拿到的都是 1，继续转圈。这种一直转圈检查的 lock 叫 spin lock。

它满足 mutual exclusion，但不满足 bounded waiting：谁抢到全看时机，一个 thread 可能一直抢不到。在单个 CPU 上它还很浪费。设 $q=10$ ms，4 个 thread 抢同一个 lock，持有者在 critical section 里被 timer interrupt 换下。另外 3 个 thread 依次上来，各自把整个 quantum 都花在 `while` 里转圈，因为持有者不上 CPU 就不会 unlock。持有者再次拿到 CPU 之前，白白浪费了 $3\times10=30$ ms。

所以等待的 thread 不应该转圈，应该进入 Blocked，让出 CPU，等 lock 被释放时再被叫醒。这就是下一站 semaphore 做的事。

:::edge 多个 CPU 上 spin lock 反而合适
Critical section 通常只有几条 instruction。持有者在另一个 CPU 上跑着，马上就会 unlock，这时转几圈比做一次 context switch（第 1 站，微秒量级）便宜。OSTEP 的结论是：thread 数和 CPU 数差不多时，spin lock 表现不错。
:::

:::back
Timer interrupt 能落在任意两条 instruction 之间、thread 换下时 register 存进 PCB，来自[第 1 站](#proc)。

## [sema] Semaphore 与 deadlock

:::skip
能用 semaphore invariant 证明 mutual exclusion，写出三个 semaphore 的 bounded buffer 并说出两个 wait 写反会怎样，能列出 deadlock 的四个 condition，并证明按固定顺序拿 lock 不会有 circular wait，就可以去第 5 站。
:::

### Semaphore：等不到就睡

上一站的 spin lock 让等待的 thread 占着 CPU 转圈。改进的方向是：等不到就进入 Blocked，由释放的一方把它叫醒。Semaphore 把这件事包装成一个 integer $S$ 加两个 atomic 的 operation（NUS 讲义的写法）：

- **Wait(S)**（也写作 P 或 down）：如果 $S\le0$，进入 Blocked；等到 $S>0$ 时把 $S$ 减 1，继续。
- **Signal(S)**（也写作 V 或 up）：把 $S$ 加 1；如果有 thread 在这个 semaphore 上 Blocked，叫醒其中一个。

$S$ 永远不会小于 0。还有一条从定义直接得到的 invariant：每完成一次 Wait，$S$ 减 1；每做一次 Signal，$S$ 加 1。所以任何时刻

$$S_{\text{current}}=S_{\text{initial}}+\#\text{Signal}(S)-\#\text{Wait}(S)$$

这里的 $\#\text{Wait}$ 只数已经完成的 Wait，还睡着的不算。

**用 semaphore 做 mutual exclusion。** 取 $S_{\text{initial}}=1$，每个 thread 进 critical section 前 Wait，出来后 Signal：

```c
semaphore s = 1;
wait(s);
counter = counter + 1;        /* critical section */
signal(s);
```

证明最多一个 thread 在里面。在 critical section 里的 thread 都完成了 Wait、还没做 Signal，所以它们的个数是 $N_{\text{CS}}=\#\text{Wait}-\#\text{Signal}$。代进 invariant：

$$S_{\text{current}}=1+\#\text{Signal}-\#\text{Wait}=1-N_{\text{CS}}$$

$S_{\text{current}}\ge0$，所以 $N_{\text{CS}}\le1$。初值为 1 的 semaphore 叫 binary semaphore，作用就是 mutex。

初值取 $K$，同样的推导给出 $N\le K$：最多 $K$ 个 thread 同时通过。这用来管理 $K$ 个相同的资源，例如 $K$ 个 buffer slot。

### Producer–consumer：三个 semaphore 各管一件事

Producer 不断产生 item 放进一个有 $K$ 个 slot 的 buffer，consumer 不断取出。有三个约束：buffer 满了 producer 要等；buffer 空了 consumer 要等；改 buffer 的 index 时两边不能同时改。每个约束用一个 semaphore：

```c
item buf[K];  int in = 0, out = 0;
semaphore mutex = 1;          /* 改 buf、in、out 时 mutual exclusion */
semaphore notFull = K;        /* 空 slot 的个数 */
semaphore notEmpty = 0;       /* 装了 item 的 slot 的个数 */

void producer(void) {
    while (1) {
        item x = produce();
        wait(notFull);
        wait(mutex);
        buf[in] = x;  in = (in + 1) % K;
        signal(mutex);
        signal(notEmpty);
    }
}

void consumer(void) {
    while (1) {
        wait(notEmpty);
        wait(mutex);
        item x = buf[out];  out = (out + 1) % K;
        signal(mutex);
        signal(notFull);
        consume(x);
    }
}
```

取 $K=2$，producer 先连跑三轮，然后 consumer 取一次：

| 事件 | notFull | notEmpty | buffer 里的 item |
|---|---|---|---|
| 开始 | 2 | 0 | 无 |
| Producer 放入 #1 | 1 | 1 | #1 |
| Producer 放入 #2 | 0 | 2 | #1 #2 |
| Producer 第三轮 `wait(notFull)`：$S=0$，Blocked | 0 | 2 | #1 #2 |
| Consumer 取出 #1，`signal(notFull)` 把 0 变 1 并叫醒 producer | 1 | 1 | #2 |
| Producer 完成 Wait（1 变 0），放入 #3 | 0 | 2 | #2 #3 |

Buffer 满时 producer 真的睡着了，没有转圈；consumer 一腾出 slot 就把它叫醒。

:::wrong 两个 wait 只是先后，顺序无所谓
把 producer 的两行换成先 `wait(mutex)` 再 `wait(notFull)`。仍取 $K=2$，buffer 已满：notFull = 0，notEmpty = 2，mutex = 1。Producer 执行 `wait(mutex)`，mutex 变 0；再执行 `wait(notFull)`，$S=0$，Blocked，手里还拿着 mutex。Consumer 执行 `wait(notEmpty)`，2 变 1，通过；执行 `wait(mutex)`，mutex 是 0，Blocked。现在 producer 等 consumer 腾出 slot，consumer 等 producer 释放 mutex，两边都永远等下去。原来的顺序先确认有空 slot、再拿 mutex，拿着 mutex 的人不会去等别的东西。
:::

### Deadlock

上面这种“每个人都在等另一个人手里的东西”叫 deadlock。它不是罕见的毛病：OSTEP 引用 Lu 等人对 MySQL、Apache、Mozilla、OpenOffice 的研究，105 个 concurrency bug 里有 31 个是 deadlock。

最小的例子是两个 thread、两个 lock，拿的顺序相反：

```c
/* Thread 1 */            /* Thread 2 */
lock(L1);                 lock(L2);
lock(L2);                 lock(L1);
```

Thread 1 拿到 L1 之后被换下，Thread 2 拿到 L2。接着 Thread 1 等 L2，Thread 2 等 L1，谁都不会放手。

Deadlock 要四个 condition 同时成立（Coffman 等人）：

1. **Mutual exclusion。** 资源一次只能给一个 thread。
2. **Hold and wait。** Thread 拿着已有的资源，同时等新的。
3. **No preemption。** 资源不能从持有者手里强行拿走。
4. **Circular wait。** 存在一圈 thread，每个都在等下一个手里的资源。

四个缺一个就不会 deadlock，所以 prevention 就是挑一个打破。

### Dining philosophers：拆掉 circular wait

五个 philosopher 围坐一桌，相邻两人之间放一根 chopstick，一共五根。吃饭要同时拿起左右两根。每个人的做法都是先拿左边、再拿右边。

如果五个人同时拿起左边那根，每人手里一根，都在等右边那根，而右边那根在右边邻居手里。五个人围成一圈，四个 condition 全部成立。

打破 circular wait 的办法是给所有资源定一个 total order，规定每个 thread 只能按从小到大的顺序拿。把 chopstick 编号 0 到 4，philosopher $i$ 坐在 chopstick $i$ 和 $(i+1)\bmod5$ 之间，每人先拿编号小的那根。Philosopher 0 到 3 仍然是先左后右，philosopher 4 的两根是 4 和 0，他先拿 0。

::fig[cs2106-dine] 左边每人先拿左手的 chopstick，“拿着”和“等着”的箭头连成一圈；右边按编号先拿小的，philosopher 4 改为先等 chopstick 0，圈断了，philosopher 3 能拿到两根。

**为什么 lock ordering 一定不会有 circular wait。** 按顺序拿 lock 的 thread，在等 lock $b$ 时手里拿着的每个 lock 编号都小于 $b$。假设出现了一圈：thread $T_1$ 拿着 $a_1$、等 $a_2$，$a_2$ 在 $T_2$ 手里；$T_2$ 拿着 $a_2$、等 $a_3$；……；$T_m$ 拿着 $a_m$、等 $a_1$。每个 thread 都是“拿着的比等着的小”，于是

$$a_1<a_2<\cdots<a_m<a_1$$

不可能。所以 circular wait 不会出现，deadlock 也就不会出现。前面两个 lock 的例子，规定先 L1 后 L2，Thread 2 改成先 `lock(L1)`，就修好了。

打破另外三个 condition 也各有办法，但各有代价：

- **Hold and wait。** 一次把所有要用的 lock 都拿到，例如先拿一个全局的 lock 再依次拿其他的。这要求事先知道要哪些，而且降低了 concurrency。
- **No preemption。** 用 `trylock`：拿不到就把手里的都放掉，过一会儿重来。可能出现 livelock：两个 thread 一直同时放、同时重试，都在动却都没有进展；加一个随机的等待时间可以缓解。
- **Mutual exclusion。** 用 compare-and-swap 这类 atomic instruction 写不需要 lock 的 data structure。写起来很难。

也可以不预防，允许 deadlock 发生，再定期检查“谁在等谁”构成的 graph 里有没有 cycle，有就重启其中某个 thread。很多 database 是这样做的。

:::edge Deadlock 和 starvation 不是一回事
Deadlock 里所有相关的 thread 都停住了，而且永远不会恢复。Starvation 是某个 thread 一直轮不到，别的 thread 却在正常前进，例如第 3 站 TestAndSet spin lock 下一直抢不到的 thread，或者第 2 站 MLFQ 里沉在最底层的长 job。没有 deadlock 的程序仍然可能有 starvation。
:::

:::back
Mutual exclusion、critical section 的三条要求、spin lock 的浪费，来自[第 3 站](#race)。
:::

:::from
Deadlock 的例子、四个 condition 的表述、按 condition 逐一 prevention（含 trylock 与 livelock、lock-free）、detect and recover、Lu 等人的 bug 统计，来自 [OSTEP 第 32 章](https://pages.cs.wisc.edu/~remzi/OSTEP/threads-bugs.pdf)（全文）。Semaphore 的定义和 invariant 按 NUS 讲义的写法，是凭对 NUS 课程的了解写的，没有读到 NUS 的 slides；OSTEP 第 31 章（Semaphores）没有读。Bounded buffer 的 code、$K=2$ 的 trace、wait 写反的 deadlock 推演、dining philosophers 的编号方案和 lock ordering 的证明是为这一页写的。

## [paging] Paging、page table 与 TLB

:::skip
能把 virtual address 切成 VPN 和 offset 并查表得到 physical address，能算 single-level 和 two-level page table 各占多少 memory，能对 two-level page table 走一遍 walk 并数出 memory access 的次数，能算有 TLB 时的 effective access time，就可以去第 6 站。
:::

### Contiguous allocation 卡在哪

最简单的做法是给每个 process 一整段连续的 physical memory。Process 的 code 里用的 address 都从 0 算起（叫 logical address 或 virtual address），CPU 里放两个 register：base 是这段 memory 的起点，limit 是它的长度。每次 access，hardware 检查 $\text{virtual}<\text{limit}$，然后访问 $\text{base}+\text{virtual}$。越界就触发 exception。Process 换上 CPU 时，OS 把它的 base 和 limit 装进去，所以每个 process 都以为自己从 address 0 开始。

问题就是开头第三件事。Process 来来去去，留下大小不一的空洞。开头那张图里空着 16 KB，最大的一块却只有 6 KB，10 KB 的 process 放不下。空闲 memory 被切碎、单块不够用，叫 external fragmentation。把正在跑的 process 往一边挪，空洞就能合并（compaction），可挪动时要复制它们的全部 memory，这段时间里这些 process 都不能跑。

根子在“连续”两个字。如果一个 process 的 memory 可以拆成小块、分散放在任何空着的地方，16 KB 的空闲就都能用上。

### Page 与 frame

Paging 把 virtual address space 切成固定大小的 page，把 physical memory 切成同样大小的 frame。任何一个 page 可以放进任何一个空 frame。每个 process 有一张 page table，第 $i$ 项记着 virtual page $i$ 放在哪个 frame。

因为 page 的大小是 2 的 power，切分只是把 address 的 bit 分成两段：高位是 virtual page number（VPN），低位是 page 内的 offset。翻译时 offset 原样保留，只把 VPN 换成 physical frame number（PFN）。

OSTEP 的小例子：virtual address space 64 byte，page 16 byte，所以有 4 个 page；physical memory 128 byte，有 8 个 frame。Page table 是 VP 0 → PF 3，VP 1 → PF 7，VP 2 → PF 5，VP 3 → PF 2。

翻译 virtual address 21。64 byte 要 6 个 bit（$2^6=64$），每个 page 16 byte，offset 占低 4 位，VPN 占高 2 位。21 的 binary 是 $010101$：VPN 是 $01$，即 page 1；offset 是 $0101$，即 page 里第 5 个 byte。查表，page 1 在 frame 7，binary $111$。把 VPN 换成 PFN，得到 $111\,0101$，即 $64+32+16+4+1=117$。

::fig[cs2106-paging] Virtual address 21 的翻译。Offset 的 4 个 bit 原样往下抄，只有 VPN 经过 page table 换成 PFN。四个 page 在 physical memory 里不连续，顺序也被打乱了。

在 paging 下，memory 从一开始就按 frame 分配和回收，空出来的也总是整数个 frame。把开头的例子换成 4 KB 的 frame 来想：16 KB 空闲就是 4 个空 frame，10 KB 的 process 要 3 个 page，放进哪 3 个空 frame 都行，它们挨不挨着无所谓。

:::wrong Paging 消灭了所有 fragmentation
它消灭了 external fragmentation，但带来了 internal fragmentation：process 要的 memory 不一定是 page 的整数倍。Page 4 KB，一个 process 要 10 KB，得分给它 $\lceil10/4\rceil=3$ 个 page 共 12 KB，最后一个 page 里有 2 KB 用不上。平均每段 memory 浪费半个 page。Page 越大，这个浪费越大；page 越小，page table 越长。这是选 page size 时的取舍。
:::

### Page table 太大

现实的设定：32-bit virtual address，page 4 KB。Offset 要 12 位（$2^{12}=4096$），VPN 是剩下的 20 位，所以 page table 有 $2^{20}$ 项。每项（page table entry，PTE）4 byte，一张表 $2^{20}\times4=4$ MB。每个 process 一张，100 个 process 光 page table 就要 400 MB。

而一个典型的 process 只用了 address space 的两头：低处的 code、data、heap，高处的 stack，中间几乎全空。那些空的 PTE 也占着位置。

办法是对 page table 本身再做一次 paging。把 4 MB 的 page table 切成一页一页：每页 4 KB，放得下 $4096/4=1024=2^{10}$ 个 PTE。再建一张 page directory，记着每一页 page table 在哪个 frame；如果某一页 page table 里全是空项，就根本不分配它，directory 里那一项标成 invalid。

于是 20 位 VPN 拆成两个 10 位：高 10 位查 directory，低 10 位查那一页 page table。每一级的 bit 数不是随便定的：一页 page table 恰好占一个 frame，正好装 $2^{10}$ 项，所以每一级是 10 位。

只用两头的 process：directory 一页 4 KB，code 所在的那 4 MB 区域要一页 page table，stack 所在的那 4 MB 区域要一页，共 $4+4+4=12$ KB，比 4 MB 小 341 倍。

拿一个具体的 address 走一遍。Virtual address `0x00403004`，写成 binary 是

$$\underbrace{0000000001}_{\text{dir index}=1}\ \underbrace{0000000011}_{\text{table index}=3}\ \underbrace{000000000100}_{\text{offset}=\texttt{0x004}}$$

设 page directory 在 physical address `0x00100000`（它的 address 放在一个 register 里，x86 叫 CR3，通称 page table base register），directory 第 1 项指向一页 page table，在 frame `0x2A0`；那页的第 3 项记着 frame `0x5C1`。

::fig[cs2106-walk] 同一个 address 访问两次。第一次 TLB 里没有，hardware 走 directory 和 page table 两级，各读一次 memory，再读 data，并把翻译存进 TLB；第二次访问同一个 page，TLB 直接给出 frame。

1. 读 directory 的第 1 项：address 是 $\texttt{0x00100000}+1\times4=\texttt{0x00100004}$，读出 frame `0x2A0`。
2. 读那页 page table 的第 3 项：address 是 $\texttt{0x002A0000}+3\times4=\texttt{0x002A000C}$，读出 frame `0x5C1`。
3. 拼上 offset：physical address 是 `0x005C1004`，读 data。

一次 load 变成了三次 memory access。

xv6 跑的 RISC-V Sv39 是同样的设计放大到 64 位：只用 virtual address 的低 39 位，page 仍是 4 KB，offset 12 位；PTE 变成 8 byte，一页放得下 $4096/8=512=2^9$ 项，所以每一级 9 位，一共三级，$9+9+9+12=39$。Page directory 的 address 放在 `satp` register 里。

### TLB：把翻译 cache 起来

两级 page table 解决了空间，却让每次 access 变成三次。解决办法和 [CS2100 第 8 站](../courses/CS2100.html#cache)的 cache 同一个道理：program 有 locality，刚用过的 page 很快会再用，把最近用过的几十个翻译（VPN → PFN）存在 MMU 里一块很快的 hardware 里，叫 translation lookaside buffer（TLB）。每次 access 先查 TLB：hit 就直接得到 PFN；miss 才去走 page table，走完把结果放进 TLB。TLB 一般有 32 到 128 项，fully associative，所有项同时比较。

套用 CS2100 的 average access time。设查 TLB 1 ns，一次 memory access 100 ns，两级 page table。Hit 时是 $1+100=101$ ns；miss 时多走两级，$1+100+100+100=301$ ns。TLB hit rate 98% 时

$$0.98\times101+0.02\times301=98.98+6.02=105\ \text{ns}$$

没有 TLB 时每次都是 300 ns。

Hit rate 为什么能这么高，看 OSTEP 的例子：8-bit virtual address，page 16 byte（4 位 VPN、4 位 offset），一个 `int a[10]` 从 virtual address 100 开始，循环把它读一遍。100 的 binary 是 $0110\,0100$，`a[0]` 在 VPN 6、offset 4。

| | a[0] | a[1] | a[2] | a[3] | a[4] | a[5] | a[6] | a[7] | a[8] | a[9] |
|---|---|---|---|---|---|---|---|---|---|---|
| address | 100 | 104 | 108 | 112 | 116 | 120 | 124 | 128 | 132 | 136 |
| VPN | 6 | 6 | 6 | 7 | 7 | 7 | 7 | 8 | 8 | 8 |
| TLB | miss | hit | hit | miss | hit | hit | hit | miss | hit | hit |

只有每个 page 的第一次 access 是 miss，hit rate $7/10=70\%$。这里 page 只有 16 byte；4 KB 的 page 装得下 1024 个 `int`，同样的循环每 1024 次 access 才 miss 一次。再读第二遍，三个翻译都还在 TLB 里，全部 hit。

### Context switch 之后的 TLB

TLB 里的一项只说“VPN 10 → PFN 100”，没说是哪个 process 的。Process P1 的 VPN 10 在 frame 100，P2 的 VPN 10 在 frame 170。从 P1 切到 P2 之后，如果 TLB 里还留着 P1 的那项，P2 访问 VPN 10 就会 hit 到 P1 的 frame，读到别人的 data。

一个办法是每次 context switch 把 TLB 清空（flush）。正确，但 P2 刚上来时每个 page 都要 miss 一次，这是第 1 站说的 context switch 间接开销的一部分。另一个办法是给每项加一个 address space identifier（ASID），记着它属于哪个 process；CPU 里有一个 register 存当前 process 的 ASID，只有 ASID 也相同才算 hit：

| VPN | PFN | valid | ASID |
|---|---|---|---|
| 10 | 100 | 1 | 1 |
| 10 | 170 | 1 | 2 |

两项可以同时留在 TLB 里，切换时不用清空。

:::edge Inverted page table
Page table 的长度跟着 virtual address space 走，有多少个 process 就有多少张。另一种做法是整个系统只有一张表，按 physical frame 编号，每个 frame 一项，记着“哪个 process 的哪个 page 在这里”。8 GB 的 memory、4 KB 的 frame，就是 $2^{33}/2^{12}=2^{21}$ 项，和 process 的个数无关。代价是翻译时要按 (PID, VPN) 去找它在哪一项，表是按 frame 排的，只能搜索，实际中要配一个 hash table。
:::

:::back
Context switch 的间接开销来自[第 1 站](#proc)。TLB 和 average access time 的道理是 [CS2100 的 cache](../courses/CS2100.html#cache)。
:::

:::from
64 byte、16 byte page 的小例子与 address 21 → 117、4 MB 与 400 MB 的 page table、PTE 的 bit，来自 [OSTEP 第 18 章](https://pages.cs.wisc.edu/~remzi/OSTEP/vm-paging.pdf)。TLB 的 hit 和 miss 流程、`a[10]` 的 70% hit rate、VPN 10 映射到 100 和 170 的 context switch 问题和 ASID 表，来自 [OSTEP 第 19 章](https://pages.cs.wisc.edu/~remzi/OSTEP/vm-tlbs.pdf)（全文）。Sv39 的 9 + 9 + 9 + 12 和 `satp`，来自 [xv6 book 第 3 章](https://pdos.csail.mit.edu/6.S081/2022/xv6/book-riscv-rev3.pdf)。Contiguous allocation 与 base、limit register 凭自己的知识写；OSTEP 第 20 章（Smaller Tables）没有读，two-level page table 的讲法、`0x00403004` 的 walk、12 KB 的计算、105 ns 的 effective access time 和 inverted page table 的数字是为这一页写的。

## [vm] Virtual memory 与 page replacement

:::skip
能说出一次 page fault 的处理步骤，算出 page fault rate 要低到多少 slowdown 才能接受，能对一串 reference string 走 FIFO、LRU、OPT 和 Clock，能用 stack property 解释 Belady's anomaly，并说出 thrashing 是怎么来的，就可以去第 7 站。

### Page 不一定在 memory 里

有了 page table，page 放在哪个 frame 已经由 OS 说了算。再走一步：page 也可以暂时不在 memory 里，放在 disk 上，用到了再搬进来。这样所有 process 的 address space 加起来可以比 physical memory 大，每个 process 也只需要把正在用的 page 留在 memory 里。这叫 virtual memory。

每个 PTE 里有一个 present bit（也叫 valid 或 resident bit）。Hardware 翻译时发现 present bit 是 0，就触发一个 exception，叫 page fault，交给 OS：

1. Hardware 查 page table，发现这个 page 不在 memory，trap 进 kernel。
2. OS 确认这个 address 是合法的（不合法就是 segmentation fault，杀掉 process）。
3. 在 disk 上找到这个 page 的位置。
4. 找一个空 frame；没有空的，就挑一个 page 赶出去（下面的 page replacement）。
5. 从 disk 把 page 读进这个 frame。读 disk 要几 ms，这期间 process 进入 Blocked，CPU 去跑别人。
6. 更新 PTE：填上 PFN，present bit 设为 1。
7. 回到引起 page fault 的那条 instruction，重新执行。这次翻译成功。

第 7 步和 system call 不同：system call 回到 trap 的下一条 instruction，page fault 要重新执行同一条。

一个 page 只在第一次被用到时才搬进来，叫 demand paging。新 process 启动时一个 page 都不在 memory 里，所以启动快，但最初一段会连续 page fault。

:::wrong TLB miss 就是 page fault
两件事发生在不同的层，代价差了五个数量级。TLB miss 是 TLB 里没有这个翻译，page 本身多半就在 memory 里；hardware 走一遍 page table（上一站的例子里多两次 memory access，约 200 ns）就解决了，OS 甚至不知道。Page fault 是 PTE 说这个 page 不在 memory 里，要 OS 介入、从 disk 读，约 10 ms，即 $10^7$ ns。顺序是：先查 TLB；miss 了去走 page table；走到 PTE 发现 present bit 是 0，才是 page fault。
:::

### Page fault 有多贵

设一次正常 access 100 ns，一次 page fault 的处理（主要是读 disk）10 ms $=10^7$ ns，page fault 的 probability 是 $p$：

$$\text{effective access time}=(1-p)\times100+p\times10^7\ \text{ns}$$

要求比没有 page fault 时最多慢 10%，即不超过 110 ns：

$$(1-p)\times100+p\times10^7\le110\quad\Longrightarrow\quad p\,(10^7-100)\le10\quad\Longrightarrow\quad p\le1.0\times10^{-6}$$

一百万次 access 里最多一次 page fault。Virtual memory 能用，完全靠 locality：program 在一段时间里只反复用少数几个 page。也正因为代价这么高，赶走哪个 page 值得仔细选。

### 赶走哪一个

用 reference string 来比较：只记 access 了哪些 page，按顺序写成一串。OSTEP 的例子是

$$0,\ 1,\ 2,\ 0,\ 1,\ 3,\ 0,\ 3,\ 1,\ 2,\ 1$$

有 3 个 frame。前三次一定是 miss（compulsory miss），frame 装满之后，三种 policy 在第 6 次 access（page 3）时开始分道：

- **OPT。** 赶走将来最久不会再用的 page。此刻往后看，0 下一次在第 7 次、1 在第 9 次、2 在第 10 次，赶走 2。它的 page fault 最少，但要预知将来，实际做不到，只用作比较的下限。
- **FIFO。** 赶走最早进来的 page。0 最早进来，赶走 0，可下一次 access 恰好就是 0。
- **LRU（least recently used）。** 赶走最久没被用过的 page，拿“过去”去猜“将来”。此刻最近一次使用的时刻，0 是第 4 次、1 是第 5 次、2 是第 3 次，赶走 2，和 OPT 一样。

::fig[cs2106-repl] 三种 policy 同步走完 11 次 access。每一步高亮刚 access 的 page；miss 时标出被赶走的那个。FIFO 在第 6 步赶走了马上要用的 0，接着连续 miss。

| | OPT | LRU | FIFO |
|---|---|---|---|
| hit | 6 | 6 | 4 |
| miss | 5 | 5 | 7 |

赶走的 page 如果在 memory 里被改过（PTE 里的 dirty bit 是 1），要先写回 disk；没改过的直接丢掉，disk 上那份仍然是对的。所以同样是候选，赶走 clean page 更便宜。

### Belady's anomaly 与 stack property

直觉上 frame 越多，page fault 越少。FIFO 不一定。Reference string $1,2,3,4,1,2,5,1,2,3,4,5$，每一步之后 frame 里的 page（M 是 miss，H 是 hit）：

| access | 1 | 2 | 3 | 4 | 1 | 2 | 5 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 3 个 frame | M 1 | M 12 | M 123 | M 234 | M 134 | M 124 | M 125 | H 125 | H 125 | M 235 | M 345 | H 345 |
| 4 个 frame | M 1 | M 12 | M 123 | M 1234 | H 1234 | H 1234 | M 2345 | M 1345 | M 1245 | M 1235 | M 1234 | M 2345 |

3 个 frame 有 9 次 page fault，4 个 frame 反而有 10 次。这叫 Belady's anomaly。分叉在第 7 次 access（page 5）：3 个 frame 时赶走的是 4，留下了马上要用的 1 和 2；4 个 frame 时赶走的是 1，之后 1、2、3、4 依次被赶走又依次被用到。

LRU 不会这样。原因是它有 stack property：$n$ 个 frame 的 LRU，任何时刻装着的是“最近用过的 $n$ 个不同的 page”；$n+1$ 个 frame 装着的是“最近用过的 $n+1$ 个不同的 page”。前者永远是后者的 subset。所以 $n$ 个 frame 时 hit 的 access，$n+1$ 个 frame 时一定也 hit，page fault 只会更少。FIFO 的内容取决于“什么时候进来的”，加一个 frame 会改变后面每一次赶走谁，没有这种包含关系；上表第 7 步之后，3 个 frame 的 $\{1,2,5\}$ 就不是 4 个 frame 的 $\{2,3,4,5\}$ 的 subset。

### LRU 太贵，用 Clock 近似

真正的 LRU 要在每一次 memory access 时记下时刻（每个 PTE 一个 counter，赶走时找最小的），或者维护一个按使用先后排的 stack（每次 access 把那个 page 挪到顶上）。每次 access 都要做额外的事，hardware 支持不起。

Hardware 能便宜做到的，是每次 access 时把 PTE 里的 reference bit 设成 1。Clock（也叫 second chance）只用这一个 bit：所有 frame 排成一圈，一根 clock hand 指着下一个候选。要赶走一个时，看指针下的 page：

- reference bit 是 1：最近用过，给它第二次机会，把 bit 清成 0，hand 往前走一格。
- reference bit 是 0：从上次 hand 经过到现在都没被用过，赶走它。

最近被用过的 page 总能躲过一轮，被赶走的是hand 转一圈都没人碰过的 page，近似“最久没用过”。

:::edge 所有 reference bit 都是 1 时，Clock 就是 FIFO
拿上面 OSTEP 那串 reference string 走 Clock（hand 从 frame 0 开始，page 装进来时 reference bit 设为 1）。到第 6 次 access（page 3）要赶人时，0、1、2 刚刚都被用过，三个 bit 全是 1。hand 转一整圈把它们都清成 0，回到起点，赶走 frame 0 里的 page 0，和 FIFO 一样。往后每次要赶人时情况相同，最后 Clock 也只有 4 次 hit，和 FIFO 完全相同。Reference bit 只有在“有的用过、有的没用过”时才有区分能力。
:::

### Thrashing 与 working set

Frame 怎样分给各个 process：可以平均分，可以按 process 的大小按比例分。Page fault 时赶谁，也有两种范围：只在自己的 page 里挑（local replacement），或者在所有 process 的 page 里挑（global replacement）。Global 更灵活，但一个 process 的大量 page fault 会抢走别人的 frame，让别人也开始 page fault。

如果一个 process 拿到的 frame 装不下它正在反复使用的那些 page，就会每赶走一个、很快又要把它读回来，几乎每次 access 都是 page fault，CPU 大部分时间在等 disk。这叫 thrashing。按上面的计算，page fault rate 只要从 $10^{-6}$ 涨到 $10^{-3}$，effective access time 就从 110 ns 变成约 $0.999\times100+0.001\times10^7\approx10{,}100$ ns，慢了近一百倍。

要避免它，就要知道一个 process 此刻“正在反复使用”的 page 有多少。Working set model 的定义：取一个时间窗口 $\Delta$，$W(t,\Delta)$ 是时刻 $t$ 之前最近 $\Delta$ 次 access 用到的不同 page 的集合。只要给每个 process 至少 $|W|$ 个 frame，它在当前这段 locality 里就几乎不 page fault。

取 $\Delta=4$，reference string 是 $1,2,1,3,1,2,4,5,4,6,5,4$：

| $t$ | 4 | 6 | 8 | 10 | 12 |
|---|---|---|---|---|---|
| 最近 4 次 | 1 2 1 3 | 1 3 1 2 | 1 2 4 5 | 4 5 4 6 | 4 6 5 4 |
| $W(t,4)$ | {1, 2, 3} | {1, 2, 3} | {1, 2, 4, 5} | {4, 5, 6} | {4, 5, 6} |

前半段 program 在 {1, 2, 3} 里打转，后半段转到 {4, 5, 6}，各要 3 个 frame；$t=8$ 正好跨在两段之间，窗口里混了两段的 page，暂时要 4 个。$\Delta$ 太小，装不下当前这段的全部 page；太大，又会把上一段的 page 也算进来。如果所有 process 的 $|W|$ 加起来超过了 frame 总数，就该暂停一些 process，让剩下的能装下，而不是让所有 process 一起 thrash。

:::back
PTE、TLB 和 page table walk 来自[第 5 站](#paging)。Page fault 期间 process 进入 Blocked，是[第 1 站](#proc)的 state transition。
:::

### File descriptor 背后的三张表

Disk 本身只提供“读写第 $n$ 个 block”。Program 想要的是有名字、能按 byte 读写、能变长的 file。File system 就是在 block 之上搭出这层。

Process 用 `open` 打开一个 file，得到一个小 integer，叫 file descriptor；之后 `read`、`write` 都拿它当参数。它背后是三层：

1. **每个 process 一张 file descriptor table。** Descriptor 就是这张表的 index，表项指向下一层。0、1、2 照惯例是 standard input、output、error。
2. **整个系统一张 open file table。** 每次 `open` 产生一项，记着当前的 offset（下一次读写从第几个 byte 开始）、打开的 mode，以及有几个 descriptor 指向它。
3. **每个打开的 file 一个 in-memory inode。** File 本身的信息：大小、owner、permission、data 在 disk 的哪些 block 上。同一个 file 被打开几次都只有一个。

为什么 offset 放在第二层而不是第一层或第三层，看一个例子：

```c
int fd = open("log.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
if (fork() == 0) {
    write(fd, "child\n", 6);
    exit(0);
}
wait(NULL);
write(fd, "parent\n", 7);
```

`fork` 复制的是 descriptor table，复制出的表项指向同一个 open file table 项，于是共享同一个 offset。Child 写 6 个 byte，offset 从 0 变成 6；parent 接着从 6 开始写，file 最后是 13 个 byte：`child\nparent\n`。

::fig[cs2106-fdtab] `fork` 之后，parent 和 child 的 3 号 descriptor 指向 open file table 的同一项，offset 只有一份。下面是另一种情况：两个 process 各自 `open`，各有一项、各有一个 offset，但都指向同一个 inode。

如果改成两个 process 各自 `open` 一次，就有两项、两个 offset，都从 0 开始。Child 写下 `child\n`，parent 从 offset 0 写 `parent\n`，7 个 byte 把前 6 个全部盖掉，file 只剩 `parent\n`。Shell 执行 `(echo a; echo b) > out` 时，两条命令的输出能依次排好，靠的就是前一种共享。

### 一个 file 的 block 放在哪

File 的 data 存在若干个 block 里（下面都取 block 4 KB）。Inode 里要记下“这个 file 的第 0、1、2…个 block 在 disk 的哪里”。有四种记法，比较的是两件事：能不能快速找到第 $k$ 个 block（random access），以及记这些位置要占多少空间。

**Contiguous。** 每个 file 占一段连续的 block，只记起点和长度。第 $k$ 个 block 就在 $\text{起点}+k$，random access 最快。但这和第 5 站的 contiguous memory 一模一样：file 删来删去留下空洞，产生 external fragmentation；file 要变长时，后面的 block 可能已经被别人占了。

**Linked list。** 每个 block 末尾存下一个 block 的编号，inode 只记第一个。任何空 block 都能用，没有 external fragmentation。代价是找第 $k$ 个 block 要从头读 $k$ 个 block，每一次都是一次 disk read；而且每个 block 少了 4 byte 能放 data。

**FAT（File Allocation Table）。** 把所有 block 里的“下一个” pointer抽出来，集中放在一张表里，开机时整张读进 memory。表的第 $i$ 项是 block $i$ 的下一个 block 的编号，最后一个 block 记一个 end-of-file 标记，空 block 记 0。Directory 里记着 file 的第一个 block。

例子：一个 file 从 block 5 开始，FAT[5] = 9，FAT[9] = 2，FAT[2] = EOF，所以它依次占 block 5、9、2。要读它的第 2 个 block（从 0 数），在 memory 里走 5 → 9 → 2，然后只读一次 disk。

FAT 的问题是大小。1 TB 的 disk、4 KB 的 block，一共 $2^{40}/2^{12}=2^{28}$ 个 block。每项 4 byte，FAT 要 $2^{28}\times4\text{ B}=1$ GB，整张放在 memory 里太大；而且 random access 虽然不读 disk，仍要在 memory 里走一条可能很长的 chain。

**Indexed（inode）。** 每个 file 自己一张 index，按顺序列出它所有 block 的编号，第 $k$ 个就是 index 的第 $k$ 项。只有打开的 file 的 index 需要在 memory 里。问题是 index 多长：固定得长，小 file 浪费；固定得短，大 file 放不下。

### ext2 的 inode：不平衡的 index tree

ext2（以及 OSTEP 的教学用 file system）的 inode 里有 15 个 block pointer：

- 前 12 个是 direct pointer，直接指向 data block。
- 第 13 个是 single indirect：指向一个装满 pointer 的 block。4 KB 的 block、4 byte 的 pointer，一个 block 装 $4096/4=1024$ 个 pointer。
- 第 14 个是 double indirect：指向一个 block，里面 1024 个 pointer 各指向一个 single indirect block。
- 第 15 个是 triple indirect，再多一层。

::fig[cs2106-index] 同一个三 block 的 file 在 FAT 和 inode 里的样子（上），以及 inode 的 15 个 pointer 各自能覆盖多少 data（下）。

各级能覆盖的 data：

| pointer | 能指到的 data block 数 | 大小 |
|---|---|---|
| 12 个 direct | 12 | 48 KB |
| single indirect | $1024$ | 4 MB |
| double indirect | $1024^2=2^{20}$ | 4 GB |
| triple indirect | $1024^3=2^{30}$ | 4 TB |

只用 direct 和 single indirect 的最大 file 是 $(12+1024)\times4\text{ KB}=4144$ KB。加上后两级，上限约 4 TB。

这个 tree 故意不平衡。OSTEP 引用的测量显示，最常见的 file 只有约 2 KB，大多数 file 很小：它们只用 direct pointer，读 inode 之后就能直接找到 data。少数大 file 才走 indirect，多读一两次 disk 相对于读几 GB 的 data 微不足道。

**给定 byte offset，在哪个 pointer 下？** 读一个 file 的第 5,000,000 个 byte。

1. 它在第几个 block：$\lfloor5{,}000{,}000/4096\rfloor=1220$，block 内的 offset 是 $5{,}000{,}000-1220\times4096=2880$。
2. Block 0 到 11 归 direct pointer。$1220\ge12$，减掉之后是 1208。
3. 接下来 1024 个归 single indirect（block 12 到 1035）。$1208\ge1024$，减掉之后是 184，所以在 double indirect 下面。
4. Double indirect block 里的每个 pointer 管 1024 个 block。$\lfloor184/1024\rfloor=0$，用第 0 个 pointer，找到一个 single indirect block；在那里面取第 $184\bmod1024=184$ 个 pointer。

要读的 disk block 依次是：inode、double indirect block、single indirect block、data block，一共 4 次（inode 已经在 memory 里就是 3 次）。

### Directory 与 path lookup

Directory 也是一个 file，它的 data 是一张表，每项是一个名字和一个 inode number。Root directory 的 inode number 是约定好的（ext2 里是 2）。

OSTEP 数过打开 `/foo/bar` 要读几次 disk（假设每个 directory 的内容只占一个 block）：

1. 读 root 的 inode，找到 root directory 的 data 在哪。
2. 读 root directory 的 data，找到 `foo` 的 inode number。
3. 读 `foo` 的 inode。
4. 读 `foo` 的 data，找到 `bar` 的 inode number。
5. 读 `bar` 的 inode，检查 permission，在 open file table 里建一项，返回 descriptor。

一共 5 次，path 每多一层就多两次。之后每 `read` 一个 block 又要 3 次 I/O：读 inode 找到 block 的位置，读 data block，再把 inode 写回去更新最后访问时间。所以 `bar` 有 3 个 block 时，打开再读完一共约 $5+3\times3=14$ 次 I/O。实际系统会把最近用过的 inode 和 directory block cache 在 memory 里，大部分这样的读都不用真的去 disk。

两个 directory 项可以写同一个 inode number，这叫 hard link。两个名字指向同一个 file，没有哪个是“原件”。Inode 里有一个 link count，记着有几个名字指向它。Symbolic link 则是一个单独的小 file，内容是另一个 path；原 file 删掉后，它就指向一个不存在的 path。

:::wrong 删除一个 file，就是把它的 data 从 disk 上抹掉
Unix 删除 file 的 system call 叫 `unlink`：它只是把 directory 里那一项去掉，并把 inode 的 link count 减 1。只有 link count 变成 0、而且没有 process 还开着它时，file system 才回收 inode 和 data block，也就是在 free space 的记录里把它们标成空闲。Data block 里的 byte 原封不动，直到被新 file 覆盖。所以用 hard link 多建一个名字之后再删掉原名，file 照样能读；刚删的 file 常常还能被恢复工具找回来。
:::

### Free space：bitmap

File system 还要知道哪些 block 和 inode 是空的。最常见的做法是 bitmap：每个 block 一个 bit，0 是空，1 是已用；inode 另有一张。一个 4 KB 的 bitmap block 有 $4096\times8=32{,}768$ 个 bit，管 $32{,}768\times4\text{ KB}=128$ MB 的 data。1 TB 的 disk 有 $2^{28}$ 个 block，bitmap 是 $2^{28}$ bit $=32$ MB，是同一块 disk 上 FAT 的 $1/32$，因为每个 block 只记 1 bit 而不是 4 byte 的 pointer。

建一个新 file、写一个新 block，都要先在 bitmap 里找一个 0、改成 1、写回 disk。OSTEP 数过：给 file 追加一个新 block 要 5 次 I/O（读写 data bitmap、读写 inode、写 data block）。

:::back
Descriptor 0、1、2 和 `fork` 复制 descriptor table 来自[第 1 站](#proc)。Contiguous allocation 的 external fragmentation 和[第 5 站](#paging)是同一个问题，FAT 和 inode 的区别也和那里“一张大表还是按需分配的小表”是同一种取舍。
:::
