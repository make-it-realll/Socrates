::fig[cs2102-flat] 一张 table 记下所有东西。看右边三处：同一个事实存了两遍、删一行丢掉另一件事、一个合法的学生存不进来。

这张 table 一行一行看都没错，合在一起却出了三次事故。

**第一次。** Ana 转去 DSA。她的 dept 存在两行里，只改一行，database 里就同时说“Ana 是 CS 的”和“Ana 是 DSA 的”。

**第二次。** Cai 退掉 CS2040。这是他唯一的一行，删掉之后，“Cai 是 CS 的学生”这个和选课毫不相干的事实也没了。

**第三次。** 新生 Dee 还没选课。一行要靠 (sid, cid) 才能区分，cid 空着就没法存，于是 Dee 这个人进不了 database。

三次事故有同一个原因：一个 table 里装了两件独立的事，“学生属于哪个 dept”和“学生选了哪门课”。这门课的后半段（第 4、5、6 站）给出一套可以检查的办法，判断一个 table 装了几件事、该怎么拆开。前半段（第 1、2、3 站）先回答拆开之后的问题：数据分散在几个 table 里，怎样把需要的东西拼回来、怎样保证存进去的数据彼此一致。

## [rel] Relational model 与 relational algebra

:::skip
能在上面三个小 table 上手算 $\sigma$、$\pi$、$\bowtie$、$-$ 组成的 expression，能把“选了所有 CS course 的学生”写成 algebra 和 calculus，就可以去第 2 站。
:::

### 为什么不直接用文件

最朴素的做法是每个 table 存成一个 CSV 文件，程序自己读。要找 Ana 选了什么课，程序先扫一遍 Student 找到她的 sid，再扫一遍 Enrolled 找 sid 等于 1 的行。CMU 15-445 第一讲列出了这样做会遇到的问题，每一个都在上面的小例子里出现过：

- Enrolled 里写一个 sid 5，文件不会拒绝，可是 sid 5 的学生不存在；grade 那一栏写成 `"E"`，文件也照收。
- 找一行只能从头扫到尾；两个程序同时改同一个文件，后写的覆盖先写的。
- 改到一半机器断电，文件可能只写了一半。

更根本的问题是，“怎么找”被写死在程序里。数据从 100 行变成一亿行，程序原来的扫法太慢，就得改程序。

Relational model 的回答是把两件事分开：用户只说要什么，“怎么找”交给 database management system（DBMS）去决定。存储方式可以随便换，query 不用改，这叫 data independence。为了做到这一点，数据的形状必须非常简单。

### Relation、tuple、key

一个 relation 就是一个 table，形式上是一个 set of tuples。Student 的 schema 写成 Student(sid, name, dept)，每个 attribute 有一个 domain（允许的取值），每一行是一个 tuple。

“Set”这个词有两个后果，后面都会用到。第一，tuple 没有顺序，Ana 写在第一行还是最后一行是同一个 relation。第二，不能有两个完全相同的 tuple。

**Key。** 一组 attribute，任意两个 tuple 在它上面都不同，而且去掉其中任何一个 attribute 就做不到，这组 attribute 叫 candidate key。Student 的 key 是 sid；Enrolled 的 key 是 (sid, cid)，因为 sid 单独不够（Ana 有两行），cid 单独也不够（CS2102 有两行）。从 candidate key 里选一个作为 primary key。

Key 是 schema 的性质，不能从一个 instance 读出来。上面的 Student 里 name 恰好互不相同，但两个同名的学生完全可能存在，所以 name 不是 key。第 5 站会把这一点说得更精确。

**Foreign key。** Enrolled.sid 的每个值都必须出现在 Student.sid 里，这叫 foreign key，它让“sid 5 的学生不存在”这类错误被 DBMS 当场拒绝。第 3 站讲它被违反时怎么办。

### Relational algebra：输入是 relation，输出还是 relation

有了统一的形状，就可以定义一组 operator，每个都吃进一两个 relation、吐出一个 relation。输出还是 relation，所以 operator 可以任意嵌套。

**Selection** $\sigma_p(R)$：留下满足 predicate $p$ 的 tuple。

$$\sigma_{\text{grade}=\text{'A'}}(\text{Enrolled})=\{(1,\text{CS2102},\text{A}),\ (3,\text{CS2040},\text{A})\}$$

**Projection** $\pi_{A_1,\dots,A_k}(R)$：只留下这几个 attribute。结果是 set，重复的 tuple 只留一个：

$$\pi_{\text{dept}}(\text{Student})=\{\text{CS},\ \text{DSA},\ \text{Math}\}$$

Student 有 4 行，结果只有 3 行，因为 Ana 和 Cai 都投影成 CS。

**Cross product** $R\times S$：$R$ 的每个 tuple 和 $S$ 的每个 tuple 拼一次。Student $\times$ Enrolled 有 $4\times5=20$ 行、6 个 attribute（两个 sid 分别记作 Student.sid 和 Enrolled.sid）。

**Join。** Cross product 里大部分行没有意义，比如 Ana 拼上 Ben 的选课。真正要的几乎总是“先拼，再按条件筛”：

$$R\bowtie_{\theta}S=\sigma_{\theta}(R\times S)$$

这叫 theta join。条件全是等号的叫 equijoin。**Natural join** $R\bowtie S$ 是一种简写：在所有同名的 attribute 上取等号，并且同名的 column 只保留一份。

**Set operator** $\cup$、$\cap$、$-$：两个 relation 的 attribute 必须一一对应、domain 相同（union-compatible）才能用。

**Rename** $\rho_{S_1}(\text{Student})$：给一个 relation 换名字。同一个 table 要用两次时离不开它，比如找“同一个 dept 的两个不同学生”：

$$\pi_{S_1.\text{name},\,S_2.\text{name}}\Big(\sigma_{S_1.\text{dept}=S_2.\text{dept}\ \wedge\ S_1.\text{sid}<S_2.\text{sid}}\big(\rho_{S_1}(\text{Student})\times\rho_{S_2}(\text{Student})\big)\Big)=\{(\text{Ana},\text{Cai})\}$$

条件 $S_1.\text{sid}<S_2.\text{sid}$ 去掉了 (Ana, Ana) 这种自己配自己的，也让 (Ana, Cai) 和 (Cai, Ana) 只出现一次。

### Join 是怎么算出来的

定义说 join 是“cross product 再 select”，最直接的执行办法就照着定义做：对 Student 的每一行，把 Enrolled 从头到尾扫一遍，sid 相等就拼成一行输出。这叫 nested-loop join。

::fig[cs2102-nlj] Student $\bowtie_{\text{Student.sid}=\text{Enrolled.sid}}$ Enrolled 用 nested loop 执行。左边亮的是 outer 的当前行，中间亮的是 inner 的当前行；深色加实线表示 sid 相等，拼成的行出现在右边。

20 对里有 5 对相等，所以结果 5 行。Dee 没有任何一行配得上，从结果里消失了，这一点第 2 站的 outer join 会处理。

比较次数是 $|R|\times|S|$。数据一大，这个乘积就是代价的来源，而 algebra 恰好允许在不改变结果的前提下调整顺序。

### 同一个结果，两种顺序

“选了 CS2102 的学生的名字”可以写成

$$\pi_{\text{name}}\Big(\sigma_{\text{cid}=\text{'CS2102'}}\big(\text{Student}\bowtie\text{Enrolled}\big)\Big)$$

也可以先在 Enrolled 上筛，再 join：

$$\pi_{\text{name}}\Big(\text{Student}\bowtie\sigma_{\text{cid}=\text{'CS2102'}}(\text{Enrolled})\Big)$$

两式相等，因为 cid 只是 Enrolled 的 attribute，一行 Student 拼上一行 Enrolled 之后能不能通过筛选，只看 Enrolled 那一半。

::fig[cs2102-plan] 两棵 operator tree，边上的数是流过的行数。结果都是 {Ana, Ben}，join 那一步的工作量差得很多。

Nested-loop join 的比较次数是两边行数的乘积。左边是 $4\times5=20$，右边 Enrolled 先筛到 2 行，是 $4\times2=8$。放大到 40,000 个学生、200,000 条选课、其中 400 条是 CS2102：左边 $40{,}000\times200{,}000=8\times10^9$，右边 $40{,}000\times400=1.6\times10^7$，相差 500 倍。

用户写 SQL 时只说要什么，DBMS 里的 query optimizer 负责在这些等价的 tree 里挑便宜的那棵。这正是开头说的 data independence 的回报，也是 algebra 要先学的理由：optimizer 改写 query 时依据的就是 algebra 的等式。

:::wrong Natural join 只会在我想要的那个 column 上配对
Natural join 在**所有**同名 attribute 上取等号。想查“每个学生选的课和课属于哪个 dept”，写 Student $\bowtie$ Enrolled $\bowtie$ Course：Student 和 Course 都有一个叫 dept 的 attribute，于是条件里多出一个 Student.dept = Course.dept。结果是

| sid | name | dept | cid | grade |
|---|---|---|---|---|
| 1 | Ana | CS | CS2102 | A |
| 1 | Ana | CS | CS2040 | B |
| 3 | Cai | CS | CS2040 | A |

只剩 3 行。Ben 是 DSA 的，他选的 CS2102 属于 CS、MA2101 属于 Math，两行都因为 dept 不等被丢掉了。Schema 里两个 dept 的含义不同（学生的专业、课的开课单位），名字相同纯属巧合。要按意思配对就写 theta join，把条件写明。
:::

### For-all：用 difference 表达“每一个”

“选了**所有** CS course 的学生”是 algebra 最难写的一类 query。$\sigma$ 每次只看一个 tuple，没法直接说“对每一门课都成立”。办法是绕一圈：先找出反例。

**第一步。** 列出“每个学生都应该选的每门 CS 课”，即所有可能的 (sid, cid) 配对：

$$P=\pi_{\text{sid}}(\text{Student})\times\pi_{\text{cid}}\big(\sigma_{\text{dept}=\text{'CS'}}(\text{Course})\big)$$

4 个学生乘 2 门课，8 行。

**第二步。** 去掉实际选了的，剩下的就是“该选而没选”的配对：

$$M=P-\pi_{\text{sid},\,\text{cid}}(\text{Enrolled})=\{(2,\text{CS2040}),\ (3,\text{CS2102}),\ (4,\text{CS2102}),\ (4,\text{CS2040})\}$$

8 行里 (1, CS2102)、(1, CS2040)、(2, CS2102)、(3, CS2040) 被减掉。(2, MA2101) 不在 $P$ 里，减它没有影响。

**第三步。** 在 $M$ 里出现过的学生至少缺一门，从全体学生里去掉他们：

$$\pi_{\text{sid}}(\text{Student})-\pi_{\text{sid}}(M)=\{1,2,3,4\}-\{2,3,4\}=\{1\}$$

答案是 Ana。这个 pattern 有个专门的名字 division，记作 $\pi_{\text{sid},\text{cid}}(\text{Enrolled})\div\pi_{\text{cid}}(\sigma_{\text{dept}=\text{'CS'}}(\text{Course}))$，展开就是上面三步。第 2 站在 SQL 里写同一个 query 时，会用两层 NOT EXISTS 走同样的“找反例”路线。

### Relational calculus：只写条件，不写步骤

Algebra 仍然规定了步骤的顺序。Relational calculus 更进一步：只写出“结果里的 tuple 满足什么条件”，完全不写怎么算。

**Tuple relational calculus（TRC）** 的 variable 代表一个 tuple。“选了 CS2102 的学生的名字”：

$$\{\,t\mid\exists s\in\text{Student}\ \big(t.\text{name}=s.\text{name}\ \wedge\ \exists e\in\text{Enrolled}\,(e.\text{sid}=s.\text{sid}\wedge e.\text{cid}=\text{'CS2102'})\big)\,\}$$

逐句读：结果里的 $t$，要有一个 Student 的 tuple $s$ 和它同名，并且存在一个 Enrolled 的 tuple $e$，它的 sid 是 $s$ 的、cid 是 CS2102。

**Domain relational calculus（DRC）** 的 variable 代表一个 attribute 的值，tuple 写成 $\langle\cdot\rangle$：

$$\{\,\langle n\rangle\mid\exists i,d\ \big(\langle i,n,d\rangle\in\text{Student}\ \wedge\ \exists g\ (\langle i,\text{'CS2102'},g\rangle\in\text{Enrolled})\big)\,\}$$

两个 $i$ 写成同一个 variable，就表达了 join 条件。

For-all 在 calculus 里反而最直接，因为有 $\forall$。“选了所有 CS course 的学生”：

$$\{\,s\mid s\in\text{Student}\ \wedge\ \forall c\in\text{Course}\ \big(c.\text{dept}=\text{'CS'}\Rightarrow\exists e\in\text{Enrolled}\,(e.\text{sid}=s.\text{sid}\wedge e.\text{cid}=c.\text{cid})\big)\,\}$$

拿 Ben 检验：取 $c$ = CS2040，$\Rightarrow$ 左边的 $c.\text{dept}=\text{'CS'}$ 为真，Enrolled 里找不到 (2, CS2040)，右边为假，implication 为假，所以“对所有 $c$ 成立”失败，Ben 不在结果里。拿 Ana 检验：两门 CS 课都找得到，MA2101 和 GEA1000 的左边为假，implication 自动为真，Ana 在结果里。

把 $\forall c\,(A\Rightarrow B)$ 改写成 $\neg\exists c\,(A\wedge\neg B)$，就是“不存在一门她该选而没选的 CS 课”，和 algebra 的三步、SQL 的两层 NOT EXISTS 是同一句话。

:::edge Calculus 可以写出算不完的东西
$\{\,t\mid\neg(t\in\text{Student})\,\}$ 是“所有不是学生的 tuple”，有无穷多个，没有 DBMS 能给出这个结果。只允许结果取自 database 里出现过的值的 expression 叫 safe expression。Codd 证明了 safe 的 relational calculus 和 relational algebra 能表达的 query 完全一样多，所以“写条件”和“写步骤”是同一种能力的两种写法。SQL 的 WHERE 更像 calculus，DBMS 内部执行时用的是 algebra。
:::

:::from
Flat file 的三类问题、data independence 的动机、各个 operator 的定义、“$\sigma_{b\_id=102}(R\bowtie S)$ 与 $R\bowtie\sigma_{b\_id=102}(S)$ 结果相同、代价不同”的观察，跟的是 [CMU 15-445 Spring 2026 Lecture #01 notes](https://15445.courses.cs.cmu.edu/spring2026/notes/01-relationalmodel.pdf)（读的是全文）。那份 notes 用的是音乐商店的 artist 和 album，这里换成了学生选课，以便和第 5、6 站的 normalization 接上。Nested-loop join 的逐对执行、40,000 学生的代价数字、natural join 多配一个 column 的反例、for-all 的三步写法和 TRC、DRC 都是为这一页写的；TRC/DRC 和 safe expression、Codd 定理部分凭自己的知识写，没有找到对应讲义核对。所有结果用 PostgreSQL 16 实际跑过。

## [sql] SQL query

:::skip
能说出一条带 GROUP BY 和 HAVING 的 query 每个 clause 的执行顺序，能写两层 NOT EXISTS 的 for-all query，能解释 NOT IN 遇到 NULL 为什么返回空，就可以去第 3 站。

### SELECT–FROM–WHERE 就是 $\pi$、$\sigma$、$\times$

“选了 CS2102 的学生的名字”在 SQL 里写成

```sql
SELECT s.name
FROM   Student s, Enrolled e
WHERE  s.sid = e.sid AND e.cid = 'CS2102';
```

逐个 clause 对照：FROM 列出的 table 做 cross product，WHERE 是 $\sigma$，SELECT 是 $\pi$。所以这条 query 的意思就是

$$\pi_{\text{name}}\big(\sigma_{\text{s.sid}=\text{e.sid}\ \wedge\ \text{cid}=\text{'CS2102'}}(\text{Student}\times\text{Enrolled})\big)$$

结果是 Ana、Ben。`s`、`e` 是 alias，相当于 $\rho$。同一个 query 也可以把 join 条件写进 FROM：`FROM Student s JOIN Enrolled e ON s.sid = e.sid`，意思相同，读起来把“怎么拼”和“要哪些行”分开了。

和 algebra 有一处不同：SQL 的 table 是 multiset，SELECT 默认不去重。`SELECT dept FROM Student` 返回 4 行，CS 出现两次；写 `SELECT DISTINCT dept` 才是 $\pi_{\text{dept}}$ 的 3 行。不去重是为了省事：去重要把结果 sort 或 hash 一遍，而很多时候用户并不在乎重复。

### 一条 query 的执行顺序

加上 aggregate 之后，问题变成“每个 dept 有多少条成绩不是 C 的选课，只看至少 2 条的 dept”：

```sql
SELECT   s.dept, COUNT(*) AS n
FROM     Student s, Enrolled e
WHERE    s.sid = e.sid
  AND    e.grade <> 'C'
GROUP BY s.dept
HAVING   COUNT(*) >= 2;
```

SQL 写的顺序是 SELECT 在最前，执行的顺序不是。按 clause 的意思，结果必须等于下面这个过程的结果：

::fig[cs2102-eval] 这条 query 按概念上的执行顺序一步一步走。左边亮的是当前执行的 clause，右边是那一刻手上的数据。

| 顺序 | clause | 做什么 | 这个例子里剩多少 |
|---|---|---|---|
| 1 | FROM | 所有 table 做 cross product | 20 行 |
| 2 | WHERE | 逐行判断，只留结果为 TRUE 的行 | 4 行 |
| 3 | GROUP BY | 在指定 column 上相同的行归成一个 group | 2 个 group |
| 4 | HAVING | 逐个 group 判断，只留结果为 TRUE 的 group | 1 个 group |
| 5 | SELECT | 每个 group 算出一行 | (CS, 3) |
| 6 | ORDER BY、LIMIT | sort、截断 | |

WHERE 那一步具体是：20 行里 sid 相等的有 5 行，其中 Ben 的 MA2101 grade 是 C，去掉，剩 4 行。GROUP BY 按 dept 分：CS 有 Ana 的两行和 Cai 的一行，共 3 行；DSA 有 Ben 的 CS2102，1 行。HAVING 去掉 DSA。

这个顺序解释了几条规则，都不需要背：

- WHERE 里不能写 `COUNT(*)`：执行到 WHERE 时还没有 group，没有东西可数。“group 的条件”只能放 HAVING。
- SELECT 里起的 alias `n` 不能在 WHERE 里用：WHERE 执行时 SELECT 还没执行。
- GROUP BY 之后，SELECT 只能写 group 的 column 和 aggregate。原因是每个 group 只输出一行，`s.name` 在 CS 这个 group 里有 Ana 和 Cai 两个值，填不进一行。PostgreSQL 会报 `column "s.name" must appear in the GROUP BY clause or be used in an aggregate function`。

这是“概念上”的顺序，规定的是结果长什么样。DBMS 实际不会先造出 20 行，第 1 站那棵先 select 再 join 的 tree 才是它会做的。

:::edge GROUP BY primary key 时，SELECT 可以写同一个 table 的其他 column
`SELECT s.sid, s.name, COUNT(e.cid) FROM Student s LEFT JOIN Enrolled e ON s.sid = e.sid GROUP BY s.sid` 在 PostgreSQL 里能跑。sid 是 Student 的 primary key，同一个 group 里 s.name 只可能有一个值，规则的理由不存在了。第 5 站会把“sid 决定 name”叫作 functional dependency。别的 DBMS 不一定支持，考试按严格规则写最安全。
:::

### NULL 和 three-valued logic

Course 里 GEA1000 的 dept 是 NULL，意思是“没有值”或“不知道”。`'CS' = NULL` 该是 TRUE 还是 FALSE？两个都不对，因为不知道 NULL 代表什么。SQL 的处理是引入第三个 truth value，UNKNOWN：任何值和 NULL 比较，结果都是 UNKNOWN，连 `NULL = NULL` 也是。

UNKNOWN 参与 AND、OR、NOT 时，按“把它当成 TRUE 和 FALSE 都试一下”来定：两种情况结果一样，就取那个结果；不一样，就是 UNKNOWN。

| $p$ | $q$ | $p$ AND $q$ | $p$ OR $q$ |
|---|---|---|---|
| TRUE | UNKNOWN | UNKNOWN | TRUE |
| FALSE | UNKNOWN | FALSE | UNKNOWN |
| UNKNOWN | UNKNOWN | UNKNOWN | UNKNOWN |

NOT UNKNOWN 还是 UNKNOWN。检验第一行：$q$ 当成 TRUE，AND 得 TRUE；当成 FALSE，AND 得 FALSE；两次不同，所以 UNKNOWN。OR 两次都是 TRUE，所以 TRUE。

最后一条规则：**WHERE 和 HAVING 只留下 TRUE**，FALSE 和 UNKNOWN 一样被丢掉。要找 dept 为空的课，只能写 `WHERE dept IS NULL`；写 `WHERE dept = NULL` 永远得到空结果。

Aggregate 对 NULL 的规则：`SUM`、`AVG`、`MIN`、`MAX`、`COUNT(column)` 都跳过 NULL；`COUNT(*)` 数的是行数，不管里面有没有 NULL。

### Outer join：留下配不上的行

第 1 站的 join 把 Dee 丢了。想列出“每个学生选了几门课”，Dee 应该是 0，而不是不出现。LEFT OUTER JOIN 的定义是：先做普通的 join，再把左边 table 里一行都没配上的 tuple 补回来，右边的 column 全部填 NULL。

::fig[cs2102-outer] Left outer join。五条连线照常拼成五行；Dee 没有连线，保留下来，右边的 column 填 NULL。

RIGHT OUTER JOIN 保留右边配不上的行，FULL OUTER JOIN 两边都保留。

:::wrong Outer join 之后用 COUNT(*) 数每个学生选了几门课
```sql
SELECT s.name, COUNT(*), COUNT(e.cid)
FROM Student s LEFT JOIN Enrolled e ON s.sid = e.sid
GROUP BY s.sid, s.name;
```
| name | COUNT(*) | COUNT(e.cid) |
|---|---|---|
| Ana | 2 | 2 |
| Ben | 2 | 2 |
| Cai | 1 | 1 |
| Dee | 1 | 0 |

Dee 那个 group 里有一行，就是补出来的那行，所以 `COUNT(*)` 是 1。那一行的 e.cid 是 NULL，`COUNT(e.cid)` 跳过它，得到正确的 0。拿它去算“平均每个学生选几门”，`COUNT(*)` 给出 $(2+2+1+1)/4=1.5$，正确答案是 $(2+2+1+0)/4=1.25$。
:::

:::edge 条件放在 ON 里和放在 WHERE 里，对 outer join 不一样
想列出每个学生以及他成绩不是 A 的课。写 `... LEFT JOIN Enrolled e ON s.sid = e.sid WHERE e.grade <> 'A'`，结果只有 Ana、Ben、Ben 三行：Cai 唯一的课是 A，被 WHERE 删掉；Dee 那行的 grade 是 NULL，`NULL <> 'A'` 是 UNKNOWN，也被删掉。Outer join 补回来的行又被 WHERE 去掉了。把条件挪进 ON：`ON s.sid = e.sid AND e.grade <> 'A'`，配对时就排除 A，之后 Cai 和 Dee 配不上，作为补 NULL 的行留下来，一共 5 行。ON 决定“怎么配对”，WHERE 决定“结果留哪些行”，对 inner join 两者没有区别，对 outer join 有。
:::

### Subquery：IN 和 EXISTS

WHERE 里可以放另一个 query。“选了 CS2102 的学生”也可以写成

```sql
SELECT name FROM Student
WHERE  sid IN (SELECT sid FROM Enrolled WHERE cid = 'CS2102');
```

括号里的 query 算出 {1, 2}，外层留下 sid 在其中的学生。这个 subquery 和外层无关，算一次就够。

**Correlated subquery。** “本 dept 只有自己一个学生的人”：

```sql
SELECT s.name FROM Student s
WHERE NOT EXISTS (SELECT * FROM Student t
                  WHERE t.dept = s.dept AND t.sid <> s.sid);
```

里面引用了外层的 `s`，所以要对外层的每一行重新算一次。逐行走：s = Ana 时，里层找 dept 为 CS、sid 不是 1 的学生，找到 Cai，EXISTS 为 TRUE，NOT EXISTS 为 FALSE，Ana 不要。s = Ben 时，dept 为 DSA 的只有他自己，里层为空，NOT EXISTS 为 TRUE，留下。Cai 同 Ana，Dee 同 Ben。结果 Ben、Dee。里层能看到外层的 variable，外层看不到里层的。

**ANY 和 ALL。** `x > ALL (subquery)` 要求比每一个都大，`x > ANY (subquery)` 要求至少比一个大；`IN` 等价于 `= ANY`。“选课最多的学生”：

```sql
SELECT sid, COUNT(*) FROM Enrolled
GROUP BY sid
HAVING COUNT(*) >= ALL (SELECT COUNT(*) FROM Enrolled GROUP BY sid);
```

里层得到每个学生的选课数 {2, 2, 1}，外层留下不少于其中每一个的，即 sid 1 和 2。

### For-all：两层 NOT EXISTS

回到第 1 站的“选了所有 CS course 的学生”。SQL 没有 $\forall$，按 calculus 那一行改写：不存在一门 CS 课，使得这个学生没选它。

```sql
SELECT s.name FROM Student s
WHERE NOT EXISTS (
  SELECT * FROM Course c
  WHERE c.dept = 'CS'
    AND NOT EXISTS (SELECT * FROM Enrolled e
                    WHERE e.sid = s.sid AND e.cid = c.cid));
```

从里往外读。最里层：学生 s 选了课 c 吗？中间层：有没有一门 CS 课 c，s 没选？外层：没有这样的课，就留下 s。

拿 Ben 走一遍。中间层扫 CS 课：c = CS2102，最里层找 (2, CS2102)，找到，NOT EXISTS 为 FALSE，这门课不算反例；c = CS2040，找不到 (2, CS2040)，NOT EXISTS 为 TRUE，这门课是反例。中间层非空，外层的 NOT EXISTS 为 FALSE，Ben 不要。Ana 的两门都找得到，中间层为空，留下。结果只有 Ana，和 algebra 的三步一致。

:::wrong NOT IN 和 NOT EXISTS 可以随便互换
“所在 dept 没有开任何课的学生”，写成

```sql
SELECT name FROM Student WHERE dept NOT IN (SELECT dept FROM Course);
```

应该得到 Ben（DSA 没开课），实际得到空结果。Subquery 返回 CS、CS、Math、NULL，GEA1000 的 NULL 也在里面。`'DSA' NOT IN (...)` 的意思是 'DSA' 和每一个都不相等：

$$\text{'DSA'}\ne\text{'CS'}\ \wedge\ \text{'DSA'}\ne\text{'CS'}\ \wedge\ \text{'DSA'}\ne\text{'Math'}\ \wedge\ \text{'DSA'}\ne\text{NULL}=\text{TRUE}\wedge\text{TRUE}\wedge\text{TRUE}\wedge\text{UNKNOWN}=\text{UNKNOWN}$$

WHERE 只留 TRUE，Ben 被丢掉。对 CS、Math 的学生，有一项是 FALSE，整个是 FALSE，也被丢掉。于是一行都不剩。

换成 `WHERE NOT EXISTS (SELECT 1 FROM Course c WHERE c.dept = Student.dept)`：对 Ben，里层逐行比较，`'DSA' = NULL` 是 UNKNOWN，那一行不进结果，里层为空，NOT EXISTS 为 TRUE，Ben 留下。EXISTS 只问“有没有 TRUE 的行”，UNKNOWN 和 FALSE 一样处理，所以不受 NULL 影响。Subquery 的 column 可能有 NULL 时，用 NOT EXISTS。
:::

:::back
每个 clause 对应的 operator、join 的含义、for-all 的“找反例”思路，都来自[第 1 站](#rel)。
:::

## [ddl] Constraint、modification 与 trigger

:::skip

### 让 DBMS 替你拒绝坏数据

开头说过，文件不会拒绝 sid 5，也不会拒绝 grade `"E"`。在 SQL 里，这些规则写在 CREATE TABLE 里，之后每一次 INSERT、UPDATE、DELETE，DBMS 都检查，违反就整条语句不执行。

```sql
CREATE TABLE Dept (
  dname  TEXT PRIMARY KEY,
  office TEXT
);
CREATE TABLE Student (
  sid  INTEGER PRIMARY KEY,
  name TEXT NOT NULL,
  dept TEXT NOT NULL REFERENCES Dept(dname)
);
CREATE TABLE Course (
  cid  TEXT PRIMARY KEY,
  dept TEXT REFERENCES Dept(dname)
);
CREATE TABLE Enrolled (
  sid   INTEGER REFERENCES Student(sid) ON DELETE CASCADE,
  cid   TEXT    REFERENCES Course(cid),
  grade CHAR(1) CHECK (grade IN ('A', 'B', 'C', 'D', 'F')),
  PRIMARY KEY (sid, cid)
);
```

Dept 是为了让 dept 这个 column 也有 foreign key 可指（第 4 站会从 ER 设计里得到它）。每一种 constraint 各管一件事，在上面的数据上各试一次，PostgreSQL 的反应如下：

| 语句 | 违反的 constraint | 结果 |
|---|---|---|
| `INSERT INTO Enrolled VALUES (1, 'CS2102', 'B')` | PRIMARY KEY：(1, CS2102) 已存在 | 拒绝 |
| `INSERT INTO Enrolled VALUES (5, 'CS2102', 'B')` | FOREIGN KEY：Student 里没有 sid 5 | 拒绝 |
| `INSERT INTO Enrolled VALUES (3, 'CS2102', 'E')` | CHECK：E 不在列表里 | 拒绝 |
| `INSERT INTO Student VALUES (5, 'Eve', NULL)` | NOT NULL | 拒绝 |
| `INSERT INTO Enrolled VALUES (3, 'CS2102', NULL)` | 无 | 接受 |

PRIMARY KEY 等于 UNIQUE 加 NOT NULL。单独的 UNIQUE 允许 NULL，而且允许多个 NULL：两个 NULL 比较是 UNKNOWN，不算“相同”。Course.dept 没有写 NOT NULL，所以 GEA1000 可以是 NULL，foreign key 对 NULL 不做检查。

:::edge CHECK 放过 UNKNOWN，WHERE 丢掉 UNKNOWN
上表最后一行，grade 是 NULL，`NULL IN ('A', ..., 'F')` 是 UNKNOWN，CHECK 却接受了。规则是：CHECK 只在条件为 FALSE 时拒绝。和第 2 站对照，WHERE 只在条件为 TRUE 时保留。两条规则都偏向“不知道就放行”的一边：CHECK 不知道就不拒绝，WHERE 不知道就不返回。要禁止 NULL，单独写 NOT NULL。
:::

### Foreign key 被违反时怎么办

INSERT 一个不存在的 sid，拒绝就行。反方向更麻烦：删掉一个学生，Enrolled 里还有行指着他。DBMS 有几种做法，在 REFERENCES 后面用 ON DELETE 指定：

| action | 删掉被 reference 的那一行时 |
|---|---|
| NO ACTION（默认）、RESTRICT | 拒绝这条 DELETE |
| CASCADE | referencing 的行一起删 |
| SET NULL | referencing 的 column 改成 NULL |
| SET DEFAULT | 改成 column 的 default 值 |

::fig[cs2102-fk] 执行 `DELETE FROM Student WHERE sid = 1`。左边 Enrolled.sid 设了 ON DELETE CASCADE，右边用默认的 NO ACTION。

选哪一个取决于 referencing 的行离开被 reference 的行还有没有意义。Ana 的选课记录离开 Ana 没有意义，所以 Enrolled.sid 用 CASCADE。Student.dept 用默认的 NO ACTION：`DELETE FROM Dept WHERE dname = 'Math'` 会被拒绝，报 `Key (dname)=(Math) is still referenced from table "student"`，因为 Dee 不能凭空没有 dept。SET NULL 适合“关系断了，行本身还有用”，比如课的开课 dept 撤销后课还在；但 Student.dept 有 NOT NULL，对它用 SET NULL 会在执行时失败。ON UPDATE 同理，管的是被 reference 的 key 改值。

### Modification

INSERT、UPDATE、DELETE 的 WHERE 和 SELECT 的 WHERE 是同一套规则，也可以带 subquery。“把 CS 学生在 CS2040 的 grade 都改成 A”：

```sql
UPDATE Enrolled SET grade = 'A'
WHERE cid = 'CS2040'
  AND sid IN (SELECT sid FROM Student WHERE dept = 'CS');
```

Subquery 得到 {1, 3}，被改的是 (1, CS2040) 和 (3, CS2040)。

### CHECK 管不到的规则：trigger

学校规定每个学生最多选 2 门课。能不能写成 CHECK？CHECK 的条件只能看正在插入的这一行：`(1, 'MA2101', NULL)` 这一行本身没有任何问题，问题在于 Enrolled 里已经有两行 sid 为 1。要检查它，必须在插入前去数别的行。

Trigger 就是“某个 table 发生某种修改时，自动执行的一段程序”。PostgreSQL 里分两步写：先写一个返回 TRIGGER 的 function，再把它挂到 table 上。

```sql
CREATE FUNCTION check_load() RETURNS TRIGGER AS $$
DECLARE k INTEGER;
BEGIN
  SELECT COUNT(*) INTO k FROM Enrolled WHERE sid = NEW.sid;
  IF k >= 2 THEN
    RAISE EXCEPTION 'student % already takes % courses', NEW.sid, k;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER max_load
BEFORE INSERT ON Enrolled
FOR EACH ROW EXECUTE FUNCTION check_load();
```

`NEW` 是即将插入的那一行（UPDATE 时还有 `OLD`，是改之前的那一行；DELETE 只有 `OLD`）。逐个执行两次 INSERT：

- `INSERT INTO Enrolled VALUES (1, 'MA2101', NULL)`：NEW.sid = 1，k = 2，RAISE EXCEPTION，整条 INSERT 失败，错误信息是 `student 1 already takes 2 courses`。
- `INSERT INTO Enrolled VALUES (3, 'CS2102', NULL)`：k = 1，RETURN NEW，这一行照常插入。

挂 trigger 时有两个选择：

**BEFORE 还是 AFTER。** BEFORE 在修改生效前执行，可以拦下修改，也可以改写 NEW 再返回（比如自动把 grade 转成大写）。AFTER 在修改生效后执行，返回值被忽略，适合“已经改了，再去改别的 table”，比如写一条 log。

**FOR EACH ROW 还是 FOR EACH STATEMENT。** 一条 INSERT 插入三行，ROW trigger 执行三次，每次有自己的 NEW；STATEMENT trigger 只执行一次，没有 NEW。

一条 INSERT 插入多行时，ROW trigger 在每行之前执行，能看到同一条语句里已经插进去的行。Cai 有 1 门课时执行 `INSERT INTO Enrolled VALUES (3, 'CS2102', NULL), (3, 'MA2101', NULL)`：第一行之前 k = 1，插入；第二行之前 k = 2，被拦下。

:::wrong BEFORE trigger 返回 NULL，DBMS 会报错
把上面的 RAISE EXCEPTION 改成 RETURN NULL，再执行 `INSERT INTO Enrolled VALUES (1, 'MA2101', NULL)`。PostgreSQL 的回应是 `INSERT 0 0`，没有任何错误：BEFORE ROW trigger 返回 NULL 的意思是“跳过这一行”，语句本身成功，只是插入了 0 行。调用它的程序如果只看有没有报错，会以为选课成功了。要让调用者知道规则被违反，用 RAISE EXCEPTION；它让整条语句失败，同一条语句里已经插入的行也一起撤销。
:::

:::back
CHECK 的 UNKNOWN 规则对照的是[第 2 站](#sql)的 three-valued logic。第 4 站会遇到 ER diagram 里一种 foreign key 表达不了的 constraint，那时又要用到 trigger。
:::

## [er] ER 设计

:::skip
能把一段需求画成带 key constraint、participation constraint 和 weak entity 的 ER diagram，并翻译成 CREATE TABLE，说得出 many-to-many relationship 为什么要单独成表，就可以去第 5 站。

### 先画需求，再写 table

前三站假设 table 已经设计好了。开头那张 flat table 说明，设计错了，后面的 SQL 写得再好也会出事。设计时不直接想 table，先把需求里的“东西”和“东西之间的联系”画出来，再按规则翻译成 table。这张图叫 ER diagram（entity-relationship）。

需求是：

1. 每个学生有 sid 和 name，每门课有 cid 和 title，每个 dept 有 dname 和 office。
2. 学生可以选任意多门课，一门课可以有任意多个学生，每次选课有一个 grade。
3. 每个学生恰好属于一个 dept。
4. 每门课最多属于一个 dept，通识课可以不属于任何 dept。
5. 每门课有若干 tutorial group，编号 1、2、3……在每门课里各自从 1 开始。

### Entity、attribute、relationship

**Entity set** 是一类东西，画成矩形：Student、Course、Dept。它的 **attribute** 画成椭圆，key attribute 加下划线。

**Relationship set** 是 entity 之间的一类联系，画成菱形：Enrolls 连接 Student 和 Course。Relationship 也可以有 attribute。

grade 该挂在哪里？挂在 Student 上，Ana 有两门课两个 grade，一个 attribute 装不下；挂在 Course 上，CS2102 有 Ana 的 A 和 Ben 的 B，也装不下。grade 由“哪个学生、哪门课”这一对决定，所以它是 Enrolls 的 attribute。一个 relationship 由它连接的 entity 确定：Ana 和 CS2102 之间最多只有一个 Enrolls。

### 一个 entity 能参与几次

需求 2 和需求 3 都在说两个 entity set 之间的联系，区别在“一个学生能连几条”。把实际的 instance 画出来就看清了。

::fig[cs2102-erinst] 上面是两个 relationship set 的 instance，每条线是一个 relationship。下面是 ER diagram 里对应的画法。

两种限制分开记：

- **Key constraint**（箭头）：Student 一侧画箭头，表示每个 Student **最多**参与一个 MajorIn。
- **Participation constraint**（粗线）：Student 一侧画粗线，表示每个 Student **至少**参与一个 MajorIn，叫 total participation；细线是 partial participation，可以一个都没有。

两个合起来，粗线加箭头，就是需求 3 的“恰好一个”。需求 4 只有“最多一个”，所以 Course 到 Offers 是细线加箭头。Enrolls 两边都是细线：Ana 连 2 条，Dee 连 0 条，都允许。

教材的叫法：Enrolls 是 many-to-many；MajorIn 从 Student 看是 many-to-one（多个学生对一个 dept）。

### Weak entity 与 ISA

需求 5 的 tutorial group 编号 1 在 CS2102 和 CS2040 里各有一个，光凭编号区分不了，必须带上课号。这样的 entity set 叫 **weak entity set**：它的 key 一部分是自己的 **partial key**（group），一部分借自 owner entity（Course 的 cid）。画法是双线矩形，连接它和 owner 的 identifying relationship 画成双线菱形；每个 tutorial 恰好属于一门课，所以 Tutorial 一侧是粗线加箭头。

::fig[cs2102-er] 需求 1 到 5 画成的 ER diagram。

**ISA** 表达 subclass：如果交换生还要额外记 home_univ，就画 ExchangeStudent ISA Student。Subclass 自动继承 Student 的 key、attribute 和 relationship（交换生也有 sid、也能选课），只加自己的 attribute。ISA 上可以再标两种约束：overlap（一个 entity 能否同时属于两个 subclass）和 covering（每个 Student 是否必须属于某个 subclass）。

### 翻译成 table

规则按 ER diagram 里的每种记号逐个给：

| ER 记号 | 翻译成 |
|---|---|
| entity set | 一个 table，key 是 primary key |
| many-to-many 的 relationship set | 一个 table，column 是两边的 key 加自己的 attribute，primary key 是两边 key 合起来，各自是 foreign key |
| 带 key constraint 的 relationship set | 合进“箭头那一边”的 entity 的 table：加一个指向另一边的 foreign key |
| 再加上 total participation | 那个 foreign key 加 NOT NULL |
| weak entity set | 一个 table，primary key 是 owner 的 key 加 partial key，owner 的 key 是 foreign key，ON DELETE CASCADE |
| ISA 的 subclass | 一个 table，primary key 同时是指向 superclass 的 foreign key，ON DELETE CASCADE |

用在上面的 diagram 上：

```sql
CREATE TABLE Dept    (dname TEXT PRIMARY KEY, office TEXT);
CREATE TABLE Student (sid INTEGER PRIMARY KEY, name TEXT,
                      dept TEXT NOT NULL REFERENCES Dept(dname));      -- MajorIn
CREATE TABLE Course  (cid TEXT PRIMARY KEY, title TEXT,
                      dept TEXT REFERENCES Dept(dname));               -- Offers
CREATE TABLE Enrolls (sid INTEGER REFERENCES Student(sid),
                      cid TEXT REFERENCES Course(cid),
                      grade CHAR(1),
                      PRIMARY KEY (sid, cid));
CREATE TABLE Tutorial (cid TEXT REFERENCES Course(cid) ON DELETE CASCADE,
                       grp INTEGER,
                       PRIMARY KEY (cid, grp));
```

逐条对照：MajorIn 有箭头，合进 Student，变成 dept column；有粗线，加 NOT NULL。Offers 有箭头没有粗线，合进 Course，dept 可以是 NULL，这正是 GEA1000。Enrolls 两边都没有箭头，单独成表。Tutorial 的 primary key 是 (cid, grp)，课删了 tutorial 跟着删。

这五个 table 和第 3 站写的 schema 一样（多了 title 和 Tutorial），开头那张 flat table 的三次事故在这里一次也不会发生：Ana 的 dept 只存在 Student 里一处；删掉 Cai 的选课不影响 Student；Dee 不选课也能进 Student。

:::wrong Many-to-many 的 relationship 也可以合进一边的 table，省一个 table
把 Enrolls 合进 Student，给 Student 加 cid 和 grade 两个 column。Ana 选了两门课，就要两行 Student，sid 不再是 key，name 和 dept 重复两遍；Dee 没选课，cid 只能空着。这正好退回到开头那张 flat table，三次事故一个不少。合并只在“箭头那一边每个 entity 最多对应一个”时才成立，因为那时新加的 column 每行只需要一个值。

## [fd] Functional dependency 与 closure

:::skip
能从一组 FD 求 attribute closure、找出全部 candidate key、求 minimal cover，并能求 FD 在一部分 attribute 上的 projection，就可以去第 6 站。
:::

### Redundancy 从哪里来

第 4 站靠画图避开了开头的事故，但画图靠经验。假如拿到的就是那张 flat table，有没有办法不靠经验，判断它该怎么拆？

看那张 table 里 Ana 的两行：name 和 dept 重复了，因为“sid 是 1 的学生叫 Ana、属于 CS”是一条规则，每出现一次 sid 1，就得再写一遍。grade 没有重复，因为它由 (sid, cid) 决定，每个 (sid, cid) 只出现一次。Redundancy 的来源是：**某组 attribute 决定了另一些 attribute，而这组 attribute 在 table 里会重复出现。**

### 定义

$X\to Y$ 读作“$X$ functionally determines $Y$”：任意两个 tuple，如果在 $X$ 上的值相同，在 $Y$ 上的值也相同。

在 flat table 上检验两条：

- sid $\to$ dept：sid 为 1 的两行，dept 都是 CS；sid 为 2 的两行，dept 都是 DSA；sid 3 只有一行。没有违反。
- cid $\to$ grade：cid 为 CS2102 的两行，grade 一个是 A、一个是 B。违反。

$X\to Y$ 中 $Y\subseteq X$ 的叫 trivial，比如 {sid, cid} $\to$ sid，任何 instance 都满足，不提供信息。

**用 FD 重新定义 key。** $X$ 是 superkey，当且仅当 $X\to$（所有 attribute）。去掉任何一个 attribute 后都不再是 superkey 的 superkey 叫 candidate key。这和第 1 站“任意两个 tuple 在 key 上不同”说的是同一件事：两个 tuple 如果在 $X$ 上相同，就在所有 attribute 上相同，那它们是同一个 tuple。

:::wrong 当前的数据满足 $X\to Y$，所以 $X\to Y$ 是一条 FD
Flat table 里 name 互不相同，所以 name $\to$ sid 在这个 instance 上成立：没有两行 name 相同而 sid 不同。可是明天来一个也叫 Ana 的学生，这条“规则”就破了。FD 是关于所有合法 instance 的断言，来自需求（“每个学生有唯一的 sid”），不来自数据。一个 instance 只能**否定**一条 FD（像上面的 cid $\to$ grade），不能**证明**一条 FD。
:::

### 从几条 FD 推出更多

把 flat table 扩充成 R(sid, name, dept, office, cid, grade)，office 是 dept 的办公室。需求给出

$$F=\{\ \text{sid}\to\text{name},\quad \text{sid}\to\text{dept},\quad \text{dept}\to\text{office},\quad \text{sid},\text{cid}\to\text{grade}\ \}$$

sid $\to$ office 没写，但显然成立：sid 相同的两行 dept 相同，dept 相同的两行 office 相同。这种推理可以归结成三条规则，叫 Armstrong's axioms：

- **Reflexivity**：$Y\subseteq X$，则 $X\to Y$。
- **Augmentation**：$X\to Y$，则 $XZ\to YZ$。
- **Transitivity**：$X\to Y$ 且 $Y\to Z$，则 $X\to Z$。

sid $\to$ office 就是 transitivity 用在 sid $\to$ dept 和 dept $\to$ office 上。

由它们可以推出两条常用的：**union**，$X\to Y$ 且 $X\to Z$ 则 $X\to YZ$；**decomposition**，$X\to YZ$ 则 $X\to Y$。推一下 union：$X\to Y$ 两边 augment 上 $X$，得 $X\to XY$；$X\to Z$ 两边 augment 上 $Y$，得 $XY\to YZ$；transitivity 得 $X\to YZ$。

所以右边有几个 attribute 无所谓，可以拆成每条 FD 右边只有一个 attribute，也可以合起来写。左边不能拆：sid, cid $\to$ grade 不能推出 sid $\to$ grade。

所有能从 $F$ 推出的 FD 构成 $F^+$，叫 closure of $F$。Armstrong's axioms 是 sound 的（推出的都真成立）和 complete 的（真成立的都能推出），所以“$X\to Y$ 是否成立”就是“$X\to Y$ 是否在 $F^+$ 里”。

### Attribute closure：一个 algorithm 回答所有问题

$F^+$ 可能很大，直接列出来不现实。实际只需要一个更小的东西：给定 $X$，它能决定哪些 attribute。这个 set 记作 $X^+$，叫 attribute closure。

Algorithm：从 $X^+=X$ 开始；反复扫 $F$，只要某条 $U\to V$ 的左边 $U$ 全在 $X^+$ 里，就把 $V$ 加进 $X^+$；扫完一整遍没有新东西就停。

每加一个 attribute 都有依据：$X\to U$（因为 $U\subseteq X^+$，归纳地成立）和 $U\to V$，transitivity 给出 $X\to V$。所以 $X^+$ 里的都被 $X$ 决定。反过来，停下时不在 $X^+$ 里的 attribute 确实不被 $X$ 决定（completeness 的证明构造一个两行的 instance：两行在 $X^+$ 上相同、其余都不同，它满足 $F$ 里每一条 FD，却违反 $X\to A$），这里不展开。

在 R(sid, name, dept, office, cid, grade) 上算 $\{\text{sid}\}^+$：从 {sid} 开始，sid $\to$ name、sid $\to$ dept 加入 name、dept，dept $\to$ office 加入 office，sid, cid $\to$ grade 的左边缺 cid，用不上。结果 {sid, name, dept, office}。不含 cid 和 grade，所以 sid 不是 superkey。$\{\text{sid},\text{cid}\}^+$ 再加上 grade，是全部 attribute，所以 {sid, cid} 是 superkey。

再看一个只用字母的例子，考试多是这种形式。R(A, B, C, D, E)，

$$F=\{\ AB\to C,\quad C\to D,\quad D\to B,\quad D\to E\ \}$$

::fig[cs2102-closure] 计算 $\{A,C\}^+$。左边亮的是正在检查的 FD，右边是 closure 的当前内容。

第一遍：AB $\to$ C 左边缺 B，跳过；C $\to$ D 加入 D；D $\to$ B 加入 B；D $\to$ E 加入 E。第二遍：AB $\to$ C 左边满足了，但 C 已经在里面；没有新东西，停。$\{A,C\}^+=ABCDE$，AC 是 superkey。

Attribute closure 能回答的问题：

| 问题 | 做法 |
|---|---|
| $X\to Y$ 成立吗 | 看 $Y\subseteq X^+$ |
| $X$ 是 superkey 吗 | 看 $X^+$ 是不是全部 attribute |
| $X$ 是 candidate key 吗 | 是 superkey，并且去掉任何一个 attribute 后都不是 |

### 找出全部 candidate key

逐个试 R(A, B, C, D, E) 的 $2^5$ 个 subset 太慢。先用两条观察缩小范围：

- 一个 attribute 不出现在任何 FD 的右边，就没有别的东西能决定它，它必须在每个 key 里。这里是 A。
- 一个 attribute 只出现在右边、从不出现在左边，它不帮助决定任何别的东西，任何 key 都不需要它。这里是 E。

先试 A 本身：$A^+=A$，不够。再试 A 加上 B、C、D 中的一个：

$$\{A,B\}^+=ABCDE,\qquad\{A,C\}^+=ABCDE,\qquad\{A,D\}^+:\ AD\xrightarrow{D\to B}ABD\xrightarrow{D\to E}ABDE\xrightarrow{AB\to C}ABCDE$$

三个都是 superkey。去掉任何一个 attribute 只剩单个 attribute，A 已经试过不行；$B^+=B$，$C^+=BCDE$，$D^+=BDE$，都不含 A。所以三个都是 candidate key。含有其中某一个的更大 set（如 ABC）是 superkey 但不 minimal。全部 candidate key 是 **AB、AC、AD**。

出现在某个 candidate key 里的 attribute 叫 **prime attribute**，这里是 A、B、C、D；E 是 non-prime。第 6 站的 3NF 要用到这个区分。

### Minimal cover：把 F 化到最简

同一个 $F^+$ 可以由很多组 FD 生成。第 6 站的 3NF algorithm 需要最简的那一组，叫 minimal cover，满足三条：每条 FD 右边只有一个 attribute；左边没有多余的 attribute；没有一条 FD 能由其余的推出。

需求有时写得很啰嗦。假设拿到的是

$$F=\{\ \text{sid}\to\text{name},\ \text{sid}\to\text{dept},\ \text{sid}\to\text{office},\ \text{dept}\to\text{office},\ \text{sid},\text{cid}\to\text{grade},\ \text{sid},\text{cid}\to\text{name}\ \}$$

**第一步：右边拆成单个 attribute。** 已经是了。

**第二步：去掉左边多余的 attribute。** 对左边有多个 attribute 的 FD，试着去掉一个：如果剩下的部分在 $F$ 下的 closure 已经包含右边，去掉的那个就是多余的。

- sid, cid $\to$ name：试去掉 cid，$\{\text{sid}\}^+=\{\text{sid},\text{name},\text{dept},\text{office}\}$ 含 name，所以 cid 多余，变成 sid $\to$ name，和第一条重复，合并。
- sid, cid $\to$ grade：$\{\text{sid}\}^+$ 不含 grade，$\{\text{cid}\}^+=\{\text{cid}\}$ 也不含，两个都不能去。

**第三步：去掉多余的 FD。** 逐条试：暂时拿掉它，用剩下的 FD 算左边的 closure，如果仍包含右边，这条就是多余的。

- sid $\to$ office：拿掉后，$\{\text{sid}\}^+$ 经 sid $\to$ dept、dept $\to$ office 仍得到 office。多余，删去。
- sid $\to$ dept：拿掉后（sid $\to$ office 已删），$\{\text{sid}\}^+=\{\text{sid},\text{name}\}$，没有 dept。保留。
- dept $\to$ office：拿掉后 $\{\text{dept}\}^+=\{\text{dept}\}$。保留。sid $\to$ name、sid, cid $\to$ grade 同样保留。

$$F_{\min}=\{\ \text{sid}\to\text{name},\ \text{sid}\to\text{dept},\ \text{dept}\to\text{office},\ \text{sid},\text{cid}\to\text{grade}\ \}$$

第二步必须在第三步之前，因为左边变短以后 FD 变强了，原来不多余的 FD 可能变得多余。看 $F=\{A\to B,\ AB\to C,\ C\to B\}$。先做第三步：拿掉 $A\to B$，$A^+=A$；拿掉 $AB\to C$，$\{A,B\}^+=AB$；拿掉 $C\to B$，$C^+=C$；三条都保留。再做第二步：$A^+=ABC$ 含 C，B 多余，$AB\to C$ 变成 $A\to C$。得到 $\{A\to B,\ A\to C,\ C\to B\}$，其中 $A\to B$ 可以由 $A\to C$、$C\to B$ 推出，不是 minimal。按正确的顺序，先把 $AB\to C$ 化成 $A\to C$，第三步就会删掉 $A\to B$，得到 $\{A\to C,\ C\to B\}$。

### FD 在一部分 attribute 上的 projection

第 6 站要把 table 拆开，拆出来的 table 上有哪些 FD？R(A, B, C, D, E) 拆出 R₁(B, C, D, E)，原来的四条里 C $\to$ D、D $\to$ B、D $\to$ E 的 attribute 都在 R₁ 里，AB $\to$ C 不在。但 R₁ 上成立的 FD 不止这三条。

求法：对 R₁ 的每个 subset $X$，算 $X^+$（用原来的整个 $F$），再和 R₁ 取 intersection，$X\to(X^+\cap R_1)-X$ 就是 R₁ 上的 FD。$C^+=BCDE$，所以 C $\to$ BDE；$D^+=BDE$，所以 D $\to$ BE；其余 subset 给出的都能由这两条推出。

这个“取 intersection”不能省。设 R(A, B, C)，$F=\{A\to B,\ B\to C\}$，拆出 R'(A, C)。$F$ 里没有一条 FD 的 attribute 全在 {A, C} 里，看上去 R' 上没有 FD；可是 $A^+=ABC$，与 {A, C} 取 intersection 得 A $\to$ C。漏掉它，就会以为 R' 上 A 和 C 毫无关系。第 6 站有一个例子正是栽在这里。

:::back
Key 的定义来自[第 1 站](#rel)；第 2 站 GROUP BY primary key 的 edge case 就是 sid $\to$ name 这条 FD。
:::

:::from
FD 的定义、trivial FD、用 FD 定义 key、Armstrong's axioms 及推出的 splitting / combining 规则、attribute closure 的 algorithm 和“用 closure 检查 FD、检查 superkey”，跟的是 [Duke CompSci 316 Spring 2020 Lecture 06](https://courses.cs.duke.edu/spring20/compsci316/Lectures/06-design-theory.pdf)（全文）；它的例子是 UserJoinsGroup(uid, uname, twitterid, gid, fromDate)，这里换成了选课。Union 的推导、找 key 时“只在左边 / 只在右边”的两条观察、minimal cover 的三步、FD projection 和 $A\to C$ 的反例凭自己的知识写；R(A, B, C, D, E) 的 closure、candidate key 和 projection 用一段 Python 枚举了全部 subset 核对过。

## [nf] Normalization：BCNF 与 3NF

:::skip
能判断一个 schema 的 normal form，能做 BCNF decomposition 并检查 lossless 和 dependency preservation，能用 minimal cover 做 3NF synthesis，就完成了这门课的设计部分。
:::

### 把“redundancy”写成一条可以检查的条件

第 5 站找到了 redundancy 的来源：$X\to Y$ 成立，而 $X$ 会在 table 里重复出现。$X$ 什么时候不会重复？当 $X$ 是 superkey 时，两行在 $X$ 上相同就是同一行，$X$ 的每个值只出现一次，$Y$ 也就只写一次。

**BCNF**（Boyce–Codd normal form）：对每一条 non-trivial 的 $X\to Y$，$X$ 都是 superkey。

在 R(sid, name, dept, office, cid, grade) 上检查：sid $\to$ name 是 non-trivial，$\{\text{sid}\}^+$ 不含 cid，sid 不是 superkey。违反 BCNF，这正是开头三次事故的根源。

### 拆开：用违反的那条 FD 来拆

拆的办法由违反的 FD 直接给出。设 $X\to Y$ 违反 BCNF，把 R 拆成两个：

$$R_1=X^+\ (\text{与 }R\text{ 取 intersection}),\qquad R_2=X\cup(R-X^+)$$

$R_1$ 里装“$X$ 决定的所有东西”，$X$ 在 $R_1$ 里是 key，不再重复。$R_2$ 保留 $X$ 作为两个 table 的连接点，加上剩下的 attribute。

在 R 上做：$\{\text{sid}\}^+=\{\text{sid},\text{name},\text{dept},\text{office}\}$，

$$R_1(\text{sid},\text{name},\text{dept},\text{office}),\qquad R_2(\text{sid},\text{cid},\text{grade})$$

$R_2$ 上的 FD 只有 sid, cid $\to$ grade，key 是 (sid, cid)，BCNF。$R_1$ 上的 key 是 sid，但 dept $\to$ office 的 dept 不是 superkey，继续拆：$\{\text{dept}\}^+\cap R_1=\{\text{dept},\text{office}\}$，

$$R_{11}(\text{dept},\text{office}),\qquad R_{12}(\text{sid},\text{name},\text{dept})$$

最后三个 table：Dept(dept, office)、Student(sid, name, dept)、Enrolled(sid, cid, grade)。和第 4 站从 ER diagram 翻译出来的一样，这一次没有用任何“经验”，只用了 FD 和 closure。

### 拆了能拼回去吗：lossless join

拆开的 table 要能 join 回原来的 table，不多不少。拆错了会怎样？把 Student(sid, name, dept) 拆成 (sid, dept) 和 (name, dept)：

::fig[cs2102-lossy] 按 dept join 回去，CS 的两个 sid 和两个 name 交叉配对，多出两行。

多出来的 (1, Cai, CS) 和 (3, Ana, CS) 让结果没法区分“1 号是 Ana 还是 Cai”。行数变多了，信息却少了，这叫 lossy decomposition。

问题出在连接点 dept 上：一个 dept 值在两边都对应多行，join 时就两两交叉。如果连接点在某一边是 key，那一边每个值只有一行，另一边的每一行只能配上唯一的那一行，不会交叉。这给出判断条件：

> 把 R 拆成 $R_1$、$R_2$ 是 lossless 的，当且仅当 $R_1\cap R_2\to R_1$ 或 $R_1\cap R_2\to R_2$。

用它检验：(sid, dept) 和 (name, dept) 的 intersection 是 dept，$\{\text{dept}\}^+$ 不含 sid 也不含 name，lossy。改成 (sid, name) 和 (sid, dept)，intersection sid 决定两边，lossless。

BCNF 的拆法自动满足这个条件：$R_1\cap R_2=X$，而 $R_1=X^+$，所以 $X\to R_1$。上面 R 的两次拆分，intersection 分别是 sid 和 dept，都是 key。

### 拆完以后，还能检查每条 FD 吗

字母的例子。R(A, B, C, D, E)，$F=\{AB\to C,\ C\to D,\ D\to B,\ D\to E\}$，第 5 站算出 candidate key 是 AB、AC、AD。

::fig[cs2102-bcnf] BCNF decomposition 一层一层展开。每一步写出用来拆的 FD 和拆出来的两个 table。

逐步核对：

1. C $\to$ D 违反（$C^+=BCDE$，C 不是 superkey）。$R_1=C^+=BCDE$，$R_2=C\cup(R-C^+)=AC$。
2. $R_1$(B, C, D, E) 上的 FD 要用 projection 求（第 5 站算过）：C $\to$ BDE、D $\to$ BE。C 是 $R_1$ 的 key；D $\to$ B 的 D 不是。$R_{11}=D^+\cap R_1=BDE$，$R_{12}=D\cup(R_1-BDE)=CD$。
3. $R_{11}$(B, D, E) 上 D $\to$ BE，key 是 D，BCNF。$R_{12}$(C, D) 和 $R_2$(A, C) 只有两个 attribute，一定是 BCNF（两个 attribute 的 relation 上，non-trivial FD 的左边是单个 attribute，它决定另一个，所以是 key）。

结果是 (B, D, E)、(C, D)、(A, C)，都是 BCNF，join 回去 lossless。但 AB $\to$ C 去哪了？A、B、C 不在同一个 table 里，这条 FD 没法在任何一个 table 内部检查。只用三个 table 上的 FD（D $\to$ BE、C $\to$ D，以及 (A, C) 上什么也没有）算 $\{A,B\}^+$，得到的还是 AB，推不出 C。

一个 decomposition 若满足“各个 table 上 projection 出来的 FD 合起来，能推出原来的全部 $F$”，就叫 **dependency preserving**。这个例子不是。

丢了 dependency 意味着什么，用一个有含义的例子看。每个学生在每门课有一个 tutor，每个 tutor 只带一门课：

$$\text{Tutoring}(\text{sid},\text{cid},\text{tutor}),\qquad F=\{\ \text{sid},\text{cid}\to\text{tutor},\quad \text{tutor}\to\text{cid}\ \}$$

$\{\text{sid},\text{tutor}\}^+$ 经 tutor $\to$ cid 得到全部，所以 candidate key 是 (sid, cid) 和 (sid, tutor)。tutor $\to$ cid 的 tutor 不是 superkey，违反 BCNF。按它拆：TutorOf(tutor, cid) 和 Assigned(sid, tutor)。

现在在两个 table 里各插入两行：

| TutorOf | |
|---|---|
| **tutor** | **cid** |
| Tom | CS2102 |
| Uma | CS2102 |

| Assigned | |
|---|---|
| **sid** | **tutor** |
| 1 | Tom |
| 1 | Uma |

TutorOf 里 tutor 是 key，没有重复；Assigned 里 (sid, tutor) 是 key，也没有重复。两个 table 各自的 constraint 全部满足，DBMS 一行都不会拒绝。Join 回去却是 (1, CS2102, Tom) 和 (1, CS2102, Uma)：Ana 在 CS2102 有两个 tutor，违反了 sid, cid $\to$ tutor。要防止它，每次插入都得先 join 两个 table 再检查，也就是写第 3 站那种 trigger。

这不是拆法选得不好。Tutoring 只有三个 attribute，BCNF 要求把 tutor $\to$ cid 单独拆出去，任何一种拆法都会把 sid, cid $\to$ tutor 的三个 attribute 分到不同的 table 里。**有些 schema 不存在既是 BCNF、又 dependency preserving 的 decomposition。**

### 3NF：为了留住 dependency，容忍一点 redundancy

把 BCNF 的条件放宽一点：

**3NF**：对每一条 non-trivial 的 $X\to A$（$A$ 是单个 attribute），$X$ 是 superkey，**或者 $A$ 是 prime attribute**。

Tutoring 上 tutor $\to$ cid 的 tutor 不是 superkey，但 cid 在 candidate key (sid, cid) 里，是 prime。所以 Tutoring 是 3NF，不用拆，sid, cid $\to$ tutor 作为 primary key 由 DBMS 直接检查。代价是 tutor $\to$ cid 带来的 redundancy：如果 sid 1 和 sid 3 都由 Tom 带，(1, CS2102, Tom) 和 (3, CS2102, Tom) 两行里“Tom 带 CS2102”存了两遍。

回到 R(A, B, C, D, E)：prime attribute 是 A、B、C、D。C $\to$ D、D $\to$ B 的右边是 prime，3NF 允许；D $\to$ E 的 D 不是 superkey、E 不是 prime，违反 3NF。

### 3NF synthesis

3NF 有一个保证同时 lossless 和 dependency preserving 的 algorithm，从 minimal cover 直接拼出 table：

1. 求 $F$ 的 minimal cover。
2. 左边相同的 FD 归成一组，每组建一个 table，attribute 是左边加上这一组所有的右边。
3. 如果没有一个 table 包含某个 candidate key，再加一个只含某个 candidate key 的 table。
4. 如果某个 table 的 attribute 完全包含在另一个 table 里，删掉它。

每条 FD 都整条落在第 2 步的某个 table 里，所以 dependency preserving；第 3 步那个含 candidate key 的 table 保证 lossless。

在 R(A, B, C, D, E) 上做。第 5 站的检验方法逐条试：AB $\to$ C 左边去掉 A 或 B，$B^+=B$、$A^+=A$，都不含 C，不能去；四条 FD 逐条拿掉都推不回来。所以 $F$ 本身已经是 minimal cover。按左边分组：AB 一组、C 一组、D 一组（D $\to$ B 和 D $\to$ E 合并）：

$$(A,B,C),\qquad(C,D),\qquad(B,D,E)$$

(A, B, C) 包含 candidate key AB，第 3 步不用加；没有谁包含谁。和 BCNF 的结果 (A, C)、(C, D)、(B, D, E) 对比，区别只在第一个 table：3NF 把 AB $\to$ C 整条留在 (A, B, C) 里。

(A, B, C) 是不是 BCNF？用 projection：$C^+=BCDE$，与 ABC 取 intersection 得 C $\to$ B，而 C 在 (A, B, C) 里不是 superkey。所以它不是 BCNF，只是 3NF（B 是 prime）。这就是为了保住 AB $\to$ C 付出的代价。

在 R(sid, name, dept, office, cid, grade) 上，第 5 站得到的 minimal cover 按左边分组得 (sid, name, dept)、(dept, office)、(sid, cid, grade)，第三个包含 candidate key (sid, cid)。和 BCNF 的结果相同：这个 schema 没有 BCNF 与 dependency 之间的冲突。

:::wrong 拆完之后，检查每个 table 里“原来那几条 FD”就知道它是不是 BCNF
3NF synthesis 得到的 (A, B, C)：原来的 $F$ 里 attribute 全落在 {A, B, C} 中的只有 AB $\to$ C，AB 是这个 table 的 key，看上去是 BCNF。可是 C $\to$ D $\to$ B 这条链经过不在表里的 D，推出的 C $\to$ B 在 (A, B, C) 上同样成立，C 不是 superkey。只看原来的 FD 会漏掉它。判断拆出来的 table 时，必须用第 5 站的 projection：对 subset 求 closure，再与 table 的 attribute 取 intersection。
:::

### 2NF 和整个层级

**1NF**：每个 attribute 的值是 atomic 的，不在一格里存一个 list。本页所有 table 都是 1NF。

**2NF**：没有 non-prime attribute 只依赖于某个 candidate key 的一部分（partial dependency）。R(sid, name, dept, office, cid, grade) 的唯一 candidate key 是 (sid, cid)，name、dept、office 都只依赖于 sid，违反 2NF。拆出的 $R_1$(sid, name, dept, office) 的 key 只有一个 attribute，不可能有 partial dependency，是 2NF；但 dept $\to$ office 中 dept 不是 superkey、office 不是 prime，不是 3NF。sid $\to$ dept $\to$ office 这种经过 non-key attribute 的依赖叫 transitive dependency，3NF 要排除的正是它。

每一级都比上一级严格：

$$\text{BCNF}\subset\text{3NF}\subset\text{2NF}\subset\text{1NF}$$

BCNF $\subset$ 3NF 直接从定义看出：BCNF 要求 $X$ 是 superkey，3NF 允许“$X$ 是 superkey 或 $A$ 是 prime”，条件更宽。

| | 消除 FD 带来的 redundancy | Lossless join | Dependency preserving |
|---|---|---|---|
| BCNF decomposition | 完全 | 保证 | 不保证 |
| 3NF synthesis | 可能剩一些 | 保证 | 保证 |

:::edge Normalization 不是越彻底越好
Normalize 之后，原来一行能读出的东西要 join 几个 table 才能拼回来，第 1 站算过 join 的代价。读多写少的系统（报表、分析）常常故意保留 redundancy，叫 denormalization，用写入时多维护几份换读取时少做 join。CMU 15-445 的 notes 也提到，实际系统里 schema 并不总是按 normal form 设计的。这门课考的是 normalization 本身，设计取舍以题目给的需求为准。
:::

:::
