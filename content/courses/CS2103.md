先看四次失败。每一次，代码本身都能跑。

**第一次。** Alice 和 Bob 各自把 `AddressBook.java` 拷到自己电脑上改。Alice 加了一个 `find` method，先传回共享文件夹；Bob 改了 `delete` 的 bug，后传回去。Bob 的文件里没有 `find`，于是 Alice 的工作消失了，谁也没有收到任何警告。

::fig[cs2103-lost] 两个人从同一个版本出发，各改各的，后存的那一份整个覆盖了先存的那一份。

**第二次。** 图书馆系统的需求只有一句 “Members should be able to renew a borrowed book.” 团队交出一个能用的实现：任何时候都能续借、次数不限。图书馆员看了说不行：最多续两次，有人预约的书不能续，过期的书要先交罚款。这三条需求里一个字都没有。

**第三次。** 团队决定把数据从文本文件换成 JSON。改完 `Storage` 之后，`Ui` 有两处、`Logic` 有三处、四个 test 都要跟着改，因为它们都直接读过文件里的字段。

**第四次。** `isValidMonth(int m)` 测了 `3`、`6`、`9`，全部通过。上线后 12 月的数据全被拒收：代码里写的是 `m < 12`。

四次失败都和“程序写得对不对”无关。第一次是多人改同一份代码却没有历史可查；第二次是做出来的东西不是用户要的；第三次是一处改动波及到不相干的地方；第四次是测试用例选得不好。软件工程处理的就是这些：一群人在有限时间里，把会不断变化的需求做成一个能长期维护的产品。

这一页的顺序沿着一个项目走：先是让多人协作成为可能的工具（第 1 站）和组织工作的方式（第 2 站）；然后弄清要做什么（第 3 站）；用 UML 把设计画出来（第 4、5 站）；判断设计好不好（第 6 站），借用前人的解法（第 7 站），把系统拆成几个大块并拼起来（第 8 站）；写出好读、出错时不出事的代码（第 9 站）；最后是测试：测在哪一层（第 10 站），以及测哪些输入（第 11 站）。上面四次失败分别在第 1、3、6、11 站得到解释。

## [git] Revision control：commit graph、branch 与 merge

:::skip
能对着一张 revision graph 说出每个 branch 含哪些 commit、merge base 是哪一个、这次 merge 会不会 fast-forward、`main` 合进 `fix1` 和 `fix1` 合进 `main` 结果有什么不同，就可以去第 2 站。

### 只保留“最新版”为什么不够

开头第一次失败的根源是：共享文件夹里任何时刻只有一份文件，后写的覆盖先写的。要避免它，系统至少得做到三件事：

1. 记住每一次改动之前和之后的样子，误删了能找回来；
2. 允许两个人同时在两条线上改，互不干扰；
3. 两条线要合并时，自动把互不冲突的改动拼在一起，真正冲突的地方停下来问人。

Revision control software（RCS）就是做这三件事的工具，这门课用 Git。Git 是 distributed 的：每个人的电脑上都有一份完整的 history，而不是只有一台中心服务器有。

### Commit 是一个 snapshot，history 是一张 graph

Git 里有三个地方：

| 地方 | 是什么 |
|---|---|
| working directory | 你正在编辑的那些文件 |
| staging area（index） | 下一次 commit 要包含的内容，用 `git add`（或 `git stage`）放进去 |
| repository | 所有 commit 组成的 history |

一次 `git commit` 把 staging area 里的内容存成一个 commit。一个 commit 包含：整个项目在那一刻的 snapshot、作者和 message，以及它的 **parent**，也就是它是在哪个 commit 的基础上做的。Git 对这些内容整体算一个 SHA-1 hash，作为这个 commit 的名字（例如 `d25cfe8`）。注意 parent 也是被 hash 的内容之一，后面讲 rebase 时会用到这一点。

每个 commit 指向自己的 parent，所有 commit 连起来是一张 directed acyclic graph，叫 revision graph。在这张图上：

- **branch** 是一个名字，指向某个 commit，这个 commit 叫这个 branch 的 **tip**。从 tip 沿 parent 一路走得到的所有 commit 都算这个 branch 的。
- **HEAD** 是一个特殊的 ref，指向你当前所在的 branch。

做一次 commit 时发生两件事：新 commit 的 parent 是 HEAD 当前指向的那个 commit；然后 HEAD 所在的 branch 的 ref 挪到新 commit 上。别的 branch 一动不动。

### 走一遍：一个 feature branch 和一个 hotfix

这个例子来自 Pro Git 3.2。`master` 上已经有 C0、C1、C2 三个 commit。

```bash
git checkout -b iss53        # 新建 branch iss53 并切过去，它和 master 都指向 C2
git commit -am "C3"          # C3 的 parent 是 C2，iss53 挪到 C3
git checkout master          # 回到 master，working directory 变回 C2 的样子
git checkout -b hotfix
git commit -am "C4"          # 紧急修复：C4 的 parent 是 C2
git checkout master
git merge hotfix             # 输出：Fast-forward
git checkout iss53
git commit -am "C5"          # 继续做 feature
git checkout master
git merge iss53              # 产生 merge commit C6
```

::fig[cs2103-gitdag] 每做一步，revision graph 和几个 ref 怎么变。注意 fast-forward 那一步只是 `master` 的标签往前挪，没有新 commit；最后一步才产生有两个 parent 的 C6。

**第一次 merge 为什么是 fast-forward。** 把 `hotfix` 合进 `master` 时，`master` 的 tip 是 C2，`hotfix` 的 tip 是 C4，而 C2 正是 C4 的 parent。也就是说，`master` 在 `hotfix` 分出去之后没有任何新 commit，它的 tip 是 `hotfix` 的祖先。这时没有什么需要“合”的，Git 只要把 `master` 这个 ref 往前挪到 C4 就完成了。这就是 fast-forward：只有在 destination branch 自从两者分开后没有新 commit 时才会发生，不产生新 commit。

**第二次 merge 为什么不是。** 把 `iss53` 合进 `master` 时，`master` 的 tip 是 C4，`iss53` 的 tip 是 C5。两条线都在 C2 之后各自有了新 commit，谁也不是谁的祖先，不能靠挪 ref 解决。Git 先找两者最近的共同祖先，叫 **merge base**，这里是 C2（在这台机器上实际跑了一遍，`git merge-base master iss53` 给出的正是 C2）。然后做 **three-way merge**，用到三个 snapshot：

| snapshot | 在例子里 |
|---|---|
| merge base | C2 |
| destination branch 的 tip（ours） | C4 |
| source branch 的 tip（theirs） | C5 |

对文件的每一处，Git 拿 ours 和 theirs 分别与 base 比：

- 只有一边改了，就用改了的那一边；
- 两边都没改，就照旧；
- 两边改得一模一样，用那个共同结果；
- 两边改成了不同的样子，这就是 **conflict**，Git 停下来让人决定。

为什么一定要有 base？只拿 C4 和 C5 两个版本比，看到某一行一边有一边没有，无法知道是一边加了还是另一边删了。有了 base 就知道谁动过。

结果存成一个新 commit C6，它有两个 parent：C4 和 C5。destination branch 那边的 C4 叫 first parent，source branch 那边的 C5 叫 second parent。`master` 挪到 C6，`iss53` 仍然指向 C5。

> Merge 是有方向的：把 `iss53` 合进 `master`，只改变 `master`。

### Conflict 长什么样

Git-Mastery 的例子：base 里 `colours.txt` 只有一行 `blue`。`main` 在后面加了 `black`、`red`、`white`，`fix1` 加了 `green`、`red`、`white`。在 `main` 上执行 `git merge fix1`，实际输出是

```
Auto-merging colours.txt
CONFLICT (content): Merge conflict in colours.txt
Automatic merge failed; fix conflicts and then commit the result.
```

文件变成

```
blue
<<<<<<< HEAD
black
=======
green
>>>>>>> fix1
red
white
```

`<<<<<<< HEAD` 到 `=======` 之间是当前 branch（`main`）的版本，`=======` 到 `>>>>>>> fix1` 之间是被合进来的 `fix1` 的版本。`red` 和 `white` 没有被标成 conflict：两边在这里加的内容完全相同，按上面第三条规则直接采用。

解决的步骤：把文件编辑成想要的样子（例如 `black` 和 `green` 都留下），删掉三行 marker；`git add colours.txt` 告诉 Git 这个文件解决好了；再 `git commit` 完成这次 merge。

:::wrong 把 `fix1` 合进 `main` 和把 `main` 合进 `fix1` 是一回事，反正最后内容都合在一起了
两者产生的 snapshot 内容确实相同，但改变的是不同的 branch。设 `main` 上有 commit `d`，`fix1` 上有 `d1`、`e1`。在 `main` 上 `git merge fix1`，新的 merge commit 挂在 `main` 上，`main` 从此包含 `d`、`d1`、`e1`；`fix1` 的 tip 仍然是 `e1`，它看不到 `d`。反过来在 `fix1` 上 `git merge main`，是 `fix1` 得到了 `d`，而 `main` 仍然看不到 `d1`、`e1`。团队里说“把 main 合进你的 branch”是为了让你的 branch 跟上别人的改动，和“把你的 branch 合进 main”交付你的 feature 是两件事。
:::

### Fast-forward、`--no-ff` 与 rebase

Fast-forward 之后，graph 看起来就像所有改动都是直接在 `master` 上做的，看不出曾经有过一个 `hotfix` branch，也看不出它是什么时候合进来的。如果想保留这个信息，可以 `git merge --no-ff hotfix`，即使能 fast-forward 也强制产生一个 merge commit。

**Rebase** 是让一个 branch 跟上另一个 branch 的另一种办法。设 `feature` 从 `main` 的 `m1` 分出来，有 `f1`、`f2`，而 `main` 后来又多了 `m2`。在 `feature` 上 `git rebase main`，Git 把 `f1`、`f2` 的改动依次“重放”到 `m2` 之上，得到 `f1a`、`f2a`，`feature` 指向 `f2a`。结果是一条直线，没有 merge commit。

::fig[cs2103-rebase] 同一个起点，左边用 merge 让 `feature` 跟上 `main`，右边用 rebase。rebase 之后的 `f1a`、`f2a` 内容上的改动和 `f1`、`f2` 一样，却是新的 commit。

`f1a` 和 `f1` 为什么不是同一个 commit？因为 commit 的 hash 是对它的全部内容算的，而 parent 是内容的一部分：`f1` 的 parent 是 `m1`，`f1a` 的 parent 是 `m2`，hash 必然不同，`f2a` 跟着也不同。所以 rebase 是在**改写 history**。如果 `f1`、`f2` 已经 push 出去、别人在上面接着做了，rebase 之后他们手里的 commit 在你的 history 里不存在了，下次同步会出一堆重复和冲突。规则是：不要 rebase 已经公开的 branch。

撤销一个旧 commit 也有两种对应的办法：

| 命令 | 做了什么 | 是否改写 history |
|---|---|---|
| `git revert C2` | 算出 C2 的反向改动，作为一个新 commit 加在最后 | 否，C2 仍在 history 里 |
| `git reset C2` | 把当前 branch 的 ref 挪回 C2，之后的 commit 不再属于这个 branch | 是 |

`reset` 还分三种，区别只在被丢掉的那些 commit 里的改动去了哪里：`--soft` 把它们留在 staging area；`--mixed`（默认）把它们留在 working directory、不 stage；`--hard` 连同 working directory 里的改动一起丢掉。

### Remote、fork 与 pull request

`git clone` 把一个 remote repository（例如 GitHub 上的）完整复制到本地，并记下它叫 `origin`。本地除了自己的 `main`，还有一个 **remote-tracking branch** `origin/main`，记录上一次和 remote 通信时 remote 的 `main` 在哪里。

- `git fetch`：从 remote 下载新的 commit，更新 `origin/main`，不动你自己的 `main`；
- `git pull` = `git fetch` 再 `git merge origin/main`；
- `git push`：把本地 branch 的 commit 上传，挪动 remote 上对应的 ref。

**Fork** 是在 hosting service（GitHub）上把别人的 repository 复制一份到自己账号下；它和 clone 不同，clone 是复制到自己电脑上。Forking workflow 的一轮是这样走的：

1. Jean 在本地新建一个 branch 修 bug（不要直接在 `main` 上改，否则她同时只能开一个 PR：`main` 上的任何改动会出现在所有基于 `main` 的 PR 里）；
2. 把这个 branch push 到她自己的 fork；
3. 从 fork 的这个 branch 向原 repository（upstream）开一个 **pull request**（PR）；
4. 别人 review，Jean 按意见继续 push commit，PR 自动更新；
5. 有写权限的 maintainer merge 这个 PR；
6. 所有人从 upstream pull 新的 `main`，再 push 到自己的 fork，完成同步。

::fig[cs2103-fork] Forking workflow 里三个 repository 之间的箭头。PR 只从下游（fork）指向上游，同步则是先从上游 pull 到本地、再 push 到自己的 fork。

这种 workflow 的好处是大多数贡献者不需要 upstream 的写权限，坏处是每次都要绕道 fork。

Git-Mastery 把各种 workflow 归到两个维度上：谁能 push 到主 repository（**centralized**：所有人直接 push 到同一个 repository；**forking**：各自在 fork 上工作、靠 PR 提交），以及多久合并一次（**feature-branch**：在一个 branch 上做几天甚至几周，做完再合；**trunk-based**：只有一条主干，改动小而频繁地合进去，branch 很短命甚至没有）。两个维度一组合得到四种，Gitflow 之类有名字的 workflow 都是其中某一种的具体做法。

:::edge Branch 没有“起点”
常说 `fix1` 从 C2 开始，但从 `fix1` 的 tip 沿 parent 能走到 C2、C1、C0，这些 commit 全都属于 `fix1`，也同时属于 `master`。Branch 只记录 tip，不记录自己是从哪里分出来的；“从哪里分出来”是我们看图时说的话。
:::

:::from
三件事的动机、branch 是指向 tip 的 ref、HEAD 的定义、merge base、first parent 与 second parent、merge 的方向性、fast-forward 的条件、colours 的 conflict 例子、rebase 改变 SHA、revert 与 reset 的三种模式、workflow 的两个维度和 forking workflow 的步骤，来自 Git-Mastery 的 [Branch](https://git-mastery.github.io/lessons/trail/branchingLocally)、[Merge](https://git-mastery.github.io/lessons/merge) 等几课原文（clone 了仓库读）。iss53 与 hotfix 的走法和 three-way merge 的三个 snapshot 来自 [Pro Git 3.2](https://git-scm.com/book/en/v2/Git-Branching-Basic-Branching-and-Merging.html)。为什么 three-way 比 two-way 多出一个 base 的论证是另加的；两个例子都在本机用 Git 实际跑过，输出照录。

## [process] SDLC process model 与 project planning

:::skip
能说出 sequential 和 iterative 各在什么时候拿到 feedback，能从一个 WBS 算出 critical path 和每个 task 的 slack，并解释为什么给晚了的项目加人会更晚，就可以去第 3 站。
:::

### 没有 process 会怎样

最简单的做法是直接写代码、坏了就修，叫 code-and-fix。一个人写一个小程序，这样完全够用。人一多、时间一长，它就失灵了：说不出做到哪一步了，没法把工作分给几个人而不互相踩脚，也没有任何地方记下已经做过的决定。

软件开发要经过 requirements、analysis、design、implementation、testing 这些阶段，合称 software development lifecycle（SDLC）；deployment、operation、maintenance 通常也算在内。Process model 规定怎样走过这些阶段：每一段的目标、产出，以及它们之间的先后关系。最基本的两种是 sequential 和 iterative，区别在于项目按什么切开。

### Sequential：按 activity 切

**Sequential model**（也叫 waterfall）把项目按 activity 切开：先把整个产品的 requirements 做完，交出一份 requirements 文档；design 阶段拿着它做完整个 design；如此往下。每个阶段交出的东西（specification、model、test case）叫 artifact，是下一阶段的输入。严格的 sequential model 只往前走，实际中常常允许退回上一阶段，但退回就意味着重做已经算作“完成”的工作。

它适合问题已经被充分理解的项目：requirements 稳定，工作量能估准，而且进度一目了然，处在哪个阶段就做到哪里。它的两个弱点都和 feedback 有关：

- 用户往往要用过一个东西才知道自己要什么，而 sequential model 要求一开始就把 requirements 说全；
- 每个阶段的产出主要由下一阶段检查，integration 和真实用户都排在最后。Requirements 或 design 里的错误，恰好在“回头改已经完成的工作”代价最大的时候才暴露。

### Iterative：按有界的 cycle 切

**Iterative model** 把项目切成几个 iteration，每个 iteration 都走一遍若干阶段，结束时交出一个新版本，并收集 feedback 用于下一个 iteration。

拿一个具体的安排比较。设一个 12 周的项目，sequential 的排法是 requirements 2 周、design 2 周、implementation 5 周、testing 2 周、deployment 1 周；iterative 的排法是 4 个 3 周的 iteration。

::fig[cs2103-seqiter] 同一个 12 周的项目。上面按 activity 切，用户第一次见到能用的东西是第 12 周；下面按 iteration 切，第 3 周就有 v0.1，之后每 3 周一次 feedback。

在 sequential 的安排下，用户第一次见到能运行的产品是第 12 周；在 iterative 的安排下是第 3 周，之后第 6、9、12 周各有一次。如果第 9 周 iteration 3 拖期，iterative 的项目仍然可以交出第 6 周的 v0.2；sequential 的项目在 implementation 拖期时，手里没有任何可以交付的版本。这也是课本练习题的结论：iterative 项目超出 deadline 的风险更低，但不保证一开始承诺的 feature 都能交付。

一个 iteration 怎样分配工作，有两种做法，课本用 Minesweeper 说明：

- **breadth-first**：每个 iteration 都把所有主要 component 和所有功能各推进一点，每次结束都有一个能玩的版本。第一个版本可能只有简陋的文字界面、固定大小的 board，后面的 iteration 再逐一改进。
- **depth-first**：一个 iteration 只把某几个 component 或某一块功能做深。早期的 iteration 可能交出完整的 UI 但完全没有游戏逻辑，玩不了，但可以拿 UI 去收集 feedback。

两者可以混用。值得放进早期 iteration 的，是那些一旦错了代价最大的假设：没用过的技术、没把握的用户需求、没人达到过的性能目标。早一点发现自己错了，改方向还便宜。

:::edge Iterate 和 increment 不是一回事
To iterate 是根据 feedback 改进已有的东西；to increment 是往上加新的东西。大多数项目两者都做，所以常合称 iterative and incremental。一个 iteration 交出的、对用户有用的改进叫 increment。
:::

### Agile、Scrum、XP 与 Unified Process

2001 年，几种轻量方法的作者聚在一起，写下了它们共同的价值观，即 agile manifesto：

- individuals and interactions over processes and tools
- working software over comprehensive documentation
- customer collaboration over contract negotiation
- responding to change over following a plan

右边的东西也有价值，只是更看重左边。按这些价值组织的 process 统称 agile process：requirements 按用户需要排优先级、随时调整；plan 和 design 只做粗的、边做边演化；整个团队共同对交付负责。它依赖两个条件：客户能持续给 feedback，以及能便宜地交付改动。固定价格、范围已签字的合同，或者发布前必须认证的软件，就不满足这两个条件。

**Scrum** 是一个轻量的 agile framework，只规定很少几样东西：

| 类别 | 内容 |
|---|---|
| 三种 accountability | Product Owner：代表 stakeholder，决定产品接下来要什么；Scrum Master：负责团队把 Scrum 用好；Developers：跨职能，做 analysis、design、implementation、testing |
| Sprint | 固定长度、不超过一个月的 iteration，常见 1 到 4 周；一个项目里每个 Sprint 一样长 |
| event | Sprint Planning（选工作、定 Sprint Goal）、Daily Scrum（Developers 同步进度、说出卡在哪里，不在会上解决问题）、Sprint Review（和 stakeholder 一起检查 increment）、Sprint Retrospective（检查团队自己的工作方式） |
| artifact | Product Backlog（整个产品的、排好优先级的高层 requirements）、Sprint Backlog（本 Sprint 选中的条目）、Increment |

Sprint 里 Sprint Goal 不变，但达成它的计划可以调整；Sprint 必须按时结束，没做完的回到 Product Backlog。

**Extreme Programming（XP）** 的“extreme”不在于用了什么新做法，而在于把公认好的做法用到最频繁：release 小而频繁，而不是攒到里程碑；code 持续 integrate（continuous integration）；test 写在被测代码之前（test-driven development，第 10 站）；design 持续 refactor；两个人在一个键盘上写代码，代码在写的同时就被 review（pair programming）。

**Unified Process（UP）** 由创造 UML 的三个人（Jacobson、Booch、Rumbaugh）提出，分四个 phase：inception（理解问题、定范围、粗计划）、elaboration（细化 requirements、定 architecture）、construction（主要的实现和各级测试，多次 release）、transition（准备投入生产、培训用户）。Phase 和 iteration 是两回事：phase 说明项目处在整体弧线的哪一段，每个 phase 里可以有多个 iteration，每个 iteration 又包含 requirements、design 等几种工作，只是比重不同。所以 UP 既分 phase 又是 iterative 的。

### 从 WBS 到 critical path

计划从 **work breakdown structure**（WBS）开始：把整个项目的范围层层拆成小而明确的 task，标上工作量和前置 task。工作量用 person-day 这样的单位，即一个人一天能做的工作。每个 task 都要能判断什么时候算做完：“more coding” 不行，“implement component X” 可以。

课本里一个游戏项目的 WBS：

| Task | 工作量（天） | 前置 |
|---|---|---|
| A. High level design | 1 | 无 |
| B.1 UI design | 0.5 | A |
| B.2 Game logic design | 1 | A |
| B.3 Persistency support design | 0.5 | A |
| C.1 UI coding | 1.5 | B.1 |
| C.2 Game logic coding | 2 | B.2 |
| C.3 Persistency support coding | 1 | B.3 |
| D. Final testing | 1 | C.1、C.2、C.3 |
| E. Deployment | 1 | D |

把 task 画成节点、前置关系画成箭头，就是 **PERT chart**。它一眼回答三个问题：哪些 task 必须排在前面，哪些可以同时做，以及整个项目最短要多久。

::fig[cs2103-pert] 上面那张 WBS 画成 PERT chart。粗框连成的路径是 critical path，长 6 天；每个节点下方是算出来的 slack。

最短工期怎么算？一个 task 最早能开始的时间（earliest start，ES）是它所有前置 task 最早完成时间（earliest finish，EF）的最大值，EF = ES + 工期。从 A 开始往下推：

- A：ES = 0，EF = 1。
- B.1、B.2、B.3 都只依赖 A，ES = 1；EF 分别是 1.5、2、1.5。
- C.1：ES = 1.5，EF = 3；C.2：ES = 2，EF = 4；C.3：ES = 1.5，EF = 2.5。
- D 要等三个 C 都完成：ES = max(3, 4, 2.5) = 4，EF = 5。
- E：ES = 5，EF = 6。

所以项目最短 6 天。再从后往前推每个 task 最晚必须完成的时间（latest finish，LF），不能让 E 晚于第 6 天：E 的 LF = 6，LS = 5；D 的 LF = 5，LS = 4；三个 C 的 LF 都是 4，于是 C.1 的 LS = 4 − 1.5 = 2.5，C.2 的 LS = 2，C.3 的 LS = 3；B.1 的 LF = 2.5，LS = 2；B.2 的 LF = 2，LS = 1；B.3 的 LF = 3，LS = 2.5；A 的 LF = min(2, 1, 2.5) = 1，LS = 0。

LS − ES 叫 slack：这个 task 最多能推迟多久而不拖累整个项目。

| Task | ES | LS | slack |
|---|---|---|---|
| A | 0 | 0 | 0 |
| B.1 | 1 | 2 | 1 |
| B.2 | 1 | 1 | 0 |
| B.3 | 1 | 2.5 | 1.5 |
| C.1 | 1.5 | 2.5 | 1 |
| C.2 | 2 | 2 | 0 |
| C.3 | 1.5 | 3 | 1.5 |
| D | 4 | 4 | 0 |
| E | 5 | 5 | 0 |

slack 为 0 的 task 连成 A → B.2 → C.2 → D → E，长 1 + 1 + 2 + 1 + 1 = 6 天，这就是 **critical path**：其上任何一个 task 延误，整个项目就延误同样长。它也是 PERT chart 里从头到尾最长的那条路径（在 DAG 上求最长路，按 topological order 推一遍即可，见 [CS2040 的 graph 一站](../courses/CS2040.html#graph)）。

用 slack 检验课本的两个说法。B.3 从 0.5 天变成 1 天，晚了 0.5 天，它的 slack 是 1.5，吸收得了，项目仍是 6 天。B.2 从 1 天变成 1.5 天，它在 critical path 上，slack 为 0，项目变成 6.5 天。

### Gantt chart、milestone 与 buffer

**Gantt chart** 把同样的计划画成横轴为时间、每个 task 一根横条的图，适合看“这一天谁在做什么”。按上面算出的 ES 摆放横条，就得到最早开工的排法。

::fig[cs2103-gantt] 按 ES 排出的 Gantt chart，浅色延长段是 slack。动图依次演示：B.3 晚 0.5 天被 slack 吸收，终点不动；B.2 晚 0.5 天，后面整串跟着右移，终点到 6.5 天。

**Milestone** 标出一个有意义的进展点，通常是一个阶段的结束，例如“第 3 天：new game 功能实现完毕”。在 Gantt chart 上画成菱形。项目太不确定时，可以只给整个项目一个粗计划，只为接下来几个 milestone 做细计划。

**Buffer** 是专门留出来吸收意外延误的时间。软件的工作量出了名地难估，所以计划里必须有 buffer，但要显式地留，而不是把每个 task 的估计偷偷放大。

:::wrong 与其单独留 buffer，不如把每个 task 的估计都多报一点，效果一样
两个 task X、Y，各估 2 天。做法一：把估计放大成 X 3 天、Y 4 天，计划总长 7 天。做法二：X 2 天、buffer 1 天、Y 2 天、buffer 2 天，总长同样是 7 天。差别在事后。按做法一，X 实际用了 3 天，看起来“按计划完成”，没人知道最初的 2 天估低了；按做法二，X 用了 3 天就是明明白白地吃掉了 1 天 buffer，估计偏低这件事被记录下来，下次估类似的 task 可以修正。隐藏的 buffer 把估计误差也一并藏起来了。
:::

### 人数、沟通与 Brooks' law

计划里的 person-day 暗示人和天可以互换：4 person-day 的活，两个人做 2 天。Fred Brooks 在 *The Mythical Man-Month* 里指出这对软件不成立，并给出了著名的 **Brooks' law**：给一个已经晚了的项目加人，只会让它更晚。

原因可以算出来。n 个人两两之间都要沟通时，沟通渠道有 $\binom n2=\dfrac{n(n-1)}2$ 条。4 个人是 $\tfrac{4\times3}2=6$ 条；加 2 个人变成 6 个人，是 $\tfrac{6\times5}2=15$ 条，人多了 50%，渠道多了 150%。再加上新人要花时间熟悉项目，而熟悉的过程要占用老成员的时间，越接近 deadline，加人的净效果越可能是负的。

团队结构正是在决定这些渠道里哪些真的存在：

| 结构 | 怎样组织 | n = 6 时的沟通渠道 |
|---|---|---|
| egoless team | 所有人平等，共同决策 | 15 |
| chief programmer team | 一个人做主要决定并协调其他人 | 5 |
| strict hierarchy | 层层汇报，例如 1 人管 2 人、2 人各管 1 到 2 人 | 5 |

后两种渠道少、决策快，但依赖少数关键人物，信息也要层层转达；egoless 讨论充分，但人一多就难以收敛。

:::from
Code-and-fix、SDLC 的定义、sequential 的两个弱点、按 activity 切与按 cycle 切、breadth-first 与 depth-first 的 Minesweeper 例子、iterate 与 increment、agile manifesto、Scrum（按 Scrum Guide 的写法）、XP 的“extreme 在于频率”、UP 的四个 phase 与 phase 不等于 iteration、WBS 与 PERT 的游戏项目例子（task 名称和天数）、B.3 和 B.2 延误的两个结论、buffer、Brooks' law 和三种团队结构，来自课本 SDLC Process Models、Project Planning、Software Engineering 几章及练习答案。12 周项目的具体排法、ES/LS/slack 的逐步计算、隐藏 buffer 的数字比较和沟通渠道数是为这一页另算的。Agile 方式依赖 iteration 时长 1 到 2 周的说法与 [Berkeley CS 169 Lecture 8](https://courses.edx.org/c4x/BerkeleyX/CS-169.1x/asset/169xLecture8.pdf) 一致。

## [req] Requirements：user story、use case 与 NFR

:::skip
能把一句“系统要好用”改写成可以用测试判定的 requirement，能写出一个带 extensions 的 use case，并说出 user story 和 use case 各自擅长什么，就可以去第 4 站。
:::

### Requirement 从哪里来

一个 software requirement 说明产品要满足的一项需要。项目分两种：替换或更新已有系统的叫 brownfield project，从零做新系统的叫 greenfield project。不论哪种，requirement 都来自 **stakeholder**：所有参与项目或受项目影响的人和组织。以 Canvas 这样的 LMS 为例，显然的 stakeholder 有学生、老师、管理员、付钱的学校、卖系统的公司；不那么显然的有开发和测试人员、第三方插件开发者、管数据保护的监管机构、关心未成年人权益的团体。

开头第二次失败说明，stakeholder 说出来的话不等于他们的需要。课本给了一段面试记录，对象是一个审批请假的经理：

> 你：讲讲上一次有人向你请假的经过。
> 经理：她发邮件给我，我查了共享的表格，然后回复同意。
> 你：你在表格里查什么？
> 经理：那一周有没有别人已经请假。还有她的假期余额，不过那个经常不准，所以我会去问 HR。

没有人提过“需求”，却浮出了两条：审批人要能看到同一时段还有谁请假；余额必须足够新，能拿来做决定。从这段对话可以看出面试的几条做法：从一个具体的最近事件问起，而不是问“你需要什么”；追问现在哪里出错、大家怎么绕过去，私下维护的表格就是系统失职的地方；用自己的话复述对方的意思；事后让对方核对记录。

其他收集 requirement 的办法各能拿到面试拿不到的东西：

| 办法 | 能拿到什么 |
|---|---|
| observation | 用户实际怎么做，而不是他们说自己怎么做；已有系统的使用数据还能显示用户在哪里出错 |
| user survey | 大量 stakeholder 的意见 |
| focus group | 一群人在讨论中互相启发出的看法 |
| brainstorming | 大量不加评判的想法，目的是产生而不是筛选 |
| product survey | 现有同类产品的做法和缺陷 |
| prototyping | 用户和界面怎么交互；用户对着一个草图挑错，比对着一段文字容易得多 |

### Functional、non-functional 与“可测试”

**Functional requirement** 说系统应该做什么，例如“用户能按书名搜索书”。**Non-functional requirement**（NFR）说系统在什么约束下开发和运行，例如“搜索在两秒内返回结果”。NFR 包括 performance、security、usability、data（数据量、持久性）、environment（要兼容的技术环境）、business rule（“minefield 不能小于 5×5”）、process（“每个月交付一组功能”）等。NFR 要特别早地找出来：stakeholder 总是先想到功能，容易漏掉 NFR；而一个太慢或不安全的 web 应用，功能再全也不会成功。

一条好的 requirement 应当 unambiguous、testable、clear、correct、understandable、feasible、independent、atomic、necessary、implementation-free；整组 requirement 还应当 consistent、non-redundant、complete。其中最实用的检验是 testable：能不能靠观察一个结果来判定它是否被满足，而不是靠争论字面意思。

- “The system should respond within two seconds.” 测一下就知道。
- “The system should be usable by a novice who has never carried out an online purchase.” 两个人可以对“usable”各执一词，谁也说服不了谁。

第二条可以改写成有证据能判定的形式：“A user who has never carried out an online purchase should be able to complete a purchase unaided, on the first attempt, within five minutes.” 现在找几个从没网购过的人试一试，就有了答案。

### User story

User story 是从想要这个功能的人的角度写的一句简短描述，格式是

```
As a {user type/role} I can {function} so that {benefit}
```

例如 “As a student, I can download files uploaded by lecturers, so that I can get my own copy of the files.” benefit 显而易见时可以省略，但最好确认它确实存在，否则可能在做没人受益的功能。

User story 可以写在不同层次。大的叫 **epic**，再拆成普通大小的 story：

- [Epic] As a lecturer, I can monitor student participation levels
  - As a lecturer, I can view the forum post count of each student so that I can identify the activity level of students in the forum
  - As a lecturer, I can view webcast view records of each student so that I can identify the students who did not view webcasts

一个 story 可以附上 **acceptance criteria**（课本也叫 conditions of satisfaction），写明怎样算“做完”，例如第一个 story：每个 forum 分别显示 post count；显示学生的 total post count；列表能按姓名和 post count 排序。Acceptance criteria 正是 story 里给出可观察结果的那一部分。

User story 和传统 requirement 文档最大的差别在详细程度：它只写到足以低风险地估出工作量为止，具体细节到要实现时再当面和客户谈。所以它轻便，适合早期大量收集，也方便排优先级、估工作量、安排进度。Berkeley CS 169 给 user story 一个检查清单 SMART：specific 且 measurable（能写成测试），achievable（一个 iteration 内做得完），relevant（一路追问“为什么”能追到业务价值，否则就删掉），timeboxed（按团队的 velocity 估）。他们给每个 story 打 1 到 3 个 point，一个 iteration 完成的 point 数就是 velocity，用来规划下一个 iteration 能装多少 story。

:::wrong 只要套上 user story 的格式，写下来的就是 user story
课本的练习：“As a developer, I want to use Python to implement the software, so that we can reuse existing Python modules.” 格式完全正确，但它不是从用户或客户的角度写的，说的是一个实现上的选择，对买东西的人没有任何价值可言。User story 记录的是用户的需要；用什么语言是 design 决定，不该出现在这里。NFR 倒是可以写成 user story，因为它也让某个 stakeholder 受益，例如 “As an impatient user, I want to be able to experience reasonable response time from the website while up to 1000 concurrent users are using it, so that I can use the app even when the traffic is at the maximum expected level.”
:::

### Use case

User story 刻意不写细节；但有些交互流程，尤其是“出错了怎么办”，必须事先说清。**Use case** 描述一个 actor 和系统之间为完成一项功能而进行的交互。Actor 是一个角色，不是一个人：同一个学生在 LMS 里可以扮演 Student、Guest、Tutor 三个角色；本科生、研究生、交换生都可以扮演 Student。Actor 也可以是另一个系统。

课本的例子：

```
System: Online Banking System (OBS)
Use case: UC23 - Transfer Money
Actor: User
Preconditions: User is logged in.
Guarantees:
  * Money will be deducted from the source account only if the transfer
    to the destination account is successful.
MSS:
  1. User chooses to transfer money.
  2. OBS requests for details of the transfer.
  3. User enters the requested details.
  4. OBS requests for confirmation.
  5. User confirms.
  6. OBS transfers the money and displays the new account balance.
  Use case ends.
Extensions:
  3a. OBS detects an error in the entered data.
      3a1. OBS requests for the correct data.
      3a2. User enters new data.
      Steps 3a1-3a2 are repeated until the data entered are correct.
      Use case resumes from step 4.
  3b. User requests to schedule the transfer for a future date.
      3b1. OBS requests for confirmation.
      3b2. User confirms future transfer.
      Use case ends.
  *a. At any time, User chooses to cancel the transfer.
      *a1. OBS requests to confirm the cancellation.
      *a2. User confirms the cancellation.
      Use case ends.
```

逐项看：

- **Main success scenario（MSS）**：假设一切顺利时最直接的流程。它必须自成一体，单独读就是一个完整的使用场景。
- **Extensions**：MSS 某一步不如预期时的替代流程。编号是约定：`3a`、`3b` 是第 3 步之后可能发生的两种情况；`*a` 可以在任何一步发生。每个 extension 写明结束后是回到 MSS 的哪一步（“resumes from step 4”）还是整个 use case 结束。
- **Preconditions**：use case 开始前系统应处的状态。
- **Guarantees**：use case 结束时承诺的结果。它对 use case 的作用，和 acceptance criteria 对 user story 的作用一样。

::fig[cs2103-ucflow] UC23 的流程。MSS 是中间一列，3a 绕一圈回到第 4 步，3b 和 *a 各自结束 use case。

写 use case 步骤的规矩：每一步是“谁做什么”的简单句；只写外部可见的行为，“LMS saves the file into the cache” 不该出现；写 actor 的意图而不是操作细节，“User clears the input” 而不是 “User right-clicks the text box and chooses ‘clear’”，把界面怎么做留给 UI 设计者。

一个 use case 可以 **include** 另一个：在步骤里用带下划线的文字引用它，例如 “Staff creates the survey (UC44)”，用于把低层步骤拆出去，或者复用几个 use case 共有的步骤。Use case diagram 把所有 use case 画成椭圆、actor 画成小人，作为一张目录；include 画成指向被包含 use case 的虚线箭头，标 `<<include>>`；extension 画成从 extension 指向被扩展 use case 的虚线箭头，标 `<<extend>>`。

:::edge 什么不该写进 use case
断电、系统崩溃这类灾难性故障不写成 extension，系统在那之后已经无法运作，写了也没有内容。Performance 这类 NFR 也不写进 use case。Use case 的主要缺点正在这里：它只能表达有 actor 参与的交互，所以不能作为 requirement 的唯一载体。
:::

### 其他格式，以及 requirement 不等于 specification

各种格式各管一件事：

| 格式 | 用来做什么 |
|---|---|
| prose | 说清问题和产品的目的，例如 product vision；不要用长篇 prose 写具体 requirement |
| feature list | 按某个标准（方面、优先级、交付顺序）分组列出功能，用于讨论范围 |
| user story | 记录一小块可以协商的用户价值 |
| use case | 把一个流程以及其中可能出的错写精确 |
| glossary | 统一名词：领域术语、一词多义时取哪一义、多个词指同一概念时用哪一个 |
| supplementary requirements | 放不进上面任何一种的，通常是大部分 NFR |

Requirement 要排优先级，例如分成 essential（没有它用户不接受）、typical（同类产品大多有）、novel（能让产品与众不同），或 must-have、nice-to-have、unlikely-to-have。有些会被判定为超出范围（out of scope）而放弃。Requirement 还会一直变：stakeholder 见到实物才知道自己要什么，外部环境（法规、竞争对手）在变，团队也会发现某件事比预想的贵十倍。所以不更新的 specification 会误导人，而接受一个新 requirement，也就意味着挤掉另一个。

Requirement 说的是问题和要达到的结果；software specification 说的是系统的行为，精确到可以照着实现和验证。同一件事：

- requirement：“A member should be able to renew a borrowed book.”
- specification：“When a member selects Renew for an eligible loan, the system shall extend the due date by the configured loan period and display the new due date.”

:::wrong Requirement 写清楚了，剩下的就是开发者把它实现出来
回到开头第二次失败。团队交出的实现是：“续借把 due date 再延长一个借期；会员可以无限次续借，在到期前的任何时间都可以在账户页面续借。” 这段描述里至少有三个决定是 requirement 没有说、团队默默替图书馆做的：续借次数不限（多数图书馆有上限，可以写成 acceptance criterion “A book may be renewed at most twice in a row.”）；有人预约的书也能续借（“A book with an outstanding reservation cannot be renewed.”）；过期后不能续借（也可能应该允许交了罚款再续：“An overdue book cannot be renewed until the outstanding fine is paid.”）。再怎么仔细读那一句 requirement 也得不出这些答案，因为它们本来就不在里面，是图书馆要做的决定，只能去问。
:::

## [uml] Class diagram 与 object diagram

:::skip
给一段 Java 代码，能画出 multiplicity 尽可能严格的 class diagram，再画出程序跑到某一刻的 object diagram，并说出 class diagram 和 conceptual class diagram 差在哪里，就可以去第 5 站。
:::

### 为什么要画图

一个几十个 class 的系统，没人能靠读代码在脑子里拼出“谁持有谁、谁继承谁”。Model 是对某样东西的一个简化表示，只抓住其中一个方面，所以它本身就是一种 abstraction。一个系统要用好几种 model 才能描述全：class diagram 只管结构，不管行为；行为交给下一站的 sequence diagram 和 activity diagram。Model 有三种用法：分析问题（画出问题领域的样子）、和 stakeholder 交流（用 architecture diagram 给新同事讲系统）、作为 blueprint 照着写代码。

这门课用的 notation 是 UML（Unified Modeling Language），由 Rumbaugh、Booch、Jacobson 三人把各自的 notation 合并而成。

### 一个 class 怎么画

::fig[cs2103-classbox] 左边是 `Table` class 的 UML 画法：名字、attribute、operation 三栏，前面的符号是 visibility。右边是几种特殊写法：class-level member 加下划线，abstract 写 `{abstract}`，interface 和 enumeration 在名字上方加 `<<interface>>`、`<<enumeration>>`。

```java
class Table {
    private Integer number;
    private Chair[] chairs = null;
    public Integer getNumber() { ... }
    public void setNumber(Integer n) { ... }
}
```

Attribute 写成 `name: type = default`，operation 写成 `name(param: type): returnType`。Visibility 的符号：`+` public、`-` private、`#` protected、`~` package private（Java 的默认 visibility）。Attribute 栏永远在 operation 栏上面；两栏都可以省略，也可以只列出和这张图目的有关的成员。

UML 里没有“默认 visibility”：图上没写，意思是没有指明（可能还没决定，或者和这张图无关），不是 package private，也不是 public。

### Association：一个 object 持有另一个 object

一个 object 把另一个 object 存在自己的 field 里，两个 class 之间就有 **association**，画成一条实线。线上可以加四种信息：

| 信息 | 写法 | 含义 |
|---|---|---|
| label | 线中间一个动词短语，可加小箭头指示阅读方向 | 这个关系是什么，例如 `Admin` *uses* `Student` |
| role | 线某一端的名字 | 这一端的 object 在关系里扮演什么，通常就是 field 名 |
| multiplicity | 线某一端的数字 | 另一端的一个 object 能连着几个这一端的 object |
| navigability | 线某一端的箭头 | 谁知道谁：`Logic` → `Minefield` 表示 `Logic` 持有 `Minefield` 的 reference，反过来没有 |

常用的 multiplicity：`0..1`（可有可无）、`1`（任何时候都恰有一个）、`*`（零个或多个）、`n..m`（在 n 到 m 之间，例如 `1..*`、`2..5`）。和 visibility 一样，UML 没有默认 multiplicity，没写就是没指明。

一个 association 可以画成线，也可以写成 attribute：`isOn: Square [0..1] = null`。两种写法等价，但同一个 association 只能用其中一种，不能既画线又写 attribute。一般推荐画线，更容易看出来。

### 从代码画 class diagram

课本的练习：为下面的代码画 class diagram，multiplicity 在不和代码矛盾的前提下尽量严格；再画出 `main` 跑完时的 object diagram。

```java
public class Main {
    public static void main(String[] args) {
        Item item1 = new Item();
        Item item2 = new Item();
        Box box1 = new Box(item1);
        Box box2 = new Box(item2);
        item2.setMainCard(new Card());
        item2.addPreviousBox(box1);
        item2.addPreviousBox(box2);
    }
}
class Box {
    private Item item;
    Box(Item item) { this.item = item; }
}
class Item {
    private List<Box> previousBoxes = new ArrayList<>();
    private Card mainCard = null;
    private Card subCard = null;
    void setMainCard(Card card) { this.mainCard = card; }
    void setSubCard(Card card) { this.subCard = card; }
    void addPreviousBox(Box previousBox) { previousBoxes.add(previousBox); }
}
class Card {
}
```

逐个 field 看：

- `Box.item`：`Box` 持有一个 `Item`，所以是一条从 `Box` 指向 `Item` 的 association。它在 constructor 里被赋值，之后没有 setter 能改，所以 `Item` 那一端的 multiplicity 是 `1`。
- `Item.previousBoxes`：`Item` 持有一个 `Box` 的 list，长度不限，所以是从 `Item` 指向 `Box` 的 association，`Box` 那一端写 `*`，role 是 `previousBoxes`。
- `Item.mainCard` 和 `Item.subCard`：两个都是 `Card`，初值 `null`，可以被 set，所以是两条从 `Item` 指向 `Card` 的 association，`Card` 那一端都是 `0..1`，用 role `mainCard`、`subCard` 区分。
- `Card` 没有 field，不指向任何东西。

`Box.item` 和 `Item.previousBoxes` 连着同样两个 class，但不能合并成一条双向箭头的线：一个 box 装的 item，和一个 item 以前待过的 box，是两个不同的关系。一条双向 association 的意思是“a 持有 b，那么 b 也持有 a”，这里并不成立：`box1` 装着 `item1`，但 `item1` 的 `previousBoxes` 是空的。

::fig[cs2103-boxclass] 上面是 class diagram：Box → Item 是 `1`，Item → Box 是 `*`（previousBoxes），Item → Card 有两条，各是 `0..1`。下面是 `main` 跑完时的 object diagram。

### Object diagram：某一刻的快照

Class diagram 说的是规则：哪些 class 的 object 之间允许怎样连接、各连几个。**Object diagram** 画的是程序运行到某一刻，实际存在的 object 和它们之间实际的连接。同一张 class diagram 对应无数张 object diagram，每一张都必须满足它的规则。

Notation 上的差别：

- 方框里写 `objectName:ClassName`，并加下划线；匿名的 object 写 `:Card`。
- 可以列 attribute 的值，写成 `size = 3`，不写类型和 visibility；不列 method。
- 线上不写 multiplicity：object diagram 里的一条线就是连着一个 object。
- 一个 `Employee` object `jake`（`Employee` 是 `Person` 的 subclass）只能画一个框，写成 `jake:Employee`，或者在无关紧要时写 `jake:Person`；不能画成两个框。

把 `main` 逐行执行：两个 `Item`、两个 `Box` 各自被创建，`box1` 连 `item1`，`box2` 连 `item2`；一个匿名 `Card` 被创建并成为 `item2` 的 `mainCard`；`item2` 的 `previousBoxes` 先后加入 `box1`、`box2`。最后一共 5 个 object、5 条连接，就是上图的下半部分。`item1` 没有指出去的连接，这和 class diagram 的 `*` 和 `0..1` 都不矛盾，因为两者都允许 0。

拿 object diagram 检查 class diagram：如果把 Item → Box 的 multiplicity 写成 `1`，这张 object diagram 里 `item2` 连着两个 box 就违反了它；写成 `0..1` 也一样。`main` 至少要求 `*`（或 `0..2` 之类的上限，但代码并没有限制长度），所以 `*` 是不和代码矛盾的最严格写法。

:::wrong Multiplicity 没写，就是 1
UML 没有默认 multiplicity。课本里的 `Admin` 和 `Student`：`Admin` 端写 `1`、`Student` 端写 `*`，意思是每个 student 恰由一个 admin 负责，一个 admin 负责任意多个 student。如果两端都不写，意思是“这张图不说明”，读的人既不能当成 1 对 1，也不能当成多对多。同理，visibility 没写不是 package private。
:::

### 其他关系

::fig[cs2103-relations] 七种关系的画法，每种配一个课本里的例子。注意线是实线还是虚线、箭头是空心三角、普通箭头还是菱形。

- **Inheritance**：实线加空心三角，三角指向 parent，`Car` ▷ `Vehicle`。三角填不填实无所谓，通常空心。
- **Interface 的实现**：和 inheritance 一样，只是线改成虚线，`AcademicStaff` 和 `AdminStaff` 都实现 `SalariedStaff`。
- **Composition**：实心菱形在 whole 那一端。`Book` 由 `Chapter` 组成，`Book` 被销毁时它的 `Chapter` 也随之销毁；part 离开 whole 就没有意义。
- **Aggregation**：空心菱形，表示 container 和 contained 的关系，但 part 可以独立存在。它和 composition 的界线很模糊，Martin Fowler 在 *UML Distilled* 里建议干脆不用，课本也这样建议。
- **Dependency**：虚线箭头，`A` ⇢ `B` 表示 `A` 依赖 `B`。只在这个依赖没有被别的关系表达时才画：association 和 inheritance 本身已经蕴含 dependency，再画一条是冗余的。例如 `ScoreBoard` 的某个 method 接收一个 `Player` 参数，但不把它存进 field，这时才画 dependency。
- **Association class**：一条虚线把一个 class 挂在一个 association 上，表示这个 class 存的是关于这次关联的信息。`User` borrows `Book`，`Loan`（借出日期、到期日）就是这个 association 的 association class。

### Conceptual class diagram

到目前为止画的都是 solution：软件里的 class。但在 design 之前还有一步，要先弄懂问题领域本身。Snakes and ladders 的描述是：两个或更多 player 用一块 board 和一个 die 玩；board 有 100 个 square；每个 player 有一个 piece；轮流掷 die 前进；落在 snake 头上滑到尾，落在 ladder 脚下爬到顶；先到第 100 格的赢。

**Conceptual class diagram**（CCD，也叫 OO domain model）用 class diagram 的 notation 画问题领域的结构：`Board`、`Square`、`Snake`、`Ladder`、`Piece`、`Player`、`Die` 以及它们之间的 association 和 multiplicity（`Board` 有 100 个 `Square`，每个 `Player` 有 1 个 `Piece`）。它是 class diagram 的一个子集：

- 不画 method，也不画 navigability：现实世界里的 square 不“持有”任何 reference；
- 不出现 solution 才有的 class，例如 `DatabaseConnection`、`TextUi`。

CMU 17-214 给了找 concept 的办法：读需求描述，把名词圈出来作为候选 concept，把动词作为候选 operation 或 association。还有一条判断 concept 和 attribute 的规则：如果某样东西在现实世界里不只是一个数字或一段文字，就把它画成独立的 concept，用 association 连起来，而不是塞成别人的 attribute。

:::from
Model 的三种用途、class 的画法和 visibility 表、没有默认 visibility 和 multiplicity、association 的 label、role、multiplicity、navigability、association 写成 attribute、Box/Item/Card 练习（题目与课本给的参考答案图）、object diagram 的 notation 和 `jake` 的例子、七种关系、Fowler 对 aggregation 的意见、dependency 只在未被其他关系表达时才画、snakes and ladders 的 CCD 和 CCD 与 class diagram 的区别，来自课本 UML 和 Modeling 两章。逐个 field 推 multiplicity、两条 association 不能合并的理由、用 object diagram 反过来检验 multiplicity，是为这一页写的。名词抽取和 concept 与 attribute 的判别来自 [CMU 17-214 Lecture 6](https://cmu-17-214.github.io/f2022/slides/06-oo-analysis.pdf)。
:::

## [behavior] Sequence diagram 与 activity diagram

:::skip
能把一段有 `if`、循环、`new` 和链式调用的 Java 代码画成 sequence diagram，能把一段文字描述的流程画成带 fork、join、branch 的 activity diagram，并判断一个执行顺序是否被允许，就可以去第 6 站。
:::

### Class diagram 回答不了的问题

上一站的 class diagram 说明了谁持有谁，却说不出“调用 `executeStep` 时，到底先调了哪个 method、后调了哪个、在什么条件下调”。要检查一个设计能不能产生想要的行为，或者从交互里找出每个 class 需要哪些 method，需要画行为。

### Sequence diagram

一个 **sequence diagram** 画一个具体场景里几个 object 之间的交互。课本的例子：

```java
class Workflow {
    Step executeStep(Step step) {
        step.init();
        if (step.isValid()) {
            step.execute();
        }
        return step;
    }
}
```

::fig[cs2103-seq] `executeStep` 的 sequence diagram。动图按时间顺序依次点亮每一条消息；`opt` 框里的 `execute()` 只在 `isValid()` 返回 true 时发生。

读法：

- 每个参与者是顶上的一个框，下面拖一条虚线 **lifeline**，时间从上往下走。`:Workflow` 表示一个匿名的 `Workflow` object，`step:Step` 有名字。和 object diagram 不同，这里的名字**不**加下划线。
- method call 画成实线箭头，返回画成虚线箭头，返回值写在虚线上。普通的 Java 调用是 synchronous 的，箭头用实心三角。
- 一个 method 正在执行的那一段，在 lifeline 上画一根细长的 **activation bar**。它从调用箭头到达时开始、到返回箭头离开时结束，中间不能断，也不能伸到调用之前或返回之后。
- 有条件的部分装进一个 frame：`opt [条件]` 表示满足条件才执行；`alt` 用虚线把 frame 分成几个分区，各带一个 guard，最多只执行其中一个；`loop [条件]` 表示重复；`par` 表示其中几个分区同时进行（对应的 Java 实现多半是 multi-threaded）；`ref` 表示这一段交互另画在别的图里。

创建、删除和自调用：

- 构造一个新 object 时，调用箭头直接指向新 object 的框（框画在箭头的高度，而不是顶上），activation bar 表示 constructor 运行的时间。
- Lifeline 末端画一个 X 表示 object 被删除。Java 没有 `delete`，X 用来表示从这一刻起它不再被引用，可以被 garbage collect。
- 一个 object 调用自己的 method，画成从自己 lifeline 出发又回到自己的箭头，新的 activation bar 叠在原来那根上面。
- 调用 static method 时，接收者是 class 本身，框里写 `<<class>> Person`。

第二个例子来自课本练习，加上了循环和创建：

```java
PersonList personList = new PersonList();
while (hasRoom) {
    Person p = new Person("Adam", "friend");
    personList.addPerson(p);
}
```

其中 `Person` 的 constructor 会 `tag = new Tag(tagName)`。

::fig[cs2103-seqloop] 循环里每一轮先创建一个 `Person`，它的 constructor 又创建一个 `Tag`，然后 `Person` 被加进 `personList`。

链式调用要先拆开再画。`person.getAddress().printStreet()` 这一行其实是两次调用，先改写成

```java
Address a = person.getAddress();
a.printStreet();
```

于是图上是：调用者先调 `person` 的 `getAddress()`，拿到返回的 `a`；再调 `a` 的 `printStreet()`。`printStreet()` 的箭头是从调用者出发的，不是从 `person` 出发的，这正是拆开之后才看得清的事。

为了不让图太乱，不影响理解时可以省掉 activation bar 和返回箭头；参数无关紧要时写成 `foo(...)`。

### Activity diagram

Sequence diagram 一次只画一个场景里的几个 object。一个流程本身（处理一份订单、计算一个成绩）的步骤、分支和并行，用 **activity diagram** 画，它相当于 UML 版的 flowchart：

| 元素 | 画法 | 规则 |
|---|---|---|
| action | 圆角矩形 | 流程里的一步 |
| control flow | 带箭头的线 | 不能是双向箭头 |
| start node、end node | 实心圆；外面再套一圈的实心圆 | |
| branch node、merge node | 菱形 | branch 的每条出线带一个方括号里的 guard，**恰好一个**为真；merge 在不会引起歧义时可省 |
| fork node、join node | 粗横条 | fork 之后的几条路径并行；join 要等所有从同一个 fork 出来的路径都完成，才继续往下 |

课本的练习：一家汉堡店处理订单的流程是，先由收银员接单；然后三个员工同时开始准备，一个做饮料、一个做汉堡、一个做甜点；同时顾客付款，有 voucher 就用 voucher，否则付现金；付完款并且三样都准备好之后，顾客取餐。

把它拆成元素：“同时”说明要 fork；付款和三样准备也是同时进行的，所以 fork 出 4 条路径；付款路径内部有一个二选一，是 branch 加 merge，两条出线的 guard 是 `[has voucher]` 和 `[else]`；“付完款并且三样都准备好之后”说明 4 条路径在同一个 join 汇合，然后才是取餐。

::fig[cs2103-activity] 汉堡店流程的 activity diagram。四条并行路径从一个 fork 出来、汇入一个 join；付款路径里有一个 branch。

Parallel path 允许什么样的执行顺序？课本的练习：fork 出两条路径，一条依次是 G1、G2，另一条依次是 H1、H2。允许的顺序必须满足两条：每条路径内部保持自己的先后（G1 在 G2 前，H1 在 H2 前），而且所有路径最终都要走完。G1 G2 H1 H2、G1 H1 G2 H2、G1 H1 H2 G2 都允许；G1 H2 G2 H1 不允许（H2 跑到了 H1 前面）；G1 H1 G2 不允许（H2 没走）。允许的顺序一共有多少种？4 个位置里选 2 个放 G（G 内部的先后已经定了），$\binom42=6$ 种。

较大的流程有两种整理办法：在某个 action 里画一个 rake 符号（像一把耙子），表示这一步的细节另画在一张 activity diagram 里；把图分成几条纵向的 swimlane，每条代表一个执行者（收银员、厨房、顾客），一眼看出谁做哪一步。

:::wrong Branch 的几个 guard 只要覆盖了所有情况就行，重叠一点无所谓
课本练习里有一张图，branch 的两条出线分别是 `[x <= 5]` 和 `[x >= 5]`。所有的 x 都被覆盖了，但 x = 5 时两个 guard 同时为真，流程不知道该走哪条，这张图是错的。Activity diagram 要求 branch 处恰好一个 guard 为真；sequence diagram 的 `alt` 同样要求最多一个分区被执行。n 条出线里有 n − 1 条写了 guard 时，剩下那条可以省略不写，自动理解为 `[else]`。
:::

:::edge 什么时候值得画
课本的提示：设计 component 时不必为每件事画完整的 UML。只有在不确定每个 class 需要哪些 operation，或者想验证某个 class 结构确实能支持某个行为时，才画 sequence diagram，而且草图就够了。课本用 Minesweeper 演示过这一点：先画 `TextUi` 收到 `newgame` 之后和 `Logic` 的交互，从图上读出 `Logic` 需要 `newGame()`、`getWidth()`、`getHeight()` 等 method，这就是 `Logic` 的 API。
:::

:::back
Sequence diagram 里的 object 必须和[第 4 站](#uml)的 class diagram 一致：图上 `A` 调用 `B` 的 method，class diagram 里 `A` 就得有途径拿到 `B`（association、参数或局部变量）。
:::

Sequence diagram 的全部 notation（lifeline、activation bar 的两种常见错误、opt、alt、loop、par、ref、创建、删除、自调用、static method、链式调用的拆法、最简 notation）、`Workflow` 的代码、`PersonList` 的练习、activity diagram 的元素和规则、汉堡店练习、parallel path 允许哪些顺序的练习、`[x <= 5]` 与 `[x >= 5]` 的错误、rake 与 swimlane、“不必画完整 UML”的提示和 Minesweeper 推 API 的例子，来自课本 UML、Modeling、Reuse（APIs）几章。两张 sequence diagram 和汉堡店的 activity diagram 是按课本的题目自己画的答案，没有对照课本的参考答案图；6 种顺序的计数是另加的。

## [design] Abstraction、coupling、cohesion 与 design principles

:::skip
能对一段代码判断 A 是否 coupled to B、某个 class 是否 cohesive，能指出它违反了 SRP、OCP、LSP、ISP、DIP、LoD 中的哪一条并改好，还能说出 DIP 和 dependency injection 的区别，就可以去第 7 站。
:::

### Abstraction

程序要处理的细节远多于一个人同时能记住的。**Abstraction** 的原则是：只考虑和当前任务有关的细节，把其余的藏到下面去。

- data abstraction：在某个 component 里只把 user 当作一个整体，不管里面的 name、date of birth；
- control abstraction：`print("Hello")` 把底层的输出机制藏起来。

Abstraction 可以一层层叠上去：`File` 比 array 高一层，array 比 bit 高一层；`execute(Game)` 比 `print(Char)` 高一层，`print(Char)` 比汇编指令 `MOV` 高一层。一个 class 是对一组数据和行为的 abstraction，architecture 是对整个 design 的 abstraction，UML model 是对现实某一方面的 abstraction。

Stanford CS 190 把这件事落到 module 上：每个 module 分成 **interface**（别的 module 必须知道的一切，包括 method signature，也包括 side effect 这类非正式的约定）和 **implementation**（兑现 interface 承诺的代码）。一个 module 应当把某个 design decision 藏在 implementation 里，interface 不透露它，这样决定改了，别人不用跟着改。反过来，implementation 的细节被别的 module 知道并依赖，叫 **information leakage**。

### Coupling：改 Y 时，X 可能要跟着改

开头第三次失败可以精确地描述出来。**X is coupled to Y**，如果 X 依赖 Y，使得 Y 的某些改动**可能**迫使 X 跟着改。

```java
class Foo {
    ...
    new Bar().read();
    ...
}
class Bar {
    void read() { ... }
    void write() { ... }
}
```

`Foo` 调用了 `Bar#read()`，所以 `Foo` coupled to `Bar`：`read()` 的 signature 一改，`Foo` 就得改。但不是 `Bar` 的每个改动都波及 `Foo`，改 `write()` 就不会，因为 `Foo` 没用它。所以定义里是“可能”。

A coupled to B 的几种情形：A 能访问 B 的内部结构（最强的 coupling）；A 和 B 依赖同一个 global variable；A 调用 B；A 接收或返回一个 B 的 object；A 继承 B；A 和 B 必须遵守同一种数据格式或通信 protocol。方向要看清：child class coupled to parent class，parent 并不 coupled to child；两个 class 由同一个人写，不构成 coupling。

拿开头的例子算一下。数据从文本文件换成 JSON，这是对“文件格式”的改动。

::fig[cs2103-ripple] 同样是把文件格式换成 JSON。左边 `Ui`、`Logic` 和 test 都直接读文件字段，四处都要改；右边只有 `Storage` 知道文件格式，其他 component 只依赖 `Storage` 的 interface，只改一处。

左边的设计里，`Ui`、`Logic`、test 都和文件格式 coupled，一个改动要改 4 处；右边只有 `Storage` 和文件格式 coupled，改 1 处。Coupling 高的代价正是这样算出来的：

- 维护难：一处改动沿着依赖反向扩散（ripple effect）；
- integration 难：互相 coupled 的几个 component 必须一起集成；
- 测试和复用难：要测或要拿走一个 component，得把它依赖的全带上。

Coupling 按强弱还有名字：content coupling（改动或依赖另一个 module 的内部）、common/global coupling（共享 global data）、control coupling（传一个 flag 告诉对方该怎么做）、data coupling（只传数据参数）、external coupling（共同遵守外部强加的格式或 protocol）、subclass coupling（继承）、temporal coupling（只因为恰好同时发生，就把不相关的动作捆在一起，例如把一段相邻但互不相关的语句 extract 成一个 method）。

### Cohesion：一个 component 的职责有多相关

**Cohesion** 衡量一个 component 的各项职责之间有多紧密相关。高 cohesion 好：相关的放一起，不相关的不放进来。课本比较了两个版本的 `EmailMessage`：

```java
// version 2
class EmailMessage {
    private String sendTo;
    private String subject;
    private String message;
    private String username;
    public EmailMessage(String sendTo, String subject, String message) { ... }
    public void sendMessage() { ... }
    public void login(String username, String password) {
        this.username = username;
        // code to login
    }
}
```

version 1 没有 `username` 和 `login`。version 2 的 cohesion 更低：登录和“一封邮件”这个概念无关。再进一步，两个版本都可以去掉 `sendMessage()` 来提高 cohesion：发送当然和邮件有关，但这个 class 代表的是一封邮件，不是邮件服务器。

Cohesion 低的代价：说不清这个 module 是干什么的；它会因为互不相关的原因被修改，或者反过来，一个小的行为改动要改好几个 module（相关代码没有集中）；不构成一个完整的功能单元，难以复用。

### Design principles

下面几条 principle 都可以看成是在具体情形下降低 coupling、提高 cohesion。前五条的首字母合起来叫 SOLID。

**Single responsibility principle（SRP）**：一个 class 应当只有一个改变的理由。一个 `TextUi` 既解析用户命令又负责和用户交互，UI 格式一变它要改，命令语法一变它也要改，有两个理由，违反 SRP。Robert C. Martin 的说法是：把因为同样理由而变的东西放在一起，把因为不同理由而变的东西分开。

**Open-closed principle（OCP）**：一个 module 应当对 extension 开放、对 modification 封闭，也就是不改它的代码就能扩展它的行为。做法通常是把 interface 和 implementation 分开。`CommandQueue` 只认识抽象的 `Command`，执行队列里每一个的 `execute()`；要支持删除，只需新写一个 `Delete extends Command`，`CommandQueue` 一行不改。Java 的 `ArrayList<Student>` 和 `ArrayList<Admin>` 也是一例：同一份 `ArrayList` 代码，换一个 type parameter 就装别的东西。

**Liskov substitution principle（LSP）**：subclass 必须能替换它的 base class。它比 Java 语言层面的 substitutability 更进一步：subclass 不能比 superclass 规定的行为更严格。课本的例子：`Staff#adjustMySalary(int percent)` 规定对所有正的 percent 都能工作，`Payroll` 依赖这一点。`Admin` 的 override 对正负 percent 都能工作，没有问题；`Academic` 的 override 只接受 1 到 100，`Payroll` 传入 150 时就会出错，违反 LSP。Precondition 不能加强、postcondition 不能减弱的完整论证见 [CS2030 的 LSP 一站](../courses/CS2030.html#lsp)。

**Interface segregation principle（ISP）**：不应强迫 client 依赖它不用的 method。`Payroll#adjustSalaries(AdminStaff staff)` 只用到发薪相关的 method，却依赖了带 `arrangeMeeting()` 的 `AdminStaff`；改成依赖只含发薪 method 的 `SalariedStaff` interface，`AdminStaff` 的会议功能怎么改都和 `Payroll` 无关了。

**Dependency inversion principle（DIP）**：高层 module 不应依赖低层 module，两者都应依赖 abstraction；abstraction 不应依赖细节，细节应依赖 abstraction。

::fig[cs2103-dip] 左边 `Payroll` 直接依赖 `Employee`；右边引入 `Payee` interface，`Payroll` 依赖它，`Employee` 实现它。箭头数从 1 变成 2，但 `Employee` 再怎么改，只要还满足 `Payee`，`Payroll` 都不用动。

:::wrong DIP 减少了 dependency
数一数上图的箭头。左边只有一条：`Payroll` → `Employee`。右边有两条：`Payroll` → `Payee`，以及 `Employee` ⇢ `Payee`（实现 interface 也是一种 dependency）。Dependency 的数目从 1 变成了 2，DIP 还多引入了一个 abstraction，让 design 更复杂。它改变的是方向：原来 `Payroll` 指向具体的 `Employee`，现在两者都指向抽象的 `Payee`，`Employee` 的那条箭头从“被依赖”变成了“去依赖”，所以叫 inversion。好处是 `Payroll` 不再和 `Employee` 的细节 coupled。另一个常见的混淆是把 DIP 和 dependency injection 当成一回事：后者是在测试时把一个 dependency 换成 stub（第 10 站），是一种技术；DIP 是关于依赖方向的 design principle。
:::

**Law of Demeter（LoD）**，又叫 “don't talk to strangers” 或 principle of least knowledge：object `O` 的 method `m` 只应调用以下几类 object 的 method：`O` 自己；`m` 的参数；`m` 里创建的 object；`O` 直接 associated 的 object。课本拿 Minesweeper 的 `Logic#setMinefield(Minefield mf)` 逐行检查：

| `setMinefield` 里的一行 | 是否违反 LoD | 理由 |
|---|---|---|
| `mf.init();` | 否 | `mf` 是参数 |
| `mf.getCell(1, 3).clear();` | 是 | `Cell` 是参数内部的 object，朋友的朋友；应改成 `mf.clearCellAt(1, 3);` |
| `timer.start();` | 否 | `timer` 是 `Logic` 自己的 field |
| `Cell c = new Cell(); c.init();` | 否 | `c` 在方法里创建 |

违反 LoD 的那一行让 `Logic` 依赖了 `Minefield` 内部用 `Cell` 来表示格子这个细节，也就是上面说的 information leakage。

**Separation of concerns（SoC）**：把代码分成不同部分，每部分处理一个 concern（一个 feature、一个方面如 persistence 或 security、一个实体如 `Employee`）。Persistence 的代码和 security 的代码分开，改存储方式就不用动安全机制。它在 class 层面和更高层面（把应用分成 layer）都适用，结果是更高的 cohesion 和更低的 coupling。

**DRY（Don't Repeat Yourself）**：每一份知识在系统里只有一个权威表示。同一个功能实现两遍（即使两遍写法不同）、系统级的 timeout 值在几个地方各定义一次，都违反 DRY：将来只改了其中一处，两处就不一致了。

**YAGNI（You Aren't Gonna Need It）**：不要因为“将来也许用得上”现在就写。对未来的预测会落空，为落空的预测做的工作就白做了，还白白增加了要维护的代码。

### Design 的进行方式

Multi-level 的 design 可以 top-down（先定高层，再细化低层，适合大而新的系统，高层要先稳定）、bottom-up（先设计低层 component 再拼起来，适合在已有 component 的基础上做变体），或者高层 top-down、低层 bottom-up 混用。Agile design 认为 design 会随着产品演化：一开始只做刚够团队起步的 architecture 建模，详细的 design 在过程中逐步浮现，而不是在写代码之前就画齐所有 model。

:::from

## [patterns] Design patterns

:::skip
能对一个场景说出该用 Singleton、Facade、Command、Abstraction Occurrence、MVC 还是 Observer，写出 Singleton 和 Observer 的骨架，并说清每个 pattern 用什么切断了哪条 dependency，就可以去第 8 站。
:::

### Pattern 是什么

有些 design 问题在一定的 context 下反复出现：后端数据变了，UI 要更新，但后端不该依赖 UI；系统要连接几个用不同技术实现的已有系统。人们反复解决之后，沉淀出一些经过检验的好解法，叫 **design pattern**。这个词因 Gamma、Helm、Johnson、Vlissides 四人（Gang of Four，GoF）的书而流行，书里有 23 个 pattern，分成三类：creational（关于 object 怎么创建，如 Singleton）、structural（关于 object 怎么组合成更大的结构，如 Facade）、behavioral（关于 object 怎么交互、职责怎么分配，如 Command、Observer）。

描述一个 pattern 的固定格式：context（问题在什么情形下出现）、problem（要解决的主要困难）、solution（解法的核心，只含最一般的细节），可选的 anti-pattern（常见但更差的做法）、consequences（利弊）和其他信息。Pattern 还提供了一套交流用的词汇：说“这里用 Observer”就够了，不必把机制从头描述一遍。

下面每个 pattern 都按这个格式来。

### Singleton

**Context**：有些 class 只应有一个 instance，例如系统的主 controller。**Problem**：普通的 class 可以通过调用 constructor 被任意多次 instantiate。**Solution**：constructor 设为 `private`，用一个 `private static` field 保存唯一的 instance，提供一个 `public static` method 访问它。

```java
class Logic {
    private static Logic theOne = null;

    private Logic() {
        ...
    }

    public static Logic getInstance() {
        if (theOne == null) {
            theOne = new Logic();
        }
        return theOne;
    }
}
```

外面拿不到 `new Logic()`，只能写 `Logic.getInstance()`；第一次调用时创建，之后每次返回同一个。在 class diagram 里给它加上 stereotype `<<Singleton>>`。

**Consequences**：容易实现，效果确实达到，在任何地方都能拿到这个 object。代价是：它实际上是一个 global variable（CMU 17-214 的说法是 “Singleton = global variable”），增加了整个代码库的 coupling；测试时难以换成 stub，因为 static method 不能被 override；而且它会把数据从一个测试带到下一个测试。

:::wrong 用了 pattern，design 就更好；需要一个 object 时用 Singleton 最省事
看 Singleton 把数据带进下一个测试是什么样子。设 `Logic` 是 Singleton，里面有一个 task list。测试一调用 `Logic.getInstance()` 加了 3 个 task，检查 size 是 3，通过。测试二也调用 `Logic.getInstance()`，期望一个空的 list，检查 size 是 0，结果是 3，失败，而测试二本身没有任何错。更糟的是，单独跑测试二会通过，按另一种顺序跑测试也可能通过，失败取决于执行顺序。所以课本建议：只有在除了“只需要一个”之外，还确实存在误建多个的风险、且多个 instance 会造成实际损害时，才用 Singleton。一般地，pattern 都带有额外的 class 和 abstraction 层，只有在对 design 有实质改进时才用。
:::

### Facade

**Context**：component 需要访问另一个 component 深处的功能，例如图书馆系统的 `UI` 想用 `Logic` component 里 `Book` class 的功能。**Problem**：要允许访问，但不暴露 component 的内部细节，`UI` 不应知道 `Logic` 里有一个 `Book` class。**Solution**：在 component 内部和它的使用者之间放一个 facade class，所有访问都经过它。图书馆的例子里，`LibraryLogic` 就是 facade：`TextUI` 和 `GUI` 都只依赖 `LibraryLogic`，`Book` 等内部 class 怎么改都和 UI 无关。这正是 LoD 和 information hiding 在 component 层面的做法。

### Command

**Context**：系统要执行很多种 command，各做不同的事，例如 `Sort`、`List`、`Reset`。**Problem**：希望某部分代码能执行这些 command 而不必知道每一种是什么，例如一个 `CommandQueue` 负责排队执行，不关心每个 command 具体做什么。**Solution**：定义一个通用的 `Command` 类型（abstract class 或 interface），有 `execute()`，需要时还有 `undo()`；每种 command 是它的一个 subclass。

::fig[cs2103-command] Command pattern 应用到 `CommandQueue`。`CommandCreator` 创建具体的 command 并放进队列；`CommandQueue` 只认识 `Command`，靠 polymorphism 调用每一个的 `execute()`；具体的 command 执行时去操作 `DataStore`。

一般形式里的角色：client 创建 command object 交给 invoker；invoker 把所有 command 都当作 `Command` 对待，调用 `execute()` 发出请求；command 执行时作用在它的 receiver 上；如果 command 可以 undo，invoker 在调用 `execute()` 之前保存撤销所需的状态。上一站 OCP 的例子就是它：加一个 `Delete` 只需加一个 subclass。

CMU 17-214 指出，Command 和 Strategy 两个 pattern 的结构几乎一样，区别在 intent：Command 是一个可以延后执行、排队、记录、复用的“请求”；Strategy 是配置一个算法中可替换的一部分。分辨 pattern 看 intent，不看结构。

### Abstraction Occurrence

**Context**：一组相似的实体看起来是同一样东西的若干“occurrence”，共享大量信息，又在重要的地方各不相同。图书馆里同一个 title 有好几本：书名、作者、ISBN 都一样，购买日期和条形码各不相同。

**Problem**：用一个 class 表示它们会重复存数据。设某个 title 有 5 本，每本都存一份书名、作者、ISBN。作者名拼错了，要改 5 个 object；漏改一个，数据就不一致；新进第 6 本时，又要保证录入的信息和前 5 本一模一样。

**Anti-pattern**：给每个 title 写一个 subclass，把共同数据写死在 class 里。图书馆有几千个 title 就有几千个 class，每买一种新书都得改源代码。

**Solution**：把一个实体拆成两个 object：abstraction 保存共同的信息，occurrence 保存各自的信息，每个 occurrence 连向它的 abstraction。

::fig[cs2103-abstocc] 左边每本书各存一份共同信息；右边 `BookTitle` 存共同信息，5 个 `BookCopy` 只存各自的条形码和购买日期，作者名只有一处。

现在作者名拼错只改 `BookTitle` 一处。注意 “Abstraction” 和 “Occurrence” 是角色名，不是 class 名。判断能不能用这个 pattern，看“一个真实实体是不是由一个 abstraction object 加一个 occurrence object 共同表示”：`CarModel` 和 `Car`、`Magazine` 和 `MagazineIssue` 可以；`Car` 和 `Wheel` 不行（wheel 是 car 的一部分，不是它的 occurrence）；`Club` 和 `Member`、`TeamLeader` 和 `TeamMember` 也不行。

### MVC

**Context**：多数应用都要存取信息、把信息展示给用户（常常是几种不同格式的界面），并按外部输入修改信息。**Problem**：这几件事交织在一起，容易造成高 coupling。**Solution**：把数据、展示和控制逻辑分成三个 component：

- **Model**：保存应用的状态，实现作用在其上的规则和操作，状态变化时可以通知感兴趣的 component；
- **View**：把信息展示给用户，提供交互用的 UI 元素，从 model（或 controller 提供的数据）拉取要显示的内容；
- **Controller**：处理用户输入（如鼠标点击），解释它，调用 model 的操作或触发 view 的更新。

通常 UI 是 view 加 controller；只有一个 view 的简单 UI 里，两者可以合成一个 class。MVC 有很多变体，桌面 GUI 和 web 应用里用的就不一样。

### Observer

**Context**：一个学生管理系统，用户通过 `NewStudentUi` 加了一个学生到 `StudentList`。另外还有两个界面同时开着：`StudentListUi` 显示学生名单，`StudentStatsUi` 显示统计。加了学生之后，这两个界面都应当自动更新。但 `StudentList` 并不知道这两个 UI 的存在（navigability 是从 UI 指向 `StudentList` 的），没办法通知它们。

**Problem**：被观察的 object 不希望和观察它的 object coupled。如果让 `StudentList` 直接持有 `StudentListUi` 和 `StudentStatsUi`，model 就依赖了 view，每加一种新界面都要改 `StudentList`。

**Solution**：通过一个双方都认识的 interface 来通信。

```java
interface Observer {
    void update();
}

class StudentList {
    private List<Observer> observerList = new ArrayList<>();

    public void addUi(Observer o) {
        observerList.add(o);
    }

    public void add(Student s) {
        ...
        notifyUIs();
    }

    private void notifyUIs() {
        for (Observer o : observerList) {
            o.update();
        }
    }
}

class StudentListUi implements Observer {
    public void update() {
        // refresh by pulling data from StudentList
    }
}
```

系统初始化时，两个 UI 各调用一次 `studentList.addUi(...)`，叫作订阅（subscribe）；之后每当 `StudentList` 变化，`notifyUIs()` 逐个调用 `update()`，UI 再从 `StudentList` 拉取新数据。

::fig[cs2103-observer] 应用 Observer 前后。之前 `StudentList` 无路通向两个 UI；之后它只依赖 `Observer` interface，两个 UI 实现这个 interface 并订阅。

这里有两处用到了 polymorphism。`StudentList` 把所有订阅者都当作 `Observer`，调用的是同一个 `update()`；但 `StudentListUi` 和 `StudentStatsUi` 的 `update()` 各自以不同方式刷新，具体执行哪个由 object 的实际类型决定（[CS2030 的 dynamic binding](../courses/CS2030.html#dispatch)）。一般形式里，被观察者叫 observable（subject），提供 `addObserver(Observer)` 和 `notifyObservers()`。

:::edge Observer 之后，subject 并非不依赖任何东西
`StudentList` 仍然依赖 `Observer` 这个 interface，只是不再依赖具体的 UI class，这和第 6 站 DIP 的结构一样。Northeastern CS 3500 还指出一个实际问题：每个 observer 都收到每一次通知（他们的例子是每个订阅者都收到每场演唱会开票的通知，哪怕只关心其中一场），订阅者一多就成了垃圾消息，可以改成按主题订阅，或者把多次更新合并成一次通知。另外 Java 的 `Object` 已经有一个 `notify()`（用于线程同步），所以 observer 的方法不要取这个名字。
:::

### 几个 pattern 放在一起

Pattern 通常嵌在更大的 design 里，也常常组合使用。课本的商店库存系统（SIS）逐步应用了五个：`StockItem` 的共同信息和每件货物分开，用 Abstraction Occurrence；用一个 facade 把 SIS 的内部挡在 UI 之外；UI 有好几个 view（店员终端、店长终端一直显示所有货物），用 MVC；数据变了店长的 view 要更新，用 Observer；facade class 只需要一个，用 Singleton。

:::from

## [arch] Architecture、integration 与 reuse

:::skip
能说出 layer 和 tier 的区别、modular monolith 与 microservices 各自付出什么，能给一棵 dependency 树排出 top-down 和 bottom-up 的 integration 次序并数出要写几个 stub、几个 driver，还能区分 library 和 framework，就可以去第 9 站。
:::

### Architecture 与 architecture diagram

**Architecture** 是一个软件系统的高层结构：由哪几个主要部分组成、它们之间是什么关系。它本身是 design 的一个 abstraction，用 architecture diagram 表达。Architecture diagram 没有统一的 notation，所以读的时候按顺序问四个问题：这是哪种 view（代码组织、部署位置、通信方式……）；主要部分是哪些（通常是几个框，不是三十个）；每个部分负责什么；每条线是什么意思（看箭头方向和图例）。

同一个系统可以有不同的 view。课本用一个桌面版的 invoice manager 说明：

- **logical view** 画主要部分和它们之间的 dependency：`Ui`、`Logic`、`Model`、`Storage` 四个 component，箭头表示依赖；
- **deployment view** 画各部分实际在哪里运行：四个 component 都在同一台电脑的同一个程序里，图很无聊。

“这个系统有 4 个 component”和“这个系统跑在 4 台电脑上”是完全不同的两句话，一张把两者混在一起的图会误导所有读者。

画 architecture diagram 的几条规矩：component 按职责命名，而不是按当前实现（叫 `Storage`，不叫 `JsonFileHandler`，后者换成数据库就不对了）；只画 architecture 层面的东西，超过一把手指能数的 component 多半说明已经滑到了低层；用常见的符号（圆柱表示数据库）并配图例；不要到处用双向箭头。最后一条的原因：如果每对 component 之间都是一条不带说明的双向箭头，读者无法分辨哪对是真的互相依赖、哪对只是一方依赖另一方，而依赖的方向恰恰是 architecture diagram 最重要的信息。

### Architectural style

**Architectural style** 是组织系统主要部分的一种可复用的方式。几种 style 描述的是系统的不同方面，所以一个系统可以同时属于好几种。

**Layered**：软件分成若干 layer，dependency 一律向下，上层使用下层的服务，下层对上层一无所知。Strict（closed）layering 只允许用紧邻的下一层；更常见的 relaxed layering 允许跨层往下用。不论哪种，dependency 从不向上，于是可以单独理解、测试、替换任何一层而不用顾及上面的层。Invoice manager 里 `Logic` 既用 `Storage` 又用 `Model`，是 relaxed layering。操作系统和网络协议栈是典型例子。

**Layer 不是 tier。** Layer 是软件内部的逻辑划分；tier 是一个单独部署的部分（不一定是一台物理机器）。桌面版 invoice manager 有 4 个 layer，却只有 1 个 tier。容易混淆是因为 “n-tier” 常被拿来指 layered。

**Client-server**：server 提供某种能力或数据，一个或多个 client 使用它。共享数据或计算是最常见的理由：几个用户要编辑同一批 invoice，各自电脑上的本地文件就不够用了。加一个 server，两种 view 都会变：logical view 里 `Storage` 换成通过网络发请求的 `RemoteStorage`；deployment view 里 client 和 server 成了两个 tier。因为 `Logic` 依赖的是 `Storage` 的 interface，一个守同样 interface 的 `RemoteStorage` 可能让 `Logic` 一行不改。但整个系统多了本地调用从来没有的负担：请求慢得多且耗时不定；timeout 时不知道 server 是在做之前还是做之后失败的，草率重试可能把操作做两遍；新 server 可能收到旧 client 的请求；server 要决定谁能读写共享的数据。

::fig[cs2103-arch] 同一个 invoice manager 的两种 architecture。左边是单机的 layered 结构，4 个 layer、1 个 tier；右边加了 server，`Storage` 换成 `RemoteStorage`，经过网络和 server 上的 request handler 通信，变成 2 个 tier。

**Event-driven**：工作由 event 触发，而不是由直接调用触发。发出 event 的叫 emitter，响应它的叫 consumer，由一个 dispatcher 把 event 送到对应的 consumer。写过 GUI 就写过 event-driven 的代码：按钮并不包含点击后要执行的逻辑，UI framework 把 click event 交给登记过的 handler。分布式的系统常用 publish-subscribe：emitter 把 event 发给 message broker，broker 送给所有订阅了的 component。它降低了 coupling（新 consumer 订阅时 emitter 不用改），代价是可追踪性：要回答“删除一张 invoice 时会发生什么”，得去找好几个 handler，代码里没有任何一处能直接告诉你。

**Transaction processing**：系统接收一个个独立的请求（transaction），可靠地、通常是大量地处理它们，例如银行终端把交易提交给中央系统，由一个 dispatcher 分给对应的 executor。这里的 transaction 和 database transaction（一组要么全成功要么全失败的数据库操作）是两回事。

**Service-oriented（SOA）与 microservices**：service 通过网络公开一个 interface，调用者依赖这份约定，而不依赖它用什么语言、怎么实现。例如第三方把一家公司的商品服务和一家银行的信用卡服务组合成一个网上书店，三个系统在三个不同平台上。**Microservice** style 把一个产品做成一组可以各自独立部署的 service，每个专注一项能力，通常各自拥有背后的数据。

另一端是 **monolith**：整个系统作为一个单元部署。“monolith” 不等于“结构混乱”，它只说部署方式；一个 monolith 内部可以有清楚的 component、清楚的 interface 和单向的 dependency，这叫 **modular monolith**。

| | modular monolith | microservices |
|---|---|---|
| 部署 | 一个单元，一起发布 | 很多单元，各自发布 |
| 通信 | 主要是同一个 process 内的调用 | 跨网络的请求或消息 |
| 数据归属 | 靠纪律维持，常共用一个存储 | 靠隔离维持，每个 service 只能通过 interface 访问 |
| 一部分失败时 | 通常影响整个单元 | 其余部分可以继续运行，但前提是专门为此设计过 |
| 测试与 debug | 构建和检查一样东西 | 要启动和协调很多样东西 |
| 适合 | 一个团队发布一个产品 | 多个团队需要各自发布 |

Microservices 用运维上的简单换来团队和部署上的独立。对一个团队做一个产品，modular monolith 是合理的默认；只有当一个具体的 requirement 值得付出网络带来的延迟、部分失败、安全和运维成本时，才加一道网络边界。

### Integration：拼起来的次序

把软件的各部分组合成整体叫 integration，它几乎从不顺利。一般的建议有两条，都是在控制一次暴露出来的问题有多少：

- 按频率：late and one-time（所有 component 做完了才在项目末尾一次合起来）不推荐，前期的误解会集中爆发，导致交付延误；early and frequent（先写一个 walking skeleton，大家在上面并行地一点点加功能，每做完一个就合进去）推荐。
- 按粒度：big-bang（一次合很多）会同时冒出很多问题，难以定位；incremental（一次合几个）推荐。

Incremental integration 还要决定次序。课本的练习给了一棵 dependency 树：A 依赖 B、C、D；B 依赖 E、F；C 依赖 G；D 依赖 H、I；E 依赖 J；G 依赖 K、L；H 依赖 M。

**Top-down**：先合高层，再合低层。A 要运行就得调用 B、C、D，而它们还没合进来，只能用 **stub**（和真 component 的 interface 一样，但只返回写死的结果）顶替。次序是：A 加 B、C、D 的 stub；然后合入真的 B、C、D，再为它们的下层 E、F、G、H、I 写 stub；然后合入这一层，为 J、K、L、M 写 stub；最后合入 J、K、L、M。要写的 stub 是 3 + 5 + 4 = 12 个，A 以外的每个 component 都被 stub 过一次。好处是高层的问题（往往也是最贵的问题）最早暴露。

**Bottom-up**：反过来，先合低层。低层 component 合在一起之后，上面还没有调用它的代码，要写 **driver**（通过 API 给 component 提供输入、检查输出的代码）来驱动它们。次序是：E 和 J、G 和 K、L、H 和 M 各合成一组；再分别并入 B 和 F、C、D 和 I；最后由 A 把三组合起来。每合成一组都要一个 driver 来调用这一组的顶端，在 A 进来之前一共要为 E、G、H、B、C、D 写 6 个 driver。

**Sandwich**：上面几层 top-down、下面几层 bottom-up，在中间会合。

::fig[cs2103-integ] 同一棵 dependency 树的两种 integration 次序。动图先演示 top-down：每一轮把 stub（虚线框）换成真 component，同时为下一层补上新的 stub；再演示 bottom-up：从叶子往上，一组组合起来，每组顶端由 driver 驱动。

实际项目往往混用。课本的医院系统练习：`HospitalUI` 会先做出来以便早拿客户反馈，所以它适合 top-down 地配 stub 先合；`HospitalFacade` 只是转发调用，为它写 stub 不值得，适合 bottom-up；`IO_Helper` 从旧项目拿来、很多 class 都用它，可以先完成并 bottom-up 地合入；外包的 `OutPatient` 要到后半程才交付，`PatientMgr` 只能先配它的 stub。

**Build automation** 把构建的各个步骤（拉代码、编译、运行测试、打包、部署……）写成脚本自动执行，Java 常用 Gradle 或 Maven，它们同时管理第三方 library 的版本（dependency management）。把它推到极致是 **continuous integration（CI）**：每次代码改动都自动 integrate、build、test；再进一步是 **continuous deployment（CD）**：通过了的改动同时自动部署给用户。

### Reuse：API、library、framework、platform

**API**（application programming interface）规定其他程序怎样和一个 component 交互，是 component 和它的 client 之间的约定。一个 class 的 API 是它的 public method；GitHub 的 API 是它接受的一组 web request 格式和对应的响应。及早定下各 component 的 API，团队就能并行开发。课本建议用 sequence diagram 推出 API（第 5 站最后一个例子），并把每个 operation 写精确：

```
Operation:      clearCellAt(int x, int y): void
Description:    Records the cell at x, y as cleared.
Preconditions:  game state is READY or IN_PLAY.
                x and y are in 0..(H-1) and 0..(W-1), respectively.
Postconditions: Cell at x, y changes state to ZERO, ONE, ..., EIGHT,
                or INCORRECTLY_CLEARED. Game state changes to IN_PLAY,
                WON or LOST as appropriate.
```

Precondition 是调用前必须成立的条件，postcondition 描述调用完成后系统的状态，不说过程中怎么做。

复用的三种形式：

- **library**：一组通用的代码，供别的程序调用，例如 JDK 里的 `String`、`ArrayList`。用之前要读文档确认功能合适、检查 license 是否允许你的用法。
- **framework**：某一类软件的可复用实现，提供通用的功能，留出可以定制的地方，例如 JavaFX（GUI）、JUnit（测试）、Spring（web）。它和 library 的关键区别是 **inversion of control**（又叫 Hollywood principle：don't call us, we'll call you）：你的代码调用 library；framework 调用你的代码。你在 JUnit 里写一个 `@Test` method，从来不自己调用它，是 JUnit 找到并调用它。
- **platform**：提供一个 runtime environment，通常还附带 library、framework 和工具，例如 JavaEE（运行在 JVM 上）、.NET（运行在 CLR 上）；操作系统本身也是 platform。

**Cloud computing** 把计算作为通过网络提供的服务，分三个层次：IaaS 提供基础设施（虚拟服务器、存储，如 Amazon EC2），你自己装软件、部署；PaaS 提供一个可以在上面构建应用的平台，部署和负载均衡由平台负责，代价是只能用平台提供的设施（如 Google App Engine）；SaaS 直接通过网络提供应用本身（如 Google Docs、Google Calendar）。

复用也有代价：可能大材小用，拖大程序、拖慢性能；不成熟的 library 可能剧烈变动甚至停止维护；license 可能限制你的用法；它的 bug 和安全漏洞对你很重要、对维护者不重要；被入侵的 dependency 可能带进恶意代码。

:::wrong Monolith 就是结构混乱的旧式系统，拆成 microservices 才是好的 architecture
课本的练习：一个团队做一个桌面 invoice manager，有人提议把本地存储拆成 invoice storage、search、reminder 三个单独部署的后端 service，理由是“microservices 是现代 architecture”。拆分能换来的是独立部署和独立扩容，而一个团队一起发布整个产品、也没有任何部分承受高负载时，这两样几乎没有价值。付出的却是每次操作都走网络、要处理部分失败、要运行三套后端部署、测试和 debug 都更难。更好的起点是一个 modular monolith，里面有清楚的 storage、search、reminder component；边界清楚，将来真有 requirement 时再把某一块拆成 service，现在不必付分布式的成本。Monolith 描述的是部署方式，不是内部的质量。
:::

### Readability 为什么排在前面

Production code 会被别人读、理解、修改很多次，几个月后你自己也成了陌生人。所以在 run-time efficiency、security、robustness 等各种质量里，readability 排在最前面。课本的 guideline 很多，这里拿几条最有机制可讲的，各用课本的例子走一遍。

**让 happy path 显眼。** 下面这段代码里，主流程（`start` 到 `exit`）被埋在两层 `if` 里，而“发现异常情况”和“处理它”隔得很远：

```java
if (!isUnusualCase) {  // detecting an unusual condition
    if (!isErrorCase) {
        start();    // main path
        process();
        cleanup();
        exit();
    } else {
        handleError();
    }
} else {
    handleUnusualCase(); // handling that unusual condition
}
```

用 guard clause 改写：一发现特殊情况就处理并 `return`，主流程不缩进。

```java
if (isUnusualCase) { // guard clause
    handleUnusualCase();
    return;
}
if (isErrorCase) {   // guard clause
    handleError();
    return;
}
start();
process();
cleanup();
exit();
```

读的人不用再把“外层 `if` 的条件是什么”一直记在心里，读到哪个特殊情况就看到它的处理。循环里的同一个技巧是用 `continue` 跳过特殊情况。

**SLAP（single level of abstraction principle）。** 一段代码里不要混着几个 abstraction 层次：

```java
readData();
salary = basic * rise + 1000;
tax = (taxable ? salary * 0.07 : 0);
displayResult();
```

`readData()` 和 `displayResult()` 是高层的步骤，中间两行是低层的算式，读者被迫在两个层次之间跳。改成三个同一层次的步骤 `readData(); processData(); displayResult();`，算式放进 `processData()`。

**不用 magic literal。** 上面的 `1000` 和 `0.07` 是什么？读者无从知道。换成 named constant（`BONUS`、`TAX_RATE`）之后，名字本身就是说明，改税率也只改一处，这同时是在遵守 DRY。

其余的 guideline 课本按类别列出，考试会直接问，所以这里列全：避免长 method（超过 30 行左右就考虑拆）、深嵌套和复杂表达式；不要过早优化（make it work, make it right, make it fast）；KISS，不写“聪明”的代码；遵守 coding standard，让整个代码库像一个人写的；class 和 variable 用名词、method 用动词，单值和多值的名字要分得开；`switch` 一定要有 `default` 分支，并且用它表示真正的默认情况或者报错，而不是放最后一个选项；不要留空的 `catch`；不复用 variable 或 parameter 做别的用途；variable 的 scope 尽量小；死代码立刻删（需要时从 revision control 找回）；注释写给别的程序员，说明 what 和 why，而不是 how，不重复代码里已经显而易见的东西。

### Refactoring

**Refactoring** 是在不改变外部行为的前提下，小步地重构代码。两个“不是”：从头重写不是 refactoring，因为它不是小步进行的；修 bug 和加功能也不是，因为它们改变了外部行为。

课本的两个例子：

- **Consolidate duplicate conditional fragments**：同一段代码出现在 conditional 的每个分支里，就把它移到外面。

```java
if (isSpecialDeal()) {
    total = price * 0.95;
    send();
} else {
    total = price * 0.98;
    send();
}
```

两个分支最后都调用 `send()`，改成在 `if-else` 之后调用一次。

- **Extract method**：把一段可以归为一组的代码变成一个 method，用名字说明它的目的。`printOwing()` 里打印 name 和 amount 的两行，提成 `printDetails(double outstanding)`。

怎样发现需要 refactor 的地方？看 **code smell**：一眼就能看出、通常对应更深问题的表面迹象，例如 long method、large class、只有数据没有行为的 data class、一个改动要改很多地方的 shotgun surgery。持续 refactor 是偿还 **technical debt** 的办法：代码质量的欠缺让每次加功能都多花力气，多花的那部分就是利息。但也会 refactor 过头：收益不再抵得上成本时就停。正因为如此，有些 refactoring 是互为反向的，例如 extract method 和 inline method。

> Refactoring 即使由 IDE 自动完成，也可能引入 regression。每一小步之后都要跑 regression test。

### Exception：处理来自用户和环境的意外

程序运行时会遇到一些不寻常、但并非完全意外的情况：连接 timeout、文件损坏读不出来、用户输入了非法的值。发现问题的代码往往不知道该怎么处理，例如读文件的低层 method 不知道该弹窗、重试还是放弃，这要由更高层决定。

Exception 机制解决的就是这个：出错的代码把错误的信息包装成一个 exception object 交给 runtime（throw）；runtime 沿着 call stack，从出错的 method 开始逆着调用顺序往回找，第一个能处理这种类型 exception 的 handler 就 catch 它；找遍整个 call stack 都没有，程序终止。

::fig[cs2103-stack] `main` 调用 `load`，`load` 调用 `readLine`，`readLine` 抛出 exception。runtime 从 `readLine` 往回找：`readLine` 和 `load` 都没有对应的 handler，直到 `main` 的 `catch` 接住。动图逐帧演示这次往回查找。

这带来两个好处：错误信息能沿 call stack 传到懂得处理它的地方；处理特殊情况的代码和做正常工作的代码分开。但 exception 只用于不寻常的情况，正常流程里的分支用普通的 `return`。

### Assertion：抓程序员自己的错

**Assertion** 写下对程序状态的一个假设，让 runtime 去检查：

```java
x = getX();
assert x == 0 : "x should be 0";
```

assertion 失败说明代码有 bug：程序到达了一个“按理不可能”的状态。此时最安全的做法是立刻停下来。两者的分工：

| | exception | assertion |
|---|---|---|
| 说明了什么 | 用户或环境造成的不寻常情况 | 程序员犯了错 |
| 例子 | 用户输入非法、需要的文件不存在 | 一个按设计绝不返回 `null` 的 method 返回了 `null` |
| 应对 | 尽量恢复 | 终止执行 |

Java 默认关闭 assertion，要用 `java -ea`（`-enableassertions`）运行才会检查。这一点很危险：你以为所有 assertion 都通过了，其实它们根本没被检查。测试代码里用 JUnit 的 `assertEquals` 等，它们不会被关闭；产品代码里用 Java 的 `assert`。

:::wrong 写 `assert writeFile() : "File writing is supposed to return true";` 既写了文件又检查了结果，一举两得
Assertion 可以被关闭，而 Java 默认就是关闭的。关闭时整个 `assert` 语句不被执行，`writeFile()` 根本不会被调用，文件没有写，程序在 `-ea` 下工作正常、在默认设置下悄悄地少做了一件事。规则是不让 assertion 做“工作”：先 `boolean ok = writeFile();`，再 `assert ok : ...;`。同类的错误还有拿 assertion 检查用户输入：课本的练习里，计算器对负数开方报 “assertion failure” 而退出，这说明代码有 bug，因为负数输入是用户造成的，应当用 exception 或普通的错误提示处理，程序不应因此终止。
:::

**Logging** 是在运行时有意记录一些信息供日后查看，像飞机的黑匣子：它不防止问题，但出事后能看出发生了什么。Java 的 `java.util.logging` 给每条记录一个 level（`INFO`、`WARNING`……），运行时把 level 设成 `WARNING`，`INFO` 的记录就不会写出，不用改代码就能调整记录的详细程度。

### Defensive programming

**Defensive programmer** 的信条是：如果留了出错的余地，它就一定会出错。所以要主动消除这些余地。

最简单的例子是 defensive copy：`MainApp#getConfig()` 如果直接返回内部的 `config`，调用者改了它就改了 `MainApp` 的状态；返回 `config.copy()`，调用者怎么改都不影响内部。

**强制 compulsory association。** Class diagram 规定每个 `Account` 恰好连着 1 个 `Guarantor`。如果只写一个普通的 field 和 setter，`a.setGuarantor(null)` 就造出一个没有 guarantor 的 account。Defensive 的写法是在 constructor 和 setter 里都检查：

```java
class Account {
    private Guarantor guarantor;

    public Account(Guarantor g) {
        if (g == null) {
            stopSystemWithMessage("multiplicity violated. Null Guarantor");
        }
        guarantor = g;
    }

    public void setGuarantor(Guarantor g) {
        if (g == null) {
            stopSystemWithMessage("multiplicity violated. Null Guarantor");
        }
        guarantor = g;
    }
}
```

如果 association 还是 `{immutable}` 的（一旦建立就不能改），就干脆不提供 `setGuarantor`。

**维护 referential integrity。** 一个 bidirectional association 在代码里是两个 field，各在一端。课本的例子：`Man` 有 `girlfriend`，`Woman` 有 `boyfriend`，各有一个简单的 setter。本该这样用：`james.setGirlfriend(jean); jean.setBoyfriend(james);`。但如果有人写的是 `james.setGirlfriend(jean); jean.setBoyfriend(yong);`，结果是 James 的女朋友是 Jean，Jean 的男朋友却是 Yong，两端的 reference 互相矛盾，这叫 referential integrity 被破坏。

Defensive 的实现让每个 setter 同时负责两端：

```java
public class Woman {
    private Man boyfriend;

    public void setBoyfriend(Man m) {
        if (boyfriend == m) {
            return;
        }
        if (boyfriend != null) {
            boyfriend.breakUp();
        }
        boyfriend = m;
        if (m != null) {
            m.setGirlfriend(this);
        }
    }

    public void breakUp() {
        if (boyfriend == null) {
            return;            // early exit prevents infinite loops
        }
        Man ex = boyfriend;
        boyfriend = null;      // set to null first, also to prevent infinite loops
        ex.breakUp();
    }
}
```

`Man` 对称地写。现在执行 `jean.setBoyfriend(yong)`：Jean 当前的男朋友是 James，不等于 Yong，于是先 `james.breakUp()`，James 把 `girlfriend` 置空，再回调 `jean.breakUp()`，Jean 把 `boyfriend` 置空；然后 Jean 的 `boyfriend` 设为 Yong，并调用 `yong.setGirlfriend(jean)`；Yong 那边的 `setGirlfriend` 发现自己还没有女朋友，设为 Jean，再回调 `jean.setBoyfriend(yong)`，这次 `boyfriend == m`，第一行就返回。最终 James 单身，Jean 和 Yong 互相指向对方。

::fig[cs2103-refint] 同样两行调用，上面是普通 setter：三个 object 之间出现一条指向不一致的链接；下面是 defensive setter：每一步之后两端都保持一致，James 被正确地解除。

两个 early return 和“先置空再回调”缺一不可：没有它们，`setBoyfriend` 和 `setGirlfriend` 会无限地互相调用。

Defensive 要做到什么程度，取决于系统有多关键、代码会不会被作者以外的人使用、语言提供了多少支持、以及这些检查的开销。不必处处 100%。

**Design by contract（DbC）** 在“谁检查 precondition”上和 defensive programming 立场相反：DbC 认为满足 precondition 是调用者的责任，precondition 不满足时 operation 的行为是 unspecified 的；defensive 的做法是 operation 先自己检查 precondition，违反就 throw exception。Eiffel 这样的语言直接支持 DbC；Java 里可以用 assertion 来确认 precondition。

:::from

### 测试能证明什么

测试就是执行一组 **test case**。一个 test case 至少写明给 **software under test（SUT）** 的输入和预期的行为。对每个 test case：喂输入，观察实际输出，和预期比较。两者不一致叫 **failure**，它指向一个可能的 **defect**（bug），说“可能”是因为也可能是 test case 自己写错了。

Software Engineering Body of Knowledge 的定义点出了测试的四个关键词：testing 是 dynamic 的（要执行程序，不是读代码）；只能测 finite 的一组情况；这组情况是从通常无穷的输入中 selected 出来的；需要知道 expected 的行为。由此 Dijkstra 的那句话是必然的：测试能证明 bug 存在，不能证明 bug 不存在。

QA（quality assurance）包括两方面：**validation**，are you building the right system，也就是 requirement 本身对不对；**verification**，are you building the system right，也就是 requirement 有没有被正确实现。测试是最常用的 QA 手段，但不是唯一的：

- **code review**：系统地检查代码，形式有 PR review、pair programming（实时的 review）、formal inspection（作者、主持、记录、审查者各司其职）。它能发现编码规范之类测试发现不了的问题，能检查非代码的 artifact 和还没写完的代码，不需要 driver 和 stub；缺点是人工进行，本身容易出错。
- **static analysis**：不执行代码就分析它，从找出没用到的 variable 到定位潜在 bug；linter 是其中专门让代码更“干净”的一类。需要执行代码的分析叫 dynamic analysis。
- **formal verification**：用数学方法证明程序正确。它能证明没有错误，这是测试做不到的；但它只能证明程序符合 specification，不能证明程序有用，而且需要专门的 notation 和知识，成本高，所以多用于飞行控制这类 safety-critical 软件。

### 越早测越便宜：developer testing

把测试推迟到整个产品完成之后，问题很多：一个 failure 的原因要在几百万行代码里找；如果 bug 来自 requirement 或 design，修它意味着大返工；一个 bug 可能把别的 bug 藏住，修了一个才冒出另一个；bug 太多会拖延交付。所以要早测，而早期的测试往往只能由开发者自己做，叫 **developer testing**。它的好处是开发者清楚内部结构，可以在 method、class 这样的低层测试；风险是开发者可能下意识只测自己知道能工作的情况，对自己的盲点视而不见，甚至从一开始就误解了 SUT 该做什么。

要能反复地测，测试就得自动化。驱动 SUT 做测试的代码叫 **test driver**：

```java
public class PayrollTest {
    public static void main(String[] args) throws Exception {
        Payroll p = new Payroll();
        // test case 1
        p.setEmployees(new String[]{"E001", "E002"});
        if (p.totalSalary() != 6400) {
            throw new Error("case 1 failed ");
        }
        // test case 2
        p.setEmployees(new String[]{"E001"});
        if (p.totalSalary() != 2300) {
            throw new Error("case 2 failed ");
        }
        System.out.println("All tests passed");
    }
}
```

JUnit 把这件事标准化了：每个 test 写成一个 `@Test` method，用 `assertEquals(expected, actual)` 比较，由 JUnit 找到并运行所有 test（第 8 站说的 inversion of control）。CLI 程序还可以半自动地测：把输入写进 `input.txt`，预期输出写进 `expected.txt`，运行 `java AddressBook < input.txt > output.txt`，再用 `diff`（Windows 上是 `FC`）比较 `output.txt` 和 `expected.txt`。这个办法要求输出每次都一样，输出里有时间戳就不行了。

### Unit testing 与 stub

**Unit test** 测一个 unit（method、class）是否正确，而且应当把它和它的 dependency 隔离开：dependency 里的 bug 不应该让这个 unit 的测试失败。

```java
class Logic {
    Storage s;
    Logic(Storage s) { this.s = s; }
    String getName(int index) {
        return "Name: " + s.getName(index);
    }
}
interface Storage {
    String getName(int index);
}
class DatabaseStorage implements Storage {
    public String getName(int index) { return readValueFromDatabase(index); }
    ...
}
```

用 `new Logic(new DatabaseStorage())` 来测 `Logic`，`DatabaseStorage` 有 bug、数据库没连上、数据库里的数据变了，测试都会失败，失败了也不知道是谁的错。这不是纯粹的 unit test。

**Stub** 和被替换的 component 有相同的 interface，但实现简单到几乎不可能有 bug，只对预先定好的输入返回写死的结果：

```java
class StorageStub implements Storage {
    public String getName(int index) {
        if (index == 5) {
            return "Adam";
        } else {
            throw new UnsupportedOperationException();
        }
    }
}

@Test
void getName() {
    Logic logic = new Logic(new StorageStub());
    assertEquals("Name: Adam", logic.getName(5));
}
```

::fig[cs2103-stub] 左边 `Logic` 连着真的 `DatabaseStorage`，测试结果受数据库影响；右边换成 `StorageStub`，测试只取决于 `Logic` 自己。

能把 stub 塞进去，是因为 `Logic` 依赖的是 `Storage` interface，并且由 constructor 从外面接收它。把一个 dependency 从外面换成另一个 object，叫 **dependency injection**，通常靠 polymorphism 实现。另一个例子：`Payroll` 内部 `new` 了一个 `SalaryManager`，但提供了 `setSalaryManager(SalaryManager sm)`；测试时注入一个 `SalaryManagerStub extends SalaryManager`，对 `"E001"` 返回 1000.0、对 `"E002"` 返回 1500.0，于是 `totalSalary()` 对这两个人应当返回 2500.0。如果 `Payroll` 在内部写死 `new SalaryManager()` 而没有任何注入的入口，就没法这样测。

这引出 **testability**：一个 SUT 有多容易测。`getGreeting()` 中午前返回 “Good morning”、之后返回 “Good afternoon”。如果它自己读系统时钟，要测下午的情况就只能下午跑测试，或者去改电脑时间；如果改成 `getGreeting(int hour)`，`getGreeting(9)` 和 `getGreeting(15)` 随时都能测。Coupling 越高，testability 越低，因为要隔离的 dependency 越多。

### 往上一层层测

**Integration testing** 测几个部分合在一起是否正常工作，目标是组件之间的“胶水”里的 bug，这类 bug 通常来自对彼此行为的误解。`Car` 用 `Engine` 和 `Wheel`：如果 `Car` 以为 `Wheel` 能承受 200 mph，而实际只能 150 mph，各自的 unit test 都会通过，只有 integration test 能发现。Integration testing 不是把 unit test 换上真的 dependency 再跑一遍，而是额外加上针对交互的 test case。纯粹的做法分三步：先 unit test `Engine` 和 `Wheel`；再用 stub unit test `Car`；最后把三者放在一起做 integration test。实际中常省掉中间一步，直接把 `Car` 的 unit test 和 integration test 一起在真的 `Engine`、`Wheel` 上做，省掉写 stub 的工夫，代价是 `Car` 从未被单独测过；因为 `Engine` 和 `Wheel` 已经测过，这个风险通常可以接受。

**System testing** 由测试团队（QA team）拿整个系统对照 system specification 测。它也会测超出 specification 的情况，看系统是否 fail gracefully：浏览器规定支持 5000 字符以内的网页，就加载一个更长的网页，预期它停止加载并给出有意义的错误信息，而不是崩溃。System testing 还包括针对 NFR 的测试：performance、load（stress）、security、compatibility、usability、portability。

**Acceptance testing**（user acceptance testing，UAT）向客户保证系统做了它该做的事，通常在 system testing 之后：

| | system testing | acceptance testing |
|---|---|---|
| 对照 | system specification | requirements specification |
| 谁做 | 项目团队的测试人员 | 代表客户的团队（真实用户或代表用户的测试人员） |
| 在哪里 | 开发环境或 test bed | 部署现场或对它的近似模拟 |
| 侧重 | positive 和 negative test case 都有 | 更侧重 positive test case |

通过 system test 不等于通过 acceptance test：系统在 test bed 上能跑，到部署环境可能因为细微差别出问题；系统完全符合 specification，却可能没有解决用户的问题，因为 design 本身有缺陷。前一种是 verification 的漏洞，后一种是 validation 的漏洞。

其他几种按“谁来测”划分：**alpha testing** 由用户在开发团队设定的受控条件下测；**beta testing** 由一部分目标用户在自己的真实环境中测，open beta 则向所有人开放；**dogfooding** 是开发者自己长期真实地使用自己的产品，例如做邮件客户端的公司让员工日常用它收发邮件，前提是有意识地收集使用中的观察。

**Regression** 是修改带来的意外副作用，**regression testing** 是改完之后重测以发现它，通常要把相关部分全部重测一遍，即使它们以前测过。改动越小越频繁、regression test 跑得越勤越有效，所以几乎只能自动化。课本的练习特别提醒：regression testing 不必自动化，只是强烈推荐自动化。

按方式还分两种。**Scripted testing** 先根据预期行为写好一组 test case，再照着执行；**exploratory testing**（也叫 reactive testing、error guessing、attack-based testing、bug hunting）边测边设计，下一个 test case 取决于上一个的结果，在出错多的地方测得更多。前者更系统，时间充足时能发现更多 bug；后者依赖测试者的经验，有经验的人能很快发现一些问题，但关键系统不能只靠它。两者混用最好。

**Test-driven development（TDD）** 先写 test 再写被测代码，小步交替推进：决定要实现的一个行为；写一个测它的 test；运行，看它失败；实现这个行为；运行到通过；refactor；对下一个小行为重复。它不是先把所有 test 都写完。一个明显的好处是代码一定是可测的。JUnit 支持 TDD，但用 JUnit 不等于在做 TDD。

### Coverage：测到了多少代码

写了一组 test，怎样知道哪些代码根本没被执行过？**Test coverage** 衡量测试执行了代码的多大部分，有几种标准：

- **function/method coverage**：执行到的 method 占多少；
- **statement coverage**：执行到的语句占多少；
- **decision/branch coverage**：每个判断点（`if`、循环条件）都分别取过 true 和 false；
- **condition coverage**：一个判断里的每个 boolean 子表达式都分别取过 true 和 false；
- **path coverage**：所有可能的执行路径都走过；
- **entry/exit coverage**：method 的所有调用入口和所有返回出口（`return`、throw exception）都走过。

Path 要借助 **control flow graph（CFG）** 来数。课本的例子（行号按下面的排法）：

```java
int findRate(int input) {          // 1
    if (input == 0) {              // 2
        return 0;                  // 3
    }                              // 4
    int cap = 100 / input;         // 5
    if (cap < 0) {                 // 6
        return -1;                 // 7
    } else {                       // 8
        return cap;                // 9
    }
}
```

::fig[cs2103-cfg] `findRate` 的 control flow graph。动图依次点亮三条路径和触发它们的输入：0、−5、8。

从入口出发，第 2 行分两路：`input == 0` 走第 3 行结束；否则到第 5、6 行，第 6 行又分两路，`cap < 0` 走第 7 行，否则走第 9 行。所以一共 3 条路径：

| 路径 | 触发的输入 | 经过的计算 |
|---|---|---|
| enter → 2 → 3 → exit | 0 | 直接返回 0 |
| enter → 2 → 5 → 6 → 7 → exit | −5 | cap = 100 / (−5) = −20 < 0，返回 −1 |
| enter → 2 → 5 → 6 → 9 → exit | 8 | cap = 100 / 8 = 12（integer division），返回 12 |

100% path coverage 至少要 3 个 test case。这个例子里 statement coverage 和 branch coverage 恰好也都要这 3 个，下面的 wrong 会给出两者不一样的情况。

有循环时 path 会爆炸：

```java
void sayHello(List<String> names) {
    for (String n : names) {
        System.out.println(n);
    }
}
```

`names` 为空是一条路径，一个元素是一条，两个元素又是一条……每种长度一条，100% path coverage 实际上做不到。

Condition coverage 和 branch coverage 也不同。`if (x > 2 && x < 44)` 是一个判断点、两个 condition。Branch coverage 只要整个条件取过 true 和 false：`x = 4`（true）、`x = 100`（false），2 个就够。Condition coverage 要求 `x > 2` 和 `x < 44` 各自取过 true 和 false，需要 3 个：

| x | `x > 2` | `x < 44` | 整体 |
|---|---|---|---|
| 4 | true | true | true |
| 100 | true | false | false |
| 0 | false | 不求值 | false |

为什么必须有 `x = 4` 这一个？Java 的 `&&` 是 short-circuit 的：`x > 2` 为 false 时根本不算 `x < 44`。只用 0 和 100，`x < 44` 只在 `x = 100` 时被求值过一次，取值 false，从没取过 true。

Coverage 由 coverage analysis tool 测量，多数 IDE 自带或有插件；它的用处是指出哪里还没测到，例如 branch coverage 不到 100% 就为漏掉的分支补 test case。

:::wrong Statement coverage 达到 100%，每一行都执行过了，这个 method 就测完了
构造一个例子。规格是：返回数组的平均值，空数组返回 0。

```java
double average(int[] a) {
    int sum = 0;
    if (a.length > 0) {
        for (int x : a) {
            sum += x;
        }
    }
    return (double) sum / a.length;
}
```

只用一个 test case `average(new int[]{2, 4})`：`sum = 0`、`if` 条件为 true、循环把 sum 加到 6、最后 `6.0 / 2 = 3.0`，每一行都执行过，statement coverage 100%，测试通过。但 `if` 从没取过 false。Branch coverage 要求再加一个让它为 false 的输入，只能是空数组：此时 `sum = 0`，跳过循环，返回 `0.0 / 0`，在 Java 里是 `NaN`，不是规格要求的 0。Bug 就在那个“没有语句”的 false 分支上，statement coverage 看不见它。反过来，就算 100% path coverage，也只说明已有的每条路径都走过；程序员漏写的路径（例如根本没有处理空数组的分支）不在任何路径里，coverage 也发现不了。
:::

## [tcd] Test case design：equivalence partitioning、boundary value analysis 与组合输入

:::skip
能为一个多 input 的 method 列出 equivalence partition 和 boundary value，用 at least once 或 all pairs 组合出 test case，再按两条 heuristic 修正，并说出每一步为什么，就算学完了这一页。

### 不能全测，就得会挑

开头第四次失败里，`isValidMonth` 测了 3、6、9，没测 12。`int` 有约 43 亿个值，不可能都测；即使是一个看似简单的操作，例如往一个 collection 里加东西，也可以列出无穷多种情况（空的时候加、有一个时加、有 n 个时加、加一个已存在的、刚启动就加……）。每个 test case 都有成本，有的系统一个 test case 就要几千美元（飞控软件的实地测试）。所以 test case 要设计，目标是同时做到：

- **effective**：找到的 bug 占现有 bug 的比例高。在同一个系统上找到 60 个 defect 的一组 test，比只找到 30 个的 effective。
- **efficient**：每个 test case 找到的 bug 多。20 个 test case 找到 8 个 defect，比 40 个 test case 找到同样 8 个的 efficient。

原则是：每加一个 test case，都应当瞄准一个现有 test case 还没瞄准的可能的错误。

设计 test case 时对 SUT 的内部知道多少，分三种：**black-box**（specification-based）只根据规定的外部行为设计；**white-box**（glass-box）根据实现的代码设计；**gray-box** 利用一些关键的实现信息，例如知道排序对 1000 个以下和以上的 list 用不同算法，就在两边各加 test case。另外，按预期结果分：**positive test case** 预期正常的行为；**negative test case** 预期一个表示异常的行为，例如错误信息。

### Equivalence partitioning

大多数 SUT 并不是把每个输入都区别对待，而是用少数几种方式处理所有输入。`isValidMonth(m)` 规定 `m` 在 1 到 12 之间返回 true。如果 233 出错，234 多半也出错，没必要两个都测。

**Equivalence partition**（EP，也叫 equivalence class）是一组很可能被 SUT 以同样方式处理的输入。把所有输入分成 EP 之后：同一个 EP 里不要测太多（不太可能发现新 bug，提高 efficiency）；每个 EP 都要测到（漏掉一个 EP 就可能漏掉一类 bug，提高 effectiveness）。MIT 6.031 补充了两个要求：这些子集要 disjoint（互不重叠）并且 complete（覆盖所有输入）。

`isValidMonth` 的 EP 可以是 `[MIN_INT .. 0]`（低于有效范围，返回 false）、`[1 .. 12]`（返回 true）、`[13 .. MAX_INT]`（高于有效范围，返回 false）。另一个测试者也可能只分成 `[1 .. 12]` 和“其他所有整数”两个。EP 是一种 heuristic，取决于对 SUT 内部怎样处理输入的推测，不是精确的科学；用 white-box 或 gray-box 的知识能分得更准。

几个规律：

- 一个 EP 里的值不一定相邻。`isPrime(int i)` 的 EP 是“质数”和“非质数”。
- 输入只有少数几个值、而每个值都可能有独特行为时，每个值自成一个 EP。`showStatusMessage(GameStatus s)` 对 enum 的每个值返回不同的消息，每个值都是一个 EP。
- 从 specification 推 EP。`isValidFlag(String s)` 在 `s` 是 `"F"`、`"T"`、`"D"` 之一时返回 true，区分大小写。EP 是：`["F"]`、`["T"]`、`["D"]`、`["f", "t", "d"]`（小写单独一组，正是因为“区分大小写”这句话，最可能写错的就是它们）、其他任意 string、`null`。
- OOP 的 method 要考虑所有可能影响行为的数据参与者：调用它的 target object、parameter、它访问的其他数据（如 global variable，black-box 时可能看不到）。`DataStack#push(Object o)`：栈未满时把 `o` 压栈并返回 true；global flag `FREEZE == true` 时 throw `MutabilityException`；`o` 为 `null` 时 throw `InvalidValueException`。EP 是：`DataStack` object 分 full 和 not full；`o` 分 null 和 not null；`FREEZE` 分 true 和 false。

### Boundary value analysis

**Boundary value analysis（BVA）** 基于一个观察：bug 常出在 EP 的边界处理上。边界值常出现在分支条件里，程序员在那里容易犯 off-by-one 之类的错。

课本的例子：Minesweeper 的 `markCellAt(int x, int y)`，有效的 x 是 `[0 .. W-1]`。设实现里写的是 `if (x > 0 && x <= (W-1))`。取 W = 9，有效范围是 0 到 8，这个条件实际接受的是 1 到 8。用中间值 x = 4 测：条件为 true，正确。用 x = 8 测：`8 > 0` 且 `8 <= 8`，true，正确。用 x = 0 测：`0 > 0` 为 false，有效的输入被拒绝，bug 出现。只有边界值 0 能发现它。

::fig[cs2103-ep] `isValidMonth` 的三个 EP 画在数轴上，圆点是建议的 test value，实心的是 boundary value。动图里一个“写错”的实现 `m >= 1 && m < 12` 让 12 落到了错误的一边：中间的值都测不出来，只有 boundary value 12 能抓到它。

BVA 建议优先测 boundary value，同时也测非边界值：每个 EP 至少取一个非边界值，条件允许时在边界内外各取一个。课本给的几组：

| EP | 可选的 test value（加粗的是 boundary） |
|---|---|
| `[1 .. 12]` | 0、**1**、2、11、**12**、13 |
| `[MIN_INT .. 0]` | **MIN_INT**、MIN_INT+1、−1、**0**、1 |
| 任意非 null 的 string（关心长度时） | **空 string**、**最大长度的 string** |
| 质数；`["F"]`；`["A", "D", "X"]` | 没有特定的边界 |
| 固定大小的非空 stack | 没有元素、**一个元素**、两个元素、**没有空位**、只剩一个空位 |

类型本身的极值也是边界。MIT 6.031 的例子：`Math.abs(Integer.MIN_VALUE)` 返回的仍是 `Integer.MIN_VALUE` 这个负数，因为它的相反数超出了 `int` 的范围。只测 17 和 −3 发现不了这件事，所以 MIT 把 `abs` 的 test suite 定为 0、`MIN_VALUE`、`MAX_VALUE`、17、−3。

:::wrong BVA 的意思是只测恰好在边界上的值
课本的判断题正是这一句，答案是 false。BVA 说的是边界上和边界附近的值更容易出 bug，所以优先测它们；它并不让你放弃非边界的值。上面 `[1 .. 12]` 的推荐值里有 2 和 11，它们紧挨着边界但不在边界上；而且每个 EP 至少要有一个非边界值，用来确认 SUT 对这一整类输入的“一般”处理是对的。只测 1 和 12，如果实现恰好对 1 和 12 写了特殊处理而一般情况写错了，就测不出来。
:::

### 多个输入怎样组合

SUT 有多个输入时，先为每个输入各自选好值，再决定怎样组合。课本的 `calculateGrade(participation, projectGrade, isAbsent, examScore)`：

| 输入 | 有效值 | 无效值 |
|---|---|---|
| participation | 0、1、19、20 | 21、22 |
| projectGrade | A、B、C、D、F | |
| isAbsent | true、false | |
| examScore | 0、1、69、70 | 71、72 |

全部组合是 $6\times5\times2\times6=360$ 个，effective 但不 efficient。几种组合策略，用一个更小的例子 `foo(char p1, int p2, boolean p3)` 对比，p1 取 a、b、c，p2 取 1、2、3，p3 取 T、F：

- **all combinations**：每种组合一个，$3\times3\times2=18$ 个。
- **at least once**：每个值至少出现一次，个数等于取值最多的那个输入的取值数，这里是 3 个：(a, 1, T)、(b, 2, F)、(c, 3, 任意)。
- **all pairs**：任意两个输入之间的所有值对都出现过。依据是 bug 很少由两个以上的因素相互作用引起。p1 和 p2 之间有 $3\times3=9$ 对，p1 和 p3 之间 $3\times2=6$ 对，p2 和 p3 之间 6 对，共 21 对要覆盖。p1、p2 那 9 对每对至少占一个 test case，所以至少 9 个；课本给出了恰好 9 个的解：

| | p1 | p2 | p3 |
|---|---|---|---|
| 1 | a | 1 | T |
| 2 | a | 2 | T |
| 3 | a | 3 | F |
| 4 | b | 1 | F |
| 5 | b | 2 | T |
| 6 | b | 3 | F |
| 7 | c | 1 | T |
| 8 | c | 2 | F |
| 9 | c | 3 | T |

::fig[cs2103-pairs] 把这 9 个 test case 填进三张值对表：p1 × p2 的 9 格、p1 × p3 的 6 格、p2 × p3 的 6 格，每一格都至少被一个 test case 覆盖。格子里的数字是覆盖它的 test case 编号。

逐张核对：p1 × p2 的 9 格各被一个 test case 覆盖（1 到 9 恰好一一对应）。p1 × p3：a 配 T 的是 1、2，a 配 F 的是 3；b 配 F 的是 4、6，b 配 T 的是 5；c 配 T 的是 7、9，c 配 F 的是 8。p2 × p3：1 配 T 的是 1、7，1 配 F 的是 4；2 配 T 的是 2、5，2 配 F 的是 8；3 配 F 的是 3、6，3 配 T 的是 9。21 对全部覆盖，9 个 test case，是 all combinations 的一半。

- **random**：先用某种策略生成，太多时随机取一个子集。

MIT 6.031 用 `BigInteger.multiply(a, b)` 说明同样的取舍：a 和 b 各分 6 类值，Cartesian product 是 $6\times6=36$ 个 test case；如果只要求 a 的 6 类和 b 的 6 类各自被覆盖，一个 test case 同时覆盖 a 的一类和 b 的一类，6 个就够。代价是可能漏掉 a 和 b 相互作用才出现的 bug，所以他们另加一个关于“两者符号组合”的 partition 专门覆盖它。

### 两条 heuristic

**Heuristic 1：每个有效的输入值至少出现在一个 positive test case 里。** 课本的 `printLabel(String fruitName, int unitPrice)`：Apple 打圆形标签，Banana 打椭圆形，Cherry 打方形，Dog 不是水果；单价 1 和 20 有效，0 和 −1 无效。用 at least once 得到

| case | fruitName | unitPrice | 预期 |
|---|---|---|---|
| 1 | Apple | 1 | round label |
| 2 | Banana | 20 | oval label |
| 3 | Cherry | 0 | “invalid price” |
| 4 | Dog | −1 | “invalid fruit” |

跑完之后能确认方形标签打得对吗？不能。能产生方形标签的只有 Cherry，而它出现的唯一一个 test case 带着无效的单价，输出是错误信息，打印方形标签的代码根本没被执行。修正：加一个 case 2.1，Cherry 配任意有效的单价，预期 square label。

**Heuristic 2：无效的输入先单独测，再组合。** 看上表的 case 4：输出 “invalid fruit”，能确认是 Dog 触发的吗？不能。也可能是 −1 因为某个 bug 错误地触发了这条信息。一个 test case 里有两个无效输入时，它通过了也不能证明 SUT 对每一个都处理对了；何况大多数 SUT 遇到第一个无效输入就报错返回，后面那个根本没被检查。修正：case 4 改成任意有效的水果配 −1，再加 case 4.1 Dog 配任意有效的单价。这不是说永远不能有两个无效输入同时出现：单个都确认过之后，有余力可以再测组合，因为 SUT 也可能单个都对、组合起来出错。

把所有步骤用在 `calculateGrade` 上。先用 at least once 得到 V1（VV/IV 表示任意有效或无效的值）：

| case | participation | projectGrade | isAbsent | examScore |
|---|---|---|---|---|
| 1 | 0 | A | true | 0 |
| 2 | 1 | B | false | 1 |
| 3 | 19 | C | VV/IV | 69 |
| 4 | 20 | D | VV/IV | 70 |
| 5 | 21 | F | VV/IV | 71 |
| 6 | 22 | VV/IV | VV/IV | 72 |

应用 heuristic 1：有效值 F 只出现在 case 5，而 case 5 有无效输入（21、71），所以加一个 5.1：F 配上其他全部有效的值。应用 heuristic 2：case 5 有两个无效值 21 和 71，case 6 有 22 和 72，各拆开，每个 test case 只留一个无效值，其余都取有效值。最后考虑输入之间隐藏的依赖：缺考的学生只能是 examScore = 0。于是 isAbsent = true 配 examScore ≠ 0 本身就是一个无效的组合，需要一个专门的 test case；而 case 3 及之后的 isAbsent 都要设成 false，否则它们配上非 0 的 examScore 会意外地变成无效输入。得到 V4：

| case | participation | projectGrade | isAbsent | examScore | 预期 |
|---|---|---|---|---|---|
| 1 | 0 | A | true | 0 | 正常结果 |
| 2 | 1 | B | false | 1 | 正常结果 |
| 3 | 19 | C | false | 69 | 正常结果 |
| 4 | 20 | D | false | 70 | 正常结果 |
| 5.1 | VV | F | false | VV | 正常结果 |
| 5.2 | 21 | VV | false | VV | 错误信息 |
| 5.3 | 22 | VV | false | VV | 错误信息 |
| 6.1 | VV | VV | false | 71 | 错误信息 |
| 6.2 | VV | VV | false | 72 | 错误信息 |
| 7 | VV | VV | true | ≠ 0 | 错误信息 |

10 个 test case，对比全部组合的 360 个。每一行都能说出它针对的是哪一种可能的错误，这就是开头说的“每加一个 test case，都瞄准一个还没被瞄准的错误”。

:::edge Use case 也能变成 test case
Use case 可以用于 system testing 和 acceptance testing：MSS 是一个 test case，每个 extension 引出的变体是另一个。但 use case 不写具体数据（“user enters his personal data”），测试者还要用 EP 和 BVA 选数据，一个 use case 因此会变成很多 test case。高优先级的 use case 可以用 scripted 的方式测，其他地方用 exploratory 的方式。
:::

:::back
Partition 的依据是 SUT 的 specification，例如[第 3 站](#req)的 requirement 和[第 8 站](#arch)的 operation precondition；一个 test case 测 positive 还是 negative，取决于输入有没有违反它们。
:::
