一个 token 只有固定的计算量

先看 model 写下一个 token 时做了什么。NNN 个 parameter 的 Transformer，每个 token 的 forward 大约是 2N2N2N 次 floating-point operation（推导在 CS336 第 3 站）。A3 用的 Qwen2.5-Math-1.5B 每个 token 约 2×1.5×109=3×1092\times1.5\times10^9=3\times10^92×1.5×109=3×109 次。这个数和题目难不难无关：回答“1+1”和回答 Countdown，写第一个 token 花的计算一样多。

更要紧的是串行的步数。一个 token 的计算从 embedding 出发，依次经过 LLL 个 layer；每个 layer 可以读前面所有位置在下一层的结果，但在一次 forward 里信息只能往上走 LLL 层。一个计算如果必须先得到 uuu 才能算 vvv、得到 vvv 才能算 www，链条长过 LLL，一次 forward 就装不下。

Countdown 直接写答案时，第一个答案 token 就得“知道”是 96+97−68。要知道它，model 得在内部把候选 expression 过一遍，或者凭某种捷径猜中。候选的数目随数字个数增长得很快。只用 +++、−-−、×\times×（减法大数在前），每一步从剩下的数里挑两个、选一个 operation、换成结果，所以

写出中间步骤以后情况就变了。Model 写下“96+97=193”，这几个 token 进了 context；下一步它面对的是一个小得多的问题：用 193 和 68 凑 125，三选一。每一行只需要一次小的计算，下一行可以直接读上一行写下的结果。

这个直觉有一个 theory 的版本：Li、Liu、Zhou、Ma（ICLR 2024）证明，constant depth、constant precision 的 Transformer 不写中间 token 时只能解 AC0\mathsf{AC}^0AC0 这一类很浅的 circuit 能算的问题；写 TTT 步 chain-of-thought 以后，能解任何大小为 TTT 的 boolean circuit 能算的问题（这个结论是凭记忆写的，没有读原文核对）。

写出来的中间 token 给了 model 额外的串行计算：每写一个 token，就多一次能读到上一步结果的完整 forward pass。

两种花 test-time compute 的方式

可以跳过吗

快速路线可以先跳。跳过会少掉 test-time compute 的成本账，第 4 站末尾和第 6 站的 budget forcing 会用到。

CMU 11-711 的那一讲把多花 test-time compute 的办法分成两类：

  • Parallel：独立地采 NNN 条 (z,a)(z,a)(z,a)，再用一个 aggregation 合成一个答案。取出现最多的答案是 majority vote（第 2 站），用 verifier 打分挑最高的是 best-of-NNN（第 3 站）。
  • Sequential：让一条 zzz 变长，在里面检查、回头、换一种做法。o1、R1 这一类 reasoning model 走的是这条路；长度可以靠 RL 训练出来（第 5 站），也可以在 decoding 时强行控制（第 6 站的 budget forcing）。

两者都按生成的 token 付钱。按每 token 2N2N2N FLOPs：1.5B 的 model 写 10,000 个 token 是 2×1.5×109×104=3×10132\times1.5\times10^9\times10^4=3\times10^{13}2×1.5×109×104=3×1013；32B 的 model 写 1,000 个 token 是 2×3.2×1010×103=6.4×10132\times3.2\times10^{10}\times10^3=6.4\times10^{13}2×3.2×1010×103=6.4×1013。小 model 多想 10 倍，花的 compute 还不到大 model 想一遍的一半。CMU 讲义转述的 Wu 等人的 inference scaling law 正是把 compute 写成“model 大小乘以生成的 token 数”，再问固定 compute 下怎样分配；讲义的结论是，小 model 多生成可能比大 model 少生成更划算。

FLOPs 只是下界。Decode 是 memory-bound 的，每生成一个 token 要把 parameter 和整个 KV cache 读一遍（CS336 第 8 站），一条 10,000 token 的 trace 越往后越慢；而且 sequential 的 token 只能一个接一个地生成，latency 随长度线性增长，JHU 的 slides 专门列出了这项代价。Parallel 的 NNN 条可以放进同一个 batch 一起生成，latency 几乎不随 NNN 增长。

看起来对，其实不对一次 forward 做不到的事，换一个更大的 model 就能一步做到

更大的 model 主要是更宽、层数多一些，串行的层数仍是一个固定的 LLL。Countdown 的候选从 3 个数的 27 个涨到 6 个数的 656,100 个，是 exponential 的增长；要在固定的 LLL 层里把它们并行地过一遍，宽度也得跟着 exponential 地涨。写中间步骤的做法每一步只面对一个小问题（6 个数时第一步最多 (62)⋅3=45\binom62\cdot3=45(26​)⋅3=45 个选择），配上第 4 站的 search，总代价随步数增长。Snell 在他的 guest lecture 里举的正是这个例子：Countdown 这样简单的题也可能需要 search，不是什么都能一次答出来。

pass@k：至少一次做对

对一道题，model 每次 sample 做对的 probability 记作 ppp（由 model、prompt 和 temperature 决定）。独立采 kkk 次，全错的 probability 是 (1−p)k(1-p)^k(1−p)k，所以至少一次对的 probability 是

pass@k=1−(1−p)k\text{pass@}k=1-(1-p)^kpass@k=1−(1−p)k

开头那个随机 policy 在 Countdown 题上 p=1/9p=1/9p=1/9：pass@1 =0.111=0.111=0.111，pass@8 =1−(8/9)8=0.610=1-(8/9)^8=0.610=1−(8/9)8=0.610，pass@64 =1−(8/9)64=0.9995=1-(8/9)^{64}=0.9995=1−(8/9)64=0.9995。

pass@k 回答的问题是：如果有一个完美的 verifier 能从 kkk 个答案里认出对的那个，能做对多少。代码有 unit test，Countdown 可以把 expression 直接算一遍，这时 pass@k 就是真的拿得到的 accuracy。数学题在 test time 没有标准答案，pass@k 只是一个上限。

一个 benchmark 的 pass@k 是各题 pass@k 的平均。各题的 ppp 差别很大，平均值随 kkk 怎样变，主要由难题决定。

这 10 道题平均的 pass@1 是 0.319，pass@8 是 0.602，pass@256 是 0.872。从 pass@1 到 pass@8 涨了 0.28，从 pass@8 到 pass@256 只涨了 0.27，后面这一段 kkk 翻了五倍。

def pass_at_k(n, c, k):
    """n 个 sample 里 c 个对，返回 pass@k 的 unbiased estimate。"""
    if n - c < k:            # 任取 k 个必然含对的

    return 1.0 - np.prod(1.0 - k / np.arange(n - c + 1, n + 1))

ORM 和 PRM：在哪一步打分

上面的 vvv 只看完整的解，叫 outcome reward model（ORM）。它的 label 便宜（最终答案对不对），但信号粗：一个 10 步的解在第 2 步就错了，ORM 也要等看完才给一个分，而且不说错在哪。Process reward model（PRM）给每一步打分。Lightman 等人（2023，OpenAI）请人逐步标注 MATH 的解，数据集 PRM800K 有约 80 万个 step label（规模凭记忆）。JHU 的 slides 指出人工标注的问题：step 的空间太大，标不过来。

Math-Shepherd（Wang 等人，2024）把 label 换成可以自动算的东西：从第 ttt 步的 prefix 出发，用 model 往下采 KKK 个 completion，看最终答案对了几个。对的比例叫 soft label，“至少一个对”记 1 叫 hard label（这两个名字凭记忆）。Snell 的 PRM 用的是 soft label。

这个 label 到底是什么，用 Countdown 算一遍就清楚了。Completion policy 取开头那个随机 policy：在剩下两个数的 3 种合并里均匀地选。

  • Prefix “97+96=193”：剩下 193 和 68，三个 completion 是 261、125、13124，一个对。Soft label 是 1/31/31/3，hard label 是 1。
  • Prefix “96−68=28”：剩下 97 和 28，completion 是 125、69、2716，同样是 1/31/31/3 和 1。
  • Prefix “97−96=1”：剩下 68 和 1，completion 是 69、67、68，都不对。Soft 和 hard 都是 0。

这里 completion 恰好能穷举，soft label 是精确值。一般只能采 KKK 个，soft label 是一个 binomial 比例的估计：真值为 1/31/31/3、K=8K=8K=8 时，它的 standard error 是 (1/3)(2/3)/8=0.167\sqrt{(1/3)(2/3)/8}=0.167(1/3)(2/3)/8​=0.167。Hard label 在 K=8K=8K=8 时有 1−(2/3)8=96%1-(2/3)^8=96\%1−(2/3)8=96% 的 probability 是 1，几乎分不出 1/31/31/3 和 1 的 prefix。

Soft label 估计的量有一个名字。Reward 只在结尾给、对为 1 错为 0 时，“从这个 prefix 出发、按这个 policy 走下去最终成功的 probability”就是 RL 里的 value function Vπ(s)V^\pi(s)Vπ(s)（定义见 CS4246 第 1 站）。Snell 的 slides 也是这样说的：Math-Shepherd 式的 PRM 学的是一个 value function。

看起来对，其实不对PRM 的分数就是在判断这一步算得对不对

“97−96=1”这一步的 arithmetic 完全正确，Monte Carlo label 却是 0，因为它把问题带进了一个凑不出 125 的 state。反过来，这个 label 也依赖 completion policy：换一个更会做题的 policy，同一个 prefix 的 label 会变高。所以 rollout 训出来的 PRM 量的是“从这里走下去还有多大希望”；PRM800K 那样请人判断每一步的 label，量的才更接近“这一步本身有没有错”。两种 PRM 拿去做 search，偏好的东西不一样。

为什么要在步骤上 search

Best-of-NNN 每一条都走到底才打分。长的解大多在前几步就走错了，后面的 token 白写了。有了 PRM，可以每走一步就评估一次，把没希望的 prefix 砍掉，把 compute 留给有希望的。

Step-level beam search（JHU、CMU 的讲义）：保留 BBB 个 prefix（beam）；每一步把每个 prefix 扩展出 MMM 个下一步，用 PRM 给这 B⋅MB\cdot MB⋅M 个候选打分，留下最高的 BBB 个；如此往下，直到写出答案。

Snell 等人：哪种 search 在什么时候好

Snell 等人（2024）在 MATH 上比较了这些方法（base model 是 PaLM 2-S*，凭记忆）。他们先给题目分难度：每题采 2048 个 sample，按做对的比例把题目分成 5 个 quantile（oracle difficulty）；部署时没有标准答案，就改用 verifier 的预测分数来分（predicted difficulty）。Guest lecture 的结论：

  • 所有用 verifier 的 search 都胜过 majority vote。
  • 简单的题、大的 budget：best-of-NNN 更好，beam search 出现 over-optimization 的迹象。
  • 中等和较难的题、小的 budget：beam search 更好。
  • 最难的那一档：所有方法都做不动。
  • 每个难度选最好的方法（compute-optimal），最多能少用 4 倍的 test-time compute 达到 best-of-NNN 的效果。

第 3 站的 toy model 说明了简单题上 beam search 为什么会 over-optimize。Beam search 每一步都对 PRM 做一次 argmax，相当于把 best-of-NNN 的选择压力加到每一步上。题目简单时对的路本来就多，多挑几次主要的效果是挑中 PRM 的错（toy model 里 NNN 从 12 涨到 1024，accuracy 从 0.733 掉到 0.358）；题目难时不挑就几乎找不到对的路，选择压力利大于弊。

Sequential 的版本是 revision：fine-tune 一个 model，让它看着前面几次错的尝试再写一次（训练数据是把同一题的几个错解接成一串，最后接上一个对的）。Snell 发现 revision 有时会把对的改错，所以要用 verifier 在整串 revision 里挑。Sequential 和 parallel 之间存在最佳的比例：简单题偏向多做 revision，难题要两者混合；按难度选比例，同样最多省 4 倍 compute。

他们还和 pretraining 比了一次：FLOPs 相等时，小 model 加 test-time compute 能胜过一个大 14 倍的 model，但只在小 model 本来就有一定成功率的题上（14 倍这个数凭记忆，slides 上没有）。划不划算还取决于 inference 的量：用户多时，每次多花的 test-time compute 要乘上调用的次数，slides 的结论是 test-time compute 适合简单到中等的题和 inference 量不大的场景。

看起来对，其实不对o1、R1 这类 reasoning model 在回答时内部跑着 tree search

每个 token 分多少：masked_mean 与 masked_normalize

A3 的 grpo_microbatch_train_step 要把 per-token 的 loss 聚合成一个数。Handout 有一道不做实验、只做分析的题（think about length normalization），比较两种做法，例子是一个 batch 里两个回复，分别长 4 和 7 个 token，常数取 7：

  • masked_mean：每个回复在自己的 token 上平均。
  • masked_normalize：每个回复在自己的 token 上求和，再除以同一个常数。

Handout 打印出的结果是 masked_mean 给 [2, 2][2,\,2][2,2]，masked_normalize 给 [1.1429, 2.0000][1.1429,\,2.0000][1.1429,2.0000]。这和每个 token 的值都是 2 的情形对得上：前者是 8/4=28/4=28/4=2 和 14/7=214/7=214/7=2，后者是 8/7=1.14298/7=1.14298/7=1.1429 和 14/7=214/7=214/7=2。

对 gradient 来说，要看的是每个 token 的 weight。

masked_mean 下每个回复的 weight 总和都是 1，与长度无关，代价是长回复的每个 token 被稀释。乘上 advantage 看：错的回复 advantage 是负的，写得越长，每个 token 受的惩罚越轻，model 被推向把错的回答写长；对的回复反过来偏向短。这是 Dr. GRPO 去掉 length normalization 的理由（Lecture 7 的 DrGRPO 一页；数值例子在 CS336 第 10 站）。masked_normalize 下每个 token 的 weight 一样，长回复整体的 weight 更大，没有这个偏向；代价是 gradient 的大小随回复长度变化，长回复多的 batch gradient norm 更大。Handout 让你在 grpo_length_normalization 里看 gradient norm 这类稳定性指标，原因在此。

DAPO 的 token-level loss（凭记忆）是把整个 batch 所有 token 的 loss 加起来，除以 batch 里的 token 总数。它和 masked_normalize 一样让 batch 里每个 token 的 weight 相同，区别只在除数随 batch 变。

Long CoT 的长度：budget forcing

s1（Muennighoff 等人，2025）把这一站的两件事放在了一起。数据只有 1,000 道题（s1K，按难度、多样性、质量三条标准挑选，三条都做了 ablation），每道带一条 reasoning trace，在 Qwen2.5-32B-Instruct 上 SFT。然后在 decoding 时控制 reasoning 的长度，叫 budget forcing：model 想结束 reasoning 时，不让它结束，在后面接上“Wait”，它常常会回头检查、改掉错误；要压短时，在预算用完的地方强行结束 reasoning，让它直接给答案。摘要报告，用 budget forcing 把 AIME24 从 50% 推到了 57%。

这就是第 1 站 sequential 的那条路，而且是一个可以连续调节的旋钮。它的局限在于只是从外面打断或延长，model 自己不知道预算。L1（Aggarwal 与 Welleck，2025）把预算写进 prompt（例如“最多用 2000 个 token”），用 RL 训练，reward 是答案的正确性减去违反长度约束的 penalty（CMU 讲义）。

两个系统比较要 paired

看起来对，其实不对两个系统的 95% 区间重叠，说明差别不显著

Lecture 11 的例子：系统 1 是 60%，区间 (50%, 70%)；系统 2 是 65%，区间 (55%, 75%)。区间重叠，但不能就此下结论，因为两个系统做的是同一组题，对错高度相关。构造一个具体的情形：100 道题，系统 2 在系统 1 做对的 60 道上全对，另外多做对 5 道，没有一道是反过来的。分别 bootstrap，区间是 (0.50, 0.70) 和 (0.56, 0.74)，重叠。Paired bootstrap 每次对同一组重抽的题比较两个系统：只有 100 次抽取一次都没抽中那 5 道题时，系统 2 才不比系统 1 好，probability 是 (95/100)100=0.0059(95/100)^{100}=0.0059(95/100)100=0.0059。p 值是 0.006，差别是可信的。反过来，Lecture 11 的 10 道题的例子里系统 2 在多数重抽中都赢，p 值却是 0.21，题太少。

import numpy as np

def paired_bootstrap(a, b, B=10_000, seed=0):
    """a、b：两个系统在同一组题上的对错（1/0），顺序一致。
    返回 p 值：重抽后 b 不比 a 好的比例。"""
    rng = np.random.default_rng(seed)
    a, b = np.asarray(a), np.asarray(b)
    idx = rng.integers(0, len(a), size=(B, len(a)))   # 每行是一次重抽
    delta = b[idx].mean(axis=1) - a[idx].mean(axis=1)
    return (delta <= 0).mean()

Lecture 11 还提醒了 multiple testing：试 20 组 hyperparameter，即使没有一组真的更好，每组都用 0.05 的标准，至少一组“显著”的 probability 是 1−0.9520=0.641-0.95^{20}=0.641−0.9520=0.64。Bonferroni correction 把标准除以检验的次数，20 次就是 0.05/20=0.00250.05/20=0.00250.05/20=0.0025。Lecture 11 用 jelly bean 的例子讲 file drawer effect：20 个研究里 19 个没结果、没发表，发表出来的那一个就是 false positive。RL 的实验 variance 大，A3 的 learning rate sweep、各种 ablation 都在做多次比较，同一个结论最好在不同 seed 上重复。

Contamination

Lecture 11 把 contamination 分成三种：benchmark 的题出现在 pretraining 数据里；连同答案出现在 post-training 数据里；出现在 RL 的题库里。分数本身看不出虚高了多少。

GSM1k（Zhang 等人，2024）的做法是重新出题：照 GSM8K 的风格和难度出约 1,000 道新题，人的解题率、解题步数、答案大小等指标都与 GSM8K 对齐，再比较 model 在两套题上的分数。摘要报告：有的 model 在 GSM1k 上低了多达 8 个点；一个 model 生成 GSM8K 原题的 probability 越高，它在两套题上的分差越大（Spearman r2=0.36r^2=0.36r2=0.36）；多数 frontier model 没有明显的 overfitting 迹象（只读了摘要）。

Oren 等人（2024）在只能拿到 model log-likelihood 的条件下检测（Lecture 11）。如果一个 benchmark 被原样放进过训练数据，model 会记住题目的排列顺序。题目本来是 exchangeable 的，任何顺序的 likelihood 应该差不多；按原始顺序排的 likelihood 显著高于打乱后的顺序，就说明见过。按这个原理写成 permutation test（具体做法是我按原理写的，原文没有读）：算原始顺序下整个数据集的 log-likelihood，再算很多个随机 permutation 下的，原始顺序排进最高的那一小撮就有证据。Lecture 11 留了一个问题：它测不到什么？按原理推（这是我的推断）：题目被打乱顺序后才进入训练数据、被改写过、或零散地混在别的文本里，顺序的信号就没有了；所以它能给出“见过”的证据，不能给出“没见过”的证据。

答案解析：model 错还是 parser 错

A3 的第一题（math_baseline）就是这件事。Grader question_only_reward_fn 只认回复里的最后一个 \boxed{...}：找不到 \boxed，format reward 和 answer reward 都是 0；找到了，再用 mathd 的 normalization 和 sympy 判断它与标准答案是否相等（1/21/21/2 和 0.50.50.5 算相等），不相等就是 format 1、answer 0。Handout 要你把 500 道 MATH test 题的结果分成三类（format 1 且 answer 1，format 1 且 answer 0，format 0），后两类各至少看 10 个，判断是 model 的问题还是 parser 的问题。

从 grader 的代码可以读出几种会误判的情形：

  • 答案写在 \boxed 外面（“the answer is 5”），format 是 0，但 model 其实做对了。这是 parser 的错，换 prompt 或换 grader，分数都会变。
  • 回复里有不止一个 \boxed{}（先给一个、后来又改），grader 只取最后一个。
  • 同一个文件里的 r1_zero_reward_fn 是给 R1 格式用的，它要求回复里恰好出现 </think> <answer>（中间一个空格），格式稍有不同，整条回复的 format 就是 0。

Lecture 7 的最后一节讲的也是这件事：prompt 的格式是 reasoning model 的关键组成，答案的格式各家不同（OpenThoughts 在“Final Answer”一行里用 \boxed{}，R1 用 <answer> tag），A3 会让你看到 parsing error 怎样造成看起来的失败。

边界情况Format 也是 reward

RL 拿同一个 grader 当 reward 时，parser 的偏好会被训练进 model。question_only_reward_fn 对“格式对、答案错”给 format 1、reward 0，代码注释写明这样做是为了防止 hacking：如果格式对就给一部分 reward，model 会先学会只写格式。所以 A3 要求分别 log format reward 和 answer reward：训练前期 total reward 在涨，先要确认涨的是哪一个。
