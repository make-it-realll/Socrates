一个 token 只有固定的计算量

先看 model 写下一个 token 时做了什么。NNN 个 parameter 的 Transformer，每个 token 的 forward 大约是 2N2N2N 次 floating-point operation（推导在 CS336 第 3 站）。A3 用的 Qwen2.5-Math-1.5B 每个 token 约 2×1.5×109=3×1092\times1.5\times10^9=3\times10^92×1.5×109=3×109 次。这个数和题目难不难无关：回答“1+1”和回答 Countdown，写第一个 token 花的计算一样多。

更要紧的是串行的步数。一个 token 的计算从 embedding 出发，依次经过 LLL 个 layer；每个 layer 可以读前面所有位置在下一层的结果，但在一次 forward 里信息只能往上走 LLL 层。一个计算如果必须先得到 uuu 才能算 vvv、得到 vvv 才能算 www，链条长过 LLL，一次 forward 就装不下。

Countdown 直接写答案时，第一个答案 token 就得“知道”是 96+97−68。要知道它，model 得在内部把候选 expression 过一遍，或者凭某种捷径猜中。候选的数目随数字个数增长得很快。只用 +++、−-−、×\times×（减法大数在前），每一步从剩下的数里挑两个、选一个 operation、换成结果，所以

C(n)=(n2)⋅3⋅C(n−1),C(1)=1C(n)=\binom n2\cdot3\cdot C(n-1),\qquad C(1)=1C(n)=(2n​)⋅3⋅C(n−1),C(1)=1

写出中间步骤以后情况就变了。Model 写下“96+97=193”，这几个 token 进了 context；下一步它面对的是一个小得多的问题：用 193 和 68 凑 125，三选一。每一行只需要一次小的计算，下一行可以直接读上一行写下的结果。

Denny Zhou 在 Berkeley 那一讲里给了这个直觉的 theory 版本（Li、Liu、Zhou、Ma，ICLR 2024）。论文摘要的说法更精确：constant depth、constant-bit precision 的 Transformer 不写中间 token 时，只能解 AC0\mathsf{AC}^0AC0（TC0\mathsf{TC}^0TC0 的一个真子集）里的问题；同样 constant depth、constant-bit precision、embedding 维度只有 O(log⁡n)O(\log n)O(logn) 的 Transformer，写 TTT 步 chain-of-thought，就能解任何大小为 TTT 的 boolean circuit 能解的问题。直接生成最终答案，要么需要极大的 depth，要么根本解不了。他从中得出的实际含义是：生成更多中间 token 是一个可以 scale 的方向。

写出来的中间 token 给了 model 额外的串行计算：每写一个 token，就多一次能读到上一步结果的完整 forward pass。

A3 的 Countdown prompt 让 model 先一步步解释 reasoning，最后在 <answer> 和 </answer> 之间给答案（答案可以是几行“Step X:”，也可以是一个等式）。把 reasoning 的部分记作 zzz、答案记作 aaa，model 给出的是 joint distribution p(z,a∣x)=p(z∣x) p(a∣x,z)p(z,a\mid x)=p(z\mid x)\,p(a\mid x,z)p(z,a∣x)=p(z∣x)p(a∣x,z)。Berkeley 那一讲把问题摆得很直白：decoding 时 model 在做的是

写出来的步骤也会算错

可以跳过吗

快速路线可以先跳。跳过会少掉“CoT 的哪一步交给工具”的判断，第 3 站讲 verifier 时会再用到。

中间 token 给了串行计算，但每一步仍然是 model 采样出来的，照样会错。Lecture 9 用一道题把 CoT 拆成三件事：理解题意（interpret）、列出计划（plan）、执行计算（execute）。题目是：9 升浓度 50% 的酸液，加多少水能稀释到 30%。

正确的做法：酸有 9×0.5=4.59\times0.5=4.59×0.5=4.5 升，加水 xxx 升后浓度是 4.59+x=0.3\dfrac{4.5}{9+x}=0.39+x4.5​=0.3，所以 9+x=159+x=159+x=15，x=6x=6x=6。

Slides 上 GPT 的 CoT 写出了 0.3(9+x)=0.5×90.3(9+x)=0.5\times90.3(9+x)=0.5×9，这一步是对的：理解了水的浓度是 0，计划也对。接下来要算 0.3x=0.5×9−0.3×9=4.5−2.7=1.80.3x=0.5\times9-0.3\times9=4.5-2.7=1.80.3x=0.5×9−0.3×9=4.5−2.7=1.8，它却写成 0.150.150.15，得出 x=0.5x=0.5x=0.5。Lecture 9 的评语是：这是让 LLM 去做它不擅长的事。

两种把执行交出去的办法：

  • PAL（program-aided）让 model 写一段 Python，由 interpreter 执行。Slides 上那段程序是 water_added = 9 * (50 - 30) / 50，结果 3.6，错在计划：它把理解题意和列计划混在一段命令式代码里。
  • SatLM（Ye、Chen、Dillig、Durrett，NeurIPS 2023）只让 model 把题目翻译成形式化的 constraint（liters_after = liters_initial + water_added、percent_after = percent_initial * liters_initial / liters_after、percent_after = percent_desired），由 SMT solver Z3 去解，得到 6。Z3 还能报告 constraint 有错、无解或有歧义；slides 说 SatLM 给出答案时的 accuracy 比 program-aided 高得多。

这件事和第 3 站是同一个思路：model 生成，外部的东西检查或执行。能把检查交出去的地方（代码、形式化的 constraint、Countdown 的 expression），不必相信 model 自己的执行。

两种花 test-time compute 的方式

可以跳过吗

快速路线可以先跳。跳过会少掉 test-time compute 的成本账，第 4 站末尾和第 6 站的 budget forcing 会用到。

CMU 11-711 的那一讲把多花 test-time compute 的办法分成两类：

  • Parallel：独立地采 NNN 条 (z,a)(z,a)(z,a)，再用一个 aggregation 合成一个答案。取出现最多的答案是 majority vote（第 2 站），用 verifier 打分挑最高的是 best-of-NNN（第 3 站）。
  • Sequential：让一条 zzz 变长，在里面检查、回头、换一种做法。o1、R1 这一类 reasoning model 走的是这条路；长度可以靠 RL 训练出来（第 5 站），也可以在 decoding 时强行控制（第 6 站的 budget forcing）。

两者都按生成的 token 付钱。按每 token 2N2N2N FLOPs：1.5B 的 model 写 10,000 个 token 是 2×1.5×109×104=3×10132\times1.5\times10^9\times10^4=3\times10^{13}2×1.5×109×104=3×1013；32B 的 model 写 1,000 个 token 是 2×3.2×1010×103=6.4×10132\times3.2\times10^{10}\times10^3=6.4\times10^{13}2×3.2×1010×103=6.4×1013。小 model 多想 10 倍，花的 compute 还不到大 model 想一遍的一半。Wu 等人（ICLR 2025）的 inference scaling law 正是这样记账的：inference compute 是 parameter 数、生成的 token 数和 inference 策略的函数，FLOPs 按 Kaplan 等人的公式算，再问固定 compute 下怎样分配。他们在 MATH 上的结果是，Llemma-7B 配上他们的 tree search（REBASE），在所有试过的 inference 策略下都胜过 Llemma-34B，用约一半的 FLOPs 达到和 34B 相当的 accuracy；摘要的结论是，小 model 配上更好的 inference algorithm，在成本和效果上是 Pareto-optimal 的。第 4 站会把这笔账和 pretraining 的成本放在一起算。

FLOPs 只是下界。Decode 是 memory-bound 的，每生成一个 token 要把 parameter 和整个 KV cache 读一遍（CS336 第 8 站），一条 10,000 token 的 trace 越往后越慢；而且 sequential 的 token 只能一个接一个地生成，latency 随长度线性增长，JHU 的 slides 专门列出了这项代价。Parallel 的 NNN 条可以放进同一个 batch 一起生成，latency 几乎不随 NNN 增长。

看起来对，其实不对一次 forward 做不到的事，换一个更大的 model 就能一步做到

更大的 model 主要是更宽、层数多一些，串行的层数仍是一个固定的 LLL。Countdown 的候选从 3 个数的 27 个涨到 6 个数的 656,100 个，是 exponential 的增长；要在固定的 LLL 层里把它们并行地过一遍，宽度也得跟着 exponential 地涨。写中间步骤的做法每一步只面对一个小问题（6 个数时第一步最多 (62)⋅3=45\binom62\cdot3=45(26​)⋅3=45 个选择），配上第 4 站的 search，总代价随步数增长。Snell 在他的 guest lecture 里举的正是这个例子：Countdown 这样简单的题也可能需要 search，不是什么都能一次答出来。

pass@k：至少一次做对

对一道题，model 每次 sample 做对的 probability 记作 ppp（由 model、prompt 和 temperature 决定）。独立采 kkk 次，全错的 probability 是 (1−p)k(1-p)^k(1−p)k，所以至少一次对的 probability 是

Best-of-N：用一个打分函数代替 oracle

Best-of-NNN：采 NNN 个，用打分函数 vvv 挑最高的，

CMU 讲义说 vvv 可以叫 reward model、evaluator、value model 或 verifier。有的任务有完美的 verifier：代码跑 unit test，定理交给 Lean 检查，Countdown 把 expression 算一遍。这时 best-of-NNN 的 accuracy 就是 pass@N。数学题的标准答案在 test time 不知道，只能用一个学出来的 vvv 去近似“这个解对”的 probability。Cobbe 等人（2021）为此造了 GSM8K（约 8.5K 道小学数学应用题），并训练了这样一个 verifier：先把 generator 在 train set 上 fine-tune 2 个 epoch，对每道训练题采 100 个解，只按最终答案对不对打 label（推理错、答案碰对的也算对），再训练 verifier 预测“这个解对”的 probability（在每个 token 后都预测一次，比只在结尾预测效果好）；test time 每题采 100 个，取 verifier 分数最高的那个。在完整的数据上，6B 的 generator 加 6B 的 verifier 略胜过 fine-tune 过的 175B model，论文说这相当于 model 放大约 30 倍。

Verifier 的好坏直接决定 best-of-NNN 能拿到 pass@N 的多少。Codex 论文里有一组现成的数：每题采 100 个 sample，随机挑一个只能做对 28.8%；如果有 unit test 当 oracle，是 70.2%；不用 test，只按“每个 token 的平均 log-probability”挑最高的那个，是 44.5%。Model 自己的 likelihood 是一个免费但很弱的 verifier；论文还说按 log-probability 的总和挑，比随机挑还略差（我的解释：每个 token 的 log-probability 都是负的，总和天然偏向短的回答）。

ORM 和 PRM：在哪一步打分

上面的 vvv 只看完整的解，叫 outcome reward model（ORM）。它的 label 便宜（最终答案对不对），但信号粗：一个 10 步的解在第 2 步就错了，ORM 也要等看完才给一个分，而且不说错在哪。Process reward model（PRM）给每一步打分。

Lightman 等人（2023，OpenAI，Let's Verify Step by Step）请人逐步标注 MATH 的解：每一步标 positive（对且合理）、negative（错或不合理）或 neutral（有歧义），PRM800K 一共 80 万个 step label，来自 1.2 万道题的 7.5 万个解。在 500 道留出的 MATH test 题上，每题从 1860 个 sample 里挑：ORM 做对 72.4%，PRM 78.2%，majority vote 69.6%。

  • Prefix “96−68=28”：剩下 97 和 28，completion 是 125、69、2716，同样是 1/31/31/3 和 1。
  • Prefix “97−96=1”：剩下 68 和 1，completion 是 69、67、68，都不对。Soft 和 hard 都是 0。

这里 completion 恰好能穷举，soft label 是精确值。一般只能采 NNN 个，soft label 是一个 binomial 比例的估计：真值为 1/31/31/3、N=8N=8N=8 时，它的 standard error 是 (1/3)(2/3)/8=0.167\sqrt{(1/3)(2/3)/8}=0.167(1/3)(2/3)/8​=0.167。Hard label 在 N=8N=8N=8 时有 1−(2/3)8=96%1-(2/3)^8=96\%1−(2/3)8=96% 的 probability 是 1，几乎分不出 1/31/31/3 和 1 的 prefix。Math-Shepherd 自己也注意到了：NNN 越大，hard label 越容易出 false positive。他们用 160 个人工标注的 GSM8K 步骤核对，N=4N=4N=4 时 hard label 的 accuracy 是 86%。

为什么要在步骤上 search

Best-of-NNN 每一条都走到底才打分。长的解大多在前几步就走错了，后面的 token 白写了。有了 PRM，可以每走一步就评估一次，把没希望的 prefix 砍掉，把 compute 留给有希望的。

Step-level beam search（JHU、CMU 的讲义）：保留 BBB 个 prefix（beam）；每一步把每个 prefix 扩展出 MMM 个下一步，用 PRM 给这 B⋅MB\cdot MB⋅M 个候选打分，留下最高的 BBB 个；如此往下，直到写出答案。Snell 等人的写法是给定总数 NNN 和 beam width MMM：每一轮留下分数最高的 N/MN/MN/M 个 step，每个再采 MMM 个下一步，最多 40 轮。

Snell 等人：哪种 search 在什么时候好

Snell 等人（2024）用 PaLM 2-S* 在 MATH 上比较了这些方法（train 12k 题、test 500 题，就是 Lightman 等人的划分）。他们先给题目分难度：每题采 2048 个 sample 估计 pass@1，按它把 test 题分成 5 个 quantile（oracle difficulty）；部署时没有标准答案，就改用 verifier 对同样 2048 个 sample 的平均打分来分（predicted difficulty），并在每个难度上做 two-fold cross validation，避免用 test 题调参。Guest lecture 和论文的结论：

  • 所有用 verifier 的 search 都胜过 majority vote。
  • 简单的题、大的 budget：best-of-NNN 更好，beam search 出现 over-optimization 的迹象。
  • 中等和较难的题、小的 budget：beam search 更好。
  • 最难的那一档：所有方法都做不动。
  • 每个难度选最好的方法（compute-optimal），最多能少用 4 倍的 test-time compute 达到 best-of-NNN 的效果（摘要说“more than 4×”，正文第 8 节的说法是 2 到 4 倍）。

第 3 站的 toy model 说明了简单题上 beam search 为什么会 over-optimize。Beam search 每一步都对 PRM 做一次 argmax，相当于把 best-of-NNN 的选择压力加到每一步上。题目简单时对的路本来就多，多挑几次主要的效果是挑中 PRM 的错（toy model 里 NNN 从 12 涨到 1024，accuracy 从 0.733 掉到 0.358）；题目难时不挑就几乎找不到对的路，选择压力利大于弊。

Sequential 的版本是 revision：fine-tune 一个 model，让它看着前面几次错的尝试再写一次。训练数据是事后拼出来的：对每道题用较高的 temperature 并行采 64 个回答，每个对的回答前面接上 0 到 4 个错的（个数均匀地抽，按字符的 edit distance 挑和对的回答最接近的错解），只在最后那个对的回答上做 SFT；inference 时 context 里只留最近 4 次 revision。Snell 等人发现大约 38% 的对的答案会在后续 revision 中被改错，所以要用 verifier 在整串 revision 里挑。Sequential 和 parallel 之间存在最佳的比例：简单题偏向多做 revision，难题要两者混合；按难度选比例，同样最多省 4 倍 compute。

Base model 决定了 RL 能走多远

Lecture 7 引 Gandhi 等人（2025）的结论：RL 只在 base model 已经具备某种能力时才起作用。他们的实验正好是 A3 的任务：同样用 PPO 在 Countdown 上训练 250 步（答对 reward 1、错 0，格式对再加 0.1），Qwen-2.5-3B 到了约 60%，Llama-3.2-3B 只有约 30%。他们让 GPT-4o-mini 数每条 trace 里四种行为出现的次数：verification（系统地检查中间结果）、backtracking（发现错了就明确地换一种做法）、subgoal setting（把问题拆成可以处理的中间目标）、backward chaining（从目标往回推）。Lecture 7 第 37、38 页并排放了两个 model 的回答：Qwen 写“先试最大的两个数之和减最小的……不是 39，再试另一种组合……”，Llama 只写一行答案；Qwen 每条 trace 里 verification 和 backtracking 的平均次数在训练早期分别冲到约 12 次和约 8 次的峰值，Llama 始终几乎为 0。先用含这些行为的例子对 Llama 做一点 SFT（priming）再 RL，Llama 能追上 Qwen；用“行为模式对、但答案错”的例子 priming，效果和用正确答案的相同；只给空 CoT 的 priming，Llama 停在约 30% 到 35%，和不 priming 一样。

RL 在小 model 上为什么慢

第 5 站的结论是：RL 只能放大 base model 已经偶尔做对的东西，而且每道题的信号要靠采样碰出来。小 model 做难题时 ppp 接近 0，大多数 group 没有 gradient。手边如果有一个更强的 model（teacher），可以直接拿它写出的 reasoning 做 SFT：每个 token 都有 target，不需要等 student 自己碰对。这就是 distillation。

DeepSeek-R1 的报告（arXiv v2）做了这个对比，AIME 2024 pass@1：在 Qwen2.5-32B 上直接做大规模 RL（报告里叫 Qwen2.5-32B-Zero）是 47.0，和 QwQ-32B-Preview 的 50.0 相当；用 R1 生成的约 80 万条 sample（约 60 万条 reasoning、20 万条非 reasoning）对同一个 base model 做 SFT，得到 72.6。同一批数据 distill 到不同大小的 model：Qwen 1.5B 28.9、7B 55.5、14B 69.7、32B 72.6，student 越大越好。报告的结论是把大 model distill 到小 model 效果很好。

RL 的 objective 是在 student 自己的 sample 上算的，distillation 的 sample 来自 teacher。Student 在 teacher 走过的 prefix 上学，到自己生成时，一旦写出 teacher 不会写的 prefix，就进了训练里没见过的 state，这时没有任何 target 告诉它怎么接下去。这是 distillation 的结构性弱点，也是有了 distill 出来的 model 之后还要再做 RL 的一个理由。A3 handout 在 SFT 一节也说，实际训练 reasoning model 时 SFT 常常是 RL 之前的 warm start：SFT 需要带 reasoning trace 的数据，RL 只需要答案；而且即使数据充足，RL 仍能找到比 SFT 数据更好的 policy。A3 本身没有把两步接起来。

Lecture 6 的最后一部分讲的是 OpenThoughts（Durrett 是作者之一）：用 QwQ-32B 当 teacher，为一个 7B 的 student 造 reasoning 的 SFT 数据。Pipeline 是收集题目、混合、过滤题目、为每道题生成多个回答（16 个）、过滤回答、选 teacher。几条结论都和直觉相反，slides 和论文的数字是：

Long CoT 的长度：budget forcing

s1 的另一半是在 decoding 时控制 reasoning 的长度，叫 budget forcing。要压短时，到预算就强行插入结束 reasoning 的 delimiter，可以再接上“Final Answer:”，让 model 交出当前最好的答案。要拉长时，在 model 想结束 reasoning 的地方把 delimiter 压掉，接上“Wait”，它常常会回头检查、改掉错误。s1-32B 不加干预时 AIME24 是 50.0，接两次“Wait”是 53.3，一路拉到约 7,320 个 thinking token 时是 57%；接到六次左右曲线就平了，论文还提醒，压 delimiter 压得太频繁，model 会陷入重复的 loop。论文也比较了 parallel：Qwen2.5-32B-Instruct 用 majority vote 采到 64 个，也追不上 s1-32B 用 budget forcing 的 sequential scaling。

import numpy as np

def paired_bootstrap(a, b, B=10_000, seed=0):
    """a、b：两个系统在同一组题上的对错（1/0），顺序一致，b 是分数高的那个。
    返回两个 p 值：Lecture 11 的规则（差超过观察到的差的两倍），
    以及重抽后 b 不比 a 好的比例。"""
    rng = np.random.default_rng(seed)
    a, b = np.asarray(a), np.asarray(b)
    delta = int(b.sum() - a.sum())                     # 用“多做对几道”计，全是整数
    idx = rng.integers(0, len(a), size=(B, len(a)))   # 每行是一次重抽
    d = b[idx].sum(axis=1) - a[idx].sum(axis=1)
    return (d - delta > delta).mean(), (d <= 0).mean()

Multiple testing

Lecture 11 的问法：试 20 组 hyperparameter，其中一组的提升“显著”。每组都用 0.05 的标准，即使没有一组真的更好，至少一组显著的 probability 是 1−0.9520=0.641-0.95^{20}=0.641−0.9520=0.64。Slides 用 xkcd 的 jelly bean 漫画说明：测了 20 种颜色，绿色那一种 p<0.05p<0.05p<0.05，于是上了新闻。Bonferroni correction 把标准除以检验的次数，20 次就是 0.05/20=0.00250.05/20=0.00250.05/20=0.0025。Lecture 11 还讲了 file drawer effect：如果 20 个研究者各做一次，19 个没结果、不发表，发表出来的那一个用不着做任何 correction，看起来干干净净，其实就是那个 false positive。RL 的实验 variance 大，A3 的 learning rate sweep、各种 ablation 都在做多次比较，同一个结论最好在不同 seed 上重复。

Contamination

Lecture 11 把 contamination 分成三种：benchmark 的题出现在 pretraining 数据里；连同答案出现在 post-training 数据里；出现在 RL 的题库里。分数本身看不出虚高了多少。

重新出题。 GSM1k（Zhang 等人，2024）请人按 GSM8K 的风格和难度重新出了 1,205 道题，没有用任何 language model 帮忙，人的解题率、解题步数、答案大小等指标都与 GSM8K 对齐；为了不被污染，数据集暂不公开。比较 model 在两套题上的分数（5-shot，取回答里最后一个数）：差得最多的是 Yi-6B-Chat，8.0 个点，其后有用 Math-Shepherd 的 PRM 做过 RL 的 Mistral-7B（7.2）和 phi-2（6.3）；GPT-4o、GPT-4-Turbo、Gemini 1.5 Pro 的差都在 1 个点以内，Claude 3 Opus 在 GSM1k 上反而高 2.2。一个 model 生成 GSM8K 原题的 per-character log-likelihood 越高，它的分差越大（Spearman 相关系数 0.36，p=0.03p=0.03p=0.03），但作者认为 contamination 可能不是全部原因。

看顺序。 Oren 等人（2024）只用 model 的 log-likelihood 检测（Lecture 11 第 57 到 59 页）。如果一个 benchmark 被原样放进过训练数据，model 会记住题目的排列顺序。题目本来是 exchangeable 的，任何顺序的 likelihood 应该差不多；按原始顺序排的 likelihood 显著高于打乱后的顺序，就说明见过。他们的 sharded rank comparison test：把题目分成 rrr 个 shard，每个 shard 算原始顺序的 log-likelihood，减去 mmm 个随机 permutation 下的平均，得 sis_isi​，再对 sis_isi​ 的平均做 one-sided t-test。他们自己从头训了一个 1.4B 的 model，在 Wikitext 里故意插入 benchmark：只插入 1 次的（BoolQ、HellaSwag、OpenbookQA），p 值是 0.099 到 0.544，测不出来；插入 10 次及以上的，p 值都小到 10−1110^{-11}10−11 以下。

Lecture 11 留了一个问题：它测不到什么？上面的表已经给了一部分答案：只见过一次的测不出来。再按原理推（这是我的推断）：题目被打乱顺序后才进入训练数据、被改写过、或零散地混在别的文本里，顺序的信号就没有了。所以它能给出“见过”的证据，不能给出“没见过”的证据。

训练数据要去重。 造训练数据的人也要反过来防 contamination。OpenThoughts 对每个 benchmark 做 decontamination：按归一化 LCS 的相似度超过 75%，或者 13-gram 重叠，就删掉；在一个人工构造的测试集上，3,092 个污染样本漏掉了 12 个。MATH-500 本身也有一段来历：Lightman 等人为了扩大 PRM 的训练集，把 MATH 的 5,000 道 test 题里的 4,500 道并进了训练数据，只均匀随机地留下 500 道做评测。用 PRM800K 一类数据训练过的 model，在完整的 MATH test 上就是被污染的。

答案解析：model 错还是 parser 错

A3 的第一题（math_baseline）就是这件事。Grader question_only_reward_fn 只认回复里的最后一个 \boxed{...}：找不到 \boxed，format reward 和 answer reward 都是 0；找到了，再用 mathd 的 normalization 和 sympy 判断它与标准答案是否相等（handout 的例子是 1/21/21/2 和 0.50.50.5 要算相等），不相等就是 format 1、answer 0。Handout 要你把 500 道 MATH test 题的结果分成三类（format 1 且 answer 1，format 1 且 answer 0，format 0），后两类各至少看 10 个，判断是 model 的问题还是 parser 的问题。

从 grader 的代码可以读出几种会误判的情形：

  • 答案写在 \boxed 外面（“the answer is 5”），format 是 0，但 model 其实做对了。这是 parser 的错，换 prompt 或换 grader，分数都会变。
  • 回复里有不止一个 \boxed{}（先给一个、后来又改），grader 只取最后一个。
  • 同一个文件里的 r1_zero_reward_fn 是给 R1 格式用的，它要求回复里恰好出现 </think> <answer>（中间一个空格），格式稍有不同，整条回复的 format 就是 0。

Lecture 7 的最后一节讲的也是这件事：prompt 的格式是 reasoning model 的关键组成，答案的格式各家不同（OpenThoughts 在“Final Answer”一行里用 \boxed{}，R1 用 <answer> tag），A3 会让你看到 parsing error 造成了多少问题。GSM1k 的做法是取回答里最后一个数，和示例格式不符的一律判错；作者用人工标注做了一次 ablation，结论没有大变。

边界情况Format 也是 reward

RL 拿同一个 grader 当 reward 时，parser 的偏好会被训练进 model。question_only_reward_fn 对“格式对、答案错”给 format 1、reward 0，代码注释写明这样做是为了防止 hacking：如果格式对就给一部分 reward，model 会先学会只写格式。Gandhi 等人在 Countdown 上就给了 0.1 的 format reward（第 5 站）。所以 A3 要求分别 log format reward 和 answer reward：训练前期 total reward 在涨，先要确认涨的是哪一个。

  • flash_backward 不要求写 Triton：forward 存下 logsumexp LLL，backward 用 recomputation，按 handout 的式 13 到 19（先算 DDD）写成普通的 PyTorch 函数再 torch.compile。flash_benchmarking 一律用 batch size 1、causal mask，sequence length 从 128 到 65536、head 维度从 16 到 128、bf16 和 fp32 都要扫，要报告用的是哪种 GPU。可选的加速部分如果把 backward 也写成 Triton，handout 建议分两遍算（一遍算 dQdQdQ，一遍算 dKdKdK、dVdVdV），避免 block 之间的 atomic 或同步。更多的提示见 CS336 A1、A2 的提示。（A2 handout）

Final project（有余力再做）

要做什么。 自选一个和 LLM reasoning 有关的题目，可以 2 到 3 人一组。两条路：原创研究（工程型：选任务和数据，改进一个方法；或分析型：把一个问题刻画清楚），或者复现一篇论文（照 ML Reproducibility Challenge 的标准）。交付物是一页 proposal（5 分）、2 到 3 页带初步结果的 check-in（5 分）、6 到 8 页会议论文格式的报告（80 分，从 70 分的基准分往上下调）和 3 分钟的课堂展示（10 分）。Handout 给的方向有四类：capability（评测和改进前沿 reasoner 与 agent）、science（在作业那样的小规模设置里研究 RL、训练、inference）、interpretability、safety。

做完会什么。 从提出问题、设计 baseline 到写成一篇论文的完整流程，以及第 7 站的那些统计工具在自己的实验里怎么用。

时间与算力。 Handout 没有给时间。它明确建议避开高算力的题目：要训练就用很小的 model，要做 prompting 或 reasoning harness 就用最强的 frontier model 或最大的开源 model；课程不提供闭源 model 的费用，但说很多项目花不到 20 美元。

提示。

  • 让成功不是全有或全无：先定一个很可能达到的目标，再加 stretch goal；即使最终方法没成，也要有能报告的结果和分析，而不只是“代码报错了”。（handout）
  • 复现不是把代码重跑一遍：要批判地检查代码是否真的做了论文说的事，可以给它写 unit test；也不要挑一篇 20 行 PyTorch 就能复现的论文。（handout）
  • 避开主要靠领域工程的题目（handout 的反例是给博彩市场做 agent），以及在大 model 上做 fine-tuning 或 GRPO 的题目，除非自带算力。（handout）
  • 报告结果时用第 7 站的方法：给出 standard error、做 paired 的比较、说明比较了多少组设置。（经验）
