TinyML and Efficient Deep Learning Computing

TinyML 与高效深度学习计算

这门课回答的是：一个已经训练好的模型，怎样变小、变快、塞进算力和内存都受限的设备。内容覆盖 pruning、quantization、NAS、knowledge distillation，在 microcontroller 上跑 CNN 的 MCUNet/TinyEngine，以及 LLM、ViT、diffusion 的部署优化和 on-device training。对想做“能在边缘平台上跑的机器人模型”的人，这是这一组里最直接的一门：学完能给一个 policy 或 VLM backbone 做 int8/int4 quantization、structured pruning，并且知道怎样量 latency 和 memory，而不是只看参数量。

公开的材料课程主页每讲都有 slides（Dropbox）和 YouTube 录像（2026 已到 Lecture 19，2024 全部齐全）。Lab 0-5 公开：Lab 0/2/3/4 是 Colab notebook，Lab 1 GPU Basics 是 zip，Lab 5 是 Drive 文件夹（2026 版文件夹内容本次未能读到；往期 Lab 5 的说明在 GitHub 的 tinychat-tutorial 仓库）。没有考试，评分靠 5 个 lab 和 final project；project idea 列表是公开的 Google Doc。作业在 MIT Canvas 提交，外部学习者没有 autograder，只能看 notebook 内的检查和自己对照结果。Colab notebook 需要登录 Google 才能看到内容，本次调研没有直接读到 notebook 正文，lab 细节来自 2024 版 lab 的公开社区镜像。

前置会写 PyTorch training loop，懂 CNN 和 Transformer 的基本结构；Lecture 10-11 和 Lab 5 需要计算机组成的概念（cache、SIMD、多线程、内存层级）。MIT 官方先修是 6.191 Computation Structures 和 6.390 Intro to ML。本站对应：CS2100（计算机组成）、CS2109S / CS3244（ML 基础）、CS3210（并行计算，对 Lab 5 有帮助）。（本站：CS2100、CS2109S、CS3244、CS3210）

作业

  • 先做Pruning lab（2026 编号 Lab 2，2024 编号 Lab 1）

    在 CIFAR 规模的 VGG 上实现 magnitude-based fine-grained pruning，做逐层 sensitivity scan 选每层 sparsity，再实现按 importance 排序的 channel pruning，最后 fine-tune 恢复精度并测 MACs、模型大小和 CPU latency。

    时间
    handout 未给出。镜像中记录 sensitivity scan 约 2 分钟、fine-tune 约 3 分钟（GPU 上）；整份 lab 估计 4-6 小时（估计）。
    环境
    notebook 里调用 .cuda()，需要 Colab GPU runtime，免费 T4 足够；latency 部分在 CPU 上测，用来模拟边缘设备。
    • fine-tune 时每次 optimizer.step() 之后都要把 mask 重新乘回 weight，否则被剪掉的权重会长回来，sparsity 悄悄失效。
    • sensitivity scan 每试一个 (layer, sparsity) 组合后要恢复原始权重，否则后面的扫描是在已经剪过的模型上做的，曲线会整体偏低。
    • channel pruning 改了一层的输出通道，必须同步改这一层的 BatchNorm 参数和下一层 conv 的输入通道，三处顺序要一致，否则模型直接错掉。
    • 镜像结果显示：只剪不排序时精度掉到 28%，按 Frobenius norm 排序后是 37%，fine-tune 5 个 epoch 回到 92%。看到精度暴跌先别怀疑实现，先看 fine-tune 之后。
    • fine-grained sparsity 只减模型大小，在普通 dense 硬件上不提速；channel pruning 才有真实 latency 收益（镜像里 30% channel pruning 约 1.9 倍 CPU 加速）。lab 最后一问就在问这个区别，部署时选方法要记住。

    提示来源：前四条与第五条的数字来自 2024 版 lab 的公开社区镜像（tinyml-kor 博客，含 notebook 原文和运行结果）；“dense 硬件不提速”这一点是 lab Q9 的内容。

  • 先做Quantization lab（2026 编号 Lab 4，2024 编号 Lab 2）

    实现 k-means quantization 和 codebook 更新（QAT），实现 linear quantization 的 scale/zero-point、int32 bias、quantized_linear 与 quantized_conv2d，融合 BatchNorm、收集 activation range，把 VGG 转成 integer-only 的 int8 模型。

    时间
    handout 未给出；估计 5-8 小时（估计）。
    环境
    用到 fast_pytorch_kmeans 且调用 .cuda()，需要 Colab GPU runtime；整数推理部分也有 CPU 分支。
    • k-means quantization 不做 fine-tune 时，4 bit 掉到约 79%，2 bit 掉到 10%（等于随机猜）；更新 centroid 做 QAT 后分别回到约 92% 和 91%。看到 2 bit 的 accuracy collapse 是预期现象，要看 QAT 之后的数。
    • zero point 必须 round 成整数并 clamp 到量化范围内，不能把整数 Z 直接加到浮点的 r/S 上。
    • 输出 cast 到 int8 之前要先 clamp 到 bitwidth 范围，否则会 wraparound。镜像代码里先 cast 成 int8 再加 zero point，加法本身可能溢出；更稳妥的做法是在 int32 里完成加法和 clamp 再 cast。
    • bias 用 int32 存，S_bias = S_input × S_weight，Z_bias = 0；input zero point 带来的修正项要折进 bias 里。
    • 先 fuse BatchNorm 再收集 activation range；输入图像在 (0,1) 范围，要额外写 preprocessing 把它映射到 int8 范围，这一步漏掉会让整个 int8 模型精度很低。

    提示来源：第 1、2、4、5 条来自 2024 版 lab 社区镜像的 notebook 和结果；第 3 条前半句来自镜像，int8 加法溢出的判断是对镜像代码的观察加自己的经验。

  • 先做Lab 5: LLM Deployment on Laptop（TinyChatEngine）

    在 TinyChatEngine 里部署 AWQ int4 的 LLaMA2-7B-chat，对 linear kernel 依次加 loop unrolling、multithreading、SIMD，测每一步对端到端 latency 的影响；提交 git diff 生成的 patch 和报告。

    时间
    handout 未给出（详细步骤在 tutorial 链接的 Google Doc 里，本次未能读到）；估计 8-12 小时（估计）。
    环境
    不需要 GPU。x86 或 ARM 笔记本都可以（patch 按 ISA 命名为 x86 或 ARM）；7B int4 模型需要几 GB 磁盘和内存（估计）。TinyChatEngine 本身还支持 Raspberry Pi 4（推荐 8GB）和 compute capability 6.1 以上的 CUDA 设备，README 举的例子包括 Jetson AGX Orin。
    • 提交要求 patch 命名为 {studentID}-{ISA}.patch，ISA 取 x86 或 ARM：先确认自己机器的 ISA，只改对应的 SIMD 代码路径（x86 是 AVX，ARM 是 NEON）。
    • macOS 上编译 TinyChatEngine 需要先用 Homebrew 装 boost 和 llvm，Apple Silicon 还需要 Xcode 提供 Metal compiler；CUDA 设备要按自己 GPU 的 compute capability 改 Makefile 里的 -arch/-gencode。
    • 报告要分别给出每一步优化的提速，所以每加一种优化都先单独测一次并记下数字，不要三种一起改完才测。
    • 每加一步优化先对比参考输出确认结果没变，再测速度；笔记本测速时插电、多跑几次取稳定值，散热降频会让同一份代码的 latency 波动很大。
    • 做完 lab 后，同一套代码可以直接搬到 Jetson 或 Raspberry Pi 上跑，这是本组里少数能直接延伸到嵌入式硬件的作业。

    提示来源：第 1 条来自 tinychat-tutorial README；第 2 条和第 5 条中的平台支持来自 TinyChatEngine README；第 3 条来自 tutorial 对报告内容的要求；第 4 条是自己的经验。

深度学习系统：算法与实现

作业

  • 先做hw1: Automatic Differentiation

    给 needle 的各个 op 写 forward 和 gradient，实现 topological sort 和 reverse-mode autodiff，再用自己的 autograd 训练 softmax regression 和两层网络。

    时间
    handout 未给出；估计 8-12 小时（估计）。
    环境
    纯 Python/NumPy，CPU 即可，Colab 也行。
    • 每个 op 的 gradient 都要保持和输入相同的 dtype。hw2 里大量“结果变成 float64”的问题根源都在 hw1 的 op 实现，而 autograd 里没有 cast 的手段，只能从一开始就保证。
    • 检查 rsub 的定义：仓库 issue 指出它被直接设成 sub，而减法不交换，scalar - tensor 会算错。
    • test_transpose_forward 报 “axes don't match array” 的公开 issue 很常见：先弄清 needle 的 transpose 默认交换最后两个轴、给定 axes 时只交换那两个轴，与 numpy.transpose 的语义不同。
    • broadcast_to 和 summation 的 gradient 是一对：broadcast 的反向要对被广播的轴求和，summation 的反向要先 reshape 回保留维度再 broadcast，形状写错是这次作业最常见的 bug。

    提示来源：第 1、2 条来自 dlsyscourse/hw1 的公开 GitHub issues（#20、#21）；第 3 条的报错来自 issue #24 的标题，对 transpose 语义的解释是自己的经验；第 4 条是自己的经验。

  • 值得做hw2: Neural Network Library

    在 hw1 的 autograd 上实现 neural network modules（Linear、normalization、Dropout 这类层）和 optimizers（SGD、Adam 这类），再用它们训练网络。课程页只写了“Neural network modules and optimizers”，具体清单以 notebook 为准。

    时间
    handout 未给出；估计 8-12 小时（估计）。
    环境
    CPU 即可。
    • LayerNorm 对每个样本的最后一维做归一化，BatchNorm 对每个特征跨 batch 归一化；写之前先把这两个维度在纸上画清楚。
    • optimizer 更新参数时要在 .data / detach 后的值上算，否则每一步更新都会被接进计算图，内存越跑越大。
    • BatchNorm 的 running mean/var 只在 training 模式更新，eval 模式要用 running 统计量，测试里两种模式都会查。

    提示来源：第 1 条来自一篇公开的 2024 Fall 学习笔记（aliceraylu.github.io）；第 2、3 条是自己的经验。

  • 先做hw3: NDArray Library with CPU/CUDA Backends

    实现基于 strides 的 NDArray：reshape/permute/broadcast 作为 view，compact、setitem、elementwise 和 reduction，再分别用 C++（pybind11）写 CPU backend、用 CUDA 写 GPU backend，包括 tiled matmul。

    时间
    handout 未给出；估计 15-25 小时（估计）。
    环境
    CPU backend 任何机器都能编译；CUDA backend 需要 NVIDIA GPU，课程推荐 Colab GPU runtime。需要 CMake、pybind11 和 nvcc。
    • 有公开笔记记录在 Colab T4 上 make 编译 ndarray_backend_cuda.cu 时，pybind11 在注册含 CudaArray 参数的函数处报模板递归过深、最后 CMake 报 “Error generating file”，作者没有解决。遇到同样报错时，先核对 Colab 当前的 nvcc、pybind11 与 CMake 版本是否匹配，必要时固定 pybind11 版本。
    • CPU backend 的 matmul 用固定 TILE（8）分块，尺寸不是 8 的倍数时会走慢路径；有人在 benchmark 中因此看到被夸大的 GPU 加速比。边界块要单独正确处理，计时时注意这个偏差。
    • 先把 compact 写对，并让所有 backend 计算 op 都假设输入是 compact 的；permute、broadcast_to、getitem 只改 shape/strides/offset，不复制数据。
    • setitem 和 getitem 的 offset 计算最容易错，先用 numpy.lib.stride_tricks.as_strided 在 Python 里验证同样的 strides/offset，再写 C++。

    提示来源：第 1 条中的报错现象来自公开学习笔记（aliceraylu.github.io），后半句处理建议是自己的经验；第 2 条来自 dlsys-needle-m1 仓库 README 的 benchmark 说明；第 3、4 条是自己的经验。

  • 值得做hw4: Convolutions, RNNs, and Advanced Architectures

    在自己的 NDArray backend 上实现 convolution 和 RNN/LSTM 等结构，训练 CNN 和序列模型（课程页写作 Convolutions, RNNs, and advanced architectures，具体题目以 notebook 为准）。

    时间
    handout 未给出；估计 15-20 小时（估计）。
    环境
    训练部分实际需要 GPU，课程推荐 Colab GPU runtime。
    • conv 按 Lecture 14 notebook 的思路用 strides 做 im2col 再接 matmul，比写多重循环简单得多也快得多，反向用 flip 和 dilate 组合表达。
    • 有人把 needle 移植到 Apple M1 时发现 RNN/LSTM 在 GPU 上比 CPU 还慢，只能缩小 seq_len 和 hidden size 来测：这类逐时间步的小算子受 kernel launch 开销支配，调试时可以先在 CPU 上跑小规模。

    提示来源：第 1 条是自己的经验，参考了 Lecture 14 公开 notebook；第 2 条来自 dlsys-needle-m1 仓库 README。

Parallel Computing

并行计算

这门课教的是怎样推理性能：SIMD、多核、内存带宽、GPU 执行模型、data-parallel 思维，以及 DNN 在 GPU 上怎样高效求值、专用硬件为什么快。边缘平台（例如 Jetson 这类 ARM 多核加 CUDA GPU 的板子）上的瓶颈几乎都是这些，学完能判断一个模型在某块板子上是 compute-bound 还是 memory-bound。

作业

  • 先做Assignment 1: Analyzing Parallel Program Performance on a Quad-Core CPU

    用 std::thread、课程的 fake SIMD intrinsics 和 ISPC 分别并行化 Mandelbrot、clamped exp、sqrt、saxpy 和 k-means，并解释每种加速为什么达不到理想值。

    时间
    handout 未给出；估计 10-15 小时（估计）。
    环境
    不需要 GPU。官方在带 AVX2 的四核 myth 机器上评测；自己的 x86 机器装 ISPC 即可，Apple Silicon 有单独的 README_aarch64.md。
    • Program 1 里 3 个线程那个数据点是线索：加速比反而不好时，先画出每个线程的耗时，看是不是空间划分造成了负载不均。
    • SIMD 代码要用不是向量宽度整数倍的输入测试（README 给的例子是 ./myexp -s 3），并用 -l 打印向量指令日志，tail 处理和 mask 的 bug 都靠这个发现。
    • saxpy 是 memory-bound，加更多 SIMD 和线程也不会线性提速，写分析时要从带宽而不是算力出发。
    • k-means 题只允许并行化一个函数且不能改算法语义，先 profile 找 hotspot；数据集约 800MB，README 建议用符号链接而不是复制。

  • 先做Raspberry Pi: Object Detection

    在 Pi 上用 Flask 采集图片、Roboflow 标注，分别训练并部署 Edge Impulse 的 SSD-MobileNetV2 与 FOMO、Ultralytics YOLOv8n（Colab 上训练），比较它们在板子上的延迟和效果，并处理 int8 输入和 NMS 后处理。

    时间
    页面未给出；估计 5-8 小时（估计）。
    环境
    Raspberry Pi 4 或 5（页面也列出 Zero 2 W），至少 32GB SD 卡；YOLOv8n 训练用 Colab T4。
    • int8 的 SSD 模型输入是 int8：像素先除以 255，再按输入 tensor 的 quantization 参数做 x / scale + zero_point，clip 到 [-128, 127] 后 cast，scale 和 zero point 要从模型的 input details 读，不要写死。
    • 加载模型后的第一次推理慢很多（页面里 YOLOv8n NCNN 第一次约 17 秒，之后约 2 秒），测延迟要先 warm-up。
    • 把置信度阈值调到 0.3 会出现误检和重复框，需要按 IoU 做 NMS。
    • 非正方形图像要缩放压扁而不是裁剪；训练前先修好 data.yaml 里的图片路径。
    • Edge Impulse 免费版的数据集不能导出到其他平台，所以作者用 Roboflow 管理数据。

    提示来源：全部来自该实验页面。
