从进度块恢复

先看三件事。

第一件。 这是 TA 在 Tutorial 2 开头放的 program，只多加了一行：test1 先睡 100 ms，保证 test2 先跑到 loop。

int a = 0, b = 0, flag = 0;

void test1() {
    std::this_thread::sleep_for(std::chrono::milliseconds(100));
    a = 1;
    b = 1;
    flag = 1;
}

void test2() {
    while (flag == 0) {}
    std::printf("a=%d b=%d\n", a, b);
}

两个 thread 分别跑 test1 和 test2。按字面读，test2 等到 flag 变成 1 才打印，a、b 早已是 1。用 g++ 13 编译，-O0 打印 a=1 b=1；-O2 立刻打印 a=0 b=0，根本没有等。

第二件。 同样在 x86 上，两个 thread 各自先写一个 variable、再读对方的 variable：

// Thread 1          // Thread 2
x = 1;               y = 1;
r1 = y;              r2 = x;

任何“一个 thread 走一步、另一个 thread 走一步”的交错里，总有一个 write 排在两个 read 之前，所以 r1、r2 不会同时是 0。真实的 x86 处理器会给出 r1 == 0 && r2 == 0。

第三件。 一个 Go program 只有三行：

c := make(chan int)
c <- 1
fmt.Println(<-c)

它不打印 1，报的是 fatal error: all goroutines are asleep - deadlock!。

第一件是 compiler 做的，第二件是 hardware 做的，第三件是 channel 的 semantics。三件事都说明同一点：并发程序的意思不是“把各个 thread 的语句随便交错着执行一遍”。这门课要回答的是：一个 language 到底对并发程序许诺了什么，怎样写出在这个许诺之内、没有 data race、没有 deadlock、没有 undefined behaviour 的 code。

课程用三门 language 讲三种做法，TA 的 Tutorial 5 给的比例是 C++ 约一半、Go 和 Rust 各四分之一。

共享 data 的方式 谁来保证没有 data race
C++ shared memory，加 lock 或 atomic programmer；有 data race 的 program 是 undefined behaviour
Go 主要靠 channel 传消息 programmer，辅以 runtime 的 race detector
Rust 两种都有 compiler：有 data race 的 safe Rust 编译不过

一个 std::thread 必须被 join 或 detach

std::thread t(f); 一构造就开始执行 f。t.join() 等它结束；t.detach() 让它独自跑下去，t 不再管它。两样都没做，t 被销毁时还是 joinable 的，C++ 规定这时调用 std::terminate，整个 program 直接结束。Tutorial 1 的复习题考的就是这一条。

std::thread 只能 move，不能 copy。std::thread t2 = std::move(t); 之后，执行流归 t2 管，t 不再拥有任何 thread，这时调用 t.join() 会抛出 exception，要 join 的是 t2。

Thread 结束得晚，它用到的东西也必须活得够久。Tutorial 1 的另一道复习题：留一个 pointer 指向一个 std::string，string 离开 scope 之后再 dereference，结果是 undefined behaviour。换成 thread 就是：把一个 local variable 的 reference 交给 thread，然后 detach，function 返回后 thread 还在读那块已经不存在的 stack。第 7 站会看到 Rust 怎样在编译时就拒绝这种 code。

Data race：按定义检查

两个 thread 各把一个共享的 int 加一百万次，这是 Tutorial 1 的 Task 1：

int counter = 0;
void work() { for (int i = 0; i < 1000000; i++) counter++; }

int main() {
    std::thread t1(work), t2(work);
    t1.join(); t2.join();
    std::cout << counter << "\n";
}

C++ 对 data race 的定义有四个条件：两个 access 访问同一个 memory location，至少一个是 write，至少一个不是 atomic，而且两者之间没有 happens-before 关系（第 4 站给出 happens-before 的精确定义；这里只需要知道 lock、atomic、thread 的创建和 join 才会建立它）。

逐条检查 counter++：两个 thread 都读写 counter，有 write；counter 是普通的 int；两个 loop 之间没有任何 synchronization。四条都满足，这是 data race。C++ 规定有 data race 的 program 是 undefined behaviour：整个 program 没有任何被定义的意思，后果远不止“结果少几次”。

同一台机器上实测：

编译 五次的结果
-O0 1088488、1094495、1195009、1082535、1004025
-O2 2000000、2000000、2000000、2000000、2000000

-O0 的结果少了一半左右，原因是 CS2106 第 3 站讲过的 load、add、store 三步交错。

看起来对，其实不对跑了很多次都是 2000000，说明这段 code 没有问题

看 -O2 生成的 work：

_Z4workv:
    addl    $1000000, counter(%rip)
    ret

Compiler 把一百万次加 1 合并成了一条“加 1000000”。它这样做完全合法：单看一个 thread，结果相同，而 compiler 有权假定没有别的 thread 同时在写 counter（如果有，那就是 data race，program 本来就没有意义）。两个 thread 各只执行一条 instruction，碰巧没撞上，于是每次都是 2000000。这条 addl 前面没有 lock prefix，两个 core 同时执行仍会丢失更新。换一个 compiler 版本、把 loop 里加一个 function call，race 就会重新显形。Data race 不能靠测试排除，只能按定义检查。

用 mutex 修：RAII 的 lock wrapper

修法是让每次 counter++ 都在同一个 std::mutex 的保护下执行。直接写 m.lock(); counter++; m.unlock(); 有一个漏洞：两行之间如果抛出 exception，unlock 永远不会执行，别的 thread 永远拿不到 lock。Tutorial 1 的建议是用 RAII：一个 object 在构造时 lock、在析构时 unlock，离开 scope 时无论怎样离开都会析构。

std::mutex m;
int counter = 0;
void work() {
    for (int i = 0; i < 1000000; i++) {
        std::lock_guard<std::mutex> lk(m);   // 构造时 lock
        counter++;
    }                                        // lk 析构时 unlock
}

标准库有三个这样的 wrapper，Tutorial 1 比较了它们：

wrapper 能做什么 用在哪里
std::lock_guard 只能在构造时 lock、析构时 unlock 最简单的 critical section
std::unique_lock 可以中途 unlock、再 lock，可以 move condition variable 的 wait 必须用它（第 2 站）
std::scoped_lock 构造时一次锁住多个 mutex，内部用避免 deadlock 的算法 同时需要两把以上的 lock

另一种修法是把 counter 换成 std::atomic<int>。Tutorial 2 对比了两者生成的 x86 code，这里用 g++ 13 重新编译核对过：mutex 版本是 call pthread_mutex_lock、addl 1,counter(1, counter(%rip)`、`call pthread_mutex_unlock` 三步；`fetch_add` 版本只有一条 `lock addl1,counter(1, ac(%rip)。lock prefix 让这条 read-modify-write 在所有 core 看来不可分割。第 4 站专门讲 atomic。

每个 method 都上锁，还是不够

Tutorial 1 的 Task 2 是一个包着 std::queue 的 JobQueue：

class JobQueue {
    std::queue<Job> q;
public:
    void enqueue(Job j) { q.push(j); }
    std::optional<Job> try_dequeue() {
        if (q.empty()) return std::nullopt;
        Job j = q.front();
        q.pop();
        return j;
    }
};

题目问三种情形安不安全，答案是都不安全。Producer–producer：两个 push 同时改 queue 内部的 size 和末尾 pointer，是 data race。Producer–consumer：push 写 size 的同时 empty 在读它，同样是 data race。Consumer–consumer 最值得看，因为它说明光给每个小操作上锁不够。

假设 std::queue 自带 lock，empty、front、pop 每一个单独调用都是 thread-safe 的。Queue 里只有一个 job JJJ，两个 consumer 同时调用 try_dequeue：

C1 和 C2 都执行了 front，拿到同一个 JJJ，这个 job 被做了两次；第二个 pop 作用在一个已经空了的 queue 上，对 std::queue 来说是 undefined behaviour。错误在于“检查不空”和“取出”是两个操作，结论在两步之间失效了。这类错误叫 check-then-act。修法是把整个 try_dequeue 放进同一把 lock：

std::optional<Job> try_dequeue() {
    std::lock_guard<std::mutex> lk(m);
    if (q.empty()) return std::nullopt;
    Job j = std::move(q.front());
    q.pop();
    return j;
}

enqueue 也拿同一把 m。Lock 保护的是一条 invariant（这里是“我判断不空的那个 job 还在 queue 里”），它可以在 critical section 里暂时被破坏，出来时必须恢复。

两把 lock、相反的顺序

Tutorial 1 最后一题把一个 mutex 和一个 counting semaphore 混在一起，两个 function 以相反的顺序获取它们。下面是按题意写出的一个版本（semaphore 的初值是 1，acquire 把它减 1，为 0 时等待；第 2 站讲 C++20 的 semaphore）：

std::mutex m;
std::counting_semaphore<1> slot{1};

void f() {
    std::lock_guard<std::mutex> lk(m);   // 先 m
    slot.acquire();                      // 再 slot
    /* ... */
    slot.release();
}

void g() {
    slot.acquire();                      // 先 slot
    std::lock_guard<std::mutex> lk(m);   // 再 m
    /* ... */
    slot.release();
}

这正是 deadlock 的四个 condition 同时成立（CS2106 第 4 站有完整的讨论和 lock ordering 的证明）。修法是规定一个全局的顺序，f 和 g 都先 slot 后 m。如果两样都是 mutex，可以写 std::scoped_lock lk(m1, m2);，它内部用 std::lock 的算法：拿到一把、试另一把，试不到就把手里的放掉重来，所以两个 thread 无论以什么顺序写 scoped_lock(m1, m2) 和 scoped_lock(m2, m1) 都不会 deadlock。Semaphore 没有 lock/unlock 接口，不能交给 scoped_lock，只能靠人排好顺序。

等一个条件成立

第 1 站的 try_dequeue 在 queue 空的时候直接返回 nullopt。很多时候 consumer 想要的是“等到有 job 为止”。两种直接的写法都不行。

转圈。 在 loop 里反复上锁、检查、放锁。Queue 一直是空的时候，这个 thread 占满一个 core 什么也不做。

放锁、睡觉、再上锁。 检查到空之后放掉 lock，睡下，等 producer 叫醒。问题在“放锁”和“睡下”之间：producer 恰好在这时 push 一个 job 并发出通知，consumer 还没睡，通知没人接收；consumer 随后睡下，再也等不到这条已经发过的通知。这叫 lost wakeup。

Condition variable 把“放锁”和“睡下”合成一步。cv.wait(lk) 在持有 lk 时调用，它原子地放掉 lock 并睡下；被叫醒后先重新拿到 lock，再返回。Producer 必须拿着同一把 lock 才能改 queue，所以它的 push 不可能落在 consumer“检查到空”和“睡下”之间。

class BlockingQueue {
    std::mutex m;
    std::condition_variable not_empty;
    std::queue<Job> q;
public:
    void push(Job j) {
        { std::lock_guard<std::mutex> lk(m); q.push(std::move(j)); }
        not_empty.notify_one();
    }
    Job pop() {
        std::unique_lock<std::mutex> lk(m);
        while (q.empty())
            not_empty.wait(lk);          // 放锁并睡下；醒来时已重新拿到锁
        Job j = std::move(q.front());
        q.pop();
        return j;
    }
};

wait 需要在中途放锁、再上锁，所以只能配 std::unique_lock，不能配 lock_guard。Condition variable 本身没有 counter：没有人在等时 notify_one 什么也不留下，这正是它和 semaphore 的区别。所以“条件是否成立”必须存在共享的 state 里（这里是 q.empty()），由 lock 保护。

为什么是 while，不是 if

把 while (q.empty()) 换成 if (q.empty()) 看起来也对：被叫醒说明有人 push 了。Cambridge 的讲义给了反例，用一个容量为 1、两边都会等的 bounded buffer：producer 在满时等 not_full，consumer 取走一个 item 后 notify_one(not_full)。

问题出在“被叫醒”和“重新拿到 lock”之间可以有别人插进来。被 notify 的 thread 只是被移进等 lock 的队伍，notify 的一方继续执行，这叫 signal-and-continue，也叫 Mesa semantics（Xerox PARC 的 Mesa language 这样实现）。另一种是 Hoare 的 signal-and-wait：notify 的一方立刻停下，lock 直接交给被叫醒的 thread，中间没人能插进来，if 就够了。Hoare semantics 难实现，而且 Cambridge 指出它要求 notify 时 invariant 已经恢复。POSIX、C++、Java 用的都是 Mesa semantics。

C++ 还允许 spurious wakeup：没有任何人 notify，wait 也可能返回。两个原因都要求醒来后重新检查条件，所以 wait 永远写在 while 里。标准库有一个带 predicate 的重载，not_empty.wait(lk, [&]{ return !q.empty(); });，它内部就是这个 while。

notify_one 什么时候不够

Producer 和 consumer 如果共用同一个 condition variable changed，notify_one 可能叫醒错误的一方。仍用容量为 1 的 buffer，开始时是空的：

步 事件 buffer 在 changed 上等的
1 C1、C2 看到空，先后 wait 空 C1、C2
2 P1 放入 x，notify_one 叫醒 C1（C1 去等 lock） x C2
3 P2 先拿到 lock，看到满，wait x C2、P2
4 C1 拿到 lock，取走 x，notify_one 叫醒了 C2 空 P2
5 C2 拿到 lock，看到空，wait 空 P2、C2

Buffer 是空的，P2 手里有东西要放，却没人会叫醒它；C2 想要 item，也在睡。如果之后没有新的 thread 来，两个都永远等下去。第 4 步那次 notify 本该给 P2，却给了 C2。修法有两种：producer 和 consumer 各用一个 condition variable（not_full、not_empty），使每次 notify 只叫醒等同一个条件的 thread；或者用 notify_all，让所有人醒来各自重新检查，代价是醒来又睡回去的那些 thread 白白抢了一次 lock。

Monitor：把 lock、条件和 data 包在一起

上面的 BlockingQueue 是一个固定的形状：一个 class，private 的 data，一把 mutex，几个 condition variable；每个 public method 一进来就上锁，等待时在 while 里 wait。Tutorial 1 把它叫 monitor pattern。Monitor 是 1970 年代提出的 language 构造：同一时刻只有一个 thread 能在 monitor 的 method 里，其他调用者在入口排队。Java 的每个 object 都自带一把 lock 和一个 condition queue，synchronized method、wait()、notify()、notifyAll() 就是 monitor；它也是 Mesa semantics，wait 同样要写在 while 里。

C++20 的 semaphore、barrier 与 latch

C++20 加入了 std::counting_semaphore<N> s{k};（初值 kkk，最大值 NNN），s.acquire() 和 s.release() 就是 Wait 和 Signal（定义和用法见 CS2106 第 4 站）；std::binary_semaphore 是 counting_semaphore<1>。和 condition variable 不同，semaphore 有 counter，没人在等时 release 也会留下记录。

std::barrier b(n); 让 nnn 个 thread 互相等：每个 thread 调用 b.arrive_and_wait()，前 n−1n-1n−1 个睡下，第 nnn 个到达时 nnn 个一起继续，barrier 随即重置，可以用下一轮（phase）。std::latch 只能用一次。

H2O：两种 primitive 合起来

Tutorial 7 的第一题。H atom 和 O atom 各是一个 thread，每个 thread 调用一次 bond()；要求每次一起 bond 的恰好是 2 个 H 和 1 个 O。

第一次尝试：只用 std::barrier(3)。 每个 atom arrive_and_wait() 之后 bond()。三个一组确实一起走，但组成不对：先到的 3 个 H 就能凑成一组。

第二次尝试：只用 semaphore。 O 用初值 1 的 semaphore，H 用初值 2 的，每个 atom acquire、bond、release。比例上限对了：任何时刻最多 1 个 O、2 个 H 在里面。可它们互不等待，一个 O 进来就直接 bond，不会等两个 H。

合起来。 先过 semaphore，再过 barrier：

std::counting_semaphore<1> o_sem{1};
std::counting_semaphore<2> h_sem{2};
std::barrier<> bar{3};

void oxygen()   { o_sem.acquire(); bar.arrive_and_wait(); bond(); o_sem.release(); }
void hydrogen() { h_sem.acquire(); bar.arrive_and_wait(); bond(); h_sem.release(); }

为什么一定是 2 个 H、1 个 O。 把“已经 acquire、还没 release”的 thread 叫 holder。两个 semaphore 一共只有 3 个 permit，所以任何时刻 holder 最多 1 个 O、2 个 H。Barrier 的一轮要完成，必须有 3 个 thread 在这一轮到达，而到达 barrier 的 thread 都是 holder，在 barrier 上等着时还没有 release。所以这一轮完成的那一刻，这 3 个 thread 同时是 holder，用掉了全部 3 个 permit：恰好 1 个 O、2 个 H。有的 holder 已经过了上一轮 barrier、还在 bond 里没 release，它占着 permit 却不会在这一轮再到达，只会让这一轮等得更久，不会让组成出错。

FIFO semaphore：不让人插队

普通的 semaphore 不保证先来先得，一个 thread 可能一直被后来的抢先，这是 starvation。Tutorial 7 的第二题要一个 FIFO 的 semaphore。第一种做法借用 ticket 的思路：

class FifoSemaphore {
    std::atomic<long> next_ticket{0};
    std::atomic<long> now_serving;            // 初值是 permit 的个数 k
public:
    explicit FifoSemaphore(long k) : now_serving(k) {}
    void acquire() {
        long t = next_ticket.fetch_add(1);    // 取号：0, 1, 2, ...
        while (now_serving.load(std::memory_order_acquire) <= t) {}
    }
    void release() { now_serving.fetch_add(1, std::memory_order_release); }
};

取 k=2k=2k=2。前三个来的 thread 拿到 ticket 0、1、2。now_serving 是 2，ticket 0 和 1 满足 t<2t<2t<2，直接进去；ticket 2 等着。有人 release 之后 now_serving 变成 3，ticket 2 进去。之后来的拿 ticket 3，要等 now_serving 变成 4。号码按 fetch_add 的先后发，进门也按号码的先后，所以是 FIFO。缺点是等待者在转圈。

第二种做法不转圈：一把 mutex 保护 permit 计数 count 和一个 Waiter 的 queue，每个 Waiter 里有一个初值为 0 的 std::binary_semaphore。acquire 在 lock 下看 count，大于 0 就减 1 返回；否则把自己的 Waiter 放进 queue 尾，放锁，在自己的 semaphore 上 acquire 睡下。release 在 lock 下看 queue，空就把 count 加 1；否则取出队头的 Waiter，放锁，对它的 semaphore release。谁先排进 queue 谁先被叫醒。Permit 是从释放者直接交给队头的，count 不经过加 1 再减 1，后来的 thread 抢不走它。

边界情况叫醒之后，Waiter 还在不在

Tutorial 7 在 release 那一行留了一个问题：“safe?” Waiter 是 acquire 的 local variable，住在等待者的 stack 上。release 对它的 semaphore 调用 release() 的那一刻，等待者就可能醒来、返回，Waiter 随 stack frame 一起销毁；而 binary_semaphore::release() 在把 counter 加 1 之后，还可能要访问这个 object 去唤醒睡着的 thread。这是 use-after-free 的风险。稳妥的做法是让 Waiter 住在 heap 上，由 std::shared_ptr 管理，queue 和等待者各持一份。这个回答是我写的，tutorial 没有给答案。

想当然的模型：sequential consistency

写并发 code 时脑子里默认的模型是 Lamport 1979 年给的定义：执行的结果，等于把所有 thread 的 operation 排成一个序列、每个 thread 自己的 operation 在序列里按 program order 出现时的结果。这叫 sequential consistency（SC）。开头第二件事的那个交错论证，用的就是 SC。

SC 的问题是它太贵。Compiler 和 hardware 都靠调换、合并、删除 memory operation 来提速，而这些优化只保证单个 thread 看不出区别。

Compiler：as-if rule

C++ 允许 compiler 对 code 做任何变换，只要单线程下可观察的行为不变，这叫 as-if rule。合法的变换包括：把 loop 里不变的 load 提到 loop 外面；调换两个无关的 store；把一串 store 合并成一个（第 1 站那条 addl $1000000）；删掉结果没人用的 load。

回到开头的 test2。flag 是普通的 int，test2 里没有任何 synchronization。Compiler 的推理是：如果有别的 thread 在 loop 运行期间写 flag，那就是 data race，program 是 undefined behaviour，不必考虑；所以可以假定 loop 里 flag 不会变。于是 while (flag == 0) {} 只有两种可能：一开始 flag != 0，loop 一次也不执行；或者一开始 flag == 0，loop 永远转下去。C++ 还规定，一个没有 I/O、没有 volatile 或 atomic access、没有 synchronization 的 loop 可以被假定终止（forward progress 的规则）。永远转下去的那种可能于是也被排除了，loop 就成了“什么也不做”，被删掉。a 和 b 的 load 也没有理由等，直接读，读到的是 0。

DRF-SC：一份约定

如果 programmer 必须对着这张表写 code，没人写得对。Adve 和 Hill 在 1990 年提出了一份约定，后来 Java（2004 年的新 memory model）和 C++11 都采用了它：

只要 program 没有 data race，它的每次执行都和某个 SC 的执行一样。

这叫 DRF-SC（data-race-free implies sequential consistency）。分工是：language 提供一组 synchronization operation（mutex 的 lock 和 unlock、atomic variable 的 operation、thread 的创建和 join），compiler 和 hardware 在它们周围不做越界的重排，必要时插入 fence；其余的普通 access 随便优化。Programmer 的责任只有一条：任何两个 conflicting access（同一个 location、至少一个 write）之间，都要被 synchronization 排出先后。

C++ 对违约的处理是最严厉的一种：有 data race 的 program 整个是 undefined behaviour，Russ Cox 称之为“DRF-SC or Catch Fire”。Java 则仍然给有 race 的 program 规定了有限的意思，因为 Java 要保证一个有 bug 的 program 也不能破坏 memory safety。

拿这份约定检查开头的 program。flag 有 race，所以 program 没有意思，-O2 打印 a=0 b=0 不违反任何规则。把 flag 改成 std::atomic<int>，a 和 b 保持普通的 int：

// test2: while (flag.load() == 0) {}  然后打印 a、b

flag 上的 access 都是 atomic 的，不构成 data race。a 的 write 在 test1 里排在 flag.store(1) 之前，test2 读到 1 的那次 flag.load() 和这次 store 之间建立了 synchronization，a 的 read 又排在 load 之后，所以 write 和 read 之间有先后，也不是 race。整个 program data-race-free，于是它的行为和某个 SC 执行一样，而 SC 下只能打印 a=1 b=1。用 g++ 13 -O2 实测，打印 a=1 b=1。第 4 站把“建立了 synchronization”说精确。

看起来对，其实不对x86 是 TSO，比较强，所以只在 x86 上跑的 C++ code 可以不管 memory model

开头的第一件事就发生在 x86 上：错误的结果是 compiler 造成的，没有用到任何 hardware 的重排。C++ 的 memory model 约束的是 compiler 和 hardware 两者合起来的行为，而 compiler 对 x86 和 ARM 一视同仁地依赖“没有 data race”这个假定。x86 的强只体现在 atomic 的成本上：第 4 站会看到，x86 上 release store 和 relaxed store 都是一条普通的 mov。

边界情况volatile 不是 synchronization

在 C++ 里，volatile 只要求 compiler 不删除、不合并对这个 variable 的 access，对开头的 loop 来说它确实能阻止 loop 被删掉。但它不建立任何 happens-before，两个 thread 对一个 volatile int 一读一写仍然是 data race，a、b 的可见性也不受它保护。Java 的 volatile 不同，它的语义接近 C++ 的 seq_cst atomic。

Relaxed：每个 variable 有一个 modification order

对一个 atomic variable x，所有对它的 write 排成一个所有 thread 都同意的 total order，叫 x 的 modification order（mo）。即使全用 relaxed，也有四条 coherence 规则：

  • write–write。 同一个 thread 里先写的，在 mo 里也在前。
  • read–read。 同一个 thread 先后两次读 x，后一次读到的不会比前一次在 mo 里更早。
  • read–write、write–read。 一个 thread 先读 x 再写 x，写入的值在 mo 里排在读到的值之后；先写再读，读到的不会早于自己写的。

不同 variable 的 mo 之间没有任何关系。Tutorial 2 的例子：Thread 1 依次 x.store 1、3、5、7、9，Thread 2 依次 store 0、2、4、6、8，Thread 3 和 Thread 4 各读 x 十次，全是 relaxed。哪组输出可能？

  • A。 Thread 3 读到 1 1 3 2 6 5 9 9 9 9，Thread 4 读到 0 1 4 6 8 5 9 9 9 9。
  • B。 Thread 3 读到 1 2 6 6 3 7 9 9 9 9，Thread 4 读到 1 1 3 4 8 9 9 9 9 9。

判断的办法：找一个 mo，同时满足两个 writer 的 program order（write–write）和每个 reader 读到的值不倒退（read–read）。A 可以取 mo 为 0 → 1 → 3 → 2 → 4 → 6 → 8 → 5 → 7 → 9：Thread 1 的 1、3、5、7、9 依次在第 2、3、8、9、10 位，Thread 2 的 0、2、4、6、8 依次在第 1、4、5、6、7 位，都是递增的；Thread 3 读到的 1、1、3、2、6、5、9 在第 2、2、3、4、6、8、10 位，Thread 4 读到的 0、1、4、6、8、5、9 在第 1、2、5、6、7、8、10 位，都不倒退。A 可能。

Release 与 acquire：把之前的 write 一起带过去

Relaxed 只管一个 variable。开头的 flag 问题需要的是：看到 flag 的新值时，也看到写 flag 之前写的 a、b。这要靠下面几个关系，Tutorial 2 给的定义是：

  • sequenced-before（sb）。 同一个 thread 里 program order 上的先后。
  • synchronizes-with（sw）。 一个带 release（或更强）的 store 写了 y，另一个 thread 里一个带 acquire（或更强）的 load 读 y，读到了这个 store 写的值（或者它的 release sequence 里后来的值，见下一节），那么这个 store synchronizes-with 这个 load。这个关系取决于这次执行里 load 实际读到了什么。
  • happens-before（hb）。 sb 和 sw 连起来的链：A sb B、B sw C、C sb D，则 A hb D。

hb 的作用有两条：hb 在一个 read 之前的 write，这个 read 能看到它或者 mo 里更新的值（write–read coherence 推广到跨 thread）；任何两个 conflicting access 只要有 hb 关系，就不是 data race。

Tutorial 2 的 Snippet A：

// Thread 1                                  // Thread 2
x.store(1, std::memory_order_relaxed); // a   while (y.load(std::memory_order_acquire) != 2) {}  // p
y.store(2, std::memory_order_release); // b   std::cout << x.load(std::memory_order_relaxed);    // q

Tutorial 2 接着问两个变化。

x 改成普通的 int。 a 和 q 是 conflicting access，但 a hb q，不是 data race，q 仍然读到 1。这就是 publish 一份普通 data 的标准写法：先写 data，再 release 一个 flag；对方 acquire 到 flag，再读 data。

去掉 while，只读一次 y。 如果这次读到的是 0，没有 sw，a 和 q 之间没有 hb，q 读到 0 或 1 都可以。如果 x 又是普通的 int，a 和 q 之间就成了 data race，整个 program 是 undefined behaviour。

// Thread 1                       // Thread 2
x.store(1, relaxed); // a          while (y.load(acquire) != 2) {}  // p
y.store(2, release); // b          print(x.load(relaxed));          // q
x.store(3, relaxed); // c          while (z.load(acquire) != 4) {}  // r
z.store(4, release); // d          print(x.load(relaxed));          // s

并集是 11、12、13、22、23、32、33 七种。21 不可能：1 在 2 之前（write–write），先读到 2 再读到 1 就倒退了。31 也不可能：先读 3 再读 1 要求 mo 里 3 在 1 之前，可那样 3 早于 1，hb 不允许第一次 read 读到它。

第 3 题加入了 RMW。RMW 的 read 和 write 在 mo 里必须相邻：它读到的一定是 mo 里紧挨在它自己前面的那个值。所以两个 fetch_add(1) 不可能读到同一个旧值，Tutorial 2 的 Snippet D 问“p 能不能也读 0 写 1”，答案是不能。

// Thread 1               // Thread 2                 // Thread 3
x.store(1, relaxed);      z.fetch_add(1, relaxed);    while (z.load(acquire) != 2) {}
z.store(1, release);                                  print(x.load(relaxed));

先问 program 一定会结束吗？不一定。如果 fetch_add 先执行，读 0 写 1，然后 z.store(1) 再写一次 1，z 的 mo 是 0 → 1 → 1，永远不会出现 2，Thread 3 一直转下去。

再问：如果 Thread 3 退出了 loop，一定打印 1 吗？是。退出说明读到了 2，2 只能由 fetch_add 写出，它读到的是 z.store(1) 写的 1，所以 mo 是 0 → 1（store）→ 2（RMW）。C++ 规定，一个 release store 之后，mo 里紧跟着的一串 RMW（不论哪个 thread 做的、不论什么 memory order）构成它的 release sequence；acquire load 读到这串里任何一个值，都和最前面那个 release store sw。所以 Thread 1 的 z.store sw Thread 3 的 load，x = 1 hb 那次 print，只能打印 1。

如果 Thread 2 改成先 z.load(relaxed)、再 z.store(2, release)，2 是一个普通 store 写的，它打断了 release sequence。Thread 3 读到 2 时只和 Thread 2 的 store sw，Thread 2 和 Thread 1 之间没有 sw（它的 load 是 relaxed 的），x = 1 不 hb print，可以打印 0。

Seq_cst：所有 seq_cst operation 一个 total order

Acquire/release 产生的 hb 边只来自“一个 read 读到了某个 write”。开头第二件事（store buffering）里，两个 read 都读到初值 0，没有读到任何 thread 的 write，于是一条 sw 也没有：

// Thread 1                     // Thread 2
x.store(1, release);            y.store(1, release);
r1 = y.load(acquire);           r2 = x.load(acquire);

(0,0)(0,0)(0,0) 在 acquire/release 下允许，正如 hardware 上那样。seq_cst 多一条规定：所有 seq_cst operation 排成一个所有 thread 都同意的 total order SSS，它和每个 thread 的 program order 一致，每个 seq_cst load 读到的是 SSS 里在它之前最后一个写同一个 variable 的值。把四个 operation 都改成 seq_cst：SSS 里第一个出现的是某个 store，不妨是 x.store(1)，那么 r2 = x.load() 在 SSS 里排在它后面，读到 1。所以 (0,0)(0,0)(0,0) 不可能。

// Thread 1         // Thread 2         // Thread 3                      // Thread 4
x.store(true);      y.store(true);      while (!x.load()) {}             while (!y.load()) {}
                                        if (y.load()) z.fetch_add(1);    if (x.load()) z.fetch_add(1);

全换成 acquire/release，zzz 可以是 0。Thread 3 和 Thread 4 读的是两个不同的 variable，没有一个所有人同意的“x 和 y 谁先写”：

Lock 的问题与 progress guarantee

Tutorial 4 列了 lock 的四个问题：deadlock；priority inversion（低 priority 的 thread 拿着 lock，高 priority 的 thread 只能等）；reliability（拿着 lock 的 thread 死掉，lock 永远不会被放掉）；performance（持有者被 scheduler 换下时所有人陪着等，critical section 里没有 parallelism）。不用 lock 的算法按保证的强弱分三级：

  • Wait-free。 每个 thread 的每次 operation 都在有限步内完成。
  • Lock-free。 任何时刻至少有一个 thread 在有限步内完成 operation（整个 system 在前进），个别 thread 可能一直失败重试。
  • Obstruction-free。 一个 thread 单独执行（别人都停住）时，有限步内完成。

Compare-and-swap

old = x.load(); x.store(old + 1); 不是正确的 increment，两步之间别人可以改 x（上一站的 x = x + 1）。这里能用 fetch_add，但大多数 data structure 的更新不是“加一个数”，需要一个更一般的 primitive：x.compare_exchange_weak(expected, desired)，在 x 等于 expected 时原子地把它换成 desired 并返回 true；否则不写，把 x 的当前值写回 expected，返回 false。

int increment(std::atomic<int>& x) {
    int v = x.load();
    while (!x.compare_exchange_weak(v, v + 1)) {}   // 失败时 v 已被更新成当前值
    return v;
}

_weak 版本允许 spurious failure：值相等也可能返回 false。在用 load-linked/store-conditional 实现 CAS 的 hardware（例如 ARM）上，这让它可以编成更短的 instruction 序列；反正在 loop 里，多转一圈无妨。_strong 版本不会 spurious failure，适合不在 loop 里的一次性判断。

Tutorial 4 问这个 loop 属于哪一级，答案是 lock-free，不是 wait-free。一个 thread 的 CAS 失败，说明在它 load 和 CAS 之间有别人的 CAS 成功了，system 在前进；但同一个 thread 可能每次都被别人抢先，一直失败。

Lock-free stack

Stack 只有一个入口 top，所有更新都是“改 top 这一个 pointer”，正好用 CAS：

struct Node { Job job; Node* next; };
std::atomic<Node*> top{nullptr};

void push(Job job) {
    Node* n = new Node{job, top.load(std::memory_order_relaxed)};
    while (!top.compare_exchange_weak(n->next, n,
                                      std::memory_order_release,     // 成功时
                                      std::memory_order_relaxed)) {} // 失败时 n->next 被更新
}

std::optional<Job> try_pop() {
    Node* old = top.load(std::memory_order_acquire);
    while (old && !top.compare_exchange_weak(old, old->next,
                                             std::memory_order_acquire,
                                             std::memory_order_acquire)) {}
    if (!old) return std::nullopt;
    Job j = old->job;
    delete old;        // 下面会看到这一行有问题
    return j;
}

Memory order 为什么这样标：push 先写普通的 n->job 和 n->next，再用 CAS 把 n 挂上 top；try_pop 读 top 得到 n，然后读 n->next 和 n->job。这正是上一站 publish 的形状，挂上去的 CAS 要 release，读 top 的 load 和 CAS（包括失败时，它会把新的 top 读进 old，下一圈要读 old->next）要 acquire。Tutorial 4 让学生先全写 relaxed，再找 race：push 写 next 和 try_pop 读 next、job 之间没有 hb，是 data race。修法就是上面的标法。

ABA

try_pop 的 CAS 只比较 top 的值。设 stack 从 top 往下是 A → B → C：

值从 A 变到别的再变回 A，CAS 看不出来，这叫 ABA problem。它的前提是 address 被重用：node 被 free 之后，allocator 很可能把同一块 memory 交给下一个 new。CS149 第 7 站用另一组 node 走过同样的过程。

修法是 generation counter：top 不只存 pointer，还存一个每次成功修改都加 1 的计数，CAS 同时比较两者。

struct Top { Node* ptr; std::uint64_t gen; };   // 16 byte
std::atomic<Top> top;
// pop 的 CAS：{old.ptr, old.gen} → {old.ptr->next, old.gen + 1}

A 回到 top 时 gen 已经从 0 变成 3，T1 拿着的是 gen 0，CAS 失败。16 byte 的 CAS 在 x86-64 上要用 cmpxchg16b（g++ 要加 -mcx16），否则 std::atomic<Top> 会退回用 lock 实现，可以用 top.is_lock_free() 检查。

什么时候可以 delete

即使没有 ABA，delete old 也有问题。T1 读到 old = A，正要读 old->next；T2 先一步 pop 掉 A 并 delete 了它。T1 读的是已经 free 的 memory：use-after-free。Lock-free 结构里，一个 node 离开了结构，并不代表没人还拿着指向它的 pointer。Tutorial 4 列出的办法：

  • 永远不 free（leak）。
  • 标记为待删，等所有 thread 都离开 data structure 时一起 free。
  • Reference counting（atomic 的 shared_ptr）。
  • Hazard pointer：每个 thread 在读一个 node 之前，先把它的 address 公布在自己的 hazard 槽里；被 pop 的 node 先放进 retire list，只有不在任何人 hazard 槽里的才 free（CS149 的讲法）。
  • Tutorial 用的办法：“recycling centre”。被 pop 的 node 不 free，push 进另一个 lock-free stack；new 之前先从这个 stack 取。

Recycling centre 让 node 的 memory 永远有效，use-after-free 没了；但它本身是一个 lock-free stack，有它自己的 ABA，所以也要加 generation counter。Tutorial 的 checkpoint 正是这样问的：“recycling centre 有 ABA”“要给它加 generation counter”这两句对。

Lock-free queue：每一步都对，整体不对

Tutorial 4 接着做了一个 multi-producer multi-consumer 的 queue：一条 linked list，末尾永远有一个空的 dummy node，back 指向它。

void enqueue(Job job) {
    Node* new_dummy = new Node{};
    Node* work = back.exchange(new_dummy, std::memory_order_acq_rel); // 抢到原来的 dummy
    work->job = job;                                                  // 把它变成真 node
    work->next.store(new_dummy, std::memory_order_release);           // 接上新 dummy
}

Consumer 从 front 开始：front->next 是空就说明 queue 空，返回 nullopt；否则 CAS 把 front 推到下一个，取走旧 front 的 job。

Tutorial 在修完 data race、ABA、use-after-free、recycling centre 里的 race 之后，ThreadSanitizer 已经不报错，又给出第五个问题：

为什么说这是错的？对一个并发的 data structure，标准的正确性要求是 linearizability（Herlihy 与 Wing）：每个 operation 好像在它调用和返回之间的某一瞬间一次性完成，这些瞬间排出的顺序，构成一个合法的 sequential 执行。Tutorial 把这叫 serializability，意思相同，都是拿“排成一列”来检验（排成一列的一般讲法见概念线“排成一列”）。

检验上图。T2 的 enqueue(34) 在 try_pop 调用之前已经返回，所以在任何排法里它都在 try_pop 之前。T1 的 enqueue(56) 还没返回，可以排在任何位置。两种情况：56 排在 try_pop 之前或之后，queue 里至少有 34，sequential 的 queue 不可能返回空。没有一种排法能解释这个 nullopt，所以这个 queue 不是 linearizable 的。根子在 T1 的一个 operation 分成了三步，中间那段时间 list 断开了，后面的 node 从 front 走不到。

Michael 和 Scott 1996 年的 queue 修好了这一点：back 只要求是“从 front 走得到的某个 node”，不要求是最后一个。Enqueue 先用 CAS 把新 node 接到真正的最后一个 node 的 next 上（这一步成功就算 enqueue 完成，list 从不断开），再用 CAS 把 back 推过去；任何 thread 发现 back->next 不空，说明有人接上了 node 却还没推 back，就替它推一下，这叫 helping。Tutorial 按两次 CAS 的成败分了四种情形：都成功是正常的 enqueue；接 next 失败、推 back 成功，是在帮别人；接上了但推 back 失败，是有人帮了自己；都失败就重来。

两个 atomic 不等于一个 atomic

AY24/25 期末的 Ticket Master 题，Q26 要用 atomic 写 reserveSeat，seat 有 atomic<bool> available 和 atomic<int> heldBy。示范解法先 available.compare_exchange_strong(true, false)，成功后再 heldBy.store(userID)。TA 在 Tutorial 10 指出：两个 variable 应该一起变或者都不变，而这里是两步。CAS 之后、store 之前，另一个 thread 看到 available == false，读 heldBy 却得到旧的值；如果它按 heldBy 判断“这个座位是不是我的”，结论就是错的。一种修法是只留一个 atomic：heldBy 用 −1-1−1 表示空座，heldBy.compare_exchange_strong(expected = -1, userID) 一步同时完成“检查空”和“记下是谁”。

看起来对，其实不对每一步都是 atomic operation，整个 operation 就是 atomic 的

x.load() 加 x.store(old + 1)、Tutorial 4 queue 的 exchange 加 store、Ticket Master 的 CAS 加 store，每一步单独都不可分割，组合起来都不是。正确性要的是整个 operation 能被看成在一瞬间完成；做法要么是把需要一起变的东西放进一个 CAS 里，要么像 Michael–Scott queue 那样，让中间状态对别人也是合法的、可以被别人接着完成。

Goroutine 与 unbuffered channel

go f() 启动一个 goroutine：一个由 Go runtime 调度的轻量执行流（OS 看不见它），很多个 goroutine 复用少数几个 OS thread。main 返回时整个 program 结束，不等其他 goroutine。

Goroutine 之间主要靠 channel 交换 data。Tutorial 5 引了 Rob Pike 的一句话：“Don't communicate by sharing memory; share memory by communicating.” 想法是：一份 data 在任一时刻只归一个 goroutine 所有，要给别人就通过 channel 送过去，没有两个 goroutine 同时碰它，也就没有 data race。

make(chan int) 是 unbuffered channel，没有存东西的地方。Send 要等到有人 receive 才完成，receive 要等到有人 send 才完成，两边在同一刻交接，叫 rendezvous。开头第三件事：

c := make(chan int)
c <- 1             // 等一个 receiver
fmt.Println(<-c)   // 永远走不到这里

main 在 c <- 1 上等 receiver，而唯一可能 receive 的就是 main 自己的下一行。Runtime 发现所有 goroutine 都在等，报 fatal error: all goroutines are asleep - deadlock!，并指出 goroutine 1 [chan send]。修法有两种：把 send 放进另一个 goroutine（go func() { c <- 1 }()），或者用 make(chan int, 1)，buffer 里有一个空位，send 放进去就完成。

Buffered channel、close 与 range

make(chan int, C) 是容量为 CCC 的 buffered channel：buffer 不满时 send 立即完成，满了才等；buffer 不空时 receive 立即完成，空了才等。

close(ch) 表示不会再有 send。之后的 receive 先取完 buffer 里剩下的值，然后立刻返回 element type 的 zero value；v, ok := <-ch 里 ok 为 false 表示 channel 已关且已空。for v := range ch 一直 receive，直到 channel 关闭且取空。Tutorial 5 的第二题：

ch := make(chan int)

fmt.Println(<-ch)
fmt.Println(<-ch)

输出永远是 1、1729、0、0。前两个 receive 和两个 send 一一交接，unbuffered channel 保证顺序；后两个发生在 close 之后，得到 zero value，不会 block。

另外两条规则：对已经 close 的 channel send 会 panic；close 一个已经 close 的 channel 也会 panic。Tutorial 5 留了一段没有说明的 code，两个 goroutine 各 c <- 1 再 close(c)，main 用 range 读。实测三次都是先打印 1，然后 panic: send on closed channel：第一个 goroutine 交接完就 close 了，第二个的 send 撞上了已关的 channel。如果两个 send 都先完成，就是第二次 close 时 panic。两种顺序都 panic，规则是：只由唯一的 sender 来 close，或者由协调者在确认所有 sender 结束之后 close。

第三题：

func producer(val int, c chan<- int) { c <- val; c <- val }

func main() {
    c := make(chan int)
    go producer(1, c)
    go producer(7, c)
    fmt.Println(<-c + <-c)
}

main 收两个值，各来自两个 producer 中的任意一个，可能是 (1, 1)、(1, 7)、(7, 1)、(7, 7)，打印 2、8 或 14。之后两个 producer 都可能卡在没人接收的 send 上，但 main 已经返回，program 照样结束。

Go memory model：channel 就是 happens-before

Channel 不只传值，也排顺序。Go 的 memory model 用的是和 C++ 同样的思路（happens-before、DRF-SC），synchronization 的规则写在 channel 和 lock 上：

  1. 一次 send synchronized before 对应的那次 receive 完成。
  2. 关闭 channel synchronized before 一次因为 channel 已关而返回 zero value 的 receive。
  3. 对 unbuffered channel，一次 receive synchronized before 对应的 send 完成。
  4. 对容量为 CCC 的 channel，第 kkk 次 receive synchronized before 第 k+Ck+Ck+C 次 send 完成。

规则 1 的例子：f 里先 a = "hello, world" 再 c <- 0，main 里 <-c 之后 print(a)。Write sb send，send sw receive 完成，receive sb print，一定打印 hello, world。规则 3 方向相反：f 里写 a 之后 <-c，main 里 c <- 0 之后 print(a)；unbuffered 时这也一定对，换成容量 1 的 channel 就不保证了，main 的 send 放进 buffer 就返回，不等 f。

规则 4 让 buffered channel 可以当 counting semaphore：容量是允许同时进入的数目，send 是 acquire，receive 是 release。Go 文档的例子，最多 3 个 work 同时执行：

var limit = make(chan int, 3)

func main() {
    for _, w := range work {
        go func(w func()) {
            limit <- 1   // 第 4 个 send 要等第 1 个 receive
            w()
            <-limit
        }(w)
    }
    select {}
}

Princeton COS 418 的 precept 用同一个想法写 mutex：容量为 1 的 channel 里预先放一个 token，Lock 是取走 token，Unlock 是放回去。还可以把 data 本身放进去：bank account 的 balance 存在容量为 1 的 channel 里，Withdraw 取出、减掉、放回，谁拿着这个值谁就是唯一的 owner。

没有这些规则保护的写法都是错的。Go 文档给的反例和开头第一件事是同一个形状：

var a string
var done bool

func setup() { a = "hello, world"; done = true }

func main() {
    go setup()
    for !done {}
    print(a)
}

done 不是 channel、不是 lock、不是 sync/atomic，main 看到 done == true 也不保证看到 a，甚至不保证 loop 会结束。Go 文档的建议很直接：如果要读完 memory model 才能弄懂你的 program，你就写得太聪明了。

1000 个 goroutine 加一个 counter

Tutorial 5 的第二部分：

count := 0
for i := 0; i < 1000; i++ {
    go func() { count++ }()
}
fmt.Println("Count: ", count)

实测五次：857、976、874、923、928。两个错误叠在一起：count++ 是 data race；main 不等 goroutine 结束就打印。go run -race 会报 WARNING: DATA RACE，指出两个 goroutine 在同一个 address 上的 read 和 write。

修法一：mutex 加 sync.WaitGroup。 wg.Add(1) 在启动 goroutine 之前调用，goroutine 结束时 wg.Done()，main 在 wg.Wait() 上等计数归零；count++ 包在 mu.Lock() 和 mu.Unlock() 之间。

修法二：把 counter 放进 channel 传来传去。 Tutorial 5 给了一个会 deadlock 的版本，这里取两个 goroutine：

ch := make(chan int)
var wg sync.WaitGroup
for i := 0; i < 2; i++ {
    wg.Add(1)
    go func() {
        count := <-ch
        count++
        ch <- count
        wg.Done()
    }()
}
ch <- 0
wg.Wait()
fmt.Println("Count: ", <-ch)

实测报 fatal error: all goroutines are asleep - deadlock!，goroutine 1 [sync.WaitGroup.Wait]，另一个 goroutine 停在 [chan send]。最后一个 goroutine 的 send 要等 main 来 receive，而 main 要等它 Done 之后才去 receive。改成 make(chan int, 1)：最后那次 send 放进 buffer 就完成，wg.Done() 得以执行，实测打印 Count: 2。

修法三：sync/atomic。 var count atomic.Int64，count.Add(1)，仍然要配 WaitGroup。

Select 与 context：让 goroutine 停下来

select 同时等几个 channel operation，哪个先能进行就执行哪个；同时有几个能进行时随机选一个。没有 default 时它会 block，有 default 时一个都不能进行就走 default，永不 block。Tutorial 5 的 producer 用它在“送出一个值”和“收到停止信号”之间二选一：

func producer(done chan struct{}, q chan<- int) {
    for {
        select {
        case q <- 1:
        case <-done:
            return
        }
    }
}

main 执行 close(done)，所有 producer 的 <-done 同时变得可以进行（规则 2），各自返回。用 close 而不是逐个 send，是因为 close 能一次通知任意多个 receiver。

context package 把这个模式标准化。ctx, cancel := context.WithTimeout(context.Background(), time.Second) 得到一个一秒后自动取消、也可以提前 cancel() 的 context，goroutine 在 select 里等 <-ctx.Done()。Context 组成一棵 tree，parent 取消时所有 child 跟着取消。Tutorial 5 的例子：ctx 4 秒 timeout，ctx2 := WithTimeout(ctx, 2s)，ctx3 := WithCancel(ctx) 由收到 signal 的 goroutine 调用 cancel。等 ctx2 的 goroutine 最晚 2 秒后醒来；等 ctx3 的 goroutine 在收到 signal 或 4 秒到时（parent 取消）醒来，哪个先到算哪个。Tutorial 列的退出条件有三类：外部要求停止；一起工作的另一个 goroutine 失败或被取消；timeout 或 deadline 到了。

AY24/25 期末 Load Balancer 的 Q28 问怎样优雅地停掉 server goroutine，答案正是这三样：一个 context.Context，server loop 的 select 里加一个 case <-ctx.Done(): return，再用 WaitGroup 等它们都退出。

Pipeline 与 fan-out：AY22/23 期末的 Go server

AY22/23 期末以 Linux 的 io_uring 为背景：request 进 submission queue（SQ），worker 处理后放进 completion queue（CQ），结果送回发出 request 的那个 client。Q29 要求用 channel 实现。

TA 的评注有三点。SQ 和 CQ 用 buffered channel，容量 SIZE 就是“最多积压多少 request”。每个 request 带着自己的 response channel，结果才能回到原来的 client，这比在 CQ 之后再查一张“request 属于谁”的表简单。示范解法在 for 里写了一个带 default: 的 select，channel 空着时它会不停地空转，白白占满一个 core，直接写阻塞的 receive 就行。

这是 pipeline（读、处理、写三段，用 channel 连起来）加 fan-out/fan-in（一个 SQ 分给 W 个 worker，W 个 worker 汇进一个 CQ）。最大的 concurrency 是 worker 的个数 W。

看起来对，其实不对Go 用 channel 通信，所以 Go program 不会有 data race

Go 只是提供了 channel，并不禁止共享 memory：closure 可以捕获外面的 variable，pointer 可以传给任何 goroutine。上面的 counter 就是 1000 个 goroutine 共享一个 count，实测结果是 857 到 976 之间的数。Go memory model 对 data race 的定义和 C++ 一样，有 race 的 program 可能出现非 SC 的结果。Go 比 C++ 多给的是 -race 这个 runtime 检测器，但它只能发现这次运行里实际发生的 race。

边界情况Loop variable 被 closure 捕获

Tutorial 10 和 MIT 6.5840 的讲义都提到这个坑：在 loop 里 go func() { use(i) }()，closure 捕获的是 variable i 本身，而不是启动时 i 的值。在 Go 1.22 之前，整个 loop 只有一个 i，goroutine 真正执行时读到的可能都是最后的值，而且这还是一个 data race。Go 1.22 起每次 iteration 有自己的一个 i，这个问题消失了；考试里遇到旧代码，要按题目给的版本判断，或者把值当参数传进去（go func(i int) {...}(i)），这在两种版本下都对。

Rust 保证什么

Tutorial 8+9 列的清单。Safe Rust 里不会发生：use-after-free 和 double free；越界访问（会检查并 panic）；无效的 reference、未初始化就使用；data race。仍然可能发生：deadlock、livelock、memory leak。办法是 compiler 在编译时检查，有时检查得过分保守，一些其实正确的 code 也会被拒绝。

Ownership 与 borrowing：编译期的 readers–writer lock

每个值在任一时刻只有一个 owner；把值传给 function 或赋给另一个 variable，ownership 就 move 过去，原来的名字不能再用。Owner 离开 scope 时值被 drop。只有一个 owner，就不会有两次 free。

不想交出 ownership 时可以 borrow：&T 是 shared reference，只能读，同时可以有任意多个；&mut T 是 exclusive reference，可以写，存在期间不能有任何别的 reference，连 owner 自己也不能用。这条规则和 readers–writer lock 是同一个形状：任意多个 reader，或者一个 writer。区别在于它在编译时检查，运行时没有任何开销。

对照 data race 的定义：两个 access 至少一个是 write、又同时发生。一个 write 需要 &mut，&mut 存在期间不可能有别的 access，于是 conflicting 的 access 不可能同时发生。这就是 safe Rust 没有 data race 的根本理由。

每个 reference 有一个 lifetime：从创建到最后一次使用。Tutorial 8+9 的例子：

let mut x = 1;
let y = &mut x;
x = 2;
*y += 1;

实测 compiler 报 error[E0506]: cannot assign to x because it is borrowed，并标出 borrow 的位置和“borrow later used here”。把 x = 2 移到 *y += 1 之后就能编译：那时 y 的 lifetime 已经结束。

thread::spawn 要 'static：E0373

把第 1 站的 counter 直接翻译成 Rust：

let mut counter = 0;
let t = thread::spawn(|| {
    counter += 1;
});
t.join().unwrap();
println!("{}", counter);

实测报 error[E0373]: closure may outlive the current function, but it borrows counter, which is owned by the current function，附注 function requires argument type to outlive 'static。thread::spawn 不知道这个 thread 会活多久，可能比 main 的 stack frame 还久，所以要求 closure 里的东西都是 'static 的，不能借用 local variable。这正是第 1 站那个“detach 之后 thread 还在读已经不存在的 stack”。Tutorial 8+9 给的两个问题也是这两个：thread 可能比 main 活得久，造成 use-after-free；main 和 thread 之间有 data race。

一种修法是 scoped thread：thread::scope(|s| { s.spawn(...); }) 保证 scope 结束前里面 spawn 的 thread 全部 join，所以它们可以借用 scope 外的 local variable。可是两个 scoped thread 都改 counter：

let mut counter = 0;
thread::scope(|s| {
    s.spawn(|| counter += 1);
    s.spawn(|| counter += 1);
});

报 error[E0499]: cannot borrow counter as mutable more than once at a time。两个 closure 各要一个 &mut counter，同时存在，违反 borrowing 规则。Compiler 在这里拒绝的，正是 C++ 里会编译通过的那个 data race。

Mutex<T>：锁住的是 data

Rust 的 Mutex<T> 把要保护的 data 放在 mutex 里面。lock() 返回一个 LockResult<MutexGuard<T>>，只有通过 guard 才能拿到 &mut T，guard 被 drop 时自动 unlock。不上锁就碰不到 data，这在 C++ 里只能靠约定。

let counter = Mutex::new(0);
thread::scope(|s| {
    for _ in 0..2 {
        s.spawn(|| {
            for _ in 0..1_000_000 {
                *counter.lock().unwrap() += 1;
            }
        });
    }
});
println!("{}", counter.into_inner().unwrap());

实测打印 2000000。这里两个 closure 都只借用了 &counter（shared reference），却能改里面的值。Tutorial 8+9 解释了原因：Mutex 里面是一个系统 mutex、一个 poison flag 和包在 UnsafeCell 里的 data，guard 用 UnsafeCell::get 取得 raw pointer 来改 data。这叫 interior mutability：compiler 在 UnsafeCell 这里放松了检查，由标准库的实现保证正确。Poison flag 的作用：一个 thread 拿着 lock 时 panic 了，data 可能停在一半的状态，mutex 被标为 poisoned，之后的 lock() 返回 Err，unwrap() 也就 panic。

Arc 与 Send/Sync

不用 scoped thread、用 thread::spawn 时，每个 thread 都要拥有一份 counter 的 ownership。Rust Book 的推导：直接 move 进第一个 closure，第二轮 loop 就报 E0382（value 已在上一轮被 move）；换成 reference counting 的 Rc<Mutex<i32>>，每个 thread 一份 clone：

let counter = Rc::new(Mutex::new(0));
let c = Rc::clone(&counter);
thread::spawn(move || { *c.lock().unwrap() += 1; });

实测报 error[E0277]: Rc<std::sync::Mutex<i32>> cannot be sent between threads safely，附注 the trait Send is not implemented for Rc<...>。Rc 的引用计数用普通的加减，两个 thread 同时 clone 或 drop，计数本身就有 data race。Arc（atomically reference counted）用 atomic 的 fetch_add 和 fetch_sub 维护计数，可以跨 thread：

Compiler 怎么知道 Rc 不行、Arc 行？靠两个 marker trait：

  • Send。 一个类型的值可以 move 到另一个 thread。
  • Sync。 一个类型可以同时被多个 thread 通过 shared reference 访问。精确的定义是：TTT 是 Sync 当且仅当 &T 是 Send。

它们是 auto trait：一个 struct 的所有 field 都是 Send，它自动是 Send；Sync 同理。thread::spawn 要求 closure 是 Send，closure 里装着一个 Rc，Rc 不是 Send，closure 也就不是，于是 E0277。几个例子：

类型 Send Sync 理由
Rc<T> 否 否 计数不是 atomic 的
Arc<T>（TTT 是 Send + Sync） 是 是 计数是 atomic 的
Cell<T>、RefCell<T> 是（TTT 是 Send 时） 否 改内部值、或检查 borrow 计数时没有 synchronization
Mutex<T>（TTT 是 Send） 是 是 访问 TTT 必须先拿 lock
MutexGuard<T> 否 是（TTT 是 Sync 时） 有的平台要求在 lock 的那个 thread 上 unlock
raw pointer 否 否 compiler 不知道它指向什么

手动给一个类型 unsafe impl Send 是允许的，unsafe 表示 programmer 自己担保它确实安全。

Atomic 与 Rayon

一个 connection 一个 thread 的代价

Tutorial 8+9 的 line echo server：client 发来文字，server 收到换行时把这一行发回去。Thread 版本对每个接受的 connection thread::spawn 一个 thread 跑 handle_client。TA 指出的问题：thread 都浪费在大部分时间在睡觉的 connection 上。一个 thread 有自己的 stack（Rust 的 std::thread 默认给 2 MiB），切换要进 kernel 保存和恢复整套 register；一万个空闲的 connection 就是一万个这样的 thread，而它们几乎都在 read 上等 network。

Async 的想法：把“等 I/O”从 thread 里拿出来。一个任务做到要等的地方就把自己挂起，交还 thread，等 I/O 就绪时再被接着执行；少数几个 thread 轮流执行成千上万个任务。

Future 与 poll

Rust 用一个 trait 描述“还没完成的计算”：

pub trait Future {
    type Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}

poll 推动它往前走一段：做完了返回 Poll::Ready(value)，要等返回 Poll::Pending。返回 Pending 之前，future 必须安排好在能继续时调用 cx 里那个 Waker 的 wake()；executor 收到 wake，才再 poll 它一次。所以 executor 不用轮询所有 future，只 poll 被 wake 过的。

Future 是 lazy 的。let f = async { println!("hi"); }; 只是造出一个 future，没有人 poll 或 .await 它，hi 永远不会打印（实测确实不打印）。这和 thread::spawn 一调用就开始跑完全不同。

async fn 是一个 state machine

async fn 被调用时返回一个 future，函数体里每个 .await 是一个可能挂起的点。Compiler 把函数体切成几段，生成一个 enum：每个 variant 是“停在哪个 .await”，里面存着跨过这个 .await 还要用的 local variable。poll 就是一个 match：根据当前 state 执行下一段，遇到子 future 返回 Pending 就把 state 存好、返回 Pending；执行到底就返回 Ready。

Tutorial 8+9 的例子 add_to_inbox：先读一条 message，再取 user（get_user 先查 cache，命中就不用查 database），最后加进 inbox。

挂起和恢复不需要保存 register 或切换 stack：state 都在这个 enum 里。一个 future 就是一个普通的值，大小在编译时确定。为这一页写了一个 async fn two()，里面先后 await 两个小的 async fn，std::mem::size_of_val(&two()) 实测是 16 byte。

一个 state 里存的 local variable 可能是对同一个 enum 里另一个 field 的 reference（比如一个 buffer 和指向它的 slice）。这个 future 一旦被 move 到别的 address，reference 就指向旧位置了。poll 的参数是 Pin<&mut Self>：通过它能改 future，但不能 move 它。所以 future 要先被 pin 住（例如 Box::pin）才能 poll。

Executor、tokio 与 spawn

标准库只定义 Future，执行 future 的 executor 由 crate 提供。课程用 tokio：一个多 thread 的 runtime，维护一个任务队列，各个 worker thread 从队列里取被 wake 的任务来 poll。#[tokio::main] 展开成“建一个 runtime，在它上面 block_on 这个 async 的 main”。

Echo server 的 async 版本，Tutorial 8+9 先写了这样一个 main：

#[tokio::main]
async fn main() -> std::io::Result<()> {
    let listener = TcpListener::bind("127.0.0.1:50000").await?;
    loop {
        let (socket, _) = listener.accept().await?;
        handle_client(socket).await?;
    }
}

TA 问“看出问题了吗”，答案是 server 一次只服务一个 client。main 本身就是一个任务，.await 的意思是“这个任务等到 handle_client 做完再往下走”。handle_client 要等 client 关掉 connection 才结束，在那之前 loop 回不到 accept。

修法是把每个 connection 交给一个新任务：

loop {
    let (socket, _) = listener.accept().await?;
    tokio::spawn(async move {
        let _ = handle_client(socket).await;
    });
}

tokio::spawn 立刻把 future 交给 runtime 调度并返回一个 JoinHandle，不等它完成；JoinHandle 本身也是 future，需要结果时 .await 它。Toronto ECE1724 的讲义强调了两者的区别：.await 是在当前任务里顺序地等，spawn 才产生并发。

Spawn 为什么要 Send + 'static

tokio::spawn 的 signature 要求 future 和它的 output 都是 Send + 'static。'static 的理由和 thread::spawn 一样：任务可能比调用者活得久。Send 的理由在于 tokio 的 worker thread 会 work-stealing：一个任务在某个 .await 挂起后，可能在另一个 thread 上被恢复，它的 state 要能 move 过去。

由此有一条具体的规则：一个不是 Send 的值不能跨过 .await 活着。tokio 文档的例子：在 spawn 的任务里用 Rc，只要它在 .await 之前已经被 drop 就能编译；如果 Rc 在 yield_now().await 之后还要用，它就会被存进 state machine 的某个 state，整个 future 不再是 Send，spawn 编译不过，报错类似“cannot be sent between threads safely”。同样的道理，std::sync::MutexGuard 不是 Send，拿着标准库 mutex 的 guard 跨过 .await 会被拒绝；需要跨 .await 持锁时用 tokio::sync::Mutex。

在 async code 里 block

Executor 的 worker thread 只有几个。一个任务在 poll 里执行了会 block 的 call，例如 std::thread::sleep、标准库的同步 I/O、长时间的纯计算，它占着的那个 worker thread 就不能去 poll 别的任务，排在这个 thread 上的所有任务都停住。Async 只在每个任务都“要等就返回 Pending”时才成立。所以 async code 里用 tokio::time::sleep 和 tokio 的 I/O；必须调用的 blocking 代码交给 tokio::task::spawn_blocking，它在另一个专门的 thread pool 上执行。

Tokio 的同步工具：H2O 与 mpsc

第 2 站的 H2O 在 tokio 里几乎原样搬过来：tokio::sync::Semaphore 和 tokio::sync::Barrier，只是 acquire() 和 wait() 都是 async 的，要 .await，等待时让出 thread 而不是 block。Tutorial 8+9 的 WaterFactory 把两个 semaphore 和一个 barrier 放进 struct，用 Arc 共享给 spawn 出来的 2n 个 hydrogen 任务和 n 个 oxygen 任务；acquire().await 返回一个 permit，permit 被 drop 时自动 release，和 C++ 的 scoped_lock 一样是 RAII。

AY22/23 期末的 Q30 要求 Rust 版的 io_uring server，SQ 和 CQ 用容量 100 的 tokio::sync::mpsc channel。TA 的评注：mpsc 是 multi-producer、single-consumer，只能有一个任务从 SQ receive，所以结构是：每个 connection 一个读任务往 SQ 送 request；唯一的 dispatcher 任务从 SQ 取出，每个 request spawn 一个任务去处理（fan-out），结果送进 CQ（fan-in）；写任务从 CQ 取出写回。最大的 concurrency 受 channel 容量限制。TA 还指出示范解法读 socket 时用了一个空的 Vec，capacity 是 0，read 永远读不到 data，要先分配好大小。

看起来对，其实不对把函数改成 async、调用处加上 .await，它们就会并发执行

.await 是“在这里等它做完”，同一个任务里的 .await 一个接一个执行，和同步 code 的顺序完全相同。上面第一版 echo server 就是这样：每个 handler 都是 async 的，server 仍然一次只服务一个 client。并发只来自 executor 同时持有多个任务：tokio::spawn，或者把几个 future 交给 tokio::join! 在同一个任务里交替 poll。
