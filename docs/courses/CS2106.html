Process：一个正在跑的 program

Disk 上的 program 只是一个 file，里面是 instruction 和初始的 data。把它跑起来，就多出了一堆只在运行时才有的东西：一片 memory（code、global data、heap、stack），CPU 里的 register（PC 指向下一条 instruction，SP 指向 stack 顶），以及打开的 file。这些合起来叫一个 process。同一个 program 可以同时跑成好几个 process，各有各的 memory 和 register。

OS 为每个 process 保存一份记录，叫 process control block（PCB）：process ID（PID）、当前 state、不在 CPU 上时那一组 register 的值、memory 的映射信息、打开的 file 列表。Process 不在 CPU 上的时候，它的全部“运行状态”就在 PCB 里。所有 process 的 PCB 合起来由 kernel 放在一张 process table 里。NUS 讲义把这些信息分成三类 context：memory context（code、data、stack、heap），hardware context（register、PC、SP、FP、PSW），OS context（PID、state、用了哪些资源）。

Memory context：stack frame 和 heap

Code 和 global data 的大小在 program 开始跑之前就定了。另外两块是因为运行时才出现的需要而存在的。

Stack。 看一个 function call：

int g(int a, int b) { int t = a * b; return t + 1; }
int f(int x)        { int y = g(x, 3); return y; }
int main(void)      { int r = f(5);  return r; }

f 调用 g 时要解决两类问题。Control flow：跳进 g 的 code，g 结束后还要回到 f 里调用的下一条 instruction，所以 f 的 PC（return address）必须存在某个地方。Data：要把 x 和 3 交给 g，要拿回 g 的 return value，g 还有自己的 local variable t。这些东西在调用时出现，返回时就没用了，而且后调用的先返回：g 一定比 f 先结束。这正好是 stack 的 LIFO 顺序。每次调用在 stack 上压一块，叫 stack frame，里面放 return address、argument、local variable、被保存的 register 和上一层的 frame pointer。

NUS 讲义描述的通用做法（具体顺序因 architecture 和 compiler 而不同）：

  1. Caller 准备。 f 把 argument x、3 放进 register 或压到 stack 上，再把 return PC 存到 stack 上，然后跳到 g。
  2. Callee 建 frame。 g 先把自己要用到的 register 原来的值存到 stack 上（之后要还给 f），保存旧的 FP，把 FP 设到自己 frame 里一个固定位置，在 stack 上为 t 留出空间，把 SP 调到新的栈顶。
  3. g 执行。
  4. Callee 拆 frame。 把 return value 放进约定的 register 或 stack 上的位置，恢复保存过的 register、旧的 FP 和 SP。
  5. 回到 caller。 用存着的 return PC 跳回 f，f 取走 return value，接着跑。

为什么除了 SP 还要 FP：g 执行中间还可能往 stack 上压东西（再调用别的 function、临时存 register），SP 一直在变，同一个 t 相对 SP 的距离也跟着变。FP 在 g 的整个执行期间不动，t 永远在“FP 往下第几个 word”，argument 永远在“FP 往上第几个 word”，compiler 生成的 code 用这个固定距离去取。

“被保存的 register”是因为 general purpose register 很少，f 在 g 返回后还要用自己放在 register 里的值；g 要用同一批 register，就得先把旧值存到 stack 上，返回前再写回去。Register 不够用时把值暂时放到 memory 里叫 register spilling。

Heap。 再看一个需要：

node *make_node(int v) {
    node *p = malloc(sizeof(node));
    p->value = v;
    return p;                 /* make_node 返回之后，这个 node 还要能用 */
}

这个 node 在运行时才分配，所以不能放进 data 区（data 的大小在 program 启动前就定了）；它要比 make_node 活得久，什么时候 free 由 program 决定、没有固定顺序，所以也不能放在 make_node 的 stack frame 里，frame 在 return 时就被拆掉了。这类 memory 放在 heap。Heap 比 stack 难管：每块大小不一，分配和释放的时机也没有规律，于是会出现第 5 站里那种零碎的空洞。

fork 与 exec

Unix 里新建 process 只有一个办法：fork()。它把调用者完整地复制一份，复制出来的叫 child，原来的叫 parent。

int x = 100;
int main(void) {
    pid_t pid = fork();
    if (pid == 0) {                 /* child */
        x = x + 1;
        printf("child: x = %d\n", x);
        exit(0);
    } else {                        /* parent */
        wait(NULL);
        printf("parent: x = %d, child pid = %d\n", x, pid);
    }
    return 0;
}

fork() 调用一次、返回两次：parent 和 child 都从 fork() 的返回处接着跑，区别只在 return value。Child 拿到 0，parent 拿到 child 的 PID。所以 if 的两个 branch 各被一个 process 走了。输出是

child: x = 101
parent: x = 100, child pid = 4242

（PID 的具体数由 OS 分配，4242 只是举例。）Child 把 x 改成了 101，parent 看到的仍然是 100：两个 process 的 x 在同一个 address 上，却是两份不同的 memory。wait(NULL) 让 parent 停下来等 child 结束，所以 child 的那行一定先打印。

NUS 讲义把 child 和 parent 的区别列成三样：PID、parent 的 PID（PPID），以及 fork() 的 return value。其余的 memory、打开的 file、register 都是复制来的。真去复制几 MB 的 memory 很慢，第 5 站会讲 OS 怎样用 copy-on-write 把这一步推迟到真正有人写的时候。

fork() 只会复制自己。要跑另一个 program，child 接着调用 exec()：把自己的 memory 整个换成另一个 program 的 code 和 data，从那个 program 的开头跑起。exec() 成功就不会返回，因为调用它的那段 code 已经不存在了。

为什么不把两件事合成一个“新建一个跑某 program 的 process”？xv6 book 给的理由是 shell 的 I/O redirection。在 shell 里输入 cat < input.txt，shell 先 fork()，child 在 exec("cat") 之前做两件事：close(0)，然后 open("input.txt")。open 总是返回最小的空闲 file descriptor，刚空出来的正是 0，于是 0 号 descriptor（standard input）指向了 input.txt。然后 exec("cat")，cat 照常从 0 号读，读到的就是这个 file。cat 自己对 redirection 一无所知，parent shell 的 descriptor 也没有被动过。分成两个 call，中间就留出了一段由 child 自己调整环境的空隙。

为什么不能直接调用 OS 的 function

Process 要读 file，最直接的办法是让它自己去操作 disk。可这样一来，file system 里记的 permission 就没有意义了：任何 process 都能绕过检查把整个 disk 读一遍。OS 必须让 process 不能自己做某些事，但能请 OS 代做。

硬件为此提供一个 mode bit。CPU 在 user mode 下跑 process 的 code，此时访问 I/O device、改 page table、关 interrupt 这类 privileged instruction 一执行就触发 exception，交给 OS 处理（通常是杀掉这个 process）。OS 的 code 在 kernel mode 下跑，什么 instruction 都能执行。

Process 请 OS 做事的入口叫 system call。它要同时完成两件事：切到 kernel mode，跳进 OS 的 code。危险在于“跳到哪里”：如果 process 可以指定 kernel 里的任意 address，它就能跳过 permission 检查，直接跳到“检查已通过”之后的那一行。所以跳转目标不由 process 决定。开机时 OS 在 kernel mode 下把一张 trap table 交给硬件，写明“发生 system call 时跳到哪个 handler、发生 timer interrupt 时跳到哪个 handler”。之后 process 执行一条 trap instruction（MIPS 里叫 syscall，RISC-V 里叫 ecall），硬件就按表跳转。Process 能选的只有 system call 的编号，放在约定的 register 里（MIPS 是 $v0，xv6 的 RISC-V 是 a7）。

以 write(1, buf, 3) 为例，走一遍：

  1. Program 调用 C library 里的 write，这是一个普通的 function call。和 system call 同名同参数的 library function（write、getpid）NUS 讲义叫 function wrapper；printf 这种先在 user mode 里排好格式、最后再调用 write 的，叫 function adapter。
  2. Library 把 write 的编号放进约定的 register，三个 argument 放进 argument register，然后执行 trap instruction。
  3. 硬件把 user 的 PC 等 register 存到这个 process 的 kernel stack 上，切到 kernel mode，跳到 trap table 里登记的 system call handler。
  4. Handler（NUS 讲义叫 dispatcher）拿编号当 index 找到 sys_write，检查 argument：1 号 descriptor 是否打开、buf 到 buf + 3 是否都在这个 process 自己的 memory 里。检查通过才去做。
  5. 把 return value 放进 return register，执行 return-from-trap：硬件从 kernel stack 恢复 register，切回 user mode，回到第 2 步那条 trap instruction 的下一条。Library 再用普通的 function return 把结果交回 program。

每个 process 除了 user stack，还有一个只在 kernel mode 下用的 kernel stack（xv6 里是 p->kstack）。第 3 步把 register 存在这里而不是 user stack 上，因为 user stack 的 SP 是 process 自己设的，可能指向任何地方。

看起来对，其实不对System call 就是一个普通的 function call，只是 function 写在 kernel 里

从 program 的角度看，write(1, buf, 3) 长得和 function call 一样，因为 library 把 trap 包在了 function 里面。但 CPU 做的事完全不同：跳转目标由 trap table 而不是 caller 决定；mode 从 user 切到 kernel；register 存到 kernel stack；kernel 要逐个检查 argument。如果它真是普通 call，buf 只要指向 kernel 自己的 memory，write 就会把 kernel 的 data 写到屏幕上。开销也不在一个量级：普通 function call 是几条 instruction；OSTEP 引用的测量里，1996 年的 Linux 一次 system call 约 4 µs，现在的机器也要零点几 µs，相当于几百到上千个 cycle。

Timer interrupt：OS 拿回 CPU 的唯一可靠办法

Process 在 CPU 上跑的时候，OS 的 code 没有在跑。OS 想做任何事，前提是 CPU 先回到它手里。如果只靠 process 自己做 system call 或者主动让出（cooperative 的做法），开头那个 while (1) { } 就永远不还。

解决办法还是硬件：一个 timer，每隔固定的时间发一次 interrupt。NUS 讲义把这个间隔叫 interval of timer interrupt（ITI），典型值 1 到 10 ms。Interrupt 和 trap 走同一套机制：硬件保存 register，切到 kernel mode，按 trap table 跳到 timer 的 handler。开机时设置 timer 和登记 handler 都是 privileged 的，process 关不掉它。每次 timer interrupt 之后 OS 都能重新决定让谁跑。分给一个 process 一次连续运行的时间叫 time quantum，它必须是 ITI 的整数倍，典型值 5 到 100 ms。例如 ITI 是 10 ms、quantum 是 20 ms，scheduler 每 10 ms 被唤醒一次，但每隔一次才真的换人。

能让 CPU 离开 process 的 code、跳进 OS 的事件，NUS 讲义分成两类。Exception 由正在执行的那条 instruction 自己引起，例如除以 0、overflow、访问非法 address、未对齐的 access，同一个 program 用同样的输入跑，每次都在同一个地方发生，所以是 synchronous 的。Interrupt 来自 CPU 外面的 device（timer 到点、disk 读完、按了一个键），和此刻在执行哪条 instruction 无关，是 asynchronous 的。上面那次 write 的 trap 是 process 有意触发的 exception；timer interrupt 属于后一类。两类都按 trap table 跳到各自的 handler，handler 的固定流程是：保存 register，做处理，恢复 register，return from interrupt。

Context switch：register 分两次存

OS 决定从 process A 换到 process B，就要把 A 的运行状态存起来、把 B 的装回去。OSTEP 第 6 章把一次 timer interrupt 引起的 switch 拆成两次保存：

  1. 硬件保存。 Timer interrupt 到来时，硬件把 A 的 user register（PC、SP 等）存到 A 的 kernel stack 上，切到 kernel mode，跳进 timer handler。
  2. OS 保存。 Handler 决定换成 B，调用 switch()：把 A 此刻在 kernel 里的 register 存进 A 的 PCB，从 B 的 PCB 里装回 B 的 kernel register，其中包括 SP，于是 stack 换成了 B 的 kernel stack。
  3. 回到 B。 执行 return-from-trap。硬件从当前的 kernel stack（已经是 B 的）恢复 user register，切回 user mode，从 B 上次被打断的地方接着跑。

第 3 步之所以能“回到 B 上次被打断的地方”，是因为 B 上一次离开 CPU 时，也走过同样的第 1、2 步。

Context switch 的代价有直接和间接两部分。直接的是保存和恢复 register、执行 scheduler 本身，OSTEP 引用的 1996 年测量约 6 µs，现在在 1 µs 以下。间接的是 cache：B 刚上来时，cache 里装的多半是 A 的 data，B 的前一段 access 大多是 miss（cache 的道理见 CS2100 第 8 站）。第 5 站会看到 TLB 也有同样的问题。

五个 state

一个 process 在它的一生里不是一直在 CPU 上。按“能不能马上跑”分成五个 state：

State 意思
New 刚创建，OS 还在为它准备 PCB 和 memory
Ready 什么都不缺，只等 CPU
Running 正在 CPU 上跑
Blocked 在等某件事（disk 读完、child 结束、key 被按下），给它 CPU 也没用
Terminated 已经结束，等 OS 回收

用上面的 fork 例子检验。Parent 执行 wait(NULL) 时 child 还没结束，parent 从 Running 进入 Blocked。Child 被 scheduler 选中，Ready 到 Running，打印，exit(0)，进入 Terminated。“child 结束”这个事件让 parent 从 Blocked 回到 Ready，等 scheduler 再选中它才回到 Running，打印第二行。

NUS 讲义给每条 transition 起了名字：create（无到 New）、admit（New 到 Ready）、switch（Ready 和 Running 之间的两个方向）、event wait（Running 到 Blocked）、event occurs（Blocked 到 Ready）。Ready 到 Running 的 switch 是 scheduler 选中了它；Running 到 Ready 的 switch 是它自己让出 CPU，或者 time quantum 用完被 timer interrupt 换下。在 Ready 的一堆 process 里选谁，就是第 2 站的问题。有 mmm 个 CPU 时，同一时刻最多 mmm 个 process 在 Running。

边界情况Child 先结束、parent 还没 wait：zombie

Child exit 之后，它的 memory 可以立刻回收，PCB 却不能，因为 exit status 和用掉的 CPU time 存在里面，parent 将来 wait 时要读。所以每个 process 在 exit 之后、parent wait 之前都处在只剩 PCB 的状态，叫 zombie；zombie 已经死了，kill 不掉它。Parent 一直不 wait，zombie 就一直占着 process table 的一项和一个 PID，积多了 process table 会满。反过来，parent 先结束，child 就成了 orphan，Unix 让 init（开机时由 kernel 建立、PID 为 1、所有 process 的共同祖先）当它的 parent，child 结束时由 init 来 wait。wait 在调用者还有 child 时 block 到其中一个结束；一个 child 都没有时立即返回 -1。

Kernel 的结构：monolithic、microkernel 与 virtual machine

上面 write 一路走进了 kernel 里的 sys_write。File system、device driver、scheduler、memory 管理这些 code 都在 kernel mode 下跑，任何一处有 bug 都可能写坏 kernel 的 data、让整台机器死掉。Kernel 里放多少东西，是 OS 设计的第一个取舍。

Monolithic kernel。 所有服务都在一个大的 kernel program 里，彼此直接用 function call 交互。大多数 Unix 和 Windows NT 是这样。一次 read 只需一次 trap 进 kernel，在 kernel 里调用 file system 的 function，再调用 disk driver，开销小；代价是模块之间没有隔离，一个 driver 写错一个 pointer 就能破坏 file system 的 data。Layered system 是它的一种变形：把 kernel 按层组织，每层只用下一层的服务，结构更清楚、更好 debug，但仍然都在 kernel mode 里。

Microkernel。 Kernel 只留最基本的东西：IPC、最底层的 scheduling 和 memory 管理、interrupt 处理。File system、driver 都做成在 user mode 下跑的 server process。Program 要读 file，就给 file system server 发一条 message，server 再给 disk driver server 发 message，结果再一路传回来。每一次 message 都要经过 kernel，一次 read 变成好几次 trap 和 context switch，比 monolithic 慢；换来的是隔离：driver 崩了只是一个 user process 崩了，可以重启它，kernel 本身不受影响。

Virtual machine。 OS 默认自己独占 hardware，在 kernel mode 下直接改 page table、开关 interrupt。想在一台机器上同时跑两个 OS（或者在一个随时可以重来的环境里测试一个可能把系统弄坏的 OS），就需要在 OS 下面再加一层软件，叫 hypervisor（virtual machine monitor），它模拟出一份 hardware 给每个 guest OS。Type 1 hypervisor 直接跑在 hardware 上，guest OS 之间不共享任何 host OS；type 2 hypervisor 作为普通程序跑在一个 host OS 上，要通过 host OS 去拿 CPU 和 memory，隔离性也弱一些。

waiting time=turnaround time−burst time\text{waiting time}=\text{turnaround time}-\text{burst time}waiting time=turnaround time−burst time
response time=first run time−arrival time\text{response time}=\text{first run time}-\text{arrival time}response time=first run time−arrival time

Priority scheduling 与 priority inversion

RR 对所有 job 一视同仁，可有些 job 就是更要紧：处理键盘输入的 process 比后台备份更该先跑。Priority scheduling 给每个 process 一个 priority 值，每次挑 priority 最高的 ready process。它有两种版本：preemptive 的，一个高 priority 的 process 一变成 ready 就立刻抢走 CPU；non-preemptive 的，它要等当前 process 自己让出，到下一轮 scheduling 才轮到。

Starvation。 只要高 priority 的 process 一直有活干，低 priority 的就永远轮不到，preemptive 版本尤其严重。NUS 讲义给的两个办法：正在跑的 process 每用完一个 time quantum 就把它的 priority 降一点；或者给正在跑的 process 一个 time quantum，用完之后下一轮不让它参加。讲义也指出，priority 只决定先后，很难用它精确控制一个 process 能拿到 CPU 的多少比例（这正是后面 lottery scheduling 要解决的）。

Priority inversion。 Priority 碰上 lock（第 3 站）会出一个更隐蔽的问题。三个 process，priority 从高到低是 H、M、L，preemptive：

  • L 在 t=0t=0t=0 到达，先跑 1 ms，在 t=1t=1t=1 拿到一个 lock R，接下来要在 R 里跑 4 ms，放掉 R 之后再跑 1 ms。
  • H 在 t=2t=2t=2 到达，一上来就要 R，拿到后跑 2 ms。
  • M 在 t=3t=3t=3 到达，不用 R，要跑 10 ms。

t=2t=2t=2 时 H 抢走 CPU，马上去拿 R，R 在 L 手里，H 进入 Blocked。L 接着跑。t=3t=3t=3 时 M 到达，M 比 L 高，抢走 CPU，一口气跑到 t=13t=13t=13。L 这时才回来，还剩 2 ms 的 critical section，到 t=15t=15t=15 放掉 R，H 才被叫醒，t=17t=17t=17 跑完。H 从 t=2t=2t=2 等到 t=15t=15t=15，共 13 ms，其中 10 ms 是在等一个 priority 比它低、和 R 毫无关系的 M：效果上 M 的 priority 比 H 还高了。这叫 priority inversion。

常用的修法是 priority inheritance：一个 process 拿着某个 lock 时，如果有更高 priority 的 process 在等这个 lock，持有者临时继承等待者的 priority，放掉 lock 后再降回去。同一个例子里，t=2t=2t=2 时 L 继承 H 的 priority，t=3t=3t=3 到达的 M 抢不走它；L 的 critical section 在 t=2t=2t=2 时已经跑了 1 ms，还剩 3 ms，于是 L 在 t=5t=5t=5 放掉 R、降回原来的 priority，H 在 t=5t=5t=5 到 t=7t=7t=7 跑完，然后才轮到 M（t=7t=7t=7 到 17）和 L 最后的 1 ms。H 只等了 3 ms，正是 L 剩下的那段 critical section。

MLFQ：不知道 burst 也能接近 SRT

SRT 要知道剩余时间，RR 不管长短一律平等，priority scheduling 的 priority 又要人事先定好。Multi-Level Feedback Queue（MLFQ）想做到：不预先知道 burst，靠观察 job 的行为自动给它定 priority。它有几个 priority 不同的 queue。NUS 讲义的规则是两条基本规则加三条调整 priority 的规则：

  1. Priority(A) > Priority(B)，A 跑。
  2. Priority(A) = Priority(B)，A 和 B 之间 RR。
  3. 新 job 进入最高 priority。
  4. Job 用满了它这一级的 time quantum，priority 降一级。
  5. Job 在 quantum 用完之前就主动让出或 blocked，priority 不变。

讲义说它的目标是同时把 I/O-bound process 的 response time 和 CPU-bound process 的 turnaround time 都压低。

OSTEP 第 8 章的例子，三级 queue，每级 q=10q=10q=10 ms。一个长的 CPU-bound job A 从最高一级进入，每用满一次 quantum 降一级，20 ms 之后就沉到最低一级。t=100t=100t=100 时来了一个要 20 ms 的短 job B，它进入最高一级，比 A 优先，立刻抢到 CPU；跑满 10 ms 降到中间一级，仍然高于 A，再跑 10 ms 就结束。B 的 turnaround 是 20 ms，和 SRT 下一样。一个每次只用 1 ms CPU 就去等 I/O 的 interactive job，永远在 quantum 用完前让出，按第 5 条一直留在最高一级，response 很好。短 job 和 interactive job 浮在上面，长 job 沉到下面，效果接近 SRT。

但这五条有两个漏洞。

Gaming。 一个 job 每次跑到 quantum 的 99% 时故意做一次无意义的 I/O，按第 5 条它永远留在最高一级，几乎独占 CPU。OSTEP 的修正是把第 4、5 条合并改写：记录 job 在这一级累计用掉的 CPU 时间，累计满了就降级，不管中间让出过几次。

Starvation。 高 priority 的 interactive job 一多，合起来就能占满 CPU，沉到最低一级的长 job 永远轮不到。修正是 priority boost：每隔一段时间 SSS，把所有 job 重新放回最高一级。SSS 没有理论上的最优值，OSTEP 说它要靠调；Solaris 的默认设置是 60 级 queue，quantum 从最高一级的约 20 ms 到最低一级的几百 ms，大约每秒 boost 一次。

Lottery scheduling：按比例分

另一种思路是直接规定每个 process 应该得到 CPU 的多少比例。给每个 process 发一些 ticket，每次 scheduling 随机抽一张，抽中谁就跑谁一个 quantum。A 有 75 张、B 有 25 张，每次 A 被抽中的 probability 是 0.75。跑 100 个 quantum，A 得到的个数服从 binomial distribution，expectation 是 100×0.75=75100\times0.75=75100×0.75=75，standard deviation 是 100×0.75×0.25≈4.3\sqrt{100\times0.75\times0.25}\approx4.3100×0.75×0.25​≈4.3，所以 A 大致拿到 71 到 79 个。比例越长期越准。NUS 讲义列的三个好处都从“ticket”这个记法直接得来：responsive，新 process 进来，下一次抽签就有它的份；可控，重要的 process 多发 ticket，一个 process 也可以把自己的 ticket 分给它的 child，每种资源（CPU、某个 I/O device）还可以各发一套 ticket；实现简单，只要一个 random number 和一次查找。

两个 process 怎样交换 data

第 1 站里 parent 和 child 的 x 是两份，各改各的。可很多任务需要合作：shell 把 ls 的输出交给 wc，web server 的几个 worker 共用一个 cache。Process 之间交换 data（inter-process communication，IPC）有两条路。

Shared memory。 P1 请 OS 建一块 shared memory region M，P2 把 M attach 进自己的 address space，之后两边读写 M 就像读写自己的 memory，写进去的值对所有 attach 了 M 的 process 都可见。OS 的做法是让两个 process 的 page table 把同一块 physical memory 映射进各自的 address space（第 5 站讲 page table）。Unix 的 System V 接口正好对应这几步：shmget 建立或找到 region、返回它的 id，shmat 用 id 把它 attach 进来、返回一个 pointer，shmdt detach，shmctl 销毁（只需要一个 process 做，而且要等没人再 attach 着）。

只有建立和 attach 两步要进 kernel，之后的读写是普通的 load 和 store，不经过 kernel，不复制，什么类型、多大的 data 都能直接放。代价是两边可能同时改同一个地方，必须自己做 synchronization，这正是这一站的问题。

Message passing。 P1 准备一条 message，用 send 交给 kernel，kernel 把它存在 kernel memory 里，P2 用 receive 取走。send 和 receive 都是 system call。要定的有两件事。

  • Naming：direct communication 是 send(P2, msg)、receive(P1, msg)，双方要知道对方是谁，每一对 process 之间一条 link；indirect communication 是往一个 mailbox（port）里 send(MB, msg)、从里面 receive(MB, msg)，一个 mailbox 可以被很多 process 共用。
  • Synchronization：blocking（synchronous）的 receive 在没有 message 时让 receiver 进入 Blocked，blocking 的 send 让 sender 一直等到 message 被收走；non-blocking（asynchronous）的 send 立即返回，receive 有 message 就拿，没有就返回一个“还没有”的标记。Blocking 版本自带了同步，写起来简单，但可能等很久；non-blocking 版本不卡住，但 program 要自己处理“还没好”的情况，写不好就变成反复去查的 busy waiting。

Message passing 不用担心两边同时改同一份 data，因为 data 由 kernel 排好队交过去，换一台机器、换一种 OS 也容易实现。代价是每传一次都要两次 system call，data 还要先复制进 kernel、再复制出来，message 的大小和格式也受限制。

Unix pipe。 最常见的 message passing。pipe(p) 得到两个 file descriptor，p[1] 是 write end，p[0] 是 read end，写进去的 byte 按顺序读出来，中间的 buffer 在 kernel 里。NUS 讲义把它描述成一个有界的 circular byte buffer，自带 synchronization：buffer 满了 writer 等，buffer 空了 reader 等。这和第 4 站的 bounded buffer 是同一个问题，只是 kernel 替你做好了。

Shell 执行 ls | wc 时先建 pipe 再 fork 两次。第一个 child 执行 close(1) 再 dup(p[1])：dup 把参数复制到最小的空闲 descriptor 上，刚空出来的正是 1，于是 standard output 变成了 pipe 的 write end；然后 exec("ls")。第二个 child 用同样的办法把 0 换成 p[0]，然后 exec("wc")。dup2(p[1], 1) 一步做完这两件事。这和第 1 站 cat < input.txt 是同一个办法。xv6 book 提醒了一个细节：wc 那一边必须 close 掉自己手里多余的 p[1]，因为 pipe 只有在所有 write end 都关掉之后才会让 reader 读到 end-of-file，wc 自己拿着一个 write end，就会永远等下去。

Unix signal。 还有一种只传“发生了什么事”、不传 data 的方式：signal 是发给 process 的 asynchronous notification，例如按 Ctrl-C 时 terminal 给前台 process 发 SIGINT，访问非法 address 时 kernel 发 SIGSEGV。收到 signal 的 process 要么执行默认的 handler（多半是结束 process），要么事先用 signal(SIGINT, handler) 换成自己的 function，handler 收一个 int（signal 的编号）、返回 void。不是所有 signal 都能换：SIGKILL 不能被捕获，所以 kill -9 一定能结束一个 process。

Thread：一个 process 里的多个执行流

如果合作的双方本来就是同一个 program 的两部分，用两个 process 再搭 shared memory 就太绕了：fork 要复制整个 process，context switch 要换掉整套 memory context，交换 data 还要走 IPC。Thread 是更直接的做法：一个 process 里跑多个执行流，共享同一个 address space。

同一个 process 的 thread 之间
共享 memory context（code、global data、heap），OS context（PID、打开的 file）
各有一份 thread ID，register（包括 PC、SP、FP），stack

每个 thread 有自己的 PC，所以能各自走到 code 的不同位置；有自己的 stack，所以 local variable 互不干扰。Global variable 和 heap 是共享的。同一个 process 里的两个 thread 之间切换只需换 register 和 stack pointer，memory context 不用动。NUS 讲义列的好处是 economy（比多个 process 省资源）、resource sharing（不需要 IPC）、responsiveness 和 scalability（能用上多个 CPU）。

Thread 也让几个 process 层面的 operation 变得含糊，NUS 讲义举的 Linux 的做法是：一个 thread 调用 fork，child process 里只有这一个 thread；任何一个 thread 调用 exit，整个 process 连同所有 thread 都结束；一个 thread 调用 exec，整个 process 的 image 被换掉，其余 thread 也就没了。多个 thread 还可能同时执行 system call，kernel 自己也要能正确处理这种并发。

User thread 与 kernel thread

Thread 可以由两个层次来实现，区别在 kernel 知不知道它们。

User thread。 Thread 由 process 里的一个 user-level library 实现，thread 的建立、切换、scheduling 都是普通的 function call，kernel 只看到一个 process。好处是任何 OS 上都能用、操作很快、可以自定 thread 的 scheduling policy。坏处来自“kernel 不知道”：一个 process 里有 4 个 user thread，其中一个调用 read 去读 disk，kernel 看到的是这个 process 发起了一个要等的 system call，把整个 process 放进 Blocked，另外 3 个本来能跑的 thread 也一起停住；机器有 4 个 core，kernel 也只会把这个 process 放到 1 个 core 上，4 个 thread 只能轮流用这一个。

Kernel thread。 Thread 由 kernel 实现，kernel 除了 process table 还维护一张 thread table，按 thread 来 scheduling。上面那种情况里，读 disk 的 thread 进入 Blocked，其余 3 个照样可以被 schedule，而且可以同时在不同的 core 上跑。代价是每个 thread operation 都是 system call，更慢；功能由 kernel 定死，对简单的 program 太重，对复杂的 program 又可能不够灵活。

Hybrid。 两种都有：kernel 只 schedule kernel thread，user thread 再绑定到 kernel thread 上，一个 process 能同时用几个 kernel thread 由它自己（或 OS 的限制）决定。

POSIX thread（pthread）只规定 API 和行为，不规定用哪一种实现。pthread_create(&tid, attr, start, arg) 建一个 thread 去执行 start(arg)，成功返回 0；thread 用 pthread_exit(value) 或从 start return 结束；pthread_join(tid, &status) 等那个 thread 结束并取回它的 exit value。编译时加 -lpthread。

几个名词：

  • 结果取决于各 thread 执行的先后时机，叫 race condition。
  • 访问共享 data、不能有两个 thread 同时在里面执行的那段 code，叫 critical section。这里就是那三条 instruction。
  • 保证同一时刻最多一个 thread 在 critical section 里，叫 mutual exclusion。

NUS 讲义要求一个正确的 critical section 方案满足四条：

  1. Mutual exclusion。 一个 thread 在 critical section 里时，其他 thread 都进不去。
  2. Progress。 里面没人、又有 thread 想进时，必须有一个能进去。
  3. Bounded wait。 一个 thread 提出要进之后，别人插到它前面进去的次数有上限。
  4. Independence。 不在 critical section 里的 thread 不能挡住别人进去。

同步写错时的症状也有三种名字。Deadlock：所有相关的 thread 都 blocked，谁也不再前进。Livelock：thread 为了避开 deadlock 不停地改变状态（放下、重试、再放下），一直在动，却没有进展。Starvation：别的 thread 都在前进，某几个 thread 永远拿不到需要的东西。

几个看起来对的办法

下面每个办法都只违反四条中的某一条，看清楚是哪一条，就知道 Peterson's algorithm 为什么要写成那样。

关掉 interrupt。 进 critical section 前关 interrupt，出来再开。单个 CPU 上，没有 interrupt 就没有 context switch，确实不会被打断。但关 interrupt 是 privileged instruction，让任意 program 执行它，一个 while (1) 就能重新独占机器（第 1 站的问题又回来了），一个有 bug 的 critical section 出了 exception 没有重新开 interrupt，整个系统就停住；在多个 CPU 上它也没用，别的 CPU 照样在跑另一个 thread。所以它只用在 OS 自己内部很短的地方。

用一个 lock variable。

int flag = 0;
void lock(void)   { while (flag == 1) ; flag = 1; }
void unlock(void) { flag = 0; }

看起来对，其实不对用一个 flag variable当 lock 就行：看到 0 就设成 1 进去，别人看到 1 就会等

“看 flag”和“设 flag”是两步，interrupt 可以落在中间。OSTEP 给的 interleaving，flag 从 0 开始：

步 Thread 1 Thread 2 flag
1 while (flag == 1)：读到 0，不等 0
2 （interrupt，换到 Thread 2） 0

两个 thread 都在里面了，违反的是 mutual exclusion。这个 lock 本身就有 race condition：保护 counter 的问题原样转移到了保护 flag 上。

轮流：一个 turn variable。 让两个 thread 按 turn 轮流进：

int turn = 0;
/* Thread 0 */                    /* Thread 1 */
while (turn != 0) ;               while (turn != 1) ;
/* critical section */            /* critical section */
turn = 1;                         turn = 0;

turn 任何时刻只有一个值，最多一个 thread 能通过 while，mutual exclusion 成立。问题在于它强制严格交替。Thread 0 进出一次之后 turn = 1；如果 thread 1 此后很长时间都在做别的事、根本不想进 critical section，thread 0 想再进一次就只能一直等。挡住 thread 0 的是一个不在 critical section 里的 thread，违反 independence（也违反 progress：里面没人，想进的进不去）。

各自表态：一个 want 数组。 改成每个 thread 先说“我想进”，再看对方想不想：

int want[2] = {0, 0};
/* Thread 0 */                    /* Thread 1 */
want[0] = 1;                      want[1] = 1;
while (want[1]) ;                 while (want[0]) ;
/* critical section */            /* critical section */
want[0] = 0;                      want[1] = 0;

Thread 1 不想进时 want[1] == 0，thread 0 直接进，independence 有了。可是 thread 0 执行完 want[0] = 1 就被 interrupt 打断，thread 1 执行 want[1] = 1，之后两边的 while 都看到对方是 1，谁也过不去，永远等下去：deadlock。

两次失败各缺一样：turn 能在两人相争时裁决，但会拦住没在争的人；want 只在对方真想进时才拦，但两人同时想进时没有裁决。Peterson 把两样合在一起。

Peterson's algorithm

两个 thread（编号 0 和 1）只用普通的 load 和 store 也能做到 mutual exclusion。沿用上面的两样东西：want[i] 表示 thread iii 想进去，turn 表示两个都想进时让谁。

int want[2] = {0, 0};
int turn;

void lock(int self) {              /* self 是 0 或 1 */
    int other = 1 - self;
    want[self] = 1;                /* 我想进 */
    turn = other;                  /* 但先让你 */
    while (want[other] == 1 && turn == other)
        ;                          /* 你也想进、而且轮到你：等 */
}
void unlock(int self) { want[self] = 0; }

Mutual exclusion 的证明。 假设 thread 0 和 thread 1 同时在 critical section 里。两个都执行过 turn = other，turn 只有一个值，看谁最后写的。不妨设 thread 0 最后写，它写的是 turn = 1。此后在两人都离开 critical section 之前，没有人再写 turn，所以 thread 0 做 while 判断时 turn == 1，turn == other 成立。Thread 0 要能通过 while，就必须读到 want[1] == 0。可是 thread 1 在写 turn 之前已经写了 want[1] = 1，那发生在 thread 0 写 turn 之前，也就在 thread 0 判断之前；thread 1 进了 critical section 还没出来，want[1] 仍然是 1。Thread 0 读到的只能是 1，过不去，矛盾。设 thread 1 最后写也一样。所以两人不可能同时在里面。

另外三条也满足。Progress 和 independence：只有一个 thread 想进时，want[other] == 0，它立刻通过，不想进的 thread 挡不住它。两个都想进时，turn 只有一个值，至少一个的 while 条件不成立，不会像 want 数组那样一起卡住。Bounded waiting：thread 1 出来后如果马上又想进，它会重新执行 turn = 0，把机会让给正在等的 thread 0，所以 thread 0 最多被插队一次。

把 counter = counter + 1 包在 lock(self) 和 unlock(self) 之间，上面那种重叠就不可能发生，结果是 20,000,000。

NUS 讲义写明了它依赖的假设：对 turn 的写入是 atomic 的。它的局限：还是 busy waiting；只适用于两个 thread，不容易推广；写法很底层，容易错；另外，OSTEP 指出现代 CPU 为了速度会调换 load 和 store 的顺序，上面证明里“先写 want 再写 turn”在 hardware 上不一定成立，不加 memory barrier 就会失效。

Hardware 的帮助：TestAndSet

Lock variable 失败是因为“读旧值”和“写新值”是两步。如果 hardware 保证这两步不可分割（atomic），问题就没了。TestAndSet 就是这样一条 instruction：

/* hardware 一步完成，中间不会被打断，也不会被别的 CPU 插进来 */
int TestAndSet(int *p) { int old = *p; *p = 1; return old; }

void lock(int *L)   { while (TestAndSet(L) == 1) ; }
void unlock(int *L) { *L = 0; }

Lock 空着时 *L == 0。几个 thread 同时执行 TestAndSet，hardware 让它们一个一个来，只有第一个拿到旧值 0 并把它设成 1，其余拿到的都是 1，继续转圈。这种一直转圈检查的 lock 叫 spin lock。

它满足 mutual exclusion。Bounded wait 要看怎么理解：OSTEP 的评价是 simple spin lock 没有任何 fairness 保证，谁抢到全看时机，一个 thread 在激烈竞争下可能一直抢不到；NUS 讲义（据两份学生笔记）把 TestAndSet 列为一个可用的 critical section 实现，指出的缺点是 busy waiting。考 NUS 的题时，把“busy waiting、浪费 CPU”作为它的主要问题；被问到 starvation 时，能说出上面这种一直抢不到的情形。同类的 atomic instruction 还有 compare-and-exchange、atomic swap、load-link / store-conditional，大多数 CPU 都提供其中几种。在单个 CPU 上它还很浪费。设 q=10q=10q=10 ms，4 个 thread 抢同一个 lock，持有者在 critical section 里被 timer interrupt 换下。另外 3 个 thread 依次上来，各自把整个 quantum 都花在 while 里转圈，因为持有者不上 CPU 就不会 unlock。持有者再次拿到 CPU 之前，白白浪费了 3×10=303\times10=303×10=30 ms。

所以等待的 thread 不应该转圈，应该进入 Blocked，让出 CPU，等 lock 被释放时再被叫醒。这就是下一站 semaphore 做的事。

边界情况多个 CPU 上 spin lock 反而合适

Critical section 通常只有几条 instruction。持有者在另一个 CPU 上跑着，马上就会 unlock，这时转几圈比做一次 context switch（第 1 站，微秒量级）便宜。OSTEP 的结论是：thread 数和 CPU 数差不多时，spin lock 表现不错。

Producer–consumer：三个 semaphore 各管一件事

Producer 不断产生 item 放进一个有 KKK 个 slot 的 buffer，consumer 不断取出。有三个约束：buffer 满了 producer 要等；buffer 空了 consumer 要等；改 buffer 的 index 时两边不能同时改。每个约束用一个 semaphore：

item buf[K];  int in = 0, out = 0;
semaphore mutex = 1;          /* 改 buf、in、out 时 mutual exclusion */
semaphore notFull = K;        /* 空 slot 的个数 */
semaphore notEmpty = 0;       /* 装了 item 的 slot 的个数 */

void producer(void) {
    while (1) {
        item x = produce();
        wait(notFull);
        wait(mutex);
        buf[in] = x;  in = (in + 1) % K;
        signal(mutex);
        signal(notEmpty);
    }
}

void consumer(void) {
    while (1) {
        wait(notEmpty);
        wait(mutex);
        item x = buf[out];  out = (out + 1) % K;
        signal(mutex);
        signal(notFull);
        consume(x);
    }
}

取 K=2K=2K=2，producer 先连跑三轮，然后 consumer 取一次：

看起来对，其实不对两个 wait 只是先后，顺序无所谓

把 producer 的两行换成先 wait(mutex) 再 wait(notFull)。仍取 K=2K=2K=2，buffer 已满：notFull = 0，notEmpty = 2，mutex = 1。Producer 执行 wait(mutex)，mutex 变 0；再执行 wait(notFull)，S=0S=0S=0，Blocked，手里还拿着 mutex。Consumer 执行 wait(notEmpty)，2 变 1，通过；执行 wait(mutex)，mutex 是 0，Blocked。现在 producer 等 consumer 腾出 slot，consumer 等 producer 释放 mutex，两边都永远等下去。原来的顺序先确认有空 slot、再拿 mutex，拿着 mutex 的人不会去等别的东西。

Readers–writers：允许多个 reader，writer 独占

很多共享的 data structure 大部分时间只是被读：几个 thread 同时读完全没问题，只有写的时候必须独占。用一个 mutex 把读也锁起来，读和读之间也要排队，浪费了 concurrency。NUS 讲义的 readers–writers 问题：reader 可以一起读 data structure D，writer 写 D 时必须一个人在里面。

NUS 讲义给的第一个写法用一个 binary semaphore roomEmpty 表示“D 里没人”，再用一个计数 nReader 和保护它的 mutex：

semaphore roomEmpty = 1, mutex = 1;
int nReader = 0;

void writer(void) {
    wait(roomEmpty);
    /* 写 D */
    signal(roomEmpty);
}

void reader(void) {
    wait(mutex);
    nReader++;
    if (nReader == 1) wait(roomEmpty);   /* 第一个进来的 reader 替所有 reader 占住房间 */
    signal(mutex);

    /* 读 D */

    wait(mutex);
    nReader--;
    if (nReader == 0) signal(roomEmpty); /* 最后一个离开的 reader 把房间让出来 */
    signal(mutex);
}

Writer 必须拿到 roomEmpty 才能写，于是写的时候不可能有 reader，也不可能有别的 writer。Reader 之间不互相等：只有第一个 reader 去拿 roomEmpty，后面的 reader 只是把 nReader 加 1 就进去了。

走一遍，看这个写法的毛病。R1、R2、R3 是 reader，W 是 writer：

事件 nReader roomEmpty 谁在读 W
R1 进来：第一个 reader，wait(roomEmpty) 1 0 R1
R2 进来：不是第一个，直接进 2 0 R1 R2
W 来了：wait(roomEmpty)，S=0S=0S=0，Blocked 2 0 R1 R2 睡着
R1 离开 1 0 R2 睡着
R3 进来：nReader 从 1 变 2，不用等 2 0 R2 R3 睡着
R2 离开 1 0 R3 睡着

（最后一行 Signal 把 roomEmpty 从 0 变 1，W 完成 Wait 又把它变回 0。）W 在第三行就来了，却一直等到所有 reader 都走光。只要新的 reader 总在旧的离开之前到达，nReader 就永远不会回到 0，W 永远写不了：writer starvation。

修法是让一个正在等的 writer 挡住后来的 reader。加一个 semaphore turnstile = 1，reader 进门前先穿过它：wait(turnstile); signal(turnstile);，再做原来的事；writer 则先 wait(turnstile)，拿着它去 wait(roomEmpty)，写完再依次 signal(turnstile)、signal(roomEmpty)。W 一旦拿到 turnstile，后来的 reader 都卡在门口，房间里已有的 reader 读完就走，nReader 一定会降到 0。上表里 R3 在 W 之后到达，这时它会停在 turnstile 上，R2 离开时 W 就能进去。

Deadlock

上面这种“每个人都在等另一个人手里的东西”叫 deadlock。它不是罕见的毛病：OSTEP 引用 Lu 等人对 MySQL、Apache、Mozilla、OpenOffice 的研究，105 个 concurrency bug 里有 31 个是 deadlock。

最小的例子是两个 thread、两个 lock，拿的顺序相反：

/* Thread 1 */            /* Thread 2 */
lock(L1);                 lock(L2);
lock(L2);                 lock(L1);

Thread 1 拿到 L1 之后被换下，Thread 2 拿到 L2。接着 Thread 1 等 L2，Thread 2 等 L1，谁都不会放手。

Deadlock 要四个 condition 同时成立（Coffman 等人）：

  1. Mutual exclusion。 资源一次只能给一个 thread。
  2. Hold and wait。 Thread 拿着已有的资源，同时等新的。
  3. No preemption。 资源不能从持有者手里强行拿走。
  4. Circular wait。 存在一圈 thread，每个都在等下一个手里的资源。

四个缺一个就不会 deadlock，所以 prevention 就是挑一个打破。

Dining philosophers：拆掉 circular wait

五个 philosopher 围坐一桌，相邻两人之间放一根 chopstick，一共五根。吃饭要同时拿起左右两根。每个人的做法都是先拿左边、再拿右边。

如果五个人同时拿起左边那根，每人手里一根，都在等右边那根，而右边那根在右边邻居手里。五个人围成一圈，四个 condition 全部成立。

打破 circular wait 的办法是给所有资源定一个 total order，规定每个 thread 只能按从小到大的顺序拿。把 chopstick 编号 0 到 4，philosopher iii 坐在 chopstick iii 和 (i+1) mod 5(i+1)\bmod5(i+1)mod5 之间，每人先拿编号小的那根。Philosopher 0 到 3 仍然是先左后右，philosopher 4 的两根是 4 和 0，他先拿 0。

为什么 lock ordering 一定不会有 circular wait。 按顺序拿 lock 的 thread，在等 lock bbb 时手里拿着的每个 lock 编号都小于 bbb。假设出现了一圈：thread T1T_1T1​ 拿着 a1a_1a1​、等 a2a_2a2​，a2a_2a2​ 在 T2T_2T2​ 手里；T2T_2T2​ 拿着 a2a_2a2​、等 a3a_3a3​；……；TmT_mTm​ 拿着 ama_mam​、等 a1a_1a1​。每个 thread 都是“拿着的比等着的小”，于是

a1<a2<⋯<am<a1a_1<a_2<\cdots<a_m<a_1a1​<a2​<⋯<am​<a1​

不可能。所以 circular wait 不会出现，deadlock 也就不会出现。前面两个 lock 的例子，规定先 L1 后 L2，Thread 2 改成先 lock(L1)，就修好了。

NUS 讲义另给了两种解法，各拆掉一个不同的 condition。

Limited eater。 再加一个初值为 4 的 general semaphore seats，每个 philosopher 拿 chopstick 之前先 wait(seats)，吃完放下两根之后 signal(seats)。最多 4 个人同时在拿 chopstick。4 个人、5 根 chopstick：即使 4 个人每人都已经拿起了一根，也只用掉 4 根，桌上至少剩 1 根，而这一根的两边至少有一个是在座的人，他就能拿到第二根吃完、放下，其他人跟着前进（pigeonhole principle）。五个人围成一圈的 circular wait 需要 5 个人，现在凑不齐。

Tanenbaum 的解法。 不按根去拿 chopstick，而是在一个 mutex 的保护下检查“两边邻居都没在吃”，一次决定能不能同时拿两根：

int state[5];                 /* THINKING, HUNGRY, EATING */
semaphore mutex = 1, s[5] = {0, 0, 0, 0, 0};

void safeToEat(int i) {       /* 调用时已持有 mutex */
    if (state[i] == HUNGRY && state[LEFT(i)] != EATING && state[RIGHT(i)] != EATING) {
        state[i] = EATING;
        signal(s[i]);         /* 让 i 的 wait(s[i]) 能通过 */
    }
}
void takeChopsticks(int i) {
    wait(mutex); state[i] = HUNGRY; safeToEat(i); signal(mutex);
    wait(s[i]);               /* 不能吃就睡在自己的 semaphore 上 */
}
void putChopsticks(int i) {
    wait(mutex); state[i] = THINKING;
    safeToEat(LEFT(i)); safeToEat(RIGHT(i));   /* 看两边的邻居现在能不能吃 */
    signal(mutex);
}

没有人会“拿着一根、等另一根”：要么两根一起拿到（state[i] = EATING），要么一根都不拿、睡在 s[i] 上，hold and wait 不成立，所以没有 deadlock。一个人吃完时替两边的邻居各检查一次，正在等的邻居就会被叫醒。它不保证没有 starvation：philosopher 1 饿着，而 0 和 2 交替着吃，1 的两边总有一个在 EATING，它就一直吃不上。

打破另外三个 condition 也各有办法，但各有代价：

  • Hold and wait。 一次把所有要用的 lock 都拿到，例如先拿一个全局的 lock 再依次拿其他的。这要求事先知道要哪些，而且降低了 concurrency。
  • No preemption。 用 trylock：拿不到就把手里的都放掉，过一会儿重来。可能出现 livelock：两个 thread 一直同时放、同时重试，都在动却都没有进展；加一个随机的等待时间可以缓解。
  • Mutual exclusion。 用 compare-and-swap 这类 atomic instruction 写不需要 lock 的 data structure。写起来很难。

也可以不预防，允许 deadlock 发生，再定期检查“谁在等谁”构成的 graph 里有没有 cycle，有就重启其中某个 thread。很多 database 是这样做的。

边界情况Deadlock 和 starvation 不是一回事

Deadlock 里所有相关的 thread 都停住了，而且永远不会恢复。Starvation 是某个 thread 一直轮不到，别的 thread 却在正常前进，例如第 3 站 TestAndSet spin lock 下一直抢不到的 thread，或者第 2 站 MLFQ 里沉在最底层的长 job。没有 deadlock 的程序仍然可能有 starvation。

POSIX 里的 semaphore、mutex 与 condition variable

实际写 C 时用的是 POSIX 提供的版本。Semaphore 在 <semaphore.h> 里：sem_init 设初值，sem_wait 和 sem_post 就是上面的 Wait 和 Signal（编译时链接 -lrt）。Pthread 另有专门的 mutex，pthread_mutex_lock 和 pthread_mutex_unlock，相当于 binary semaphore。

还有一种等待用 semaphore 写起来别扭：等一个条件成立，例如“nReader 变成 0”，而且条件成立时可能要叫醒所有在等的 thread。Condition variable 就是为这个准备的。pthread_cond_wait(&cv, &m) 必须在持有 mutex m 时调用，它把 thread 放进 Blocked、同时放掉 m，被叫醒时重新拿回 m 再返回，所以检查条件和睡下之间不会漏掉别人的通知；pthread_cond_signal 叫醒一个在等的 thread，pthread_cond_broadcast 叫醒全部。被叫醒的 thread 要在一个 while 里重新检查条件，因为别人可能抢先把条件又改掉了：

pthread_mutex_lock(&m);
while (nReader != 0)
    pthread_cond_wait(&cv, &m);
/* 此刻持有 m，并且 nReader == 0 */
pthread_mutex_unlock(&m);

没有 memory abstraction 会怎样

最直接的做法是 program 里写的 address 就是 physical address：load r1, 1000 读的就是 RAM 的第 1000 个 byte。只跑一个 program 时这没问题。同时放两个就不行了：两个 4 KB 的 program 都是按“从 0 开始”编译的，A 放在 0 到 4095，B 只能放在 4096 到 8191，可 B 的 code 里写着 jump 28，跳到的是 A 的地盘。

一个补救是在 load 时改写 address（relocation）：把 B 里每个 memory reference 都加上 4096。这让 load 变慢，而且 loader 分不清一个数到底是 address 还是普通的 integer constant（28 可能是跳转目标，也可能是一个计数）。

NUS 讲义接下来的办法是 base 和 limit 两个 register。Program 里用的 address 都从 0 算起，叫 logical address（这门课里也常叫 virtual address），CPU 里的 base register 放这个 process 在 physical memory 里的起点，limit register 放它的长度。每次 access，hardware 检查 logical<limit\text{logical}<\text{limit}logical<limit，然后访问 base+logical\text{base}+\text{logical}base+logical，越界就触发 exception。例如 base 5000、limit 3000，logical address 2800 合法，physical address 是 5000+2800=78005000+2800=78005000+2800=7800；logical address 3000 已经越界，因为合法的只有 0 到 2999。Process 换上 CPU 时，OS 把它的 base 和 limit 装进去，每个 process 都以为自己从 address 0 开始，代价是每次 access 都多一次加法和一次比较。

Contiguous allocation：partition 怎样分

在“每个 process 占一段连续 memory”这个前提下，OS 要决定每段放在哪里。分给一个 process 的那段连续 memory 叫 partition，有两种分法。

Fixed partitioning。 开机时把 memory 切成固定的几块，每个 process 占一块。分配很快，随便给一块空的即可。但每一块都得装得下最大的 process，小 process 放进去，partition 里剩下的部分没人能用，叫 internal fragmentation。

Dynamic partitioning。 按 process 实际要的大小切一块出来，没有 internal fragmentation。Process 来来去去之后，memory 里留下大小不一的空洞（hole），这就是开头第三件事。开头那张图里空着 16 KB，最大的一块却只有 6 KB，10 KB 的 process 放不下。空闲 memory 被切碎、单块不够用，叫 external fragmentation。

OS 用一个 linked list（每项记 occupied 还是 free、起点、长度、下一项）或一个 bitmap 记录哪些地方是 partition、哪些是 hole。来了一个要 NNN KB 的 process，就在 hole 里挑一个 M≥NM\ge NM≥N 的，切成 NNN 和 M−NM-NM−N 两段，前者给 process，后者成为新的 hole。挑哪个 hole 有三种规则：

  • First-fit： 从头找，第一个够大的就用。
  • Best-fit： 用够大的 hole 里最小的那个。
  • Worst-fit： 用最大的那个。

拿开头那张图的三个 hole 试：20 KB 处 6 KB，38 KB 处 4 KB，52 KB 处 6 KB。依次来三个 process，分别要 4、6、6 KB。

4 KB 放在 6 KB 放在 6 KB 放在 最后剩下的 hole
First-fit 20（剩 2） 52 放不下 24 处 2 KB，38 处 4 KB
Best-fit 38（正好） 20 52 无
Worst-fit 20（剩 2） 52 放不下 24 处 2 KB，38 处 4 KB

这不说明 best-fit 总是最好。换成依次要 3、3、6 KB：first-fit 放在 20 和 23（把第一个 hole 用完），6 KB 放进 52，全部成功；best-fit 先用 38 处的 4 KB，剩下一个 1 KB 的 hole，几乎不可能再被用上；worst-fit 把两个 3 KB 分别放进两个 6 KB 的 hole，剩下 3、4、3 KB，6 KB 的请求就放不下了。三种规则各有坏的情况，first-fit 的优点是找得最快。

Process 结束时，它的 partition 变回 hole，并且和相邻的 hole 合并（merge）。也可以把正在跑的 process 往一边挪，把所有 hole 并成一块（compaction），可挪动时要复制它们的全部 memory，所以不能常做。

Buddy system

Dynamic partitioning 每次都要在 hole 的 list 里找、切，释放时还要找出相邻的 hole 合并，都慢。Buddy system 限定所有块的大小都是 2 的 power，换来三件事都很快。

做法：要管理的 memory 是 2K2^K2K。维护一个 array A[0..K]A[0..K]A[0..K]，A[j]A[j]A[j] 是一个 linked list，记着所有大小为 2j2^j2j 的空闲块的起点。

  • 分配 NNN： 找最小的 SSS 使 2S≥N2^S\ge N2S≥N。A[S]A[S]A[S] 里有空闲块就拿走一块。没有，就往上找最小的 R>SR>SR>S 使 A[R]A[R]A[R] 非空，取出一块，对半分成两块 2R−12^{R-1}2R−1，一块放进 A[R−1]A[R-1]A[R−1]，另一块继续对半分，直到分出 2S2^S2S 的为止。同一次对半分出的两块互为 buddy。

Page 与 frame

Paging 把 virtual address space 切成固定大小的 page，把 physical memory 切成同样大小的 frame。任何一个 page 可以放进任何一个空 frame。每个 process 有一张 page table，第 iii 项记着 virtual page iii 放在哪个 frame。

因为 page 的大小是 2 的 power，切分只是把 address 的 bit 分成两段：高位是 virtual page number（VPN），低位是 page 内的 offset。翻译时 offset 原样保留，只把 VPN 换成 physical frame number（PFN）。

OSTEP 的小例子：virtual address space 64 byte，page 16 byte，所以有 4 个 page；physical memory 128 byte，有 8 个 frame。Page table 是 VP 0 → PF 3，VP 1 → PF 7，VP 2 → PF 5，VP 3 → PF 2。

翻译 virtual address 21。64 byte 要 6 个 bit（26=642^6=6426=64），每个 page 16 byte，offset 占低 4 位，VPN 占高 2 位。21 的 binary 是 010101010101010101：VPN 是 010101，即 page 1；offset 是 010101010101，即 page 里第 5 个 byte。查表，page 1 在 frame 7，binary 111111111。把 VPN 换成 PFN，得到 111 0101111\,01011110101，即 64+32+16+4+1=11764+32+16+4+1=11764+32+16+4+1=117。

在 paging 下，memory 从一开始就按 frame 分配和回收，空出来的也总是整数个 frame。把开头的例子换成 4 KB 的 frame 来想：16 KB 空闲就是 4 个空 frame，10 KB 的 process 要 3 个 page，放进哪 3 个空 frame 都行，它们挨不挨着无所谓。

它消灭了 external fragmentation，但带来了 internal fragmentation：process 要的 memory 不一定是 page 的整数倍。Page 4 KB，一个 process 要 10 KB，得分给它 ⌈10/4⌉=3\lceil10/4\rceil=3⌈10/4⌉=3 个 page 共 12 KB，最后一个 page 里有 2 KB 用不上。平均每段 memory 浪费半个 page。Page 越大，这个浪费越大；page 越小，page table 越长。这是选 page size 时的取舍。

Page table 太大

现实的设定：32-bit virtual address，page 4 KB。Offset 要 12 位（212=40962^{12}=4096212=4096），VPN 是剩下的 20 位，所以 page table 有 2202^{20}220 项。每项（page table entry，PTE）4 byte，一张表 220×4=42^{20}\times4=4220×4=4 MB。每个 process 一张，100 个 process 光 page table 就要 400 MB。

而一个典型的 process 只用了 address space 的两头：低处的 code、data、heap，高处的 stack，中间几乎全空。那些空的 PTE 也占着位置。

办法是对 page table 本身再做一次 paging。把 4 MB 的 page table 切成一页一页：每页 4 KB，放得下 4096/4=1024=2104096/4=1024=2^{10}4096/4=1024=210 个 PTE。再建一张 page directory，记着每一页 page table 在哪个 frame；如果某一页 page table 里全是空项，就根本不分配它，directory 里那一项标成 invalid。

于是 20 位 VPN 拆成两个 10 位：高 10 位查 directory，低 10 位查那一页 page table。每一级的 bit 数不是随便定的：一页 page table 恰好占一个 frame，正好装 2102^{10}210 项，所以每一级是 10 位。

只用两头的 process：directory 一页 4 KB，code 所在的那 4 MB 区域要一页 page table，stack 所在的那 4 MB 区域要一页，共 4+4+4=124+4+4=124+4+4=12 KB，比 4 MB 小 341 倍。

Context switch 之后的 TLB

TLB 里的一项只说“VPN 10 → PFN 100”，没说是哪个 process 的。Process P1 的 VPN 10 在 frame 100，P2 的 VPN 10 在 frame 170。从 P1 切到 P2 之后，如果 TLB 里还留着 P1 的那项，P2 访问 VPN 10 就会 hit 到 P1 的 frame，读到别人的 data。

一个办法是每次 context switch 把 TLB 清空（flush）。正确，但 P2 刚上来时每个 page 都要 miss 一次，这是第 1 站说的 context switch 间接开销的一部分。另一个办法是给每项加一个 address space identifier（ASID），记着它属于哪个 process；CPU 里有一个 register 存当前 process 的 ASID，只有 ASID 也相同才算 hit：

VPN PFN valid ASID
10 100 1 1
10 170 1 2

两项可以同时留在 TLB 里，切换时不用清空。

NUS 讲义把 TLB 当作 process 的 hardware context 的一部分，题目里默认 context switch 时 TLB 整个 flush，process 重新上 CPU 时要经过一串 TLB miss 才把它填满。做 NUS 的题按 flush 算，除非题目说有 ASID。

PTE 里的其他 bit：protection、sharing 与 copy-on-write

PTE 里除了 PFN 还有几个 bit，每个都对应一个前面遇到的需要。

  • Access right bit。 记这个 page 能不能 read、write、execute。Code 所在的 page 设成可读、可执行、不可写，program 一旦往自己的 code 上写，hardware 检查 bit 时就触发 exception。
  • Valid bit。 一个 process 的 address space 里大部分 page 根本没用到（上面那个只用两头的 process），对应的 PTE 标成 invalid，访问它就 trap 进 OS，OS 发现是越界访问，杀掉 process。
  • Shared。 几个 process 的 PTE 可以写同一个 PFN，共享同一个 frame。C library 的 code 被几百个 process 用，在 physical memory 里只放一份。

共享 frame 最重要的用途是 copy-on-write（COW），它解决第 1 站留下的问题：fork 要复制 parent 的全部 memory，可 child 接下来多半马上 exec，复制的东西全白费。COW 的做法是 fork 时只复制 page table，不复制 frame，parent 和 child 的 PTE 指向同样的 frame，并且都标成只读。

拿第 1 站的例子走一遍。设 x 所在的 data page 是 VP 2，在 PF 9。

  1. fork 之后，两个 page table 都是 VP 2 → PF 9，只读。Child 读 x，读到 100，不需要任何复制。
  2. Child 执行 x = x + 1，要写 VP 2。PTE 说只读，hardware 触发 exception，trap 进 OS。
  3. OS 看到这是一个 COW 的 page，不是真的越权：找一个空 frame，比如 PF 14，把 PF 9 的 4 KB 复制过去，把 child 的 PTE 改成 VP 2 → PF 14、可写，再让那条 store 重新执行。
  4. Child 的 x 在 PF 14 里变成 101；parent 的 VP 2 仍然指向 PF 9，x 还是 100。Parent 的 PTE 也可以改回可写，因为 PF 9 现在只有它一个人用了。

输出和第 1 站完全一样，fork 的语义没有变；变的是代价，只复制被写到的 page。

Segmentation：按用途分段

Paging 把 address space 当成一整片切成同样大小的 page，不管哪一段是做什么的。可一个 process 的 memory 本来就分成用途不同的几块：code 和 global data 大小固定，heap 和 stack 在运行中会长会缩，而且朝不同方向长。放在一片连续的 logical address space 里，很难让它们各自自由伸缩，也很难判断一次 access 是不是越过了某一块的边界。

Segmentation 让每一块自成一段（segment），每段有自己的 base 和 limit，相当于这一站开头的 base 和 limit register 每段一对。Logical address 写成 (segment id, offset)，segment id 是名字编成的号，例如 code 0、data 1、heap 2、stack 3。Segment table 按 segment id 存 (base, limit)，因为段数少，可以整张放在 register 里。翻译时：

  3. Physical address 是 base+offset\text{base}+\text{offset}base+offset。

Segmentation with paging。 两者合起来：每个 segment 再切成 page，各有一张 page table。Segment table 里存的不再是段的 base，而是这个段的 page table 在哪里，limit 照旧。Logical address 是 (segment id, page number, offset)：先用 segment id 找到段的 page table，检查越界，再用 page number 查出 frame，拼上 offset。段仍然可以独立伸缩（多加几个 page），physical memory 里却只需要零散的 frame。

Page 不一定在 memory 里

有了 page table，page 放在哪个 frame 已经由 OS 说了算。再走一步：page 也可以暂时不在 memory 里，放在 disk 上，用到了再搬进来。这样所有 process 的 address space 加起来可以比 physical memory 大，每个 process 也只需要把正在用的 page 留在 memory 里。这叫 virtual memory。

每个 PTE 里有一个 present bit（也叫 valid 或 resident bit）。Hardware 翻译时发现 present bit 是 0，就触发一个 exception，叫 page fault，交给 OS：

  1. Hardware 查 page table，发现这个 page 不在 memory，trap 进 kernel。
  2. OS 确认这个 address 是合法的（不合法就是 segmentation fault，杀掉 process）。
  3. 在 disk 上找到这个 page 的位置。
  4. 找一个空 frame；没有空的，就挑一个 page 赶出去（下面的 page replacement）。
  5. 从 disk 把 page 读进这个 frame。读 disk 要几 ms，这期间 process 进入 Blocked，CPU 去跑别人。
  6. 更新 PTE：填上 PFN，present bit 设为 1。
  7. 回到引起 page fault 的那条 instruction，重新执行。这次翻译成功。

第 7 步和 system call 不同：system call 回到 trap 的下一条 instruction，page fault 要重新执行同一条。

一个 page 只在第一次被用到时才搬进来，叫 demand paging。新 process 启动时一个 page 都不在 memory 里，所以启动快、占的 physical memory 少，能让更多 process 同时留在 memory 里；代价是刚启动时会连续 page fault，显得卡，而这些 page fault 抢 disk 和 frame，还会拖慢别的 process。

看起来对，其实不对TLB miss 就是 page fault

两件事发生在不同的层，代价差了五个数量级。TLB miss 是 TLB 里没有这个翻译，page 本身多半就在 memory 里；hardware 走一遍 page table（上一站的例子里多两次 memory access，约 200 ns）就解决了，OS 甚至不知道。Page fault 是 PTE 说这个 page 不在 memory 里，要 OS 介入、从 disk 读，约 10 ms，即 10710^7107 ns。顺序是：先查 TLB；miss 了去走 page table；走到 PTE 发现 present bit 是 0，才是 page fault。

一百万次 access 里最多一次 page fault。Virtual memory 能用，完全靠 locality：program 在一段时间里只反复用少数几个 page。NUS 讲义分两种：temporal locality，刚用过的 address 很可能马上再用，一个 page 搬进来之后会被用很多次，搬一次的代价被分摊掉；spatial locality，用过的 address 附近的 address 很可能接着用，它们多半在同一个 page 里，一次搬进来就都有了。也正因为代价这么高，赶走哪个 page 值得仔细选。

赶走哪一个

用 reference string 来比较：只记 access 了哪些 page，按顺序写成一串。OSTEP 的例子是

有 3 个 frame。前三次一定是 miss（compulsory miss），frame 装满之后，三种 policy 在第 6 次 access（page 3）时开始分道：

  • OPT。 赶走将来最久不会再用的 page。此刻往后看，0 下一次在第 7 次、1 在第 9 次、2 在第 10 次，赶走 2。它的 page fault 最少，但要预知将来，实际做不到，只用作比较的下限。
  • FIFO。 赶走最早进来的 page。0 最早进来，赶走 0，可下一次 access 恰好就是 0。
  • LRU（least recently used）。 赶走最久没被用过的 page，拿“过去”去猜“将来”。此刻最近一次使用的时刻，0 是第 4 次、1 是第 5 次、2 是第 3 次，赶走 2，和 OPT 一样。

LRU 不会这样。原因是它有 stack property：nnn 个 frame 的 LRU，任何时刻装着的是“最近用过的 nnn 个不同的 page”；n+1n+1n+1 个 frame 装着的是“最近用过的 n+1n+1n+1 个不同的 page”。前者永远是后者的 subset。所以 nnn 个 frame 时 hit 的 access，n+1n+1n+1 个 frame 时一定也 hit，page fault 只会更少。FIFO 的内容取决于“什么时候进来的”，加一个 frame 会改变后面每一次赶走谁，没有这种包含关系；上表第 7 步之后，3 个 frame 的 {1,2,5}\{1,2,5\}{1,2,5} 就不是 4 个 frame 的 {2,3,4,5}\{2,3,4,5\}{2,3,4,5} 的 subset。

LRU 太贵，用 Clock 近似

真正的 LRU 要在每一次 memory access 时记下时刻（每个 PTE 一个 counter，赶走时找最小的），或者维护一个按使用先后排的 stack（每次 access 把那个 page 挪到顶上）。每次 access 都要做额外的事，hardware 支持不起。

Hardware 能便宜做到的，是每次 access 时把 PTE 里的 reference bit 设成 1。Clock（也叫 second chance）只用这一个 bit：它是改过的 FIFO，所有 frame 按装入顺序排成一圈，一根 clock hand 指着最老的那个，作为下一个候选。要赶走一个时，看 hand 下的 page：

  • reference bit 是 1：最近用过，给它第二次机会，把 bit 清成 0，hand 往前走一格，再看下一个。
  • reference bit 是 0：从上次 hand 经过到现在都没被用过，赶走它，新 page 装进这个 frame，hand 走到下一格。

NUS 的约定是：page 刚装进来时 reference bit 是 0，之后每被 access 一次设成 1。两份 NUS 学生笔记（Hanming Zhu 的 cheatsheet 特意注明“for CS2106”，以及一位 TA 的 Virtual Memory 讲义页）都这样写。

File：metadata、type、protection 与 access method

Disk 本身只提供“读写第 nnn 个 block”。Program 想要的是有名字、能按 byte 读写、能变长、关机也不丢的 file。File system 就是在 block 之上搭出这层，NUS 讲义对它的要求是三条：self-contained（disk 上的信息足够描述整个组织，拔下来插到另一台机器上照样能读）、persistent（比 process 和 OS 活得久）、efficient（管好空闲和已用的空间，记账的 overhead 小）。它和 memory 管理面对的是不同的 storage：memory 按 address 访问、速度恒定、被 program 隐式使用；disk 按 sector 访问、每次 I/O 的时间随 head 的位置变，program 要显式调用 open、read 才用得到。

一个 file 由 data 和 metadata 组成。Metadata 是关于 file 的信息：给人看的 name，file system 内部用的唯一 identifier，type，当前 size，protection，创建、修改的时间和 owner，以及“data 在哪些 block 上”的那张 table of contents（下面的 allocation 讲的就是它）。

Type。 OS 认识几类 file：regular file（又分 ASCII 的 text file，能直接显示；binary file，例如 executable、PDF，有固定的内部结构，要专门的 program 才能处理）、directory，以及代表 device 的 special file。Windows 用 name 里的 extension 判断 type，report.pdf 改名成 report.txt 就会被当成 text；Unix 不看名字，看 file 开头的 magic number，例如 ELF executable 的头四个 byte 是 0x7F 'E' 'L' 'F'。

Protection。 能对 file 做的事有 read、write、execute、append、delete、list（读 metadata）几种。Unix 把 user 分成 owner、group、universe（其他所有人）三类，每类给 r、w、x 三个 bit。ls -l 显示的 -rw-r--r--：第一个字符 - 表示 regular file，接着三组 rw-、r--、r--，owner 能读写，group 和其他人只能读，没有人能执行。更细的控制用 access control list（ACL），可以对具体某个 user 单独授权，getfacl 能看到。

Data 的结构与 access method。 File 的 data 可以是一串 byte（每个 byte 有自己的 offset，Unix 和 Windows 都这样），也可以是 fixed-length record（第 kkk 条 record 在 k×k\timesk× 长度处，能直接跳过去）或 variable-length record（灵活，但要找第 kkk 条只能从头数）。访问方式有 sequential（从头按顺序读，可以 rewind，不能跳）、random（任意位置），以及对 record 的 direct access。Unix 的 random access 用 lseek(fd, offset, whence) 先移动当前位置再 read：whence 是 SEEK_SET 时从 file 开头算，SEEK_CUR 时从当前位置算，SEEK_END 时从结尾算，offset 可以是负数。一个 100 byte 的 file，lseek(fd, -10, SEEK_END) 把位置移到 90，接下来的 read(fd, buf, 20) 只读到 10 个 byte。

Operation。 对 metadata 的有 rename、改 attribute（permission、owner）、读 attribute；对 data 的有 create、open、read、write、reposition（seek）和 truncate（把某个位置之后的 data 删掉）。它们都做成 system call，因为 OS 要检查 protection、协调多个 process 同时访问，还要维护每个打开的 file 的状态。read 和 write 都从当前 offset 开始，做完把 offset 往后挪实际读写的 byte 数；write 写过了结尾，file 就变长。

File descriptor 背后的几张表

Process 用 open 打开一个 file，得到一个小 integer，叫 file descriptor；之后 read、write 都拿它当参数。一个打开的 file 要记三样东西：file pointer（当前 offset）、file 在 disk 上的位置、open count（有几处在用它，降到 0 时才能删掉这一项）。NUS 讲义把它们组织成两张表（two-table approach），再往下指向 file 本身：

  1. Per-process open-file table。 每个 process 一张，descriptor 就是这张表的 index，表项指向下一层。0、1、2 照惯例是 standard input、output、error。
  2. System-wide open-file table。 整个系统一张，每次 open 产生一项，记着当前的 offset、打开的 mode，以及有几个 descriptor 指向它。
  3. 再往下是 file 本身的信息（ext2 里是 in-memory inode）：大小、owner、permission、data 在 disk 的哪些 block 上。同一个 file 被打开几次都只有一份。

OSTEP 第 39 章用 xv6 的 struct file 说明第二层一项里的东西：ref（reference count）、readable 和 writable、指向 inode 的 ip，以及 offset off。

为什么 offset 放在第二层而不是第一层或第三层，看一个例子：

int fd = open("log.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
if (fork() == 0) {
    write(fd, "child\n", 6);
    exit(0);
}
wait(NULL);
write(fd, "parent\n", 7);

fork 复制的是 per-process 那张表，复制出的表项指向同一个 system-wide 表项，于是共享同一个 offset，那一项的 reference count 变成 2。Child 写 6 个 byte，offset 从 0 变成 6；parent 接着从 6 开始写，file 最后是 13 个 byte：child\nparent\n。OSTEP 第 39 章的版本是 child 执行 lseek(fd, 10, SEEK_SET)，parent 之后查当前 offset，得到的也是 10。

如果改成两个 process 各自 open 一次，就有两项、两个 offset，都从 0 开始。Child 写下 child\n，parent 从 offset 0 写 parent\n，7 个 byte 把前 6 个全部盖掉，file 只剩 parent\n。同一个 process 对同一个 file open 两次也一样是两项：OSTEP 的例子里 fd1 和 fd2 各 read 100 byte，两边的 offset 各自变成 100，互不影响。Shell 执行 (echo a; echo b) > out 时，两条命令的输出能依次排好，靠的就是前一种共享。第 3 站的 dup(fd) 也是让两个 descriptor 指向同一项、共享 offset，只不过在同一个 process 里。

Directory 让 user 把 file 分组，也让 system 记住有哪些 file。NUS 讲义按结构从简单到复杂排了四种。

  • Single-level。 所有 file 都在 root 下面。两个 user 都想要一个叫 notes.txt 的 file 就不行，名字不能重复。
  • Tree。 Directory 里可以再有 directory。一个 file 可以用 absolute pathname 从 root 一路写下来（/home/alice/notes.txt），也可以用相对 current working directory 的 relative pathname（在 /home/alice 里就是 notes.txt）。
  • DAG（directed acyclic graph）。 让一个 file 同时出现在几个 directory 里，而 data 只有一份。Unix 有两种做法。Hard link（ln）：directory A 和 B 各有一项直接指向 file F，开销只是多一个指针，问题是删除：A 删了 F，B 里那一项怎么办（下面的 link count 回答这个问题）。Hard link 只能指向 file。Symbolic link（ln -s）：B 里建一个特殊的小 file G，内容是 F 的 path name，访问 G 时 OS 转去访问 F。删除很简单：B 删 G 不影响 F；A 删了 F，G 还在，只是再也找不到 F。代价是 G 本身占 disk 空间，每次访问多解析一次 path。
  • General graph。 Symbolic link 可以指向 directory，于是 directory 之间可能形成 cycle。遍历时可能无限循环，判断一个 directory 什么时候可以删也变难，所以它可能出现，但不受欢迎。

Disk 的组织

File system 眼里的 disk 是一个一维的 logical block array，block 通常 512 byte 到 4 KB，logical block 到实际 sector 的对应由 hardware 决定。Sector 0 是 master boot record（MBR），里面是一小段 boot code 和一张 partition table；之后是一个或多个 partition，每个 partition 是一个独立的 file system，里面依次放 OS boot block、partition 的细节（一共多少 block、空闲 block 的数目和位置）、directory structure、各个 file 的信息，最后是 file 的 data。

一个 file 的 block 放在哪

File 的 data 存在若干个 block 里（下面都取 block 4 KB）。File 的大小一般不是 block 的整数倍，最后一个 block 有 internal fragmentation。File system 要记下“这个 file 的第 0、1、2…个 block 在 disk 的哪里”。有四种记法，比较的是两件事：能不能快速找到第 kkk 个 block（random access），以及记这些位置要占多少空间。

Contiguous。 每个 file 占一段连续的 block，只记起点和长度。第 kkk 个 block 就在 起点+k\text{起点}+k起点+k，random access 最快，读整个 file 也只需 seek 一次。但这和第 5 站的 contiguous memory 一模一样：file 删来删去留下空洞，产生 external fragmentation；而且 file 的大小要事先定好，要变长时，后面的 block 可能已经被别人占了。

Linked list。 每个 block 里除了 data 还存下一个 block 的编号，file 的信息里记第一个和最后一个 block。任何空 block 都能用，没有 external fragmentation。代价是找第 kkk 个 block 要从头读 kkk 个 block，每一次都是一次 disk read；每个 block 少了 4 byte 能放 data；而且只要一个 pointer 坏了，后面的 block 就全找不到了。

FAT（File Allocation Table）。 把所有 block 里的“下一个” pointer 抽出来，集中放在一张表里，开机时整张读进 memory（MS-DOS 的做法）。表的第 iii 项描述 block iii，取值有四种：FREE（空闲）、下一个 block 的编号、EOF（这是 file 的最后一个 block）、BAD（这个 block 坏了，不能用）。Directory 里记着 file 的第一个 block。

NUS 讲义的例子：root directory 里有三项，ex1.c 从 block 3 开始，ex2.c 从 block 6 开始，subdirectory test 从 block 2 开始；FAT 里 FAT[3] = 5，FAT[5] = 8，FAT[8] = EOF，FAT[6] = 7，FAT[7] = EOF，FAT[2] = EOF。所以 ex1.c 依次占 block 3、5、8，ex2.c 占 6、7，test 只有 block 2 一个 block。要读 ex1.c 的第 2 个 block（从 0 数），在 memory 里走 3 → 5 → 8，然后只读一次 disk。如果是普通的 linked list，要依次读 block 3、5、8 三次 disk。

FAT 的问题是大小：它为 partition 里的每一个 block 都留一项，不管用没用。1 TB 的 disk、4 KB 的 block，一共 240/212=2282^{40}/2^{12}=2^{28}240/212=228 个 block。每项 4 byte，FAT 要 228×4 B=12^{28}\times4\text{ B}=1228×4 B=1 GB，整张放在 memory 里太大；而且 random access 虽然不读 disk，仍要在 memory 里走一条可能很长的 chain。

Indexed。 每个 file 一个 index block，里面按顺序列出它所有 block 的编号，第 kkk 个就是 index 的第 kkk 项。只有打开的 file 的 index block 需要在 memory 里，找第 kkk 个 block 也不用顺着 chain 走。问题是 index block 多大：一个 block 装得下的 pointer 个数就是 file 的最大 block 数，4 KB 的 block、4 byte 的 pointer，最大 file 只有 1024×4 KB=41024\times4\text{ KB}=41024×4 KB=4 MB。变通的办法有把几个 index block 连成 linked list、像 multi-level page table 那样分层，或者两者混合。ext2 用的是混合。

MS-DOS FAT 的细节

NUS 讲义专门讲了 FAT 和 ext2 两个 case study。FAT partition 依次是 OS boot block、FAT、一份可选的 FAT 副本、root directory、data block。

Directory 是一种特殊的 file。Root directory 放在固定的位置，其他 directory 和普通 file 一样放在 data block 里。Directory 的内容是一串固定 32 byte 的 directory entry，每个 file 或 subdirectory 一项：

name + extension 8 + 3 所以名字最多 8 个字符加 3 个字符的 extension；name 的第一个 byte 还兼做标记：已删除、directory 结束、parent directory 等

8+3+1+10+2+2+2+4=328+3+1+10+2+2+2+4=328+3+1+10+2+2+2+4=32。2 byte 的 date 里给年份的只有 7 bit，从 1980 算起，1980+27−1=21071980+2^7-1=21071980+27−1=2107；time 里给秒的 bit 不够表示 0 到 59，只好存秒数除以 2，于是精度是 2 秒。

读一个 file 的过程：读出 directory 所在的 block，找到这个 file 的 directory entry，取出第一个 block 的编号；用 FAT 顺着 chain 找出后面所有 block 的编号，直到 EOF；用这些编号去读 disk。如果这个 file 是 subdirectory，读出来的 data 又是一串 directory entry，回到第一步。

FAT 的几个版本区别在“block 编号用几个 bit”：FAT12、FAT16、FAT32（实际用 28 bit）。为了管更大的 partition，FAT 的分配单位可以不是一个 block，而是几个连续 block 组成的 cluster。最大 partition 是 cluster 大小乘以编号个数，cluster 取 4 KB 时：

版本 编号 bit 数 最大 partition
FAT12 12 212×4 KB=162^{12}\times4\text{ KB}=16212×4 KB=16 MB

FAT32 28 228×4 KB=12^{28}\times4\text{ KB}=1228×4 KB=1 TB

Cluster 越大，partition 能越大，internal fragmentation 也越大：一个 1 byte 的 file 也要占掉整整一个 cluster。8 + 3 的名字太短，后来的 VFAT 让一个长名字占用几个连续的 directory entry，最后一个 entry 仍然是一个 8 + 3 的短名字，旧系统照样能读。

ext2 的 inode：不平衡的 index tree

ext2 把 partition 切成若干 block group（见上面的布局图）。每组开头是 superblock（描述整个 file system：inode 和 block 的总数、每组有多少）和 group descriptor（描述每一组：空闲的 block 和 inode 有多少、bitmap 在哪里），这两样每组都存一份副本，坏了一份还有别的；然后是这一组的 block bitmap、inode bitmap、inode table（一个 inode 的 array）和 data block。

每个 file 或 directory 对应一个 inode（index node），128 byte，里面有 mode（file type 加 permission，2 byte）、owner 的 user id 和 group id（各 2 byte）、file size（4 byte，大 file 用 8 byte）、三个 timestamp（各 4 byte）、reference count（有几个 directory entry 指向它，2 byte），以及 15 个 4 byte 的 block pointer：

  • 前 12 个是 direct pointer，直接指向 data block。
  • 第 13 个是 single indirect：指向一个装满 pointer 的 block。4 KB 的 block、4 byte 的 pointer，一个 block 装 4096/4=10244096/4=10244096/4=1024 个 pointer。
  • 第 14 个是 double indirect：指向一个 block，里面 1024 个 pointer 各指向一个 single indirect block。
  • 第 15 个是 triple indirect，再多一层。

各级能覆盖的 data：

pointer 能指到的 data block 数 大小
12 个 direct 12 48 KB
single indirect 102410241024 4 MB
double indirect 10242=2201024^2=2^{20}10242=220 4 GB
triple indirect 10243=2301024^3=2^{30}10243=230 4 TB

只用 direct 和 single indirect 的最大 file 是 (12+1024)×4 KB=4144(12+1024)\times4\text{ KB}=4144(12+1024)×4 KB=4144 KB。加上后两级，上限约 4 TB。

NUS 讲义算的是 1 KB 的 block：一个 block 装 1024/4=2561024/4=2561024/4=256 个 pointer，最大 file 是

12×1 KB+256×1 KB+2562×1 KB+2563×1 KB=12+256+65,536+16,777,216=16,843,020 KB12\times1\text{ KB}+256\times1\text{ KB}+256^2\times1\text{ KB}+256^3\times1\text{ KB}=12+256+65{,}536+16{,}777{,}216=16{,}843{,}020\text{ KB}12×1 KB+256×1 KB+2562×1 KB+2563×1 KB=12+256+65,536+16,777,216=16,843,020 KB

约 16 GB。Block 从 1 KB 变成 4 KB，最大 file 从约 16 GB 变成约 4 TB，涨了约 256 倍：每个 block 大 4 倍，triple indirect 下的 block 数又多 43=644^3=6443=64 倍。

这个 tree 故意不平衡。OSTEP 引用的测量显示，最常见的 file 只有约 2 KB，大多数 file 很小：它们只用 direct pointer，读 inode 之后就能直接找到 data。少数大 file 才走 indirect，多读一两次 disk 相对于读几 GB 的 data 微不足道。

给定 byte offset，在哪个 pointer 下？ 回到 4 KB 的 block，读一个 file 的第 5,000,000 个 byte。

  1. 它在第几个 block：⌊5,000,000/4096⌋=1220\lfloor5{,}000{,}000/4096\rfloor=1220⌊5,000,000/4096⌋=1220，block 内的 offset 是 5,000,000−1220×4096=28805{,}000{,}000-1220\times4096=28805,000,000−1220×4096=2880。
  2. Block 0 到 11 归 direct pointer。1220≥121220\ge121220≥12，减掉之后是 1208。
  3. 接下来 1024 个归 single indirect（block 12 到 1035）。1208≥10241208\ge10241208≥1024，减掉之后是 184，所以在 double indirect 下面。
  4. Double indirect block 里的每个 pointer 管 1024 个 block。⌊184/1024⌋=0\lfloor184/1024\rfloor=0⌊184/1024⌋=0，用第 0 个 pointer，找到一个 single indirect block；在那里面取第 184 mod 1024=184184\bmod1024=184184mod1024=184 个 pointer。

要读的 disk block 依次是：inode、double indirect block、single indirect block、data block，一共 4 次（inode 已经在 memory 里就是 3 次）。

Directory 的实现与 path lookup

Directory 要做的是把 file name 对应到 file 的信息。两个设计选择：

  • 用什么 data structure 找名字。Linear list：一项一项往下比，directory 大、path 深时很慢，可以把最近几次查找的结果 cache 起来。Hash table：把名字 hash 到 0 到 N−1N-1N−1，冲突的用 chaining，查找快，但表的大小有限，效果取决于 hash function。
  • File 的信息放在哪。全部放在 directory entry 里（FAT 就是这样，entry 里有 size、时间、第一个 block）；或者 entry 里只放名字和一个指向别处的 pointer（ext2 的 entry 里只有 inode number）。

ext2 的 directory 也是一个 file，它的 data block 里是一串长度不固定的 directory entry，每项依次是：inode number（0 表示这一项没在用）、这一项的总长度（据此跳到下一项）、名字的长度、type（file、directory 或 special）、名字（最多 255 个字符）。Root directory 的 inode number 约定是 2。

NUS 讲义的例子：读 /sub/file。

  1. 读 inode 2（root），它的 data block pointer 指向 block 15。
  2. 读 block 15，在 directory entry 里找到 sub，type 是 directory，inode number 8。
  3. 读 inode 8，data 在 block 20。
  4. 读 block 20，找到 file，type 是 file，inode number 6。
  5. 读 inode 6，检查 permission；它的第一个 data block 是 block 23。
  6. 读 block 23，拿到 file 的内容。

open 就是走到第 5 步为止：在 system-wide 表里建一项指向 inode 6，再在 process 的表里建一个 descriptor 指向它，返回 descriptor。OSTEP 数打开 /foo/bar 也是同样的 5 次读，path 每多一层就多两次。之后每 read 一个 block 又要 3 次 I/O：读 inode 找到 block 的位置，读 data block，再把 inode 写回去更新最后访问时间。所以 bar 有 3 个 block 时，打开再读完一共约 5+3×3=145+3\times3=145+3×3=14 次 I/O。实际系统会把最近用过的 inode 和 directory block cache 在 memory 里，大部分这样的读都不用真的去 disk。

Link。 Hard link 在 ext2 里就是在 directory B 里新建一项，写上和 A 里那个 file X 相同的 inode number，再把 X 的 inode 的 reference count 加 1。两个名字指向同一个 inode，没有哪个是“原件”。Symbolic link 是新建一个 file Y（有自己的 inode 和 directory entry），它的 data 就是 X 的 path name；X 改名或删掉，Y 就失效了。OSTEP 第 39 章的例子：echo hello > file 之后 stat 显示 Links: 1；ln file file2 后两边都是 Links: 2；再 ln file2 file3 变成 3；依次 rm file、rm file2，count 降到 2、1，file3 照样能读，直到最后一个也删掉。换成 ln -s file file2，rm file 之后 cat file2 报错 No such file or directory。Hard link 不能指向 directory（会造成 cycle），也不能跨 partition（inode number 只在一个 file system 里唯一）。

看起来对，其实不对删除一个 file，就是把它的 data 从 disk 上抹掉

Unix 删除 file 的 system call 叫 unlink：它只是把 directory 里那一项去掉，并把 inode 的 reference count 减 1。NUS 讲义描述 ext2 去掉 directory entry 的办法：把前一项的长度加大，让它“盖住”被删的这一项；如果被删的是第一项，就把它的 inode number 设成 0，变成空白项。只有 count 变成 0、而且没有 process 还开着它时，file system 才回收：在 inode bitmap 里把 inode 标成空闲，在 block bitmap 里把它的 data block 标成空闲。Data block 里的 byte 原封不动，直到被新 file 覆盖。所以用 hard link 多建一个名字之后再删掉原名，file 照样能读；刚删的 file 常常还能被恢复工具找回来。

Free space：bitmap 与 linked list

File system 还要知道哪些 block 和 inode 是空的。分配时从空闲记录里拿掉一个 block，释放时把它加回去。

Bitmap。 每个 block 一个 bit。一个 4 KB 的 bitmap block 有 4096×8=32,7684096\times8=32{,}7684096×8=32,768 个 bit，管 32,768×4 KB=12832{,}768\times4\text{ KB}=12832,768×4 KB=128 MB 的 data。1 TB 的 disk 有 2282^{28}228 个 block，bitmap 是 2282^{28}228 bit =32=32=32 MB，是同一块 disk 上 FAT 的 1/321/321/32，因为每个 block 只记 1 bit 而不是 4 byte 的 pointer。用 bit operation 很容易找到第一个空闲的 block，或者连续 nnn 个空闲的 block；但为了快，bitmap 要放在 memory 里。

Bit 的含义要看清约定。NUS 讲义在讲一般的 free space management 时写的是 1 表示 free、0 表示 occupied；讲 ext2 时，block bitmap 和 inode bitmap 又是 1 表示 occupied、0 表示 free（OSTEP 也是后一种）。两份学生笔记（AY20/21 和 AY25/26）都这样记，做题时以题目给的约定为准。

Linked list。 把空闲 block 的编号写在一些空闲 block 里，这些 block 再串成 linked list，memory 里只需要放第一个 block 的 pointer。要一个空闲 block，直接从表头拿一个编号即可。Overhead 用空闲 block 自己来装，不占额外空间；但表头那个 block 里的编号用完，就要读 disk 取下一个。如果空闲空间多是连续的一段段，可以只记“起点和长度”，可 fragmentation 一严重这招就不灵了。

建一个新 file、写一个新 block，都要先在 bitmap 里找到一个空闲 block、改掉那个 bit、写回 disk。OSTEP 数过：给 file 追加一个新 block 要 5 次 I/O（读写 data bitmap、读写 inode、写 data block）。

Disk scheduling

最后一层是 disk 本身。机械 disk 读一个 sector 的时间是 seek time（把 head 移到对应的 track，学生笔记记的是 2 到 10 ms）加 rotational latency（等 sector 转到 head 下面，2 到 6.25 ms）加 transfer time（真正读写，微秒级）。前两项是机械动作，占了绝大部分时间，transfer 可以忽略。几个 process 同时发来请求时，OS 可以重新排它们的顺序，让 head 少跑路。

NUS 讲义（据 AY25/26 的学生笔记）的例子：head 在 track 13，请求依次是 13、14、2、18、17、21、15。

FCFS。 按到达顺序：13→14→2→18→17→21→1513\to14\to2\to18\to17\to21\to1513→14→2→18→17→21→15，移动 0+1+12+16+1+4+6=400+1+12+16+1+4+6=400+1+12+16+1+4+6=40 个 track。从 14 跳到 2 再跳回 18，来回白跑。

SSF（shortest seek first）。 每次去离 head 最近的请求：在 13 时最近的是 13 本身，然后 14、15、17、18、21，最后才是 2：移动 0+1+1+2+1+3+19=270+1+1+2+1+3+19=270+1+1+2+1+3+19=27 个 track，比 FCFS 少三分之一。代价是 starvation：只要 head 附近不断有新请求，track 2 这种远处的请求可能一直等下去。

SCAN。 防 starvation 的办法是让 head 像电梯一样单向扫：一直往一个方向走，沿途服务所有请求，到头再掉头。Disk 的 track 是 0 到 24 时，从 13 往大的方向走：服务 14、15、17、18、21，走到 24 掉头，再回来服务 2，移动 (24−13)+(24−2)=11+22=33(24-13)+(24-2)=11+22=33(24−13)+(24−2)=11+22=33。比 SSF 多走 6，但任何请求最多等 head 来回一趟。Hanming Zhu 的 AY20/21 cheatsheet 还列了 C-SCAN（只朝一个方向服务，到头后直接回到起点），以及 Linux 的几种实际 I/O scheduler（deadline、noop、cfq、bfq）；AY25/26 的笔记只记了 FCFS 和 SSF。

  • OSTEP 第 6 章：Mechanism: Limited Direct Execution第 1 站：restricted operation 与 switching 两个问题、trap table、register 分两次保存的时间线、system call 和 context switch 的实测开销。据 marvinthang 的笔记，AY26/27 的 NUS 讲义也直接用了这一章。
  • xv6: a simple, Unix-like teaching operating system（MIT 6.1810 的教材，RISC-V rev3）第 1 到 3 章第 1 站的 fork、exec、cat < input.txt，ecall 与 kernel stack；第 3 站 pipe 的 write end；第 5 站的 Sv39 三级 page table。第 4 章只读到开头。
  • OSTEP 第 7 章：Scheduling: Introduction第 2 站的 metric 定义、SJF 与 STCF 的 arrival 例子、time slice 的 amortization。
  • OSTEP 第 8 章：Multi-level Feedback Queue第 2 站 MLFQ 的规则、三个例子、gaming、priority boost 和 Solaris 的数字。这次用 WebFetch 逐项核对，拿到的是转述。
  • Berkeley CS162 Lecture 11：Scheduling 2: Classic Policies (Con't), Case Studies（Kubiatowicz）第 2 站贯穿全站的四个 process（53、8、68、24）、RR 的 Gantt chart、10 个 100 秒 job 的 RR 与 FIFO 对比。
  • OSTEP 第 26、28、32 章：Concurrency: An Introduction；Locks；Common Concurrency Problems第 3 站的 counter 例子与逐条 instruction 的 interleaving、lock variable 的失败、Peterson、TestAndSet；第 4 站 deadlock 的四个 condition 与 prevention。
  • OSTEP 第 18、19、22 章：Paging: Introduction；TLBs；Beyond Physical Memory: Policies第 5 站的 64-byte 小例子、page table 大小、TLB 的 array 例子与 ASID；第 6 站的 reference string、Belady's anomaly、Clock。
  • OSTEP 第 39 章：Interlude: Files and Directories（Villanova 的镜像）第 7 站的 open file table、fork 后共享 offset、两次 open 各自的 offset、dup、link count、symbolic link。用 WebFetch 按问题逐项读的，拿到的是转述。
  • OSTEP 第 40 章：File System Implementation第 7 站的 inode、multi-level index、读 /foo/bar 要几次 I/O。

动手做

各校公开课里和这门课内容对得上的编程作业，链接都核实过能打开。讲义读懂了不等于会做，挑一个从头写完。

  • Lab pgtbl: Page tablesMIT 6.1810 Operating System Engineering (Fall 2026) · C (xv6, RISC-V)读懂并修改 xv6 的 page table：实现 vmprint() 打印 page table、用 PTE_A 实现 pgaccess()、给每个 process 映射一个只读 page 来加速 getpid，再加上 superpage。lab 说明、xv6 源码、make grade tests 都公开
  • Lab cow: Copy-on-write forkMIT 6.1810 Operating System Engineering (Fall 2026) · C (xv6, RISC-V)在 xv6 kernel 里实现 copy-on-write fork()：fork 时共享 physical page，写的时候在 page fault handler 里再复制，并给每个 physical page 维护 reference count。lab 说明、xv6 源码、make grade tests 都公开
  • Lab fs: File systemMIT 6.1810 Operating System Engineering (Fall 2026) · C (xv6, RISC-V)给 xv6 file system 加两个功能：用 doubly-indirect block 支持大文件，以及实现 symlink system call。做完对 inode 的结构有具体的印象。lab 说明、xv6 源码、make grade tests 都公开
  • ostep-projects: Shell、Memory Allocator、Parallel Zip 等UW–Madison OSTEP projects (Remzi Arpaci-Dusseau) · C配合 OSTEP 教材的一组 project：在 Linux 上写 Unix utilities、shell、memory allocator、parallel zip、web server，另有几个修改 xv6 kernel 的题目（lottery scheduling、kernel threads）。可以挑和课程进度对应的那几个做。project 说明和 tests 公开在 GitHub（README 说明并非每个 project 都已有 tests）
