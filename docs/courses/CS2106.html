Process：一个正在跑的 program

Disk 上的 program 只是一个 file，里面是 instruction 和初始的 data。把它跑起来，就多出了一堆只在运行时才有的东西：一片 memory（code、global data、heap、stack），CPU 里的 register（PC 指向下一条 instruction，SP 指向 stack 顶），以及打开的 file。这些合起来叫一个 process。同一个 program 可以同时跑成好几个 process，各有各的 memory 和 register。

OS 为每个 process 保存一份记录，叫 process control block（PCB）：process ID（PID）、当前 state、不在 CPU 上时那一组 register 的值、memory 的映射信息、打开的 file 列表。Process 不在 CPU 上的时候，它的全部“运行状态”就在 PCB 里。

Unix 里新建 process 只有一个办法：fork()。它把调用者完整地复制一份，复制出来的叫 child，原来的叫 parent。

int x = 100;
int main(void) {
    pid_t pid = fork();
    if (pid == 0) {                 /* child */
        x = x + 1;
        printf("child: x = %d\n", x);
        exit(0);
    } else {                        /* parent */
        wait(NULL);
        printf("parent: x = %d, child pid = %d\n", x, pid);
    }
    return 0;
}

fork() 调用一次、返回两次：parent 和 child 都从 fork() 的返回处接着跑，区别只在 return value。Child 拿到 0，parent 拿到 child 的 PID。所以 if 的两个 branch 各被一个 process 走了。输出是

child: x = 101
parent: x = 100, child pid = 4242

（PID 的具体数由 OS 分配，4242 只是举例。）Child 把 x 改成了 101，parent 看到的仍然是 100：两个 process 的 x 在同一个 address 上，却是两份不同的 memory。wait(NULL) 让 parent 停下来等 child 结束，所以 child 的那行一定先打印。

fork() 只会复制自己。要跑另一个 program，child 接着调用 exec()：把自己的 memory 整个换成另一个 program 的 code 和 data，从那个 program 的开头跑起。exec() 成功就不会返回，因为调用它的那段 code 已经不存在了。

为什么不把两件事合成一个“新建一个跑某 program 的 process”？xv6 book 给的理由是 shell 的 I/O redirection。在 shell 里输入 cat < input.txt，shell 先 fork()，child 在 exec("cat") 之前做两件事：close(0)，然后 open("input.txt")。open 总是返回最小的空闲 file descriptor，刚空出来的正是 0，于是 0 号 descriptor（standard input）指向了 input.txt。然后 exec("cat")，cat 照常从 0 号读，读到的就是这个 file。cat 自己对 redirection 一无所知，parent shell 的 descriptor 也没有被动过。分成两个 call，中间就留出了一段由 child 自己调整环境的空隙。

为什么不能直接调用 OS 的 function

Process 要读 file，最直接的办法是让它自己去操作 disk。可这样一来，file system 里记的 permission 就没有意义了：任何 process 都能绕过检查把整个 disk 读一遍。OS 必须让 process 不能自己做某些事，但能请 OS 代做。

硬件为此提供一个 mode bit。CPU 在 user mode 下跑 process 的 code，此时访问 I/O device、改 page table、关 interrupt 这类 privileged instruction 一执行就触发 exception，交给 OS 处理（通常是杀掉这个 process）。OS 的 code 在 kernel mode 下跑，什么 instruction 都能执行。

Process 请 OS 做事的入口叫 system call。它要同时完成两件事：切到 kernel mode，跳进 OS 的 code。危险在于“跳到哪里”：如果 process 可以指定 kernel 里的任意 address，它就能跳过 permission 检查，直接跳到“检查已通过”之后的那一行。所以跳转目标不由 process 决定。开机时 OS 在 kernel mode 下把一张 trap table 交给硬件，写明“发生 system call 时跳到哪个 handler、发生 timer interrupt 时跳到哪个 handler”。之后 process 执行一条 trap instruction（MIPS 里叫 syscall，RISC-V 里叫 ecall），硬件就按表跳转。Process 能选的只有 system call 的编号，放在约定的 register 里（MIPS 是 $v0，xv6 的 RISC-V 是 a7）。

以 write(1, buf, 3) 为例，走一遍：

  1. Program 调用 C library 里的 write，这是一个普通的 function call。
  2. Library 把 write 的编号放进约定的 register，三个 argument 放进 argument register，然后执行 trap instruction。
  3. 硬件把 user 的 PC 等 register 存到这个 process 的 kernel stack 上，切到 kernel mode，跳到 trap table 里登记的 system call handler。
  4. Handler 按编号找到 sys_write，检查 argument：1 号 descriptor 是否打开、buf 到 buf + 3 是否都在这个 process 自己的 memory 里。检查通过才去做。
  5. 把 return value 放进 return register，执行 return-from-trap：硬件从 kernel stack 恢复 register，切回 user mode，回到第 2 步那条 trap instruction 的下一条。

每个 process 除了 user stack，还有一个只在 kernel mode 下用的 kernel stack（xv6 里是 p->kstack）。第 3 步把 register 存在这里而不是 user stack 上，因为 user stack 的 SP 是 process 自己设的，可能指向任何地方。

看起来对，其实不对System call 就是一个普通的 function call，只是 function 写在 kernel 里

从 program 的角度看，write(1, buf, 3) 长得和 function call 一样，因为 library 把 trap 包在了 function 里面。但 CPU 做的事完全不同：跳转目标由 trap table 而不是 caller 决定；mode 从 user 切到 kernel；register 存到 kernel stack；kernel 要逐个检查 argument。如果它真是普通 call，buf 只要指向 kernel 自己的 memory，write 就会把 kernel 的 data 写到屏幕上。开销也不在一个量级：普通 function call 是几条 instruction；OSTEP 引用的测量里，1996 年的 Linux 一次 system call 约 4 µs，现在的机器也要零点几 µs，相当于几百到上千个 cycle。

Timer interrupt：OS 拿回 CPU 的唯一可靠办法

Process 在 CPU 上跑的时候，OS 的 code 没有在跑。OS 想做任何事，前提是 CPU 先回到它手里。如果只靠 process 自己做 system call 或者主动让出（cooperative 的做法），开头那个 while (1) { } 就永远不还。

解决办法还是硬件：一个 timer，每隔固定的时间（几 ms 量级，NUS 的讲义叫 timer interrupt interval）发一次 interrupt。Interrupt 和 trap 走同一套机制：硬件保存 register，切到 kernel mode，按 trap table 跳到 timer 的 handler。开机时设置 timer 和登记 handler 都是 privileged 的，process 关不掉它。每次 timer interrupt 之后 OS 都能重新决定让谁跑。分给一个 process 一次连续运行的时间叫 time quantum，它是 timer interrupt interval 的整数倍。

Context switch：register 分两次存

OS 决定从 process A 换到 process B，就要把 A 的运行状态存起来、把 B 的装回去。OSTEP 第 6 章把一次 timer interrupt 引起的 switch 拆成两次保存：

  1. 硬件保存。 Timer interrupt 到来时，硬件把 A 的 user register（PC、SP 等）存到 A 的 kernel stack 上，切到 kernel mode，跳进 timer handler。
  2. OS 保存。 Handler 决定换成 B，调用 switch()：把 A 此刻在 kernel 里的 register 存进 A 的 PCB，从 B 的 PCB 里装回 B 的 kernel register，其中包括 SP，于是 stack 换成了 B 的 kernel stack。
  3. 回到 B。 执行 return-from-trap。硬件从当前的 kernel stack（已经是 B 的）恢复 user register，切回 user mode，从 B 上次被打断的地方接着跑。

第 3 步之所以能“回到 B 上次被打断的地方”，是因为 B 上一次离开 CPU 时，也走过同样的第 1、2 步。

Context switch 的代价有直接和间接两部分。直接的是保存和恢复 register、执行 scheduler 本身，OSTEP 引用的 1996 年测量约 6 µs，现在在 1 µs 以下。间接的是 cache：B 刚上来时，cache 里装的多半是 A 的 data，B 的前一段 access 大多是 miss（cache 的道理见 CS2100 第 8 站）。第 5 站会看到 TLB 也有同样的问题。

五个 state

一个 process 在它的一生里不是一直在 CPU 上。按“能不能马上跑”分成五个 state：

State 意思
New 刚创建，OS 还在为它准备 PCB 和 memory
Ready 什么都不缺，只等 CPU
Running 正在 CPU 上跑
Blocked 在等某件事（disk 读完、child 结束、key 被按下），给它 CPU 也没用
Terminated 已经结束，等 OS 回收

用上面的 fork 例子检验。Parent 执行 wait(NULL) 时 child 还没结束，parent 从 Running 进入 Blocked。Child 被 scheduler 选中，Ready 到 Running，打印，exit(0)，进入 Terminated。“child 结束”这个事件让 parent 从 Blocked 回到 Ready，等 scheduler 再选中它才回到 Running，打印第二行。

Ready 和 Running 之间的两条 transition，一条是 scheduler 选中（dispatch），一条是 time quantum 用完被 timer interrupt 换下（preempt）。在 Ready 的一堆 process 里选谁，就是第 2 站的问题。

边界情况Child 先结束、parent 还没 wait：zombie

Child exit 之后，它的 memory 可以立刻回收，PCB 却不能，因为 exit status 存在里面，parent 将来 wait 时要读。这种只剩 PCB 的 process 叫 zombie。Parent 一直不 wait，zombie 就一直占着一个 PCB 和一个 PID。反过来，parent 先结束，child 就成了 orphan，Unix 把它过继给 init（PID 1），由 init 来 wait。

要优化的是什么

Ready 里有好几个 process，CPU 只有一个，scheduler 要决定先跑谁。先要说清“好”指什么。每个 process 的一次 CPU 使用叫一个 burst。对每个 process 定义三个时间：

turnaround time=completion time−arrival time\text{turnaround time}=\text{completion time}-\text{arrival time}turnaround time=completion time−arrival time
waiting time=turnaround time−burst time\text{waiting time}=\text{turnaround time}-\text{burst time}waiting time=turnaround time−burst time
response time=first run time−arrival time\text{response time}=\text{first run time}-\text{arrival time}response time=first run time−arrival time

Waiting time 是在 Ready 里干等的总时间（这里先不考虑 I/O）。Response time 是从到达到第一次拿到 CPU。没有人在等结果的 batch job 关心 turnaround；有人对着屏幕的 interactive job 关心 response。另外还有系统层面的 throughput（单位时间完成几个 job）和 CPU utilization（CPU 忙的时间占比）。

MLFQ：不知道 burst 也能接近 SRT

SRT 要知道剩余时间，RR 不管长短一律平等。Multi-Level Feedback Queue（MLFQ）想做到：不预先知道 burst，靠观察 job 的行为来区分长短。它有几个 priority 不同的 queue，规则是（NUS 讲义的三条，加上同 priority 的处理）：

  1. Priority 高的先跑；priority 相同的之间 RR。
  2. 新 job 进入最高 priority。
  3. Job 用满了它这一级的 time quantum，priority 降一级。
  4. Job 在 quantum 用完之前就主动让出或 blocked，priority 不变。

OSTEP 第 8 章的例子，三级 queue，每级 q=10q=10q=10 ms。一个长的 CPU-bound job A 从最高一级进入，每用满一次 quantum 降一级，20 ms 之后就沉到最低一级。t=100t=100t=100 时来了一个要 20 ms 的短 job B，它进入最高一级，比 A 优先，立刻抢到 CPU；跑满 10 ms 降到中间一级，仍然高于 A，再跑 10 ms 就结束。B 的 turnaround 是 20 ms，和 SRT 下一样。一个每次只用 1 ms CPU 就去等 I/O 的 interactive job，永远在 quantum 用完前让出，按第 4 条一直留在最高一级，response 很好。短 job 和 interactive job 浮在上面，长 job 沉到下面，效果接近 SRT。

但这四条有两个漏洞。

Gaming。 一个 job 每次跑到 quantum 的 99% 时故意做一次无意义的 I/O，按第 4 条它永远留在最高一级，几乎独占 CPU。OSTEP 的修正是把第 3、4 条合并改写：记录 job 在这一级累计用掉的 CPU 时间，累计满了就降级，不管中间让出过几次。

Starvation。 高 priority 的 interactive job 一多，合起来就能占满 CPU，沉到最低一级的长 job 永远轮不到。修正是 priority boost：每隔一段时间 SSS，把所有 job 重新放回最高一级。SSS 没有理论上的最优值，OSTEP 说它要靠调；Solaris 的默认设置是 60 级 queue，quantum 从最高一级的约 20 ms 到最低一级的几百 ms，大约每秒 boost 一次。

两个 process 怎样交换 data

第 1 站里 parent 和 child 的 x 是两份，各改各的。可很多任务需要合作：shell 把 ls 的输出交给 wc，web server 的几个 worker 共用一个 cache。Process 之间交换 data（inter-process communication，IPC）有两条路。

Message passing。 通过 kernel 转交。Unix 的 pipe 就是这样：pipe(p) 得到两个 file descriptor，p[1] 写进去的 byte 从 p[0] 按顺序读出来，中间的 buffer 在 kernel 里。Shell 执行 ls | wc 时先建 pipe 再 fork 两次，第一个 child 把 standard output 换成 p[1] 后 exec("ls")，第二个把 standard input 换成 p[0] 后 exec("wc")，用的正是第 1 站 cat < input.txt 的同一个办法。xv6 book 提醒了一个细节：wc 那一边必须 close 掉自己手里多余的 p[1]，因为 pipe 只有在所有 write end 都关掉之后才会让 reader 读到 end-of-file，wc 自己拿着一个 write end，就会永远等下去。

Message passing 不用担心两边同时改同一份 data，因为 data 由 kernel 排好队交过去。代价是每传一次都要两次 system call（一次 write、一次 read），data 还要先复制进 kernel、再复制出来。

Shared memory。 让两个 process 的 page table 把同一块 physical memory 映射进各自的 address space（第 5 站讲 page table）。建好之后读写就是普通的 load 和 store，不经过 kernel，不复制。代价是两边可能同时改同一个地方，这正是这一站的问题。

如果合作的双方本来就是同一个 program 的两部分，用两个 process 再搭 shared memory 就太绕了。Thread 是更直接的做法：一个 process 里跑多个执行流，共享同一个 address space。

同一个 process 的 thread 之间
共享 code、global data、heap、打开的 file

每个 thread 有自己的 PC，所以能各自走到 code 的不同位置；有自己的 stack，所以 local variable 互不干扰。Global variable 和 heap 是共享的。新建一个 thread 不用复制 memory，在多个 core 上几个 thread 可以真正同时跑。

几个名词：

  • 结果取决于各 thread 执行的先后时机，叫 race condition。
  • 访问共享 data、不能有两个 thread 同时在里面执行的那段 code，叫 critical section。这里就是那三条 instruction。
  • 保证同一时刻最多一个 thread 在 critical section 里，叫 mutual exclusion。

一个正确的 critical section 方案要满足三条：

  1. Mutual exclusion。 最多一个 thread 在里面。
  2. Progress。 里面没人、又有 thread 想进时，必须有一个能进去；不在 critical section 里的 thread 不能挡住别人。
  3. Bounded waiting。 一个 thread 提出要进之后，别人插到它前面的次数有上限，它不会被饿死。

两个看起来对的办法

关掉 interrupt。 进 critical section 前关 interrupt，出来再开。单个 CPU 上，没有 interrupt 就没有 context switch，确实不会被打断。但关 interrupt 是 privileged instruction，让任意 program 执行它，一个 while (1) 就能重新独占机器（第 1 站的问题又回来了）；在多个 CPU 上它也没用，别的 CPU 照样在跑另一个 thread。所以它只用在 OS 自己内部很短的地方。

用一个 flag。

int flag = 0;
void lock(void)   { while (flag == 1) ; flag = 1; }
void unlock(void) { flag = 0; }

看起来对，其实不对用一个 flag variable当 lock 就行：看到 0 就设成 1 进去，别人看到 1 就会等

Peterson's algorithm

两个 thread（编号 0 和 1）只用普通的 load 和 store 也能做到 mutual exclusion。要用两样东西：flag[i] 表示 thread iii 想进去，turn 表示两个都想进时让谁。

int flag[2] = {0, 0};
int turn;

void lock(int self) {              /* self 是 0 或 1 */
    int other = 1 - self;
    flag[self] = 1;                /* 我想进 */
    turn = other;                  /* 但先让你 */
    while (flag[other] == 1 && turn == other)
        ;                          /* 你也想进、而且轮到你：等 */
}
void unlock(int self) { flag[self] = 0; }

Mutual exclusion 的证明。 假设 thread 0 和 thread 1 同时在 critical section 里。两个都执行过 turn = other，turn 只有一个值，看谁最后写的。不妨设 thread 0 最后写，它写的是 turn = 1。此后在两人都离开 critical section 之前，没有人再写 turn，所以 thread 0 做 while 判断时 turn == 1，turn == other 成立。Thread 0 要能通过 while，就必须读到 flag[1] == 0。可是 thread 1 在写 turn 之前已经写了 flag[1] = 1，那发生在 thread 0 写 turn 之前，也就在 thread 0 判断之前；thread 1 进了 critical section 还没出来，flag[1] 仍然是 1。Thread 0 读到的只能是 1，过不去，矛盾。设 thread 1 最后写也一样。所以两人不可能同时在里面。

另外两条也满足。Progress：只有一个 thread 想进时，flag[other] == 0，它立刻通过。Bounded waiting：thread 1 出来后如果马上又想进，它会重新执行 turn = 0，把机会让给正在等的 thread 0，所以 thread 0 最多被插队一次。

把 counter = counter + 1 包在 lock(self) 和 unlock(self) 之间，上面那种重叠就不可能发生，结果是 20,000,000。

Peterson 的局限：只适用于两个 thread；而且 OSTEP 指出，现代 CPU 为了速度会调换 load 和 store 的顺序，上面证明里“先写 flag 再写 turn”在 hardware 上不一定成立，不加 memory barrier 就会失效。

Hardware 的帮助：TestAndSet

Flag lock 失败是因为“读旧值”和“写新值”是两步。如果 hardware 保证这两步不可分割（atomic），问题就没了。TestAndSet 就是这样一条 instruction：

/* hardware 一步完成，中间不会被打断，也不会被别的 CPU 插进来 */
int TestAndSet(int *p) { int old = *p; *p = 1; return old; }

void lock(int *L)   { while (TestAndSet(L) == 1) ; }
void unlock(int *L) { *L = 0; }

Lock 空着时 *L == 0。几个 thread 同时执行 TestAndSet，hardware 让它们一个一个来，只有第一个拿到旧值 0 并把它设成 1，其余拿到的都是 1，继续转圈。这种一直转圈检查的 lock 叫 spin lock。

它满足 mutual exclusion，但不满足 bounded waiting：谁抢到全看时机，一个 thread 可能一直抢不到。在单个 CPU 上它还很浪费。设 q=10q=10q=10 ms，4 个 thread 抢同一个 lock，持有者在 critical section 里被 timer interrupt 换下。另外 3 个 thread 依次上来，各自把整个 quantum 都花在 while 里转圈，因为持有者不上 CPU 就不会 unlock。持有者再次拿到 CPU 之前，白白浪费了 3×10=303\times10=303×10=30 ms。

所以等待的 thread 不应该转圈，应该进入 Blocked，让出 CPU，等 lock 被释放时再被叫醒。这就是下一站 semaphore 做的事。

边界情况多个 CPU 上 spin lock 反而合适

Critical section 通常只有几条 instruction。持有者在另一个 CPU 上跑着，马上就会 unlock，这时转几圈比做一次 context switch（第 1 站，微秒量级）便宜。OSTEP 的结论是：thread 数和 CPU 数差不多时，spin lock 表现不错。

void producer(void) {
    while (1) {
        item x = produce();
        wait(notFull);
        wait(mutex);
        buf[in] = x;  in = (in + 1) % K;
        signal(mutex);
        signal(notEmpty);
    }
}

        wait(notEmpty);
        wait(mutex);

        signal(mutex);
        signal(notFull);

Deadlock

上面这种“每个人都在等另一个人手里的东西”叫 deadlock。它不是罕见的毛病：OSTEP 引用 Lu 等人对 MySQL、Apache、Mozilla、OpenOffice 的研究，105 个 concurrency bug 里有 31 个是 deadlock。

最小的例子是两个 thread、两个 lock，拿的顺序相反：

/* Thread 1 */            /* Thread 2 */
lock(L1);                 lock(L2);
lock(L2);                 lock(L1);

Thread 1 拿到 L1 之后被换下，Thread 2 拿到 L2。接着 Thread 1 等 L2，Thread 2 等 L1，谁都不会放手。

Deadlock 要四个 condition 同时成立（Coffman 等人）：

  1. Mutual exclusion。 资源一次只能给一个 thread。
  2. Hold and wait。 Thread 拿着已有的资源，同时等新的。
  3. No preemption。 资源不能从持有者手里强行拿走。
  4. Circular wait。 存在一圈 thread，每个都在等下一个手里的资源。

四个缺一个就不会 deadlock，所以 prevention 就是挑一个打破。

Dining philosophers：拆掉 circular wait

五个 philosopher 围坐一桌，相邻两人之间放一根 chopstick，一共五根。吃饭要同时拿起左右两根。每个人的做法都是先拿左边、再拿右边。

如果五个人同时拿起左边那根，每人手里一根，都在等右边那根，而右边那根在右边邻居手里。五个人围成一圈，四个 condition 全部成立。

打破 circular wait 的办法是给所有资源定一个 total order，规定每个 thread 只能按从小到大的顺序拿。把 chopstick 编号 0 到 4，philosopher iii 坐在 chopstick iii 和 (i+1) mod 5(i+1)\bmod5(i+1)mod5 之间，每人先拿编号小的那根。Philosopher 0 到 3 仍然是先左后右，philosopher 4 的两根是 4 和 0，他先拿 0。

为什么 lock ordering 一定不会有 circular wait。 按顺序拿 lock 的 thread，在等 lock bbb 时手里拿着的每个 lock 编号都小于 bbb。假设出现了一圈：thread T1T_1T1​ 拿着 a1a_1a1​、等 a2a_2a2​，a2a_2a2​ 在 T2T_2T2​ 手里；T2T_2T2​ 拿着 a2a_2a2​、等 a3a_3a3​；……；TmT_mTm​ 拿着 ama_mam​、等 a1a_1a1​。每个 thread 都是“拿着的比等着的小”，于是

a1<a2<⋯<am<a1a_1<a_2<\cdots<a_m<a_1a1​<a2​<⋯<am​<a1​

不可能。所以 circular wait 不会出现，deadlock 也就不会出现。前面两个 lock 的例子，规定先 L1 后 L2，Thread 2 改成先 lock(L1)，就修好了。

打破另外三个 condition 也各有办法，但各有代价：

  • Hold and wait。 一次把所有要用的 lock 都拿到，例如先拿一个全局的 lock 再依次拿其他的。这要求事先知道要哪些，而且降低了 concurrency。
  • No preemption。 用 trylock：拿不到就把手里的都放掉，过一会儿重来。可能出现 livelock：两个 thread 一直同时放、同时重试，都在动却都没有进展；加一个随机的等待时间可以缓解。
  • Mutual exclusion。 用 compare-and-swap 这类 atomic instruction 写不需要 lock 的 data structure。写起来很难。

也可以不预防，允许 deadlock 发生，再定期检查“谁在等谁”构成的 graph 里有没有 cycle，有就重启其中某个 thread。很多 database 是这样做的。

边界情况Deadlock 和 starvation 不是一回事

Contiguous allocation 卡在哪

最简单的做法是给每个 process 一整段连续的 physical memory。Process 的 code 里用的 address 都从 0 算起（叫 logical address 或 virtual address），CPU 里放两个 register：base 是这段 memory 的起点，limit 是它的长度。每次 access，hardware 检查 virtual<limit\text{virtual}<\text{limit}virtual<limit，然后访问 base+virtual\text{base}+\text{virtual}base+virtual。越界就触发 exception。Process 换上 CPU 时，OS 把它的 base 和 limit 装进去，所以每个 process 都以为自己从 address 0 开始。

问题就是开头第三件事。Process 来来去去，留下大小不一的空洞。开头那张图里空着 16 KB，最大的一块却只有 6 KB，10 KB 的 process 放不下。空闲 memory 被切碎、单块不够用，叫 external fragmentation。把正在跑的 process 往一边挪，空洞就能合并（compaction），可挪动时要复制它们的全部 memory，这段时间里这些 process 都不能跑。

根子在“连续”两个字。如果一个 process 的 memory 可以拆成小块、分散放在任何空着的地方，16 KB 的空闲就都能用上。

Page 与 frame

Paging 把 virtual address space 切成固定大小的 page，把 physical memory 切成同样大小的 frame。任何一个 page 可以放进任何一个空 frame。每个 process 有一张 page table，第 iii 项记着 virtual page iii 放在哪个 frame。

因为 page 的大小是 2 的 power，切分只是把 address 的 bit 分成两段：高位是 virtual page number（VPN），低位是 page 内的 offset。翻译时 offset 原样保留，只把 VPN 换成 physical frame number（PFN）。

OSTEP 的小例子：virtual address space 64 byte，page 16 byte，所以有 4 个 page；physical memory 128 byte，有 8 个 frame。Page table 是 VP 0 → PF 3，VP 1 → PF 7，VP 2 → PF 5，VP 3 → PF 2。

翻译 virtual address 21。64 byte 要 6 个 bit（26=642^6=6426=64），每个 page 16 byte，offset 占低 4 位，VPN 占高 2 位。21 的 binary 是 010101010101010101：VPN 是 010101，即 page 1；offset 是 010101010101，即 page 里第 5 个 byte。查表，page 1 在 frame 7，binary 111111111。把 VPN 换成 PFN，得到 111 0101111\,01011110101，即 64+32+16+4+1=11764+32+16+4+1=11764+32+16+4+1=117。

在 paging 下，memory 从一开始就按 frame 分配和回收，空出来的也总是整数个 frame。把开头的例子换成 4 KB 的 frame 来想：16 KB 空闲就是 4 个空 frame，10 KB 的 process 要 3 个 page，放进哪 3 个空 frame 都行，它们挨不挨着无所谓。

Context switch 之后的 TLB

TLB 里的一项只说“VPN 10 → PFN 100”，没说是哪个 process 的。Process P1 的 VPN 10 在 frame 100，P2 的 VPN 10 在 frame 170。从 P1 切到 P2 之后，如果 TLB 里还留着 P1 的那项，P2 访问 VPN 10 就会 hit 到 P1 的 frame，读到别人的 data。

Page 不一定在 memory 里

有了 page table，page 放在哪个 frame 已经由 OS 说了算。再走一步：page 也可以暂时不在 memory 里，放在 disk 上，用到了再搬进来。这样所有 process 的 address space 加起来可以比 physical memory 大，每个 process 也只需要把正在用的 page 留在 memory 里。这叫 virtual memory。

每个 PTE 里有一个 present bit（也叫 valid 或 resident bit）。Hardware 翻译时发现 present bit 是 0，就触发一个 exception，叫 page fault，交给 OS：

  1. Hardware 查 page table，发现这个 page 不在 memory，trap 进 kernel。
  2. OS 确认这个 address 是合法的（不合法就是 segmentation fault，杀掉 process）。
  3. 在 disk 上找到这个 page 的位置。
  4. 找一个空 frame；没有空的，就挑一个 page 赶出去（下面的 page replacement）。
  5. 从 disk 把 page 读进这个 frame。读 disk 要几 ms，这期间 process 进入 Blocked，CPU 去跑别人。
  6. 更新 PTE：填上 PFN，present bit 设为 1。
  7. 回到引起 page fault 的那条 instruction，重新执行。这次翻译成功。

第 7 步和 system call 不同：system call 回到 trap 的下一条 instruction，page fault 要重新执行同一条。

一个 page 只在第一次被用到时才搬进来，叫 demand paging。新 process 启动时一个 page 都不在 memory 里，所以启动快，但最初一段会连续 page fault。

看起来对，其实不对TLB miss 就是 page fault

两件事发生在不同的层，代价差了五个数量级。TLB miss 是 TLB 里没有这个翻译，page 本身多半就在 memory 里；hardware 走一遍 page table（上一站的例子里多两次 memory access，约 200 ns）就解决了，OS 甚至不知道。Page fault 是 PTE 说这个 page 不在 memory 里，要 OS 介入、从 disk 读，约 10 ms，即 10710^7107 ns。顺序是：先查 TLB；miss 了去走 page table；走到 PTE 发现 present bit 是 0，才是 page fault。

赶走哪一个

Belady's anomaly 与 stack property

直觉上 frame 越多，page fault 越少。FIFO 不一定。Reference string 1,2,3,4,1,2,5,1,2,3,4,51,2,3,4,1,2,5,1,2,3,4,51,2,3,4,1,2,5,1,2,3,4,5，每一步之后 frame 里的 page（M 是 miss，H 是 hit）：

access 1 2 3 4 1 2 5 1 2 3 4 5

4 个 frame M 1 M 12 M 123 M 1234 H 1234 H 1234 M 2345 M 1345 M 1245 M 1235 M 1234 M 2345

3 个 frame 有 9 次 page fault，4 个 frame 反而有 10 次。这叫 Belady's anomaly。分叉在第 7 次 access（page 5）：3 个 frame 时赶走的是 4，留下了马上要用的 1 和 2；4 个 frame 时赶走的是 1，之后 1、2、3、4 依次被赶走又依次被用到。

LRU 不会这样。原因是它有 stack property：nnn 个 frame 的 LRU，任何时刻装着的是“最近用过的 nnn 个不同的 page”；n+1n+1n+1 个 frame 装着的是“最近用过的 n+1n+1n+1 个不同的 page”。前者永远是后者的 subset。所以 nnn 个 frame 时 hit 的 access，n+1n+1n+1 个 frame 时一定也 hit，page fault 只会更少。FIFO 的内容取决于“什么时候进来的”，加一个 frame 会改变后面每一次赶走谁，没有这种包含关系；上表第 7 步之后，3 个 frame 的 {1,2,5}\{1,2,5\}{1,2,5} 就不是 4 个 frame 的 {2,3,4,5}\{2,3,4,5\}{2,3,4,5} 的 subset。

LRU 太贵，用 Clock 近似

真正的 LRU 要在每一次 memory access 时记下时刻（每个 PTE 一个 counter，赶走时找最小的），或者维护一个按使用先后排的 stack（每次 access 把那个 page 挪到顶上）。每次 access 都要做额外的事，hardware 支持不起。

Hardware 能便宜做到的，是每次 access 时把 PTE 里的 reference bit 设成 1。Clock（也叫 second chance）只用这一个 bit：所有 frame 排成一圈，一根 clock hand 指着下一个候选。要赶走一个时，看指针下的 page：

  • reference bit 是 1：最近用过，给它第二次机会，把 bit 清成 0，hand 往前走一格。
  • reference bit 是 0：从上次 hand 经过到现在都没被用过，赶走它。

最近被用过的 page 总能躲过一轮，被赶走的是hand 转一圈都没人碰过的 page，近似“最久没用过”。

边界情况所有 reference bit 都是 1 时，Clock 就是 FIFO

拿上面 OSTEP 那串 reference string 走 Clock（hand 从 frame 0 开始，page 装进来时 reference bit 设为 1）。到第 6 次 access（page 3）要赶人时，0、1、2 刚刚都被用过，三个 bit 全是 1。hand 转一整圈把它们都清成 0，回到起点，赶走 frame 0 里的 page 0，和 FIFO 一样。往后每次要赶人时情况相同，最后 Clock 也只有 4 次 hit，和 FIFO 完全相同。Reference bit 只有在“有的用过、有的没用过”时才有区分能力。

Thrashing 与 working set

Frame 怎样分给各个 process：可以平均分，可以按 process 的大小按比例分。Page fault 时赶谁，也有两种范围：只在自己的 page 里挑（local replacement），或者在所有 process 的 page 里挑（global replacement）。Global 更灵活，但一个 process 的大量 page fault 会抢走别人的 frame，让别人也开始 page fault。

File descriptor 背后的三张表

Disk 本身只提供“读写第 nnn 个 block”。Program 想要的是有名字、能按 byte 读写、能变长的 file。File system 就是在 block 之上搭出这层。

Process 用 open 打开一个 file，得到一个小 integer，叫 file descriptor；之后 read、write 都拿它当参数。它背后是三层：

  1. 每个 process 一张 file descriptor table。 Descriptor 就是这张表的 index，表项指向下一层。0、1、2 照惯例是 standard input、output、error。
  2. 整个系统一张 open file table。 每次 open 产生一项，记着当前的 offset（下一次读写从第几个 byte 开始）、打开的 mode，以及有几个 descriptor 指向它。
  3. 每个打开的 file 一个 in-memory inode。 File 本身的信息：大小、owner、permission、data 在 disk 的哪些 block 上。同一个 file 被打开几次都只有一个。

为什么 offset 放在第二层而不是第一层或第三层，看一个例子：

int fd = open("log.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
if (fork() == 0) {
    write(fd, "child\n", 6);
    exit(0);
}
wait(NULL);
write(fd, "parent\n", 7);

fork 复制的是 descriptor table，复制出的表项指向同一个 open file table 项，于是共享同一个 offset。Child 写 6 个 byte，offset 从 0 变成 6；parent 接着从 6 开始写，file 最后是 13 个 byte：child\nparent\n。

如果改成两个 process 各自 open 一次，就有两项、两个 offset，都从 0 开始。Child 写下 child\n，parent 从 offset 0 写 parent\n，7 个 byte 把前 6 个全部盖掉，file 只剩 parent\n。Shell 执行 (echo a; echo b) > out 时，两条命令的输出能依次排好，靠的就是前一种共享。

一个 file 的 block 放在哪

File 的 data 存在若干个 block 里（下面都取 block 4 KB）。Inode 里要记下“这个 file 的第 0、1、2…个 block 在 disk 的哪里”。有四种记法，比较的是两件事：能不能快速找到第 kkk 个 block（random access），以及记这些位置要占多少空间。

Contiguous。 每个 file 占一段连续的 block，只记起点和长度。第 kkk 个 block 就在 起点+k\text{起点}+k起点+k，random access 最快。但这和第 5 站的 contiguous memory 一模一样：file 删来删去留下空洞，产生 external fragmentation；file 要变长时，后面的 block 可能已经被别人占了。

Linked list。 每个 block 末尾存下一个 block 的编号，inode 只记第一个。任何空 block 都能用，没有 external fragmentation。代价是找第 kkk 个 block 要从头读 kkk 个 block，每一次都是一次 disk read；而且每个 block 少了 4 byte 能放 data。

FAT（File Allocation Table）。 把所有 block 里的“下一个” pointer抽出来，集中放在一张表里，开机时整张读进 memory。表的第 iii 项是 block iii 的下一个 block 的编号，最后一个 block 记一个 end-of-file 标记，空 block 记 0。Directory 里记着 file 的第一个 block。

例子：一个 file 从 block 5 开始，FAT[5] = 9，FAT[9] = 2，FAT[2] = EOF，所以它依次占 block 5、9、2。要读它的第 2 个 block（从 0 数），在 memory 里走 5 → 9 → 2，然后只读一次 disk。

FAT 的问题是大小。1 TB 的 disk、4 KB 的 block，一共 240/212=2282^{40}/2^{12}=2^{28}240/212=228 个 block。每项 4 byte，FAT 要 228×4 B=12^{28}\times4\text{ B}=1228×4 B=1 GB，整张放在 memory 里太大；而且 random access 虽然不读 disk，仍要在 memory 里走一条可能很长的 chain。

Indexed（inode）。 每个 file 自己一张 index，按顺序列出它所有 block 的编号，第 kkk 个就是 index 的第 kkk 项。只有打开的 file 的 index 需要在 memory 里。问题是 index 多长：固定得长，小 file 浪费；固定得短，大 file 放不下。

ext2 的 inode：不平衡的 index tree

ext2（以及 OSTEP 的教学用 file system）的 inode 里有 15 个 block pointer：

  • 前 12 个是 direct pointer，直接指向 data block。
  • 第 13 个是 single indirect：指向一个装满 pointer 的 block。4 KB 的 block、4 byte 的 pointer，一个 block 装 4096/4=10244096/4=10244096/4=1024 个 pointer。
  • 第 14 个是 double indirect：指向一个 block，里面 1024 个 pointer 各指向一个 single indirect block。
  • 第 15 个是 triple indirect，再多一层。

各级能覆盖的 data：

single indirect 102410241024 4 MB
double indirect 10242=2201024^2=2^{20}10242=220 4 GB

只用 direct 和 single indirect 的最大 file 是 (12+1024)×4 KB=4144(12+1024)\times4\text{ KB}=4144(12+1024)×4 KB=4144 KB。加上后两级，上限约 4 TB。

这个 tree 故意不平衡。OSTEP 引用的测量显示，最常见的 file 只有约 2 KB，大多数 file 很小：它们只用 direct pointer，读 inode 之后就能直接找到 data。少数大 file 才走 indirect，多读一两次 disk 相对于读几 GB 的 data 微不足道。

  1. 它在第几个 block：⌊5,000,000/4096⌋=1220\lfloor5{,}000{,}000/4096\rfloor=1220⌊5,000,000/4096⌋=1220，block 内的 offset 是 5,000,000−1220×4096=28805{,}000{,}000-1220\times4096=28805,000,000−1220×4096=2880。
  2. Block 0 到 11 归 direct pointer。1220≥121220\ge121220≥12，减掉之后是 1208。
  3. 接下来 1024 个归 single indirect（block 12 到 1035）。1208≥10241208\ge10241208≥1024，减掉之后是 184，所以在 double indirect 下面。

要读的 disk block 依次是：inode、double indirect block、single indirect block、data block，一共 4 次（inode 已经在 memory 里就是 3 次）。

Directory 与 path lookup

Directory 也是一个 file，它的 data 是一张表，每项是一个名字和一个 inode number。Root directory 的 inode number 是约定好的（ext2 里是 2）。

OSTEP 数过打开 /foo/bar 要读几次 disk（假设每个 directory 的内容只占一个 block）：

  1. 读 root 的 inode，找到 root directory 的 data 在哪。
  2. 读 root directory 的 data，找到 foo 的 inode number。
  3. 读 foo 的 inode。
  4. 读 foo 的 data，找到 bar 的 inode number。
  5. 读 bar 的 inode，检查 permission，在 open file table 里建一项，返回 descriptor。

一共 5 次，path 每多一层就多两次。之后每 read 一个 block 又要 3 次 I/O：读 inode 找到 block 的位置，读 data block，再把 inode 写回去更新最后访问时间。所以 bar 有 3 个 block 时，打开再读完一共约 5+3×3=145+3\times3=145+3×3=14 次 I/O。实际系统会把最近用过的 inode 和 directory block cache 在 memory 里，大部分这样的读都不用真的去 disk。

两个 directory 项可以写同一个 inode number，这叫 hard link。两个名字指向同一个 file，没有哪个是“原件”。Inode 里有一个 link count，记着有几个名字指向它。Symbolic link 则是一个单独的小 file，内容是另一个 path；原 file 删掉后，它就指向一个不存在的 path。

看起来对，其实不对删除一个 file，就是把它的 data 从 disk 上抹掉

Unix 删除 file 的 system call 叫 unlink：它只是把 directory 里那一项去掉，并把 inode 的 link count 减 1。只有 link count 变成 0、而且没有 process 还开着它时，file system 才回收 inode 和 data block，也就是在 free space 的记录里把它们标成空闲。Data block 里的 byte 原封不动，直到被新 file 覆盖。所以用 hard link 多建一个名字之后再删掉原名，file 照样能读；刚删的 file 常常还能被恢复工具找回来。

Free space：bitmap

File system 还要知道哪些 block 和 inode 是空的。最常见的做法是 bitmap：每个 block 一个 bit，0 是空，1 是已用；inode 另有一张。一个 4 KB 的 bitmap block 有 4096×8=32,7684096\times8=32{,}7684096×8=32,768 个 bit，管 32,768×4 KB=12832{,}768\times4\text{ KB}=12832,768×4 KB=128 MB 的 data。1 TB 的 disk 有 2282^{28}228 个 block，bitmap 是 2282^{28}228 bit =32=32=32 MB，是同一块 disk 上 FAT 的 1/321/321/32，因为每个 block 只记 1 bit 而不是 4 byte 的 pointer。

建一个新 file、写一个新 block，都要先在 bitmap 里找一个 0、改成 1、写回 disk。OSTEP 数过：给 file 追加一个新 block 要 5 次 I/O（读写 data bitmap、读写 inode、写 data block）。
