从进度块恢复

先看三件事。

第一件。 一张电子照片可以复制一百份，每份都和原件一模一样。如果“一个 coin”只是一个文件，持有人把它发给 Bob 之后，手里还留着一份，可以再发给 Carol。数字世界里复制几乎不要成本，所以任何数字形式的 money 首先要回答：怎样阻止同一个 coin 被花两次。这叫 double spending problem。

第二件。 Bank 早就解决了这个问题：balance 不在你手里，在 bank 的 ledger 上，转账就是 bank 在 ledger 上一边减、一边加。代价是所有人都要相信这个 ledger 的维护者：它不乱记、不冻结、不拒绝服务、不在倒闭时把账本一起带走。

第三件。 2023 年 3 月 10 日晚，issue USDC 的 Circle 宣布有 33 亿 USD 的 reserve 困在刚倒闭的 Silicon Valley Bank，约占它 reserve 的 8%。按 reserve 算，每个 USDC 最坏也值 0.92 USD 左右，但第二天它在市场上跌到了 0.86。

这门课要回答的问题由这三件事串起来：在没有一个大家都信任的维护者时，怎样让很多互不信任的人维护同一个 ledger（第 1 到 4 站）；ledger 上除了记账还能跑什么 program，这些 program 能做什么、不能做什么（第 5、6 站）；用这些技术造出来的“money”在经济上靠什么维持价值，又在哪里失效，和 central bank 发的 money 有什么不同（第 7、8 站）。NUS 的课程描述把这条线概括为：先弄清 blockchain 在技术上怎样工作，再评估一个 blockchain application 的 business、economic 和 financial performance 与它的技术设计之间的关系。前半学期在 Ethereum 上做一个 application，后半学期分析已有的 application。

先造一个最简单的 coin，看它在哪里坏掉

Princeton 的书从一个故意做得很简陋的 coin 开始，叫 GoofyCoin。规则只有两条：

  1. Goofy 可以随时造新 coin：签一条“CreateCoin [一个新的 ID]”。
  2. 谁持有一个 coin，谁就能把它转给别人：签一条“Pay this to public key X”，其中 “this” 是一个指向上一条记录的 pointer（书里用的是下面要讲的 hash pointer）。

验证一个 coin 是否有效，就顺着 pointer 一路往回查，每一步的 signature 都对得上，最后到达 Goofy 的 CreateCoin。

这里用到的 digital signature 是三个 algorithm：Gen()\mathrm{Gen}()Gen() 生成一对 key (sk,pk)(sk,pk)(sk,pk)；Sign(sk,m)\mathrm{Sign}(sk,m)Sign(sk,m) 对 message mmm 生成 signature σ\sigmaσ；Verify(pk,m,σ)\mathrm{Verify}(pk,m,\sigma)Verify(pk,m,σ) 输出 accept 或 reject。它的安全性是：只看到 pkpkpk 和一些别的 message 的 signature，造不出一条新 message 的 signature。和手写签名的关键区别在于，σ\sigmaσ 依赖于 mmm，把一份文件上的 signature 剪下来贴到另一份上，Verify 会 reject。

现在 Alice 持有一个 GoofyCoin。她签一条“把它付给 Bob”，又签一条“把它付给 Chuck”。两条都是她亲手签的，都能通过 Verify。Bob 和 Chuck 各自顺着 pointer 往回查，都觉得这个 coin 是自己的。

看起来对，其实不对Digital signature 能防止 double spending

Signature 证明的是“这个 coin 的主人同意了这笔转账”，它回答 authorization 的问题。Double spending 是另一个问题：主人同意了两次，而两次互相矛盾。要发现矛盾，必须知道所有已经发生的转账。Nakamoto 论文第 2 节说的就是这一点：确认一笔 transaction 没有发生过的唯一办法，是知道所有 transaction。Signature 是局部的，double spending 是全局的。

加一个记账人：ScroogeCoin

既然要知道所有转账，就让一个人把它们全记下来。ScroogeCoin 里，Scrooge 维护一个只能往后追加的 ledger，每条 transaction 有一个 transaction ID，Scrooge 对最新的记录签名后公开。Transaction 有两种：

  • CreateCoins：造新 coin，一次可以造好几个。每个 coin 有 transaction 内的序号、面值和收款人的 public key；coinID 是“transaction ID + 序号”。只要 Scrooge 签了，它就有效。
  • PayCoins：消费掉若干旧 coin，造出总值相同的新 coin，分给不同的人。

一笔 PayCoins 只有出现在 Scrooge 签名的 ledger 上才算数，Scrooge 只接受满足四条的：

  1. 被消费的 coin 确实是以前某笔 transaction 造出来的；
  2. 被消费的 coin 以前没有被消费过；
  3. 新造出的总值等于消费掉的总值（只有 Scrooge 能凭空造价值）；
  4. 被消费的每个 coin 的主人都签了名。

第 2 条就是 double spending 的解法：Alice 的第二笔转账会被 Scrooge 拒绝。

ScroogeCoin 里的 coin 是 immutable 的：不能拆、不能合并、不能改，每个 coin 只在一笔 transaction 里被造出一次、在另一笔里被消费一次。要把一个面值 5 的 coin 拆成 3 加 2，就写一笔 PayCoins 消费掉它，造出两个新 coin，都付给自己。第 4 站会看到，Bitcoin 的 UTXO 正是这个设计。

代价也清楚：Scrooge 可以拒绝替某人记账（censorship），可以收任意的 fee，可以给自己造 coin，可以哪天不干了。这正是开头第二件事里 bank 的位置。整个 Bitcoin 的设计可以看成一个问题：把 Scrooge 换成一群互不信任、随时可以加入和离开的人，还能不能得到同一个 ledger？

在换掉 Scrooge 之前，先解决一个更小的问题：即使 Scrooge 诚实，他公开的 ledger 怎样防止事后被人改动？

Hash pointer：把 commitment 串起来

普通 pointer 记的是“数据在哪”。Hash pointer 再加一项：数据的 hash。顺着它取到数据时，可以重算 hash 检查数据有没有被改过。

把 ledger 按 block 分组，每个 block 里放一个指向前一个 block 的 hash pointer，就得到一条 block chain。

Block 2 的内容一改，它的 hash 就从 e0011e51 变成 391fb577，而 block 3 里存的还是 e0011e51，对不上。要掩盖，就得把 block 3 的 prev 也改掉，于是 block 3 的 hash 变了，block 4 又对不上……一直要改到最新的 block。所以只要把最新一个 block 的 hash（叫 head）存在一个改不了的地方，整条历史中任何一处改动都会被发现。

这把“保护整个 ledger”化简成了“大家对一个 32 byte 的 head 达成一致”。下一站讨论的 consensus，本质上就是在争这个 head。

换掉 Scrooge 难在哪里

想让一群 node 轮流当 Scrooge：每轮选一个 node 提议下一个 block，其他 node 检查后接在后面。要回答两个问题。

选谁？ 如果按“一个 node 一票”，attacker 可以凭空造出一百万个 node，这叫 Sybil attack。在一个任何人都能加入、没有身份登记的 network 里，node 的数目不能当作权重。CS251 的说法是：必须把权重绑在一种造不出来、很稀缺的资源上。Proof of work 用的是 hash power，proof of stake 用的是锁定的 coin（第 3 站）。

选出的 node 作恶怎么办？ 它偷不了别人的 coin，因为偷要伪造 signature。它可以不收录某人的 transaction，但下一轮换了 honest 的 node，那笔 transaction 还是会进来。它真正能做的坏事是 double spending，后面细算。

换一种稀缺资源

Proof of work 的问题上一站已经列出：没有 finality，事后无法 punish，耗电。Proof of stake 把稀缺资源从 hash power 换成 coin：想参与 consensus，先把 coin 锁进一个 contract（stake）。被选为 leader 的 probability 和投票的权重都按 stake 算，当 leader 拿 reward，相当于 stake 的 interest。

关键的新东西是 punishment。Validator 的每一票都是一个 digital signature，签在“某个 epoch 的某个 block”上。如果一个 validator 给同一个 epoch 里两个冲突的 block 都签了名，这两个 signature 本身就是证据，任何人都可以提交，protocol 把他锁定的 stake 烧掉。这叫 slashing。Proof of work 里作恶的 miner 只是白花电费，proof of stake 里作恶的 validator 会被点名并没收 stake。

2/3 quorum 为什么 safe

CS251 用一个最简单的 protocol 说明：nnn 个 validator，一个 block 得到至少 2n/32n/32n/3 个 validator 的 signature 就 finalize。

假设出了事故：两个冲突的 block X、Y 都 finalize 了。设 X 的 signature 集合是 AAA，Y 的是 BBB，∣A∣≥2n/3|A|\ge2n/3∣A∣≥2n/3，∣B∣≥2n/3|B|\ge2n/3∣B∣≥2n/3。两个集合都在 nnn 个 validator 里，所以

∣A∩B∣ ≥ ∣A∣+∣B∣−n ≥ 2n3+2n3−n=n3|A\cap B|\ \ge\ |A|+|B|-n\ \ge\ \frac{2n}3+\frac{2n}3-n=\frac n3∣A∩B∣ ≥ ∣A∣+∣B∣−n ≥ 32n​+32n​−n=3n​

重叠的这些 validator 每人都签了两个冲突的 block，违反了规则。所以：只要作恶的 validator 少于 n/3n/3n/3，safety 就不会被破坏；一旦被破坏，至少能点名 n/3n/3n/3 个作恶者，而且不会冤枉 honest 的 validator，因为 honest 的人不会签两次。CS251 把这个性质叫 accountable safety。

这个论证没有用到“消息多久送达”。所以即使 network 任意延迟（asynchrony），已经 finalize 的 block 也不会被推翻，这就是 finality。对比上一站：Bitcoin 的 safety 依赖于 network 延迟有上界。

上面的 protocol 只证明了 safety。CS251 在脚注里指出它的 liveness 有洞：leader 作恶时，把 block X 发给一半 validator、把冲突的 block Y 发给另一半。n=9n=9n=9 时两边各得 4 到 5 票，都不到 6，这一轮什么都 finalize 不了；每轮轮到作恶的 leader 都可以这样做，而且没有任何 validator 签过两次，抓不到证据，也就 slash 不了谁。补上这个洞要用 PBFT 那一类 protocol 的多轮投票，现代的实现有 Tendermint 和 HotStuff。

Ethereum 怎样把两种性质拼在一起

CS251 指出还有一个更根本的冲突。Bitcoin 有 dynamic availability：参与的 node 来来去去，只要还有 honest 的 miner 在线，chain 就继续长。Finality 要求 quorum，在线的人少于 2/3 时就停。可以证明：一个 protocol 不可能在 network 可能分区的条件下同时做到两者。CS251 称之为 blockchain 的 CAP theorem。

CS251 的证明用三个“世界”。World 1：Alice 以为别人都掉线了，只有她在线，按 dynamic availability 她必须继续出 ledger，得到 tx1、tx2、tx3。World 2：Bob 以为别人都掉线了，得到相反的顺序 tx3、tx2、tx1。World 3：其实大家都在线，只是 network 分区，Alice 和 Bob 互相收不到消息。Alice 分不清自己在 World 1 还是 World 3，Bob 也一样，所以在 World 3 里他们各自照 World 1、2 的样子出 ledger，两本 ledger 冲突，safety 破了；而 finality 要求的正是“分区时也 safe”。

Ethereum 的办法是两层 ledger：底下一条 available chain 一直往前长（fork choice 用 LMD GHOST），上面每隔一段由 validator 投票做 checkpoint，得到 2/3 票的 checkpoint 就 finalize（Casper FFG）。Finalized chain 永远是 available chain 的 prefix。用户自己选信哪一条。CS251 的例子是周末：在线的 validator 少了，可能是大家去度假，也可能是 network 分区，从链上分不出来。卖 boba 的小摊每笔金额小，跟着 available chain，周末照常营业，承担分区时被 double spend 的风险；卖车的经销商承受不了一次 double spend，跟着 finalized chain，周末 finalized chain 可能停住，他就等到周一在线的人多了、恢复 liveness 再交车。

Ledger 记什么：每一笔还是每个人

MIT 15.S12 第二讲里 Gensler 说：Bitcoin 是一种存 transaction 的机制，另一些 blockchain（例如 Ethereum）存的是 balance。按这句话可以把 ledger 分成两种：transaction ledger 记一笔笔资金的移动，balance ledger 记每个 account 现在有多少。两种都能防 double spending，但“检查一笔钱有没有被花过”的办法不同，由此带来一串不同的性质。

UTXO：只记还没被花掉的 output

Bitcoin 里没有“Alice 的 balance”这个数。每笔 transaction 有若干 input 和若干 output。Output 写着金额和一段锁定 script（谁能花它）；input 指向以前某笔 transaction 的某个 output，并提供解锁所需的证据（通常是 signature）。还没被任何 input 指过的 output，叫 UTXO（unspent transaction output）。全网 node 都在内存里维护当前所有 UTXO 的集合。2025 年 9 月前后大约有 1.66 亿个，比当年 1 月的峰值 1.875 亿少了约 11%；CS251 Fall 2022 的 slide 记的 2022 年 9 月是约 8,500 万个。

一个 output 只能整个花掉。Alice 要付 5 BTC，只能把整个 7 BTC 的 output 当 input，再造两个 output：5 BTC 给 Bob，1.9998 BTC 找零给自己。Input 总额减 output 总额就是 fee，7−6.9998=0.00027-6.9998=0.00027−6.9998=0.0002 BTC，归 miner。Fee 不写在任何地方，是差额。

Miner 对每个 input 检查三件事：

  1. 它指向的那个 output 在当前 UTXO set 里，也就是还没被花掉。
  2. 解锁 script 接上锁定 script 运行后返回 true。
  3. Input 总额 ≥\ge≥ output 总额。

第一条就是 ScroogeCoin 里的“尚未花掉”。Double spend 就是两笔 transaction 指向同一个 output；先被打包进 block 的那笔把它从 UTXO set 里删掉，后一笔检查第一条时失败。

锁和钥匙：执行一段 P2PKH script

最常见的锁定方式叫 P2PKH（pay to public key hash）。Bob 生成 key pair，把 public key 的 hash 当作 address 给 Alice。Alice 的 output 上的锁定 script 是

OP_DUP OP_HASH160 <pkhashBob> OP_EQUALVERIFY OP_CHECKSIG

Bob 要花它时，在 input 里提供解锁 script <sig> <pkBob>。Script 是一个 stack machine，把两段接起来从左到右执行（stack 写成左边是底、右边是 top）：

步骤 执行 执行后的 stack
1 push <sig> sig
2 push <pkBob> sig, pk
3 OP_DUP：复制 top sig, pk, pk
4 OP_HASH160：把 top 换成它的 hash sig, pk, H(pk)
5 push <pkhashBob> sig, pk, H(pk), pkhashBob
6 OP_EQUALVERIFY：弹出两个，不相等就失败 sig, pk
7 OP_CHECKSIG：弹出 pk 和 sig，验证 sig 是 pk 对这笔 transaction 的 signature 1

第 6 步检查 Bob 给的 public key 确实是 address 对应的那个；第 7 步检查 signature。最后 stack 上是 1，解锁成功。Signature 覆盖了这笔 transaction 的 output，所以 miner 不能偷偷把 output 改成付给自己。

Bitcoin Script 没有 loop，每段 script 的执行步数不超过它的长度，一定会停。这一点在下一站很重要。

Account model：记每个人的状态

Ethereum 的 world state 是一张表：20 byte 的 address 对应一个 account。每个 account 有 balance（单位 Wei，1 Wei=10−181\text{ Wei}=10^{-18}1 Wei=10−18 ETH）和 nonce；contract account 另外还有 code 和 storage。

一笔 transaction 直接说“从 Alice 转 5 ETH 给 Bob”。设 Alice 的 balance 是 7、nonce 是 4，transaction 里写着 nonce 4。执行后 Alice 的 balance 变成 222 减 fee，nonce 变成 5，Bob 加 5。

Nonce 防的是 replay。Account model 里没有“这个 output 已经花掉”的记录，一笔签好的 transaction 被人原样再广播一次，如果没有 nonce，它会再转 5 ETH。有了 nonce，第二次广播时 Alice 的 nonce 已经是 5，transaction 里的 4 对不上，被拒绝。UTXO model 不需要 nonce，因为重放的 transaction 指向的 output 已经不在 UTXO set 里了。

两种 model 的取舍

CS251 用一个例子说明 UTXO model 的局限：一个 wallet 想规定“每天最多转出 2 BTC”。这个 wallet 的钱分散在 100 个 UTXO 上，每个 UTXO 的锁定 script 只能规定花它自己的条件，看不到今天别的 UTXO 已经花了多少。“今天已经转出多少”是一个跨越所有 UTXO 的状态，UTXO model 里没有地方放它。Account model 里，contract 的 storage 里存一个“今天已转出”的数，每次转账检查并更新它就行。

一笔 transaction 跑一整个 program

上一站的结论是：要表达跨 transaction 的规则，ledger 里得有状态，还得有能读写这些状态的 code。Ethereum 让一个 account 可以带 code，叫 contract。一笔发给 contract 的 transaction 会触发它的 code，code 可以读写这个 contract 自己的 storage、转出 ETH、调用别的 contract。每个 validator 都执行同一段 code，得到同一个新的 world state。

Code 用 Solidity 写，编译成 EVM bytecode。EVM 和 Bitcoin Script 一样是 stack machine，但多了 JUMP，可以写 loop。

一个最小的 contract

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract Bank {
    mapping(address => uint256) public balances;

    function deposit() external payable {
        balances[msg.sender] += msg.value;
    }

    function withdraw(uint256 amount) external {
        require(balances[msg.sender] >= amount, "insufficient balance");
        balances[msg.sender] -= amount;                     // effect
        (bool ok, ) = msg.sender.call{value: amount}("");    // interaction
        require(ok, "transfer failed");
    }
}

逐行看 EVM 做了什么。

谁在调用、带了多少钱。 msg.sender 是直接调用这个 contract 的 address，msg.value 是这次调用附带的 Wei。只有标了 payable 的 function 能收 ETH，往 withdraw 里附带 ETH 会被拒绝。

怎样找到要执行的 function。 Transaction 的 data 字段开头 4 个 byte 叫 function selector，是 function signature 的 Keccak-256 hash 的前 4 byte。实算：withdraw(uint256) 的 selector 是 0x2e1a7d4d，deposit() 是 0xd0e30db0。调用 withdraw(1 ether) 的 data 就是 2e1a7d4d 后面跟着把 101810^{18}1018 编码成的 32 byte。编译器生成的 bytecode 开头是一段分派 code，拿这 4 byte 和每个 function 的 selector 比较，跳到对应的位置。

balances 存在哪。 每个 contract 有自己的 storage，是 22562^{256}2256 个 32 byte 的格子，初值全为 0。balances 是第 0 个 state variable，balances[a] 存在第 keccak256(a 补成 32 byte ∥ 0 补成 32 byte)\text{keccak256}(a\text{ 补成 32 byte}\ \|\ 0\text{ 补成 32 byte})keccak256(a 补成 32 byte ∥ 0 补成 32 byte) 号格子里。读写分别是 SLOAD、SSTORE。Storage 是公开的，任何人都能读任何 contract 的任何格子，所以 contract 里不能存密码之类的秘密，标成 private 只是不让别的 contract 通过 code 读取，挡不住人直接读 storage。

require 失败时。 执行 REVERT，这笔 transaction 对 state 的所有改动撤销，到这一步为止消耗的 gas 照付。

Overflow。 Solidity 0.8 起编译器自动检查加减法的 overflow，balances[msg.sender] -= amount 如果会变成负数，直接 revert。上面那行 require 是为了给出可读的错误信息。

为什么要 gas

有了 loop，就有了一个 Bitcoin Script 没有的问题：有人提交一个永不结束的 program，每个 validator 都得执行它，全网卡死。能不能先检查一个 program 会不会停？不能，这是 halting problem，没有 algorithm 能对所有 program 判定。

Ethereum 的办法是不判定，而是收费：每条 instruction 有一个 price，单位叫 gas。发 transaction 时写一个 gasLimit，执行过程中 gas 用完就强行停止，所有改动撤销，但已经用掉的 gas 不退。这样一个死循环最多烧掉发送者自己预付的 gas。每个 block 也有 gas 上限，所以一个 block 的执行时间有上界。这个上限由 validator 投票逐步调整：CS251 Fall 2025 的 slide 写的是 4,500 万（2025 年 7 月起的值），2025 年 11 月 25 日起提高到 6,000 万。下面的算例用 6,000 万。

Price 按 instruction 消耗的资源定。最贵的是永久 storage，因为每个 node 要永远存着它。2021 年的 EIP-2929 又把“一笔 transaction 里第一次碰某个 storage 格子”（cold access）单独收 2,100，因为这一次要从硬盘读。现在的几个数：

把格子清零给退款，是在鼓励大家缩小全网必须保存的 state。CS251 的 slide 上清零的退款写的是 15,000，那是 2021 年 EIP-3529 之前的值。EIP-3529 把它降到 4,800，并规定一笔 transaction 的退款总额最多是 gasUsed 的五分之一，理由是：退款被 GasToken 一类的做法滥用（便宜时占格子，贵时清零拿退款），反而让 state 变大；而且退款使一个 block 实际消耗的 gas 可以接近名义上限的两倍。

先改账再转钱：reentrancy

上面 contract 里 withdraw 先改账、后转钱，顺序是刻意安排的。CS251 的反例是一个先转钱、后改账的版本，一次取出全部 balance：

function withdrawAll() external {
    uint256 amount = balances[msg.sender];
    require(amount > 0);
    (bool ok, ) = msg.sender.call{value: amount}("");   // 先转钱
    require(ok);
    balances[msg.sender] = 0;                           // 后改账
}

看起来对，其实不对先转账后改 balance 也没关系，反正都在同一个 transaction 里，最后结果一样

msg.sender 可以是一个 contract。给 contract 转 ETH 时，EVM 会执行对方的 receive() function，而这段 code 是 attacker 写的。他可以在 receive() 里再次调用 withdrawAll。这时外层那次还没执行到最后一行，balances 还是原来的数，读出来的 amount 还是 75，于是又转一次钱，又触发 receive()……

设 Bank 里原有别人的 300 Wei，attacker 存入 75 Wei，共 375。每一层取 75：第 1 层后剩 300，第 2 层后 225，第 3 层后 150，第 4 层后 75，第 5 层后 0。Attacker 的 receive() 先检查 Bank 还有没有 75，没有了就不再调用，于是各层依次返回，每一层都执行一次 balances[msg.sender] = 0，都不出错。Attacker 存了 75，取走 375。

如果最后一行写成 balances[msg.sender] -= amount，在 Solidity 0.8 下，最里层把 balance 减到 0 之后，外面一层再减 75 就 underflow，整笔 transaction revert，攻击碰巧失败。但这是 overflow 检查顺带挡住的，换一种记账写法就不成立，不能当作防御。

治法是一条写 contract 的纪律，叫 checks-effects-interactions：先检查条件，再改自己的 state，最后才和外部 contract 交互。第一个版本正是这样排的：第二次进入时 balance 已经减掉，require 失败。另一个办法是加一个锁，function 执行期间不允许再次进入。

这不是假想的攻击。The DAO 是 2016 年 4 月众筹起来的一个投资基金 contract，筹到的 ETH 约占当时 ETH 总 supply 的 14%。它的提款 function 正是先转钱、后改 balance。2016 年 6 月 17 日起，attacker 用 reentrancy 抽走约 360 万 ETH，约占 The DAO 资金的 30%。7 月 20 日，Ethereum 在 block 1,920,000 做了 hard fork，直接改写 state，把这些 ETH 退还给原来的投资者。不同意改写历史的人继续运行原来的 chain，这就是 Ethereum Classic。下面说的“部署之后不能改”，在这一次是靠全网换一套规则绕过去的。

Smart contract 不能做什么

不能主动做事。 Contract 只在被 transaction（或被别的 contract）调用时执行。“每月 1 号自动付款”得有人每月 1 号发一笔 transaction 去触发它。

不能读 off-chain 的数据。 每个 validator 都要重新执行同一段 code，并且必须得到完全相同的结果，否则大家对新 state 达不成一致。如果 code 里能发一个 HTTP 请求查 ETH 的 price，不同 validator 在不同时刻查，得到不同的数，consensus 就破了。所以 EVM 的执行必须是 deterministic 的，只能读 on-chain 已有的东西。

Off-chain 的数据要由某人写一笔 transaction 送上 chain，这个角色叫 oracle。问题随之而来：contract 本来不需要信任任何人，现在它的正确性取决于 oracle 送来的数据对不对。这叫 oracle problem。缓和的办法是让多个独立的 oracle 各报一个数、取 median，并对偏离的报价施加 penalty；但它们终究是 off-chain 的人。Blockchain 能保证的是“on-chain 的记录没有被改过”，不能保证“on-chain 的记录和现实相符”。

不能藏秘密，也不能产生真正的随机数。 Storage 和 transaction 都是公开的。block.timestamp 之类的值由 proposer 填写，可以在一定范围内操纵，拿它当随机数，proposer 就能影响结果。

部署之后不能改。 Code 写进链里就固定了，有 bug 也改不了。实际中常用的办法是在前面放一个 proxy contract 转发调用，需要升级时改 proxy 指向的 address，但这等于又引入了一个能改规则的人。

为什么需要 stablecoin

Gensler 在 15.S12 里的出发点是：BTC 和 ETH 的 price volatility 太大，当 store of value 和 unit of account 都不合格，在 crypto 之间来回 trade 时需要一个“停车的地方”；而把钱换回 bank account 要经过 exchange 和 KYC。如果 on-chain 有一个始终值 1 USD 的 token，就能 on-chain 用 USD 计价，第 6 站的 lending 和 AMM 也大多以它计价。CS251 举的另一个用途是 cross-border payment：international wire transfer 约 44 USD，在 Base 这条 chain 上转 USDC 不到 0.01 USD。

难点在于“始终值 1 USD”。Contract 能保证的只有 on-chain 的规则；1 USD 在 off-chain，怎样让 on-chain 的 token 和它挂钩？按回答方式，CS251 把 stablecoin 分成几类，这一站看三种，每种都有一次有记录的失败。

Custodial：off-chain 存 1 USD，on-chain mint 一个

USDC、USDT 是这一类。CS251 的例子：

  1. Bob 把 100 USD 汇给 custodian，custodian 调用 ERC-20 contract 的 mint(Bob, 100)。Alice 汇 35，mint(Alice, 35)。Total supply 135。
  2. Bob 转 15 给 Carol：transfer(Bob → Carol, 15)，这一步 on-chain 完成，不需要 custodian。
  3. Bob redeem 60 USD：custodian 把钱汇给他并调用 burn(Bob, 60)。Supply 变成 75：Alice 35、Bob 25、Carol 15。

Off-chain 的 bank 里的 reserve 始终等于 on-chain 的 supply。

Peg 怎样维持。 大部分持有者不直接和 custodian 打交道，而是在 exchange（secondary market）买卖。能直接 mint 和 redeem 的（primary market）是少数机构。

如果 exchange 里 1 USDC 只卖 0.98，有资格 redeem 的人就买入，拿去 custodian 换 1 USD，每个赚 0.02，买入推高 price。卖 1.02 时就反过来：给 custodian 1 USD mint 一个，拿去卖。只要 redemption 随时可用、大家相信 reserve 足额，price 偏离 1 就有人赚钱，把它推回去。

所以 peg 依赖两个条件：reserve 真的在，并且 redemption 通道开着。

谁能走这条通道。 Ma、Zeng、Zhang 的研究（Review of Financial Studies 待刊）用 Ethereum、Avalanche、Tron 上的 mint 和 redeem 记录数了一下：USDC 平均每月有 521 个 arbitrageur 做 redemption，最大的一个占 45%；USDT 平均每月只有 6 个，最大的一个占 66%。原因在门槛：USDC 允许一般企业注册，USDT 要做很长的 due diligence，对注册地有限制，最低一次 10 万 USD，每次收 0.1% 或 1,000 USD 中较高的那个。按这个费用，在 0.995 买入 10 万个 USDT 去 redeem，毛利是 100000×0.005=500100000\times0.005=500100000×0.005=500 USD，不够付 1,000 USD 的 fee，所以 0.995 这样的偏离不会被 arbitrage 消掉；一次 redeem 10 万时，要毛利超过 1,000，price 得低于 1−1000/100000=0.991-1000/100000=0.991−1000/100000=0.99。他们记录的 secondary market price 也对得上：USDT 的 discount 平均约 54 个 basis point（median 11 个），USDC 平均约 1 个。

这篇文章的核心论点是一个取舍：arbitrage 越容易，平时的 price 越贴近 1；但人人都能快速 redeem 时，reserve 一有风吹草动，redemption 会一下子涌向 issuer，issuer 只能贱卖不那么 liquid 的 reserve，run 的风险反而更高。限制 redemption（收费、设闸门）降低 run 的风险，代价是平时 price 偏离更大。

USDC，2023 年 3 月

下面的时间和数字都来自美联储 2025 年 12 月的一篇 FEDS Note。

看起来对，其实不对有 1:1 reserve 的 stablecoin 不会 depeg

USDC 的 reserve 是 cash 和短期 Treasury bill 一类的 asset，92% 没有受任何影响，它仍然跌到了 0.86。Reserve 足额只保证“最终能拿回多少”，peg 每时每刻成立靠的是 redemption 随时可用，而 redemption 又依赖 banking system 的营业时间和 bank 本身的安全。Gensler 在 2018 年就指出 fiat-backed token 最大的风险在于和 commercial bank 的关系（他的例子是当时规模约 20 亿到 25 亿 USD 的 Tether 曾因 commercial bank 的 account 出问题陷入困境），2023 年的事故是这一点的一次具体实现。

传染。 DAI 不是 custodial 的，但它有一个 Peg Stability Module，允许 USDC 和 DAI 按 1:1 互换，每日上限 9.5 亿。USDC 出事后，大家把 USDC 换成 DAI 出逃，3 月 10 日和 11 日各换进约 10 亿，两天都打满上限。结果 DAI 的 backing 里塞满了 USDC，DAI 跟着 USDC 一起跌。MakerDAO 的紧急提案在两小时内通过，但有 48 小时的生效延迟，等它在 3 月 13 日生效时，风波已经过去。

Crypto-collateralized：用 volatile 的东西支撑稳定的东西

DAI 的本来设计不靠 bank：用户把 ETH 锁进 contract 作 collateral，mint 出 DAI，按 Richmond Fed 的文章，collateral ratio 是 150%。这和第 6 站的 lending 是同一个机制，只不过借出来的是新 mint 的 DAI。ETH 跌，就像 Bob 的 health 跌破 1 一样被 liquidate。

它的代价是 capital efficiency 低：锁价值 150 USD 的 ETH 才能得到 100 个 DAI。它的风险是 collateral 在极短时间内暴跌、liquidation 来不及。2023 年它被 USDC 拖下水，是因为为了维持 peg 又引入了 USDC 这种 custodial 的 collateral。

Algorithmic：UST 与 LUNA

TerraUSD（UST）没有 off-chain 的 reserve。它的机制是一个 contract，允许任何时候用 1 个 UST 换价值 1 USD 的 LUNA（Terra 自己的 token），反之亦然。Richmond Fed 的文章这样解释 peg：

  • UST 跌到 0.98：买入 UST，burn 掉换成价值 1 USD 的 LUNA，卖掉 LUNA，赚 0.02。UST 被买入、被销毁，price 回升。
  • UST 涨到 1.03：花 1 USD 买 LUNA，burn 掉 mint 1 个 UST，卖出赚 0.03。

看起来和 custodial 一样是 arbitrage。区别在于 redeem 换到的东西：custodial 换到 bank 里的 USD，UST 换到的是新 mint 的 LUNA，而 LUNA 的价值本身依赖于大家对 UST 的信心。

边界情况Algorithmic stablecoin 是不是注定失败

这是一个有争议的问题。Richmond Fed 的文章认为 UST 的 backing 是循环的（LUNA 的价值依赖于 UST），一旦信心动摇必然自我加速，稳定的 stablecoin 需要传统形式的 backing，而后者 capital efficiency 低。另一些设计者认为问题出在 UST 的具体参数（靠 subsidy 维持、没有上限的 deposit rate、过小的 reserve），可以用 partial collateral、动态的 redemption 限额等办法改进。两方都同意的是：没有外部 backing 时，peg 最终取决于市场是否相信它。

Money 是哪一本 ledger 上的记录

15.S12 第二讲里，Gensler 问学生 money 的三个经典 function，学生答的是 medium of exchange、unit of account、store of value。然后他把现代的 money 描述成一个 ledger 的层级：central bank 像是 money 的 general ledger，记着各家 commercial bank 的 reserve；美国约 9,000 家 commercial bank 的 ledger 像 subledger，记着客户的 deposit，而它们都改不了最上面那本。Alice 和 Bob 在同一家 bank，转账只改这家 bank 的 ledger；在不同 bank，两家 bank 之间只能在最上面那本 ledger（central bank）上做一次平衡。

BTC 是表里唯一不是任何人 liability 的东西：没有人承诺把它换成别的什么。这正是它不需要信任某个 issuer 的原因，也是它的 price 完全由 supply and demand 决定的原因。

CBDC 是什么，不是什么

CBDC（central bank digital currency）是 central bank 直接 issue 的数字形式的 money。Central bank 本来就有数字的 money：commercial bank 在 central bank 的 reserve 就是。所以问题其实是：要不要把 central bank 的 ledger 开放给更多人。只开放给金融机构，叫 wholesale CBDC；开放给公众，叫 retail CBDC。设计上还有一个维度：account-based（像 bank account，按身份记）还是 token-based（像 cash，按持有记）。

看起来对，其实不对CBDC 就是 central bank 发的 cryptocurrency，必然要用 blockchain

Gensler 在 session 16 明确说 CBDC 不需要 blockchain，最多是受它启发。Central bank 本身就是大家信任的 ledger 维护者，第 1 站里 ScroogeCoin 的那个“问题”在这里不是问题。他举的 Senegal 和 Philippines 的试点，据他所知都没有用 blockchain。CBDC 和 cryptocurrency 的共同点只是“数字的”；在“谁的 liability”“谁维护 ledger”这两个根本问题上，它们恰好相反。

Retail CBDC 的争论

这是一个仍在争论的问题，各国 central bank 的做法也不同。下面把两边的主要论证各自写清楚。

支持的一方。

  • 现金在消失。Gensler 举的 Sweden：cash 占 GDP 的比例从约 4% 降到 2% 以下，而美国和欧洲接近 10%。如果公众手里只剩 commercial bank 的 deposit，就再也没有一种无风险的、由公共部门提供的支付手段。Sweden 的 e-krona 研究就是从这里出发的。
  • 防止支付被私人的 money 主导。ECB 2023 年的金融稳定报告专栏认为，digital euro 可以作为 big tech 支付服务和 stablecoin 之外的选择，让 public money 继续当整个 monetary system 的锚。

担忧的一方。

  • Disintermediation 与 bank run。 Gensler 课上提到 central banker 最担心的是 bank run。如果每个人都能在 central bank 开一个无风险的 account，危机时 deposit 会一键从 commercial bank 搬过去，速度比 2023 年 SVB 那天的 400 亿还快。平时，deposit 流走会让 bank 失去便宜而稳定的资金来源，影响放贷。
  • Credit allocation。 Gensler 把它列为 central bank 的第二个担忧。Central bank 接收了大量 deposit 之后，这些钱借给谁？如果由 central bank 直接借给企业和个人，它就从管理 money 变成了分配 credit。课上有学生认为可以用 interest rate policy 处理，Gensler 则指出 Fed 已经在做一部分这样的事：当时约 4.5 万亿 USD 的 balance sheet 里约 1.5 万亿是 mortgage。
  • Privacy。 Account-based 的 retail CBDC 意味着 central bank 能看到每一笔支付。Gensler 提到 Sweden 表示不会提供完全匿名的 e-money。

一个折中：holding limit。 ECB 的专栏讨论了每人最多持有 3,000 euro 的 digital euro 的方案。它的模拟假设 household 的 overnight deposit 有 5% 到 30% 转成 digital euro；在 3,000 euro 的上限下，即使在“所有人同时采用并立刻存满”这种极不可能的条件下，流出也最多约 15%，而它估计大型 bank 要到约 20% 的 overnight deposit 流出才会面临实质的 liquidity risk。批评者会说，有上限的 CBDC 也就失去了它作为“无风险 store of value”的大部分意义；支持者会说，它本来就只想做支付手段。

BIS 和七家 central bank 2020 年的联合报告没有主张发或不发，只提出前提：issue CBDC 不能损害 monetary stability 和 financial stability，要和现有的 money 共存。

边界情况BTC 能不能当 money

同样是争议问题。按三个 function 检查，批评者指出：price volatility 大，商家几乎不用 BTC 标价，所以它不是 unit of account；同一个理由也让它当 store of value 的可靠性存疑（这和 Gensler 对 crypto 的描述一致）。支持者认为它的 supply cap（第 2 站算出的 2,100 万）和不依赖任何 issuer，使它更像 gold 一类的 store of value，而 store of value 本来就不要求短期 price 稳定。本页不对这个问题下结论，也不构成任何 investment advice。

什么时候需要 blockchain

NUS 课程描述的后半部分是评估 blockchain application 的 business 和 economic performance 与它的技术设计之间的关系。CS251 第一讲的答案最直接：blockchain 提供的是在没有一个可信第三方时的协调；如果有一个大家都信任的第三方，就不需要 blockchain。

15.S12 讲 use case 的那一讲（session 12）把 benefit 归为两种成本的降低，slide 上各列了几项：

  • Verification cost：direct cost、privacy cost、censorship risk、settlement 与 finality risk、trust cost、中介收取的 economic rent。也就是“确认一笔记录真实、已经结算”这件事要付出的各种代价。
  • Networking cost：token 的 incentive（reward、affinity、identity 几种）、launch cost、operating cost。也就是让一个 network 从无到有建起来并维持运转的成本。

同一讲用一张表把三种系统对比：traditional database 由一个受信任的第三方托管，它可以增删改查（CRUD）；permissioned blockchain 的参与者已知、写入权限是私有的，通常仍有一个中心化的中介，通常没有原生 token；permissionless blockchain 的参与者未知、任何人都能写，是只能追加、带时间戳、公开可验证的 log，没有中心化中介，靠 token economics 运转。最后一张 slide 要求设计者回答：为什么用 blockchain 而不是 database；为什么用 public chain 而不是 private chain；如果是 permissionless 的，为什么要对所有人开放、为什么需要一个 token。

用一次：ClearLEth，一个 IS4302 往届项目做的请假审批系统。 它的 README 写的问题是：疫情期间员工很难休完年假；大家同时休假会让公司缺人；雇主可能滥用权力，在需要人手时取消员工已经安排好的假。它给出的方案是把申请和审批放进 Ethereum 上的 contract，信息不经过第三方，员工、雇主和公众都能透明地追踪。对照它的 contract 逐条走一遍：

  1. 谁需要写入？雇主调用 addEmployee、removeEmployee、approveLeave、rejectLeave、setLeaveLimit（每天最多批几个人）；员工调用 applyLeaves、cancelLeave。只有这两方，contract 的部署者另外可以添加 authority。

  2. 有没有一个大家都信任的第三方？雇主本身就维护着 HR 系统，员工的工资、合同都记在那里；员工已经在信任它。

  3. 降低了哪种 verification cost？项目要防的是“雇主取消已批的假”。看 rejectLeave 的检查：

    modifier validLeaveStatus(leave memory leaveApplication) {
    require(leaveApplication.status == leaveStatus.pending, "Leave is not pending");
    _;
}
function rejectLeave(leave memory leaveToReject)
    public validLeaveId(leaveToReject.id) validLeaveStatus(leaveToReject)
    employerOnly(leaveToReject.employee) { ... }

    它检查的 status 是调用者传进来的那个 struct 的字段，不是 storage 里存的那条记录。雇主只要传一个 {id: 一条已批的假, status: pending, employee: 这个员工}，检查就通过，function 随后按 id 找到 storage 里的那条，把它改成 rejected。另外 removeEmployee 会 delete 掉这个员工的全部请假记录。所以按现在的 code，雇主仍然能取消已批的假。Contract 能保证的是“按 code 执行”，code 要防什么，得由写 code 的人做对。

    它真正提供的是另一件事：每次 approve 都 emit 了一个 LeaveApproved event，那笔 transaction 永远留在 chain 上。即使 storage 里的状态被改掉，员工也能指着历史证明“这条假曾经被批过、何时被改掉”。这是第 1 站说的 tamper-evident，不是 tamper-proof。这确实降低了一点 verification cost，但同样的效果用一个雇主无权删除、由外部审计的 append-only log 也能做到。

  4. 降低了哪种 networking cost？没有需要从零建立的 network。

  5. 成本：每次申请和审批都是一笔付 gas 的 transaction；员工需要 wallet；请假的 reason 以 bytes32 存在 public chain 上，第 5 站说过 storage 人人可读，病假的理由也就公开了。

按这个框架，一个 database 加一份外部可审计的 log 更合适。如果问题变成“多家互不隶属的雇主共享一份工作经历记录，没有谁愿意让对手托管”，第 2 条的答案就变了，blockchain 才开始有理由。

再用一次：用 USDC 做 cross-border payment。

  1. 有没有可信第三方？传统 wire transfer 有，代价是 CS251 记录的约 44 USD fee 和几天时间。
  2. 降低了哪种 verification cost？On-chain 转账几分钟内确认，不经过代理行，CS251 记录的成本不到 0.01 USD。
  3. 没有消失的成本：两端都要把法币换进换出（on-ramp 和 off-ramp），要过 KYC；USDC 的 issuer 是一个能冻结 account 的 Scrooge；peg 本身有风险（第 7 站）。

评估结果取决于两端换汇的成本和对 issuer 的信任，而不只是 on-chain 那一步。这正是课程描述说的“经济表现与技术设计的关系”：on-chain 那一步便宜，是 public chain 的设计带来的；整个链条是否便宜，取决于 chain 和现实世界的接口。
